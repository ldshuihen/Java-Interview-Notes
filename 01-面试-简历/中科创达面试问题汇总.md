### 1. 如何在Java代码中引入第三方包？

主要依靠**依赖管理工具**：

1. **Maven**：在`pom.xml`中编写`<dependency>`坐标，Maven自动从中央仓库下载、传递依赖；
2. **Gradle**：在build.gradle中dependencies块引入；
3. 原始方式：手动下载jar包，添加到项目lib目录并添加到类路径（不推荐，依赖冲突难管理）。> 
> 补充：Maven有依赖传递、依赖排除、版本锁定、scope控制依赖生效范围。

### 2. 深入谈谈 ConcurrentHashMap 的实现原理（JDK8）

JDK8抛弃分段锁Segment，采用 **CAS + synchronized + Node + 数组+链表+红黑树**：

- 底层：Node数组，hash冲突形成链表，链表长度≥8、数组长度≥64时转为红黑树；
- 并发控制：**头节点加synchronized锁**，配合CAS做无锁尝试；
- put流程：
  1. 计算hash定位桶下标；
  2. 桶为空：CAS插入Node；
  3. 桶头节点不为空：锁住头节点，遍历链表/红黑树插入；
  4. 达到阈值触发扩容；
- 扩容：多线程协助扩容（transfer），提高迁移效率；
- 注意：**不是全方法线程安全**，组合操作（如`if(containsKey) put`）依然需要额外加锁。

### 3. Java线程池的原理、核心参数、工作流程

七大核心参数：
`corePoolSize`核心线程数、`maximumPoolSize`最大线程数、`keepAliveTime`非核心空闲存活时间、`unit`时间单位、`workQueue`阻塞队列、`threadFactory`线程工厂、`handler`拒绝策略。
工作流程：

1. 提交任务，当前线程数 < 核心线程数 → 创建核心线程执行；
2. 核心线程满了 → 任务放入阻塞队列；
3. 队列也满了 → 创建非核心线程；
4. 线程总数达到最大线程数 → 触发拒绝策略（Abort、Discard、DiscardOldest、CallerRuns）。
原理：复用线程，避免频繁创建销毁线程开销，控制并发数量，防止OOM。

### 4. HashMap 和 LinkedHashMap 区别

- **HashMap**：底层数组+链表+红黑树；**无序**；只维护hash桶；适合查询为主、不关心顺序场景。
- **LinkedHashMap**：继承HashMap，额外维护**双向链表**；默认插入顺序，开启accessOrder=true时为访问顺序（LRU缓存底层就是它）；额外维护链表会有少量内存开销。

### 5. ThreadLocal是什么？使用注意事项

ThreadLocal：**线程本地变量**，每个Thread内部维护一个ThreadLocalMap，key是ThreadLocal对象，value是存储的值，线程之间数据隔离。
⚠️ 注意点：

1. **内存泄漏**：key是弱引用，value是强引用；线程长期存活（线程池）时value无法回收，必须手动`remove()`；
2. 不能用来做线程共享；
3. 子线程拿不到父线程ThreadLocal的值（需要InheritableThreadLocal）；
4. 线程池场景下，复用线程前一定要清理，防止脏数据串线程。

### 6. 线程有什么状态（Java 6种）

`NEW`新建 → `RUNNABLE`可运行（就绪+运行中） → `BLOCKED`阻塞（等待synchronized锁） → `WAITING`无限等待（wait()/join()） → `TIMED_WAITING`限时等待（sleep、wait(time)） → `TERMINATED`终止。

> 
> 重点区分：BLOCKED是等锁，WAITING是主动等待唤醒。

### 7. 线程调用start()方法会怎么样？

- `start()`：向JVM申请创建操作系统线程，把线程状态置为RUNNABLE，由操作系统调度，**自动执行run()**；只能调用一次，重复调用抛`IllegalThreadStateException`。
- 对比：直接调用`run()`只是普通方法调用，不会开启新线程，在当前线程串行执行。

### 8. 方法重载Overload 和 重写Override

- **重载（Overload）**：同一个类中，方法名相同，**参数列表不同（个数/类型/顺序）**；返回值、修饰符不参与判定；编译期静态绑定。
- **重写（Override）**：父子类之间，方法名、参数列表、返回值（协变返回）完全一致；子类重写父类方法；父类不能是private；子类权限不能比父类更严格；运行期动态绑定（多态）。

### 9. Java多态怎么表现

多态三前提：**继承/实现 + 方法重写 + 父类引用指向子类对象**
表现形式：

1. 父类引用接收子类实例，调用重写方法时，执行的是子类逻辑；
2. 接口指向实现类；> 
> 口诀：**编译看左边，运行看右边**；成员变量不具备多态。

### 10. ArrayList扩容机制 & 性能损耗点

- 默认初始容量10；
- 扩容规则：`newCapacity = oldCapacity + oldCapacity >> 1` → 1.5倍扩容；
- 扩容步骤：判断容量不足 → new新数组 → `Arrays.copyOf`复制全部元素到新数组；
损耗点：

1. 数组拷贝：大量元素复制，CPU开销；
2. 新数组开辟堆内存，GC压力；
3. 频繁add触发多次扩容，建议预估容量，用`new ArrayList(initialCapacity)`指定初始容量。> 
> 底层是Object[]数组，允许null，查询快，中间插入删除慢（需要移动元素）。

### 11. Java主要特性 + 重点说明

主要特性：面向对象、跨平台（JVM）、自动垃圾回收、泛型、异常机制、多线程、丰富类库、字节码。
示例重点讲**GC垃圾回收**：
Java不用手动malloc/free，JVM自动识别不再被引用的对象，回收堆内存；区分可达性分析、分代收集、GC算法；避免C/C++野指针、内存泄漏问题，但不是完全没有内存泄漏。

### 12. 反射机制理解 + 项目场景

反射：在**运行时**获取类的信息（Class对象），动态创建对象、调用方法、读写属性，突破访问权限。
底层：Class对象，类加载时生成。
项目场景：

1. Spring IOC：通过反射实例化Bean；
2. ORM框架（MyBatis）：反射setter给实体类赋值；
3. 序列化/反序列化（Jackson）；
4. 工具类：通用对象拷贝；
缺点：性能比直接调用慢，破坏封装，关闭权限检查。

### 13. 集合框架理解 + 怎么选型

两大根接口：`Collection`（单列）、`Map`（键值对）

- Collection：
  - List：有序可重复 → ArrayList（随机查）、LinkedList（头尾增删）；
  - Set：不可重复 → HashSet（无序）、TreeSet（有序，红黑树）、LinkedHashSet（插入有序）
- Map：键不可重复 → HashMap、LinkedHashMap、TreeMap、ConcurrentHashMap
选型思路：

1. 是否需要线程安全：并发优先ConcurrentHashMap，单线程HashMap；
2. 是否要顺序：LinkedHashMap、TreeMap；
3. 查询多还是增删多：ArrayList查询快，LinkedList头尾增删快；
4. 是否排序：Tree系列（Comparator）。

### 14. HashMap 和 Hashtable区别

1. 线程安全：Hashtable方法加`synchronized`，线程安全，并发性能差；HashMap不安全；
2. null：HashMap允许一个key为null，多个value为null；Hashtable不允许key/value为null；
3. 继承：Hashtable继承Dictionary，HashMap继承AbstractMap；
4. 扩容：Hashtable默认容量11，扩容2倍+1；HashMap默认16，扩容1.5倍；
5. 推荐：并发场景用ConcurrentHashMap，**不要用Hashtable**。

### 15. try-catch-finally执行机制，finally什么时候不执行

执行顺序：try正常执行 → 有异常跳到catch → **finally一定会执行（绝大多数情况）**，return也会先执行finally；
finally不执行的场景：

1. `System.exit()`退出JVM；
2. 线程被直接kill；
3. 发生宕机、断电等底层系统故障。> 
> 坑点：finally里写return会覆盖try/catch的返回值，开发禁止在finally return。

### 16. Java创建线程的4种方式

1. 继承Thread类，重写run()；
2. 实现Runnable接口，传给Thread；
3. 实现Callable + FutureTask（可以有返回值、抛异常）；
4. 线程池Executors/ThreadPoolExecutor（生产推荐）；
推荐：优先Runnable/线程池，避免单继承限制，线程池控制资源。

static表示属于**类本身**，所有对象共享同一份，存储在方法区；static只是归属修饰，不是只读。
如果是 `static final` → 常量，不能修改。

### 20. 什么是线程安全？线程不安全例子

多个线程**同时访问同一个共享资源**时，程序的执行结果和预期一致，不会出现数据错乱、丢失、脏读，就是线程安全。 

核心判断：**多线程并发，不加额外同步手段，结果依然正确 → 线程安全**。

本质：共享可变资源在并发下缺少保护，出现原子性、可见性、有序性问题。

#### 线程不安全典型例子

##### 例子1：计数器自增（最常考）

```
int count = 0;
// 多个线程同时执行 count++
count++;
```

`count++` 不是原子操作，分为三步：

1. 读取 count
2. +1
3. 写回 count

两个线程同时读到 count=0，各自+1后写回，最后结果变成1，预期应该是2 → **计数丢失**。

##### 例子2：HashMap并发put

多线程同时put，JDK8之前会形成链表环，CPU100%；JDK8不会死循环，但会出现数据覆盖、丢失。HashMap是典型线程不安全集合。

##### 例子3：SimpleDateFormat

```
SimpleDateFormat sdf = new SimpleDateFormat("yyyy-MM-dd");
// 多个线程共用同一个sdf对象做parse/format
```

内部有共享的Calendar变量，并发调用会时间解析错乱。生产一般用 ThreadLocal 或者 DateTimeFormatter（线程安全）。

##### 例子4：ArrayList 并发 add

多线程同时add，数组扩容、赋值竞争，可能出现数组越界、元素丢失。

#### 对比几个常考集合

- 不安全：`ArrayList、LinkedList、HashMap、HashSet、StringBuilder`
- 安全：`Vector、Hashtable、ConcurrentHashMap、StringBuffer`

#### 补充一句话回答（面试口述精简版）

线程安全指多个线程并发访问共享资源，不需要额外同步，程序结果依旧符合预期。 典型线程不安全例子：多个线程同时执行 `count++` 计数丢失；多线程共用同一个 `HashMap` 插入数据；多线程共用 `SimpleDateFormat` 做日期解析。

## Java21-40

### 21. Java重载和重写的区别

- **重载 Overload**：同一个类内，方法名相同，参数列表不同（参数个数、类型、顺序）；返回值、访问修饰符不参与判断；**编译期静态绑定**；属于同一个类方法多样化。
- **重写 Override**：发生在父子类/实现类与接口之间；方法名、参数列表、返回值（支持协变返回类型）一致；子类方法权限不能比父类更严格，父类不能是private；**运行期动态绑定**；是多态的基础。

### 22. Java集合框架整体结构 + 集合选型

两大顶层根接口：

1. `Collection`：单列集合，存单个元素
   - `List`：有序、可重复，有索引：ArrayList、LinkedList、Vector
   - `Set`：无序（部分有序）、不可重复：HashSet、LinkedHashSet、TreeSet
   - `Queue`：队列，FIFO：ArrayDeque、PriorityQueue
2. `Map`：双列集合，key-value键值对，key唯一：HashMap、LinkedHashMap、TreeMap、ConcurrentHashMap

选型：

- 需要索引、随机查询：ArrayList
- 频繁头尾增删：LinkedList / ArrayDeque
- 去重：HashSet；需要排序：TreeSet；保留插入顺序：LinkedHashSet
- 键值查询、单线程：HashMap；并发：ConcurrentHashMap；需要有序：TreeMap

### 23. Java快速失败（fail-fast）是什么

快速失败是**迭代器的保护机制**：集合迭代过程中，如果其他线程（或当前线程）通过集合add/remove修改了集合结构，迭代器会立刻抛出`ConcurrentModificationException`，而不是继续遍历拿到脏数据。
原理：集合维护`modCount`修改计数，迭代器记录`expectedModCount`；每次迭代前对比两者，不一致直接抛异常。

> 
> ❗注意：它只是一种**风险预警**，不是线程安全方案；`CopyOnWriteArrayList`是fail-safe（安全失败），拷贝一份数组遍历，不会抛异常，但有数据弱一致性。

### 24. 单例模式实现（举例 + 线程安全）

单例：保证一个类在全局只有一个实例，提供全局访问点。

1. **饿汉式（线程安全，简单）**

```
public class Singleton {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton(){}
    public static Singleton getInstance(){
        return INSTANCE;
    }
}
```

类加载时直接初始化，不会有并发问题；缺点类加载就创建，不用也占用内存。

2. **双重检查锁 DCL（懒加载，生产常用）**

```
public class Singleton {
    private static volatile Singleton instance;
    private Singleton(){}
    public static Singleton getInstance(){
        if(instance == null){
            synchronized (Singleton.class){
                if(instance == null){
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

`volatile`禁止指令重排，防止半初始化对象被其他线程拿到。

3. 静态内部类：懒加载、线程安全，推荐

```
public class Singleton {
    private Singleton(){}
    private static class Holder{
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance(){
        return Holder.INSTANCE;
    }
}
```

4. 枚举单例：防止反射、序列化破坏，最安全

### 25. Lambda表达式写法 + 示例

Lambda用来简化**函数式接口**（只有一个抽象方法的接口）写法；格式：`(参数列表) -> {方法体}`

- 参数类型可省略；只有一个参数括号可省；单行return可省略{}和return
示例：

```
// 普通写法
Runnable r1 = () -> System.out.println("lambda run");
new Thread(r1).start();

// stream示例
List<String> list = Arrays.asList("a","b");
list.stream().filter(s -> s.equals("a")).forEach(System.out::println);
```

### 26. String是基本类型还是引用类型？

**String是引用类型**，底层是char数组（JDK9+换成byte[] + 编码标记），继承Object。
和基本类型区别：

1. 基本类型（int/boolean等）存栈上，是值；String对象存在堆，栈存引用；
2. String不可变（final修饰char数组），每次拼接都会生成新字符串；
3. 有常量池优化，`"abc"`字面量会复用池内对象；new String一定会在堆新建对象。

### 27. ArrayList 和 Array（数组）性能对比

**数组Array性能更好**
理由：

1. Array是原生结构，连续内存，没有扩容、额外封装开销；长度固定；
2. ArrayList底层就是封装了Array；自动扩容时需要`Arrays.copyOf`拷贝数组，有CPU和内存开销；
3. ArrayList支持动态扩容、提供丰富API，开发方便，但有轻微封装损耗；
✅ 选型：长度提前固定 → 原生数组；长度不确定、需要增删API → ArrayList

### 28. HashMap基本实现原理（JDK8）

底层：数组 + 链表 + 红黑树

1. key计算hash，扰动函数优化hash，取模定位桶下标；
2. 桶为空：直接放入；
3. 桶不为空：hash相等且equals相等 → 覆盖；否则形成链表；
4. 链表长度≥8，并且数组长度≥64 → 链表转红黑树；红黑树节点少于6退化成链表；
5. 负载因子默认0.75，达到阈值触发扩容，扩容为原来2倍；
6. 线程不安全，并发put会丢数据。

### 29. List、Set、Map特点&适用场景

- **List**：有序、允许重复元素，有索引；适合需要按位置访问、允许重复；例：日志列表、分页数据；实现：ArrayList、LinkedList
- **Set**：不允许重复，大多无序（TreeSet有序）；适合去重场景；实现：HashSet、TreeSet
- **Map**：key唯一，key-value映射；适合根据key快速查找；实现：HashMap、TreeMap、ConcurrentHashMap

### 30. 面向对象编程理解

四大核心：**封装、继承、多态、抽象**

1. 封装：把属性和方法包装在类里，控制访问权限，隐藏内部实现，对外暴露接口，降低耦合；
2. 继承：子类复用父类代码，实现代码复用；Java单继承；
3. 多态：父类引用指向子类对象，运行时执行子类逻辑；提高扩展性；
4. 抽象：抽象类、接口，定义规范，不关心具体实现；
面向对象思想：把事物抽象成类，以对象为单位组织代码，相比面向过程更适合大型复杂业务，易维护、易扩展。

### 31. Set接口主要方法 + 特点

特点：元素不重复；HashSet无序，TreeSet自然排序，LinkedHashSet插入有序。
常用方法：
`add(E e)` 添加元素；`remove(Object o)` 删除；`contains(Object o)` 判断是否存在；`size()`；`isEmpty()`；`clear()`；`iterator()`；`addAll()`、`retainAll()`交集、`removeAll()`差集。
去重判断逻辑：先判断hashCode，hash相等再用equals判断。

### 32. Java常用基本数据结构，分类

1. 数组：Array、ArrayList；随机访问快，中间插入删除慢
2. 链表：LinkedList（双向链表）；头尾增删快，随机查找慢
3. 栈：Stack、ArrayDeque；后进先出LIFO
4. 队列：Queue，ArrayDeque、LinkedList；先进先出FIFO；优先队列PriorityQueue（堆）
5. 哈希表：HashMap、HashSet；O(1)查询
6. 树：TreeSet、TreeMap（红黑树）；有序查找

### 33. 接口和抽象类的区别&关系

相同点：都不能实例化，都可以定义抽象方法，用来做规范。
区别：

1. 抽象类用`abstract class`；接口JDK8前`interface`；JDK8+接口支持default/static方法，JDK9支持private；
2. 类只能**单继承抽象类**；一个类可以**多实现接口**；
3. 抽象类可以有构造器、实例变量；接口不能有实例变量，默认public static final常量；
4. 设计角度：抽象类是**模板复用（is-a）**；接口是**能力契约（can-do）**。

### 34. 集合常用接口&实现类、场景

- List接口
  - ArrayList：数组实现，随机访问快，查询多优先
  - LinkedList：双向链表，头尾频繁增删
- Set接口
  - HashSet：哈希表，快速去重，无序
  - TreeSet：红黑树，自动排序
  - LinkedHashSet：哈希+双向链表，保留插入顺序
- Map接口
  - HashMap：单线程，高性能查询
  - TreeMap：key有序

  - ConcurrentHashMap：高并发场景

### 35. 创建多线程两种方式 + 优缺点（Runnable / Thread）

1. 继承Thread类，重写run()
优点：写法简单；缺点：Java单继承，占用继承名额，无法再继承其他类；多个线程之间不方便共享资源。
2. 实现Runnable接口，传入Thread构造
优点：避免单继承限制，多个线程可以共用同一个Runnable对象，方便共享资源；推荐写法。> 
> 补充：Callable带返回值、线程池是生产推荐方案。

### 36. StringBuffer 和 StringBuilder区别

底层都是可变char数组，支持append拼接；

1. StringBuffer：所有方法加`synchronized`，**线程安全**，并发场景可用；锁带来性能开销；
2. StringBuilder：无锁，**线程不安全**，性能更高；单线程拼接优先使用；
总结：单线程优先StringBuilder；多线程共享拼接才用StringBuffer。

### 37. HashMap底层原理（JDK8，深度版）

底层：Node数组 `Node<K,V>[] table`，每个Node存hash、key、value、next指针。

1. hash计算：`(h = key.hashCode()) ^ (h >>> 16)` 扰动函数，高低位混合，减少hash冲突；
2. 寻址：`(table.length - 1) & hash`；
3. put流程：
   - 空数组先扩容初始化；
   - 定位桶，桶为空直接新建Node；
   - 桶头节点key相等 → 覆盖；
   - 是红黑树节点 → 走红黑树插入；
   - 链表遍历到尾插入，同时判断链表长度；
   - 链表≥8，数组长度≥64 → 树化；
4. 扩容：负载因子0.75，threshold=容量*0.75；扩容2倍；rehash利用高位bit判断新下标；
5. get：hash定位桶，依次对比key，找到返回value。

### 38. 线程池核心线程、最大线程怎么设置？

分两类场景：

1. **CPU密集型（计算多，少IO）**：核心线程数 ≈ CPU核心数 + 1；避免频繁上下文切换；
2. **IO密集型（数据库、RPC、网络等待）**：核心线程数 > CPU核心数；公式：`核心数 = CPU核心 * (1 + IO等待时间 / CPU计算时间)`；一般设置2~4倍CPU核数；
最大线程数：根据服务峰值、机器内存、下游限流来设置，防止打爆下游或者OOM；队列不要设置无界队列（容易OOM）。> 
> 注意：这只是参考公式，最终要压测调优。

### 39. HashMap实现原理：存储结构、put/get、扩容（同37题，精简口述版）

存储结构：数组+链表+红黑树；
put：hash扰动定位桶，空桶直接放；key相同覆盖；链表尾部追加；达到阈值树化；
get：hash定位桶，依次比对key（先hash再equals）；链表/红黑树查找；
扩容：负载因子0.75，容量翻倍；迁移节点，利用高位bit分到新桶原桶；扩容开销大，预估容量可以提前指定initialCapacity。

### 40. 进程和线程的区别、关系

- **进程**：操作系统资源分配最小单位；进程有独立内存空间、文件句柄；进程之间隔离，通信成本高；
- **线程**：CPU调度执行最小单位；线程属于进程，一个进程至少一个主线程；同一个进程内多个线程共享堆、方法区资源，只独有栈、程序计数器；线程切换开销远小于进程；
一句话：**进程是资源容器，线程是执行单元；进程包含线程**。

### 48. try-catch-finally执行逻辑、finally不执行场景

1. 代码执行 `System.exit()` 退出JVM；
2. 操作系统杀死进程、断电、机器宕机；
3. try内无限死循环，永远走不到finally；
禁止在finally块写return，会覆盖try/catch的返回值，隐藏异常。

### 50. ConcurrentHashMap 和 Hashtable区别

1. 锁粒度：Hashtable是对整个table加`synchronized`，锁粒度大；JDK8 CHM是桶头节点synchronized + CAS，锁粒度小；

### 52. synchronized 和 volatile区别

1. volatile：只保证**可见性、禁止指令重排**；不保证原子性；适合状态标记（boolean开关）；
2. synchronized：保证可见性、原子性、有序性；是排他锁，保证同一时间只有一个线程执行同步代码块；可以修饰方法、代码块；
一句话总结：volatile是轻量同步，解决可见性；synchronized是锁，解决原子性+可见性。

### 53. Java常用锁机制及适用场景

2. ReentrantLock：可重入互斥锁，API层面；支持公平/非公平、可中断、超时tryLock、条件变量Condition；灵活，复杂并发控制；
3. ReadWriteLock读写锁：读共享、写排他；读多写少场景（缓存）；
4. StampedLock：乐观读锁，比读写锁更快；读多写少高并发；
5. 原子类CAS无锁：AtomicInteger、LongAdder；计数场景；
6. 分布式锁（Redisson）：跨JVM多实例并发控制。

### 61. G1垃圾回收器执行流程；标记为1代表存活，回收时是全部一起回收吗？

G1把堆划分成多个大小相等的Region，分为Eden、Survivor、Old、Humongous大对象区；**不是全堆一起回收，是增量式、按区域回收**，优先回收收益最高（垃圾最多）的Region。
G1四大阶段：

1. **初始标记（STW）**：标记GC Roots直接可达对象，速度快；
2. **并发标记**：和用户线程并行，从初始标记对象遍历整个对象图，找出存活对象；
3. **最终标记（STW）**：处理并发阶段用户线程新产生的引用变化（SATB快照）；
4. **筛选回收（STW）**：统计各个Region的垃圾占比，挑选价值最高的若干Region，复制存活对象到新Region，清空旧Region。> 
> 标记位1代表存活；G1是部分回收，只选收益高的区域做复制清理，不是整堆回收，以此控制停顿时间。

### 62. String、StringBuilder、StringBuffer区别

- **String**：不可变，final char数组（JDK9 byte[]）；每次拼接生成新对象；适合少量字符串、常量池复用；
- **StringBuffer**：可变字符数组；方法加`synchronized`，线程安全；并发拼接场景，性能差；
- **StringBuilder**：可变字符数组；无锁，线程不安全；单线程字符串拼接优先选它，性能最好。

### 66. 项目里线程池最大线程数怎么设计，为什么

举后端业务通用回答（贴合你的微服务项目）：
我的项目大多是IO密集型，大量DB、RPC调用；
核心线程一般设置为CPU核数的2倍，最大线程设置为CPU核数的4倍；

### 69. 线程池四大拒绝策略、优缺点

1. **AbortPolicy（默认）**：直接抛RejectedExecutionException；优点：快速失败，及时发现问题；缺点：任务丢失；
2. **DiscardPolicy**：默默丢弃任务，不抛异常；优点：不报错；缺点：悄无声息丢任务，风险大；
3. **DiscardOldestPolicy**：丢掉队列最老任务，再尝试提交；优点：优先处理新任务；缺点：老任务丢失；
4. **CallerRunsPolicy**：交给调用者线程执行；优点：不会丢任务，天然限流；缺点：阻塞提交线程，拖慢上游。

### 70. 强引用、软引用、弱引用、虚引用区别&场景

1. **强引用**：Object obj = new Object(); GC时只要有强引用就不会回收；日常代码默认；
2. **软引用 SoftReference**：内存不足OOM前才回收；适合缓存（图片缓存）；
3. **弱引用 WeakReference**：下一次GC一定会回收，不管内存够不够；适合和Map搭配做缓存（WeakHashMap）；
4. **虚引用 PhantomReference**：最弱，get拿不到对象；仅用来接收回收通知，配合Cleaner做堆外内存释放。

### 81. 双亲委派模型及其作用

#### 双亲委派模型（Java类加载）

##### 定义

双亲委派是**ClassLoader类加载器**的一套加载规则： 当一个类加载器收到类加载请求时，**先把请求委派给父加载器去加载**，父加载器继续向上委派，直到顶层的启动类加载器；只有父加载器加载失败（找不到该类），当前加载器才尝试自己加载这个类。

> 加载器层级（从上到下）： 启动类加载器（Bootstrap ClassLoader，C++实现，加载`rt.jar`等核心类） → 扩展类加载器（Extension ClassLoader，加载jre/lib/ext） → 应用程序类加载器（AppClassLoader，加载classpath下我们自己写的代码） → 自定义类加载器

⚠️ 注意：**不是继承关系，是组合委派关系**，子类加载器内部持有parent引用。

##### 核心作用

1. **防止核心类被篡改（安全）** 比如 `java.lang.String`，无论你自己写一个同名类，都会向上委派到启动类加载器加载原生String，不会加载你自定义的，避免替换JDK核心类。
2. **保证类的全局唯一性** 同一个全限定类名，只会被同一个加载器加载一次，避免重复加载、出现多个版本的同名类。
3. **类隔离、划分加载范围** 不同加载器负责不同路径的类，职责清晰。

#### 破坏双亲委派 

> 前置回顾：双亲委派默认逻辑：**先向上委托父加载器，父加载不到，自己加载**。 破坏 = 不遵守这个顺序，优先自己加载 / 反向委派。 双亲委派的入口是 `ClassLoader#loadClass()`，默认实现就是双亲委派逻辑。

##### 一、三种破坏场景拆解

###### 1️⃣ SPI：JDBC驱动（最常问，JDK原生SPI）

背景：

- `java.sql.Driver` 这个接口，由 **启动类加载器 BootstrapClassLoader** 加载（rt.jar）
- 但是 `com.mysql.cj.jdbc.Driver` 驱动实现类，在我们引入的mysql依赖包，classpath下，**只能由AppClassLoader加载**
- 按照双亲委派：Bootstrap 是顶层，它的parent是null；Bootstrap想加载驱动实现类，它找不到classpath下的类，又没有子加载器可以委派，直接卡住。

👉 解决方案：**线程上下文类加载器 TCCL `Thread.getContextClassLoader()`**

- 线程上下文类加载器默认就是AppClassLoader
- SPI在核心包里面，拿到当前线程的上下文类加载器，**反向委派，向下委托子类加载器去加载实现类**
- 正常是子→父；这里是父加载器 → 拿到子加载器去加载类，反向，打破双亲委派。

> 一句话总结：**父加载器需要调用子类加载器加载类，靠TCCL实现反向委派** 坑点：很多人说TCCL就是子加载器，不对，它是存在Thread里的一个ClassLoader引用，可以自定义。

###### 2️⃣ Tomcat 的 WebAppClassLoader（容器场景）

需求目标： 多个web应用部署在同一个Tomcat里，**包隔离**。 比如：A应用spring5，B应用spring6；两个应用要各自加载自己版本的spring，不能共用。 如果遵守双亲委派：会向上委托到AppClassLoader，只会加载一份，冲突。

Tomcat自定义 `WebAppClassLoader`，加载顺序改成：

1. **优先加载当前WEB-INF/classes、WEB-INF/lib下面自己的类**（自己先尝试加载）

2. 再委派给父加载器（CommonClassLoader等）

   > 和双亲委派顺序反过来，**先自己，后父**，打破委派。

额外补充： Tomcat还做了隔离：

- Common：公共包
- Catalina：tomcat自身类
- Shared：多个web共享
- WebApp：每个应用独立

> 注意：Tomcat不会破坏JDK核心类加载，`java.lang.*` 还是交给Bootstrap，防止篡改核心类。

###### 3️⃣ 自定义ClassLoader，重写 loadClass()

双亲委派逻辑写在 `ClassLoader#loadClass()` 里。

- 如果你不重写loadClass，只重写 `findClass()`：**仍然遵守双亲委派**（推荐写法）
- 如果你重写 `loadClass()`，改掉里面先委托parent的逻辑，就可以完全自定义加载顺序，主动破坏双亲委派。

典型场景：加密class、热部署、自定义class来源（网络读取字节码）。

### 93. 手写简易线程池 + 原理说明

核心组成：任务队列、工作线程集合、核心状态标识、锁/条件变量。

```
import java.util.LinkedList;
import java.util.Queue;

public class SimpleThreadPool {
    private final Queue<Runnable> taskQueue = new LinkedList<>();
    private final Thread[] workers;
    private volatile boolean isRunning = true;

    public SimpleThreadPool(int threadNum) {
        workers = new Thread[threadNum];
        for (int i = 0; i < threadNum; i++) {
            workers[i] = new Thread(() -> {
                while (isRunning) {
                    Runnable task;
                    synchronized (taskQueue) {
                        while (taskQueue.isEmpty()) {
                            try {
                                taskQueue.wait();
                            } catch (InterruptedException e) {
                                Thread.currentThread().interrupt();
                                return;
                            }
                        }
                        task = taskQueue.poll();
                    }
                    task.run();
                }
            });
            workers[i].start();
        }
    }

    public void submit(Runnable task) {
        synchronized (taskQueue) {
            taskQueue.offer(task);
            taskQueue.notify();
        }
    }

    public void shutdown() {
        isRunning = false;
        synchronized (taskQueue) {
            taskQueue.notifyAll();
        }
    }
}
```

原理：提前启动一批工作线程；提交任务放入队列，notify唤醒线程；线程循环阻塞取任务执行；shutdown关闭标记。

> 
> 简易版缺少拒绝策略、超时、非核心线程回收等能力。

集合底层依托数组、链表、红黑树；大部分非线程安全；迭代器有fail-fast快速失败机制。

### 95. 进程和线程区别、关系

- 进程：操作系统资源分配最小单位，独立内存空间，进程之间隔离；
- 线程：进程内调度执行最小单位，共享进程堆、方法区；每个线程有独立栈、程序计数器；
关系：一个进程至少有一个主线程；线程不能独立存在；进程挂了，里面所有线程全部销毁。

### 97. Java原子操作怎么实现

两种路线：

1. **CAS无锁**：AtomicInteger、LongAdder底层，依赖Unsafe调用CPU硬件指令cmpxchg；比较并交换，失败自旋重试；适合轻量计数；
2. **锁实现**：synchronized、ReentrantLock，排他锁保证复合操作原子性；适合逻辑复杂、竞争激烈场景。

### 98. 线程池使用方式，Executors默认线程池风险

使用方式：优先`new ThreadPoolExecutor`自定义参数；尽量不使用Executors。
Executors风险：

- newFixedThreadPool：无界队列，任务堆积OOM；
- newSingleThreadExecutor：无界队列；
- newCachedThreadPool：最大线程无上限，任务突增会创建大量线程，耗尽CPU和内存；

### 99. ArrayList 和 LinkedList异同、选型

相同：都实现List接口，有序可重复；
不同：

- ArrayList：动态数组；随机访问O(1)；中间插入删除要移动元素；
- LinkedList：双向链表；随机查找O(n)；首尾增删O(1)；
选型：查询多、随机访问优先ArrayList；频繁头尾增删、队列场景选LinkedList。

### 100. GC算法 + 常用回收器

基础算法：

1. 标记清除：标记垃圾，统一清除；产生内存碎片；
2. 标记复制：存活对象复制到新区域，无碎片；浪费一半空间；适合新生代；
3. 标记整理：标记存活，向一端压缩整理；无碎片；移动对象开销大；适合老年代；

常用回收器：

- Serial：单线程，客户端、小内存；
- Parallel：多线程吞吐量优先；
- CMS：并发标记清除，低停顿；容易碎片；JDK8默认老年代；
- G1：分Region，可预测停顿，标记复制+整理；JDK9默认；
- ZGC、Shenandoah：超低停顿，大堆场景。

### 102. Java构造函数分类及其作用

构造方法名和类名一致，没有返回值；

1. **无参构造**：默认提供，不写编译器自动生成；用于实例化，给成员赋默认值；一旦手写有参构造，默认无参构造消失；

### 103. synchronized 和 Lock 的区别

1. 来源：synchronized 是JVM层面关键字；Lock是API层面接口（ReentrantLock）
2. 释放锁：synchronized 自动释放（正常退出/异常）；Lock必须手动unlock()，一般放在finally
3. 可中断：synchronized 不可中断；lockInterruptibly()支持中断等待
4. 公平锁：synchronized 只能非公平；ReentrantLock支持公平/非公平切换
5. 条件队列：Lock可以多个Condition；synchronized只有一个wait集合
6. 锁升级：synchronized偏向锁→轻量级锁→重量级锁；Lock底层AQS
7. 性能：JDK6后synchronized优化很好，差距不大；
选型：简单同步优先synchronized；需要公平锁、可中断、多条件队列选Lock。

### 104. == 和 equals() 的区别（同85，精简版）

`==`：基础类型比较值；引用类型比较对象地址；

规范：重写equals必须重写hashCode。

### 105. NIO读取数据放在JVM还是其他地方

分两种Buffer：

1. **HeapBuffer（堆缓冲区）**：在JVM堆内；底层还是要拷贝到操作系统直接内存才能和内核交互，多一次拷贝；
2. **DirectBuffer（直接缓冲区）**：分配在**操作系统堆外内存**，不在JVM堆；减少一次用户态拷贝，读写文件/网络性能更好；由Cleaner虚引用回收；> 
> NIO推荐DirectBuffer做高性能IO。

### 106. HashMap 和 ConcurrentHashMap区别；CHM如何保证线程安全

HashMap：非线程安全，并发put会丢数据、链表环；
ConcurrentHashMap：线程安全；
JDK8 CHM实现：

- 取消分段锁Segment；
- 采用 **CAS + synchronized桶锁**；只锁住当前hash桶，不是全表锁；粒度更小；

### 109. Java异常处理关键字、最佳实践

- catch：捕获处理指定异常
- finally：一定会执行，用来关闭资源（流、连接）

### 110. 双亲委派机制、作用、存在问题

双亲委派：加载请求向上委托父加载器，父加载失败自己加载；
层级：Bootstrap → Extension → AppClassLoader → 自定义加载器；
作用：防止核心类被篡改、保证类全局唯一；
问题：**父加载器看不到子加载器的类**；

### 113. ThreadLocal理解，项目鉴权使用

ThreadLocal底层：每个Thread内部有ThreadLocalMap，key是ThreadLocal弱引用，value是存的数据；**数据绑定线程，线程之间隔离**。

### 114. BIO、NIO、AIO区别&场景

- **BIO（同步阻塞IO）**：一个连接一个线程；read阻塞；简单；高并发下线程爆炸；适合连接少、短连接；
- **NIO（同步非阻塞IO）**：Selector多路复用器，少量线程管理大量连接；轮询就绪事件；同步，业务线程自己读数据；Netty底层；适合高并发长连接；
- **AIO（异步非阻塞IO）**：内核完成IO后主动回调通知程序；异步；Windows支持好，Linux内核支持差，生产很少用。

### 121. 封装、继承、多态以及作用

原因：CPU缓存、JVM指令重排；共享变量在线程本地缓存修改，没有及时刷回主存，其他线程看不到最新值。
解决方案：
1. volatile：保证可见性、禁止指令重排；**不保证原子性**；适合标记位；
2. synchronized / Lock：保证可见+原子+有序；

### 1. JVM堆内存溢出和内存泄漏分别如何排查处理

**堆OOM（OutOfMemoryError: Java heap space）**
含义：堆里对象太多，GC后还是放不下。

`jmap -dump:format=b,file=xxx.hprof pid`：JDK 原生命令，导出 hprof。

`heapdump /tmp/dump.hprof`作用：导出堆快照，生成标准`.hprof`文件，可以用 MAT、JProfiler 分析，等价 jmap dump 功能Arthas

排查步骤：

1. JVM启动参数加上 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/xxx`，OOM自动dump堆快照；
2. 使用 MAT / JProfiler / JVisualVM 分析dump文件；
3. 找大对象、对象实例数最多的类，看引用链；
4. 判断：是瞬时流量大（堆太小），还是代码持续持有对象泄漏。
处理：调大堆；优化代码减少对象创建；分批处理；使用对象池。

**内存泄漏**
含义：对象已经业务不用，但还有强引用链，GC无法回收，越跑内存越高，最终OOM。
常见泄漏点：静态集合、ThreadLocal不remove、长生命周期集合持有短生命周期对象、未关闭流/连接、内部类持有外部引用。
排查：

1. 持续观察GC日志、监控（Prometheus+Grafana），看堆内存只升不降；
2. 定时dump对比，看哪些对象持续增长；
3. 追踪引用链，定位是谁持有这个对象。
处理：切断无用引用；用完 `ThreadLocal.remove()`；try-with-resources关闭资源；避免无界集合。

> 一句话区分：泄漏是**该回收收不掉**；OOM是内存不够用，泄漏久了一般会演变成OOM。

### 2. JVM内存结构，各区域作用+可能出现的内存问题

JVM运行时数据区：程序计数器、虚拟机栈、本地方法栈、堆、方法区（元空间JDK8+）
1. **程序计数器PC**：线程私有，记录当前执行字节码行号；唯一一个没有OOM的区域。
2. **虚拟机栈（Java栈）**：线程私有，栈帧（局部变量表、操作数栈、返回地址等）；方法调用入栈出栈；异常：`StackOverflowError`（递归过深、栈帧太多）；`OOM`（栈不断扩展）。
3. **本地方法栈**：线程私有，给native方法服务；同虚拟机栈，栈溢出、OOM。
4. **堆 Heap**：线程共享，存放所有对象实例、数组；GC主战场；异常：`OutOfMemoryError: Java heap space`。
5. **方法区（JDK8之后Metaspace元空间）**：线程共享；存放类元信息、常量池、静态变量；JDK8元空间在堆外本地内存；异常：`java.lang.OutOfMemoryError: Metaspace`（类加载太多，动态生成类、反射、ASM）。

### 3. JVM内存区域划分、作用、线程私有/共享、抛出异常

| 区域 | 私有/共享 | 作用 | 异常 |
|---|---|---|---|
| 程序计数器 | 私有 | 记录字节码执行位置 | 无 |
| Java虚拟机栈 | 私有 | 存放栈帧，方法执行 | StackOverflowError、OOM |
| 本地方法栈 | 私有 | Native方法执行 | StackOverflowError、OOM |
| 堆 | 共享 | 对象、数组，GC | Java heap space OOM |
| 方法区(元空间) | 共享 | 类元数据、常量、静态变量 | Metaspace OOM |

口述精简版：
线程私有三块：程序计数器、虚拟机栈、本地方法栈；
共享两块：堆、方法区。

### 4. JVM崩溃怎么查找原因

JVM崩溃一般是 **JVM进程直接挂掉（crash），不是应用抛出OOM异常**，会生成 `hs_err_pidxxx.log` 崩溃日志。
排查顺序：

1. 优先找 `hs_err_pid` 日志，看崩溃位置：是JVM本身bug、native代码、JNI、驱动、内存越界；
2. 看信号量：SIGSEGV 段错误，大多native/JNI；
3. 查看系统层面：操作系统OOM killer把进程杀了（dmesg查看）、服务器内存不足、swap；
4. 检查JVM参数、版本，是否有已知JDK bug；
5. 排查第三方native库：netty tcnative、opencv、自研JNI；
6. 查看core dump（开启core的情况下）；
7. 区分：应用抛出OOM是Java层异常；hs_err是JVM本身崩溃。

### 5. 怎么检查处理JVM崩溃

检查流程：
1. 收集日志：hs_err崩溃日志、系统dmesg、应用日志、GC日志；
2. 看是否被系统OOM Killer干掉（Linux dmesg -T）；
3. 解析hs_err：看崩溃线程、出错帧、是否native代码；
4. 复现：稳定复现优先最小复现demo；
处理方案：
- 如果是系统OOM杀进程：降低JVM堆，预留系统内存；
- JDK版本bug：升级JDK；
- JNI/第三方native库：版本降级、隔离；
- 关闭有问题的JVM参数；
临时兜底：配置进程守护，自动重启，同时抓现场日志。

### 6. 从Java代码编写到CPU指令执行，程序运行全链路

1. 编写 `.java` 源码；
2. javac编译器：源码 → `.class` 字节码（二进制，JVM指令集，平台无关）；
3. java命令启动JVM，类加载器把class加载进方法区，验证、准备、解析、初始化；
4. 执行引擎运行字节码：
   - 解释器：逐条解释字节码翻译成机器指令执行；启动快，反复执行慢；
   - JIT即时编译器（C1/C2）：热点代码检测，高频代码编译成本地CPU机器码，缓存；
5. 机器码交给CPU执行；
6. 配合内存模型、寄存器、缓存完成运算。

一句话版本：Java源码javac编译成class字节码，JVM类加载后由执行引擎解释或者JIT编译为平台相关机器码，交给CPU执行。

### 7. 讲讲JVM内存结构

同第2题，精简口述版：
JVM运行时数据区分为5块：
程序计数器：线程私有，记录执行位置，无OOM；
虚拟机栈：线程私有，方法栈帧，栈溢出；
本地方法栈：native方法；
堆：共享，对象实例，GC堆OOM；
方法区（元空间JDK8）：共享，类信息，元空间OOM。

### 8. JVM频繁GC的可能原因

1. **内存泄漏**：对象无法回收，可用堆持续变小，不断触发GC；
2. 堆太小，业务对象多，分配压力大；
3. 短生命周期对象大量生成（循环内new对象、字符串拼接、流频繁创建）；
4. 大对象频繁分配，直接进老年代，触发Full GC；
5. 老年代空间不足、晋升阈值不合理，Minor GC后大量对象晋升到老年代；
6. Metaspace满、动态生成大量类；
7. System.gc() 手动调用；
8. GC参数不合理：晋升阈值、分区大小不合理。

排查手段：打开GC日志，看GC类型、耗时、回收前后内存变化；堆dump分析。

### 9. 双亲委派机制、作用、存在问题

双亲委派：类加载收到加载请求，先交给父加载器，父加载器加载不了自己才加载。
加载器层级：Bootstrap（启动类加载器）→ Extension扩展类加载器 → Application应用类加载器 → 自定义加载器。
作用：
1. 安全：防止核心类（java.lang.String）被恶意自定义类替换；
2. 保证类全局唯一，同一个类不会重复加载。
存在问题：父加载器看不到子加载器的类；
典型场景：SPI（JDBC驱动），驱动实现类在AppClassLoader，rt.jar在Bootstrap，启动类加载器加载不到驱动实现，所以用线程上下文类加载器打破双亲委派。

### 1. @Transactional 底层原理 + 失效场景

**底层原理**
基于 **Spring AOP动态代理**。

- 启动时扫描带 `@Transactional` 的类/方法，生成代理对象；
- 调用代理方法时，先开启事务（获取数据库连接、关闭自动提交）；
- 目标方法正常执行完毕，代理提交事务；抛出指定异常时回滚；
- 本质是对数据库 `Connection` 的 `commit / rollback` 封装；
- 代理分两种：**JDK动态代理（接口）、CGLIB（类代理）**。

**失效场景（高频必背）**

1. **方法不是public**：Spring事务不支持非public方法；
2. **同类内方法自调用**：`this.xxx()`，绕过代理对象，直接调用原对象方法，AOP增强失效；
3. **异常类型不对**：默认只捕获 `RuntimeException / Error`；普通受检Exception不回滚，需要手动指定 `rollbackFor`；
4. **异常被try-catch吃掉**：方法内部catch没有往外抛，代理感知不到异常；
5. 多线程：事务在主线程，异步子线程抛异常，主线程感知不到；
6. 数据库引擎不支持事务：MyISAM；
7. 传播行为配置错误，比如 `REQUIRES_NEW`、`NOT_SUPPORTED`；
8. Bean没有被Spring管理。

### 2. Spring Bean生命周期

> 一句话主线：**加载BeanDefinition → 实例化 → 属性填充（依赖注入） → Aware回调 → BeanPostProcessor前置 → 初始化回调 → BeanPostProcessor后置（AOP代理在这里！） → Bean就绪使用 → 容器关闭时销毁**

1. **解析配置，生成 BeanDefinition**
Spring 扫描注解/XML，把Bean信息封装成BeanDefinition（类名、scope、lazy、init/destroy方法等），只是元数据，还没有对象。

2. **实例化 Instantiation**
反射调用构造方法 new 出原始对象；此时属性都是默认值。
> 单例非懒加载：容器启动创建；prototype：每次getBean才实例化。

3. **属性填充 populateBean（依赖注入）**
给字段赋值，处理 `@Autowired`、`@Value`；解决循环依赖（单例三级缓存在这里提前暴露半成品bean）。

4. **Aware 接口回调 invokeAwareMethods**
按顺序执行：
- `BeanNameAware`：拿到自己在容器中的beanName
- `BeanFactoryAware`：拿到BeanFactory
- `ApplicationContextAware`：拿到ApplicationContext
> 作用：让Bean拿到Spring容器资源

5. **BeanPostProcessor#postProcessBeforeInitialization（初始化前置后置处理器）**
属性注入完成、初始化之前执行；全局对所有Bean生效。

6. **初始化 Initialization（这一组顺序必考！）**
✅ **@PostConstruct（JSR250注解）**
✅ `InitializingBean#afterPropertiesSet()`（Spring接口）
✅ xml/@Bean指定的 `init-method` 自定义初始化方法

7. **BeanPostProcessor#postProcessAfterInitialization（初始化后置后置处理器）**
👉 **AOP动态代理就在这一步生成！**
原始bean变成代理对象，这就是为什么 `@PostConstruct` 里面的this不是代理对象。

> 到此：Bean完成创建，放入单例池，可供业务使用。

8. **Bean正常使用阶段**
业务代码 `@Autowired` 获取Bean调用。

9. **销毁阶段（容器close时才执行，prototype Bean Spring不管理销毁！）**
顺序：
✅ `@PreDestroy`
✅ `DisposableBean#destroy()`
✅ xml/@Bean指定的 `destroy-method` 自定义销毁方法
常用于关闭线程池、释放连接等资源清理

#### 高频追问

##### Q1：初始化三个回调顺序？

`@PostConstruct` → `InitializingBean.afterPropertiesSet()` → `init-method`

##### Q2：销毁三个回调顺序？

`@PreDestroy` → `DisposableBean.destroy()` → `destroy-method`

##### Q3：AOP代理在哪一步？

`BeanPostProcessor#postProcessAfterInitialization`，初始化之后。

##### Q4：原型Bean销毁？

Spring不会管理prototype Bean的销毁，容器关闭不会执行上面销毁回调，需要自己手动释放。

##### Q5：BeanPostProcessor 和 InstantiationAwareBeanPostProcessor区别？

BeanPostProcessor：**实例化完成之后**（属性填充之后），初始化前后；
InstantiationAwareBeanPostProcessor：**实例化之前、属性填充阶段**的扩展点（可以短路直接返回自定义bean，跳过构造实例化）。

5. 配置集中：application.yml，统一配置；
6. 开发效率高，快速搭建微服务；
7. 不是替代Spring，是Spring的增强封装，底层依旧是Spring。

### 8. @Async 用法、原理、适用场景

**用法**

1. 启动类加 `@EnableAsync` 开启异步；
2. 方法上加 `@Async`；调用该方法会异步执行；
3. 返回值可以用 `Future<T>` 获取结果；

**原理**
底层也是AOP代理；调用时不走原方法，交给内置线程池（SimpleAsyncTaskExecutor）或者自定义 `ThreadPoolTaskExecutor` 去异步执行；

> 
> 同样有自调用失效问题：同类this调用不生效。

**适合场景**
适合**非主链路、可以异步执行**的任务：消息通知、日志记录、推送、短信、邮件、记录审计日志；
⚠️ 不适合：强依赖返回结果、事务一致性要求高的流程；默认线程池不推荐线上直接用，建议自定义线程池，隔离线程，防止打满。

## SpringMVC / SpringBoot / SpringCloud

### 1. SpringMVC 和 SpringBoot 有什么不同

一句话：**SpringMVC 是 Spring 里的 Web 框架模块；SpringBoot 是一套快速开发脚手架，内置了 SpringMVC**。

- SpringMVC：负责Web请求处理，DispatcherServlet、HandlerMapping、适配器、视图解析器；需要自己配置xml或者JavaConfig、自己部署Tomcat；它解决的是**如何开发web接口**。
- SpringBoot：不是替代SpringMVC，基于Spring，核心是自动配置、starter、内嵌容器；引入web starter就自动装配SpringMVC，省去大量配置，jar包直接启动。

对比要点：

1. 配置：SpringMVC 需要手动配置DispatcherServlet、拦截器、视图；SpringBoot自动装配。
2. 容器：原生SpringMVC一般打war包，外置Tomcat；SpringBoot内嵌Tomcat/Jetty。
3. 定位：SpringMVC = Web MVC组件；SpringBoot = 一站式开发框架。

### 2. SpringBoot自动配置原理

核心一句话：**自动配置 = @EnableAutoConfiguration 导入自动配置类，借助条件注解按需装配Bean**

#### 1. 入口注解：@SpringBootApplication

复合注解，由三个核心注解组成：
```java
@Configuration
@ComponentScan
@EnableAutoConfiguration  // ✅ 自动配置的核心
```

重点：**@EnableAutoConfiguration**
它里面导入了 `@Import(AutoConfigurationImportSelector.class)`
> `AutoConfigurationImportSelector` 是关键选择器。

#### 2. AutoConfigurationImportSelector 做了什么

1. 读取 `META-INF/spring.factories`（SpringBoot2.7之前）
   文件里 `org.springframework.boot.autoconfigure.EnableAutoConfiguration` 对应的一长串自动配置类全限定名（比如 `DataSourceAutoConfiguration`、`WebMvcAutoConfiguration`）
> ⚠️ 版本变化：SpringBoot 2.7+ 废弃 spring.factories 自动配置方式，改用 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件；面试先说经典的spring.factories，再补充这个变更。
2. 获取到候选自动配置类列表
3. 去重、排除（`exclude` / `excludeName`）
4. **条件注解筛选**，不满足条件的配置类直接跳过

#### 3. 条件注解（核心灵魂）

所有自动配置类上面都打了条件注解，**满足条件才生效**：
- `@ConditionalOnClass`：类路径下存在指定Class才生效（例如有DataSource.class才加载数据源自动配置）
- `@ConditionalOnMissingBean`：容器中**还没有用户自己定义这个Bean**，SpringBoot才自动注入（用户自定义优先，这就是我们可以覆盖默认配置的原因）
- `@ConditionalOnProperty`：配置文件存在对应配置项，且匹配值
- `@ConditionalOnWebApplication`：当前是web环境才生效

#### 4. 配置绑定：@ConfigurationProperties

自动配置类会绑定 `application.yml/application.properties` 配置：
`@ConfigurationProperties(prefix = "spring.datasource")`
把配置文件里的参数绑定到Properties实体类，给自动配置Bean使用。
配合 `@EnableConfigurationProperties` 开启绑定。

#### 5. 完整流程串起来

1. 启动类打上 `@SpringBootApplication`，触发 `@EnableAutoConfiguration`
2. `AutoConfigurationImportSelector` 加载文件里所有候选自动配置类
3. 根据各类 `@ConditionalOnXXX` 条件进行筛选
4. 符合条件的自动配置类本身是 `@Configuration`，里面定义各种Bean
5. 里面 `@ConditionalOnMissingBean`：**用户自己写了Bean，就不创建默认的**
6. 配置文件参数通过 `@ConfigurationProperties` 注入进去，修改默认行为

#### 高频面试追问

##### Q1：为什么我们引入starter就开箱即用？

starter本质是**依赖聚合**，把需要的jar包、自动配置类一起引入；有了依赖，`@ConditionalOnClass` 条件成立，自动配置类就生效，自动装配Bean。starter本身不写业务代码，只管理依赖。

##### Q2：自动配置和SPI有关系吗？

底层是Spring自己的`@Import + ImportSelector`机制，不是JDK SPI，不要混淆。

##### Q3：@ConditionalOnMissingBean的顺序？

自动配置类加载优先级偏低，**用户自定义Bean先注册**，所以判断的时候发现已经存在，就不会创建默认Bean。

##### Q4：SpringBoot 2.7改动点

移除spring.factories里的自动配置，改用 `AutoConfiguration.imports`；3.x继续沿用新文件方式。

#### ✅ 45秒口述精简版（直接背）

SpringBoot自动配置核心在@EnableAutoConfiguration，它通过@Import引入AutoConfigurationImportSelector。这个选择器读取配置文件拿到所有候选自动配置类；再依靠@ConditionalOnClass、@ConditionalOnMissingBean等条件注解按需判断，满足条件才加载配置类。配置类是@Configuration，里面定义Bean；@ConditionalOnMissingBean保证用户自定义Bean优先。同时使用@ConfigurationProperties绑定yml配置。而starter就是用来引入对应依赖，让条件成立。

### 2. 怎么看SQL有没有走索引

使用 `EXPLAIN` / `EXPLAIN ANALYZE`（MySQL8.0支持，还能看实际耗时）
重点看 `type` 和 `key` 字段：

- `key`：实际选用的索引，不为NULL代表用到索引；NULL就是没用到；
- `type`：访问类型，优先级从好到差：`system > const > eq_ref > ref > range > index > ALL`
  - `ALL`：全表扫描，没走索引；
  - `range`：范围查询走索引；
- `Extra`额外信息：
  - `Using filesort`：文件排序，没用到索引排序；
  - `Using temporary`：创建临时表，通常group by没合适索引；
  - `Using index`：覆盖索引，不需要回表，最优。

补充：还要注意，**key有值不代表索引高效**，要看rows扫描行数是否巨大。

### 3. MySQL性能调优核心思路与手段

核心思路：**先抓瓶颈，从上层往下调，优先优化SQL和索引，最后调参数、硬件**
1. SQL与索引优化（优先级最高）
    - explain分析执行计划，避免select *；
    - 建立合适联合索引，遵循最左前缀；避免索引失效（函数、隐式转换、or、like %前缀）；
    - 优先覆盖索引，减少回表；避免大join、深分页；
2. 架构层面
    - 读写分离：主写从读；
    - 分库分表：单表数据量过大（千万级）水平拆分；
    - Redis缓存热点，击穿、穿透、雪崩防护；
3. InnoDB参数调优
    - `innodb_buffer_pool_size`：核心，一般机器内存50%~70%；
    - `innodb_flush_log_at_trx_commit`、`sync_binlog` 平衡持久化和性能；
    - 调整redo log大小；
4. 数据库设计
    - 合适字段类型，避免大字段；varchar合理长度；尽量主键自增；
5. 运维监控：慢查询日志slow_query_log，抓慢SQL。

一句话总结：抓慢SQL → 优化索引改写SQL → 合理缓存 → 参数调优 → 读写分离/分表。

### 4. MySQL死锁常用检测工具&排查方式

1. `show engine innodb status;`
    最常用，输出里找 `LATEST DETECTED DEADLOCK`，里面有死锁两个事务、锁等待信息、SQL、锁类型；
2. MySQL 8.0：`performance_schema.data_locks`、`data_lock_waits` 视图，实时查看锁和等待；
3. 开启死锁日志：`innodb_print_all_deadlocks`，死锁信息写入error日志；
4. 业务监控：接入APM（SkyWalking）抓报错堆栈；
5. 工具：mysql-deadlock抓取、自研监控脚本定时采集锁视图。

排查思路：拿到两条死锁SQL，看加锁顺序不一致；解决：统一资源加锁顺序、缩小事务范围、降低隔离级别、避免行锁升级。

### 5. 什么是回表查询

InnoDB聚簇索引：主键索引叶子节点存完整行数据；二级索引叶子节点存**主键值**。
**回表：通过二级索引查到主键，再拿着主键去主键索引树查找完整行数据，这个过程就是回表。**

对比覆盖索引：查询字段全部在二级索引里，不需要去主键索引拿数据，`Extra`显示`Using index`，避免回表，性能更好。

例子：
```sql
-- idx_name(name)
select name from t where name='xxx'; -- 覆盖索引，不回表
select name,age from t where name='xxx'; -- age不在二级索引，回表
```

### 6. MySQL索引结构类型（InnoDB）

InnoDB默认索引结构：**B+树（必考）**，还有哈希索引、全文索引、空间索引。
1. **B+树索引（聚簇索引、二级索引）【最常用】**
    - 特点：平衡多路搜索树；数据都在叶子节点；叶子有序链表，范围查询、排序友好；
    - 适用：等值查询、范围查询、排序、分页；普通主键、联合索引都是B+树；
2. **自适应哈希索引 AHI**
    InnoDB自动维护，不是人工创建；对热点等值查询做哈希缓存；只适合高频等值查询，无法范围查找；
3. **全文索引 FULLTEXT**
    针对长文本分词检索；替代like '%xxx%'；适合文章、内容搜索；
4. **空间索引 SPATIAL**
    GEOMETRY类型，地理位置、坐标范围查询；地图业务。

> 区分：MyISAM也是B+树，但是非聚簇索引；面试默认问InnoDB。







## Redis面试题

### 1. 介绍你使用过的数据库类型及项目场景（同前面，精简版）

- **MySQL（InnoDB）**：核心业务，订单、员工、票务交易，需要事务、强一致性；
- **Redis**：热点缓存、分布式锁、限流、库存预扣、token；
- **MongoDB**：审计日志、操作记录，字段灵活，不需要事务。

### 2. 缓存穿透、击穿、雪崩，概念+解决方案

#### 缓存穿透

**概念**：查询**不存在的数据**，缓存和数据库都没有，请求直接打到DB；比如恶意传一个不存在id，绕过Redis。
方案：
1. 缓存空值（短期TTL）；
2. 布隆过滤器：把合法key提前放入，不存在直接拦截；
3. 参数校验，非法参数直接拒绝。

#### 缓存击穿

**概念**：**热点key过期一瞬间**，大量并发请求过来，同时去查数据库。
方案：
1. 互斥锁（分布式锁）：只放行一个请求去更新缓存；
2. 热点key永不过期（后台异步主动刷新）；
3. 逻辑过期：value里存过期时间，不删key，后台线程异步更新。

#### 缓存雪崩

**概念**：大量key**同时过期**，或者Redis宕机，海量请求全部压到数据库，DB扛不住。
方案：
1. TTL加随机偏移量，避免同一时间大批量失效；
2. Redis集群高可用（主从+哨兵/Cluster）；
3. 服务熔断、降级、限流；
4. 多级缓存（本地Caffeine + Redis）。

> 一句话区分：穿透是查不存在的数据；击穿是单个热点key过期；雪崩是大批量key一起失效/Redis挂了。

### 3. 缓存击穿与缓存穿透的区别

- **穿透：查的这个数据本身就不存在**，缓存、数据库都没有，请求一直打DB；攻击经常用不存在ID；
- **击穿：数据是存在的，只是这个热点key刚好过期**，并发涌进来同时查DB；针对热门数据。

### 4. Redis怎么实现分布式锁

核心要求：**互斥、原子加锁、防死锁、可重入（可选）、释放安全**
1. 加锁：`SET lockKey uuid NX EX 30`
   - NX：只有key不存在才成功，保证互斥；
   - EX：自动过期，防止服务宕机锁一直不释放死锁；
   - value存唯一标识（UUID），用来区分是谁持有的锁，不能随便删别人的锁；
2. 释放锁**必须Lua脚本原子执行**：先判断value是否等于自己的标识，相等才del；
   不能 `if + del` 两条命令，中间有时间窗口，会误删别人锁；
3. 缺点：主从切换会丢锁（主节点加锁成功，还没同步到从节点，主挂了，从晋升新主，锁丢失）；
4. 进阶：Redisson封装了分布式锁，自动续期（看门狗）、可重入、主从锁问题用RedLock（一般不推荐生产用RedLock）。

### 5. 场景：Redis宕机，客户端拿到锁怎么办；任务执行超过锁超时怎么办

#### ① Redis宕机，已经拿到锁

- 如果是主从架构：主节点拿到锁，还没同步从节点，主宕机，从升级为主，新主没有这个锁，其他线程可以拿到同一把锁 → **锁失效，并发安全问题**；
- 应对：
  1. 优先使用Redisson，业务上识别风险；
  2. 高可靠场景不依赖Redis锁，改用数据库悲观锁/乐观锁、Zookeeper锁；
  3. 锁只做轻量防并发，核心业务用数据库兜底；
  4. 降低主从异步复制带来的风险，业务接受一定概率锁失效。

#### ② 任务耗时超过锁超时时间（锁自动释放，别的线程抢到锁）

问题：任务还没跑完，锁过期释放，多个线程同时执行业务，数据错乱。
解决：
1. Redisson看门狗：拿到锁之后，后台线程每隔1/3TTL自动续期，任务没结束就一直延长锁时间；
2. 自己实现：业务内部定时续期；
3. 预估任务时长，设置足够大的超时时间；
4. 业务层做幂等，防止重复执行带来脏数据。

### 6. 有哪些加锁方法

分三大类：JVM本地锁、分布式锁、数据库锁
1. **JVM本地锁（只适用于单实例）**
   - `synchronized`：偏向锁、轻量级锁、重量级锁；
   - `ReentrantLock`：可重入、公平/非公平、可中断、超时tryLock；
2. **分布式锁（多实例）**
   - Redis：SETNX + Lua / Redisson；
   - Zookeeper：临时有序节点，实现公平锁；
   - etcd：版本号机制；
3. **数据库锁**
   - 悲观锁：`select ... for update`（InnoDB行锁）；
   - 乐观锁：版本号version / CAS，更新时判断版本；

口述精简回答：本地锁synchronized、ReentrantLock；分布式锁Redis、Zookeeper；数据库乐观锁、悲观锁。

## Docker

### 1. Docker部署端口冲突怎么处理

端口冲突本质：**宿主机同一个端口被多个容器映射占用**
排查：`netstat -tulpn` / `ss -tulpn`、`docker ps` 看已占用端口
解决手段：

1. 修改端口映射：`-p 宿主机空闲端口:容器内端口`；比如原来 `-p 8080:8080` → `-p 8081:8080`
2. 不指定宿主机端口，随机分配：`-p :8080`
3. 使用不同网卡；
4. Compose环境：修改yaml里ports配置；
5. 先停掉占用该端口的容器/进程。

> 原理：-p 是宿主机端口转发到容器端口，宿主机端口唯一。

### 2. 外部修改容器内配置文件（4种方案，优先级从推荐到临时）

1. **数据卷挂载（最佳生产方案）** `-v /宿主机路径:/容器内路径`，宿主机直接改文件，容器自动生效；容器删除数据不丢失；
2. docker cp：宿主机文件拷贝进容器 `docker cp xxx.conf 容器id:/xxx`；适合临时改；容器重建丢失；
3. 进入容器内部修改：`docker exec -it xxx bash`，vi修改；不推荐，容器重建配置丢失；
4. 重新构建镜像：Dockerfile内置配置；版本可追溯。

重点提醒：直接改容器内文件属于修改容器读写层，**容器删掉就没了，不适合生产**，生产优先挂载volume。

### 3. 项目Docker使用场景&解决问题（贴合你的Jenkins、HRMS、剧院项目）

我的项目里用Docker打包MySQL、Nacos、Redis、RocketMQ、Seata还有后端服务，配合Docker Compose编排，Jenkins流水线部署：

## Nacos

### 1. 多环境Nacos如何部署

两种主流方案：
方案A（推荐，隔离强）：**每套环境独立部署一套Nacos集群** dev/test/prod，各自独立数据库；配置、服务完全隔离；缺点资源开销大；适合大型项目。
方案B（单Nacos实例，Namespace隔离）：一套Nacos，用Namespace区分环境（dev/test/prod）；Group做业务分组；**配置、服务在逻辑隔离**；优点省资源；⚠️风险：人为操作容易误改线上；适合中小项目。
补充：

- 命名空间Namespace：环境隔离；
- Group：同一个服务下不同业务组；
- DataId：配置ID；
  生产常用：测试一套Nacos、生产单独一套Nacos。

### 2. 项目Nacos用来做什么？

两大核心能力：**服务注册发现 + 分布式配置中心**

1. 注册发现：微服务启动注册到Nacos；服务调用方从Nacos拉取实例列表，结合Ribbon负载均衡；健康检查剔除不健康实例；
2. 配置中心：把yml配置放到Nacos后台；支持动态刷新 `@RefreshScope`，不用重启应用改配置；
   我在HRMS、剧院票务项目，存放数据库地址、限流参数、开关配置；同时做服务治理。

### 3. Nacos服务调用原理

一句话总结：**Nacos只负责服务注册、订阅推送实例列表；负载均衡、HTTP远程调用是客户端完成（客户端负载均衡）**
> 区分：Nacos ≠ LB；Nacos是注册中心，提供实例地址清单。

#### 完整流程

##### 1. 服务提供者：注册 + 心跳保活

1. Provider启动，`@EnableDiscoveryClient`，通过Nacos Client向Nacos Server注册：**服务名、IP、端口、权重、分组、命名空间**
2. **临时实例（默认）**：持续心跳保活（Nacos2.x是gRPC长连接保活；1.x是5s一次HTTP心跳）；15s没心跳标记不健康，30s直接摘除实例
3. Nacos集群通过Distro协议同步实例数据（AP，临时实例）

##### 2. 服务消费者：订阅服务，本地缓存实例列表

1. Consumer启动时，**订阅目标服务名**；Nacos2.x建立gRPC长连接（9848端口），实例列表变更时，服务端主动推送最新列表给客户端，更新本地内存缓存；同时有兜底轮询拉取
2. 本地缓存：**服务实例列表缓存在消费者本地**，绝大多数请求直接读本地缓存，不会每次请求都访问Nacos Server，性能高

##### 3. 发起远程调用（OpenFeign / @LoadBalanced RestTemplate）

1. 写 `@FeignClient(name = "provider-service")` 或者 `restTemplate.getForObject("http://provider-service/xxx")`
2. 请求进入Spring Cloud负载均衡拦截器（LoadBalancerClient，新版替代Ribbon）
3. 拦截器根据服务名，从**本地缓存拿到该服务全部健康实例**
4. 使用负载均衡算法（Nacos内置支持**权重轮询WRR**，也支持随机、就近、同集群优先）选出一个实例IP:port
5. 把服务名替换成真实IP端口，组装HTTP请求，直接和Provider通信
> ✅ 关键点：**消费者直连提供者，流量不经过Nacos**，Nacos只做地址通讯录

#### Nacos 2.x 和 1.x 订阅推送区别（高频追问）

- Nacos1.x：客户端定时主动拉取（pull），配合UDP推送；容易丢消息
- Nacos2.x：**gRPC长连接双向流**，订阅后服务端主动push变更；断线自动重连、全量补拉，实时性更好

#### 核心概念区分

1. **临时实例 ephemeral=true（默认）**：AP模型，心跳保活；宕机自动删除；适合无状态微服务
2. **持久实例 ephemeral=false**：CP模型，Raft一致性；适合有状态服务

#### 高频面试追问

##### Q1：客户端负载均衡 vs 服务端负载均衡（Nginx）

- Nacos+Feign：**客户端LB**，本地选地址，直连后端；适合微服务内部调用
- Nginx：服务端LB，流量统一经过网关转发

##### Q2：权重是在哪里生效？

Nacos客户端SDK自带权重负载均衡；控制台修改权重，推送下发到消费者本地缓存，选实例时生效，灰度发布常用。

##### Q3：分组、命名空间作用？

namespace：环境隔离（dev/test/prod）；group：服务分组隔离，同一个服务名下不同分组不互通。

##### Q4：为什么不用每次调用都查Nacos？

本地缓存+变更推送，降低Nacos服务端压力；注册中心本身不扛业务流量。

#### ✅ 45秒口述精简版（直接背）

Nacos服务调用分为注册、订阅、调用三步。首先服务提供者启动向Nacos注册自己的IP端口，持续心跳保活；消费者启动订阅目标服务，Nacos2.x通过gRPC长连接推送实例列表，缓存在消费者本地。调用时Feign或者带@LoadBalanced的RestTemplate，从本地缓存拿到实例列表，用权重轮询等负载均衡策略选出一个实例，替换服务名，直接发起HTTP请求访问提供者。整个过程Nacos只下发地址，业务流量不经过Nacos，属于客户端负载均衡。

### 1. 浏览器输入百度网址，涉及哪些协议

### 2. 毕业设计：密码加密、私钥管理、HTTPS传输（给你适配版本）

> 你可以直接背这个版本
在项目中用户密码**不明文存储**：前端传输先RSA加密，后端拿到密码做 **BCrypt单向哈希加盐** 存入数据库，无法反向解密；
私钥管理：RSA密钥对，公钥下发前端加密，私钥放在服务端配置中心（Nacos），不硬编码代码，生产环境做好权限隔离；
传输层全程HTTPS：基于TLS握手，身份认证+对称加密传输，防窃听、篡改、中间人攻击；

1. DNS解析：域名→IP（浏览器缓存、hosts、本地DNS、根域名服务器迭代查询）；
2. TCP三次握手，建立连接；HTTPS则先TLS握手；
3. 浏览器发送HTTP请求；
4. 服务器处理请求返回HTTP响应；
5. TCP四次挥手断开；
6. 浏览器拿到HTML，解析DOM树、CSSOM树，合成渲染树；布局、绘制、分层合成；
7. 加载图片、JS等资源，JS执行修改DOM；页面渲染完成。

### 4. HTTP和HTTPS区别，HTTPS如何保证安全

区别：
- HTTP：明文传输，80端口；无身份认证；容易抓包篡改劫持；
- HTTPS：HTTP+TLS；443端口；加密传输、身份认证、防篡改。

安全保障三点：
1. **加密**：握手协商对称密钥，传输内容加密，窃听看不到原文；
2. **身份认证**：CA证书校验服务端身份，防止中间人冒充；
3. **完整性校验**：消息摘要，防止内容被篡改。

### 5. HTTPS（TLS）工作原理（握手流程）

1. 客户端发起请求，携带支持的TLS版本、加密套件；
2. 服务端返回选中套件、服务器证书（含公钥）；
3. 客户端校验证书合法性（CA链）；
4. 客户端生成随机预主密钥，用服务端公钥加密发给服务端；
5. 服务端用自己私钥解密得到预主密钥；双方各自生成一致的会话对称密钥；
6. 双方发送握手完成报文；后续通信使用对称密钥加密传输。

> TLS1.3简化握手，一轮RTT。

### 6、7. HTTP和HTTPS主要区别（精简版）

1. 端口：HTTP 80，HTTPS 443；
2. 传输：HTTP明文；HTTPS基于TLS密文；
3. 证书：HTTPS需要CA证书；
4. 安全：HTTPS防窃听、篡改、中间人；HTTP无；
5. 性能：HTTPS握手有少量开销；
6. 协议：HTTP是应用层；HTTPS = HTTP over TLS。

# 一、网络分层 & HTTP专题
### 1. 请说明常见的网络分层模型及各层的主要功能，并列举每层典型的协议及其协议格式要点

两种主流模型：**OSI七层模型**、**TCP/IP四层（五层）模型**，后端面试优先讲五层模型。
#### 五层模型（推荐背诵）

1. **应用层**：为应用程序提供网络服务，定义交互规则
    - 协议：HTTP/HTTPS、DNS
    - 格式：HTTP 请求行+请求头+空行+body；DNS报文包含头部、问题段、回答段
2. **传输层**：端到端进程通信，端口标识，流量控制、可靠传输
    - TCP：头部20~60字节，序号、确认号、标志位SYN/ACK/FIN/RST、窗口、校验和；面向连接、可靠、有序
    - UDP：固定8字节头部，源端口、目的端口、长度、校验和；无连接，不可靠
3. **网络层**：主机寻址，路由转发
    - IP：IP头部，源IP、目的IP、TTL、协议号、分片信息
4. **数据链路层**：相邻节点传输，MAC寻址，差错检测
    - Ethernet以太网帧：源MAC、目的MAC、类型字段、数据、CRC校验
5. **物理层**：比特流传输，电气信号、光纤、网卡

> OSI七层：应用层、表示层、会话层、传输层、网络层、数据链路层、物理层。表示层负责编解码加密；会话层负责会话建立维护。

### 2. 请描述HTTP请求报文和响应报文的基本结构，并说明各部分的作用

✅ **请求报文**
1. 请求行：`Method URL Version`（GET /index HTTP/1.1），指定方法、资源、版本
2. 请求头（Header）：一堆键值对，携带附加信息：Host、Content-Type、Cookie、User-Agent
3. 空行：分隔头部和实体体，必须有
4. 请求体Body：POST/PUT携带提交数据；GET一般无body

✅ **响应报文**
1. 状态行：`Version Status-Code Reason-Phrase`（HTTP/1.1 200 OK）版本、状态码、描述
2. 响应头：Server、Content-Type、Content-Length、Set-Cookie
3. 空行
4. 响应体Body：返回给浏览器的数据（HTML、JSON）

### 3. 在浏览器输入百度的网址，会显示出百度的页面，这一过程涉及到哪些协议？

DNS、UDP（DNS默认）、IP、TCP、HTTPS(TLS)、HTTP；底层还有ARP。
简述：先用DNS域名解析（UDP 53端口），建立TCP连接，TLS握手，HTTP请求。

### 4. 从浏览器输入URL到显示页面发生了什么？

1. DNS解析：浏览器缓存 → hosts → 本地DNS服务器 → 迭代查询根域名服务器，拿到IP
2. TCP三次握手建立连接；HTTPS场景额外执行TLS握手协商密钥、校验证书
3. 浏览器组装HTTP请求发送
4. 服务器接收请求，业务处理，返回HTTP响应
5. TCP四次挥手断开连接
6. 浏览器解析HTML生成DOM树，解析CSS生成CSSOM，合并成渲染树
7. 布局（Layout）、绘制（Paint）、合成（Composite）；异步加载JS、图片资源，渲染页面

### 5 / 10. 请说明HTTP中GET和POST请求的主要区别及应用场景

1. **语义**：GET用于查询资源，**幂等**；POST用于提交资源、产生变更，不幂等
2. **传参位置**：GET参数拼接在URL；POST放请求Body
3. **缓存**：GET默认可以被浏览器缓存；POST默认不缓存
4. **长度限制**：GET受浏览器URL长度限制；POST理论无上限
5. **书签历史**：GET参数会保留在浏览器历史、书签；POST不会
6. **编码**：GET只能URL编码；POST支持多种Content-Type（form、json）

场景：
- GET：查询列表、查询详情页
- POST：登录、提交表单、新增数据

> ⚠️重点：GET不是绝对安全，只是语义上只读；抓包同样能看到参数，不要传敏感信息。

### 6 / 8 / 9. 请解释HTTP和HTTPS的区别，并说明HTTPS是如何保证通信安全的

区别：
1. HTTP：应用层协议，80端口，明文传输，无证书，易抓包篡改劫持
2. HTTPS = HTTP + TLS，443端口，加密传输，需要CA证书

HTTPS三大安全保障：
1. **加密**：握手协商对称会话密钥，传输内容加密，防止窃听
2. **身份认证**：CA证书校验服务端身份，防止中间人冒充服务器
3. **完整性**：消息摘要校验，报文被篡改后校验失败

### 7. 请简单介绍HTTP协议的特点和工作原理

特点：
- 无状态：服务器不记住上一次请求是谁；靠Cookie/Session维持会话
- 基于请求-响应模型
- 应用层协议，默认基于TCP
- HTTP1.1默认长连接keep-alive
- 明文传输（HTTP）

工作原理：客户端发起请求，服务端接收处理，返回响应；一次请求对应一次响应。

### 2. 请解释Linux的用户态和内核态及其区别

CPU分两种运行级别：
- **用户态**：应用程序运行的级别，权限受限；不能直接访问硬件、内核资源；用户代码跑在这里；系统调用、中断会切换到内核态
- **内核态**：操作系统内核运行级别，最高权限，可以访问所有硬件、内存、IO资源

区别：权限不同、可访问资源不同；切换有开销（上下文切换）。Java程序运行在用户态，调用Socket、文件读写、`new`底层内存申请都会触发系统调用陷入内核态。

### 3. 无名管道和有名管道的区别是什么？管道（pipe/FIFO）

1. **无名管道 pipe**：
    - 内存临时文件，无磁盘节点；**只能亲缘进程（父子进程）通信**；半双工；进程退出自动消失
2. **有名管道 FIFO**：
    - 在文件系统有管道文件节点；**无关进程之间也可以通信**；持久存在，rm删除；半双工

共同点：都是字节流，先进先出，不支持随机读写。

### 4. 加载设备树后形成的结构体是什么？（偏内核驱动，简单回答）

设备树DTB加载到内核，解析后生成 `struct device_node`，后续转换成 `struct platform_device`。

### 5 /6. IO多路复用中的select、epoll有什么区别？epoll原理和优势

#### select

1. 使用位图fd_set监听fd；fd上限默认1024
2. 每次调用都要把fd集合从用户态拷贝内核态；内核轮询扫描全部fd
3. 返回后用户态需要遍历所有fd找就绪事件；时间复杂度 O(n)

#### epoll（Linux高性能IO模型，Netty底层）

三个系统调用：`epoll_create` 创建epoll实例；`epoll_ctl` 添加/删除/修改fd；`epoll_wait` 阻塞等待就绪事件
原理：内核维护红黑树存监听fd，就绪链表保存就绪fd；**事件回调机制**，fd就绪主动加入就绪队列，不是轮询扫描。

优势对比select/poll：
1. 没有fd 1024上限；
2. 只拷贝就绪fd，不需要每次全量拷贝；
3. O(1)拿到就绪fd，不用遍历全部fd；高并发海量连接性能远好于select；
4. 支持边缘触发ET、水平触发LT。

> LT水平触发：只要fd还有数据就一直通知；ET边缘触发：只有状态变化一瞬间通知，需要一次性读完数据。Netty默认LT。

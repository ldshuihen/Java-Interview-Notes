#### Q1（单选，5分）—— 继承与多态

##### 📄 题目

> **以下代码的输出结果是什么？**
```java
class Device {
    public Device() { System.out.print("A"); }
    public void start() { System.out.print("B"); }
}
class Scanner extends Device {
    public Scanner() { System.out.print("C"); }
    @Override
    public void start() { System.out.print("D"); }
}
public class Main {
    public static void main(String[] args) {
        Device d = new Scanner();
        d.start();
    }
}
```
#### ✅ 答案：**ACD**

##### 解析

| 步骤 | 执行内容                                      | 输出 | 依据                                                         |
| ---- | --------------------------------------------- | ---- | ------------------------------------------------------------ |
| 1    | `new Scanner()` → 先执行父类构造器 `Device()` | `A`  | 子类构造器隐式调用 `super()`，**先父后子**                   |
| 2    | 执行子类构造器 `Scanner()`                    | `C`  | 父类构造完成后才构造子类部分                                 |
| 3    | `d.start()` → 执行**子类**的 `start()`        | `D`  | **多态/动态绑定**：方法调用看运行时实际对象类型（Scanner），而非编译类型（Device） |
**最终输出：`ACD`**
> 口诀：**构造先父后子，方法看对象不看引用**。常见错误：选含 `B` 的选项是忽略了多态。

#### Q2（单选，5分）—— equals 与 hashCode 契约

##### 📄 题目

```java
Map<Device, String> map = new HashMap<>();
Device d1 = new Device("SN001");
Device d2 = new Device("SN001");
map.put(d1, "正常");
System.out.println(map.get(d2));
```
> 已知 `Device` 重写了 `equals()`，按序列号判断相等，但**没有重写 `hashCode()`**。在常见 JVM 默认实现下，以下哪个说法最准确？
>
> - A. 一定返回 “正常”
> - B. 通常返回 null
> - C. 一定抛出异常
> - D. 无法编译
##### ✅ 答案：**B. 通常返回 null**

##### 解析

**HashMap 查找分两步：① `hashCode()` 定位桶 → ② 桶内 `equals()` 比对。**
- `d1`、`d2` 是不同对象，未重写 `hashCode()` 时使用 `Object` 默认实现（基于对象身份），**大概率返回不同哈希值**
- `put(d1)` 落入桶 X，`get(d2)` 去桶 Y 查找 —— **连桶都没找对，`equals()` 根本没机会执行**，即使 `d2.equals(d1)` 为 true 也没用 → 返回 **null**
**为什么是“通常”而非“一定”？**
默认 `hashCode()` 不保证不同对象哈希值不同，极小概率两者哈希碰撞落入同一桶，此时 `equals()` 比对成功，会返回 “正常”。所以 **B 是最准确的表述**。
> **核心考点**：重写 `equals()` 必须同时重写 `hashCode()`，保证“相等对象必有相等哈希码”。
> 修复：`@Override public int hashCode() { return Objects.hash(serialNo); }`

#### Q3（单选，5分）—— try-catch-finally 执行顺序

##### 📄 题目

```java
public static int readConfig() {
    try {
        int value = loadFromFile();  // 抛出 IOException
        return value;
    } catch (IOException e) {
        return -1;
    } finally {
        System.out.println("finally");
    }
}
```
> 如果 `loadFromFile()` 抛出 `IOException`，以下说法正确的是：
>
> - A. 输出 "finally"，方法返回 -1
> - B. 方法返回 -1，但 "finally" 不会输出
> - C. 输出 "finally" 后抛出未捕获异常
#### ✅ 答案：**A. 输出 "finally"，方法返回 -1**

##### 解析

| 步骤 | 发生的事情                                                   |
| ---- | ------------------------------------------------------------ |
| 1    | `loadFromFile()` 抛出 `IOException`，第 4 行 `return value` 不执行 |
| 2    | 异常被 `catch` 捕获，执行 `return -1` —— JVM **先暂存返回值，但不立即返回** |
| 3    | **finally 块保证执行** → 打印 `"finally"`                    |
| 4    | finally 结束后，方法才真正返回暂存的 **-1**                  |
**排除法：**
- B ❌ —— finally 除 JVM 退出外**一定执行**
- C ❌ —— 异常已被 catch 捕获，不会向外传播，无“未捕获异常”
> **扩展考点**：
> ① finally 中再写 `return` 会**覆盖** try/catch 的返回值（反模式，禁止）；
> ② 基本类型返回值在 `return` 语句处已确定，finally 中修改局部变量不影响返回值；
> ③ 释放资源应优先用 **try-with-resources**（Java 7+）。

#### Q4（单选，5分）—— Spring 依赖注入时机

##### 📄 题目

```java
@Service
public class DeviceService {
    @Autowired
    private DeviceRepository deviceRepository;
    private final String defaultIp = "192.168.1.100";
    public DeviceService() {
        System.out.println(deviceRepository.count());
    }
}
```
> 以下代码有什么问题？
>
> - A. 没有问题
> - B. `deviceRepository` 在构造时尚未注入，会抛出 NullPointerException
> - C. `@Autowired` 不能用在 private 字段上
##### ✅ 答案：**B. deviceRepository 在构造时尚未注入，会抛出 NullPointerException**

##### 解析

**核心考点：Spring Bean 生命周期 —— 构造方法执行时，字段注入还没发生。**
| 阶段       | 发生的事情                          | `deviceRepository` 状态 |
| ---------- | ----------------------------------- | ----------------------- |
| 1️⃣ 实例化   | 调用构造方法 `DeviceService()`      | **null**                |
| 2️⃣ 属性注入 | Spring 反射给 `@Autowired` 字段赋值 | 注入完成                |
| 3️⃣ 初始化   | 执行 `@PostConstruct` 等回调        | 可正常使用              |
构造方法第 8 行调用 `deviceRepository.count()` 时字段还是 null → **NPE**，Spring 容器启动即失败。
**排除法：**
- A ❌ —— NPE 必现，每次启动都会炸
- C ❌ —— `@Autowired` 恰恰常用于 private 字段，Spring 通过反射注入，完全合法
**正确修复：**
```java
// 方案一：构造器注入（推荐，Spring 官方最佳实践）
@Service
public class DeviceService {
    private final DeviceRepository deviceRepository;
    public DeviceService(DeviceRepository deviceRepository) {
        this.deviceRepository = deviceRepository;
        System.out.println(deviceRepository.count());  // ✅
    }
}
// 方案二：逻辑挪到 @PostConstruct
@PostConstruct
public void init() {
    System.out.println(deviceRepository.count());  // ✅ 注入完成后执行
}
```
> **附加 Review 点**：`defaultIp` 硬编码应改为配置项（`@Value("${device.default-ip}")`）；构造方法中访问数据库会拖慢启动且依赖数据源就绪顺序。

#### Q6（简答，15分）—— 接口偶现慢排查

##### 📄 题目

> 运维反馈：设备管理系统的设备列表接口 `/api/devices` 有时响应时间超过 5 秒（正常 < 200ms），但**不是每次都慢**。请简述你的排查思路。
##### ✅ 参考答案

**一、先取证，搞清“慢”的特征**
- 从网关/应用日志筛出 >5s 的慢请求，分析模式：是否有**时间规律**（整点、固定间隔）、**参数规律**（特定科室、深分页）、还是随机分布
- 结合 APM（SkyWalking/Arthas Trace）对齐时段、实例、请求参数，查看 P99、GC 日志、线程池、连接池、慢 SQL、缓存命中率
**二、分段定位，拆解耗时**
把链路耗时拆为：网关排队 → 线程池等待 → 应用代码 → SQL → 缓存 → 下游调用，用链路追踪确定瓶颈层级。
**三、逐层排查**
| 层级     | 排查重点                                                     |
| -------- | ------------------------------------------------------------ |
| 应用层   | GC 停顿（Full GC）、锁阻塞/死锁、线程池耗尽排队              |
| 数据库层 | 慢查询日志、执行计划（索引失效）、N+1 查询、长事务/行锁等待  |
| 缓存层   | 缓存过期瞬间的击穿、热点 key 失效、命中率波动——“偶现慢”最典型原因 |
| 数据倾斜 | 某科室数据量特别大、`LIMIT 100000,20` 深分页                 |
| 外部因素 | 下游服务超时重传、定时任务抢占资源、连接池被慢请求占满、冷启动（首次建连/JIT 未预热） |
**四、复现与验证**
- 给慢请求加 TraceID 串联日志，用 Arthas `trace` 方法级耗时，开启 MySQL `slow_query_log` 抓现场
- 找到根因后修复（加索引/缓存预热/连接池扩容/限流），并补充监控告警防止复发
> **答题关键**：突出“偶现”这一特征 → 优先怀疑 **GC、缓存失效、连接池/线程池耗尽、定时任务竞争、数据倾斜** 这几类间歇性因素。

#### Q7（简答，10分）—— 设备导入代码审查

##### 📄 题目

> 实习生小王实现了设备导入功能：
```java
public List<Device> importDevices(String filePath) throws IOException {
    String content = Files.readString(Path.of(filePath));
    String[] lines = content.split("\n");
    List<Device> devices = new ArrayList<>();
    for (String line : lines) {
        String[] parts = line.split(",");
        Device device = new Device();
        device.setName(parts[0]);
        device.setIp(parts[1]);
        devices.add(device);
    }
    return devices;
}
```
> 请以代码审查者的身份：
> 1. 指出至少 3 个潜在的问题，并说明你打算怎么解决。
> 2. 设计至少 3 类自测用例，包含必要的测试路径。
##### ✅ 参考答案

**第 1 问：问题与解决方案**
| #    | 问题                                                  | 后果                                                         | 解决方案                                                 |
| ---- | ----------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| 1    | **数组越界风险**：直接访问 `parts[0]`、`parts[1]`     | 空行、只有一列的行会抛 `ArrayIndexOutOfBoundsException`，整个导入失败 | 先校验 `parts.length`，不合法的行跳过并记录错误明细      |
| 2    | **换行符问题**：`split("\n")`                         | Windows 的 `\r\n` 会残留 `\r`，导致 IP 等字段带隐藏字符      | 改用 `Files.readAllLines()` 或 `split("\\r?\\n")`        |
| 3    | **异常处理粗糙**：直接 `throws IOException`           | 文件不存在/无权限时上层拿到裸异常，无友好提示                | 转换为业务异常（带文件路径），提前 `Files.exists()` 校验 |
| 4    | **字符编码隐患**：`readString` 默认 UTF-8             | GBK 等 CSV 文件乱码                                          | 显式指定编码                                             |
| 5    | **无数据校验**：IP 格式、名字非空、重复序列号均未校验 | 脏数据入库                                                   | 校验 + 去重，返回“成功列表 + 错误明细”                   |
| 6    | **大文件 OOM 风险**：`readString` 全量读入            | 文件过大内存溢出                                             | `BufferedReader` 流式逐行读取                            |
**第 2 问：自测用例设计（至少 3 类）**
1. **正常路径**：标准两列数据多行 → 全部解析成功，字段正确
2. **异常/边界输入**：
   - 空文件 → 返回空列表，不抛异常
   - 空行、缺 IP 的行（`设备C,`）、字段多余逗号 → 按策略跳过或报错，不中断整体
   - 字段含首尾空格 → 验证 trim 处理
3. **文件级异常**：
   - 文件不存在 / 无读取权限 → 抛友好业务异常
   - GBK 编码 / 带 BOM 文件 → 不乱码
   - Windows `\r\n` 换行 → IP 字段不带 `\r`
4. **大数据量（可选）**：10 万行文件 → 验证耗时与内存，不 OOM

#### Q8（简答，20分）—— 设备台账管理模块设计

##### 📄 题目

> 请设计一个设备云平台的“设备台账管理”模块的后端数据模型和接口。需求：
> 1. 设备字段：名称、型号、序列号、所属科室、IP 地址、入库时间、状态（正常/维修中/报废）。
> 2. 支持分页查询，按科室、入库时间范围、状态筛选，按名称或序列号搜索。
> 3. 支持新增、编辑、删除设备。
> 4. 设备序列号必须全局唯一。
> **请回答：**
> 1. 基于 MySQL 做表设计；说明唯一约束、非空约束、状态取值、索引、删除策略等设计考虑。
> 2. 完成 REST API 接口设计。
##### ✅ 参考答案

**第 1 问：MySQL 表设计**
```sql
CREATE TABLE device (
    id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY COMMENT '主键',
    name          VARCHAR(64)  NOT NULL COMMENT '设备名称',
    model         VARCHAR(64)  NOT NULL COMMENT '型号',
    serial_no     VARCHAR(64)  NOT NULL COMMENT '序列号',
    department_id BIGINT UNSIGNED NOT NULL COMMENT '所属科室ID',
    ip            VARCHAR(15)  DEFAULT NULL COMMENT 'IP地址',
    import_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '入库时间',
    status        TINYINT      NOT NULL DEFAULT 1 COMMENT '状态:1-正常 2-维修中 3-报废',
    deleted       TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除:0-未删 1-已删',
    created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_serial_no (serial_no),
    KEY idx_department (department_id),
    KEY idx_import_time (import_time),
    KEY idx_status (status),
    KEY idx_name (name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='设备台账表';
```
**设计考虑（评分点）：**
| 维度         | 说明                                                         |
| ------------ | ------------------------------------------------------------ |
| **唯一约束** | `serial_no` 加 UNIQUE KEY，由数据库兜底保证全局唯一（应用层校验只是第一道防线，并发下必须靠唯一索引防重）。若用逻辑删除，可改为 `deleted_at DATETIME` + 唯一索引 `(serial_no, deleted_at)` 避免“已删记录占用序列号”的冲突 |
| **非空约束** | 名称、型号、序列号、科室、入库时间、状态均 NOT NULL；IP 可为空（部分设备无 IP），格式校验放在应用层 |
| **状态取值** | `TINYINT` 枚举（1 正常 / 2 维修中 / 3 报废），省空间、可索引；语义由代码枚举类维护，可加 CHECK 约束（MySQL 8.0） |
| **索引设计** | 按查询条件建：科室、入库时间、状态单列索引；`name` 索引支持前缀模糊搜索（`LIKE 'x%'` 走索引，`'%x%'` 不走，数据量大考虑 ES）；科室+时间组合查询频繁可建联合索引 `(department_id, import_time)` |
| **删除策略** | **逻辑删除**（deleted 标志）——台账数据有审计价值、误删可恢复；所有查询默认拼接 `deleted = 0` |
**第 2 问：REST API 设计**
统一前缀 `/api/v1/devices`：
| 方法     | 路径                   | 说明                                                         |
| -------- | ---------------------- | ------------------------------------------------------------ |
| `GET`    | `/api/v1/devices`      | 分页查询。Query：`page、size、departmentId、status、importTimeStart、importTimeEnd、keyword`（匹配名称或序列号） |
| `GET`    | `/api/v1/devices/{id}` | 设备详情                                                     |
| `POST`   | `/api/v1/devices`      | 新增设备（Body：name、model、serialNo、departmentId、ip、importTime、status） |
| `PUT`    | `/api/v1/devices/{id}` | 编辑设备                                                     |
| `DELETE` | `/api/v1/devices/{id}` | 删除设备（逻辑删除）                                         |
**响应体与状态码约定：**
```json
{
  "code": 0, "message": "success",
  "data": { "total": 128, "page": 1, "size": 20, "list": [ /* ... */ ] }
}
```
- `201` 新增成功 / `200` 成功 / `204` 删除成功
- `400` 参数校验失败（如 IP 格式非法）
- `409` 序列号重复（捕获 `DuplicateKeyException` → 提示“序列号已存在”）
- `404` 设备不存在
- 附加业务规则：编辑时禁止修改 `serialNo`（或修改时重新唯一校验）；删除“维修中”设备需先变更状态

#### Q9（简答，10分）—— 任务优先级安排

##### 📄 题目

> 周五下午 4 点，你手上还有以下任务：
> - **A**：排查一个偶现的 Java 服务内存增长和接口变慢问题（已经跟踪了 2 天）
> - **B**：领导要求周一早上提交的新功能还差最后的测试
> - **C**：测试部门报告：你负责的模块出现严重 bug，已导致业务流程中断
> - **D**：同事请你帮忙看一个编译错误，他说“很简单，5 分钟就好”
> **请回答：**
> 1. 你会如何安排这些任务的优先级？为什么这样安排？
> 2. 根据以往同类问题的经验，任务 C 的根因分析和定位预计需要 4-5 小时。你会怎么做？为什么？
##### ✅ 参考答案

**第 1 问：优先级 C → B → D → A**
| 顺序 | 任务                     | 理由                                                         |
| ---- | ------------------------ | ------------------------------------------------------------ |
| 1️⃣ C  | 线上严重 bug，业务中断   | **影响面 × 紧急度最高**：生产事故每分钟都在扩大损失，无争议第一 |
| 2️⃣ B  | 新功能最后测试，周一截止 | **明确硬性 deadline**，只差最后一步，投入小、产出确定，周五必须收尾 |
| 3️⃣ D  | 同事的编译错误           | 先快速响应一次；但若 10-15 分钟内没解决，约定时间（下班前/周一）再帮，避免“5 分钟陷阱”挤占 C、B 时间 |
| 4️⃣ A  | 偶现性能问题             | 已跟踪 2 天、非阻断，有运行余量；布置好观察指标/埋点继续收集数据，**顺延到下周专门时段**深入排查 |
**方法论**：优先级 = 业务影响 × 紧急程度；重新排序后**主动同步相关方**（领导、同事、测试），管理预期。
**第 2 问：C 预计 4-5 小时的处理**
**核心思路：先止损，再定位；管理预期，不留孤岛。**
1. **立即止损（先于定位）**：评估快速**回滚**到上一个稳定版本恢复业务——回滚 10 分钟可能比 5 小时定位更划算；无法回滚则降级、限流、开关兜底
2. **同步上报**：第一时间告知领导和测试：现象、影响范围、预计 4-5 小时、当前止损措施；之后**每约 1 小时同步一次进展**
3. **请求支援、并行排查**：邀请熟悉模块的同事/测试一起分析（测试有复现路径），自己沿主线索定位，同事帮忙查日志、比对最近变更
4. **数据驱动**：先拿报错日志、堆栈、监控（GC/CPU/耗时）、最近 diff，把时间花在有数据支撑的方向上
5. **时间盒**：设检查点，如 **2 小时无实质进展则升级上报**、换方案（回滚 + 下周继续），不让单点问题无限吞噬时间
6. **事后闭环**：修复后回归测试 → 复盘 → 补监控告警和防回归用例

#### Q10（编程，20分）—— DeviceConfigService 代码修复

##### 📄 题目

> 请阅读以下 `DeviceConfigService` 代码，完成两件事：
> 1. 指出至少 3 个问题，并说明每个问题可能导致的后果。
> 2. 给出 `getTimeout()` 和 `loadConfigs()` 的关键修复方案或重写后的代码，并说明每个改动的原因。
```java
public class DeviceConfigService {
    private static final List<String> configCache = new ArrayList<>();
    public String getTimeout() {
        String value = System.getenv("DEVICE_TIMEOUT");
        if (value == "3000") {
            return "3秒";
        }
        return value;
    }
    public void loadConfigs(List<Path> files) {
        for (Path file : files) {
            try {
                configCache.add(Files.readString(file));
            } catch (IOException e) {
                // ignore
            }
        }
    }
}
```
##### ✅ 参考答案

**第 1 问：问题及后果**
| #    | 问题                                   | 位置              | 后果                                                         |
| ---- | -------------------------------------- | ----------------- | ------------------------------------------------------------ |
| 1    | **用 `==` 比较字符串**                 | `value == "3000"` | 比较的是引用而非内容，`getenv` 返回值与字面量几乎不可能同引用，条件**永远为 false** |
| 2    | **吞掉异常**（空 catch + ignore）      | loadConfigs       | 读文件失败被静默忽略，缓存缺配置却无任何日志告警，问题极难排查 |
| 3    | **ArrayList 作为共享缓存，非线程安全** | 第 2 行           | 多线程并发读写可能丢数据、抛异常或读到中间状态               |
| 4    | **缓存无去重、无清理**                 | add 累加          | 重复调用 loadConfigs 会重复累加同一配置，内存浪费且内容混乱  |
| 5    | **getenv 返回 null 未处理**            | getTimeout        | 环境变量未配置时返回 null，调用方易触发 NPE                  |
| 6    | **超时值无格式/范围校验**              | getTimeout        | 配成 `"abc"`、`"-1"` 会原样透传，导致运行时错误              |
| 7    | **大文件全量读入**                     | readString        | 配置文件过大时 OOM                                           |
| 8    | **魔法值/单位混乱**                    | "3000"/"3秒"      | 硬编码，毫秒与秒混用，调用方易误用                           |
**第 2 问：重写代码**
```java
public class DeviceConfigService {
    // ① 线程安全：volatile 快照 + 不可变列表整体替换（copy-on-write 思想）
    private static volatile List<String> configCache = Collections.emptyList();
    public String getTimeout() {
        String value = System.getenv("DEVICE_TIMEOUT");
        // ② equals 比较内容，常量放前面顺便防 NPE
        if ("3000".equals(value)) {
            return "3秒";
        }
        // ③ null / 格式 / 范围校验，默认值兜底，避免 NPE 和非法值透传
        if (value == null || !value.matches("\\d+")) {
            return "30";
        }
        int seconds = Integer.parseInt(value) / 1000;
        return seconds <= 0 ? "30" : seconds + "秒";
    }
    public void loadConfigs(List<Path> files) {
        if (files == null || files.isEmpty()) {
            return;
        }
        List<String> newList = new ArrayList<>();
        for (Path file : files) {
            try {
                newList.add(Files.readString(file));
            } catch (IOException e) {
                // ④ 不再吞异常：记录日志（文件路径 + 堆栈）；
                // 若配置缺失属致命错误，可抛自定义异常让启动失败（fail-fast）
                log.error("加载配置文件失败: {}", file, e);
            }
        }
        // ⑤ 全量重建而非 add 累加：消除重复膨胀，天然支持刷新；
        // volatile 写整体替换，读线程永远看到完整一致的列表；unmodifiableList 防外部篡改
        configCache = Collections.unmodifiableList(newList);
    }
}
```
**每个改动的原因：**
1. **`equals` 替代 `==`**：字符串必须比内容；`"3000".equals(value)` 字面量在前还能防 NPE
2. **null/格式校验 + 默认值**：方法永远不返回 null 或非法值，失败要快速失败 + 兜底
3. **异常不静默吞**：至少记 error 日志带路径堆栈；致命配置缺失应抛异常 fail-fast，好过带病运行
4. **线程安全**：`volatile` + 不可变列表整体替换，读线程要么看旧列表要么看新列表，永远一致（也可用 `CopyOnWriteArrayList`；不推荐 `synchronizedList`，遍历仍需手动加锁）
5. **全量重建替代累加**：消除重复调用导致的数据膨胀，天然支持配置刷新
**加分项**：超时返回 `int`/`Duration` 统一单位；限制单文件大小或流式读取防 OOM；生产环境用配置中心（Nacos）替代手写缓存。

### **1. 请描述一下Java中接口和抽象类的区别，以及各自的使用场景**

1. **继承数量**
- 抽象类：一个类**只能继承一个**抽象类，单继承。
- 接口：一个类**可以实现多个**接口，解决单继承限制。

2. **构造方法**
- 抽象类：**有构造方法**，供子类构造时调用。
- 接口：**没有构造方法**，不能实例化。

3. **成员变量**
- 抽象类：变量可以是 `private/protected/public`，普通变量、静态变量都可以。
- 接口：Java8之前，变量默认是 `public static final`，只能是常量。

4. **方法（按JDK版本）**
- 抽象类：可以有抽象方法（无实现）、普通实例方法、静态方法。
- 接口：
  - JDK8前：只能是抽象方法；
  - JDK8：新增 default 默认方法、static静态方法，带实现；
  - JDK9：可以有 private 私有方法。

5. **设计思想**
- 抽象类：**is-a，是一种**，代表一类事物的共性。
- 接口：**can-do，能做**，代表一种能力、行为规范。

#### 使用场景（加分重点）

✅ **抽象类场景：多个子类有大量公共代码、公共属性，抽取公共逻辑**
比如：所有动物都有 name、age，都有eat()，但eat实现不一样；把公共字段、通用逻辑抽到Animal抽象类。

> 适合：代码复用，提取子类通用成员与逻辑。

✅ **接口场景：定义能力规范，多实现、解耦**
比如：Runnable（可运行）、Serializable（可序列化）、Comparable（可比较）；
不同毫无关系的类，都可以具备这个能力。

> 适合：定义行为契约、做扩展、面向接口编程。

#### 一句话极简总结（回答收尾）

抽象类是**一类事物的模板，侧重代码复用，is-a关系，单继承**；
接口是**能力契约，侧重行为规范，can-do，支持多实现**。

#### 高频追问备选

Q：什么时候用default方法？
A：接口新增方法，不想让所有已经实现这个接口的类全部改代码，用default给默认实现，兼容老代码。



### **2. HashMap的底层实现原理是什么？put和get的过程是怎样的？**

HashMap底层是数组+链表+红黑树的结构。在Java 8之前是数组+链表，Java 8后当链表长度超过8且数组长度大于64时会转为红黑树。

put过程：首先对key进行hash运算得到hash值，然后通过(n-1) & hash计算出数组下标。如果该位置为空直接插入；如果不为空则判断key是否相同，相同则覆盖value；不同则遍历链表或红黑树插入。当元素数量超过阈值（容量*负载因子）时会进行扩容。

get过程：同样先计算hash值和数组下标，找到对应位置后比较key，相同则返回value，否则在链表或红黑树中查找。

### **3. 谈一下你对Java异常处理机制的理解**

Java用**异常机制**分离「业务正常逻辑」和「错误处理逻辑」，避免大量if判断去校验错误。
Throwable是顶层父类，分两大分支：**Error 和 Exception**。

1. **Error**：系统级严重错误，程序无法处理。比如OOM、栈溢出StackOverflowError。代码里一般不捕获。
2. **Exception**：程序可以尝试捕获处理的异常，又分成两类：
    - **受检异常（Checked Exception）**：编译期强制检查。要么 `try-catch`捕获，要么方法上`throws`抛出。例如 IOException、SQLException。
      适用：外部不可控的错误（文件、网络、数据库），编译器提醒开发者必须处理。
    - **非受检异常（Unchecked Exception / RuntimeException）**：运行时异常，编译不强制处理。比如空指针NullPointerException、数组越界、类型转换异常。
      大多是代码bug，优先改代码，而不是捕获。

#### 关键字

- `try`：包裹有可能抛出异常的代码
- `catch`：捕获对应类型异常，做异常处理；可以多个catch，先细粒度、后父类
- `finally`：无论是否异常、是否return，**一定会执行**（除了System.exit()）；用来释放资源：流、连接、锁
- `throw`：手动抛出一个异常对象
- `throws`：写在方法签名，声明这个方法可能抛出某种受检异常，交给调用方处理

> 补充：Java7之后 try-with-resources，实现AutoCloseable的资源，可以自动关闭，不用手写finally释放流。

#### 设计思想 & 开发规范（加分）

1. 不要吞异常：catch之后不要只打印，最好打日志+必要兜底，不要空catch；
2. 不要捕获顶层Exception笼统捕获，尽量精确捕获；
3. 异常用来处理**意外情况**，不要用异常做正常业务流程的控制；
4. 自定义异常：业务异常，区分系统异常，方便上层统一处理、返回友好错误码。

#### 一句话精简收尾

Java异常就是把错误分层，Error是JVM致命错误，Exception分受检和运行时异常；用try-catch-finally捕获，throws向外声明，核心目的是解耦错误逻辑和主业务逻辑。

#### 30秒速记版（直接背）

Java异常根类是Throwable，分为Error和Exception。Error是虚拟机严重错误，没法处理；Exception分受检异常和运行时异常。受检异常编译强制要求处理，比如IO异常；RuntimeException是运行时异常，一般是代码bug。通过try、catch、finally、throws、throw处理，finally用于资源释放，推荐try-with-resources。异常不适合做正常业务分支。

### **4. 启动多线程的方法有哪些**

Java里启动线程常见4种方式，本质都是**new Thread + start()**，run()只是业务方法，直接调用run不算开启新线程！

> 
> 重点：`start()` 才会向操作系统申请创建内核线程；直接调用 `run()` 只是普通方法调用，在当前线程执行。

1. **继承Thread类，重写run()**

```
class MyThread extends Thread {
    @Override
    public void run() {
        // 任务逻辑
    }
}
// 使用
new MyThread().start();
```

缺点：Java单继承，继承了Thread就不能继承别的类，耦合高。

2. **实现Runnable接口，传给Thread**

Runnable 是只有一个抽象方法的函数式接口，Lambda 表达式在这里就是简写，生成 Runnable 接口的实现实例。把这个 Runnable 传给 Thread，调用 start ()，start () 会创建操作系统线程，线程调度起来之后，Thread 内部 run 方法去执行这个 Runnable 的 run 方法。

```
Runnable task = () -> {
    // 任务
};
new Thread(task).start();

== 等价于
Runnable task = new Runnable() {
    @Override
    public void run() {
        // 任务
    }
};
new Thread(task).start();
```

优点：避免单继承限制；任务和线程解耦，同一个Runnable可以交给多个线程执行。**开发最常用**。

3. **Callable + FutureTask（可以拿到返回值、抛异常）**
    Runnable无返回值、不能抛出受检异常；Callable可以。
  - **Thread 只认 Runnable**，Thread 的构造方法接收的参数类型是 `Runnable`；Thread 根本不认识 Callable。
  - **Callable 有返回值、能抛受检异常**，Runnable 没有返回值。
  - `FutureTask` 实现了 **RunnableFuture**，而 RunnableFuture 继承了 `Runnable` + `Future`。 所以 FutureTask **既是一个 Runnable（可以传给 Thread），又包装了 Callable（拿到返回结果）**。

```
Callable<Integer> callable = () -> 100;
FutureTask<Integer> futureTask = new FutureTask<>(callable);
new Thread(futureTask).start();
Integer res = futureTask.get(); //阻塞获取结果
```

4. **线程池（实际项目首选）**
`Executors` 或者手动 `ThreadPoolExecutor`，提交任务：submit/execute

- execute：接收Runnable，无返回
- submit：支持Runnable、Callable，可以返回Future拿结果

#### 一句话区分

- Thread继承：耦合、少用
- Runnable：无返回，最常用
- Callable+FutureTask：需要返回值
- 线程池：生产环境标准方案，复用线程

#### 高频追问考点

Q：start() 和 run() 的区别？

- start()：native方法，创建新线程，自动调用run；只能调用一次，第二次抛IllegalThreadStateException
- run()：普通成员方法，直接调用就是同步执行，不开启新线程

启动线程四种方式：继承Thread、实现Runnable、Callable配合FutureTask、线程池。核心都是调用Thread的start方法；run只是任务逻辑，直接调用不会开启新线程。Runnable没有返回值，Callable支持返回结果，项目优先用线程池。

### **5. 声明一个list你是怎么去进行声明的**

#### 简洁版（优先说这个）

声明List一般有几种写法，我会优先用**面向接口编程**，`List`是接口，`ArrayList`是实现类。

1. 推荐写法：`List<String> list = new ArrayList<>();`

   > 好处：面向接口，后续想换实现（LinkedList）的时候，只改右边就行，上层代码不受影响。

2. 如果要初始化少量元素： Java9+：`List<String> list = List.of("a","b","c");`，这个是**不可变集合**，不能add/remove。

3. 不推荐：`ArrayList<String> list = new ArrayList<>();`，直接用实现类接收，耦合太强。

------

#### 拓展追问（面试官经常接着问）

Q：`List.of()` 和 `new ArrayList<>()` 的区别？

- `List.of()` 返回不可变List，固定大小，增删抛异常；线程安全只读。
- `new ArrayList<>()` 可变，可以add、remove。

Q：还有 `Arrays.asList()`？ `List<String> list = Arrays.asList("a","b");` ⚠️ 坑：底层是数组视图，**不能add/remove**；修改set会同步修改原数组，容易踩坑，开发尽量少用。

#### 一句话速记

**左边写接口List，右边new实现类ArrayList，面向接口编程，解耦合。**

#### 完整对比汇总

```
// 1. 最常用，可变集合，推荐
List<String> list = new ArrayList<>();

// 2. Java9+ 快速初始化，不可变
List<String> list2 = List.of("1","2","3");

// 3. 不推荐，直接实现类接收
ArrayList<String> list3 = new ArrayList<>();

// 4. 容易踩坑的方式
List<String> list4 = Arrays.asList("a","b");
```

> 额外加分：阿里规范推荐，集合声明使用接口接收；并且指定泛型，不要用raw type裸泛型 `List list = new ArrayList()`。

### 2. 重载和重写的区别

- **重载（Overload）**：同一个类里，方法名相同，参数列表不同（参数个数/类型/顺序）；返回值、修饰符不做限制；编译期绑定。
- **重写（Override）**：父子类，方法名、参数列表、返回值一致；子类重写父类方法；子类权限不能比父类更严格；父类不能是private；运行期绑定。
> 一句话：重载是同一个类多方法；重写是子类覆盖父类方法。

#### 重写（Override）原理

核心一句话：**依靠Java的动态绑定（晚期绑定），运行时根据对象的实际类型，找到对应版本的方法执行**。

> 先区分：
> 静态绑定（早绑定）：编译期就确定调用哪个方法，比如重载、static方法、final方法、private方法
> 动态绑定（晚绑定）：**重写的实例方法，运行时才确定**

##### 底层原理（JVM角度）

每个类加载后，都会生成一张**方法表（vtable，虚方法表）**
1. 父类有可重写的实例方法，会放在父类虚方法表里；
2. 子类继承父类，复制一份父类的虚方法表；
3. 如果子类重写了某个方法：**子类虚方法表里，把这个方法条目替换成自己实现的方法地址**；
4. 如果没有重写，就保留父类的方法入口。

执行过程：
```java
Father obj = new Son();
obj.say();
```
- 编译阶段：编译器只看**引用类型 Father**，校验Father有没有say方法；
- 运行阶段：JVM找到 `obj` 指向的**实际对象Son**，拿到Son的虚方法表；
- 在虚方法表里查找say方法，执行子类Son的实现。

##### 关键限制（为什么这些不能重写）

- `static`：静态方法属于类，走静态绑定，不存在虚方法表，只是隐藏；
- `private`：私有方法对子类不可见，不会放进子类虚方法表；
- `final`：禁止重写，方法不会参与动态绑定；

##### 精简背诵话术（直接背）

重写底层是JVM的动态绑定机制。每个类都有虚方法表，子类继承父类虚方法表，重写时覆盖对应方法指针。编译期看引用类型，运行时看对象实际类型，去对应虚方法表找方法执行，实现多态。

### 3. 面向对象三大特征：封装、继承、多态，Java怎么体现

### 6. String / StringBuffer / StringBuilder

- String：不可变，底层char数组（Java9后byte[]），每次拼接生成新对象；
- StringBuffer：可变，方法加synchronized，**线程安全**，性能低；
- StringBuilder：可变，无同步锁，线程不安全，性能高；
> 开发优先StringBuilder；多线程共享场景才用StringBuffer。

1. **String**：不可变；
2. **StringBuffer**：可变、线程安全（synchronized）；
3. **StringBuilder**：可变、线程不安全，性能最好，开发首选。

#### 1. String

底层：`private final char[] value`（Java9之后是 `byte[]`）
- **不可变**：一旦创建，字符数组不能修改；
- 拼接 `+` 的时候，不是修改原对象，**会新建String对象**；
- 常量池优化：字面量字符串优先放字符串常量池复用；
- 频繁拼接大量字符串会产生很多临时对象，GC压力大，性能差。
```java
String s = "a";
s += "b"; // 等价 new String
```

#### 2. StringBuffer

可变字符序列，方法上加 `synchronized`
- 线程安全，多线程并发操作可以用；
- 锁带来开销，速度慢于StringBuilder；
- 底层char数组，容量不够自动扩容。

#### 3. StringBuilder（推荐）

可变字符序列，**没有同步锁**
- 线程不安全；单线程字符串拼接首选；
- 性能最高；底层也是可变数组，自动扩容。

#### 对比汇总

|  | String | StringBuffer | StringBuilder |
|---|---|---|---|
| 是否可变 | 不可变 | 可变 | 可变 |
| 线程安全 | — | 安全（synchronized） | 不安全 |
| 性能 | 差，频繁拼接大量对象 | 中等 | 最优 |
| 使用场景 | 少量字符串、固定常量 | 多线程下拼接（极少用到） | 单线程拼接（绝大多数场景） |

#### 底层拼接补充（高频考点）

Java编译器对简单 `String a + b + c` 会做**编译期优化**，自动转成StringBuilder。
⚠️ 但是：**循环里面做字符串拼接，优化会失效，每次循环都会new一个新的StringBuilder，性能很差！循环拼接一定要手动写StringBuilder**。

示例坑：
```java
// 不推荐，循环里每次新建StringBuilder
String str = "";
for(int i=0;i<1000;i++){
    str += i;
}
```

#### ✅ 30秒背诵版

String底层字符数组final修饰，不可变，拼接会生成新对象；StringBuffer可变，方法带synchronized，线程安全，性能差；StringBuilder可变、无锁、性能最高，线程不安全。单线程拼接优先用StringBuilder；循环内禁止直接用String加号拼接。

### 7. Exception 和 Error
- Error：系统级严重错误，JVM层面，**无法捕获处理**，比如OOM、栈溢出StackOverflowError。
- Exception：程序可捕获异常，分两类：

### 8. try-catch-finally
try放可能抛异常代码；catch捕获对应类型异常做处理；**finally无论是否异常、是否return，几乎都会执行**（唯一例外：try里执行System.exit(0)）。
用途：释放资源（流、连接）。顺序：try → catch（异常时） → finally。

### 9. 项目用过反射吗？怎么实现

#### 一、List（Arra4yList / LinkedList）、Set（HashSet）

List 和 Set 都实现 Iterable，遍历方式一样

1. **for 普通for循环（下标遍历，只有List支持，Set没有下标）**

```
List<String> list = new ArrayList<>();
for (int i = 0; i < list.size(); i++) {
    String s = list.get(i);
}
Set<String> set = new ArraySet()();
for(int i=0;i<set.size;i++){
	String s = set.
	}
```

✅ 优点：可以拿到索引；
❌ Set不能用。

2. **增强for循环（for-each，底层迭代器Iterator语法糖）**

```
for(String s : list){
}

for(String s : set){
    System.out.println(s);
}
```

✅ 简洁，List、Set都能用；
⚠️ 遍历中不能用集合add/remove（会并发修改异常ConcurrentModificationException）。

3. **Iterator迭代器**

```
Iterator<String> it = list.iterator();
while(it.hasNext()){
    String s = it.next();
    it.remove(); // 安全删除元素！
}

// 2. Iterator迭代器，可以安全删除
Iterator<String> it = set.iterator();
while(it.hasNext()){
    String s = it.next();
}
```

重点：**迭代器的remove是安全删除，不会报并发修改异常**

4. **Stream forEach（Java8+）**

```
list.forEach(System.out::println);
list.stream().forEach(s->{});

// 3. Java8 forEach
set.forEach(s -> {});
```

> 
> Set没有下标，所以Set只能用：for-each、Iterator、stream

#### 二、Map（HashMap）三种遍历方式

```
Map<String,Integer> map = new HashMap<>();
```

1. **遍历 entrySet()（推荐！同时拿key和value，效率最高）**

```
for(Map.Entry<String,Integer> entry : map.entrySet()){
    String k = entry.getKey();
    Integer v = entry.getValue();
}
```

2. **遍历 keySet()，拿到key再get(value)**

```
for(String key : map.keySet()){
    Integer v = map.get(key);
}
```

❌ 缺点：多一次get查询，性能差一点。

3. **遍历 values()，只需要value，不需要key**

```
for(Integer val : map.values()){
}
```

4. Java8 stream / forEach

```
map.forEach((k,v)->{});
```

#### ⚠️高频考点：ConcurrentModificationException

增强for底层是Iterator，**集合自身add/remove会修改modCount，触发异常**；
想要遍历删除，优先用 Iterator 的 remove 方法。

#### 精简背诵版

List支持普通for、for-each、迭代器、stream；Set没有索引，不能普通for。
Map三种遍历：entrySet（同时取key-value，推荐）、keySet再get、values只取值。
遍历过程直接集合remove会并发修改异常，安全删除用迭代器remove。

#### 快速对比小结

- List：普通for + for-each + Iterator + forEach
- Set：for-each + Iterator + forEach
- Map：entrySet / keySet / values

#### 4. Redis怎么实现薪资排序

核心：**用 ZSet（有序集合 sorted set）**，底层是 **Hash表 + 跳表 SkipList**。

- member：员工唯一标识（员工id），**唯一不可重复**
- score：薪资数值（double），Redis 自动按照 score 维护顺序，不需要查询时再排序

#### 基础命令演示

```
# 添加员工薪资
ZADD salary_rank 15000 emp_101
ZADD salary_rank 22000 emp_102
ZADD salary_rank 10000 emp_103

# 升序（薪资从低到高）
ZRANGE salary_rank 0 -1 WITHSCORES
# 降序（薪资从高到低，最常用）
ZREVRANGE salary_rank 0 -1 WITHSCORES

# 查询某个员工薪资
ZSCORE salary_rank emp_102
# 查询员工排名（从0开始）
ZREVRANK salary_rank emp_102
```

> 配套：员工姓名、部门等详细信息不要放ZSet，放到 **Hash** 里 `HSET emp:101 name:"张三" dept:"研发"`，查到员工id后再查Hash补全信息，ZSet只负责排序索引，轻量化

#### 底层原理

ZSet 两层结构：

1. Hash表：`member → score`，O(1) 根据员工id查薪资
2. 跳表 SkipList：按score有序存储，**增删改查、范围查询都是 O(logN)**，天然有序，不用每次查询全量排序

排序规则：

1. 优先按 score（薪资）大小排序
2. 如果薪资相同（score相等），按 member（员工id）字典序排序

#### 业务坑点（面试必说）

1. **精度问题**：score是double浮点数，薪资很大或者小数很多会丢失精度；金额建议统一转成分（整数）存入score
2. **大Key风险**：全公司员工放同一个ZSet，员工量巨大变成大key；可以按部门拆分多个ZSet `salary_rank:dept:01`
3. **只适合实时榜单缓存**，**不能替代数据库**，以MySQL为准，Redis做查询加速；薪资变更同步更新ZSet（ZADD会自动覆盖更新score）
4. 多字段排序（薪资相同，按入职时间二次排序）：可以把薪资+时间编码成一个复合score

#### ✅ 45秒口述精简版

Redis用ZSet有序集合实现薪资排序。member存员工ID，score存薪资；底层是哈希表加跳表，哈希用来快速查薪资，跳表维护有序。ZREVRANGE实现薪资从高到低排序，ZRANGE升序。员工详情存在Hash。注意score是double，金额建议转整数避免精度丢失；数据量大按部门拆分防止大key。

#### 高频追问

Q：ZSet和MySQL order by排序区别？ MySQL是查询的时候才排序；ZSet是写入的时候就维护好顺序，查询直接取，高并发榜单性能更好。 Q：薪资相同怎么控制排序？ score一样时默认按member字典序；想要按入职时间排序，可以把薪资放大，低位拼接时间戳做成复合score。 Q：ZSet能不能分页？ 可以，`ZREVRANGE key start limit`，原生支持分页取TOPN。 Q：ZSet的跳表和平衡树对比？ 跳表实现简单、范围查询友好，Redis选择跳表而不是红黑树。

### 2. synchronized 写在哪、区别（面试官重点讲的这题！高频）

synchronized 可以修饰**实例方法、静态方法、代码块**，锁对象不一样，这是核心区别：
1. **修饰普通实例方法**：锁是 **this（当前实例对象）**
   同一个对象调用多个同步方法互斥；不同对象互不影响。
   
   ```java
   public synchronized void test(){}
   ```
2. **修饰static静态方法**：锁是 **类对象（XXX.class）**
   锁作用于整个类，所有实例共享这把锁，不同实例调用静态同步方法也会互斥。
   ```java
   public static synchronized void test(){}
   ```
3. **同步代码块**：自己指定锁对象，可以是this、obj、类.class，粒度可控，推荐！
   ```java
   synchronized (lockObj) {}
   ```
✅ 一句话总结：锁的对象不同，决定竞争范围；静态方法锁类，普通方法锁实例，代码块自定义锁。

### 8. List 和 Set 的区别

List、Set 都是 Collection 接口下的子接口，**Map 和 Collection 是平级，不属于它！**
- List：有序（插入顺序），允许元素重复；实现：ArrayList、LinkedList
- Set：不允许重复；HashSet无序，TreeSet有序；底层HashSet依托HashMap实现

### 9. ArrayList 和 LinkedList 区别

- ArrayList：底层动态数组；随机访问 get 快 O(1)；中间插入删除需要移动元素，效率低；内存连续
- LinkedList：双向链表；随机查找慢，需要遍历；头尾插入删除效率高；不支持随机索引访问；占用更多内存（存前后指针）

### 10. static变量 和 非static（实例变量）区别

1. static静态变量：属于**类本身**，类加载的时候初始化，**所有对象共享一份**；可以直接通过类名访问；JVM在方法区。
2. 实例变量（非static）：属于**每一个对象**，new对象的时候才创建，每个实例有独立副本，只能通过对象访问。

> 例子：static int a；new两个对象，改a，两个对象看到的a都会变。

```java
class Demo{
    static int a;    // 静态变量 / 类变量
    int b;           // 实例变量
}
```

#### 核心区别

1. **归属**
- static变量：属于**类**，不属于某个对象，全局一份。
- 实例变量：属于**实例（对象）**，每new一个对象，就单独一份。

2. **内存位置（JDK8之后）**
> JDK8：静态变量存在**元空间（Metaspace）**；实例变量跟着对象，在堆上。
> 旧版本永久代思路不用多说，面试讲元空间就行。

3. **初始化时机**
- static变量：**类加载的时候就初始化**，只初始化一次。
- 实例变量：**new 对象的时候**，创建实例才分配、初始化。

4. **访问方式**
- static：优先 `类名.变量名`；也可以对象访问（不推荐，编译器提醒）
  `Demo.a`
- 实例变量：**只能通过对象访问** `demo.b`

5. **生命周期**
- static：类加载时创建，类卸载才销毁，生命周期最长。
- 实例变量：对象创建产生，对象GC回收时销毁。

6. **共享特性（高频重点）**
static 所有对象共享同一份；一个对象修改静态变量，**所有对象看到的都是修改后的值**。
实例变量各个对象互相隔离，修改A对象的b，不影响B对象的b。

#### 简单示例

```java
Demo d1 = new Demo();
Demo d2 = new Demo();
d1.a = 10;
System.out.println(d2.a); // 输出10，共享
d1.b = 20;
System.out.println(d2.b); // 不是20，互不影响
```

#### 使用场景

- static变量：全局常量、计数器、全局配置（`public static final` 常量）
- 实例变量：每个对象独有的属性，比如用户的姓名、年龄

#### 30秒背诵精简版

静态变量属于类，类加载时初始化，元空间，所有对象共享一份；实例变量属于对象，new的时候在堆创建，每个实例独立。静态变量用类名访问；实例变量只能通过对象访问。

#### 常见追问

Q：能不能在static方法里访问实例变量？
答：**不能**。静态方法执行的时候，不一定有对象存在；实例变量依赖对象。反过来实例方法可以访问静态变量。

### 1. Java接口和抽象类：共同点 + 区别

**共同点**
都不能直接new实例；都可以定义抽象方法，供子类实现；都是用来做抽象定义、规范能力。

**区别**

1. 抽象类（abstract class）：用extends继承；一个类只能继承一个抽象类；可以有构造方法；成员变量不限修饰符；可以同时有普通实例方法、抽象方法。
2. 接口（interface）：implements实现；一个类可以实现多个接口；**没有构造方法**；Java8支持default、static方法，Java9支持私有方法；变量默认 public static final。

> 
> 一句话：抽象类偏向“是什么，继承复用”；接口偏向“具备什么能力，能力规范”。

### 2. 线程池核心参数（ThreadPoolExecutor 7个参数）

```
public ThreadPoolExecutor(int corePoolSize,
                          int maximumPoolSize,
                          long keepAliveTime,
                          TimeUnit unit,
                          BlockingQueue<Runnable> workQueue,
                          ThreadFactory threadFactory,
                          RejectedExecutionHandler handler)
```

- corePoolSize：核心线程数，常驻线程，默认不会回收
- maximumPoolSize：最大线程数 = 核心 + 非核心线程上限
- keepAliveTime + unit：非核心线程空闲保活时间 + 时间单位
- workQueue：阻塞任务队列，存放等待执行的任务
- threadFactory：线程工厂，创建线程，可以自定义线程名
- handler：拒绝策略，队列满、线程达到最大值时触发

### 3. 线程池接收新任务执行流程

1. 当前运行线程数 < 核心线程数：新建核心线程执行任务
2. 核心线程已满：任务放入阻塞队列排队
3. 队列也满了：新建**非核心线程**执行任务
4. 线程总数达到 maximumPoolSize：触发拒绝策略

### 4. 保活时间 keepAliveTime 作用

控制**非核心线程**空闲多久之后被回收。
避免短时间高峰过后，大量闲置线程占用内存资源；
核心线程默认不回收；可以开启 `allowCoreThreadTimeOut` 让核心线程也受保活时间控制。

### 5. 线程池常见任务队列

1. ArrayBlockingQueue：有界阻塞队列，固定容量
2. LinkedBlockingQueue：无界队列（默认容量很大），如果用它，队列永远不会满，最大线程数失效，风险：任务暴涨OOM
3. SynchronousQueue：不存储任务，直接转交，没有缓冲，来任务必须立刻有线程处理
4. PriorityBlockingQueue：优先级队列，任务按优先级执行

### 6. CAS是什么？底层原理

CAS：Compare And Swap，比较并交换，乐观锁。
三个参数：内存地址V、预期值A、新值B
逻辑：**如果V的值 == A，就把V更新成B；否则更新失败**。
底层依赖CPU硬件指令（cmpxchg），原子操作，不加锁。
优点：无锁，并发性能好；缺点：ABA问题、循环自旋消耗CPU、只能保证单个变量原子性。
解决ABA：版本号（AtomicStampedReference）。

### 7. JVM内存模型（JMM，不是运行时数据区！面试高频坑）

JMM（Java Memory Model），是抽象规范，目的解决多线程可见性、有序性问题。
规定：所有变量存主内存；线程操作变量，先拷贝一份到本地内存（工作内存），操作完写回主存。
三大特性：

- 可见性：volatile
- 原子性：CAS、synchronized
- 有序性：禁止指令重排，volatile、synchronized> 
> 区分：JMM是并发抽象规范；堆、栈、方法区这些是JVM运行时内存分区。

### 10. MySQL什么时候建索引；索引好处和代价

✅ 适合建索引场景：
经常出现在where条件、join关联字段、order by、group by的字段；区分度高（基数大）的字段。
❌ 不适合：低区分度（性别、状态）、频繁更新、数据量很小的表。
好处：加快查询速度，减少全表扫描。
代价：占用磁盘空间；增删改的时候需要维护索引，降低写入性能。

### 11. MySQL索引为什么用B+树，不用B树、红黑树

1. B+树叶子节点串联成链表，范围查询、排序非常方便；
2. 非叶子节点只存key，不存数据，单页能放更多索引键，树高度更低，IO次数更少；
3. 磁盘是页读取，B+树非常契合磁盘预读特性；
对比B树：B树每个节点存key+数据，节点存储数量少，树更高；
红黑树树高更高，不适合磁盘数据库索引。

### 12. 事务ACID

- 原子性 Atomicity：事务要么全部成功，要么全部回滚
- 一致性 Consistency：事务前后数据满足业务约束
- 隔离性 Isolation：多个并发事务之间互相隔离，由隔离级别控制
- 持久性 Durability：提交后数据持久落盘，崩溃不丢失

### 3. ArrayList、LinkedList 获取、删除元素效率差别

### 1. String、StringBuilder、StringBuffer

- **String**：字符串不可变；底层char[]（Java9改为byte[]）；拼接会生成新对象。
- **StringBuffer**：可变，所有方法加`synchronized`，**线程安全，性能较差**。
- **StringBuilder**：可变，无锁，**线程不安全，性能高，业务优先使用**。

### 2. String为什么不可变？

1. String底层value数组被 `final` 修饰，**数组引用不能指向新数组**；同时数组是private，外部拿不到引用，没有对外提供修改数组的方法。
> ⚠️注意：final修饰数组只是**引用不可变**，数组内部元素理论上可以反射修改；Java设计层面不暴露API，保证正常使用不可变。
2. 好处：字符串常量池复用、hashCode缓存、作为HashMap key安全、线程安全。

> 一句话口述：底层value数组private+final，没有提供修改内部字符的公开方法，保证正常使用下不可变。反射可以强行破坏，但不属于正常业务场景。

### 3. 进程和线程区别

1. **进程**：操作系统**资源分配最小单位**，拥有独立内存地址空间，进程之间相互隔离，切换开销大。
2. **线程**：进程内部执行单元，**CPU调度最小单位**；同一个进程内多个线程共享进程堆、方法区资源；线程切换开销小。
> 一个进程至少包含一个主线程。

### 4. 线程安全的集合

- 旧的同步集合：`Vector`、`HashTable`、`Collections.synchronizedXXX()`包装集合，全部方法加synchronized，锁粒度大，性能差。
- JUC并发集合（推荐）：
  - `ConcurrentHashMap`：Map并发安全
  - `CopyOnWriteArrayList`：读多写少，写时复制；写操作加锁，读不加锁；内存占用高，不适合大数据量频繁写
  - `CopyOnWriteArraySet`
  - 阻塞队列：`ArrayBlockingQueue`、`LinkedBlockingQueue`等

> 注意：HashMap、ArrayList、LinkedList都是线程不安全。

### 5. HashMap、Hashtable、ConcurrentHashMap

#### HashMap

线程不安全；key允许一个null，value允许null；JDK8底层数组+链表+红黑树；扰动函数；链表≥8且数组≥64树化。

#### Hashtable

线程安全，全部方法`synchronized`锁住整个对象；key、value**都不能为null**；只有数组+链表，没有红黑树；性能差，已经过时不推荐。

#### ConcurrentHashMap(JDK8)

线程安全；**CAS + synchronized锁桶头节点**，锁粒度只针对单个哈希桶；key、value都不能null；底层数组链表红黑树；相比Hashtable并发性能大幅提升。

> JDK7是Segment分段锁，JDK8废弃分段锁。

### 7. 5升杯子，3升杯子，得到4升水（智力题）

杯子A=5L，杯子B=3L
1. A装满：A=5，B=0
2. A倒给B，B满：A=2，B=3
3. 把B全部倒掉：A=2，B=0
4. A剩下的2升倒入B：A=0，B=2
5. A再次装满5升：A=5，B=2

### 8. 单链表找环 + 环的入口结点（快慢指针Floyd判圈算法）

#### 判断是否有环

快慢指针：slow一次走1步，fast一次走2步；
如果fast走到null，无环；如果slow==fast，**链表存在环**。

#### 找环的入口节点

相遇之后，**一个指针从链表头head出发，另一个指针从相遇点出发，两个指针每次都走1步，再次相遇点就是环入口**。

> 原理数学推导可以简单记：相遇后，头结点和相遇点同步前进，交点就是环入口。

伪代码思路：
```
slow=head,fast=head;
while fast!=null && fast.next!=null:
    slow=slow.next
    fast=fast.next.next
    if slow==fast: //有环
        p1=head; p2=slow;
        while p1!=p2:
            p1=p1.next;
            p2=p2.next;
        return p1 //环入口
```

### 2. 引用类型能不能用 ==

### 3. 重载 & 重写

- **重载 Overload**：同一个类内，方法名相同，参数列表不同（个数、类型、顺序）；返回值无要求；**编译期静态绑定**。
- **重写 Override**：父子类之间，方法名、参数列表、返回值一致；子类权限不能比父类严格；**运行期动态绑定（多态）**。

### 5. 接口 和 抽象类（共同点+区别）

#### 不同点

1. 抽象类用 `extends` 继承；接口用 `implements` 实现
2. 抽象类有构造方法；**接口没有构造方法**
3. 抽象类变量修饰符不限；接口成员变量默认 `public static final`（常量）
4. 一个类只能继承一个抽象类；可以实现多个接口

#### 共同点

都不能直接new对象；都可以定义抽象方法，支持多态；都支持泛型。

### 6. G1垃圾收集器

G1把整个堆切分成很多大小相同的Region，不再固定划分Eden、Survivor、老年代，每个Region可以充当新生代或者老年代。
特点：可预测停顿，优先回收垃圾最多的Region。
四个阶段：

1. **初始标记**：STW，标记GC Root直接可达对象
2. **并发标记**：和用户线程并发，遍历对象图
3. **最终标记**：STW，处理并发阶段新增的对象
4. **筛选回收**：STW，挑选收益最高的Region，复制存活对象到空闲Region，清理旧Region（复制算法，解决碎片）

对比CMS：CMS是标记清除，产生内存碎片；G1用复制算法整理内存，有STW，但可控。

### CMS 垃圾收集器

CMS：Concurrent Mark Sweep，**并发标记清除收集器**，JDK8默认老年代收集器，JDK9开始被G1替代。
> 核心：**标记-清除算法**，追求和用户线程尽可能并发，降低停顿时间。

#### 四大阶段（两个STW，两个并发）

1. **初始标记（STW）**
只扫描 GC Roots 直接可达的对象，速度很快。
2. **并发标记（并发，无STW）**
用户线程同时运行，顺着初始标记的对象，遍历整个老年代对象图。
> 并发期间用户线程还会产生新对象、修改引用，会产生**浮动垃圾**。
3. **重新标记（最终标记，STW）**
修正并发标记阶段因为用户线程运行而变动的引用（增量对象），停顿比初始标记长很多。
4. **并发清除（并发，无STW）**
清除标记为垃圾的对象，**不会整理内存**，标记清除，会产生内存碎片。

#### CMS特点

✅ 优点：
并发收集，低延迟，老年代GC停顿短。
❌ 缺点（高频考点）：
1. **标记清除，存在内存碎片**；碎片多了，明明总内存够，但找不到连续空间，触发FullGC。
2. 浮动垃圾：并发阶段新产生的垃圾，本次CMS没法回收，只能等下一次GC。
3. 占用CPU：并发阶段GC线程和用户线程抢CPU。
4. 有**预留空间**：不能等到老年代满了才GC，要提前启动；如果预留空间不够，会出现「并发失败」，退化成Serial Old，长时间STW。

#### CMS vs G1（直接背，面试官最爱问）

| | CMS | G1 |
|---|---|---|
| 算法 | 标记清除 | 标记复制 |
| 堆划分 | 传统Eden/Survivor/Old | Region分区，Region可灵活充当新生代/老年代 |
| 碎片 | 产生大量内存碎片 | 复制转移，自动整理，碎片少 |
| 停顿 | 不可预测 | 可预测停顿，可以设置目标停顿时间 |
| 回收策略 | 整个老年代一起扫描回收 | 优先回收垃圾最多的Region（收益优先） |
| 风险 | 并发失败，退化为串行收集 | 整体更稳定 |

#### 一句话精简版

CMS是并发标记清除收集器，分初始标记、并发标记、重新标记、并发清除；只有初始标记和重新标记STW。它并发低停顿，但会产生内存碎片，存在浮动垃圾、并发失败问题；G1用Region+复制算法，可预测停顿，解决碎片问题。

### 1.高并发如何保证数据一致性（仓库出库场景）

方案：
1. **悲观锁**：`synchronized`或者数据库行锁；访问数据先加锁，其他线程阻塞等待；适合写多冲突高场景。
2. **乐观锁**：版本号机制，不加锁；更新时校验版本号，版本不匹配就重试；适合读多写少。
3. 数据库事务+行级锁，保证出库业务原子性。
4. 也可以使用Redis分布式锁，应对多服务实例并发。

### 4.死锁产生4个必要条件、解决方法

**四个条件（必须全部满足才会死锁）**
1. 互斥：资源同一时间只能被一个线程占用；
2. 占有且等待：线程持有一把锁，同时等待其他锁；
3. 不可剥夺：已经拿到的锁不能被其他线程强行抢占；
4. 循环等待：线程互相等待对方手里的锁，形成环路。

**解决思路：破坏任意一个条件**
1. 破坏占有等待：一次性申请所有需要的锁；
2. 破坏循环等待：**统一锁获取顺序**，所有线程按相同顺序申请锁；
3. 使用tryLock超时获取，拿不到直接放弃，避免死等。

### 5.事务在高并发购票中的应用

高并发下要配合：数据库行锁、乐观锁防止超卖；同时要注意事务粒度，事务不要开太大，避免长事务带来性能问题。

### RabbitMQ + RocketMQ 原理

#### 一、RabbitMQ（Erlang，AMQP协议，核心：交换机+队列模型）

##### 核心组件

Producer → Exchange（交换机）→ Binding（绑定规则）→ Queue（队列）→ Consumer

> ✅ 生产者**不直接发给队列，只能发给交换机**；交换机负责路由分发

4种交换机类型（必背）

1. **Direct**：routingKey 和 bindingKey 完全相等，精准路由
2. **Fanout**：广播，忽略routingKey，消息发给所有绑定队列
3. **Topic**：通配符匹配 `*` 匹配一个词、`#` 匹配0或多个词，最常用
4. **Headers**：按消息header匹配，很少用

##### 关键机制

1. **Channel**：TCP连接之上的轻量虚拟连接，一个TCP连接开多个Channel，减少TCP开销
2. **ACK确认机制**：消费端手动ACK，Broker收到ACK才删除消息；NACK可以重回队列/死信
3. **死信队列DLX**：消息超时、拒绝、队列满时转发到死信交换机
4. 集群：普通集群（元数据共享，消息在原节点）、仲裁队列Quorum（Raft，高可用）
5. 消费模式：推模式（Broker主动push消息给消费者）为主

##### 流程一句话

生产者发送消息携带routingKey到交换机，交换机根据绑定规则路由到对应队列，消费者监听队列消费，ACK确认后消息删除。

#### 二、RocketMQ（Java，阿里开源，自定义TCP协议，核心：Topic+CommitLog存储）

##### 四大核心角色

1. **NameServer**：无状态注册中心，Broker定时上报信息；生产者、消费者从NameServer查询Topic对应的Broker地址，替代ZK，轻量
2. **Broker**：消息存储核心，主从架构（同步刷盘/异步刷盘；同步复制/异步复制）
3. **Producer**：生产者，发送消息到Topic
4. **Consumer**：消费者，**拉模式pull**为主

概念：

- **Topic**：消息一级分类；**Tag**：同一Topic下二级过滤标签

- **MessageQueue**：Topic拆分出来的物理队列（分区），分布在多个Broker，并行读写；同一个队列内消息有序

- ConsumerGroup消费组：

  - 集群消费：组内多个消费者分摊队列，一条消息只被组内一个消费（负载均衡）
- 广播消费：组内每个消费者都收到全量消息

##### 存储三层结构（面试重中之重）

1. **CommitLog**：所有Topic消息**顺序追加写入**同一个物理文件（1G一个），原始消息本体，顺序写磁盘，吞吐高
2. **ConsumeQueue**：消费索引文件，每个Topic+队列单独一份；存消息在CommitLog里的offset、长度、tag hash；消费时先查索引，再定位CommitLog读消息
3. **IndexFile**：哈希索引，支持按msgId、key检索消息

> 特点：**消息是否被消费，不影响CommitLog，消息按存储时长过期删除，不是消费完立刻删**，消费进度offset单独记录。

##### 经典特色能力（面试加分）

1. **事务消息（半消息机制）**：解决下单等场景 DB 和消息的最终一致性，支持 Broker 事务回查；
2. **延时消息**：内置延时等级，适合 30 分钟未支付关闭订单；
3. **顺序消息**：同一个队列保证有序；
4. **消息重试、死信队列**：消费失败重试，多次失败进入死信。

##### 消息刷盘 & 副本策略

- 刷盘：**同步刷盘**（落盘成功才返回生产者，安全，慢） / **异步刷盘**（写入 PageCache 就返回，吞吐高，宕机有丢消息风险）
- 主从复制：同步复制、异步复制

#### ✅ 45秒口述精简版

RabbitMQ基于AMQP，核心是交换机和队列；生产者发给交换机，交换机按绑定规则路由到队列，消费以推模式为主，路由能力灵活。 

RocketMQ 由 NameServer、Broker、生产者、消费者组成。NameServer 做服务发现；Broker 是存储核心，采用 CommitLog 顺序写，搭配 ConsumeQueue 索引。消息按 Topic 拆分出 MessageQueue，同队列消息有序；消费组支持集群和广播消费。消费是拉模式。原生支持事务消息、延时消息。支持同步 / 异步刷盘、主从副本保证可靠性。

#### 高频追问预备

Q：推模式和拉模式区别？ 

RabbitMQ默认推，实时性好；流量大容易压垮消费端；RocketMQ拉模式，消费者自己控制速度，可控性更强。 

Q：CommitLog顺序写优势？

 磁盘顺序写远快于随机写，支撑高吞吐，海量消息堆积能力强。 

Q：RabbitMQ有没有事务消息？ 

原生没有，只能本地消息表/事务消息表方案。 

Q：消息丢失怎么防？ 生产者确认、持久化、消费ACK、主从副本。





### MQ在订单业务里怎么用（以RocketMQ为主，电商最常用）

> 核心定位：MQ**不负责生成订单、不承担订单核心事务**，主要做**异步解耦、削峰、可靠通知、最终一致性**。
> 订单主流程还是数据库事务，MQ用来剥离非核心、耗时的下游动作。

#### 一、先区分两种最常见场景

##### 场景1：下单成功后，异步发送通知（普通异步消息，最常用）

业务：用户下单 → 主库创建订单（DB事务提交） → 发MQ消息
消息内容：订单号、用户ID、金额、商品信息
消费者拿到消息，异步执行：

- 扣减优惠券、积分
- 发送短信、站内信
- 生成物流单、通知仓储发货
- 订单统计、报表、大数据埋点

优点：短信、仓储这些逻辑慢，如果同步写，下单接口RT高；MQ异步，下单立刻返回，提升接口响应。
风险点：**DB事务提交成功，MQ发送失败 → 下游没执行，数据不一致**

##### 场景2：下单和发消息要保证原子性（核心！订单事务消息）

需求：**数据库订单创建成功，则消息一定发出；数据库回滚，则消息一定不发出**
👉 RocketMQ 原生【事务消息】方案（订单支付、下单经典方案）
流程（半消息机制）：

1. Producer 发送 **半消息（Prepare消息）** 给Broker；Broker收到消息，标记为不可投递，不发给消费者
2. Broker响应成功后，执行本地数据库事务：新增订单
   - ✅ 本地事务成功：提交事务消息 → Broker消息变为可见，消费者可以消费
   - ❌ 本地事务失败：回滚事务消息 → Broker直接删掉这条消息
3. 如果Broker长时间没收到提交/回滚指令（服务宕机），Broker会主动**事务回查**：调用生产者的回查接口，查询这个订单是否存在
   - 订单存在 → commit
   - 订单不存在 → rollback

> ⚠️ RabbitMQ没有原生事务消息，要用**本地消息表（可靠消息表）**实现最终一致：
> 在同一个本地事务里：插入订单记录 + 插入 `msg_log` 消息记录；再单独一个定时任务轮询msg_log，发送MQ，发送成功标记状态。

#### 二、订单支付的延时消息（高频加分）

需求：下单后30分钟未支付，自动关闭订单、释放库存
RocketMQ 延时消息：
下单成功发送一条延时消息（30min）；消费者等到时间收到消息，查询订单状态：
- 如果状态还是【待支付】：关闭订单，释放库存
- 如果已经支付：直接忽略这条延时消息

> 坑：不能用定时任务扫表做超时关闭，量大的时候数据库压力巨大；延时消息是最优方案。

#### 三、消费端幂等（订单MQ必讲！高频考点）

MQ可能重复投递，同一个订单消息可能多次被消费，下游（扣积分、出库）不能重复执行
幂等方案：
1. 消费前根据 **订单号** 查询消费记录表，已经消费过直接return；消费成功再落记录（唯一索引防重复）
2. 利用订单业务状态机判断：比如订单已经【已发货】，再次收到发货消息直接跳过

#### 四、消息丢失保障链路（一条线背）

1. 生产者：事务消息/本地消息表保证消息可靠发出
2. Broker：开启消息持久化 + 主从复制，防止Broker宕机丢消息
3. 消费端：关闭自动ACK，业务逻辑执行成功之后手动ACK；失败可以重试；多次失败进入死信队列人工排查

#### ✅ 45秒口述精简版

订单场景使用MQ主要三个用法：第一，下单成功后异步处理短信、仓储、积分等非核心逻辑，解耦提速；第二，用RocketMQ事务消息保证创建订单和发消息的最终一致性，防止DB和消息不一致；第三，延时消息实现30分钟未支付自动关单释放库存。消费端必须做幂等处理，因为MQ会重复投递，同时配合持久化、手动ACK防止消息丢失。

### 不使用MQ，怎么实现订单里那些异步、解耦、超时能力

> 核心前提：**主订单创建本身不需要MQ，本来就是数据库事务直接insert订单**。MQ解决的是三件事：异步下游逻辑、30分钟超时关单、削峰。去掉MQ之后，这些能力就要换方案实现，代价各不一样。

#### 一、下单后的下游异步逻辑（短信、扣积分、通知仓库、埋点统计）

原来MQ方案：下单DB事务提交 → 发消息 → 消费者异步执行
不用MQ，可选方案：

##### 方案1：同步调用（最简单，但是缺点明显）

下单事务里面，创建订单之后，同步调用短信、积分、仓储接口。
✅ 优点：实现简单，一致性直观
❌ 缺点：

1. 下单接口RT变长；
2. 下游任一服务慢/超时，会拖慢下单，甚至导致下单失败；
3. 雪崩风险：流量大的时候所有下游一起扛压。

> 适合：并发很低、下游很少的小系统；高并发订单服务基本不推荐。

##### 方案2：本地消息表 + 定时任务轮询（替代MQ，最终一致性）

同一个数据库事务里面：**insert order + insert message_record（消息表，状态：待发送）**
单独起定时任务（比如每1s扫一次msg表）：
查出状态=待发送、超时未处理的记录，调用下游接口；调用成功更新状态为已完成；失败标记失败，重试几次，多次失败标记人工处理。
✅ 优点：不需要中间件，DB自带事务保证；RabbitMQ没有事务消息时也是这套思路
❌ 缺点：轮询有延迟；扫表如果不加好索引，量大了DB压力大；要控制分页、避免锁表。

##### 方案3：线程池异步（JVM内异步）

创建订单事务提交成功后，提交任务到线程池去发短信、扣积分。
❌ 致命短板：**服务宕机，线程池队列里没执行的任务直接丢失，没有持久化，不可靠**。只适合允许丢失的非核心日志，订单业务不能用来做可靠操作。

#### 二、超时关闭订单（30分钟未支付自动关单、释放库存）

原来：RocketMQ延时消息
不用MQ，主流方案：**定时任务扫描订单表**
SQL示例：
```sql
select * from order 
where status = 'WAIT_PAY' 
and create_time < now() - interval 30 minute;
```
查到待关单订单，在事务里：修改订单状态、释放库存。
✅ 简单好上手
❌ 坑非常多：
1. 全表扫描压力巨大，必须建索引 `idx_status_ct(status,create_time)`；
2. 定时任务如果单机，单点故障；多机部署要加分布式锁（Redisson）防止重复关单；
3. 扫描间隔不能太小，所以存在时间误差（比如1分钟扫一次，最多晚1分钟关单）；
4. 流量大、订单量千万级，扫表会把数据库打崩。

> 优化版本：分片扫描，按订单ID分片，多个实例分担压力。

#### 三、削峰（大促流量突增场景）

MQ的一个作用是缓冲流量，削峰填谷。没有MQ：
1. 前端限流、验证码、排队页；
2. 网关层限流（Sentinel）；
3. 数据库连接池限流；
4. 也可以用Redis做令牌桶限流。
但是没有缓冲队列，突发流量直接打到DB，更容易压垮。

#### 四、幂等和重试怎么处理

同步调用：捕获异常，业务层重试（注意幂等！）；
定时任务扫表：靠消息记录/订单状态机保证幂等，同一个订单不要重复扣库存。

#### ✅ 45秒口述精简版

不使用MQ，订单主流程本身直接用数据库事务创建订单。原来MQ承担的异步下游逻辑，可以同步调用（简单但拖慢接口）或者本地消息表加定时任务轮询实现可靠异步；不推荐线程池异步，宕机容易丢任务。30分钟超时关单用定时任务扫描待支付订单，需要建立联合索引、分布式锁防止重复处理。缺点是定时任务有延迟，大数据量下数据库压力比MQ方案大，大促场景缺少削峰缓冲。

#### 高频追问

Q：本地消息表方案和MQ事务消息对比？
本地消息表不需要中间件，但需要自己开发定时轮询、重试、失败处理；MQ把这些能力内置在Broker，开发量更小、吞吐更高。

Q：定时任务扫订单关单，如果订单量很大怎么办？
按ID分片、分库分表，控制每次扫描数量；避免长事务；也可以用Redis的zset做时间轮方案。

Q：Redis时间轮怎么实现超时关单？
把待支付订单放到zset，score=到期时间；定时任务轮询zset，取出score小于当前时间的订单处理，比扫数据库更快，但也要持久化兜底，防止Redis宕机丢失数据。

### Java引用数据类型

Java的数据类型分为两大类：**8种基本数据类型** 和 **引用数据类型**。
核心定义：引用类型的变量里存储的**不是对象本身**，而是对象在堆内存中的地址；真正的对象实例存放在堆中。

#### 1. 引用数据类型有哪些

- 类（Class）：自定义实体类、String、Integer、HashMap、ArrayList等
- 接口（Interface）：List、Runnable、Map等，接口本身不能实例化，变量指向它的实现类对象
- 数组（Array）：`int[]`、`String[]`、`User[]`，**数组本身一定是引用类型，和数组里面存什么无关**
- 枚举（Enum）
- 注解（Annotation）

> 重点区分：`int` 是基本类型；`Integer`、`Long` 包装类是引用类型；`String` 是类，属于引用类型。

#### 2. 引用类型 vs 基本类型核心差异

1. 存储内容
- 基本类型：栈中直接存放真实数值
- 引用类型：栈中存放对象地址，依靠地址去堆中找到对象
```java
int a = 10;
User u = new User();
```
`a` 在栈上直接存10；`u` 在栈上存堆里User对象的地址。

2. 默认值
- 基本类型有数值默认值：int默认0，boolean默认false
- 引用类型默认值：`null`，代表当前引用没有指向任何堆对象

3. 赋值机制
- 基本类型：值拷贝，两个变量互不干扰
- 引用类型：地址拷贝，多个引用指向同一个堆对象；通过任意引用修改对象属性，其他引用都能看到变化
```java
User u1 = new User();
User u2 = u1; // u2和u1指向同一个对象
```

#### 3. ⚠️ 极易混淆：引用数据类型 ≠ JVM四种引用（加分项）

这是两个完全独立的概念，面试官很喜欢在这里挖坑：
- **引用数据类型**：属于Java语法层面，描述这是一类数据类型（类、数组等）
- **四种引用（强/软/弱/虚）**：属于JVM GC层面，描述**对象被引用的强度，控制GC回收时机**
  1. 强引用：`User u = new User()`，只要强引用存在，GC绝不回收
  2. 软引用 SoftReference：内存不足快要OOM时才回收，适合做缓存
  3. 弱引用 WeakReference：只要发生GC就会被回收，典型：ThreadLocal的key
  4. 虚引用 PhantomReference：不能通过引用拿到对象，只用来接收GC回收通知，常用于堆外内存清理

#### ✅ 45秒口述精简版

Java引用数据类型包含类、接口、数组、枚举、注解。引用变量存的是堆对象的地址，不是对象本身，默认值是null。赋值时传递地址，多个引用可以指向同一个对象。一定要区分开：这是语法上的类型分类，和GC层面的强、软、弱、虚四种引用不是一回事。

#### 高频追问（配套答案）

Q：String是引用类型，`==` 和 `equals()` 的区别？
A：`==` 判断两个引用是不是同一个对象（比较地址）；`equals()` 默认也是比较地址，String重写之后用来比较字符串内容。

Q：`int[]` 里面存的是int基本类型，数组本身是引用类型吗？
A：是的，数组本身永远是引用类型。

Q：包装类Integer是引用类型吗？
A：是，属于类，引用类型；Integer有IntegerCache缓存池。

Q：null可以赋值给基本类型吗？
A：不行，null只能赋值给引用类型，表示不指向任何对象。

### 原题4：如果不用MQ，要实现这个订单功能怎么办？（面试者答：生产者消费者模式）

> 面试官意图：让你自己在JVM内模拟简易MQ，实现下单后异步处理下游业务。
#### 完整回答

可以自己实现生产者‑消费者模式：
1. 下单主线程（生产者）：创建完订单DB事务提交后，把需要异步处理的消息（订单号等）放到**内存阻塞队列**；
2. 后台多个消费者线程，循环从队列取出消息，执行发短信、扣积分、通知仓储这些异步业务。

⚠️ 内存集合普通`ArrayList`不行，线程不安全，要用JDK `BlockingQueue`阻塞队列。
> 补充缺点：JVM内存队列，服务重启队列里未处理消息全部丢失，**不能用于可靠订单业务，只适合允许丢数据场景**；要可靠需要搭配本地消息表+定时任务持久化。
>
> `ArrayBlockingQueue` ： 内部用 `ReentrantLock` + 两个 `Condition`（notEmpty、notFull）
>
> - put：队列满时 `notFull.await()` 阻塞生产者；有空位时 `signal`
> - take：队列空时 `notEmpty.await()` 阻塞消费者；有数据时 `signal`
>
> > 它的入队、出队操作都加锁保护，多线程并发 put/take 不会出现并发异常，不需要我们自己额外加 synchronized。

### 原题5：把消息放在集合里面，如果集合满了怎么办？（面试者：生产者丢弃消息，通知消费者）

#### 标准答案

阻塞队列满的时候，有多种策略，不能直接粗暴丢弃：
1. **丢弃消息**：直接丢弃，适合允许丢失的非重要业务，同时打日志告警；
2. **阻塞等待**：生产者阻塞，直到队列有空位；会阻塞下单主线程，拖慢下单接口；
3. **抛出异常**，上层捕获做降级；
4. **溢出写到磁盘/数据库**：把满了的消息持久化落库，后续再消费，保证不丢消息（订单业务优先选这个）。

> 不建议直接丢弃订单相关消息，会造成业务数据不一致。

### 原题6：集合满了怎么通知消费者？

面试者答案：volatile变量，满false、不满true做线程通信

#### 点评：这个方案**有很大缺陷**，volatile只能保证可见性，不能做等待唤醒。

1. volatile布尔变量，生产者修改flag，消费者能立刻看到；但是消费者需要死循环轮询这个flag，空轮询消耗大量CPU。
2. 正确Java线程间通知方式：
- 方式1：`BlockingQueue`底层使用 `ReentrantLock + Condition`条件变量，`await()`等待，`signal()`唤醒；不需要轮询。
- 方式2：`wait() / notify()` 等待通知机制。

✅ 面试满分回答：
单纯volatile变量要消费者不停轮询，CPU浪费严重，不推荐。应该使用条件变量Condition的await、signal机制。队列满的时候生产者await；队列有数据的时候signal唤醒消费者线程，实现线程间等待‑通知，不需要轮询。

### 原题7：多个消费者怎么解决冲突？（面试者回答：MQ消费者组）

#### 回答拓展（自己手写简易模型如何实现）

RocketMQ消费者组：同一个消费组内，一个MessageQueue只能分配给一个消费者，避免多个消费者处理同一份消息，实现负载均衡。

如果自己手写简易版本：
1. 队列里面每条消息被取出之后，先不要直接删除；标记这条消息为处理中；
2. 其他消费者拿到消息先判断状态，如果已经被处理中，跳过这条消息；
3. 业务消费成功再删除消息；消费失败，超时后消息重新放回队列。
> 模拟MQ的offset、消息重试。
> 同时要考虑并发，队列本身要线程安全，或者加锁。

### 原题8：如果让你自己实现简易MQ，你怎么做？

> 面试者当时不会，下面是完整回答，模拟简易消息中间件。
#### 整体架构

1. **存储层**
- 内存阻塞队列做高速读写；内存满了把消息持久化到磁盘/数据库（本地消息表），防止宕机丢失。
- 每条消息设计字段：msgId、topic、body、status（待处理/处理中/已完成）、createTime。
2. **生产者**：发送消息到队列；队列满执行溢出策略（落库、告警）。
3. **消费模块**：多消费者线程；取消息标记为处理中；消费成功更新状态；消费失败超时，消息重新放回队列；多次失败进入死信。
4. **线程通信**：使用`Lock + Condition`做等待唤醒，而不是volatile轮询。
5. **可靠性问题**：JVM内存队列会丢消息，持久化存储必不可少；做幂等防止重复消费。
6. 短板对比RocketMQ：缺少NameServer注册中心、主从复制、事务消息、延时消息等高级能力。

### 原题9：讲解推荐算法

> 简单口述版（面试够用）
推荐算法分三大类：
1. **协同过滤CF**
- 用户协同：喜欢A的用户也喜欢B，找相似用户做推荐；
- 物品协同：买过A商品的用户还买B，计算物品相似度。
缺点：冷启动，新用户新物品没有行为无法推荐。

2. **基于内容推荐**：根据物品本身属性（标签、分类），给用户推荐属性相似物品；解决物品冷启动，但是多样性差。

3. **深度学习模型（现在工业界主流）**：如DeepFM、DIN，把用户特征、物品特征、行为特征输入模型，预测用户点击/购买概率，按分数排序推荐。

补充：召回 + 排序两阶段。召回从千万物料粗筛出几百候选集；排序做精细打分，输出最终结果。

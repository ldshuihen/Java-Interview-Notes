### 1. SQL 子查询 EXISTS 和 IN 的区别

1. **性能差异（核心：驱动表、短路匹配）**
- `EXISTS`：属于**半连接**，只判断子查询有没有返回数据，**找到第一条匹配记录就短路返回 true，不需要遍历全部结果集**。
  ✅ 子查询结果量大时优先用 `EXISTS`，性能更好。
- `IN`：先把子查询的所有结果全部查出来，生成一个结果集合，再让外层字段去集合里做等值匹配。
  ❌ 子查询返回数据集很大时，`IN` 效率差，还有超长集合报错风险。
> 小结：子查询数据量小，二者差别不大，可以互换；子查询数据量大，优先 `EXISTS`。

2. **NULL 值处理差异（高频坑点）**
- `EXISTS`：不受 NULL 影响，只关心子查询是否有行返回，不做值比较。
- `IN`：集合里存在 NULL 时，`column IN (..., NULL)` 的比较结果是 `unknown`，会丢失数据，出现不符合预期的查询结果。

### 2. SQL 如何优化

1. **定位慢 SQL、分析执行计划**
使用 `EXPLAIN` / `EXPLAIN ANALYZE` 查看执行计划，定位全表扫描、索引失效、Join 顺序问题等瓶颈。
2. **索引优化**
检查索引是否生效，避免索引失效场景（函数运算、隐式类型转换、or、like 前缀通配等）；建立联合索引遵循最左前缀原则。
3. **SQL 语句写法优化**
- 禁止 `select *`，按需查询字段，减少磁盘IO、网络IO；
- 合理使用 `LIMIT` 分页；
- 避免大事务、避免在循环里执行 SQL；
- 减少不必要的子查询、嵌套，优先 Join。
4. **表分区**
超大表做水平/垂直分区，查询直接定位目标分区，减少扫描的数据量，分区上也可以单独建立索引。
5. **架构层面优化**
- 读写分离：主库负责写，从库承担读请求；
- 分库分表：数据量持续膨胀，单库单表扛不住时，水平分库分表（Sharding）。

### 4. 分布式锁常见实现方案

分布式锁：在分布式多节点环境下，控制同一时刻只有一个客户端操作共享资源，保证并发安全。
1. **数据库实现**
- 悲观锁：`select ... for update` 行锁；简单，高并发下数据库压力大，容易阻塞。
- 乐观锁：版本号/时间戳，更新时校验版本，失败重试；无阻塞，适合读多写少。
- 唯一索引：利用唯一约束抢锁，插入成功即获取锁。
2. **Redis 实现**
- `SET key value NX EX`：原子命令获取锁，设置过期时间防止死锁；
- Redlock：多独立 Redis 节点共同投票的分布式锁算法，追求更高可用性。
3. **Zookeeper 实现**
利用**临时有序节点**实现，天然具备：锁自动释放（会话断开临时节点删除）、阻塞等待、公平锁特性；Zk 强一致，性能弱于 Redis。
4. 补充：消息队列一般**不是标准分布式锁**，只是通过限制消费者并发数达到限流效果，不推荐当做分布式锁方案。

> 补充面试一句话：Java 的 `ReentrantLock` 是本地锁，只能管控单 JVM，不能直接用于分布式。

### 5. JVM 原理

JVM（Java虚拟机）：跨平台的运行时环境，把 `.class` 字节码解释/编译成机器码执行，实现“一次编译，到处运行”。

#### 5.1 JVM 核心组成

1. **类加载器 ClassLoader**
负责加载 `.class` 字节码到内存，核心三类：
- 启动类加载器 Bootstrap ClassLoader：加载核心 JDK 类库
- 扩展类加载器 Extension ClassLoader：加载扩展包
- 应用程序类加载器 Application ClassLoader：加载项目自定义类
遵循**双亲委派模型**：加载请求先交给父加载器，父加载器加载不到，自己才加载；作用：防止核心类被重复加载、安全隔离。

2. **运行时数据区（内存模型）**
- 程序计数器：线程私有，记录当前字节码执行行号，唯一一个没有 OOM 的区域
- 虚拟机栈：线程私有，存放局部变量表、方法栈帧、返回地址
- 本地方法栈：线程私有，为 native 本地方法服务
- 堆 Heap：线程共享，**所有对象实例、数组分配在这里，GC 主要工作区域**
- 方法区：线程共享，存放类元信息、常量池、静态变量、即时编译代码（JDK8 之后是元空间 Metaspace，使用本地内存）

3. **执行引擎**
- 解释器：逐行解释字节码，启动快；
- JIT 即时编译器：识别热点代码，编译成本地机器码，大幅提升执行速度。

4. **GC 垃圾回收器**：自动回收堆中不再被引用的对象。

#### 5.2 类的完整生命周期

加载 → 链接（验证、准备、解析） → 初始化 → 使用 → 卸载
- 加载：读取字节码，在内存生成 Class 对象
- 验证：校验字节码合法性
- 准备：给静态变量分配内存、赋默认初始值
- 解析：符号引用转为直接引用
- 初始化：执行静态代码块、静态变量赋值

#### 5.3 GC 分代模型

堆分为年轻代、老年代：
- 年轻代：Eden + S0 + S1，新对象优先分配在这里；存活对象经过多次 GC 晋升到老年代；回收叫 Minor GC，速度快，采用**复制算法**。
- 老年代：存放长期存活的大对象；GC 叫 Major GC / Full GC，开销大；使用**标记-整理**算法。

GC 基础算法：
- 标记清除：标记垃圾，直接清除；产生内存碎片
- 复制：存活对象复制到新空间，原空间清空；无碎片，需要预留一块内存
- 标记整理：标记后，存活对象向一端压缩整理，消除碎片

#### 5.4 常见垃圾回收器

- Serial GC：单线程 GC，适合客户端、小应用
- Parallel GC：多线程并行回收，主打高吞吐量
- CMS：并发标记清除，追求低停顿；存在内存碎片，JDK8 默认，JDK9 废弃
- G1：分区化 GC，可预测停顿，兼顾吞吐量和延迟
- ZGC / Shenandoah：超低延迟回收器，大堆低延迟场景

#### 5.5 常用 JVM 参数

内存：
- `-Xms`：初始堆大小
- `-Xmx`：最大堆大小
GC：
- `-XX:+UseG1GC` 启用G1
- `-XX:+UseZGC` 启用ZGC
日志：
- `-verbose:gc`、`-XX:+PrintGCDetails` 打印GC日志

#### 5.6 JVM 调优思路

1. 根据业务选型 GC 回收器（高吞吐选 Parallel，低延迟选 G1/ZGC）
2. 合理设置堆内存，避免频繁GC、避免过大堆导致单次GC停顿太久
3. 代码层面减少短生命周期对象创建，复用对象，降低GC压力
4. 借助JIT，热点代码自动优化

### 1. 单例模式：特点 + 实现方式

**特点**

1. 一个类在整个JVM中**只有一个实例对象**；
2. 私有化构造方法，禁止外部 new；
3. 提供一个静态方法/静态变量，对外返回这个唯一实例；
4. 保证线程安全、防止序列化、反射破坏（进阶考点）。

**常见实现**
1. **饿汉式（简单，线程安全）**
类加载的时候直接初始化实例；缺点：类加载就创建，浪费内存。
```java
public class Singleton {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton(){}
    public static Singleton getInstance(){return INSTANCE;}
}
```
2. **懒汉式（非线程安全，基本不使用）**
调用getInstance才创建，多线程会创建多个实例。
3. **双重检查锁 DCL（Double-Check Locking，工作最常用）**
`volatile` 禁止指令重排，防止半初始化对象暴露。
```java
public class Singleton {
    private static volatile Singleton instance;
    private Singleton(){}
    public static Singleton getInstance(){
        if(instance == null){
            synchronized (Singleton.class){
                if(instance == null){
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```
4. **静态内部类（推荐，简洁线程安全，懒加载）**
利用类加载机制，内部类只有调用时才加载。
```java
public class Singleton {
    private Singleton(){}
    private static class Inner{
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance(){
        return Inner.INSTANCE;
    }
}
```
5. **枚举单例（最安全，防止反射、序列化破坏）**
Effective Java推荐写法。
```java
enum Singleton{
    INSTANCE;
}
```

> 一句话总结：项目里优先静态内部类 / DCL；框架底层很多用枚举单例。

  - LinkedList：双向链表，插入删除快，查询慢
  - Vector：数组，线程安全，效率低，淘汰
- Set：无序（TreeSet有序）、不可重复
  - HashSet：底层HashMap，无序
  - LinkedHashSet：链表+哈希，插入有序
  - TreeSet：红黑树，可排序
- Queue：队列，先进先出
  - ArrayDeque：数组双端队列，推荐代替Stack
  - PriorityQueue：优先队列（堆）

#### Map

- HashMap：数组+链表+红黑树，key不可重复，无序，线程不安全
- LinkedHashMap：HashMap+双向链表，插入有序，可做LRU缓存
- TreeMap：红黑树，key自动排序
- HashTable：线程安全，效率低，不推荐
- ConcurrentHashMap：分段锁/Node锁，高并发推荐

> 面试加分：HashMap 1.7头插法，1.8尾插；链表长度≥8转红黑树，≤6退链表。

### 3. Java异常体系

Throwable 是顶层父类，分为两大分支：**Error 和 Exception**
1. **Error**：系统级严重错误，程序无法处理，直接崩溃。比如 OOM、StackOverflowError。
2. **Exception**：程序可捕获处理的异常，分为
   - **受检异常（Checked Exception）**：编译期必须处理，要么try-catch，要么throws抛出。例：IOException、SQLException
   - **非受检异常（RuntimeException 运行时异常）**：编译不强制捕获，代码问题导致。例：NullPointerException、ArrayIndexOutOfBoundsException、ClassCastException

关键字：
- try：包裹可能出异常代码
- catch：捕获处理异常
- finally：无论是否异常都会执行（唯一不执行：System.exit()），用来释放资源
- throw：手动抛出单个异常对象
- throws：方法声明抛出异常，交给调用方处理

> 最佳实践：不要空catch吞异常；尽量精准捕获，不要直接catch Exception。

### 4. Java四种引用（非常高频）

从强到弱：**强引用 → 软引用 → 弱引用 → 虚引用**
1. **强引用（默认）**
`Object o = new Object()`；只要引用存在，GC永远不回收；内存不足直接OOM。
2. **软引用 SoftReference**
内存充足不回收；内存不够即将OOM时，GC回收。适合做缓存。
3. **弱引用 WeakReference**
只要发生GC，不管内存够不够，一定会回收。典型：ThreadLocal的key、WeakHashMap。
4. **虚引用 PhantomReference**
最弱，无法通过get拿到对象；只用来监听对象回收时机，配合引用队列，做堆外内存释放（NIO ByteBuffer）。

### 5. Java创建线程的4种方式

1. 继承 Thread 类，重写 run()；调用 start() 启动（start会调用native方法，创建线程，不是直接run）
2. 实现 Runnable 接口，重写 run()；传给Thread构造；**推荐，避免单继承限制**
3. 实现 Callable 接口 + FutureTask：有返回值、可抛异常；Runnable没有返回值
4. 线程池 ExecutorService：生产环境首选，复用线程，避免频繁创建销毁开销

> 重点区分：`run()` 只是普通方法；`start()` 才是真正向操作系统申请创建线程。

### 6. wait() 和 sleep() 的区别

1. **所属类不同**
wait：Object方法；sleep：Thread静态方法
2. **锁行为（核心考点）**
wait：**释放monitor锁**，进入等待队列；
sleep：**不释放锁**，抱着锁休眠。
3. **唤醒方式**
wait：需要 notify() / notifyAll() 唤醒，或者设置超时；
sleep：时间到自动恢复。
4. **使用场景与位置**
wait：必须在 synchronized 同步块内调用；
sleep：任意地方都可以调用。
5. **异常**
sleep 需要捕获 InterruptedException；wait也会抛出。

一句话口诀：wait放锁、sleep抱锁；wait靠notify唤醒。

### 8. Spring 事务传播特性（7种，背核心5个即可）

Propagation：多个事务方法嵌套调用时，事务怎么传递
1. **REQUIRED（默认）**：有事务就加入当前事务；没有就新建事务。最常用。
2. **SUPPORTS**：有事务就加入；没有就非事务执行。
3. **MANDATORY**：必须在已有事务里运行，外层无事务直接抛异常。
4. **REQUIRES_NEW**：**新建独立事务**，挂起外层事务；内外事务互不影响，各自回滚。
5. **NOT_SUPPORTED**：以非事务运行，挂起外层事务。
6. **NEVER**：强制非事务，如果外层存在事务抛异常。
7. **NESTED**：嵌套事务，有保存点savepoint；子事务回滚不会影响外层；外层回滚连带子事务一起回滚。（依赖数据库savepoint，MySQL InnoDB支持）

> 高频对比：REQUIRES_NEW 是两个独立事务；NESTED 是一个事务里的子保存点。

### 9. Spring 事务隔离级别（底层就是数据库隔离级别）

对应 `@Transactional(isolation = ...)`，解决脏读、不可重复读、幻读
1. **DEFAULT（默认）**：使用数据库本身隔离级别，生产一般用这个
2. **READ_UNCOMMITTED 读未提交**：最低，脏读、不可重复读、幻读都存在
3. **READ_COMMITTED 读已提交**：MySQL Oracle常用；解决脏读，存在不可重复读、幻读
4. **REPEATABLE_READ 可重复读（MySQL InnoDB默认）**：解决脏读、不可重复读；存在幻读（MVCC+间隙锁解决幻读）
5. **SERIALIZABLE 串行化**：最高级别，全部锁表，所有问题都解决，并发极差

三个问题一句话：
- 脏读：读到别的事务**未提交**的数据
- 不可重复读：同一事务内，两次读同一行，别的事务修改提交，数据不一样
- 幻读：同一事务范围查询，别的事务插入/删除，条数变了

### 10. 双亲委派机制

**定义**：类加载器收到加载请求，先向上委托父加载器尝试加载；父加载器加载失败，自己才加载。
加载器层级：Bootstrap（启动类加载器）→ Extension（扩展）→ Application（应用类加载器）

**好处**
1. **安全**：防止核心类库被篡改（比如自己写一个java.lang.String不会被加载）
2. **避免类重复加载**：同一个类只会被一个加载器加载一次
3. 类具备隔离性，不同加载器加载的类不是同一个Class

**破坏场景**：SPI、Tomcat自定义类加载器、热部署。

---

### 11. 类加载完整过程

**加载 → 链接（验证、准备、解析） → 初始化 → 使用 → 卸载**
1. **加载 Loading**：读取.class字节码到内存，在堆生成Class对象
2. **链接 Linking**
   - 验证：校验字节码格式、安全校验，防止恶意字节码
   - 准备：给**静态变量**分配内存，赋**默认初始值**（0、null、false，不是代码里赋值）
   - 解析：符号引用 → 直接引用
3. **初始化 Initialization**：执行静态代码块、静态变量显式赋值。触发时机：主动引用（new、静态方法/变量、反射、main方法等）；被动引用不会触发初始化。
4. 使用：正常实例化对象调用方法
5. 卸载：类加载器被回收，该类才会卸载

### 7、JVM内存划分，详细说说

运行时数据区五大块：

2. **虚拟机栈**：线程私有，栈帧，局部变量、方法调用。
3. **本地方法栈**：线程私有，服务native本地方法。
4. **堆Heap**：线程共享，对象实例、数组，GC主要区域。
5. **方法区（元空间Metaspace JDK8+）**：线程共享，存类元信息、常量池、静态变量。

4. 垃圾回收组件：负责堆内存垃圾回收。

### 9、浅拷贝、深拷贝的理解与实现

- **浅拷贝**：复制对象本身，对象内部引用类型成员只复制引用地址，新旧对象共用同一个子对象；修改子对象会互相影响。
- **深拷贝**：完整复制对象以及对象内部所有引用的对象，完全独立，修改互不干扰。

实现方式：
1. 浅拷贝：实现`Cloneable`接口重写clone()；默认就是浅拷贝。
2. 深拷贝：①递归手动clone引用对象；②序列化反序列化；③第三方工具（JSON序列化）。

### 2. 项目里分3布式事务处理方案是什么？简述

口述：
项目选用 **Seata AT模式**。
AT是无侵入的TCC改进方案，基于二阶段提交。

- 二阶段成功：异步删除undo日志；
- 二阶段失败：根据undo日志反向补偿回滚本地数据。
适配场景：订单创建、扣减业务数据、记录支付流水这类跨库操作。
同时配合RocketMQ事务消息做最终一致性，用来处理异步消息场景，比如订单创建成功后发送通知、积分这类不需要强一致、接受最终一致的流程。

一句话区分：**强一致用Seata AT；异步解耦、最终一致用RocketMQ事务消息**。

### 3. RocketMQ简单介绍

口述：
RocketMQ是阿里开源的分布式消息队列，高吞吐、高可用，支持事务消息、延时消息、死信队列，适合微服务异步解耦、削峰填谷、最终一致性场景。
核心角色：
- Producer生产者：发送消息；
- Broker：消息存储服务，主从架构；
- NameServer：注册中心，管理Broker路由，轻量无状态；
- Consumer消费者，分集群消费、广播消费。
我项目里主要用：**普通消息、事务消息**，用来异步通知、订单状态推送，解耦订单主流程和后续业务。
消息可靠机制：生产者重试、ACK确认、消息持久化、死信处理，防止消息丢失。

### 4. 对服务熔断降级了解吗

口述：
熔断、降级是高可用防护手段，项目使用Sentinel实现。
- **降级**：下游服务慢或者异常多的时候，不再调用原始接口，直接返回兜底数据，快速失败，减少等待耗时。
- **熔断**：当异常比例、慢调用比例达到阈值，直接打开熔断器，一段时间内直接拒绝请求，不调用下游；冷却时间后半开试探，恢复正常就关闭熔断。
配套还有限流，控制请求QPS，防止流量打垮服务。
场景举例：支付回调、查询订单详情，如果第三方或者下游服务不稳定，直接降级返回友好提示，避免连锁雪崩。

### 5. 举一个分布式事务场景

口述：**订单创建 + 业务数据扣减 这个跨库场景**
用户下单，需要两件事：①订单库新增一条待支付订单；②业务库扣减对应额度。
这两个操作在不同MySQL库，本地事务管不了，就产生分布式事务问题。
如果订单插入成功，扣额度失败，就会数据不一致。
方案：使用Seata AT模式。
一阶段两个分支事务都执行，记录undo日志；
两个分支都成功，二阶段提交，删掉undo；
任意一个分支失败，Seata触发回滚，通过undo日志把两个库的数据都恢复，保证原子性。

> 补充区分：如果是订单创建之后发MQ通知积分、短信，这个不用AT，用RocketMQ事务消息保证最终一致。

### 6. MQ消息积压有没有遇到？怎么解决

口述：遇到过，消费速度跟不上生产速度，出现消息堆积。
排查+处理思路分几步：

1. 先定位原因：看是不是消费者逻辑慢、DB查询慢、锁等待、报错导致大量消息重试，或者消费者实例太少；
2. 紧急方案：
    - 临时增加消费者实例，提高消费并行度（集群消费模式）；
    - 把堆积消息迁移到临时新topic，先消费新消息，堆积消息单独消费；
3. 根治优化：
    - 消费端代码优化，去掉慢SQL、减少同步IO；批量消费（RocketMQ支持批量拉取）；
    - 区分业务，非核心消息可以降级丢弃；
    - 合理设置重试次数，失败消息转入死信队列，避免无限重试拖垮消费；
    - 监控告警：监控消息堆积量、消费延迟，提前感知。
额外注意：不盲目调大单线程并发，防止压垮数据库。

### 7. 支付平台用支付宝沙箱？对支付流程开发了解多少

口述：是的，项目对接支付宝沙箱做支付能力调试，线上逻辑和沙箱基本一致。
整体支付开发流程：

### 8. HashMap原理、源码理解（Java基础压轴题）

口述：
HashMap底层JDK1.8是 **数组 + 链表 + 红黑树**。
1. put流程：
    根据key的hash值扰动函数计算hash，对数组长度取模得到桶下标；
    - 桶为空：直接放进去；
    - 桶头节点key相同：覆盖；
    - 桶是链表：顺着链表遍历，找到相同key覆盖；没有就尾部新增；链表长度 >=8 并且数组容量>=64，链表转红黑树；
    - 桶是红黑树：走树的查找、插入逻辑；
2. 扩容：负载因子默认0.75，元素数量>容量*0.75触发2倍扩容；扩容后元素重新rehash；
3. 其他要点：
    hash扰动：高低位异或，减少hash碰撞；
    链表转树阈值8，树退化成链表阈值6；
    线程不安全：并发put会丢数据、形成循环链表（1.7头插）；
    key为null只能放在0号桶；
    源码里面重点看putVal、resize扩容方法。
> 加分一句：并发场景一般用ConcurrentHashMap。

### JVM堆区、栈区介绍

- **虚拟机栈（线程私有）**：每个线程一个栈，由栈帧组成；存放局部变量、方法返回地址、操作数栈。方法调用入栈，方法结束出栈。栈溢出：StackOverflowError。
- **堆（线程共享）**：所有对象、数组分配在堆，GC主要回收区域；分为年轻代（Eden、S0、S1）、老年代；Xmx/Xms设置堆大小，容易发生OOM。

### Java怎么避免死锁

死锁四个必要条件：互斥、持有并等待、不可剥夺、循环等待。破坏任意一个即可。
手段：
1. **统一锁的获取顺序**（最常用），所有线程按固定顺序申请锁；
2. 使用带超时的锁 `tryLock(timeout)`，拿不到就释放已经持有的锁；
3. 减少锁粒度，避免嵌套锁；
4. 用并发工具类（CountDownLatch、Semaphore）、无锁CAS替代synchronized；
5. 尽量避免多个锁互相依赖。

### Java垃圾回收机制

GC自动回收堆中没有可达引用的对象。
基础算法：标记清除、复制、标记整理；
分代收集：年轻代多用复制算法，老年代标记整理；
流程：可达性分析（GC Roots）判断对象是否存活；
常见收集器：Parallel GC（高吞吐）、G1、ZGC（低延迟）；
GC Roots：栈中局部变量、静态变量、本地方法引用等。

### Java的常量是什么时候加载的 + 常量用什么修饰

### Java集合用过哪些？

常用：`ArrayList`、`LinkedList`、`HashSet`、`TreeSet`、`HashMap`、`LinkedHashMap`、`ConcurrentHashMap`

### ArrayList 和 LinkedList 区别

- **ArrayList**：底层**动态数组**；随机查询快（支持下标）；中间位置增删需要移动元素，增删慢；**线程不安全，并发效率高**
- **LinkedList**：底层**双向链表**；随机查找需要遍历，查询慢；首尾增删只改指针，增删快；**线程不安全，并发效率高** 补充：Vector底层也是数组，查询快、增删慢，加了`synchronized`，**线程安全，但效率低**，现在基本不用。

### HashMap 和 HashSet 的区别、查询时间复杂度

- `HashMap`：实现 `Map` 接口，**key-value 键值对结构**，key不可重复，value可重复
- `HashSet`：实现 `Set` 接口，单列存元素，元素不能重复；**底层就是 HashMap，元素作为 key，value是固定占位Object**

时间复杂度：

- HashMap / HashSet：理想无冲突时 **O(1)**； 哈希冲突严重：桶内链表长度 ≤6 → O(n)；链表转红黑树（≥8）→ O(logN)
- TreeSet 底层红黑树，查询、插入、删除稳定 **O(logN)**

### 它们线程安全吗？如果要改成线程安全怎么做？

HashMap、HashSet、ArrayList、LinkedList **全部线程不安全**。 两种方案：

1. **优先用并发集合：ConcurrentHashMap** 底层数组 table 用 `volatile` 修饰，保证可见性、禁止指令重排。 put流程： 先乐观判断，数组未初始化就初始化； 对应桶位为空，直接CAS插入； 桶不为空，检测是否正在扩容，帮助迁移数据； 没有扩容，对桶头节点加synchronized锁，遍历链表/红黑树，覆盖或者新增节点。 get不加锁：因为table、节点的val用volatile，保证读到最新值，不需要加锁。
2. 包装方法：`Collections.synchronizedList / synchronizedMap`，方法上加同步锁，粒度大，并发性能差，一般不推荐。

### 对锁有了解吗？synchronized 和 Lock 的区别

锁分类：公平锁/非公平锁、可重入锁/不可重入锁、悲观锁/乐观锁、JVM内置锁/分布式锁

`synchronized` 和 `Lock` 对比：

1. 出身：`synchronized` 是 **JVM内置关键字**；`Lock` 是 `java.util.concurrent.locks` 下的接口，是API层面实现
2. 锁释放：synchronized 代码块执行完 / 异常时**自动释放锁**；Lock **必须手动 unlock()**，忘记释放会直接死锁
3. 可中断：synchronized 等待锁时**不可中断**；Lock 的 `lockInterruptibly()` 支持中断等待
4. 公平性：synchronized 只能是非公平锁；ReentrantLock 可以构造时指定公平/非公平
5. 锁状态：synchronized 无法判断线程是否拿到锁；Lock 有 `tryLock()`，可以尝试获取、带超时，返回布尔知道是否拿到锁
6. 都是**可重入锁**

------

### 多线程用过吗？创建线程方式、怎么启动？

用过，项目里比如异步生成每日报表场景用到多线程。 四种方式：

1. 继承 `Thread` 类，重写 `run()`
2. 实现 `Runnable` 接口，重写 `run()`（无返回值）
3. 实现 `Callable` 接口 + FutureTask，重写 `call()`（有返回值、可抛异常）
4. 线程池（生产首选）

启动：

- Thread/Runnable/Callable：调用 `start()` 才会向操作系统申请创建新线程；直接调用 `run()` 只是普通方法执行，不会开新线程
- 线程池：`execute()` 提交无返回任务；`submit()` 提交有返回任务，返回Future

### 分布式事务控制方案

1. 2PC（二阶段提交）：协调者统一调度，阻塞，性能差，故障风险高

### Netty & NIO

#### 版本1｜45秒精简口述（AI面试、快速回答首选）

NIO是JDK提供的非阻塞IO API，核心是**IO多路复用**，基于Selector、Channel、Buffer这三大组件，单线程可以监听多个连接，对比BIO一个连接一个线程，解决了线程资源浪费的问题。但是原生NIO有很多坑，比如空轮询bug、编解码、半包粘包、线程模型、异常处理都要自己写，开发成本很高。

Netty就是对JDK NIO的高性能封装框架，底层还是JDK NIO，屏蔽了原生NIO的各种底层问题；提供Reactor线程模型、Pipeline责任链、ByteBuf、自动处理半包粘包，让我们专注业务开发。像RocketMQ、Dubbo通信层底层都是Netty；而Tomcat是自己封装原生NIO，没有用Netty。

#### 版本2｜1.5分钟完整版（面试官深挖，推荐）

先讲NIO：
NIO叫非阻塞IO，是JDK在1.4提供的一套IO模型，核心是多路复用。三大核心组件：Channel通道、Buffer缓冲区、Selector选择器。
Selector可以在一个线程里同时监听大量Channel的读写就绪事件，连接多的时候不用每个连接开一个独立线程，大幅减少线程开销。
但是原生NIO有不少痛点：比如经典的selector空轮询bug、需要手动处理TCP粘包半包、要自己维护线程模型、内存管理麻烦、API底层繁琐，很容易写出bug。

再讲Netty：
Netty底层就是封装JDK NIO，它是一个网络通信框架，把原生NIO的脏活全部封装好了。
核心亮点：

1. 实现了成熟的Reactor线程模型（单Reactor、多Reactor，默认主从Reactor）；
2. Pipeline + Handler责任链，把编解码、业务处理、日志、重试分层；
3. ByteBuf做内存池化管理，减少GC；
4. 内置处理TCP粘包半包的解码器，比如LengthFieldBasedFrameDecoder；
5. 自动规避原生NIO空轮询等bug，异常、重连、空闲检测都有现成能力。

最后落地场景：RocketMQ、Dubbo、gRPC（Nacos2.x）通信层都基于Netty；Tomcat没有使用Netty，它自己基于原生JDK NIO实现NioEndpoint。

一句话收尾：**NIO是JDK底层API，Netty是基于NIO封装的工业级网络框架**。

#### 版本3｜深挖配套追问（提前备好）

##### 1. NIO和BIO、AIO区别？

BIO：阻塞IO，一连接一线程，连接多线程爆炸；
NIO：非阻塞+多路复用，同步非阻塞；
AIO：异步IO，回调通知，Linux下底层还是epoll，Netty不推荐AIO，windows支持好，生产很少用。

##### 2. Netty主从Reactor讲一下？

主Reactor（Boss线程）：只负责接收新连接，注册到从Reactor；
从Reactor（Worker线程池）：负责已建立连接的IO读写、编解码；业务耗时逻辑建议丢到独立业务线程池，不要阻塞Worker。

##### 3. 什么是粘包半包？怎么解决？

TCP是流协议，没有边界。多条消息粘在一起是粘包；一条消息被拆分多次收到是半包。Netty常用：固定长度、分隔符、长度字段解码器LengthFieldBasedFrameDecoder。

##### 4. ByteBuf优势？

比ByteBuffer好用，双指针readIndex/writeIndex；支持池化，复用内存，降低GC；自动扩容。

##### 5. 什么时候Netty会阻塞？

Worker线程里执行耗时业务、同步数据库查询，会阻塞IO线程，影响其他连接。正确做法：业务逻辑交给自定义业务线程池。

### 为什么用NIO？

BIO一个连接对应一个线程，连接一多线程爆炸，资源耗尽；
NIO是同步非阻塞，**一个或者少量线程就可以管理大量连接**，多路复用，适合高并发长连接场景，减少线程开销。

### 除了当前项目，哪个中间件NIO场景多？

**Netty** 是最典型；Dubbo、RocketMQ、Elasticsearch、Tomcat、Gateway网关底层都大量使用NIO。

### NIO怎么实现同步非阻塞？

NIO三大组件：Channel、Buffer、Selector（多路复用器）
1. 所有Channel注册到Selector；
2. 单线程轮询Selector，查询哪些Channel已经就绪（可读、可写）；
3. 没有就绪事件的时候，线程可以阻塞等待；
4. 事件就绪后，线程去处理IO读写；
> 同步：读写操作还是要应用线程自己去完成；非阻塞：通道没有数据的时候，read不会阻塞卡住线程，直接返回。

一句话总结：**Selector多路复用 + Channel非阻塞读写，实现同步非阻塞**。

### NIO和AIO的区别

- NIO：同步非阻塞；**应用线程自己去做读写**，Selector轮询就绪事件（多路复用）；Netty主流。
- AIO（异步非阻塞）：操作系统内核完成IO读写，完成之后主动回调通知应用程序；
AIO适合连接多、IO操作时间长的场景；但是Linux下AIO实现不完善，工业界很少落地，主流框架基本不用AIO。

### 线程池运行原理

核心组件：核心线程、最大线程、阻塞队列、拒绝策略
流程：
1. 任务进来，当前运行线程数 < 核心线程数 → 新建核心线程执行；
2. 核心线程满了 → 任务放入阻塞队列排队；
3. 队列满了 → 新建非核心线程，直到达到最大线程数；
4. 达到最大线程，队列也满了 → 触发拒绝策略（Abort、Discard、DiscardOldest、CallerRuns）。
核心线程默认会常驻，空闲非核心线程超过超时时间会回收。

### MySQL引擎用的哪种？

项目全部使用 **InnoDB**。
特点：支持事务、行锁、MVCC、外键、崩溃恢复；MyISAM不支持事务、表锁，现在业务基本不用。

### 一坨SQL，怎么实现事务？

InnoDB事务基于 **redo log、undo log + MVCC**。
开启事务 begin；多条SQL在同一个事务内执行；
执行DML的时候：

1. 记录undo日志，用来回滚；
2. 修改数据页，同时写redo log（预写日志WAL，先写日志再刷盘）；
commit的时候，把redo log持久化；
commit成功，事务生效；中途异常，通过undo回滚数据。

### 在执行一些SQL时，其他线程可以看到吗？

由**当前事务隔离级别**决定。
- 读未提交：可以看到未提交数据（脏读）
- 读已提交：只能看到别的事务已经commit的数据
- 可重复读（InnoDB默认）：同一个事务内，快照固定，看不到别的事务新提交修改
- 串行化：完全串行，读加共享锁

### 可重复读 和 读已提交 的区别

1. **READ COMMITTED 读已提交**：每次select都会生成新快照，可以读到其他事务已经提交的修改；会出现不可重复读。
2. **REPEATABLE READ 可重复读（MySQL默认）**：事务第一次select生成一个一致性快照，整个事务全程复用这个快照；普通快照读避免脏读、不可重复读；
> 补充：MySQL InnoDB通过MVCC+间隙锁，在RR下解决幻读。

### SQL已经加索引，性能还是不够，可能是什么原因？

1. 索引失效：隐式类型转换、函数操作、or、like '%前缀模糊'
2. 索引选择性差，基数很低，优化器认为走索引不如全表快，主动放弃索引
3. 回表成本太高（二级索引查到主键，再回主键索引拿数据），比如select *
4. 联合索引不满足最左匹配原则
5. 数据量本身太大，IO瓶颈、Buffer Pool命中率低
6. 锁等待，事务长时间不提交，SQL被阻塞，不是索引问题
7. 排序分组，出现Using filesort、Using temporary

### 为什么避免 select *？

1. 取不需要的字段，网络传输量大；
2. 无法使用**覆盖索引**，必须回表，增加IO；
3. 表字段变更后，返回结果不可控；
4. 占用更多内存。

### MySQL慢查询有哪些原因？

- 没建索引 / 索引失效
- 回表量大，缺少覆盖索引
- 大事务、锁等待、行锁冲突阻塞
- 分页深偏移 limit 100000,10
- join顺序不合理，小表驱动大表反过来了
- 内存配置不合理，buffer pool太小，大量磁盘IO
- 单表数据量太大，没有分表
- 大量临时表、文件排序

### SQL字段冗余有什么好的解决办法？

冗余本质：反范式，换取join减少、查询提速。
方案：
1. 适度冗余，不要过度冗余；冗余字段做好**数据同步更新**（代码、触发器、binlog同步如canal），保证一致性；
2. 热点查询冗余，冷查询走关联；
3. 冗余过多带来维护困难时，拆成多张表，或者做宽表、同步到ES做查询。

### 分库分表了解吗？

分两种：水平、垂直拆分
- 垂直分库/分表：按字段拆分，比如基础信息一张表，扩展信息一张表；
- 水平分表：表结构一样，按路由规则把数据分散到多张表（按用户id、订单id哈希/范围分片）；
中间件：Sharding-JDBC、MyCat；
解决单表数据量太大的问题；代价：跨表分页、跨表join、分布式主键、分布式事务、排序聚合变复杂。

### 索引建的越多越好吗？

不是。
索引优点：加快查询；
代价：

1. 索引占用磁盘空间；
2. DML（insert/update/delete）需要同步维护索引，写性能下降；
适合：查询多、更新少的字段；频繁更新的字段不适合建索引。

### 分库分表后主键id怎么处理？

几种方案：
1. 雪花算法Snowflake（最常用）：时间戳+机器id+序列号，全局唯一，有序；
2. 数据库自增，不同分片设置不同起始、步长；
3. Redis自增生成id；
4. 号段模式：预先批量获取一段ID缓存，减少访问中间件次数。

### Spring事务：编程式、声明式

- **声明式事务 @Transactional**：AOP实现，配置简单，业务代码无侵入，项目最常用；
- **编程式事务**：用TransactionTemplate手动开启、提交、回滚，粒度更灵活，代码侵入。

### Spring @Transactional事务会失效吗？

会，高频失效场景：
1. 方法不是public；
2. 同类内方法直接调用（this调用，不走AOP代理）；
3. 异常不是RuntimeException / Error，受检异常没有指定rollbackFor；
4. 多线程，事务在子线程；
5. 数据库引擎不支持事务（MyISAM）；
6. 自己手动捕获异常吃掉，没有抛出。

### @Transactional可以嵌套吗？

可以嵌套，由**事务传播机制Propagation控制**。

### 事务传播机制（7个，核心记住5个）

REQUIRED（默认）：有就加入，没有新建
SUPPORTS：有就加入，没有非事务
MANDATORY：必须外层有事务，否则抛异常
REQUIRES_NEW：挂起外层，新建独立事务，互不影响
NESTED：嵌套事务，保存点savepoint，子回滚不影响外层，外层回滚连带子事务回滚
NOT_SUPPORTED：挂起外层，非事务执行
NEVER：禁止事务，有事务抛异常

> 重点区分：REQUIRES_NEW是两个独立事务；NESTED属于同一个事务的保存点。

### 分布式锁应用场景？代码怎么实现？

场景：防超卖、定时任务防止多实例重复执行、分布式资源抢占。
项目常用Redisson，底层封装Redis分布式锁。
核心逻辑：
`SET lockKey value NX EX` 原子抢锁；
value放唯一标识（uuid），释放锁的时候先判断标识，避免释放别人的锁；
看门狗自动续期，防止业务没执行完锁过期。

### Redis分布式锁 vs Zookeeper分布式锁

Redis：
- 基于SET NX + 过期时间；
Zookeeper：
- 基于临时有序节点；创建节点成功拿到锁，会话断开节点自动删除释放锁；监听前一个节点实现排队。

### 为什么Redis分布式锁比Zookeeper快？

1. Redis是内存KV，操作简单；Zookeeper要保证ZAB一致性协议，每次写需要过半节点确认，同步开销大；
2. Redis客户端和服务端交互次数更少；Zk有Watcher监听机制，通信交互更多；
> 缺点：Redis锁存在主从切换丢锁风险，Zk一致性更强。

### 分布式事务有没有用过？解决方案

用过，项目使用Seata AT + RocketMQ事务消息。
方案：
2PC、3PC、TCC、本地消息表、RocketMQ事务消息、Seata AT/SAGA

### 什么是二阶段提交、三阶段提交

**2PC 二阶段提交**
阶段1：准备阶段，所有分支执行、资源锁定，返回成功/失败；
阶段2：协调者统一决定提交或者回滚；
缺点：协调者单点、阻塞，准备阶段资源一直锁住，性能差。

**3PC 三阶段提交：CanCommit、PreCommit、DoCommit**
在2PC基础上拆分，增加CanCommit预检阶段；并且引入超时机制，减少长时间阻塞；
但是依然存在数据不一致风险，工业界很少使用。

#### 版本1：精简口述版（45s～1min，AI面试优先）

Spring IOC 是控制反转，核心思想**把对象的创建、依赖管理交给Spring容器，而不是自己new对象**。我们只需要定义Bean和依赖关系，容器负责实例化、注入依赖、管理Bean生命周期，降低耦合，方便单元测试。依赖注入DI是IOC的实现方式，常见有构造器注入、setter注入、字段注入。

AOP是面向切面编程，在不修改原有业务代码的前提下，对方法进行增强。底层是动态代理：目标有接口用JDK动态代理，没有接口用CGLIB。典型场景：统一日志、权限校验、事务@Transactional、接口耗时统计、异常统一处理。

#### 版本2：完整版（1.5～2min，深挖用，推荐背）

先讲IOC：
IOC全称控制反转，反转的是**对象控制权**。传统开发我们自己new对象、手动维护依赖；IOC把对象的创建、装配、销毁交给Spring IOC容器管理。
DI依赖注入是IOC的实现手段，容器自动给Bean注入所需要的依赖，不需要我们主动new依赖对象。
Bean的定义方式有XML、注解（@Component、@Service、@Bean）；注入方式：构造注入（推荐）、setter注入、@Autowired字段注入。容器启动会扫描、实例化Bean，默认单例，放到单例池。好处：解耦、便于替换实现、方便做单元测试。

然后AOP：
AOP面向切面编程，核心是**横切逻辑和业务代码解耦**。很多通用逻辑（日志、事务、权限）散布在各个方法里，AOP把这部分公共逻辑抽成切面，在目标方法执行前后、异常时织入增强，不用改动业务代码。
底层两种动态代理：

1. JDK动态代理：目标类实现了接口，代理接口；
2. CGLIB：目标没有接口，继承目标类生成子类代理。
SpringBoot 2.x之后默认CGLIB。
AOP里面几个概念：切点Pointcut（匹配哪些方法）、通知Advice（增强逻辑：前置、后置、返回、异常、环绕@Around）、切面Aspect（切点+通知）、连接点JoinPoint（被拦截的方法）。
最典型的落地就是Spring事务，@Transactional本质就是AOP环绕通知，在方法前开启事务，成功提交、异常回滚。

> 一句话收尾：IOC解决对象依赖解耦，AOP解决通用横切逻辑解耦，是Spring两大基石。

#### 依赖注入三种方式

> 三种：**构造器注入、Setter注入、字段注入（@Autowired直接打在成员变量上）**

- **构造器注入**
  原理：容器调用带参构造，传入依赖Bean。
  ✔ 优点：
  
  - 对象实例化时依赖就全部注入，**依赖不可为空，避免NPE**
  - 依赖可以用final修饰，线程安全、不可变
  - 没有反射，方便单元测试，不用Spring容器也能手动new传参
  ❌ 缺点：依赖过多时构造方法参数爆炸，可读性变差
✅ 适用：**必须的核心依赖（service、mapper）**
  
- **Setter注入**
  原理：实例化Bean之后，调用set方法赋值。
  ✔ 优点：
  
  - 对象创建后可以动态修改、替换依赖
  - 适合依赖不是必须的场景
  ❌ 缺点：无法保证一定会调用set方法，对象可能实例化完成但依赖缺失
✅ 适用：**可选依赖、运行时可切换的依赖**
  
- **字段注入（Field注入）**
  ```java
  @Autowired
  private UserMapper userMapper;
  ```
  ✔ 优点：代码最短，写起来方便
  ❌ 缺点（重点，面试必说）：
  
  1. 通过反射注入，依赖隐藏，外部看不到需要哪些依赖
  2. 不能声明为final
  3. 脱离Spring容器无法手动注入，单元测试麻烦
  4. 容易违反单一职责，不知不觉注入大量依赖
  ❗ Spring官方不推荐

### 3. Spring循环依赖，三级缓存，详细过程
> 前提：仅支持singleton、setter注入；构造注入无法解决循环依赖
三级缓存：
1. `singletonObjects`：一级缓存，存放**完全初始化好**的Bean
2. `earlySingletonObjects`：二级缓存，存放**已经实例化，但还没填充属性的半成品Bean**
3. `singletonFactories`：三级缓存，存放Bean工厂ObjectFactory，用来生成早期对象代理

流程（A依赖B，B依赖A）：
1. 创建A，实例化，放入三级缓存；开始填充属性，发现依赖B；
2. 去创建B，实例化，放入三级缓存；填充属性发现依赖A；
3. 找A：一级没有、二级没有，从A的三级缓存ObjectFactory拿到A早期对象，放到二级缓存；删掉A的三级缓存；
4. B拿到A的引用，B属性填充完毕，B初始化完成，放入一级缓存；
5. 回到A继续填充B，A完成初始化，A移入一级缓存，删除二级缓存。

> 关键点：三级缓存不是存半成品Bean，存的是工厂，为了**处理AOP代理对象**。

### 6. 大数据导出怎么做？Apache POI如何防止OOM

大数据导出核心思路是**全链路流式处理，避免全量数据加载到内存**。
Apache POI防止OOM主要用 `SXSSFWorkbook`，它是滑动窗口模式，只保留窗口内的行在内存，超出窗口的行会flush到磁盘临时文件，而XSSF是把整个Excel全部加载进内存，很容易OOM。

整体流程：
1. 查询层面：不能一次性查全表，用**主键游标分页或者MyBatis流式查询（fetchSize）**，一批一批取数据；
2. POI写入：使用SXSSFWorkbook，设置合理窗口大小，一般500~1000；**不要调用getBytes()**，直接write输出流；
3. 资源释放：写完必须调用`dispose()`清理临时文件，避免磁盘打满；
4. 业务架构：十万、百万级别不要同步导出，做成**异步任务**，MQ消费生成文件上传OSS，前端轮询下载链接，同时加并发限流；
5. 选型降级：不需要复杂样式直接导出CSV，内存开销最低；业务上也可以用EasyExcel，底层封装SXSSF，自动处理样式复用和临时文件清理，但它只是简化框架，如果一次性查出全量数据，依然会OOM。

> 补充区分坑点：SXSSF刷到磁盘的行不能回读修改；大量合并单元格、图片、批注不会落盘，常驻内存，量大依然会堆溢出。

---

#### 进阶完整版（1.5~2分钟，面试官深挖用，推荐背这个）

大数据导出是一条链路的优化，不是只改POI。
首先说POI防OOM方案：POI有三种实现，HSSF（xls，上限65536行）、XSSF（DOM模式，全数据驻内存，大数据导出极易OOM）、**SXSSF，流式滑动窗口方案**。
SXSSF原理：创建时指定窗口大小，内存只保留最近N行，新增行超过窗口，旧行写入本地临时xml文件，不再占用堆内存。

开发注意几个关键点：
第一，查询环节是最常见OOM源头，禁止一次性select全部数据。优先主键游标分页，避免limit深分页；或者JDBC流式查询，设置fetchSize，逐条返回结果，不在JVM缓存全部数据。
第二，写入的时候，**禁止workbook.getBytes()**，这个方法会把整个文件读到byte数组，直接OOM，要直接write到response输出流。
第三，资源一定要释放，`dispose()`用来删除SXSSF产生的临时文件，忘记调用会导致服务器磁盘占满。
第四，SXSSF短板：已经flush的行不能修改、读取；合并单元格、批注、图片不走磁盘缓存，大量使用会持续占用内存；CellStyle要复用，不要循环新建样式对象。

架构层面的大数据导出方案：
数据量比较大时，同步导出风险很高，容易超时、压垮服务。采用异步导出方案：前端提交导出请求，后台生成导出任务落库，返回taskId；MQ异步消费任务，分批查询+SXSSF/EasyExcel生成文件，上传对象存储；更新任务状态，前端轮询状态，完成后获取下载地址。同时增加导出并发限流，防止大量导出任务拖垮数据库和应用。

选型：带样式Excel优先EasyExcel，底层封装SXSSF，自动复用样式、自动清理临时文件，减少原生POI的踩坑；无复杂样式、超大批量优先CSV，流式文本导出，内存开销最小；千万级以上数据尽量交给数仓离线导出，不在Java应用在线导出。

### 9. Spring事务类型、传播机制、失效场景；catch + throw会不会失效
> 核心：**当前有没有事务？新方法要怎么复用 / 新建 / 挂起事务** 前提：A 方法调用 B 方法，A 是调用方，B 是被调用方

| 传播类型             | 说明                                                         | 一句话记忆                                           |
| -------------------- | ------------------------------------------------------------ | ---------------------------------------------------- |
| **REQUIRED（默认）** | 如果当前存在事务，就加入该事务；没有就新建一个事务           | 有就加入，没有就新建                                 |
| **SUPPORTS**         | 当前有事务就加入；没有就以**非事务方式**运行                 | 随缘，有事务就用，没有就裸跑                         |
| **MANDATORY**        | 必须在已有事务中执行；如果当前无事务，直接抛异常             | 强制要有事务，没有就报错                             |
| **REQUIRES_NEW**     | 不管有没有事务，**新建独立事务**；原有事务挂起，等新事务结束再恢复 | 永远开新事务，互相独立                               |
| **NOT_SUPPORTED**    | 总是以非事务执行；如果当前有事务，先**挂起**事务             | 不支持事务，有就挂起                                 |
| **NEVER**            | 禁止在事务里执行；如果当前存在事务，直接抛异常               | 绝对不能有事务，有就报错                             |
| **NESTED**           | 当前有事务，则在已有事务里**开启嵌套子事务（保存点 savepoint）**；无事务则新建事务 | 嵌套事务，子事务回滚不影响外层（外层回滚连带子事务） |

**事务失效场景**

1. 方法不是public
2. this内部调用，不走代理
3. 捕获异常没有抛出，异常被吞
4. 异常类型不是配置的rollbackFor指定异常
5. 跨线程
6. 引擎不支持事务

> 问题：**try-catch里面最后手动throw抛出异常，事务不会失效；如果catch之后不throw，事务才不会回滚，会失效。**

### 10. RabbitMQ用途；微服务用过哪些组件

RabbitMQ：异步解耦、削峰、最终一致性、延迟通知。
SpringCloudAlibaba组件：Nacos、Sentinel、OpenFeign、Gateway、RocketMQ（RabbitMQ）、Seata。

RabbitMQ 是消息队列，核心作用就是**解耦、削峰、异步、可靠投递**，常用在后端分布式系统里。

1. **异步解耦**：主流程不需要同步等待下游，比如下单后发 MQ，异步做短信、通知、积分，提升主接口响应速度；同时订单服务和通知服务代码解耦，互不依赖。
2. **流量削峰**：秒杀、大促瞬间流量很高，把请求丢进 MQ，消费者按自己处理能力慢慢消费，避免瞬间流量打垮数据库。
3. **流量 / 任务削峰填谷**：把突发流量平滑到一段时间处理。
4. **可靠消息最终一致性**：分布式事务场景，结合补偿机制，保证跨服务操作最终一致（比如订单和库存）。
5. **消息广播**：一条消息发给多个消费者，比如商品上新，同时推送给搜索、推荐、积分多个服务。

> 一句话总结：异步、解耦、削峰、广播、分布式可靠通知。

### 4. 你的优缺点；工作矛盾怎么解决；最不能接受同事什么行为

✅ 优点：底层愿意钻研，遇到问题会主动查日志、抓堆栈、复盘；写代码注重幂等、异常、稳定性；熟悉部署运维。
✅ 缺点：有时候纠结底层细节，开发进度会慢一点，现在学会先满足业务，再后续优化。
✅ 矛盾解决：先听对方思路，对齐需求目标，拿数据、日志说话，一起讨论最优方案。
✅ 不能接受：代码写完不自测、不看日志，直接甩bug；不沟通私自改公共代码，影响其他人。

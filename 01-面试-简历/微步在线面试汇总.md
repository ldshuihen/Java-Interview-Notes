XSS,CSRF是什么，如何防御

### XSS、CSRF 

#### 一、XSS 跨站脚本攻击（Cross-Site Scripting）

**本质**：攻击者把恶意 JS 注入到网页里，**在受害者浏览器执行**。
浏览器信任当前页面的内容，恶意脚本可以拿到当前页面的权限：偷 Cookie、窃取本地存储、劫持页面、跳转钓鱼、发起请求。

##### 三类 XSS

1. **存储型 XSS（持久型，危害最大）**
恶意脚本存入服务端数据库（评论、昵称、帖子），所有人访问页面都会加载并执行脚本。
2. **反射型 XSS（非持久）**
恶意脚本放在 URL 参数里，服务端直接把参数反射回页面，用户点开恶意链接才触发，不会存库。
3. **DOM 型 XSS**
完全发生在前端，JS 直接操作 DOM 把恶意内容渲染出来，**不经过后端**，后端日志看不到攻击载荷。

##### ✅ XSS 防御方案（按优先级）

1. **输入过滤 / 输出编码（最核心）**
输出到 HTML、JS、CSS、URL 不同上下文做对应转义：`< > & " '` 等特殊字符转义；前端框架 Vue/React 默认插值会自动转义，`v-html` / `dangerouslySetInnerHTML` 是高危点。
2. **CSP 内容安全策略（Content-Security-Policy）**
HTTP 响应头，限制脚本来源，禁止内联脚本、禁止 eval，就算注入了 JS 也执行不了，是兜底方案。
3. **Cookie 增加属性：HttpOnly + Secure + SameSite**
HttpOnly：JS 读不到 Cookie，防止偷 Cookie；Secure：仅 HTTPS 下携带。
4. **输入校验**：白名单优先，不要只靠黑名单（绕过手段很多）。
5. **避免不安全 API**：`eval、innerHTML、document.write` 谨慎使用。

---

#### 二、CSRF 跨站请求伪造（Cross-Site Request Forgery）

**本质**：利用浏览器 Cookie 自动携带机制，诱导用户在已经登录的状态下，在别的页面偷偷向目标网站发起请求。
> 一句话区分：**XSS 偷你的身份；CSRF 冒用你的身份**
流程举例：你登录了银行网站，Cookie 保存在浏览器；点开攻击者恶意页面，页面里隐藏表单/图片，自动发起转账请求，浏览器自动带上银行 Cookie，服务端以为是你本人操作。

##### ✅ CSRF 防御方案

1. **CSRF Token（最常用）**
后端下发随机 Token，放在表单/请求头；状态修改请求（POST/PUT/DELETE）必须带上这个 Token，后端校验；攻击者跨域页面拿不到这个Token。
2. **SameSite Cookie 属性（现代主流）**
`SameSite=Lax` / `Strict`，限制 Cookie 在跨站请求时不自动携带。Lax 是默认，GET 导航放行，POST 跨站不带 Cookie；Strict 任何跨场景都不带。
3. **校验请求来源：Referer / Origin**
校验请求头 Origin，判断是否是本站域名；注意：Referer 可以被部分场景关闭，只能做辅助，不能单独依赖。
4. **关键操作增加二次验证**：短信验证码、弹窗确认、密码验证。
5. **规范接口**：修改数据接口不要用 GET（GET 容易被图片、链接触发），增删改统一 POST/PUT。

---

#### ✅ 45秒口述背诵版

XSS 是跨站脚本，攻击者注入 JS 在用户浏览器执行，分存储型、反射型、DOM型。防御核心是输出编码、开启CSP、Cookie设置HttpOnly。
CSRF 是跨站请求伪造，利用浏览器自动携带Cookie，冒用登录用户身份发起请求。常用防御是CSRF Token、Cookie SameSite属性、校验Origin头。
简单记：XSS偷Cookie，CSRF借Cookie。

#### 高频追问准备

Q：XSS 和 CSRF 区别？
- XSS：**执行恶意代码**，主动窃取信息；根源是页面渲染信任了不可信内容；可以拿到用户完整会话。
- CSRF：**不执行脚本，不用拿到Cookie**，只是利用浏览器自动带Cookie；攻击者看不到返回结果，只能代为发起请求。

Q：SameSite 能不能替代 CSRF Token？
不能完全替代。SameSite 是浏览器策略，存在兼容性、部分跳转场景绕过；高风险业务还是搭配 Token。

Q：React/Vue 还会有XSS吗？
有，框架插值自动转义，但 `v-html`、`dangerouslySetInnerHTML`、`eval`、iframe、富文本场景很容易引入XSS。

Q：CSP 能不能防 CSRF？
不行，CSP 管脚本加载执行，不管Cookie携带和跨站请求。

### SQL注入原理

**核心一句话**：程序把外部输入直接拼接进SQL语句，攻击者输入闭合SQL语法的特殊字符，篡改原有SQL语义，让数据库执行开发者预期之外的SQL。

底层根源：**代码和数据没有分离**。正常情况：SQL是代码，用户输入只是数据；拼接之后，用户输入被数据库解析成SQL代码执行。

#### 举个经典例子

后端代码（危险写法）
```java
String sql = "select * from user where username = '" + name + "' and password = '" + pwd + "'";
```
攻击者输入 name：`admin' -- `
拼接后SQL变成：

```sql
select * from user where username = 'admin' -- ' and password = ''
```
`--` 是SQL注释，后面条件全部注释掉，直接绕过登录。

还有 union 注入：`' union select 1,version(),database() --`，查询其他表数据。

#### 常见注入分类（简单记）

1. **联合查询注入 union**：拿额外数据
2. **布尔盲注**：页面不返回数据，只返回对错，通过真假逐字符猜库表字段
3. **时间盲注**：页面无任何回显，用 `sleep()` 延时判断
4. **堆叠注入**：`;` 分隔多条SQL，执行删表、新增用户（看驱动是否支持多语句）

#### ✅ 防御手段（必背）

1. **预编译语句（PreparedStatement / 参数化查询，最核心）**
参数和SQL语法分开解析，输入永远作为纯数据，不会被当成SQL代码解析；MyBatis 用 `#{}`，不要 `${}`。
> 重点坑：MyBatis `${}` 是字符串拼接，会注入；`#{}` 是预编译。
2. **输入白名单校验**：比如排序字段、表名没法参数化，只能白名单校验，禁止直接取输入当字段名
3. **最小权限账号**：业务数据库账号不给 drop、alter 等高权限，就算注入，危害降低
4. **关闭数据库详细报错回显**，防止攻击者通过报错获取库表结构
5. **ORM框架**（JPA、MyBatis）合理使用，减少手写拼接SQL

#### ✅ 45秒口述精简版

SQL注入的原理是后端直接把用户输入拼接进SQL语句，用户输入的单引号、注释符等破坏原有SQL结构，被数据库当成SQL指令执行。根源是SQL代码和用户输入数据没有隔离。最有效的防御是预编译参数化查询，MyBatis里用#{}而不是${}；搭配白名单校验、数据库最小权限、屏蔽详细报错。

#### 高频追问

Q：为什么预编译能防注入？
> SQL模板提前发给数据库完成语法解析、生成执行计划；后续传入的参数只会被当做普通字符串，不会被解析成SQL语法。

Q：${} 一定有注入吗？
> 不是一定能利用，但是**存在注入风险**；如果输入不受控，就会被攻击；表名、order by字段无法参数化，这时要用白名单。

Q：过滤单引号能不能防住SQL注入？
> 黑名单过滤很容易绕过（编码绕过、宽字符注入等），不靠谱，不能作为主防御方案。

### MySQL索引原理

> 前提：MySQL 默认存储引擎 InnoDB，索引底层是 **B+树**，不是B树、不是二叉树。

#### 1. 什么是索引

索引是帮助数据库**快速查找数据**的排好序的数据结构，本质是空间换时间。

#### 2. B+树结构（核心）

- B+树是多路平衡查找树；
- **所有数据都存在叶子节点**，非叶子节点只存索引键 + 子节点指针，不存完整行数据；
- 叶子节点之间用双向链表串联，**有序链表**；
- 叶子节点存储：主键值 + 整行数据（聚簇索引） / 索引列 + 主键（二级索引）
- 节点大小：一页默认16KB，一页可以存非常多索引条目，树高一般只有 3~4 层；查询最多3~4次磁盘IO，速度很快。

#### 3. 聚簇索引 vs 二级索引（重中之重）

##### 聚簇索引（主键索引）

InnoDB 必须有聚簇索引：
- 如果定义了主键：主键就是聚簇索引；
- 没有主键：选唯一非空索引；
- 都没有：自动生成隐藏 row_id 作为聚簇索引。
- 叶子节点：**存放整行所有数据**
- 一张表**只能有一个聚簇索引**

##### 二级索引（普通索引、联合索引、唯一索引）

- 叶子节点：**只存索引键 + 主键值**，不存完整数据
- 通过二级索引查到主键之后，再去聚簇索引里查完整数据 → 这个动作叫 **回表**

> 举例：`idx_name(name)`
> 查 `select * from user where name='张三'`
> 二级索引找到 name=张三，拿到主键id；再拿id去聚簇索引查全部字段 → 回表。
> 如果 `select id,name from user where name='张三'`，需要的字段索引里全都有，**不需要回表，叫覆盖索引**

#### 4. 联合索引 & 最左匹配原则

联合索引 `idx_a_b_c(a,b,c)`
- 索引排序规则：先按a排序，a相同按b，b相同按c
- 最左前缀匹配：查询条件要从最左边列开始连续匹配才能走索引
✅ 可以走：where a=?；where a=? and b=?；where a=? and b=? and c=?
❌ 不走：where b=?；where b=? and c=?；where a=? and c=?（中间断了b）
##### （idx (a,b,c)）

- `a=? and b=? and c=?`：a,b,c 全部用到
- `a=? and b>? and c=?`：a、b 用到，c 失效（范围之后失效）
- `a=? and c=?`：仅 a 用到，c 失效
- `b=? and c=?`：完全不走这个联合索引
- `a=?`：正常走索引

> 注意：范围条件（> < between）之后的列**失效**
> `where a=? and b>100 and c=?`：a、b用到索引，c用不到

#### 5. 索引分类快速梳理

1. 主键索引：聚簇索引，唯一非空
2. 普通索引：允许重复、允许null
3. 唯一索引：索引值唯一，可以null
4. 联合索引：多个字段组成一个索引
5. 全文索引：针对长文本，不使用B+树
6. 空间索引：地理坐标

#### 6. 索引为什么不能无限建？（索引代价）

✅ 收益：加快查询
❌ 代价：
1. 占用磁盘空间；
2. DML（insert/update/delete）需要维护B+树，索引越多，增删改越慢；
3. 页分裂、页合并：插入无序主键会频繁页分裂，性能暴跌（推荐自增主键）

#### 7. 45秒口述精简版

InnoDB索引底层是B+树。B+树非叶子节点只存索引键，全部数据放在有序链表串联的叶子节点。分为聚簇索引和二级索引：聚簇索引叶子存整行数据，一张表只有一个；二级索引叶子存索引列+主键，查到主键后回表查询。联合索引遵循最左匹配原则，范围查询后面索引失效。索引可以加速查询，但会降低增删改性能，不能盲目创建。

#### 高频追问准备

Q：B+树对比B树优势？
- B+树叶子链表，范围查询极强；
- 非叶子节点不存数据，一页能存更多key，树更矮，IO更少；
- 所有查询都落到叶子，IO次数稳定。

Q：为什么推荐自增主键？
自增主键有序写入，B+树尾部追加，不会触发频繁页分裂；无序主键比如UUID随机插入，容易页分裂，性能差。

Q：覆盖索引是什么？
查询需要的字段在二级索引叶子节点全部存在，不需要回表，减少一次IO，优化手段。

Q：什么情况索引失效？
- 违反最左前缀；
- 索引列做函数运算、隐式类型转换；
- like '%xxx' 前缀模糊；
- or 连接条件有未索引字段；
- 优化器判断全表扫描比索引更快（数据量占比很高）。

Q：MyISAM索引和InnoDB区别？
MyISAM没有聚簇索引，所有索引叶子都存数据文件的磁盘地址，主键索引和普通索引结构一样。

### HTTP 请求完整过程

> 前提：基于 **HTTP/1.1（TCP）**，HTTPS 会多 TLS 握手环节

整体顺序：**DNS解析 → TCP三次握手 →（TLS握手，HTTPS才有）→ HTTP请求报文发送 → 服务端处理 → HTTP响应报文返回 →（TCP四次挥手断开）**

#### 分步拆解

1. **DNS 域名解析**
浏览器先查本地缓存（hosts、浏览器缓存），没有就向DNS递归服务器查询，把域名（比如 www.baidu.com）解析成目标服务器IP。
> 作用：域名 → IP。

2. **TCP 三次握手，建立可靠连接**
HTTP是应用层协议，底层依赖TCP。建立双向可靠通道：
- 客户端发 SYN（同步）
- 服务端回 SYN+ACK
- 客户端回 ACK
连接建立成功。
> HTTP1.1 默认长连接 `Connection: keep-alive`，一次连接可以传多次HTTP请求，不用每次都握手挥手。

3. 【HTTPS额外步骤】TLS握手
协商加密套件、交换密钥，生成会话密钥，后续HTTP报文全部加密传输；HTTP没有这一步。

4. **客户端组装、发送HTTP请求报文**
请求行（方法、URL、版本）+ 请求头 + 请求体（POST/PUT才有），通过TCP流发给服务端。

5. **服务端接收报文，Web服务器处理（Nginx → 后端服务）**
Nginx先接收，做反向代理、负载均衡；转发给后端Java服务；业务代码处理逻辑、查数据库。

6. **服务端构造HTTP响应报文返回**
状态码 + 响应头 + 响应体（html/json等），沿TCP通道发回客户端。

7. **浏览器渲染资源**
拿到响应数据，解析HTML、CSS、JS，渲染页面；并行加载图片、JS、CSS等静态资源（并发请求）。

8. **TCP四次挥手（连接关闭）**
长连接不会立刻关；空闲超时或者 `Connection: close` 时触发四次挥手断开TCP连接：
- 客户端FIN
- 服务端ACK
- 服务端FIN
- 客户端ACK

---
#### ✅ 45秒口述精简版

浏览器发起HTTP请求，首先DNS解析域名得到服务器IP；然后通过TCP三次握手建立可靠连接；HTTPS还要多一步TLS握手加密。客户端发送HTTP请求报文，Nginx等服务端接收并转发给后端业务处理，处理完成返回响应报文。浏览器拿到结果渲染页面。如果不需要长连接，最后TCP四次挥手断开连接。HTTP1.1支持keep-alive，一个TCP连接可以复用多次请求。

#### 高频追问预备

Q：HTTP和TCP关系？
HTTP是应用层协议，TCP是传输层；HTTP只是报文格式，TCP负责可靠传输。
Q：三次握手能不能改成两次？
不行，两次握手服务端无法确认客户端收得到自己的消息，无法确认双向通道都正常。
Q：为什么四次挥手？
TCP是全双工，双方各自关闭发送通道；服务端收到FIN时可能还有数据没发完，不能和ACK合并。
Q：HTTP2、HTTP3区别？
HTTP2：基于TCP，多路复用、二进制帧、头部压缩；
HTTP3：基于QUIC（UDP），没有队头阻塞，握手更快。
Q：GET和POST区别？
GET参数放URL，有长度限制，幂等；POST参数放请求体，一般用于提交修改数据。

### TIME_WAIT / CLOSE_WAIT

先回顾四次挥手：
1. 客户端发 FIN（我这边不再发数据） → 进入 **FIN_WAIT_1**
2. 服务端回复 ACK → 服务端进入 **CLOSE_WAIT**；客户端进入 **FIN_WAIT_2**
3. 服务端把剩下数据发完，自己发 FIN → 服务端进入 **LAST_ACK**；客户端收到FIN → **TIME_WAIT**
4. 客户端回复 ACK；服务端收到ACK → CLOSED；客户端等待 2MSL 之后才进入 CLOSED

> 一句话区分：
> **CLOSE_WAIT：在服务端（被动关闭方）**
> **TIME_WAIT：在客户端（主动关闭方）**

#### 1. CLOSE_WAIT

- 触发时机：被动关闭方收到对方FIN，回复ACK之后，**但是自己还没调用 close()**
- 含义：我知道你不发数据了（你关了发送方向），我这边还有业务数据没处理完，暂时不关闭我的发送方向。
- 正常：业务处理很快，马上调用close，CLOSE_WAIT转瞬消失。
- CLOSE_WAIT大量堆积 = **BUG信号**
  原因：**代码忘记关闭Socket连接**（io流没close、连接池泄漏、没有释放连接）。
  后果：文件描述符 fd 被占满，无法新建连接，服务卡死。
  解决：检查代码，确保连接用完正常close；检查连接池回收逻辑。

#### 2. TIME_WAIT

- 触发时机：**主动关闭方收到对方FIN，并且回复ACK之后**，进入TIME_WAIT，必须等待 **2MSL** 才彻底关闭。
- MSL：报文最大生存时间（Linux默认60s，2MSL就是120s）
- 为什么要有2MSL等待（两个核心目的，必背）
  1. 保证最后那个ACK能送到对方：如果ACK丢了，服务端（LAST_ACK）会重发FIN；TIME_WAIT状态下客户端可以重发ACK。如果客户端直接关闭，对方重发FIN过来时，客户端返回RST，服务端异常。
  2. 防止“迟到的旧报文”干扰下一次复用的同端口连接，保证旧连接的数据不会串到新连接。

#### 3. TIME_WAIT过多会怎么样？

TIME_WAIT是**主动关闭方**占用端口，等待2MSL。
- 端口资源耗尽：客户端端口范围有限（默认32768~60999），短连接高频创建销毁，大量TIME_WAIT占满临时端口，新连接无法建立（`Cannot assign requested address`）
- 注意：**TIME_WAIT不会占用文件描述符fd**（这点和CLOSE_WAIT关键区别！面试高频坑），它消耗的是**本地端口号**。

##### 优化方案（Linux）

1. 开启 `tcp_tw_reuse`：允许TIME_WAIT状态的连接，在安全条件下复用给新的出站连接（推荐）
2. 调整 `tcp_fin_timeout`：缩短等待时间（不建议随意改太小，有报文错乱风险）
3. 业务层面：改用长连接 keep-alive，减少短连接频繁断开，从根源减少TIME_WAIT
> ⚠️ tcp_tw_recycle 在新版内核已经废弃，不要提。

#### ✅ 45秒口述版

CLOSE_WAIT是被动关闭方收到FIN、回了ACK，但业务代码没调用close关闭socket，大量CLOSE_WAIT一般是连接泄漏，会耗尽文件句柄。
TIME_WAIT是主动关闭方收到FIN并回复ACK后，要等待2MSL。一是保证最后ACK可达，二是避免延迟报文影响新连接。TIME_WAIT太多会耗尽本地临时端口，新建连接失败；优化优先用长连接，或者开启tcp_tw_reuse复用。

Q：2MSL为什么是两倍MSL？

### 线程过多可以吗？（Java后端面试标准回答）

一句话结论：**不可以，线程不是越多越好，线程数量存在最优值，超过之后性能反而下降**

#### 1. 为什么不能开太多线程

##### （1）内存开销

Java线程默认栈大小 `-Xss`，一般 1MB。开1000个线程，光栈内存就要占用近1G；线程越多，内存占用越高，容易OOM。
> 注意：堆是 `heap`，线程栈是每个线程独立的，不在堆里。

##### （2）CPU上下文切换开销（最核心）

CPU核心数有限。线程多了，操作系统要不断暂停旧线程、保存寄存器、切换到新线程、恢复现场 —— **上下文切换**。
切换本身要消耗CPU时间，线程竞争CPU激烈时，大量CPU浪费在切换上，真正执行业务的时间变少，吞吐量下降、延迟升高。

##### （3）资源竞争加剧

大量线程同时抢锁、数据库连接、Redis连接、文件句柄，锁自旋、阻塞变多，很容易出现大量线程阻塞，并发上不去。

##### （4）操作系统本身限制

系统有最大线程数、最大进程、文件描述符上限，线程开太大会直接创建失败 `OutOfMemoryError: unable to create new native thread`。

#### 2. 线程数怎么估算（面试必背公式）

区分 CPU密集型 和 IO密集型
- **CPU密集型（计算为主，比如加密、解析、向量计算）**
  最优线程数 ≈ CPU核心数 + 1
  原因：充分利用CPU，减少切换；+1是兜底一个线程处理突发阻塞
- **IO密集型（DB、Redis、HTTP调用，大部分后端业务）**
  最优线程数 ≈ CPU核心数 × (1 + IO等待时间 / CPU计算时间)
  简单经验值：IO密集型一般设为 **CPU核心数的 2~5倍**
> 原理：IO的时候线程是阻塞等待，CPU空闲，可以调度其他线程干活

> 坑：这个公式只是理论参考，还要受下游资源限制（数据库连接池大小往往是瓶颈）。

#### 3. 那如果任务非常多怎么办？

不要疯狂新建线程，用**线程池**：
- 核心思路：复用线程，控制线程上限；
- 任务多了放进阻塞队列排队，而不是新建线程；
- 拒绝策略处理过载，防止雪崩。

#### 4. 补充：虚拟线程（Java21+，加分项）

平台线程（传统Thread）是OS内核线程，成本重；虚拟线程是JVM用户态轻量线程，由JVM调度，栈自动伸缩，**可以开几十万、上百万**。
但是虚拟线程也不是没有代价：
- 虚拟线程适合IO等待场景；
- 虚拟线程不要长时间持有synchronized锁（会挂载载体平台线程）；
- CPU密集型任务依然不适合开海量虚拟线程，CPU还是会打满。

#### ✅ 45秒口述精简版

线程不是越多越好。线程太多会占用大量栈内存，引发频繁CPU上下文切换，消耗CPU资源，还会加剧锁竞争，甚至触发无法创建线程的OOM。线程数要看场景：CPU密集型接近核心数；IO密集型可以适当多一些。任务量大优先用线程池控制上限。Java21虚拟线程是轻量线程，支持大量创建，但CPU密集场景依然不适合海量并发。

### 括号匹配（LeetCode 20，面试标准回答）

#### 核心思路：栈

**遇到左括号入栈；遇到右括号，看栈顶是不是对应的左括号：匹配上就弹出栈顶，不匹配直接失败。**
最后遍历完成，栈必须是空的（所有左括号都被匹配完）。

匹配规则：

- `(` 对应 `)`
- `[` 对应 `]`
- `{` 对应 `}`

#### 流程举例：`{[]}`

1. `{` → 入栈，栈：`[{]`
2. `[` → 入栈，栈：`[{, [}]`
3. `]` → 栈顶是 `[`，匹配，弹出，栈：`[{]`
4. `}` → 栈顶是 `{`，匹配，弹出，栈空
遍历结束栈为空 → 合法。

反例 `([)]`：

1. `(`入栈，2.`[`入栈，3.`)`，栈顶是`[`，和`)`不匹配 → 直接false

#### 边界条件（面试容易漏）

1. 字符串长度奇数：直接返回 false，不可能匹配
2. 遍历到右括号，但栈已经空了：没有左括号和它匹配 → false
3. 遍历结束栈不为空：还有剩余左括号没有匹配 → false

#### Java 可运行代码（Scanner输入）

```
import java.util.HashMap;
import java.util.Map;
import java.util.Stack;
import java.util.Scanner;

public class ValidParentheses {
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        String s = sc.nextLine();
        sc.close();
        System.out.println(isValid(s));
    }

    public static boolean isValid(String s) {
        if (s.length() % 2 != 0) {
            return false;
        }
        Map<Character, Character> map = new HashMap<>();
        map.put(')', '(');
        map.put(']', '[');
        map.put('}', '{');
        Stack<Character> stack = new Stack<>();
        for (char c : s.toCharArray()) {
            if (map.containsKey(c)) {
                // 右括号
                if (stack.isEmpty() || stack.pop() != map.get(c)) {
                    return false;
                }
            } else {
                // 左括号
                stack.push(c);
            }
        }
        return stack.isEmpty();
    }
}
```

时间复杂度：$(O(n))$，n是字符串长度，每个字符入栈出栈最多一次
空间复杂度：$(O(n))$，最坏全是左括号，栈存全部字符

#### ✅ 45秒口述版

括号匹配用栈解决。遍历字符串，左括号压入栈；遇到右括号，取出栈顶，判断是不是对应的左括号，匹配就弹出，不匹配直接返回不合法。如果遇到右括号时栈为空，也是非法。遍历结束之后栈必须为空。字符串长度是奇数可以直接提前返回false。

一般不行，括号存在嵌套关系，栈天然适合处理嵌套；只有单一种括号（只有小括号）可以用计数器。

> 
> 比如只有`()`：遇到`(`count++，`)`count--，count不能小于0，最后count=0。多种括号计数器区分不了类型。

Q：进阶题：最长有效括号？

### 两个栈实现队列（面试标准答案）

队列特性：**先进先出 FIFO**
栈特性：**后进先出 LIFO**
思路：两个栈分工，一个**入栈（inStack）**专门接收新增元素；一个**出栈（outStack）**专门用来弹出元素。

> 
> 核心规则：只有 outStack 为空的时候，才把 inStack 里所有元素一次性全部倒入 outStack。

#### 流程演示

入队顺序：1，2，3

1. 入队1、2、3 → 全部 push 进 inStack

```
inStack: [1,2,3] （栈顶3）
outStack: []
```

2. 现在要出队，outStack是空，把inStack全部转移到outStack

```
inStack: []
outStack: [3,2,1]（栈顶1）
```

3. outStack pop → 拿到1（最先入队的元素），符合队列FIFO
后续继续pop依次是2、3
4. 如果 outStack 还有元素，直接pop，**不要倒**！只有空了才触发转移。

> 
> ⚠️ 关键坑：不能每次取元素都倒一遍，会打乱顺序。

#### Java 代码

```
import java.util.Stack;
import java.util.Scanner;

public class MyQueue {
    private Stack<Integer> inStack;
    private Stack<Integer> outStack;

    public MyQueue() {
        inStack = new Stack<>();
        outStack = new Stack<>();
    }

    public void push(int x) {
        inStack.push(x);
    }

    public int pop() {
        if (outStack.isEmpty()) {
            transfer();
        }
        return outStack.pop();
    }

    public int peek() {
        if (outStack.isEmpty()) {
            transfer();
        }
        return outStack.peek();
    }

    public boolean empty() {
        return inStack.isEmpty() && outStack.isEmpty();
    }

    // 把inStack全部转移到outStack
    private void transfer() {
        while (!inStack.isEmpty()) {
            outStack.push(inStack.pop());
        }
    }

    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        MyQueue q = new MyQueue();
        q.push(1);
        q.push(2);
        System.out.println(q.peek());
        System.out.println(q.pop());
        System.out.println(q.empty());
        sc.close();
    }
}
```

#### 复杂度分析

- 均摊时间复杂度：$(O(1))$
每个元素最多入栈一次、倒栈一次、出栈一次，均摊下来每个操作(O(1))
- 空间复杂度：$(O(n))$，存储全部元素

#### ✅ 45秒口述版

用两个栈实现队列，一个inStack负责入队，outStack负责出队。当需要取元素的时候，如果outStack为空，就把inStack里面所有元素依次弹出压入outStack；outStack不为空就直接取栈顶。这样元素顺序反转，实现先进先出。每个元素最多转移一次，均摊复杂度(O(1))。

#### 高频追问

Q：为什么不能每次pop都转移？
如果outStack还有数据，再次转移会打乱顺序。
Q：那两个队列怎么实现栈？
反过来：一个队列存数据，出栈的时候把除最后一个元素外全部挪到另一个队列，取出最后元素。

### 线程池核心参数 + 配置调优

（Java面试，ThreadPoolExecutor）

#### 七大参数先背清楚

```
public ThreadPoolExecutor(
    int corePoolSize,          // 核心线程数
    int maximumPoolSize,       // 最大线程数
    long keepAliveTime,        // 非核心线程空闲存活时间
    TimeUnit unit,             // 时间单位
    BlockingQueue<Runnable> workQueue, // 阻塞队列
    ThreadFactory threadFactory,       // 线程工厂
    RejectedExecutionHandler handler   // 拒绝策略
)
```

#### 逐个解释 + 执行流程

任务进来顺序：

1. 当前运行线程数 < **corePoolSize** → 新建核心线程执行任务
2. 核心线程满了 → 任务进入 **workQueue 阻塞队列**排队
3. 队列也满了 → 新建**非核心线程**，直到线程总数达到 `maximumPoolSize`
4. 线程数达到最大、队列也满：触发 **拒绝策略**

> 
> 重点：**不是先开最大线程，再进队列！很多人这里记错**

---

#### 四个拒绝策略（JDK自带）

1. **AbortPolicy（默认）**：直接抛 `RejectedExecutionException`，中断提交，适合关键任务，快速发现过载
2. **CallerRunsPolicy**：提交任务的调用线程自己执行这个任务（限流，放缓提交速度，最常用）
3. **DiscardPolicy**：默默丢掉这个任务，无异常，适合不重要、可丢失的日志类任务
4. **DiscardOldestPolicy**：丢掉队列里最老的未执行任务，加入新任务

> 
> 生产一般不用默认Abort，优先 `CallerRunsPolicy`；消息、日志场景按需Discard。

---

#### ✅ 参数怎么配置（调优核心）

先区分业务类型：**CPU密集型 / IO密集型**

> 
> 前提：公式只是理论参考，**最终瓶颈往往不在CPU，而在下游资源（DB连接池、Redis、外部HTTP）**

##### 1. CPU密集型（计算、加解密、向量运算，几乎无等待）

线程不要多，多了上下文切换爆炸

- corePoolSize ≈ CPU核心数 + 1
- maximumPoolSize 和 corePoolSize 设置一样，不需要非核心线程
- 队列：短队列，比如 `ArrayBlockingQueue` 几十长度即可，防止任务堆积太多
- keepAliveTime：无所谓，因为没有非核心线程

##### 2. IO密集型（数据库、Redis、RPC、HTTP，绝大多数后端业务）

线程大量时间阻塞等待IO，CPU空闲，可以多一点线程
公式：

> 
> 线程数 = CPU核心数 × (1 + IO等待时间 / CPU计算时间)
> 经验值：**核心线程设置为 CPU核心数 2 ~ 5倍**
> 举个例子：8核机器，core可以设16~40之间
> ⚠️ 天花板约束：**不能超过下游中间件的连接池上限！**
> 比如数据库连接池只有20，你的线程池开到100没有意义，大量线程卡在拿连接，锁竞争加剧。

队列选择：

- `ArrayBlockingQueue`：有界队列，**生产推荐！必须有界**，防止无限堆积任务撑爆内存（无界队列LinkedBlockingQueue大坑：任务无限入队，永远不会创建非核心线程、不会触发拒绝策略，OOM）
- `SynchronousQueue`：不存任务，直接移交，适合任务提交很快、希望快速扩容到max线程
- `LinkedBlockingQueue`：默认无界，业务开发**禁止直接用不带容量的构造器**

keepAliveTime：非核心线程空闲多久回收，一般 60s，够用。

##### 3. 核心线程是否允许超时回收？

`allowCoreThreadTimeOut(true)`
适合：任务量波动极大，低峰期想释放核心线程，节省资源；一般业务不开。

---

#### 常见坑（面试高频）

1. ❌ 使用无界队列 `new LinkedBlockingQueue()`：队列无限装任务，maxPoolSize 失效，不会触发拒绝策略，流量突增OOM
2. ❌ core 和 max 设置很大，超过下游连接池，造成雪崩
3. ❌ 拒绝策略用Abort，高并发直接大量报错
4. ❌ 线程工厂不自定义：线程没有业务名字，出问题栈日志分不清是哪个业务线程池

---

ThreadPoolExecutor七大参数：核心线程数、最大线程数、空闲超时、时间单位、阻塞队列、线程工厂、拒绝策略。任务流程：先核心线程，核心满了进队列，队列满再开非核心线程，达到最大线程且队列满触发拒绝。

### volatile 无法保证 count++ 的原子性

一句话结论：**不是原子操作，volatile 无法保证 count++ 的原子性，多线程下依然会有并发安全问题。**

#### 1. count++ 本质是三步操作（非原子）

```java
count = count + 1;
```
拆解：
1. **读**：从主内存读取 count 的值到工作内存
2. **改**：CPU执行 +1 计算
3. **写**：把新值写回主内存

volatile 只能保证：
- ✅ **可见性**：一个线程修改后，其他线程立刻能看到最新值
- ✅ **禁止指令重排**
- ❌ **不能保证原子性**：它管不了「读-改-写」这三步整体不被打断

#### 2. 出错场景演示

初始 count=0
线程A读到0，还没写回去；线程B同时也读到0，各自+1，最后都写回1。
预期结果是2，实际结果是1，出现**覆盖丢失**。

#### 3. 解决方案（面试必背）

1. `synchronized` 包裹 count++
2. `AtomicInteger`（底层CAS，无锁，推荐）
```java
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();
```

#### 45秒口述精简版

volatile不能保证count++原子性。count++分为读取、计算、写回三步。volatile只保证可见性和禁止重排，无法保证这三步不被线程打断，多线程会出现值覆盖。想要原子自增，可以用synchronized或者AtomicInteger的CAS。

#### 高频追问

Q：volatile适合什么场景？
适合**单一赋值**：`boolean flag = true;` 这种，读和写都是单个原子操作。
Q：CAS有什么问题？
ABA问题、自旋空转消耗CPU；可以加版本号解决ABA。
Q：synchronized和volatile区别？
synchronized保证原子、可见、有序；volatile只保证可见、有序，不保证原子。





### 单例模式（面试）

**生产最推荐、最常用：双重检查锁（DCL，Double-Check Locking）单例**
其次：静态内部类（懒加载，不用锁，也非常高频）

> 不推荐：饿汉式简单但不支持懒加载；枚举单例是防反射、防序列化破坏的最优写法。

#### 1. 双重检查锁 DCL（工作最常用）

✅ 特点：懒加载、线程安全、性能好、只有第一次初始化才加锁
⚠️ 重点：`volatile` 关键字不能丢！
作用：禁止指令重排。
`instance = new Singleton()` 不是原子操作：

1. 分配内存
2. 初始化对象
3. 引用赋值给instance
不加volatile，重排可能 1→3→2，别的线程拿到半初始化对象。

```java
public class Singleton {
    private static volatile Singleton instance;
    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {         // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null) { // 第二次检查
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

#### 2. 静态内部类（懒加载，很多框架源码在用）

✅ 优点：利用类加载机制保证线程安全，没有锁，效率高；外部类加载时内部类不会加载，实现懒加载
```java
public class Singleton {
    private Singleton() {}
    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
```
原理：类的静态变量只有在首次使用时才初始化，JVM保证初始化阶段线程安全。

#### 3. 饿汉式

✅ 简单，线程安全；❌ 类加载就实例化，不支持懒加载，如果对象很大、一直不用会浪费内存
```java
public class Singleton {
    private static final Singleton instance = new Singleton();
    private Singleton(){}
    public static Singleton getInstance(){
        return instance;
    }
}
```

#### 4. 枚举单例（《Effective Java》推荐，防反射、防序列化）

✅ 天然单例，不会被反射、序列化破坏；缺点不是懒加载
```java
public enum Singleton {
    INSTANCE;
    // 业务方法
}
```

#### ✅ 45秒口述版

项目里最常用双重检查锁DCL，懒加载、线程安全，要加volatile防止指令重排。静态内部类也是很常用的方案，依靠JVM类加载保证安全，没有锁开销。饿汉式简单但不懒加载；枚举单例安全性最高，可以抵御反射和序列化攻击。

#### 高频追问

Q：volatile在这里干什么？
A：防止 new 对象的时候指令重排，避免其他线程拿到未初始化完成的实例。
Q：静态内部类为什么线程安全？
A：JVM在加载静态内部类的时候，会保证静态变量初始化只执行一次，同步由JVM保证。
Q：怎么破坏单例？怎么防止？
反射、序列化可以破坏DCL/静态内部类；枚举天然防这两种攻击。

### 枚举单例：为什么天然防反射、防序列化

先贴基础代码回顾：

```
public enum Singleton {
    INSTANCE;
}
```

#### 一、防反射原理

普通DCL、静态内部类单例，构造器是 `private`，但是**反射可以强行setAccessible(true)，调用私有构造方法创建新对象**，破坏单例。

枚举的底层规则：

1. 枚举类的构造方法，**JVM有特殊校验**；
2. `java.lang.reflect.Constructor.newInstance()` 源码里有判断：
如果这个Class是枚举类型，直接抛出异常 `IllegalArgumentException: Cannot reflectively create enum objects`> 
> 反射API直接禁止通过构造器实例化枚举。
> 👉 你拿不到构造器去new，所以反射搞不定。

> 
> 坑补充：
> 不是私有构造器不让你访问，是**newInstance方法里硬编码拦截枚举类型**。就算你拿到构造对象、打开权限，调用newInstance直接报错。

#### 二、防序列化原理

普通对象序列化：把对象字段写出；反序列化时，通过反射**新建一个对象**，再把字段填充进去，所以会产生新实例，破坏单例。

枚举序列化是JDK特殊定制逻辑：

- 序列化的时候：**只把枚举的名字字符串（name）写到流里，不会把对象实例整体序列化**
- 反序列化的时候：不是新建对象，而是调用 `Enum.valueOf(Class<T> enumType, String name)`
从枚举类里拿已经定义好的常量对象，**直接返回内存中已有的INSTANCE，不会创建新对象**

所以反序列化前后是同一个对象。

#### 三、对比一下

- DCL / 静态内部类：
反射：可以暴力调用构造器，产生新实例；
序列化：反序列化生成新对象，单例被破坏。
- 枚举单例：
反射：JDK反射API拦截，无法new；
序列化：反序列化返回原有常量实例。

#### ✅ 45秒口述精简版

枚举单例天然防反射和序列化破坏。反射方面，Constructor的newInstance方法内部做了判断，不允许创建枚举实例，直接抛异常。序列化方面，枚举序列化只保存枚举名称；反序列化时通过Enum.valueOf获取类里已经存在的常量，不会新建对象。Effective Java也推荐枚举实现单例。

#### 高频追问预备

Q：枚举能不能被克隆破坏？
枚举重写了clone，直接抛CloneNotSupportedException，不能克隆。
Q：枚举是饿汉还是懒加载？
枚举是饿汉式，类加载的时候就初始化INSTANCE，不支持懒加载。
Q：那我业务想要懒加载，又要防反射序列化怎么办？
没有完美方案；一般还是静态内部类，业务上禁止反射、序列化传输这个单例对象。

### 题目：1000万条数据，不全部排序，找出最大100个

核心方案：**小顶堆（最小堆）**，面试标准答案

> 思路：维护一个容量为100的小顶堆，堆顶是当前这100个里面最小的。遍历所有数字：
>
> 1. 堆没满：直接加入堆
> 2. 堆满：如果当前元素 > 堆顶，弹出堆顶，把当前元素入堆；否则跳过 遍历结束，堆里就是全局最大的100个数。

#### 复杂度分析（必说）

- 数据总量 N = 1000w，K = 100
- 堆操作：每次堆调整是 $O(\log K)$
- 总时间复杂度：$O(N \log K)$
- 如果全排序：$O(N\log N)$，1000w排序代价大很多
- 空间复杂度：$(O(K))$，只存100个元素，非常省内存

对比：

- 如果用大顶堆：要先全部塞进去再pop100，空间(O(N))，不行
- 快排变形（快速选择）：$(O(N))$ 期望时间，但是不稳定，最坏 $O(N^2)$；而且数据量大、流式数据（数据没法一次性全部加载进内存）的时候不好用。 ✅ 小顶堆优势：**支持流式读取，不用一次性把1000万数据加载到内存**，适合大数据场景。

#### Java代码（PriorityQueue 默认就是小顶堆）

```
import java.util.PriorityQueue;
import java.util.Scanner;

public class TopK {
    public static void main(String[] args) {
        int k = 100;
        PriorityQueue<Long> minHeap = new PriorityQueue<>(k);
        Scanner sc = new Scanner(System.in);
        while (sc.hasNextLong()) {
            long num = sc.nextLong();
            if (minHeap.size() < k) {
                minHeap.offer(num);
            } else if (num > minHeap.peek()) {
                minHeap.poll();
                minHeap.offer(num);
            }
        }
        sc.close();
        // 堆中就是最大100个，注意：堆内无序，需要再取出排序才是从大到小
        while (!minHeap.isEmpty()) {
            System.out.print(minHeap.poll() + " ");
        }
    }
}
```

> 注意一个面试坑：堆里只是top100集合，**堆内部不是降序有序**，如果要求输出按从大到小，最后拿到集合再单独排序这100个，代价 $O(K\log K)$，可以忽略。

#### ✅ 45秒口述版

1000万数据找最大100个，最优是小顶堆。维护大小为100的小顶堆，堆顶是堆里最小值。遍历每条数据，堆未满直接入堆；堆满时，元素比堆顶大就替换堆顶。时间复杂度O(N logK)，远好于全排序O(N logN)，而且支持流式读取，不需要一次性加载全部数据。缺点是最后堆内无序，如果需要有序结果，只需要对这100个元素单独排序。

#### 高频追问

1. 为什么不用大顶堆？ 大顶堆是堆顶最大，如果存全部1000万数据，空间(O(N))，1000万全放内存压力大；小顶堆只占K个空间。
2. 快速选择算法为什么不优先？ 期望(O(N))更快，但最坏O(N²)；并且需要随机访问，数据如果是文件流式、不能全部载入内存就用不了，工业上topK优先堆方案。
3. 如果数据存在磁盘，不能一次性读入内存怎么办？ 小顶堆天然支持，分批读取，逐条处理，不用加载全部数据。
4. 如果K很大，比如K=500w？ 这时堆方案性能变差，可以考虑分桶、外排序+归并思路。

### 2. 了解HTTP吗，从网络分层讲原理

从TCP/IP四层模型来讲：

1. **应用层**：HTTP属于应用层协议。客户端组装请求报文（请求行、请求头、请求体），发给服务端；服务端返回响应报文。
2. **传输层**：交给TCP协议。建立三次握手连接，分段、流量控制、可靠传输。端口：HTTP 80，HTTPS 443。
3. **网络层**：IP协议，根据IP地址寻址、路由转发数据包。
4. **网络接口层**：封装成帧，通过MAC地址在链路传输。

传输完成后TCP四次挥手断开连接；HTTP本身无状态，靠Cookie、Token维持会话。

#### 14. 交换机属于哪一层？

二层，**数据链路层**，基于MAC地址转发帧。

#### 15. 路由器哪一层？转发原理？

三层，**网络层**，基于IP地址转发数据包。 原理：维护路由表，收到数据包，取出目标IP，查路由表匹配下一跳，修改二层MAC头，转发到对应出口；跨网段隔离广播域。 作用：连接不同网段，实现跨局域网通信。

#### 16. 四层负载均衡、七层负载均衡，在哪一层，区别？

- 四层：传输层（TCP/UDP），代表LVS。只看IP+端口，不解析应用层协议，转发快，无法感知HTTP路径、Cookie；直接转发报文。
- 七层：应用层，代表Nginx。解析HTTP协议，可以根据url、header、cookie做转发策略；代价更高，性能低于四层LB。

#### 17. TCP三次握手、四次挥手

三次握手（建立连接）

1. 客户端发SYN，seq=x；
2. 服务端回复SYN+ACK，seq=y，ack=x+1；
3. 客户端回复ACK，ack=y+1。

四次挥手（断开连接）

1. 客户端FIN，关闭写方向；
2. 服务端ACK；
3. 服务端处理完剩余数据后发FIN；
4. 客户端ACK，进入TIME_WAIT。

#### 18. 为什么关闭连接需要四次挥手？

TCP是**全双工通道**，两个方向独立关闭： 一方发FIN，代表它不再发送数据，但还可以接收对方剩下的数据。 服务端收到FIN之后，先回ACK，此时服务端还能继续给客户端发剩下业务数据；等服务端数据发完，自己再发FIN。所以不能合并成三次。

#### 19. TIME_WAIT的作用

客户端最后ACK之后等待2MSL才关闭：

1. 保证最后一个ACK报文能到达服务端；如果ACK丢了，服务端超时重发FIN，客户端还能再次回复ACK；
2. 等待网络中该连接的残留旧报文消失，避免新复用端口的连接收到旧连接的脏数据包。

> 痛点：高并发短连接场景大量TIME_WAIT占满端口，是后端线上常见问题。

- **POST**：提交数据、创建资源，非幂等，请求体传参

### 常见排序思想

先分两大类：**比较排序**、**非比较排序**
> 比较排序：基于元素之间大小比较，下界 $O(n\log n)$；非比较排序不比较，利用数值特性，$\(O(n)\)$

#### 面试高频追问

1. 为什么快排比归并、堆排实际更快？

> 缓存友好、常数小；归并需要额外数组拷贝开销，堆排访问跳跃对缓存不友好

2. 稳定排序含义：相等元素**相对顺序不变**
3. TopK：堆排序（小顶堆）、快排分区（快排选择）

#### 一、冒泡排序 BubbleSort

**思想**：相邻两个元素两两比较，逆序就交换；每一轮把最大元素“冒泡”到末尾。
- 稳定 ✅
- 最好：$\(O(n)\)$（优化版，有序标记），最坏/平均：$O(n^2)$
- 空间：$\(O(1)\)$ 原地排序
- 特点：每次确定末尾最大值；适合小规模、基本有序数组
- 稳定排序；适合小规模有序数据，工程几乎不用

```
5 3 4 2 1
第一轮：3 4 2 1 5（5沉底）
第二轮：3 2 1 4 4
```

#### 二、快速排序 QuickSort

**思想（分治+递归）**：选一个基准pivot，一趟遍历把数组分成两部分：左边 ≤ pivot，右边 ≥ pivot；再递归排左右两边。

- **不稳定 ❌**（交换会打乱相等元素相对位置）
- 平均：$O(n\log n)$，最坏 $O(n^2)$（已经有序，pivot选首尾）
- 空间：$O(\log n)$ 递归栈，原地排序
- 优化：三数取中、随机pivot、小区间改用插入排序
- 不稳定排序；不需要额外辅助空间（原地快排）
> 一句话：**分区，小的放左，大的放右，递归**

#### 三、插入排序 InsertSort

**思想**：把数组分成「已排序区间」和「未排序区间」，依次拿未排序第一个元素，向前插入到有序区间合适位置。

- 稳定 ✅
- 最好 $\(O(n)\)$，最坏/平均 $O(n^2)$
- 空间 $\(O(1)\)$
- 特点：**基本有序时极快**；快排底层小区间常用它

#### 四、选择排序 SelectSort

**思想**：分有序区、无序区；每一轮在无序区找到最小值，和无序区第一个位置交换。

- 不稳定 ❌
- 最好/最坏/平均都是 $O(n^2)$
- 空间 $\(O(1)\)$
- 缺点：无论有序与否都要遍历找最小，性能差

#### 五、归并排序 MergeSort

**思想（分治）**：先拆！不断二分拆成小数组，直到单个元素；再合并两个有序小数组，拼成一个大有序数组。

- 稳定 ✅
- 最好/最坏/平均：$O(n\log n)$
- 空间：$\(O(n)\)$（需要额外辅助数组，**不是原地**）
- 特点：性能稳定；适合链表排序、外部排序（超大文件排序）

#### 六、堆排序 HeapSort

**思想**：利用大顶堆（父≥子）。先把数组建成大顶堆；堆顶就是最大值，把堆顶和末尾元素交换，然后对剩下元素重新堆化；重复。

- 不稳定 ❌
- 最好/最坏/平均：$O(n\log n)$
- 空间 $\(O(1)\)$ 原地
- 适用：TopK、海量数据取前 K；
- 缺点：节点访问跳跃，**缓存局部性差，缓存命中率低**

#### 面试追问预判

Q：为什么建堆是O(n)而不是O(nlogn)？
A：底层叶子节点多、深度小，下沉次数少，求和级数算出来线性；只有堆排序每次取最大值修复堆是logn，一共n次，所以排序O(nlogn)。

Q：堆排序为什么缓存差？
A：访问顺序是跳着找子节点，不是数组顺序连续访问，CPU预加载失效，缓存命中率低。

#### 堆化（siftDown 向下堆化，最核心！面试重点）

向下堆化：假设**只有根节点不满足堆性质，左右子树本身已经是合法堆**，把根往下沉到正确位置。
数组存储完全二叉树下标规则（从0开始）：

```
父 i
左孩子：2*i + 1
右孩子：2*i + 2
```
向下堆化步骤（大顶堆）：
1. 拿到当前节点下标 `i`，找到它左右孩子
2. 在 `i、左孩子、右孩子` 三者里选出**最大值的下标 maxIdx**
3. 如果最大值不是当前i：交换 arr[i] 和 arr[maxIdx]；然后把 i 更新为 maxIdx，继续向下堆化（递归/循环）
4. 如果i就是最大值，停止，堆化完成

> ✅ 建堆：不是逐个add上浮！标准建堆是**从最后一个非叶子节点向前，依次执行向下堆化**
> 最后一个非叶子节点下标：`(n/2)-1`
> 建堆整体复杂度是 **O(n)**，不是 O(nlogn)（这个是高频考点！很多人说错）

#### 区分两个堆化：

1. **siftDown 向下堆化（下沉）**：建堆、堆排序交换后修复堆，最常用
2. **siftUp 向上堆化（上浮）**：往堆末尾新增元素时，和父比较往上换，优先用于优先队列add

#### 完整堆排序流程串一遍（面试直接说）

1. 原始无序数组，从**最后一个非叶子节点**向前遍历，逐个向下堆化，把整个数组构建成大顶堆 O(n)
2. 堆顶 arr[0] 是当前最大值，和**数组末尾未排序区间最后一个元素**交换
3. 交换后末尾这个元素就位（排好序了），剩下前面 `len-1` 个元素，对新的根节点执行**向下堆化**，恢复大顶堆
4. 重复2、3，**直到未排序区间只剩1个元素**，数组升序完成

>当未排序区间只剩一个元素的时候，这个元素一定是最小的，本身有序，不用再处理，排序结束。

#### TopK怎么用堆？

求前K大：用**容量K的小顶堆**；遍历全部数字，堆不足K直接入堆；满了就和堆顶比较，比堆顶大才替换堆顶+堆化。最后堆内就是TopK，O(nlogK)，适合数据太大放不进内存。





#### 七、希尔排序 ShellSort（缩小增量排序）

**思想**：插入排序的升级版。先按一个增量gap分组，组内做插入排序；不断缩小gap，直到gap=1退化成普通插入排序。
- 不稳定 ❌
- 时间复杂度和增量序列有关，大概 $O(n^{1.3})$
- 原地排序

#### 八、非比较排序（三个，适合整数，有范围）

##### 计数排序 CountSort

思想：知道元素取值范围，开一个计数数组统计每个数字出现次数；最后按计数顺序输出。
- 稳定 ✅，$\(O(\(n+k\))\)$，k是数值范围
- 局限：只能整数、范围不能太大

1. **简单版本（容易写，但不稳定）** 只统计频次，从小到大循环，重复多次输出。实现简单，但**丢失原始相同元素先后顺序，不稳定**。
2. **稳定版计数排序（标准）**

- 先统计频次
- 对计数数组做**前缀和**：算出每个数值在结果数组里的**最后存放位置**
- 从**原数组末尾向前遍历**元素，放到目标位置，位置减一 👉 从后往前遍历就是保证稳定的关键！相同元素保留输入时的相对先后顺序。

##### 桶排序 BucketSort

思想：把数值分到多个区间桶里，每个桶内部单独排序（插入/快排），最后按桶顺序拼接。
- 适合数据均匀分布；平均 $\(O(n)\)$，最坏退化 $O(n^2)$

##### 基数排序 RadixSort

思想：按低位到高位（LSD），一轮一轮对每一位做稳定排序（一般用计数排序）；先排个位，再十位、百位…
- 稳定 ✅，$\(O(d(\(n+k\)))\)$，d是数字位数

### 2. MySQL主键和外键区别

### 3. TCP三次握手、四次挥手

#### 三次握手（建立连接）

1. 客户端 → 服务端：**SYN，seq=x**，同步序号，请求建立连接
2. 服务端 → 客户端：**SYN+ACK，seq=y，ack=x+1**；SYN代表服务端也要同步序号，ACK确认客户端SYN
3. 客户端 → 服务端：**ACK，ack=y+1**
连接建立，双方可以收发数据

> SYN和ACK标记不能合并成一个报文的理解：SYN是同步序号，需要消耗一个序号；ACK只是确认，不消耗序号
>
> seq 是「我这边发出去的数据的起始编号」,ack = 期望收到对方下一个字节的序号，**是对对方数据的确认**。

#### 四次挥手（断开连接，TCP是全双工，两个方向独立）

1. 客户端 → 服务端：**FIN**，客户端不再发送新数据（**还可以接收服务端发过来的数据**）
2. 服务端 → 客户端：**ACK**，确认收到FIN
> 👉 此时客户端→服务端方向关闭（半关闭）；服务端还可以继续发剩下的数据
3. 服务端数据全部发送完毕后，服务端 → 客户端：**FIN**
4. 客户端 → 服务端：**ACK**，客户端进入 **TIME_WAIT（2MSL）**；服务端收到ACK后直接CLOSED

#### 为什么挥手是四次，不能像握手三次？

握手时SYN和ACK可以放同一个包；
收到FIN的时候，服务端可能还有业务数据没发完，**不能立刻发FIN**，只能先发ACK确认，等数据发送完成之后，再单独发FIN，因此分成两步，合计四次。

---
#### 高频追问（必背）

##### Q1：TIME_WAIT 为什么是2MSL？

MSL：报文最大生存时间。
两个目的：

1. 保证自己发的最后这个ACK能够到达服务端；如果ACK丢了，服务端会重发FIN，客户端还在TIME_WAIT里，可以重发ACK，防止服务端一直卡在LAST_ACK。
2. 等待本连接中网络里残留的迟到数据包全部过期消失，避免新连接复用相同四元组，收到旧连接的脏报文。

##### Q2：2MSL是谁等待？

**主动关闭方（发第一个FIN的那一端）** 等待TIME_WAIT。被动关闭方收到ACK直接关闭，没有TIME_WAIT。

##### Q3：能不能取消TIME_WAIT？

不行，会出现旧报文干扰新连接。生产短连接高并发场景TIME_WAIT太多，会占用端口，优化手段：开启tcp_tw_reuse（Linux）。

##### Q4：CLOSE_WAIT是什么？

服务端收到FIN、回复ACK之后进入CLOSE_WAIT。
**大量CLOSE_WAIT属于故障！** 含义：内核收到FIN给应用程序了，但是应用层一直不调用close()发FIN，代码忘记关闭连接。

#### ✅ 45s口述精简稿

TCP三次握手建立连接：客户端发SYN；服务端回SYN+ACK；客户端再回ACK。
四次挥手是因为TCP全双工，两个方向可以独立关闭。客户端先发FIN，服务端先回ACK，此时单向关闭；等服务端剩余数据发送完，再发送FIN；客户端回复ACK，进入2MSL的TIME_WAIT状态。之所以是四次，是收到FIN时服务端可能还有数据要传输，ACK和FIN不能合并。



### 4. TCP 和 UDP 的区别

1. TCP面向连接；UDP无连接
2. TCP可靠传输；UDP不可靠，不保证到达、不乱序
3. TCP有流量控制、拥塞控制；UDP没有
4. TCP是字节流；UDP是数据报
5. TCP头部大，开销高；UDP头部极简，速度快

TCP可靠手段：序列号+ACK确认、超时重传、滑动窗口、校验和、拥塞控制。
UDP适用：DNS、音视频直播、QUIC。

### 一、操作系统

#### 1. 进程和线程的核心区别是什么？

进程是**资源分配的最小单位**；

线程是**CPU调度的最小单位**。 

进程之间相互隔离；线程隶属于同一个进程，共享进程资源，切换代价更小。 

一句话总结：进程是独立的程序运行实例，线程是进程内的执行流。

#### 2. 它们共享和独享哪些资源？

✅ 同进程内线程**共享**： 地址空间（堆、全局变量、方法区）、文件描述符、信号处理、进程ID、内存映射。 

✅ 线程**独享**： 栈空间、程序计数器PC、寄存器上下文、线程本地存储TLS（ThreadLocal）。 

✅ 进程之间：资源基本隔离，需要IPC（管道、socket、共享内存等）通信。

#### 3. 一个进程里有多个线程，一个线程崩溃了，为什么有可能带崩整个进程？

线程运行在同一个进程地址空间：

1. 如果线程触发**段错误、访问非法内存**，操作系统给整个进程发SIGSEGV信号，进程直接退出；
2. 线程异常没有捕获，JVM中如果非守护线程抛出未捕获异常，线程停止；**如果是OOM这类共享内存资源耗尽，整个进程所有线程都无法分配内存，全部挂掉**；
3. 多个线程共用锁、共享资源，线程崩溃时没释放锁，其他线程死锁卡死，服务不可用。

> 补充（Java场景）：普通业务线程抛Exception如果有try-catch不会崩；但Native代码、JVM内部异常、OOM会让整个JVM宕机。

#### 4. 大概有哪些类型？（进程/线程状态）

进程/线程通用五态：新建、就绪、运行、阻塞（等待）、终止。

- 就绪：等待CPU时间片；
- 运行：正在CPU上执行；
- 阻塞：等待IO、锁、信号，不抢占CPU。

#### 5. 什么情况下判断多线程性能好？什么时候线程很多性能反而差，怎么判断？

✅ 性能好：CPU利用率合理、吞吐量上升、延迟稳定，没有大量上下文切换、没有频繁锁竞争。线程数匹配负载（IO密集型可以多一点，CPU密集型≈CPU核数）。 

❌ 线程很多性能差的典型： 大量**上下文切换、自旋锁空转、锁争抢激烈**，大量时间浪费在线程调度而不是业务计算。 

👉 判断手段： Linux：`top`、`pidstat -w`看ctxt切换次数；`perf`采样；Java侧：Arthas看线程状态，大量WAITING、BLOCKED线程，CPU us不高但sy（内核CPU）很高，大概率线程过多。

#### 6. 线程上下文切换带来哪些成本？怎么判断切换多？

成本：

1. 保存/恢复寄存器、PC、栈上下文；
2. TLB、CPU缓存失效（缓存命中率下降）；
3. 内核态用户态切换开销。 判断：`pidstat -w`看 `cswch/s`（自愿切换，阻塞导致）、`nvcswch/s`（非自愿切换，时间片耗尽、被抢占）；perf看sched_switch事件。sy内核CPU占比很高也是信号。

#### 7. 单核CPU能不能并发运行多个线程？

**可以并发，不能并行。** 单核CPU靠时间片轮转调度，快速切换线程，宏观上看起来同时跑，微观同一时刻只有一个线程在执行。

> 并发：交替执行；并行：同一时刻多核同时执行。

#### 8. 用户态线程/协程为什么减少切换成本？了解协程吗？

内核线程切换需要陷入内核、操作系统调度； 协程（用户态轻量级线程）**调度在用户空间完成，不需要内核参与**，不需要触发系统调用、不用更换进程页表，上下文极小，切换成本远低于内核线程。 Java：虚拟线程（JDK21+）就是协程思想；Go goroutine也是典型协程。 局限：单核下协程如果有阻塞的系统调用（如阻塞IO），依然会绑定承载的内核线程阻塞。

#### 9. CPU亲和性（CPU绑定）了解吗？

CPU亲和性：把一个线程绑定到指定的一个或者几个CPU核上运行。 好处：减少线程在不同核之间漂移，减少TLB、Cache失效，降低上下文切换带来的缓存损失； 风险：绑定不合理会造成核负载不均衡。Java、Nginx、中间件常用这个优化。

### 二、计算机网络

#### 12. IO多路复用哪几个函数？

Linux下：`select`、`poll`、`epoll`（最常用）； macOS/BSD：`kqueue`；Windows：IOCP。 重点讲epoll：水平触发LT、边缘触发ET。

> 一句话：单个线程通过这一组函数同时监听多个文件描述符的IO就绪事件。

Linux IO多路复用三个核心函数：**select、poll、epoll**

##### 1. select

```
int select(int nfds, fd_set *readfds, fd_set *writefds, fd_set *exceptfds, struct timeval *timeout);
```

特点：

- 文件描述符集合用位图 `fd_set`，有最大fd上限（默认1024）
- 每次调用都要**重新拷贝fd集合到内核**
- 返回后需要**遍历全部fd**找就绪的，时间复杂度 O(n)
- 缺点：上限、拷贝开销、轮询扫描，适合fd数量少的场景

##### 2. poll

```
int poll(struct pollfd *fds, nfds_t nfds, int timeout);
```

特点：

- 用 `pollfd` 数组，**没有1024硬上限**
- 依然每次调用拷贝整个数组，返回后遍历找就绪fd，O(n)
- 只是解决了select的fd数量限制，没有解决性能痛点

##### 3. epoll（Linux独有，重点！）

三个配套API：

```
epoll_create()      // 创建epoll实例，返回epollfd
epoll_ctl()         // add/mod/del，向内核事件树注册、修改、删除fd和关注事件
epoll_wait()        // 阻塞等待就绪事件，内核只返回就绪的fd
```

特点：

- 内核使用红黑树保存监听fd，就绪事件放到就绪链表
- **事件就绪回调通知，不需要遍历所有fd，O(1)拿到就绪列表**，海量fd优势巨大
- 只需要一次注册，后续不用反复传fd集合，减少拷贝开销

##### ✅ LT 水平触发（Level Trigger，默认模式）

- 只要fd上还有可读/可写数据，epoll_wait就会持续通知
- 好写、不容易丢事件；缺点：不读完会反复触发，容易惊群（现在内核有EPOLLEXCLUSIVE优化）

##### ✅ ET 边缘触发（Edge Trigger）

- **只有状态发生变化的一瞬间通知一次**（缓冲区从无数据→有数据）
- 通知一次之后，哪怕缓冲区还有数据，不再通知
- 要求：收到事件必须**循环read直到返回EAGAIN/EWOULDBLOCK**把缓冲区读干净；一般搭配非阻塞IO使用
- 优点：通知次数少，性能更高；缺点：容易漏事件，编码复杂

##### 高频面试追问整理

1. epoll为什么比select/poll快？

   > select/poll每次都要把fd集合拷贝进内核，返回后遍历全部fd；epoll在内核维护红黑树，注册一次即可，就绪时内核主动放到就绪链表，epoll_wait直接拿到就绪集合，不用全量扫描，适合上万fd的高并发场景。

2. ET为什么必须非阻塞？

   > 如果是阻塞IO，读到缓冲区空的时候read会直接阻塞住，卡住整个线程，所以ET模式fd一定要设置O_NONBLOCK，循环读直到EAGAIN。

3. LT和ET怎么选？

   > 业务简单、追求稳定不容易出错用LT；高并发、fd很多，想减少通知次数，代码功底足够就用ET。

##### 简短背诵一句话版本（40s口述）

Linux IO多路复用是select、poll、epoll。select基于位图，有1024限制，返回需要遍历所有fd；poll用数组，去掉数量上限，但同样O(n)扫描。epoll是Linux独有的，通过epoll_create、epoll_ctl、epoll_wait三个接口，内核红黑树管理fd，就绪回调通知。epoll分LT水平触发和ET边缘触发：LT只要缓冲区有数据就一直通知，编码简单；ET只在状态变化瞬间通知一次，需要非阻塞IO循环读到EAGAIN，通知更少，性能更好。

#### 22. XSS 和 CSRF 攻击原理

✅ XSS（跨站脚本）： 攻击者往页面注入JS脚本，浏览器渲染页面时执行恶意JS；窃取Cookie、劫持会话、钓鱼。 分类：存储型、反射型、DOM型。 防御：输入过滤、输出转义、CSP策略、HttpOnly Cookie。

✅ CSRF（跨站请求伪造）： 利用浏览器会自动带上目标站点Cookie的特性，诱导用户在已登录状态，访问攻击者页面，悄悄发起请求（比如转账、改密码）。 防御：Token校验（CSRF Token）、校验Referer、SameSite Cookie。

> 重点区分：XSS是**执行恶意代码**；CSRF是**冒用用户身份发起请求**。

#### 23. TCP半连接队列、全连接队列

三次握手过程：

1. 客户端发SYN → 服务端放入**半连接队列（syn queue）**，状态SYN_RCVD；
2. 服务端收到ACK，握手完成，从半连接队列移出，加入**全连接队列（accept queue）**；
3. 应用程序调用accept()从全连接队列取出连接。

- 半连接队列：存放未完成三次握手的连接；SYN洪水攻击就是打满这个队列。
- 全连接队列：握手完成、等待应用层accept的连接；队列满了，新连接会丢包，线上会出现建连失败。 Java NIO、Netty、Nginx都有这两个队列参数可以调。

### 1. StringBuilder 和 StringBuffer 的区别

- **StringBuffer**：方法加了 `synchronized`，**线程安全**；同步锁带来开销，性能偏弱

- StringBuilder：无同步锁，线程不安全；性能更高，单线程场景优先使用

  共同点：底层都是可变char数组（JDK9+改为byte数组），用于字符串拼接，避免频繁创建String对象。

  > 一句话总结：安全与否是核心差异，单线程用StringBuilder，多线程共享才考虑StringBuffer。
  >
  > 大多数实际开发中更常用 `StringBuilder`，因为字符串拼接通常发生在方法内部，是局部变量，不会被多个线程共享。

### 2. 遇到过哪些线程安全问题？

#### SimpleDateFormat 为什么线程不安全

> 
> 一句话结论：**`SimpleDateFormat` 内部有一个 `Calendar` 成员变量，多线程并发调用 `format()` / `parse()` 时会共享、修改同一个 Calendar 对象，产生竞争，导致日期错乱、抛异常**。

##### 源码关键原因

`SimpleDateFormat` 继承 `DateFormat`，父类里面持有：

```
protected Calendar calendar;
```

这个 `calendar` 是**实例变量，不是局部变量**。

- `format()`：会把要格式化的时间设置进 `calendar`，再读取字段输出字符串
- `parse()`：会用 `calendar` 解析字符串，修改 calendar 的时间字段

当多个线程同时用同一个 `SimpleDateFormat` 实例：

1. 线程A刚把 calendar 设置成 `2026-10-31`
2. 线程B立刻把 calendar 改成 `2025-01-01`
3. 线程A继续读取，读到的是被B篡改后的时间 → 日期乱掉、出现随机时间
4. 极端情况：数组越界、`NumberFormatException`

##### 错误写法（面试高频坑）

```
// 全局单例，多线程共用，危险！
private static final SimpleDateFormat sdf = new SimpleDateFormat("yyyy-MM-dd");

public String formatDate(Date date) {
    return sdf.format(date);
}
```

##### 几种解决方案（优劣对比）

1. **每次 new 新对象（简单，开销一般）**

```
public String formatDate(Date date) {
    SimpleDateFormat sdf = new SimpleDateFormat("yyyy-MM-dd");
    return sdf.format(date);
}
```

缺点：频繁创建对象，高并发下GC压力大。

2. **ThreadLocal 缓存（推荐，老项目首选）**

```
private static final ThreadLocal<SimpleDateFormat> SDF_TL =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

public String formatDate(Date date) {
    return SDF_TL.get().format(date);
}
```

每个线程独有一份实例，互不干扰。

3. **Java8+ 推荐：`java.time` 包（DateTimeFormatter，线程安全！）**

```
private static final DateTimeFormatter formatter = DateTimeFormatter.ofPattern("yyyy-MM-dd");
// LocalDateTime / LocalDate 配合使用
```

✅ `DateTimeFormatter` 是不可变对象，天然线程安全，新项目优先用这个。

##### 面试简答版（背这个）

> 
> SimpleDateFormat 线程不安全，因为它内部维护了一个可修改的 Calendar 实例成员变量。多线程并发调用 format、parse 时会并发修改同一个 Calendar，造成时间覆盖、解析异常。Java8 提供 DateTimeFormatter，不可变，线程安全；旧方案可以用 ThreadLocal 隔离每个线程的实例。

### 3. ArrayList 和 LinkedList 的区别？LinkedList是双向还是单向链表？

#### 区别

1. 底层：ArrayList **动态数组**；LinkedList **双向链表**
2. 随机访问：ArrayList支持下标O(1)随机读；LinkedList必须遍历O(n)
3. 插入删除：尾部插入ArrayList很快；**中间位置插入删除LinkedList更快（不需要数组拷贝）**；头尾增删LinkedList优势明显
4. 内存：ArrayList连续内存，CPU缓存友好；LinkedList节点分散，每个节点多存前驱后继指针，内存开销更大
5. 扩容：ArrayList满了会扩容、拷贝数组；链表没有扩容概念

#### 链表结构

LinkedList 是**双向链表（Doubly Linked List）**，每个节点包含：`item数据`、`prev前驱指针`、`next后继指针`。

> 链表基础：单向链表只有next；双向链表同时有prev、next，可以向前遍历。

### 4. HashMap 原理？hash定位数组？必须重写hashCode和equals吗？

#### 底层（JDK8）

数组 + 链表 + 红黑树。链表长度≥8，数组长度≥64时链表转红黑树；树节点≤6退化为链表。

#### 定位桶下标

```
hash = key.hashCode() ^ (hash >>> 16);  // 扰动函数，高低位混合，减少hash碰撞
index = hash & (table.length - 1);      // 代替取模%，table容量是2的n次幂
```

#### hashCode & equals

**必须成对重写**：

- 如果只重写equals不重写hashCode：两个逻辑相等的对象，hashCode大概率不同，会分到不同桶，HashMap认为是两个不同key，造成重复存储。

- 如果只重写hashCode不重写equals：hash相同的不同对象，equals返回false，会判定为不同key。

  > 规则：equals相等的对象，hashCode一定相等；hashCode相等，equals不一定相等（hash碰撞）。

### 5. 单例模式怎么实现？挑常用两种讲

#### ① 双重检查锁 DCL（推荐，工程常用）

```
public class Singleton {
    private static volatile Singleton instance;
    private Singleton(){}
    public static Singleton getInstance(){
        if(instance == null){
            synchronized (Singleton.class){
                if(instance == null){
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

volatile作用：禁止指令重排，防止半初始化对象逸出。

#### ② 静态内部类（懒加载、无锁，简洁推荐面试说）

```
public class Singleton {
    private Singleton(){}
    private static class Holder{
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance(){
        return Holder.INSTANCE;
    }
}
```

利用类加载机制，内部类只有调用时才加载，天然懒加载、线程安全。

> 不推荐饿汉：提前加载占用资源；不推荐枚举（可以提一句：枚举单例天然防反射、序列化破坏）

### 6. Java类执行顺序（两层：父类、子类）

优先级：**静态 > 非静态（实例） > 构造方法** 执行顺序：

1. 父类静态代码块、父类静态变量（只加载一次）

2. 子类静态代码块、子类静态变量

3. 父类实例变量、父类普通代码块

4. 父类构造函数

5. 子类实例变量、子类普通代码块

6. 子类构造函数

   > 静态属于类，类加载阶段执行；实例代码块、构造器是new对象的时候执行。

> 
> 一句话结论：**同一个类中，按代码书写顺序依次执行静态变量赋值、静态代码块；类初始化只执行一次；先父类、后子类**

#### 1. 核心规则

1. **类加载的初始化阶段（<clinit>方法）**：编译器会把
   - 静态变量显式赋值语句
   - static{} 静态代码块
   按源码从上到下顺序，合并进同一个 `<clinit>()` 方法。
2. **顺序：父类静态 → 子类静态**
   - 先执行父类所有静态变量、静态代码块
   - 再执行子类所有静态变量、静态代码块
3. **静态只在类初始化时跑一次**，new 对象多次也不会重复执行；
（和实例代码块、构造器区分：实例是每次new都执行）
4. 静态变量如果只是声明，没有显式赋值，默认赋默认值，不会进入clinit。

##### 示例

```
class Father {
    public static int a = 10;
    static {
        System.out.println("父类静态代码块，a=" + a);
    }
}

class Son extends Father {
    public static int b = 20;
    static {
        System.out.println("子类静态代码块，b=" + b);
    }
}

public class Test {
    public static void main(String[] args) {
        System.out.println(Son.b);
    }
}
```

输出：

```
父类静态代码块，a=10
子类静态代码块，b=20
20
```

#### 同一个类内部，书写顺序决定先后（高频坑）

```
public class TestOrder {
    static {
        System.out.println(x); // ✅ 可以读，此时x是默认值0
        // x = 100;
    }
    public static int x = 10;

    static {
        System.out.println(x); // 10
    }
}
```

执行顺序：

1. 先分配内存，所有静态变量赋默认值（x=0）
2. 从上往下执行：
   - 第一个static块：打印x（0）
   - `x = 10` 赋值
   - 第二个static块：打印x（10）

⚠️ 重点：**不能在静态代码块里向前引用变量并赋值（编译报错），但是读取允许**

```
static {
    x = 10; // 编译报错：非法向前引用
}
static int x;
```

#### 对比：静态 vs 实例（面试常一起问）

完整加载顺序（new子类对象时）：

1. 父类静态变量、静态代码块（一次）
2. 子类静态变量、静态代码块（一次）
3. 父类实例变量、实例代码块
4. 父类构造方法
5. 子类实例变量、实例代码块
6. 子类构造方法

> 
> 口诀：**静态优先，父先子后；静态按书写顺序，只跑一次；实例每次new都跑**

#### 面试简答背诵版

类初始化时，先父类、后子类；同一个类里面，静态变量显式赋值和静态代码块按照源码从上到下顺序执行，统一放进`<clinit>`方法，整个类生命周期只执行一次。静态变量先分配内存赋默认值，再执行显式赋值/静态代码块。

### 13. 手撕：二分查找（Java，可直接写在白板）

```
public class BinarySearch {
    public static int binarySearch(int[] arr, int target) {
        int left = 0;
        int right = arr.length - 1;
        while (left <= right) {
            int mid = left + (right - left) / 2; // 防止left+right溢出
            if (arr[mid] == target) {
                return mid;
            } else if (arr[mid] < target) {
                left = mid + 1;
            } else {
                right = mid - 1;
            }
        }
        return -1;
    }

    public static void main(String[] args) {
        int[] nums = {1,3,5,7,9,11};
        System.out.println(binarySearch(nums,7));
    }
}
```

要点：`left <= right`；mid防溢出写法；**二分只适用于有序数组**。

### 2、线程池的参数

`ThreadPoolExecutor`七大参数：

1. **corePoolSize**：核心线程数，一直保留，不会回收
2. **maximumPoolSize**：最大线程数，核心满了，任务队列满之后才创建非核心线程
3. **keepAliveTime**：非核心线程空闲存活时间
4. **unit**：时间单位
5. **workQueue**：阻塞队列，存等待执行的任务（ArrayBlockingQueue、LinkedBlockingQueue等）
6. **threadFactory**：线程工厂，创建线程，可以设置线程名
7. **handler**：拒绝策略，队列+最大线程都满了执行

- AbortPolicy：抛异常（默认）
- DiscardPolicy：直接丢弃任务
- DiscardOldestPolicy：丢弃队列队首任务，执行当前
- CallerRunsPolicy：调用者线程执行任务

执行流程：
来了任务 → 核心线程数未满，新建核心线程；核心满→放入阻塞队列；队列满→新建非核心线程直到`maximumPoolSize`；达到最大线程，执行拒绝策略。

### 6、如何保证三个线程的执行顺序（A→B→C）

方案1：`join()`，A线程执行完，调用A.join()，B再执行；B执行完B.join()，C执行。简单直观。
方案2：CountDownLatch闭锁，A完成计数器减一，B等待；B完成再减一，C等待。适合多线程。
方案3：单线程池，只有一个线程，任务按顺序提交，天然串行。
方案4：Semaphore信号量，设置许可控制放行。

> 不推荐sleep，不稳定，靠时间不可靠。

> 前提：3个**独立Thread线程**，要求执行顺序：A先跑完 → B再跑 → C最后跑
> ❌ 禁忌方案：`Thread.sleep()`，依靠时间不可控，网络/调度波动就失效，面试直接说不推荐

#### 方案1：Thread.join()

原理：`thread.join()` 会让**当前线程阻塞，直到被join的线程执行完毕**
逻辑：主线程启动A，A.join()；A结束后启动B，B.join()；B结束启动C
```java
Thread a = new Thread(() -> System.out.println("A执行"), "A");
Thread b = new Thread(() -> System.out.println("B执行"), "B");
Thread c = new Thread(() -> System.out.println("C执行"), "C");
A.start();
A.join(); // 主线程阻塞，直到A执行完
B.start();
B.join(); // 主线程阻塞，直到B执行完
C.start();
```
✅ 优点：最简单、代码少，好理解
❌ 缺点：控制逻辑绑在主线程；只能“外部等待”，线程内部没法自主流转；不能复用等待逻辑
适用：简单串行场景

#### 方案2：CountDownLatch（最推荐，高频）

原理：闭锁，计数器递减，await()阻塞，countDown()计数器-1，计数器到0，等待线程放行；**一次性，归零不能重置**
用2个Latch：latchA（A通知B）、latchB（B通知C）

- A执行完 → latchA.countDown()
- B一开始 latchA.await()，等A放行；B执行完 → latchB.countDown()
- C一开始 latchB.await()，等B放行
```java
CountDownLatch latchA = new CountDownLatch(1);
CountDownLatch latchB = new CountDownLatch(1);
new Thread(()->{
    System.out.println("A执行");
    latchA.countDown();
},"A").start();
new Thread(()->{
    latchA.await();
    System.out.println("B执行");
    latchB.countDown();
},"B").start();
new Thread(()->{
    latchB.await();
    System.out.println("C执行");
},"C").start();
```
✅ 优点：线程之间自主等待，不需要主线程阻塞控制；语义贴合“做完通知下一个”
❌ 缺点：一次性，不能循环多次A→B→C；某个线程异常没countDown，后面永久阻塞

#### 方案3：CyclicBarrier（理论可行，不推荐做这个场景）

原理：循环屏障，**所有参与线程都到达屏障点，才统一放行；可以循环复用**，原生是“齐步走”，不是串行。
实现思路：两道屏障 barrier1(2)、barrier2(2)
A跑完等barrier1，B先等barrier1再执行，跑完等barrier2，C等barrier2再执行
✅ 优点：屏障可复用
❌ 缺点：语义很怪，属于强行改造；任意一个线程异常卡住，屏障破损，其他线程抛BrokenBarrierException；本来是多线程汇聚，不是串行流转
> 面试原话：CyclicBarrier能实现，但不是它的设计目标，优先不用。典型场景：多线程分片计算，全部算完再合并结果

#### 方案4：Semaphore 信号量

原理：许可，acquire拿许可才执行，release释放许可给下一个
初始：A许可=1，B、C许可=0
A拿到许可执行，结束释放B的许可；B拿到许可执行，结束释放C的许可

```java
Semaphore semA = new Semaphore(1);
Semaphore semB = new Semaphore(0);
Semaphore semC = new Semaphore(0);
new Thread(()->{
    semA.acquire();
    System.out.println("A执行");
    semB.release();
});
new Thread(()->{
    semB.acquire();
    System.out.println("B执行");
    semC.release();
});
new Thread(()->{
    semC.acquire();
    System.out.println("C执行");
});
```
✅ 优点：灵活，可控许可，适合流转控制
❌ 缺点：代码偏多，需要手动维护许可传递，容易写bug

#### 方案5：Lock + Condition（底层手动控制，偏难，加分项）

原理：一把锁，三个条件变量，状态标记，await阻塞、signal唤醒
状态state：0=待A，1=待B，2=待C
A执行完，state改成1，signal唤醒B；B执行完state改成2，signal唤醒C
✅ 优点：底层自主可控，可以支持循环多次顺序执行
❌ 缺点：代码量大，容易死锁，一般作为补充方案

#### 方案6：单线程池 Executors.newSingleThreadExecutor()

```java
ExecutorService pool = Executors.newSingleThreadExecutor();
pool.submit(()-> System.out.println("A"));
pool.submit(()-> System.out.println("B"));
pool.submit(()-> System.out.println("C"));
```
⚠️ 重点坑！！
它**不是3个不同线程**，是**同一个工作线程串行跑3个任务**。
如果面试官明确要求【三个线程A、B、C】，这个方案不能当主答案，只能补充。
✅ 优点：提交顺序=执行顺序，简单
❌ 缺点：不满足“三个独立线程”的题意

### 7、判断链表有环（快慢指针）
思路：快慢指针，slow每次走一步，fast每次走两步；
如果链表无环，fast会走到null；有环，快慢指针一定会在环内相遇。
扩展：相遇后，一个指针回到头节点，两个指针同速前进，相遇点就是环入口。

```
public boolean hasCycle(ListNode head) {
    ListNode slow = head, fast = head;
    while(fast != null && fast.next != null){
        slow = slow.next;
        fast = fast.next.next;
        if(slow == fast) return true;
    }
    return false;
}
```

### 12、红黑树和AVL树

两者都是自平衡二叉搜索树。

- **AVL树**：左右子树高度差不超过1；平衡严格；旋转次数多；查询快，插入删除开销大。
- **红黑树**：不追求严格平衡，通过红黑五条规则维持大致平衡；最大高度2logn；插入删除旋转少，性能更好；HashMap、TreeMap底层使用。

> 对比总结：查询多选AVL；插入删除频繁优先红黑树。

一句话总述：**两者都是自平衡二叉搜索树；AVL平衡更严格，红黑树平衡宽松一点，工程上红黑树用得更多（HashMap、TreeMap、TreeSet）**

#### AVL树

1. 平衡规则：**左右子树高度差（平衡因子）绝对值 ≤ 1**，平衡要求非常严格
2. 平衡维护：插入/删除时，不平衡就旋转（单旋、双旋：LL、RR、LR、RL）
3. 优点：查找效率稳定，高度更低，查询更快
4. 缺点：
   - 插入、删除极易破坏平衡，**旋转次数多**，修改开销大
5. 适用场景：**查询远多于增删**的场景

#### 红黑树（5条性质，背核心）

红黑树不是靠高度差平衡，靠颜色规则约束最长路径不超过最短路径2倍：
1. 节点要么红、要么黑
2. 根节点是黑色
3. 所有叶子(NIL哨兵节点)是黑色
4. **红色节点的两个子节点一定是黑色（不能连续红）**
5. 从任意节点到它所有叶子路径上，黑色节点数量相等（黑高相同）

> 推论：最长路径 ≤ 最短路径 × 2
1. 平衡规则：宽松平衡，不强制左右高度差≤1
2. 平衡维护：插入删除，通过 **变色 + 旋转** 修复，旋转次数很少（最多2次旋转）
3. 优点：增删的时候旋转少，**修改性能更好**
4. 缺点：树相比AVL略高，查询稍微慢一点点（差距很小）
5. 适用场景：**增删查都比较频繁**，Java TreeMap、HashMap树化都是红黑树

#### 对比表（面试直接看）

|对比项|AVL树|红黑树|
| ---- | ---- | ---- |
|平衡约束|严格平衡，高度差≤1|宽松平衡，最长路径≤最短2倍|
|平衡手段|只靠旋转|变色优先，必要时旋转，旋转很少|

|Java里哪里用到|几乎没有|TreeMap、TreeSet、HashMap链表转红黑树|

### 3、HashMap put过程（JDK8）

1. 计算key的hash值（扰动函数高低位混合）；
2. 判断table数组是否初始化，没有则扩容初始化；
3. 通过`hash & (n‑1)`定位桶下标；
4. 如果桶为空，直接新建Node放入；
5. 如果桶不为空：
   - 桶首节点key相等（hash相同&&equals），覆盖旧value；
   - 如果是红黑树节点，走红黑树插入；
   - 如果是链表，遍历链表末尾插入；链表长度>=8，数组长度>=64转为红黑树；
6. put完成，判断size是否大于阈值threshold，超过则执行resize扩容。

### 4、HashMap的实现（JDK8）
底层：数组 + 链表 + 红黑树。

- 数组table，存放桶；
- 链表解决hash冲突；链表过长转红黑树提高查询效率；节点数小于等于6退化成链表。
- 容量必须是2的幂，`hash & (n‑1)`代替取模；
- 负载因子默认0.75，阈值=容量*负载因子，达到阈值触发扩容，扩容为原来2倍。

### 9、字符串最长无重复子串（滑动窗口）

> LeetCode3，手撕思路
> 滑动窗口left、right双指针；用Set或者HashMap记录字符最近出现下标。right不断向右；遇到重复字符移动left，保证窗口没有重复字符，记录窗口最大长度。
> 时间复杂度O(n)。

```
public int lengthOfLongestSubstring(String s) {
    HashMap<Character,Integer> map = new HashMap<>();
    int maxLen = 0;
    int left = 0;
    for(int right =0;right<s.length();right++){
        char c = s.charAt(right);
        if(map.containsKey(c)){
            left = Math.max(left, map.get(c)+1);
        }
        map.put(c,right);
        maxLen = Math.max(maxLen, right-left+1);
    }
    return maxLen;
}
```

### 10、海量数据的排序（内存放不下全部数据，外部排序）
**外部排序**：

1. 分块：把大文件切分成多个小文件，每块能加载进内存；内存内部快排，写回磁盘。
2. 多路归并：把多个有序小文件进行k路归并，输出最终有序大文件。
优化：败者树减少归并比较开销。

### 2. equals和hashCode为什么要一起重写

> 
> 核心约定：**equals返回true的两个对象，hashCode必须相等；hashCode相等，equals不一定true**

1. 如果只重写equals、不改hashCode：两个逻辑相等的对象，hashCode大概率不一样，HashMap/HashSet会分到不同桶，集合认为是两个不同对象，出现重复存储、查不到的bug；
2. 如果只重写hashCode、不改equals：hash碰撞时，equals返回false，集合能正常区分，但违背规范，可读性差，容易出隐患。

### 3. 介绍HashMap（JDK8）

底层：**数组 + 链表 + 红黑树**

1. 容量必须是2的n次幂，用 `hash & (n-1)` 替代取模，提升效率；
2. hash扰动函数：`h = key.hashCode() ^ (h >>> 16)`，让高位参与运算，减少碰撞；
3. 负载因子默认0.75，`阈值threshold = 容量 * 0.75`，超过阈值触发2倍扩容；
4. put定位桶：
   - 桶为空：直接放节点
   - 桶首key相等：覆盖value
   - 桶是红黑树：走树插入

5. 线程不安全：并发put会丢数据、链表环，并发场景用ConcurrentHashMap。

### 5. Java异常分为哪几种

Throwable 是顶层父类，分两大分支：

1. **Error（错误）**：系统级严重错误，程序无法处理：OOM、StackOverflowError、虚拟机崩溃；
2. **Exception（异常）**：程序层面可捕获处理，又分：
   - 受检异常（Checked Exception）
   - 非受检异常（Unchecked Exception，RuntimeException及其子类）

### 6. 受检异常和非受检异常使用区别

- **受检异常**：编译期强制检查，要么 `try-catch`捕获，要么方法上`throws`抛出给上层调用方；比如IOException、SQLException；用于外部可预期失败（文件不存在、网络IO失败）
- **非受检异常（运行时异常）**：编译器不强制捕获/声明；比如NullPointerException、IndexOutOfBoundsException；大多是代码bug导致。> 
> 开发规范：业务上不要随意抛RuntimeException，框架底层常用；受检异常不要滥用，避免大量throws污染方法签名。

### 7. Java对象的创建过程（new）

1. 类加载检查：先检查类是否加载、链接、初始化，没有就先执行类加载；
2. 分配内存：在堆划分一块内存（TLAB优先分配）；
3. 初始化零值：内存全部赋默认零值（int=0，引用=null）；
4. 设置对象头：markWord、klass指针、哈希、锁标记等；
5. 执行<init>构造方法：初始化成员变量、执行构造代码块、执行构造函数；
6. 把引用赋值给栈上变量。

### 8. 对象内存分配在哪？什么情况堆溢出

- 分配位置：**优先堆Heap**；开启逃逸分析，小对象、不会逃逸的对象，JIT会做**栈上分配**；
- 堆OOM常见场景：
  1. 集合/静态List/Map持续add元素，没有清理，内存泄漏；
  2. 大对象，一次性加载超大文件、大批量数据到内存；
  3. 线程无限创建对象，循环new不释放；
  4. 内存泄漏：ThreadLocal不remove、长生命周期对象持有短生命周期对象引用。

### 9. GC为什么回收不掉OOM对象？

GC回收的前提：**对象没有有效可达引用链**。
OOM的时候，这些对象依然被GC Roots可达（静态变量、栈引用、ThreadLocal等持有），属于存活对象，GC不能回收；不是GC坏了，是业务代码一直持有引用，对象无法被判定为垃圾，堆空间被存活对象占满，触发OOM。

### 10. 除了强引用，还有哪几种引用

一共4种：

1. **强引用**：`Object o = new Object()`；只要引用存在，GC永远不回收；
2. **软引用 SoftReference**：内存不够的时候GC才回收，适合缓存；
3. **弱引用 WeakReference**：只要发生GC，一定会被回收；WeakHashMap；
4. **虚引用 PhantomReference**：最弱，无法通过引用拿到对象，只用来收到回收通知，配合Cleaner做资源释放。

### 11. CPU 100%排查流程（Java线上）

1. `top` 找到占用CPU高的Java进程PID；
2. `top -H -p pid` 看这个进程里面哪个线程TID占用CPU高；
3. printf把TID转成16进制；
4. `jstack pid` 打印线程栈，匹配十六进制TID，定位代码；
5. 分析：死循环、大量自旋CAS、频繁GC（CPU高但是业务慢，看GC）；
6. 辅助：`jstat -gc`看GC情况、Arthas `thread`命令一键定位。

> 
> 两种典型：①业务死循环（us高）；②疯狂FullGC（gc线程占满CPU）

### 12. synchronized修饰普通方法、静态方法区别

本质是锁对象不一样：

- 普通成员方法：锁是**当前实例对象 this**；同一个对象调用同步方法互斥；不同实例互不影响；
- static静态方法：锁是**类的Class对象**；所有实例共用一把类锁；> 
> 类锁和对象锁互不阻塞。

### 13. synchronized代码块里可以锁String或者Integer吗？

**语法上允许，但是工程里强烈不推荐！**

1. String：字符串常量池，`"abc"`字面量复用，不同地方锁同一个字符串，意外锁竞争、死锁；
2. Integer：-128~127缓存，`Integer i=10`多处使用会拿到同一个对象；
✅ 最佳实践：new一个专门的 `private final Object lock = new Object();` 作为锁对象。

### 14. CopyOnWriteArrayList怎么保证线程安全

**写时复制 COW**
读不加锁；写（add/set/remove）的时候：先拿到锁，复制原有数组，在新数组上修改，修改完成后，volatile引用指向新数组。
优点：读极快，适合读多写少；
缺点：写的时候拷贝数组，内存开销大，大批量写性能差；有数据弱一致性（读的是旧数组快照）。

### 15. 有没有CopyOnWriteLinkedList？为什么没有

JDK没有提供。
COW核心代价是**全数组拷贝**：ArrayList是连续数组，拷贝成本可控；
LinkedList是链表，如果做写时复制，修改一个节点就要拷贝整条链表，拷贝开销巨大，性能完全不可接受，所以没有这个实现。

### 16. 线程池7大参数（ThreadPoolExecutor）

`corePoolSize`核心线程、`maximumPoolSize`最大线程、`keepAliveTime`非核心空闲时间、时间单位unit、阻塞队列workQueue、线程工厂threadFactory、拒绝策略handler。
执行流程：任务来了→核心线程未满新建核心；核心满→入队列；队列满→创建非核心直到max；达到max执行拒绝策略。

### 17. core=8，max=10，能不能不进队列，先跑满10个线程再入队？

**原生ThreadPoolExecutor默认策略不能，原生是先队列、再扩容线程**
原生逻辑：核心满了优先丢队列，队列满才开非核心线程。
想要改成：**先开线程直到max，再入队列**，有两种办法：

1. 自定义阻塞队列，重写offer方法，返回false，让线程池认为队列满，去创建非核心线程；
2. 用第三方工具类，或者自己改造线程池逻辑。> 
> 注意：这种模式风险高，流量突刺会瞬间创建大量线程，容易打垮服务，一般不推荐。

### SKILLS

**Skills（Agent Skills）：Skill（技能）是一套编排好的SOP、流程，给AI智能体的、可模块化复用的任务能力包**，是现在SpringAI、MCP生态里的标准概念。

> 一句话区分：**Tool（工具）是单个原子调用（查数据库、调用接口）；Skill（技能）是一套编排好的SOP、流程、经验，会组合多个Tool去完成一个完整任务**

#### 结构

一个Skill就是一个文件夹，**必须包含 SKILL.md**（元信息+步骤指令），还可以附带参考文档、示例、脚本：
```
xxx-skill/
├── SKILL.md        # 核心，yaml头（name、description）+ 执行流程、约束、输出规范
├── references/     # 参考资料、业务规范
├── examples/       # 样例输入输出
└── scripts/        # 可选脚本
```
`description` 用来让模型判断：什么时候该启用这个skill

#### 核心机制：渐进式加载（Progressive Disclosure）

1. 一开始只把所有skill简短描述列表丢给大模型，token消耗很小
2. 模型判断当前任务匹配某个skill，再调用`read_skill`，按需拉取这个skill完整内容进上下文
3. 加载完成后，Agent按照SKILL.md里写好的流程、约束，调用MCP tools完成任务

#### 和MCP、Tool、Prompt对比（面试官最爱追问）

1. **Tool（MCP tools）**：原子能力，单一动作，比如执行SQL、读文件、调用HTTP接口；只做一件小事
2. **Skill**：上层编排包，写清楚「先调用哪个tool、拿到结果怎么处理、异常怎么兜底、输出格式是什么」，把多个tool串成一套业务流程
3. **普通Prompt**：一次性临时提示词，用完就丢；Skill是版本可控、持久化、团队可共享的能力包
4. **MCP**：是传输协议，用来暴露tools、resources；Skills是MCP的扩展规范（`io.modelcontextprotocol/skills`），可以通过MCP服务对外暴露skills列表，提供`skills/list`、`skills/get`接口

### 7. 0~1000万乱序整数，内存只能放下250万，排序输出文件（外部排序）

> 这道题有三种思路：
>
> 1. 通用外部归并排序，不管值域多大都能用；
> 2. 值域固定 0~1000w，如果数字不重复，可以用 Bitmap，只需要约 1.25MB 内存，把对应 bit 置 1，最后顺序遍历 bit 输出；
> 3. 如果允许数字重复，Bitmap 不行，改用计数排序

#### 核心思路：分块 + 内部排序 + 多路归并

总数据：1000万；内存上限：250万
1. **拆分分片（分块）**
把1000万数字，分成若干块，每一块大小 ≤250万。
1000 / 250 = 4块
- 块1：0~2499999
- 块2：2500000~4999999
- 块3：5000000~7499999
- 块4：7500000~9999999

> 每次读取一块进内存，**内存里用快排/堆排排序**，排好之后写入临时文件。
👉 得到4个**有序的临时子文件**。

2. **多路归并（4路归并）**
现在有4个有序文件，每个文件有一个读取指针。
每次从4个文件当前指针取出的数里，选最小的，写入最终结果文件；
被取出数字的那个文件指针往后移动；循环直到所有文件读完。

---
#### 优化&面试官追问重点

##### Q1：为什么这么分？为什么是4块？

内存只能放250万，每块不超过250万，保证单块可以全部载入内存做内部排序。
1000w / 250w = 4，生成4个有序段，然后4路归并。

##### Q2：多路归并怎么高效取最小值？

用**小顶堆**！
堆里面保存每一路当前的候选数字+属于哪个文件。
- 初始化：从每个有序文件读第一个数，放入小顶堆
- 取出堆顶最小元素，输出到结果文件
- 从刚刚取出元素对应的那个临时文件，再读下一个数字，放进堆
- 重复，直到堆为空

> 堆大小等于归并路数（这里堆大小=4，开销极小）

##### Q3：如果数据量更大，比如分成几十上百块怎么办？

内存放不下这么多路同时读，不能直接全部一起归并，用**败者树**，或者分批归并（多路归并的优化，减少IO）。本题只有4路，直接小顶堆就够用。

##### Q4：能不能用计数排序？（非常高频追问！）

数字范围是 0~1000万，一共10000001个整数。
如果用计数数组：开一个count[]，记录每个数字出现次数。
✅ 优点：O(N)，速度极快
⚠️ 判断内存：
如果int占4字节：1000万 × 4B ≈ 40MB，**远小于250万整数的内存上限**！
👉 这道题**最优方案其实是计数排序**！

> 这里两个解法，你面试可以两层回答，显得更好：
> 先说常规外排序方案（归并）；然后补充：因为数值范围连续固定0~1000w，还可以用计数排序，更高效。

#### ✅ 两种方案对比（面试推荐回答顺序）

方案A（通用外部归并排序，不限定数值范围，万金油）
- 分块 → 内存内排序生成有序临时文件 → 小顶堆多路归并输出

方案B（本题专属，计数排序，更优）
数字值域固定0~1000万，开辟计数数组统计每个数字出现次数，遍历0到1000万，按次数输出，只需要一次扫描输入。内存开销很小。

> ⚠️ 坑点：如果题目改成：整数范围很大（比如32位随机int，值域上亿、不连续），就不能计数排序，只能外部归并。

#### 45秒面试背诵稿

这道题是外部排序问题。总共有1000万整数，内存最多放250万。通用做法是外部归并排序：先把数据切分成4块，每块250万，逐块读入内存内部排序，写出4个有序临时文件；之后用小顶堆做4路归并，每次取出各路里最小的数，输出到最终文件。
另外这题数字范围是0到1000万，值域固定连续，可以用计数排序，开辟计数数组统计频次，顺序遍历输出，效率更高。

### 10. 关系型（RDB）和非关系型（NoSQL）区别

1. **数据模型**
关系型：二维表，行+列，Schema固定；
NoSQL：键值、文档、列簇、图，Schema灵活；
2. **事务**
MySQL等RDB：完整ACID，强事务；
大部分NoSQL默认弱事务，支持最终一致性；
3. **查询语言**
RDB：SQL；
NoSQL：自有API；
4. **适用场景**
关系型：金融、人力、订单，数据关联多，需要事务；
NoSQL：缓存、海量日志、文档、向量检索、高吞吐简单读写；
5. **扩展性**
NoSQL天然水平分片容易；MySQL分库分表需要额外成本。

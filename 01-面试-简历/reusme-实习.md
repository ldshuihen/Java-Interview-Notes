### 模块一：多格式简历流式解析与防 OOM 核心治理

##### 追问 1：在多格式（Word / Excel / PDF）简历与文档流式解析中，防止 JVM OOM 的全套底层解决方案与并发防护是什么？（多格式解析防 OOM 核心绝杀大题）

- **核心根因剖析（传统解析为什么极易 OOM？）**：
  传统 Apache POI（如 `XSSFWorkbook`、`XWPFDocument`）与 PDFBox 默认采用 **DOM 树全量内存模型**：
  1. **全量加载反序列化**：解析前一次性把文档结构、所有单元格、样式、批注以及多媒体大图全部读入堆内存构建巨大对象树；
  2. **高倍对象膨胀率**：一个几十兆的文档，解析为 JVM 堆中 Java 对象后会**膨胀 10 ~ 50 倍**（达到数百 MB 乃至数 GB），遇到扫描件、高清寸照/作品集大图或并发解析时，极易频繁触发 Full GC 最终导致 `java.lang.OutOfMemoryError: Java heap space`。

- **三类文档防 OOM 核心方案对比矩阵**：

| 文档类型 | 传统模式痛点 | 核心防 OOM 生产方案 | 底层核心实现原理 | 内存表现 |
| :--- | :--- | :--- | :--- | :--- |
| **Excel (.xlsx/.xls)** | `XSSFWorkbook` 基于 DOM 模型将所有 Row/Cell 装载进堆，几十兆文件膨胀数十倍 | **基于 SAX 事件驱动流式读取**（SXSSF / 阿里 EasyExcel 思想） | 基于 `XMLReader` 逐行扫描 XML 节点，通过监听器回调（`RowHandler` / `AnalysisEventListener`）单行/小批次消费，用完即释放引用触发 GC | 恒定维持在数兆~几十兆，与文件行数无关 |
| **Word (.docx/.doc)** | `XWPFDocument` 全量反序列化文档骨架与内嵌媒体图片（寸照、作品集） | **StAX 流式解包过滤媒体流** + `.doc` 纯文本流抽取 | `.docx` 本质是 ZIP 包，通过原生 `ZipFile` + `XMLStreamReader` 只扫描 `word/document.xml` 的 `<w:t>` 文本标签，**彻底不解压、不加载 `word/media/` 图片流**；老版 `.doc` 采用 POI `WordExtractor` 纯文本抽取；配置 `ZipSecureFile.setMinInflateRatio` 防御解压炸弹 | 无论文档多大多图，堆内存占用恒定在几兆 |
| **PDF (.pdf)** | PDFBox `PDDocument.load()` 默认加载 xref 交叉引用表、字体表及全部页面渲染流 | **磁盘换内存（`MemoryUsageSetting`）** + **按页流式分页提取** | 配置 `MemoryUsageSetting.setupMixed(10MB)`，堆内仅留 10MB，超额自动溢写本地磁盘临时文件；使用 `PDFTextStripper` 分页逐页抽取即时释放；`try-with-resources` 显式关闭销毁底层句柄 | 堆内存严格控制在 10MB 以内，用廉价磁盘置换宝贵堆内存 |

- **系统级并发与全局架构防线（防突发流量打满堆）**：
  即便单个文件内存压到了极限，多并发批量导入时依然可能累积打爆内存，我们在架构层设计了四道防线：
  1. **Semaphore 信号量严格并发流控**：通过 `Semaphore(4)` 严格限制全局同一时刻**最多仅允许 4 个大文件同时执行解析**，超额任务在内存队列中有序等待；
  2. **独立物理隔离线程池与反向背压**：分配专门的文件解析线程池与主业务 HTTP 线程池隔离，采用带有界队列（容量 200）的 `ThreadPoolExecutor`，拒绝策略配置为 `CallerRunsPolicy`（打满时让调用方线程降级执行，形成天然反向背压削峰）；
  3. **网关层前置门禁防御**：严格限制上传单文件上限（如不超过 20MB），并基于 Apache Tika / 文件头 Magic Number（魔数）严格校验真实文件类型，拦截伪装大文件；
  4. **异步化解耦（任务中心）**：接口接收文件后秒级返回 `task_id`，由 Worker 异步流式消费，Redis 记录原子进度，彻底杜绝长时间占用 Tomcat HTTP 工作线程。

- **面试 1~2 分钟高分口述逐字稿（结构化回答模版）**：
  > “我们在解析异构简历与大文件时，核心防 OOM 原则可以总结为：**‘弃 DOM 用流、磁盘换内存、按需解包过滤、架构背压兜底’**：
  > 1. **针对 Excel**：全面摒弃 DOM 树模型的 `XSSFWorkbook`，采用基于 SAX 事件驱动的 **EasyExcel / SXSSF**，单行或小批次读取落库后立即切断引用触发 GC，内存占用恒定维持在几十兆；
  > 2. **针对 Word**：利用 `.docx` 的标准 ZIP 归档结构，通过 **StAX `XMLStreamReader`** 只定向流式扫描 `document.xml` 中的 `<w:t>` 文本标签，**彻底不解压、不加载 `word/media/` 中的高清媒体大图**；针对老版 `.doc` 使用轻量 `WordExtractor`，同时配置 `setMinInflateRatio(0.01)` 防范 Zip Bomb 解压炸弹；
  > 3. **针对 PDF**：使用 PDFBox 的 `MemoryUsageSetting.setupMixed(10MB)` 策略，**堆内存只留 10MB，超额自动溢写磁盘临时文件**，配合 `PDFTextStripper` 按页分批拉取并严格显式释放文件句柄；
  > 4. **并发控制**：在架构层配置 `Semaphore(4)` 限流与独立隔离线程池（`CallerRunsPolicy` 反向背压），从根源杜绝了并发流量下的 JVM 堆溢出。”

##### 追问 1.1：传统 POI 解析 Excel 的 DOM 模式与 EasyExcel / SAX 流式事件驱动在底层实现上有何区别？
- **底层根因**：传统 POI 的 `XSSFWorkbook` 是基于 **DOM 树内存模型**，会将整个 Excel 的所有单元格、样式、批注一次性全部加载进 JVM 堆内存。一个几十兆的大文件会膨胀数十倍（数百兆），极易导致堆内存耗尽引发 OOM（`java.lang.OutOfMemoryError`）。
- **满分回答**：
  > “针对大批量 Excel 导入，**严禁使用传统的 DOM 模式（`XSSFWorkbook`）**。我采用的是 **基于 SAX 事件驱动的流式读取（SXSSFWorkbook / 阿里 EasyExcel 核心思想）**：
  > 1. 底层解析基于 XMLReader 逐行流式扫描 XML 标签节点，通过监听器回调函数（`RowHandler` / `AnalysisEventListener`）单行处理数据；
  > 2. 单行解析持久化后，该行对象立即切断引用被 GC 垃圾回收，常驻堆内存仅需几兆空间；
  > 3. 同时在业务层设置导入批次限制与阈值门禁校验，彻底杜绝了大文件导致的服务端内存崩溃。”

##### 追问 1.2：简历中包含大文件 Word（.doc / .docx）时，如何防范内存撑爆与性能卡顿？遇到解压炸弹（Zip Bomb）如何防御？

- **底层痛点**：很多候选人的简历带有多张超清寸照、设计作品集大图，或长达数十页。传统 POI 的 `XWPFDocument` 同样采用 DOM 树模型，解析时会将文档骨架与内嵌媒体图片一次性全部反序列化到堆内存中，极大消耗内存并频繁触发 Full GC。
- **满分回答**：
  > “针对 Word 大文件，我们在解析管道中做了针对性优化与内存防护：
  > 1. **解压流式轻量提取（绕过全量 DOM 与大图）**：`.docx` 文件本质上是标准 ZIP 压缩包，文本内容集中存储在 `word/document.xml` 中，内嵌的大体积图片存放在 `word/media/` 目录下。我们通过 Java 原生 `ZipFile` 配合 **`XMLStreamReader`（StAX 流式拉取解析器）**，只精准流式扫描读取 `word/document.xml` 里的 `<w:t>` 文本标签，**完全不解压也不加载任何图片媒体流**，将原本上百兆的文档内存开销直降至几兆；
  > 2. **老版 `.doc` 二进制轻量提取**：针对 Word 97-2003 的 `.doc` 复合二进制文档，采用 POI 的 `WordExtractor` 进行纯文本流抽取，避免构造完整的段落样式对象树；
  > 3. **Zip Bomb（解压炸弹）安全防护**：防范恶意上传 1MB 压缩包解压后膨胀为 10GB 耗尽服务器内存/磁盘的攻击，显式配置 `ZipSecureFile.setMinInflateRatio(0.01)` 与最大条目阈值限制。”

##### 追问 1.3：大文件 PDF 解析时，PDFBox 为什么容易造成内存暴涨？生产上如何优化？
- **底层痛点**：PDFBox 默认的 `PDDocument.load(file)` 会将整个 PDF 交叉引用表、字体库以及所有页面的 XObject 页面流统统读进 JVM 堆内存，遇到数百页扫描件或高清多图 PDF 时瞬时吞噬数吉字节内存。
- **满分回答**：
  > “我们针对 PDFBox 采取了 **‘磁盘换内存’** 与 **‘按页流式分批’** 的深度调优策略：
  > 1. **MemoryUsageSetting 磁盘临时文件换内存**：在加载文档时禁用纯内存模式，配置 `PDDocument.load(file, MemoryUsageSetting.setupMixed(10 * 1024 * 1024))`，限制最大仅在堆内存保留 10MB，**超出部分自动溢写到本地磁盘临时文件**，彻底将高内存占用转移到磁盘空间，杜绝 JVM 堆内存 OOM；
  > 2. **按页流式分页提取（Pagination / Batching）**：对于长篇文档，利用 `PDFTextStripper` 设置 `setStartPage(page)` 和 `setEndPage(page)`，逐页流式提取并持久化文本，上一页的资源即时释放，不再整篇文档常驻内存；
  > 3. **资源显式释放与句柄销毁**：解析逻辑一律包裹在 `try-with-resources` 或 `finally` 块中显式执行 `pdDocument.close()`，防止底层文件句柄（File Descriptor）泄漏导致操作系统句柄耗尽。”

##### 追问 1.4：PDFBox 和 Tabula 解析 PDF 时遇到双栏排版、跨行跨列表格怎么处理？非结构化文本如何对齐？
- **满分回答**：
  > “PDF 内部本质上是按坐标绘制字符的流式页面描述语言，并不存在原生的‘表格’或‘段落’概念。解析复杂格式时我们采取分而治之的策略：
  > 1. **复杂表格提取**：使用 **Tabula 抽取字符坐标矩阵**，识别表格边界线与单元格交点坐标，通过计算行高列宽区间聚类还原跨行跨列表格；
  > 2. **双栏/自由非结构化文本抽取**：通过 PDFBox 按段落与物理坐标抽取纯文本流，自研**‘双正则滑动窗口 + 容错字典’**算法（如针对‘教育经历’、‘工作年限’、‘手机号/邮箱’等关键字设置同义词容错字典，容忍空格、冒号及常见 OCR 错漏字），精准完成字段提取与结构化对齐。”

##### 追问 1.5：批量多线程并发导入简历时，如何进行全局背压防护与资源隔离？
- **满分回答**：
  > “如果 HR 一次性批量导入 100 份大文件简历，若不加控制盲目并发处理，多份大文档瞬时并发膨胀会瞬间把 JVM 堆内存打满。我们构建了全方位的**背压与隔离机制**：
  > 1. **独立物理隔离线程池**：分配专门的文件解析线程池，与主业务 HTTP 线程池隔离，采用带有界队列（容量 200）的 `ThreadPoolExecutor`，拒绝策略配置为 `CallerRunsPolicy`（让调用方线程降级处理，形成天然的反向背压削峰）；
  > 2. **Semaphore 信号量严格并发限流**：通过 `Semaphore(4)` 限制全局同一时刻**最多仅允许 4 个大文件同时执行解析**，其余任务在内存队列中有序等待；
  > 3. **前置门禁防御**：网关层严格校验单文件上限（如不超过 20MB），并基于 Apache Tika / 文件头 Magic Number 严格校验真实文件类型，拦截伪装大文件。”



### Excel的**DOM 模式** 与 **SAX 模式**

**不能简单理解为“像分页一样每次切一部分文件读取”，它的核心不是“物理切片分块”，而是“单向事件流扫描 + 内存即读即抛（不构建全量对象树）”。**

为了在面试中能够降维打击、准确表达，我们把 **DOM 模式** 与 **SAX 模式** 的底层差异拆解如下：

---

#### 一、形象比喻：DOM 是“一口吞”，SAX 是“传送带”

* **传统 DOM 模式（`XSSFWorkbook`）——“一口吞”**：
  把 Excel 的全部内容（几万行、几十万个单元格、样式、批注）一次性全部反序列化成 Java 堆对象（`XSSFRow`、`XSSFCell` 等），在 JVM 堆里**强行构建一棵完整的对象树**。
  - **结果**：一个 20MB 的 Excel 文件，反序列化成数百万个 Java 对象后会膨胀到 300MB ~ 1GB，堆内存瞬间被撑爆引发 OOM。

* **SAX 流式模式（EasyExcel / SXSSF）——“流水线传送带”**：
  底层并不把整个文件解析成对象树，而是以**单向输入流（`InputStream`）**的方式，像探针一样从头到尾按顺序扫描 XML 标签。
  - **结果**：处理完当前行，该行对象就失去引用被 GC 回收。**无论 Excel 是一万行还是一千万行，堆内存里常驻的永远只有“当前这一行”**，内存开销恒定在几兆。

---

#### 二、SAX 事件驱动（Event-Driven）的底层硬核机制

`.xlsx` 文件的本质是一个 **ZIP 压缩包**，里面的具体工作表其实就是 XML 文件（例如 `xl/worksheets/sheet1.xml`）。

SAX（Simple API for XML）在解析这个 XML 时，其运行原理如下：

```text
[ 输入流 InputStream ] ──> XMLReader 从前向后逐字节扫描
                               │
遇到 <row r="1">  ──> 触发事件：startElement("row")
遇到 <c r="A1"><v>张三</v></c> ──> 触发事件：characters("张三")
遇到 </row>       ──> 触发事件：endElement("row") 
                               │
                               ▼
               【回调你的监听器 AnalysisEventListener】
               拿到该行 DTO -> 业务消费/批次暂存 -> 断开引用
                               │
                               ▼
                     【立即触发/等待 Young GC 回收】
```

1. **事件驱动回调机制**：
   解析器（`XMLReader`）遇到标签的开始、内容、结束时，**主动触发事件，回调业务监听器（`RowHandler` 或 EasyExcel 的 `AnalysisEventListener`）**。
2. **状态不保留（Stateless）**：
   SAX 解析器只负责往前走，它**不保留之前节点的任何内存引用**。当扫描到 `</row>` 结束标签时，底层该行对应的 XML 节点和数据对象生命周期就结束了。
3. **即读即抛，内存恒定**：
   你在监听器的 `invoke()` 方法中拿到当前行数据，将其暂存或转存后，引用的对象会迅速变成不可达垃圾对象。JVM 的新生代 GC（Minor GC）能够极其轻量、高效地将其回收，堆内存不会产生任何累积。

---

#### 三、那我们在业务代码里说的“每次读 1000 条”又是什么？

你直觉里感受到的“每次读取一部分”，其实是**应用层为了兼顾“数据库 I/O 吞吐”而做的批处理（Batch Chunking）**，而不是 SAX 底层的机制：

* **SAX 底层**：是**单行**（甚至逐个 XML 标签）流式触发的；
* **应用层（如 EasyExcel 监听器）**：
  如果每读一行就执行一次 `INSERT INTO DB`，会产生海量的网络 I/O。因此通常在监听器内部维护一个固定大小的内存列表（如 `List<T> buffer = new ArrayList<>(1000)`）：
  ```java
  public class UserDataListener extends AnalysisEventListener<UserDTO> {
      private List<UserDTO> cachedList = new ArrayList<>(1000);

      @Override
      public void invoke(UserDTO data, AnalysisContext context) {
          cachedList.add(data);
          // 攒满 1000 条，执行一次批量入库
          if (cachedList.size() >= 1000) {
              userMapper.batchInsert(cachedList);
              cachedList.clear(); // 关键：清空引用，立即允许 GC 回收这 1000 个对象！
          }
      }
  }
  ```
  这 1000 条数据占用的堆内存通常不足 1MB，批量写入数据库后立即 `clear()` 释放引用，堆内存始终维持在非常健康的基准线。

---

#### 四、阿里 EasyExcel 相比原生 POI SAX 还解决了什么隐蔽 OOM？

如果面试官深入追问：*“原生的 POI SAX 难道就不会 OOM 吗？为什么还要用 EasyExcel？”*

你可以给出这个**绝杀点**：
> **原生 POI SAX 仍然会 OOM，根因在 `sharedStrings.xml`（共享字符串表）！**
>
> Excel 为了节省存储体积，会把文件内所有重复出现的文本提取到一个共享字符串表 `sharedStrings.xml` 中，单元格里只存字符串的 ID。
> - 原生 POI SAX 在解析前，**默认会把整个 `sharedStrings.xml` 全量加载进 JVM 堆内存**。如果一个文件有数百万个长文本或大量不重复的描述，这个共享字符串表在内存里可能占到几个 G，依然会 OOM！
> - **EasyExcel 的深度优化**：EasyExcel 自研了临时存储，当共享字符串表很大时，它会**利用磁盘临时文件或者自研的轻量级缓存来替代全量内存加载**，真正做到了无论多大的 Excel 文件，堆内存都不会崩。

---

#### 五、面试满分总结话术（可以直接背诵）

> “**SAX 的核心并不是对文件做物理分页切片，而是‘基于 XML 标签事件驱动的单向流式扫描’。**  
> 传统 POI 的 DOM 模式是把整张表的所有单元格反序列化成巨大的 Java 对象树驻留在堆中；而 SAX 模式是像传送带一样从前向后逐行扫描，解析到哪一行就通过监听器回调哪一行，上一行消费完后立即切断引用允许 GC 快速回收。在整个解析过程中，堆内存中常驻的仅有当前行或小批次缓存，使得 JVM 堆内存与文件大小彻底解耦。”

### Word 解析防止 OOM 

Word 解析防止 OOM 的核心手段可以总结为八个字：**“流式解包、只读文本、绕过大图”**。

如果说 Excel 的 OOM 主要是因为**“行数太多”**，那么 Word 的 OOM 绝大多数是因为**“内嵌的高清图片与设计大图”**以及 POI 默认的**“全量 DOM 树膨胀”**。

下面从**底层痛点**、**破局核心机制**与**落地实现**做深度拆解：

---

#### 一、核心痛点：Word 为什么会把内存撑爆？

1. **POI `XWPFDocument` 的全量反序列化**：
   传统的做法是直接 `new XWPFDocument(inputStream)`，它会把文档的所有段落、样式、运行块（Run）、表格以及**所有内嵌的媒体图片**全部反序列化成 Java 堆对象。
2. **真正的内存杀手：图片媒体流（`word/media/`）**：
   候选人简历或企事业单位文档中，常内嵌超清寸照、设计作品集大图，一个 20MB 的 Word，可能 18MB 都是图片。传统 POI 会把这些图片全部以 `byte[]`（字节数组）形式加载进 JVM 堆内存。
3. **XMLBeans 的巨大对象膨胀**：
   POI 底层解析 Word 的 XML 时依赖 XMLBeans，一个简单的段落节点在 XMLBeans 内存对象中会封装大量元数据，**内存膨胀率高达 20~50 倍**。一个几十页的纯文本 Word 也能把几百兆堆内存吃光。

---

#### 二、核心解决方案：StAX 定向流式拉取（绕过图片）

##### 1. `.docx` 的物理本质其实是一个 ZIP 包

如果你把一个 `.docx` 文件的后缀改成 `.zip` 并解压，会发现它的内部文件结构如下：
```text
my_resume.docx (本质是 ZIP 归档)
│
├── word/
│   ├── document.xml       <-- 【文字都在这里】正文段落与文字
│   ├── media/             <-- 【OOM 元凶】所有高清图片、寸照 (占用 90% 体积)
│   ├── styles.xml         <-- 样式信息
│   └── ...
└── [Content_Types].xml
```

##### 2. 核心操作：原生 `ZipFile` + StAX 流式只读 `document.xml`

我们**完全弃用 POI 的全量加载 `XWPFDocument`**，而是直接利用 Java 原生的 `ZipFile` 配合 **StAX 流式拉取解析器（`XMLStreamReader`）**：

1. **彻底绕过媒体流**：
   通过 `zipFile.getEntry("word/document.xml")` **只读取文本 XML 的输入流**。
   
   > **关键收益**：对于 `word/media/` 目录下动辄几十兆的高清图片，**完全不解压、不读取、不加载进内存**！原本 20MB 的大文件，瞬间变成只有几百 KB 的纯文本 XML。
2. **StAX 流式光标拉取（Pull Parsing）**：
   对 `document.xml` 采用 StAX 的 `XMLStreamReader` 逐标签拉取：
   - 碰到 `<w:t>`（Word 文本标签），拉取其中的字符；
   - 碰到 `</w:p>`（段落结束），追加一个换行；
   - 游标向前推进，读完一段文本丢弃一段，堆内存中只有轻量级的游标状态和提取出的字符串缓冲区（`StringBuilder`）。
   
   > **内存表现**：无论这份 Word 有多大、内嵌了多少张图片，**JVM 堆内存占用恒定在几百 KB 到几兆**！

---

#### 三、老版本 `.doc`（Word 97-2003）的防 OOM 方案

很多老系统上传的简历依然是 `.doc` 格式，`.doc` 不是 ZIP 压缩包，而是微软早期的 OLE2 复合二进制文件（Compound File Binary Format）。

- **防 OOM 做法**：
  严禁使用全量构造对象树的 `HWPFDocument`，改用 POI 专为纯文本提取设计的轻量级 **`WordExtractor`**：
  ```java
  WordExtractor extractor = new WordExtractor(inputStream);
  String text = extractor.getText(); // 底层直接扫描二进制文本块流，不构建段落、字体、样式对象树
  ```
  它会直接从二进制流中抽离字符编码流，避免了把复杂的排版对象装入堆内存。

---

#### 四、安全防线：防御“解压炸弹”（Zip Bomb）

在处理 Word 上传时，还有一个极易被忽略的 OOM 攻击——**Zip Bomb（42.zip 效应）**。
- **黑客攻击原理**：黑客制作一个仅 1MB 的 docx 文件（通过极高压缩比压缩全 0 或重复 XML），解压后会瞬间膨胀至 **10GB**，直接将服务器堆内存或临时磁盘打爆。
- **生产级防护配置**：
  显式配置 POI 和 Java 系统的压缩安全门禁：
  ```java
  // 限制最小解压膨胀率：如果解压膨胀比超过 100 倍（即 inflate ratio < 0.01），立即抛出异常拒绝解压
  ZipSecureFile.setMinInflateRatio(0.01);
  // 限制最大解压实体大小
  ZipSecureFile.setMaxEntrySize(50 * 1024 * 1024); // 最大允许单条目 50MB
  ```

---

#### 五、面试 1 分钟答题模板（可直接作答）

> “针对大文件 Word 解析防止 OOM，我们的核心策略是**‘利用 docx 的 ZIP 特性做流式定向解包，彻底绕过媒体大图’**：
> 1. **根因规避**：Word 解析卡顿和 OOM 的罪魁祸首通常不是文字，而是候选人内嵌的高清寸照、设计作品集等媒体图片，以及 POI `XWPFDocument` 全量反序列化带来的数十倍对象膨胀；
> 2. **StAX 流式解包**：`.docx` 本质是 ZIP 包。我们用原生 `ZipFile` 定向流式读取 `word/document.xml`，配合 **StAX `XMLStreamReader`** 游标逐标签提取 `<w:t>` 文本。整个过程**完全不解压、不加载 `word/media/` 中的任何图片**，将上百兆的文档内存开销直降到几兆；
> 3. **老格式与安全兜底**：老版 `.doc` 采用轻量级 `WordExtractor` 提取纯文本流；同时配置 `ZipSecureFile.setMinInflateRatio(0.01)` 门禁，从根源上防御恶意 Zip Bomb 解压炸弹攻击。”



### 模块二：企业级异步导入导出与下载中心体系

##### 追问 2：海量简历批量导入与全员大表导出耗时较长，如何设计企业级“异步导入导出与下载中心”体系？避免接口超时与服务端雪崩？
- **同步导入导出的致命缺陷**：
  1. **504 Gateway Timeout 超时**：Nginx/网关默认 60s 超时，大批量简历解析或数十万行报表导出耗时超过 1 分钟必断连；
  2. **Tomcat 工作线程池耗尽**：长任务独占工作线程（默认 200 个），并发量稍大便导致全站轻量接口排队假死；
  3. **前端白屏体验极差与用户频繁重复提交**；
  4. **失败无法溯源**：批量导入 100 份，若第 50 份报错，同步模式下用户无法获知哪些成功、哪些失败，也无法获取错误报告。
- **满分回答（异步导入导出生产级架构闭环）**：
  > “我们摒弃了传统低效的同步请求，主导设计了**‘异步任务中台 + 下载中心’**的标准闭环：
  > 
  > **一、异步导入全流程（秒级响应 + 实时进度 + 错误报告）**：
  > 1. **上传即返回（秒级解耦）**：前端上传 ZIP 压缩包至临时存储，服务端生成全局唯一 `task_id`，在 `async_task` 任务表插入一条记录（状态：`QUEUED 排队中`），接口耗时 < 100ms 立即返回 `task_id`；
  > 2. **后台异步消费与背压控制**：投递至文件解析线程池，Worker 线程开始解包、流式逐份解析；
  > 3. **Redis 进度原子跟踪 + 轮询进度条**：Redis 维护 Hash（`total_count, processed_count, success_count, fail_count`），每解析完一份原子递增；前端每隔 2s 轮询进度接口，直观展示百分比进度条（如 `85/100, 85%`）；
  > 4. **失败明细隔离与错误报告一键下载**：解析失败的简历（格式损坏、关键字段缺失、手机号重复）单独写入失败明细表，并由 EasyExcel 自动生成一份《导入失败明细及原因.xlsx》上传至 MinIO；任务完成后状态变为 `FINISHED`，用户可在界面一键下载错误报告，精准修改后重新增量上传。
  > 
  > **二、异步导出全流程（深分页拉取 + 流式写入 + 下载中心）**：
  > 1. **创建导出任务**：用户点击导出全部员工档案/晋升报表，服务端记录查询条件快照生成任务 ID，立即返回提示：‘导出任务已提交，请前往【下载中心】查看’；
  > 2. **游标分批拉取与 EasyExcel 流式落盘**：后台异步线程利用游标分页（`WHERE id > last_id LIMIT 1000`）按批从数据库拉取数据；采用 **EasyExcel 流式追加写入** 磁盘临时文件，单批 1000 条写完即释放内存，无论导出 10 万还是 100 万行，JVM 堆内存占用恒定在几十兆；
  > 3. **上传存储并生成时效链接**：文件生成后上传至 MinIO 私有存储桶，更新任务表状态为 `SUCCESS`，生成预签名下载链接（24小时时效）；用户在【下载中心】随时可重新下载；
  > 4. **生命周期清理**：配置 XXL-Job 定时任务每日凌晨自动清理 7 天前的历史导出文件与本地临时目录，防止磁盘被撑爆。”

##### 追问 2.1：海量数据（如 10 万条）批量导入时，数据库事务怎么控制？如果某几行数据出错怎么办？

- **核心痛点**：严禁采用一个大事务（如 `@Transactional` 标注整个导入方法）！10 万条数据全部在一个事务中，会导致数据库 Undo Log 暴涨、行锁长时间持有导致阻塞甚至死锁，且若第 99,999 条校验失败导致整批回滚，用户需要重传全部，体验极差。
- **满分回答**：
  > “我们采用的是 **‘分批独立局部事务 + 错误隔离收集 + 自动化回执生成’** 方案：
  > 1. **分批提交（Batch Chunking）**：基于 EasyExcel 的 `AnalysisEventListener` 监听器，每读取 500~1000 条数据作为一个 Batch，开启一个独立的事务执行批量 `batchInsert` 并立即 `commit`，释放数据库连接与行锁；
  > 2. **宽进严出与行级内存校验**：在批量入库前，先进行业务规则校验（必填项、手机号正则、部门外键存在性）。若该行不合格，**不中断后续数据解析**，而是将错误行号、原始输入及具体失败原因封装为 `ImportErrorRow` 对象暂存至错误收集列表；
  > 3. **合规数据落库，异常数据生成回执**：该批次中校验通过的合规数据正常落库；全量导入结束后，若存在失败行，异步线程使用 EasyExcel 自动生成一份《导入错误明细及原因_xxxx.xlsx》推送到 MinIO，并将错误文件下载地址更新至任务表；
  > 4. **界面闭环反馈**：任务完成状态下，前端明确告知‘成功导入 98,500 条，失败 1,500 条’，并提供‘下载失败明细’按钮，用户改好错误行后仅需重新增量导入，避免全量重复推倒重来。”

##### 追问 2.2：导出百万级超大表时，如何突破单个 Excel Sheet（1048576 行）上限？EasyExcel 流式写入底层为什么不会 OOM？
- **满分回答**：
  > “我们在百万级报表导出中攻克了**‘堆内存平稳’**与**‘Sheet 行数溢出’**两大难题：
  > 1. **EasyExcel 底层防 OOM 原理（SXSSF 模型）**：传统的 POI 会在内存中把所有 Row/Cell 拼装成巨大的 DOM 树；而 EasyExcel 底层基于 SXSSFWorkbook 思想，只在 JVM 堆内存维护一个极小的滑动窗口（如默认 100 行），超出窗口的数据自动流式 flush 到本地磁盘临时文件（`POIFiles` 目录），最后将磁盘临时文件拼接压缩成 `.xlsx`（本质为 ZIP 压缩包）。因此无论导出 10 万还是 100 万行，JVM 堆内存占用恒定维持在数十兆，从根源规避了 OOM；
  > 2. **突破单 Sheet 1,048,576 行上限**：
  >    - 根据 OpenXML 规范，Excel 单个工作表（Sheet）最大行数限制为 $2^{20} = 1,048,576$ 行。如果全量导出数据超过 100 万，盲目单 Sheet 追加写入会触发 `IllegalArgumentException: Invalid row number (1048576) outside allowable range`；
  >    - **多 Sheet 自动分片写入策略**：在 Worker 流式写入循环中维护全局行计数器 `totalRows`，配置分片阈值（如每 50 万行切换一个 Sheet）。当达到阈值时，调用 `EasyExcel.writerSheet(sheetNo, "员工档案_第" + sheetNo + "分卷")` 动态开启新的工作表继续追加流式写入；
  >    - 若极端场景数据量达到千万级，则在服务端自动按百万分片写入多个 Excel 文件，并利用 Java 原生 `ZipOutputStream` 流式压缩为一个 `.zip` 包供用户下载。”

##### 追问 2.3：异步任务执行中若服务器突然宕机/Pod 漂移重启，任务一直卡在 RUNNING 状态怎么办？如何实现任务自愈与幂等防重？
- **满分回答**：
  > “异步长任务最忌讳因为发版重启、OOM 重启导致任务变成‘永久僵尸任务’，我们设计了**‘心跳检测 + 定时补偿巡检 + Redis 幂等防重’**的三重保险：
  > 1. **任务心跳更新机制**：异步 Worker 线程在执行分批解析或导出时，每处理一个批次（约 2 秒），都会原子更新任务表中的 `heartbeat_time = NOW()` 与当前进度百分比；
  > 2. **XXL-Job 僵尸任务超时巡检补偿**：配置定时任务每 3 分钟轮询一次 `async_task` 任务表，查找 `status = 'RUNNING'` 且 `heartbeat_time < NOW() - INTERVAL 5 MINUTE` 的任务。若发生心跳停滞，说明执行此任务的节点已崩溃宕机；
  > 3. **故障自愈与重试流转**：系统自动将该任务标记为 `RETRYING`，若重试次数 `retry_count < 2`，则重新将任务投递至就绪队列由其他健康的 Pod 节点重新消费；若重试超限则标记为 `FAILED`，并在备注记录‘执行节点异常重启，任务已自动终止，请重新触发’，避免用户无止境等待；
  > 4. **前置幂等防重连击**：用户发起导入/导出时，基于 `userId + 业务类型 + 参数MD5` 构造 Redis 锁：`SET lock:task:{userId}:{hash} 1 EX 60 NX`。若前序相同任务正在排队或处理中，直接拒绝重复提交，杜绝用户连击导致服务端堆积大量重复长任务。”

##### 追问 2.4：下载中心如何防止越权下载敏感人事档案/薪酬报表？
- **满分回答**：
  > “人事与薪酬数据极度敏感，下载中心必须杜绝**水平越权（查看/下载他人导出的文件）**与**公网直链嗅探**：
  > 1. **任务源头强绑定与数据权限行级隔离**：创建导出任务时，系统从认证上下文（Sa-Token / JWT）获取当前登录人 `userId`、`deptId` 与数据权限范围，持久化到任务表 `user_id` 列；在后台异步拉取数据拼装 SQL 时，强制拼接该用户的数据权限过滤条件（如只能导出本部门员工），杜绝‘普通员工通过导出接口获取全员薪资’；
  > 2. **下载中心 API 水平越权拦截**：用户查询下载中心列表或发起下载申请时，查询条件强制绑定 `WHERE user_id = #{currentUserId}`，即便黑客恶意篡改请求路径中的 `task_id`，也会因归属人不匹配直接返回 403 Forbidden；
  > 3. **MinIO 私有桶存储 + 短时效预签名 URL**：存储文件的对象存储桶严禁开启公网公开读权限。用户点击下载时，服务端校验身份合法后，通过 MinIO SDK 动态签发带有时效性签名参数的 **Presigned URL（如有效期仅 15 分钟）**，链接过期即刻作废，且不可伪造；或者由后端微服务作为反向代理，校验权限后以流式（`InputStream`）写回 HTTP 响应体，杜绝对象存储底层真实路径外泄。”

>    - 支付系统不能假设接口 100% 可靠，必须靠对账兜底；

>    - 金额计算一律使用 `BigDecimal` 并指定舍入模式，数据库声明 `DECIMAL(18, 4)`，严禁浮点数计算导致的‘一分钱’对账差额；

| 对比维度 | 采购订单付款申请（PO 付款） | 楼内线付款申请（ITB 付款） | 接收付款二合一（Receive & Pay） |
| :--- | :--- | :--- | :--- |
| **业务本质与场景** | 面向**标准硬件/资产采购**（如服务器、交换机、光模块、软件 License 等）的标准采购付款 | 面向电信运营商专属的**机房弱电布线、楼宇综合接入、光缆穿线工程**等工程类服务款项结算 | 面向**周期短、即验即付的敏捷采购或小额服务**，将“资产验收”与“付款申请”合并办理 |
| **前置单据依赖** | 强依赖已审批生效的采购订单（PO），且上游 PMS 系统必须已有**实物资产验收入库单（Receipt）** | 依赖 ITB 框架合同，但**无传统实物入库单**；核心依赖现场**工程量清单（BOQ）、施工里程碑验收单与竣工报告** | 依赖已生效采购订单，但在前端由经办人**一键触发后台接收并直接发起付款**，无需预先做资产接收 |
| **匹配与校验规则** | 严格的**三单匹配（3-Way Matching）**：PO 采购订单 = 物料接收单 Receipt = AP 发票 Invoice；累计付款不得超过 PO 剩余额度与 FAC 预算 | **里程碑节点分期匹配**：按合同工期节点（如预付款 30%、初验 50%、质保金 20%）及工程量确认，扣减对应在建工程预算 | **双动作原子协同**：后端接口同时向 PMS 推送资产接收确认并在中台生成付款单，通过事务协同防两阶段不一致 |
| **核算与资产归属** | 验收后直接入固定资产（FA）或库存商品科目 | 归属于**在建工程（CIP - Construction In Progress）**，需精准分摊至具体的**机房站点（Site / POP 点）、楼层、机架资产编码**，竣工后转固 | 视物料属性直接生成对应的接收记账并挂接 AP 发票 |
| **接口核心技术点** | 校验 PO 状态、锁定时点汇率、三单金额平衡性计算、FAC 预算原子预占 | 校验工程验收附件、里程碑比例合法性、**质保金（Retention Money）延期扣留逻辑**、站点机房元数据校验 | **跨系统分布式事务与补偿**：PMS 接收接口与本地单据保存状态协同、Redis 防重并发加锁、回滚自愈机制 |

- **满分口述回答（STAR 结构）**：
  > “这三种单据分别对应了中国移动国际在不同业务场景下的财务结算模式，我们在 DDD 付款域中针对这三类单据做了统一的领域模型抽象与策略分发：
  > 
  > **一、标准【采购订单付款申请（PO 付款）】**：
  > - **业务场景**：主要面向服务器、网络设备等实物硬件采购。
  > - **核心逻辑**：采用财务严格的 **‘3-Way Matching（三单匹配）’** 机制。经办人发起申请时，必须关联 PMS 已验收入库的 Receipt 接收批次。接口在提交时严格校验：本次付款金额不得大于该 PO 的剩余可付款余额，且币种、单价、数量必须与接收记录一致，同时通过 FAC 预算引擎做额度原子预占。
  > 
  > **二、具有运营商特色的【楼内线付款申请（ITB 付款，In-Building Telecom）】**：
  > - **业务场景**：楼内线指数据中心机房综合布线、楼宇接入网、管道光纤铺设等电信基础设施工程。
  > - **核心区别与接口设计**：
  >   1. **无实物入库凭单**：工程布线不走仓库实物入库，而是依赖**现场工程量清单（BOQ）、工程进度报告与施工监理签字的验收凭据**；接口设计了必须挂接合规附件的门禁校验；
  >   2. **按工程里程碑分期付款与质保金扣留**：工程通常分为‘首期预付款 30%、完工初验 50%、终验质保金 20%’。我们在接口中实现了**质保金（Retention Money）自动扣留与到期解冻**逻辑；
  >   3. **在建工程（CIP）多维度资产分摊**：单据明细必须强制绑定具体的**机房站点（Site / POP 点）、楼宇机房及机柜编号**，确保工程款精准归集到在建工程资产核算科目中，便于竣工后一键转固定资产。
  > 
  > **三、高效极速的【接收付款二合一付款申请（Receive & Pay）】**：
  > - **业务场景**：传统流程下，经办人必须先在 PMS 做‘物料接收’，再跳转到收付中台录入‘付款申请’，系统割裂、耗时漫长。二合一单据专为周期短、即验即付的小额或敏捷业务设计，将两个动作**合并为一键办理**。
  > - **技术攻坚点**：重点解决**跨系统两阶段一致性与并发防重**。前端发起后，后端接口先落库单据并置为‘提交中’，通过 Redis 分布式锁防重复提交；利用 Spring 的 `TransactionSynchronizationManager.afterCommit`，在本地事务提交后同步调用 PMS 的接收确认接口。若 PMS 返回成功则同步更新单据为‘待审批’并挂接接收单；若 PMS 超时或异常，通过定时补偿任务重试并支持失败告警，实现了‘物料接收’与‘付款单生成’的跨系统最终一致，为业务节省了 50% 以上的人工流转耗时。”

##### 追问 2：简历上写了“多币种预算管控、跨境款项支付”，具体业务逻辑是怎样的？如何防止精度丢失？
- **业务背景**：CMI 面向跨国全球业务，结算涉及港币（HKD）、美元（USD）、人民币（RMB）等多币种。付款单包含：**原币金额**（合同/发票币种）与**本位币入账金额**（通常折算为 HKD）。
- **满分回答**：
  > “跨境财务业务中最核心的是**汇率锁定与精度控制**：
  > 1. **汇率锁定机制**：导入 Oracle EBS 生成 AP 发票时，统一拉取 Oracle EBS 当天的 Corporate 汇率快照锁定并持久化至明细表，发票日期与 GL（总账入账）日期分开记录；
  > 2. **底层精度控制规范**：
  >    - Java 代码中涉及金额计算、币种汇率换算、税额计算（如香港预提税 WHT），**一律严格使用 `BigDecimal` 并指定舍入模式（如 `RoundingMode.HALF_UP`）**，严禁使用 `double`/`float`；
  >    - 严禁使用 `new BigDecimal(double)` 构造方法，必须使用 `BigDecimal.valueOf()` 或传入字符串；
  >    - 数据库字段统一声明为 `DECIMAL(18, 4)`，彻底杜绝浮点数计算误差导致财务报表出现‘一分钱’对账差额。”

##### 追问 3：简历写了“数据库事务、缓存保障数据一致性”，在什么具体场景下使用的？
- **场景 A：付款申请提交与外部流程引擎发起（本地事务与外部 HTTP 解耦）**
  > “在提交付款申请时，需同时更新单据状态为‘待审批’并调用外部致远 BPM 流程引擎发起审批。
  > **核心避坑点**：**严禁将外部 HTTP 接口调用放在本地 `@Transactional` 事务内！** 如果第三方接口响应缓慢或超时，会导致本地数据库事务长久持锁不释放，快速耗尽数据库连接池。
  > **我们的标准解法**：本地事务先落库单据并标记为‘提交中’；利用 Spring 的 `TransactionSynchronizationManager.afterCommit` 机制，在**本地事务完全提交成功后，再异步调用流程引擎**。若外部接口调用超时，通过定时补偿任务重试发起，保证单据与流程状态最终一致。”
- **场景 B：Oracle EBS 接口强幂等性（防止重复付款与重复入账）**
  > “财务系统最忌讳重复向核算系统导入发票。EBS 接口要求 `INVOICE_NUM`（发票号）、`VENDOR_NUM`（供应商编号）、`OU`（业务实体）三者必须唯一。
  > 我们在新中台侧构建了三重防护：
  > 1. **前置防重**：利用 Redis 分布式锁拦截财务人员高频重复点击；
  > 2. **状态前置门禁**：仅允许单据处于‘待复核完成’状态才能触发凭证推送；
  > 3. **数据库物理唯一约束兜底**：在发票中间表中以 `(invoice_num, vendor_num, ou)` 建立唯一联合索引，并发重复插入直接被唯一键拦截，杜绝重复生成凭证。”

##### 追问 4：简历写了“生产环境 MySQL 索引调优与慢查排查”，具体是怎么排查和优化的？
- **真实排查场景：付款申请列表的十几个复合动态查询条件**
- **满分回答**：
  > “在测试与准生产环境中，当单据表积累数十万数据后，财务单据综合列表查询出现 2~3 秒慢查询。通过 `EXPLAIN` 分析执行计划，定位到两大瓶颈：
  > 1. **最左前缀失效与大范围扫描**：财务最常根据 `company_id`（公司主体）与 `create_time`（申请日期范围）联合过滤，但原有索引仅建立了 `create_time` 单列索引。因为日期范围扫描行数极大，MySQL 优化器判定全表扫描代价更小，直接导致索引失效。我们重新设计了复合索引 `(company_id, application_status, create_time)`，让高基数等值条件在前、范围条件在后，精准走索引范围查找；
  > 2. **深分页慢查治理**：财务翻到几十页后，`LIMIT 100000, 20` 导致数十万次无效回表。我们改用**延迟关联（Late Row Lookups）**优化：先走覆盖索引子查询提取出当前页的 `id`，再通过主键关联原表获取明细，将查询耗时从 2~3 秒压到了 200ms 以内。”

##### 追问 5：简历上提到“排查业务流程状态流转错误”，能否举一个具体的线上 Bug 案例？
- **真实业务案例：BPM 审批并发回调导致的状态覆盖与重复推票**
- **满分回答**：
  > “在与致远流程引擎联调阶段，发现过一个隐蔽的并发 Bug：
  > 当审批人在 BPM 界面短时间内快速连续点击‘通过’，或网络抖动引发流程引擎自动重试时，中台在几百毫秒内接收到了两条相同的审批通过回调请求。原先代码直接执行 `updateStatus(id, APPROVED)`，导致第二次回调仍然尝试推进状态，甚至并发触发了两次推送到 Oracle EBS 发票的逻辑。
  > 
  > **排查与解决方案**：
  > 我们重构了状态更新机制，引入**基于 SQL 受影响行数的条件乐观更新**：
  > `UPDATE payment_apply SET status = 'APPROVED', update_time = NOW() WHERE id = #{id} AND status = 'WAIT_APPROVE'`
  > 只有当前处于 `WAIT_APPROVE` 状态时，第一条请求才会更新成功（返回行数 1）并继续后续流程；第二条重复请求因条件不匹配，更新受影响行数为 0，程序捕获后判定为重复调用，**直接幂等返回成功并丢弃后续动作**，彻底根治了重复推送问题。”

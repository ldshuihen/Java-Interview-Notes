#### 2. 项目里面怎么容错（高频工程题）

容错 = 故障发生，服务不雪崩、数据不错乱、可以恢复

1. **超时+重试**：RPC/HTTP调用设置超时时间，对幂等接口做有限次数重试，非幂等不能重试；

3. **限流**：限制请求流量，保护核心接口；
4. **补偿机制**：异步任务、消息队列保证最终一致性，失败消息落死信队列人工处理；

6. **数据库层面**：事务保证原子性，重要操作记录日志，方便回滚排查；
7. **多副本/异地备份**：缓存、中间件多实例，单点故障自动切换。

#### 4. synchronized 和 Lock（ReentrantLock）区别

1. **底层**：synchronized是JVM内置锁，自动加锁释放；Lock是JDK API层面，需要手动lock()、unlock()；
2. **锁升级**：synchronized有偏向锁→轻量级→重量级锁升级；ReentrantLock底层AQS；
3. **功能**：Lock支持公平/非公平锁、可中断锁、tryLock超时获取锁；synchronized不支持超时、不可中断；
4. **条件队列**：Lock可以绑定多个Condition；synchronized只有一个等待队列；
5. **性能**：JDK6之后synchronized优化很好，性能差距不大。

```
import java.util.Scanner;
public class Main {
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        int n = sc.nextInt();
        int[] nums = new int[n];
        for(int i = 0; i < n; i++) nums[i] = sc.nextInt();
        int maxSum = nums[0];
        int cur = nums[0];
        for(int i = 1; i < n; i++){
            cur = Math.max(nums[i], cur + nums[i]);
            maxSum = Math.max(maxSum, cur);
        }
        System.out.println(maxSum);
    }
}
```

#### 1. 手写：矩阵差值（二维前缀和，O(1)查询子矩阵和）

> 
> 题目：预处理二维数组，任意给左上角、右下角坐标，O(1)求出子矩阵差值/子矩阵和，标准二维前缀和模板

```
import java.util.Scanner;
public class Main {
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        int m = sc.nextInt(), n = sc.nextInt();
        int[][] mat = new int[m+1][n+1];
        int[][] pre = new int[m+1][n+1];
        for(int i = 1; i <= m; i++){
            for(int j = 1; j <= n; j++){
                mat[i][j] = sc.nextInt();
                pre[i][j] = mat[i][j] + pre[i-1][j] + pre[i][j-1] - pre[i-1][j-1];
            }
        }
        // 查询：(x1,y1) 左上，(x2,y2)右下
        int x1 = sc.nextInt(), y1 = sc.nextInt();
        int x2 = sc.nextInt(), y2 = sc.nextInt();
        int res = pre[x2][y2] - pre[x1-1][y2] - pre[x2][y1-1] + pre[x1-1][y1-1];
        System.out.println(res);
    }
}
```

原理：预处理前缀和数组，把重复计算提前做掉，查询只做一次四则运算，O(1)。

#### 2. 手写：嵌套数组迭代器（数组的数组，内层数组长度不定，可空，实现 hasNext() next()）

思路：维护一个外层指针、内层指针；外层遍历数组，内层走到头就跳到下一个非空内层数组

```
import java.util.List;
class NestedIterator {
    private List<List<Integer>> data;
    private int outer = 0;
    private int inner = 0;
    public NestedIterator(List<List<Integer>> list) {
        data = list;
    }
    public Integer next() {
        return data.get(outer).get(inner++);
    }
    public boolean hasNext() {
        while(outer < data.size()){
            List<Integer> curr = data.get(outer);
            if(inner < curr.size()){
                return true;
            }
            outer++;
            inner = 0;
        }
        return false;
    }
}
```

#### 4. B+树特点，MySQL索引为什么选B+树

B+树特点：

1. 所有**数据都存在叶子节点**，非叶子节点只存索引键，不存数据；
2. 叶子节点之间用双向链表串联；
3. 多路平衡树，树高很低；
4. 查找任何数据，路径长度几乎一致，查询稳定。

为什么MySQL选B+，不选红黑树、B树：

1. 磁盘IO：磁盘按页加载，B+树阶数大，树矮，IO次数更少；
2. 范围查询友好：叶子链表，范围遍历直接顺序扫描，B树/红黑树范围查询要来回跳转；
3. 非叶子不存数据，一页能放更多索引，内存能缓存更多索引节点；
4. 查询性能稳定，每次都落到叶子节点。

#### 5. 手写简易HashMap（JDK7版本，数组+链表，面试手写最简版，不写红黑树）

> 
> 面试官三面手写一般不会要求红黑树，能完成put、get、hash、链表处理就达标

```
public class MyHashMap<K,V> {
    static class Node<K,V>{
        K key;
        V val;
        Node<K,V> next;
        Node(K k, V v){
            key = k;
            val = v;
        }
    }
    private Node<K,V>[] table;
    private int capacity = 16;
    public MyHashMap(){
        table = new Node[capacity];
    }
    private int hash(K key){
        if(key == null) return 0;
        return key.hashCode() & (capacity - 1);
    }
    public void put(K key, V value){
        int idx = hash(key);
        Node<K,V> cur = table[idx];
        if(cur == null){
            table[idx] = new Node<>(key,value);
            return;
        }
        // 遍历链表
        while(true){
            if(cur.key.equals(key)){
                cur.val = value;
                return;
            }
            if(cur.next == null){
                cur.next = new Node<>(key,value);
                return;
            }
            cur = cur.next;
        }
    }
    public V get(K key){
        int idx = hash(key);
        Node<K,V> cur = table[idx];
        while(cur != null){
            if(cur.key.equals(key)){
                return cur.val;
            }
            cur = cur.next;
        }
        return null;
    }
}
```

口述补充：真实JDK8会在链表过长转为红黑树、有扩容机制、扰动hash减少碰撞，手写简化版本只实现基础逻辑。

### 一、线程池系列

> 问题：线程池的参数？请求进来的流程？用过什么线程池？参数怎么配？为什么？有什么隐患？
> ThreadPoolExecutor 7大参数：
> 核心线程数corePoolSize、最大线程数maximumPoolSize、空闲保活时间keepAliveTime、时间单位unit、阻塞队列workQueue、线程工厂threadFactory、拒绝策略handler。

✅ 请求进来流程：

1. 当前运行线程 < corePoolSize → 新建核心线程执行任务；
2. 核心线程已满，任务入阻塞队列；
3. 队列也满了，并且运行线程 < maximumPoolSize → 创建非核心线程；
4. 线程达到最大，队列满 → 触发拒绝策略。

✅ 用过哪些线程池：
阿里规范**禁止直接用Executors快捷创建**，生产自定义ThreadPoolExecutor；
业务场景：

- IO密集型接口异步：核心线程数一般 `2*CPU核心数`；
- CPU密集型计算：核心线程数≈CPU核心数；
队列选LinkedBlockingQueue（有界！不能无界），拒绝策略常用AbortPolicy、或者自定义降级返回。

✅ 连环追问：为什么这么配置，有什么问题？

> 
> 坑点：很多人只背公式，说不出风险

- 如果核心线程设置过大：大量线程抢占CPU，上下文切换暴涨，CPU打高；
- 队列无界LinkedBlockingQueue不设置容量：任务无限堆积，OOM；
- 最大线程和核心线程差距太大，瞬间突刺会大量创建临时线程，GC压力上升；
- keepAliveTime设置太短：线程频繁销毁重建，失去池化意义。

### 二、synchronized 和 ReentrantLock + 公平锁排队

1. **区别（精简口述）**

- synchronized：JVM层面、自动释放锁、锁升级（偏向→轻量→重量级）、不可中断、不支持公平锁自选、只有一个等待队列；
- ReentrantLock：AQS实现、API手动lock/unlock、支持公平/非公平、支持tryLock超时、可中断、多个Condition条件队列。

2. 追问：3个线程抢同一个公平锁ReentrantLock，怎么排队？
AQS内部有一个**双向CLH等待队列**。
公平锁逻辑：线程抢锁前，先检查等待队列前面有没有排队节点：

- 锁空闲，队列前面没有等待节点，才可以拿到锁；
- 已经有排队节点，当前线程封装成Node，加到队列尾部，park阻塞；
- 持有锁的线程释放锁之后，唤醒队列**头节点后面第一个等待线程**，依次按先来后到顺序拿锁。> 
> 重点：公平锁是严格FIFO，会带来额外的排队、唤醒开销，性能一般弱于非公平锁，所以默认是非公平。

### 三、HashMap vs ConcurrentHashMap

- HashMap：线程不安全；JDK8 数组+链表+红黑树；并发put会丢数据、链表成环CPU100%；
- ConcurrentHashMap：线程安全；
JDK7：分段锁Segment；
JDK8：取消分段锁，CAS + synchronized锁**数组桶头节点**，锁粒度更细；
不锁住整个表，只锁单个哈希桶；支持并发读写，put的时候锁桶，get大部分无锁。

### 四、i++并发、volatile、AtomicInteger（经典连环题）

> 题目：3个线程，每个对i执行i++100次，i初始0，结果范围？
> i++ 不是原子操作，分为三步：读i → +1 → 写回。线程之间互相覆盖写，**最终结果范围：100 ≤ res ≤ 300**。

- 最好情况：完全没有覆盖，300；
- 最坏情况：每次都互相覆盖，每个线程的自增大量丢失，最低是100。

✅ 怎么保证一定等于300：
方案：synchronized / ReentrantLock 加锁；或者用AtomicInteger。

✅ 为什么volatile不行？
volatile只保证**可见性、禁止指令重排，不保证原子性**。
volatile能保证A修改i之后，其他线程读到最新值，但是无法把「读-改-写」打包成原子操作，i++依旧会覆盖。

✅ volatile实现机制：
CPU缓存一致性协议MESI；写volatile变量的时候，加lock前缀指令，让其他CPU核上这个变量的缓存行失效，强制重新从主存读取。

✅ AtomicInteger底层：
基于CAS + volatile；底层value是volatile修饰；compareAndSet调用native的CAS指令，循环自旋尝试更新，直到成功；无锁，适合竞争不激烈场景；竞争激烈自旋空转，CPU升高。

### 五、Spring IOC、AOP、Bean生命周期、循环依赖、三级缓存

1. IOC：控制权反转，把Bean创建、依赖注入交给Spring容器；DI依赖注入是实现方式，解耦。
2. AOP：面向切面，对方法增强（日志、权限、事务），不侵入业务代码；
实现原理：**动态代理**；接口优先JDK动态代理；类用CGLIB字节码生成子类代理。
3. Bean加载流程：
资源定位→解析BeanDefinition→注册到注册表→实例化→填充属性populateBean→初始化（InitializingBean、init-method）→放到单例池；销毁的时候执行destroy方法。
4. Spring循环依赖：A依赖B，B依赖A。
Spring**只能解决setter注入的单例循环依赖，构造注入解决不了**。
三级缓存：

- 一级缓存 singletonObjects：完全初始化好的单例Bean；
- 二级缓存 earlySingletonObjects：实例化完成、还没填充属性的半成品Bean；
- 三级缓存 singletonFactories：Bean工厂ObjectFactory，用来生成Bean的早期代理对象。

✅ 追问灵魂题：为什么不能只用二级缓存，必须三级？

> 
> 这个是很多人栽坑的地方：
> 如果只有一二级缓存：半成品Bean提前暴露，但是如果Bean需要AOP代理，提前拿到的是原始对象，不是代理对象，后续注入就会注入原生对象，失去AOP增强。
> 三级缓存放ObjectFactory，在第一次需要拿到早期引用的时候，才调用工厂方法**生成代理对象**，放到二级缓存；保证注入出去的是代理Bean，而不是原生Bean。

> 
> 补充：单例属性循环依赖就是上面这套方案；如果是原型Bean / 构造器注入循环依赖，Spring直接抛异常，无法解决。

### 六、MySQL引擎、B+树、索引、explain

1. 引擎：InnoDB、MyISAM
MyISAM不推荐原因：
不支持事务、不支持行锁，只有表锁；崩溃无法安全恢复；没有MVCC；现在生产全部InnoDB。
InnoDB支持事务、MVCC、行级锁、崩溃安全恢复。
2. InnoDB索引结构B+树，为什么不用B树：

- B+树非叶子节点只存索引key，不存行数据，一页可以存更多索引，树高度更低，磁盘IO更少；
- 叶子节点双向链表相连，范围查询、分页直接顺序遍历；B树范围查询需要来回跳转，随机IO多；
- 所有查询都落到叶子节点，查询性能稳定。

3. 聚集索引 & 辅助索引
聚集索引：主键索引，叶子节点存完整一行数据；一张表只能一个聚簇索引；
二级（辅助）索引：叶子存主键值；查询的时候拿到主键，回表到聚簇索引查行数据。
4. explain字段：
type是重点，还有：id、select_type、key、key_len、rows、Extra（非常重要！）
Extra里常见：Using filesort文件排序、Using temporary临时表、Using index（覆盖索引，最好）、Using where。

### 七、MongoDB索引 vs MySQL索引

- MySQL InnoDB：B+树，聚簇索引，支持事务，回表；
- MongoDB：默认B树索引；文档结构存储；没有聚簇索引的概念；索引指向文档地址；支持复合索引、地理索引、文本索引；没有回表逻辑，索引直接定位文档；适合非结构化、半结构化JSON数据。

### 十一、JVM GC、分代、GC器、CMS、G1

1. 分代：年轻代Eden+Survivor S0/S1、老年代；对象优先分配Eden，MinorGC存活晋升到老年代。
2. GC收集器：Serial、Parallel、CMS、G1、ZGC、Shenandoah。
CMS：并发标记清除，追求低停顿；
CMS缺点：

- 标记清除算法，**会产生内存碎片**；
- 浮动垃圾floating garbage：并发清理阶段新产生的垃圾，本次GC无法回收，只能等下一轮；
- 并发阶段占用CPU；无法处理浮动垃圾，预留担保空间，容易Concurrent Mode Failure，退化成Serial Old。

G1为什么项目常用：
G1是分Region，不再物理区分年轻老年代；可预测停顿模型；
优点：

1. 分区化，整理是局部复制，碎片少；
2. 支持设置期望最大停顿时间；
3. 兼顾吞吐量和低延迟；
启动参数示例：
`-XX:+UseG1GC -XX:MaxGCPauseMillis=200`

### 十二、三道算法

```
public List<Integer> inorderTraversal(TreeNode root) {
    List<Integer> res = new ArrayList<>();
    Deque<TreeNode> stack = new ArrayDeque<>();
    TreeNode cur = root;
    while(cur != null || !stack.isEmpty()){
        while(cur != null){
            stack.push(cur);
            cur = cur.left;
        }
        cur = stack.pop();
        res.add(cur.val);
        cur = cur.right;
    }
    return res;
}
```

2. LCA 二叉树最近公共祖先

```
public TreeNode lowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q) {
    if(root == null || root == p || root == q) return root;
    TreeNode left = lowestCommonAncestor(root.left,p,q);
    TreeNode right = lowestCommonAncestor(root.right,p,q);
    if(left != null && right != null) return root;
    return left == null ? right : left;
}
```

### 1.实习项目介绍

> 答题思路：业务背景 → 核心技术栈 → 解决什么问题 → 难点优化。

### 2.怎么实现强一致性（数据库主从场景）

MySQL主从默认是异步复制，会存在主从延迟，无法强一致。
强一致性含义：写操作完成之后，后续读必须读到本次写入的最新数据。
实现方案：

1. **写后读走主库**：写完数据，后续读请求直接访问master主库，完全不读从库；最简单，但是主库压力变大。
2. **半同步复制（semi‑sync）**：主库执行写binlog之后，**等待至少一台从库接收binlog成功应答，才返回客户端成功**。> 
> 注意：半同步只能保证binlog传到从库，**不能保证从库已经执行完事务**，只能做到半强一致。
3. 真正的强一致：使用分布式共识协议，例如Raft（MySQL‑X‑Cluster、TiDB），多数节点提交成功才返回，数据多副本强一致。

### 3.怎么实现slave读保证一致性（希望读从库，又不能读到旧数据）

业务写完之后，如果想去读从库，要保证从库已经同步完本次写的数据。
方案：

1. **等待位点方案**：写操作拿到binlog位点，读从库之前，等待从库同步进度>=该位点，再执行读请求；
2. **会话一致性（会话内读自己的写）**：同一个用户会话，刚写过的数据，该会话读强制走主库；其他用户可以读从库；
3. 半同步复制，确保binlog至少送达一台从库，再把请求路由到这台已经收到binlog的从库读取。

> 
> 痛点：会增加请求延迟，需要等待同步完成；极端情况下从库同步卡住，读请求会阻塞。

### 4.保证强一致性前提下，如何优化读slave性能

矛盾点：强一致要等同步，会拖慢读从库；需要平衡一致性和性能。

1. **会话粒度区分**：只有刚发生写操作的会话读主，大量普通只读流量继续走从库，缩小需要等待同步的请求范围；
2. 多从节点，负载均衡，把等待同步的请求分散到不同从机，不要压单台；
3. 监控主从延迟阈值，如果延迟很小，允许直接读从库；延迟超过阈值，读切回主库；
4. 半同步调整参数，不需要等待全部从库，只等待1台从库应答，降低等待时间；
5. 缓存配合：热点数据放Redis缓存，减少数据库读请求。

### 5.讲一下你理解的线性一致性（Linearizability，原子一致性）

> 
> 分布式重要概念，面试高频
> 线性一致性是最强的一致性模型。
> 核心定义：
> 所有读写操作看起来像是**在一个时间点瞬间完成**；操作的执行顺序和真实物理时间不能违背。

1. 如果写操作完成之后，后续所有读，一定可以读到这次写入的结果；
2. 不能出现：A写完，B晚于A发起读，读到比A写入更旧的数据。

对比区分：

- 线性一致性 ≠ 因果一致性；因果只保证有因果关系操作顺序，无关操作可以乱序。
- MySQL异步主从做不到线性一致性，会有复制延迟。
- Raft协议、TiDB可以提供线性一致性。

一句话口述：线性一致性是最强的一致性，就好像整个系统只有一台单机，所有操作按现实时间顺序生效。

### 6.讲一下你理解的消息队列

消息队列核心角色：生产者Producer、Broker服务端、消费者Consumer。
四大核心作用：**异步、解耦、削峰填谷、流量平滑**。
需要考虑问题：消息丢失、重复消费、消息积压、事务消息保证最终一致性。

- 消息丢失：生产者确认、Broker刷盘、消费者ACK机制；

### 7.Nacos实现原理

Nacos 核心两大能力：**配置中心（Config） + 服务发现（Naming）**，基于AP模型，支持CP/AP切换。

#### 一、核心概念

- Namespace：环境隔离（dev/test/prod）
- Group：分组隔离，同一个服务名下不同业务分组
- DataId：配置唯一标识
- 集群模式：Nacos集群，节点对等；默认**AP（Distro协议）**，切换为CP使用Raft协议

#### 二、服务注册与发现（Naming，重点）

##### 1. 服务注册

服务启动，向Nacos Server发送注册请求，带上服务名、IP、端口、权重、健康状态等元信息。
> 客户端默认**心跳上报**（5s一次），维持服务实例存活；
> 服务端超过15s没收到心跳标记不健康，30s摘除实例。

##### 2. 服务订阅 & 推送

消费者订阅某个服务：
1. 客户端拉取全量实例列表；
2. 建立长连接，Nacos Server 实例变更（上下线、权重修改）时，主动推送增量变更给订阅客户端；
> 推+拉结合：推送做实时变更，定时全量拉做兜底防丢消息。

##### 3. 一致性协议（高频考点）

- **AP模式（默认，推荐服务发现）：Distro协议**
  去中心化，每个节点独立接收写请求；收到注册的节点，异步把数据同步给集群其他节点；
  不保证强一致，保证高可用，适合服务发现（服务发现容忍短暂不一致）。
  Distro：写请求落到任意节点，节点本地保存，异步同步，节点本地校验数据完整性。
- **CP模式：Raft协议**
  选主，写请求必须交给leader，日志同步过半节点才提交，强一致；
  代价：可用性下降、选主耗时；适合需要强一致的场景，一般配置中心用。

> 一句话区分：服务发现默认Distro(AP)，配置默认Raft(CP)。

#### 三、配置中心（Config）

1. 发布配置：客户端提交DataId+内容到Nacos；Raft保证集群内配置强一致；
2. 客户端监听配置：长连接订阅；配置变更时，服务端推送变更事件；
3. 本地缓存：客户端把配置缓存到本地文件，Nacos挂了还可以读取本地缓存，不影响启动。
4. 版本、灰度、回滚：配置带版本号，支持灰度发布。

#### 四、负载均衡

Nacos本身内置权重负载均衡，服务实例带上weight权重；
客户端拿到实例列表后，**客户端侧负载均衡**（Nacos只返回实例，不代理流量！这点和Nginx、Gateway不一样）
默认负载策略：**权重随机**。

#### 五、和Eureka/Consul简单对比（面试官常追问）

- Eureka：AP，心跳，只支持服务发现；
- Consul：CP，Raft，gossip；
- Nacos：同时支持配置+注册，可切换AP/CP。

#### 六、高频坑点追问

1. Nacos的健康检查分两种：
   - **客户端心跳检测（默认，临时实例ephemeral=true）**：服务主动发心跳，适合微服务，实例临时，下线自动清除；Distro AP。
   - **服务端主动探测（持久实例ephemeral=false）**：Nacos服务端主动TCP/HTTP探活，适合外部服务；持久实例走Raft CP。
> ✅ 临时实例：常用，微服务；持久实例：保存到磁盘，CP。

2. 临时实例为什么用Distro？
临时实例生命周期短、不需要持久化，优先高可用，接受短暂不一致。

#### ✅ 极简口述版（面试直接背）

Nacos分为服务发现和配置中心两块。
服务发现默认AP，使用Distro协议，去中心化，服务注册后客户端定时心跳保活；消费者订阅服务，长连接接收实例变更推送，客户端做权重随机负载均衡；支持临时实例、持久实例。
配置中心使用Raft协议保证CP强一致性，配置变更实时推送，客户端本地缓存兜底。
可以切换AP/CP：服务发现选AP高可用，配置场景选CP保证数据一致。





### 8.算法题 LRU（最近最少使用缓存）

> 
> LRU：淘汰最久没有访问的数据。
> **数据结构组合：双向链表 + HashMap**

- HashMap：key映射链表节点，O(1)查找；
- 双向链表：维护访问顺序；头部放最近使用，尾部放很久未使用；
逻辑：

1. get(key)：存在，则把该节点移动到链表头部；不存在返回‑1；
2. put(key,value)：
   - key已存在：更新value，移到链表头部；
   - key不存在：新建节点放到头部；如果超过容量，删除链表尾部节点，同时删除map中对应key。

手写Java简化版：

```
import java.util.HashMap;

public class LRUCache {
    static class Node{
        int key,val;
        Node prev,next;
        Node(int k,int v){
            key=k;val=v;
        }
    }
    private HashMap<Integer,Node> map;
    private Node head,tail;
    private int capacity;

    public LRUCache(int capacity) {
        this.capacity=capacity;
        map=new HashMap<>();
        head=new Node(-1,-1);
        tail=new Node(-1,-1);
        head.next=tail;
        tail.prev=head;
    }
    private void removeNode(Node node){
        node.prev.next=node.next;
        node.next.prev=node.prev;
    }
    private void addFirst(Node node){
        node.next=head.next;
        node.prev=head;
        head.next.prev=node;
        head.next=node;
    }
    private void moveToHead(Node node){
        removeNode(node);
        addFirst(node);
    }
    private Node removeTail(){
        Node del=tail.prev;
        removeNode(del);
        return del;
    }

    public int get(int key) {
        if(!map.containsKey(key)) return -1;
        Node node=map.get(key);
        moveToHead(node);
        return node.val;
    }

    public void put(int key, int value) {
        if(map.containsKey(key)){
            Node node=map.get(key);
            node.val=value;
            moveToHead(node);
        }else{
            Node newNode=new Node(key,value);
            map.put(key,newNode);
            addFirst(newNode);
            if(map.size()>capacity){
                Node del=removeTail();
                map.remove(del.key);
            }
        }
    }
}
```







## 小红书4

### 1. ConcurrentHashMap底层原理

**JDK8**：底层数组+链表+红黑树；抛弃JDK7 Segment分段锁；
采用 **CAS + synchronized锁桶头节点**，锁粒度只锁住当前哈希桶；
put：空桶使用CAS插入；桶已有节点，对链表/红黑树根节点加synchronized；
get大部分无锁，依靠volatile保证数组、节点可见性；
key、value都**不允许null**。

> 
> JDK7：Segment分段锁，每段是小HashMap，段上加锁，开销大，JDK8废弃。

### 2. 手写LRU（两种写法：LinkedHashMap、手动双向链表）

#### 利用LinkedHashMap极简版（面试可以写这个）

`accessOrder=true`开启访问排序，最近访问放头部，重写removeEldestEntry做容量淘汰

```
class LRUCache extends LinkedHashMap<Integer,Integer>{
    private int capacity;
    public LRUCache(int capacity) {
        super(capacity,0.75f,true); // accessOrder=true
        this.capacity = capacity;
    }
    public int get(int key){
        return super.getOrDefault(key,-1);
    }
    public void put(int key,int value){
        super.put(key,value);
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldest) {
        return size()>capacity;
    }
}
```

> 
> 注意：面试官经常会要求**不允许使用LinkedHashMap**，就要手写双向链表+HashMap版本，上一份文档有完整代码。

### 3. HashMap底层数据结构

JDK8：**数组 + 链表 + 红黑树**

1. key经过扰动函数`hashCode() ^ (h>>>16)`得到hash；
2. `hash & (n‑1)`定位数组下标；
3. 桶为空直接放入；冲突形成链表；
4. 链表长度≥8并且数组容量≥64，链表转为红黑树；
5. 扩容容量翻倍，`hash & oldCap`判断节点留在原地或者迁移i+oldCap；
6. key允许一个null。

### 4. 为什么用红黑树不用AVL树

AVL树是**严格平衡二叉搜索树**，左右子树高度差不超过1；
红黑树是**弱平衡**，不追求绝对平衡。

- AVL：平衡条件严格，插入删除要频繁旋转，**写操作开销大**；查询很快。
- 红黑树：旋转次数少，插入删除性能更高；查询性能和AVL差距不大。
HashMap哈希冲突场景，**插入删除更频繁，优先红黑树**。

### 5. 为什么链表长度到8才树化

泊松分布统计：哈希足够均匀的情况下，链表长度达到8的概率**千万分之一**；
正常hash几乎不会到8；只有hash大量冲突才触发树化，避免无谓的树化开销。

### 6. 为什么退化阈值是6，不是8

为了**缓冲，防止抖动**。
如果树化、退化阈值都为8，节点数量在8来回波动，会频繁发生树化、解树，CPU开销巨大；
6‑8之间留开缓冲区间。

### 7. 线程池7个参数，该怎么配置最好

7参数：`corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler`

- CPU密集：核心线程数 ≈ CPU核心数；
- IO密集（接口、数据库、RPC）：核心线程数 = 2 * CPU核心数；
⚠️工程重点：

1. **队列一定要设置有界容量**，禁止无界LinkedBlockingQueue，否则任务堆积OOM；
2. maximumPoolSize不要设置过大，防止大量线程上下文切换；
3. 拒绝策略根据业务，可自定义降级；
4. keepAliveTime给非核心线程回收空闲线程，释放资源。

> 
> 阿里开发规范：禁止使用Executors快捷方法创建线程池。

### 8. 说一下volatile

volatile修饰变量；三个特性：

1. **保证可见性**：一个线程修改，其他线程立刻读到最新值；
2. **禁止指令重排序**；
3. **不保证原子性**，i++这种复合操作不能靠volatile保证线程安全。

### 9. volatile可见性、禁止重排序底层

- **可见性**：CPU MESI缓存一致性协议；写volatile变量时，CPU发出lock前缀指令，使其他CPU缓存行失效，强制从主内存读取。
- **禁止指令重排序**：内存屏障（Memory Barrier）。
JMM定义4种内存屏障：LoadLoad、LoadStore、StoreStore、StoreLoad；
volatile读写前后插入内存屏障，限制指令不能跨越屏障重排。

### 10. CAS是什么

Compare And Swap，比较并交换，乐观锁；
三个操作数：内存值V、预期旧值A、新值B。
逻辑：如果内存V等于预期A，则把V更新为B；否则更新失败。
底层CPU硬件指令cmpxchg，原子操作。
问题：ABA问题、自旋消耗CPU、只能保证单个变量原子性。
解决ABA：`AtomicStampedReference`增加版本号。

### 11. PriorityQueue底层、初始容量、扩容

底层：**最小堆（数组实现完全二叉堆）**；
初始默认容量：**11**；
扩容规则：

- 当前容量小于64：新容量 = 旧容量 * 2 + 2；
- 当前容量≥64：新容量 = 旧容量 * 1.5；
最大容量有上限，避免溢出。

### 12. HashMap容量为什么必须是2的次幂

计算下标公式 `hash & (n‑1)`；
n为2的幂，则`n‑1`二进制低位全部为1；按位与等价取模 `hash % n`，运算效率远高于取模；
如果不是2次幂，`n‑1`会出现0位，会导致hash某些下标永远访问不到，哈希冲突急剧恶化。

### 13. 跳表，使用场景

跳表：多层有序链表，通过上层索引加速查找；查询、插入、删除O(logn)。
JDK：`ConcurrentSkipListMap / ConcurrentSkipListSet`。
场景：**并发环境需要有序map**；Redis zset底层也是跳表；
对比红黑树：跳表实现简单，范围遍历性能优秀。

### 14. CopyOnWriteArrayList，迭代器是否支持fail‑fast

写时复制集合：写操作加锁，复制一份新数组修改，修改完替换旧数组；读不加锁。
迭代器基于**旧数组快照**；遍历期间集合修改，迭代器不会抛出ConcurrentModificationException。
👉 **不支持fail‑fast**。
适合：读多写少场景；不适合大数据高频写，每次写复制数组内存开销大。

### 15. InnoDB底层索引数据结构

B+树；聚簇索引，主键叶子节点存储完整行记录；二级索引叶子存储主键id。

### 16. B+树对比B树

1. B+树非叶子节点只存key，不存储真实数据，一页可以存放更多索引，树更低，磁盘IO少；
2. B+树叶子节点双向链表串联，**范围查询、排序非常友好**；B树范围查询需要来回跳转，大量随机IO；
3. B+树所有查询最终落到叶子，查询性能稳定。

### 17. B+树对比红黑树

红黑树内存数据结构；B+树专门为磁盘数据库设计：

1. 磁盘按页读取，B+树阶数大，树高度很小，减少磁盘IO；红黑树树高更高，IO次数多；
2. B+树叶子链表，范围查询优势巨大；红黑树范围遍历效率差。

### 18. 算法题

#### ①无序数组寻找第K大的数

快速选择（快排思想），partition分区，不需要完整排序，平均O(n)；最坏O(n²)。
也可以用堆：小顶堆保存K个元素。

#### ②二叉树层次遍历（BFS）

```
public List<List<Integer>> levelOrder(TreeNode root) {
    List<List<Integer>> res = new ArrayList<>();
    if(root == null) return res;
    Queue<TreeNode> q = new LinkedList<>();
    q.offer(root);
    while(!q.isEmpty()){
        int size = q.size();
        List<Integer> level = new ArrayList<>();
        for(int i=0;i<size;i++){
            TreeNode cur = q.poll();
            level.add(cur.val);
            if(cur.left!=null) q.offer(cur.left);
            if(cur.right!=null) q.offer(cur.right);
        }
        res.add(level);
    }
    return res;
}
```

流程：

2. 第i个元素(i>100)，以`100 / i`概率替换蓄水池中随机一个元素；

#### 1、怎么理解HTTP的无状态

HTTP协议本身**不保存客户端和服务端的会话状态**，每一次HTTP请求都是独立的；服务端不会记住上一次请求是谁、做过什么操作。

解决方案弥补无状态：

- Cookie：浏览器存储，每次请求自动携带；
- Session：服务端保存会话信息，cookie存sessionId；
- Token/JWT：请求头携带令牌，实现登录会话保持。

一句话口述：HTTP无状态指协议本身不会记忆会话，靠Cookie/Session/Token维持业务会话。

#### 2、除了进程，线程还有哪些？

> 
> 操作系统执行单元相关：

1. **协程（用户态线程）**：运行在用户空间，轻量级；切换不需要陷入内核，开销很小；一个线程内部可以跑多个协程，Java虚拟线程（Virtual Thread，Java21）就是协程思想。
2. 内核线程：操作系统内核管理，我们Java线程本质映射操作系统内核线程。

区分：

- 进程：资源分配单位；
- 线程（内核线程）：CPU调度单位，切换要内核；
- 协程：用户态，在一个线程内多路复用，切换开销极低。

#### 3、大文件的上传方式（项目）

1. **分片上传**：前端把大文件切分成多个小chunk块，逐个上传；后端接收各个分片；全部传完之后合并文件；支持断点续传，失败只重传失败分片，不用全部重传。
2. 流式上传：不把整个文件全部加载进内存，边读边写磁盘，防止OOM。
3. 校验：md5，前端传文件整体md5 + 分片md5，后端校验完整性。
4. 限制单分片大小，控制并发分片数量。

> 
> 坑：不能直接一次性接收完整大文件，容易占满内存导致OOM。

#### 4、A线程调用B线程工作，A只想等待指定时间，不要无限等待怎么做

场景：A等待B返回结果，带超时时间。
方案：

1. **`Future.get(timeout, TimeUnit)`**，Callable+FutureTask；超时抛出`TimeoutException`；
2. 线程池submit返回Future对象，调用带超时参数的get；
3. CountDownLatch.await(timeout,unit)；> 
> 注意：超时不等于终止B线程；get超时仅仅A不再等待；如果需要中断B，要拿到线程句柄，调用`interrupt()`。

示例核心代码片段

```
ExecutorService pool = Executors.newSingleThreadExecutor();
Future<String> future = pool.submit(() -> {
    //B线程任务
    return "result";
});
try {
    //最多等待2秒
    String res = future.get(2, TimeUnit.SECONDS);
} catch (TimeoutException e) {
    //超时处理
    future.cancel(true); //尝试中断任务
}
```

### 二面（45min）

#### 1、已经有HTTP，为什么还需要RPC？

HTTP是通用应用层协议，基于文本，适合浏览器调用；RPC用于**服务与服务之间内部调用**。
RPC优势：

1. 性能：可以使用二进制序列化（Protobuf/Hessian），比http json文本体积更小，序列化反序列化更快；
2. 内置服务注册发现、负载均衡、超时、重试、熔断，开箱即用；
3. 更贴合开发体验：像调用本地方法一样调用远程服务，屏蔽网络细节；
4. 支持长连接复用，减少TCP握手开销。

> 
> HTTP也可以做服务间调用（OpenFeign），但HTTP协议头冗余大，序列化一般JSON，性能弱于二进制RPC。

#### 2、RPC有注册中心，HTTP有没有类似组件？

HTTP本身协议没有注册中心，但是可以**额外引入组件实现相同能力**：

1. Nacos / Eureka：HTTP服务也可以注册实例；客户端拿到实例列表做负载均衡；
2. Nginx：网关，静态配置服务地址，做负载均衡；缺点服务上下线要手动改配置，没有自动感知；
3. Spring Cloud的OpenFeign + Nacos：HTTP调用，借用Nacos做注册中心，和RPC注册中心作用完全一样。

> 
> 本质：注册中心不属于RPC协议，是微服务架构组件，HTTP服务也可以用。

#### 3、算法：list给定target，输出所有和为target的子序列，两种数据规模两种解法

> 
> 子序列：元素顺序不变，可以不连续；子集，允许选或者不选元素。

1. **数据量小（n<=20）：回溯DFS暴力枚举**，每个元素两种选择：选 / 不选；收集满足总和等于target的子序列。
2. **数据量大，数组全部是正数：滑动窗口**> 
> 注意：只有数组全部正数才可以滑动窗口；存在负数不能用滑动窗口，只能回溯。

回溯代码模板

```
public class Solution {
    List<List<Integer>> ans = new ArrayList<>();
    public void dfs(int idx, List<Integer> path, int sum, int target, int[] nums){
        if(sum == target){
            ans.add(new ArrayList<>(path));
            return;
        }
        if(idx >= nums.length) return;
        //选当前
        path.add(nums[idx]);
        dfs(idx+1, path, sum+nums[idx], target, nums);
        path.remove(path.size()-1);
        //不选当前
        dfs(idx+1, path, sum, target, nums);
    }
}
```

> 
> 补充：如果是**子数组（连续）**才完全适合滑动窗口；子序列（非连续）正数也只能回溯，滑动窗口无法解决子序列。面试官容易在这里挖坑，注意区分子序列 vs 子数组。

### 1. HashMap的数据结构组成

JDK8：**数组 + 单向链表 + 红黑树**
- 数组：哈希桶，定位下标
- 链表：哈希冲突元素挂链表
- 链表长度≥8、数组容量≥64，链表转为红黑树；
- 节点key做hash扰动 `h ^ (h >>>16)`，`hash & (n-1)`定位桶下标；
JDK7：数组+链表，头插法，并发容易链表环。

### 2. HashMap线程安全吗？

**不安全**
并发put：会丢数据、JDK7容易循环链表CPU100%，JDK8虽然没有环，但依然存在覆盖丢失的问题；get和put并发也会异常。

### 3. ConcurrentHashMap线程安全吗？

**安全**
JDK8：数组+链表+红黑树，**CAS + synchronized锁住桶头节点**，锁粒度是单个哈希桶；
JDK7：Segment分段锁，每个segment是独立小HashMap。
不允许key/value为null。

### 4. CAS操作

Compare And Swap，比较并交换，乐观锁。
三个参数：内存值V、预期值A、新值B
逻辑：如果内存当前值V == A，就更新V=B；否则失败重试。
底层CPU cmpxchg硬件指令，原子。
缺点：ABA问题、自旋空转消耗CPU、只能单个变量原子更新。
ABA解决：AtomicStampedReference，增加版本戳。

### 5. 如何解决hash冲突

1. 链地址法（HashMap用的：链表/红黑树挂冲突节点）
2. 开放寻址法（线性探测、二次探测，ThreadLocalMap）
3. 再哈希法：冲突换另一个hash函数重新算位置
4. 建立公共溢出区

### 6. JMM的执行顺序原理

JMM（Java内存模型），屏蔽不同硬件CPU缓存差异，定义线程、主内存、工作内存之间的交互规则。
核心：

1. 所有变量存在主内存；线程读取变量，先拷贝到自己的**工作内存（缓存）**；读写在工作内存完成，再同步回主存；
2. 8个内存操作指令：lock、unlock、read、load、use、assign、store、write；
3. 指令重排序：编译器、CPU会为性能打乱代码执行顺序，只要单线程语义不变；
4. JMM提供happens-before规则，约束重排，保证多线程可见有序。
happens-before不是代码顺序，是可见性保证规则。

### 7. volatile怎么保证有序？修改后其他线程可见吗

✅ 可见性：**可以看到最新值**。写volatile时MESI缓存一致性协议，发lock指令，其他CPU上该缓存行失效，强制重新读主存。
✅ 有序：**内存屏障**。volatile读、写前后插入4种内存屏障（LoadLoad、LoadStore、StoreStore、StoreLoad），禁止指令跨屏障重排序。
❌ 不保证原子性，i++不能靠volatile线程安全。

### 8. synchronized 和 ReentrantLock区别、原理、场景

- synchronized：JVM层面内置锁，自动释放；锁升级（偏向→轻量→重量级）；不可中断、不能超时；只有一个等待队列；
- ReentrantLock：AQS队列同步器实现，API手动lock/unlock；支持公平/非公平锁、tryLock超时、lockInterruptibly可中断、多个Condition条件队列；
场景：
简单同步、方法锁 → synchronized；
需要公平锁、超时等待、多条件唤醒 → ReentrantLock。

### 9. 输入网址到页面展示完整流程

1. DNS解析：域名 → IP；先查本地hosts、本地DNS缓存、递归查询根域名服务器，拿到目标IP
2. TCP三次握手，建立连接
3. 发送HTTP/HTTPS请求（TLS握手加密）
4. 服务器Nginx反向代理，转发到后端服务
5. 后端业务处理，返回响应报文
6. 浏览器接收响应，解析HTML，加载CSS、JS、图片等静态资源
7. 浏览器渲染DOM树、CSSOM树、合成渲染树，布局、绘制、分层合成，页面展示

### 10. TLS如何加密（HTTPS）

TLS握手（RSA模式举例）：
1. 客户端发版本、加密套件列表、随机数client random
2. 服务端选定套件、返回server random、服务器证书（含公钥）
3. 客户端校验证书CA签名合法性
4. 客户端生成**预主密钥premaster secret**，用服务端公钥加密发给服务器
5. 服务端用自己私钥解密拿到premaster secret
6. 双方用三个随机数（client random+server random+premaster）算出相同会话密钥
7. 后续通信用这个对称密钥AES做对称加密传输数据。
>现在主流ECDHE，支持前向保密，每次会话密钥独立，私钥泄露不会解密历史报文。

### 11. TCP三次握手传递哪些包

1. SYN包：客户端→服务端，同步序列号，SYN=1
2. SYN+ACK包：服务端→客户端，同步序列号+确认收到客户端SYN
3. ACK包：客户端→服务端，确认服务端SYN

### 12. 四次挥手能不能改成3次？为什么

**可以合并，特殊场景能变成3次，但标准是4次**
原因：TCP全双工，两个方向独立关闭。
正常流程：
1. 客户端FIN（我不再发数据）
2. 服务端ACK
3. 服务端FIN（服务端数据发完，我也不发了）
4. 客户端ACK

如果**收到FIN的服务端，没有剩余数据要发送，ACK和FIN可以合并成一个报文**，就变成3个包；
但如果服务端还有数据要回传给客户端，ACK必须先发，等数据发完再发FIN，必须4次，所以标准流程设计为四次。

### 13. TCP/IP五层模型、每层协议、MTU

五层：
1. 物理层：网线、比特流
2. 数据链路层：以太网协议、ARP；**MTU 1500字节（以太网标准）**
3. 网络层：IP、ICMP
4. 传输层：TCP、UDP
5. 应用层：HTTP、HTTPS、DNS、FTP

MTU最大1500字节，限制来自**以太网帧的数据载荷上限**；TCP MSS = MTU - IP头(20) - TCP头(20) = 1460。超过MTU会分片。

### 14. TCP滑动窗口、流量控制

流量控制：**接收方告诉发送方自己还能收多少字节，防止发送方发太快把接收缓冲区打爆**。
接收方返回ACK的时候，携带window窗口大小（接收缓冲区剩余容量）；发送方发送的数据不能超过这个窗口。
滑动窗口：窗口沿着序列号向前滑动；窗口=允许发送的字节范围。
窗口为0时，发送方停止发送；开启零窗口探测，定期询问窗口是否恢复。

>注意：流量控制是端到端（接收方→发送方）；拥塞控制是全局网络。

### 15. 双亲委派机制原理

类加载器层次：Bootstrap（启动类加载器）→Extension扩展类加载器→Application应用类加载器。
加载类流程：
1. 收到加载请求，先向上交给父加载器；
2. 父加载器能加载，直接返回；
3. 父加载器加载失败，自己尝试加载。
好处：
1. 沙箱安全：防止自定义java.lang.String等核心类，覆盖JDK原生类；
2. 类全局唯一，保证同一个类只加载一份。
破坏场景：SPI、Tomcat热加载。

### 16. 线程池7参数，怎么设置核心、最大线程数

7参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler
设置原则：
- CPU密集（大量计算）：核心线程 ≈ CPU核心数；
- IO密集（DB、RPC、网络等待）：核心线程 = 2*CPU核心；
队列**必须有界**，拒绝策略兜底。

### 17. 4核机器，CPU密集任务，核心线程设4，为什么不是5？

CPU密集任务，线程主要在运算，几乎没有等待。
4核CPU，同一时刻最多并行执行4个线程。
设置5个核心线程：多出的线程会频繁上下文切换，抢占CPU，切换开销大，整体吞吐量下降、CPU变高。

### 18. Redis数据类型、场景、宕机方案

基础5种：
1. String：缓存、计数器、分布式锁
2. List：消息队列、栈
3. Set：去重、交集并集好友关系
4. Hash：对象存储，用户信息

### 20. 向量数据库、余弦相似度

向量数据库：专门存储**Embedding向量（高维浮点数数组）**的数据库，面向大模型RAG检索；支持向量索引（HNSW等），快速做相似检索。
余弦相似度：计算两个向量夹角余弦值。
公式：$cos(\theta) = \frac{A·B}{||A||*||B||}$

### 2、BIO / NIO / AIO区别（你原来的回答基础上优化完善版）

IO两个阶段：**内核数据准备、内核缓冲区→用户缓冲区的数据拷贝**
- **BIO（同步阻塞IO）**：同步+阻塞。两个阶段都阻塞。发起read，一直阻塞等到数据准备好、拷贝完成才返回。
- **NIO（同步非阻塞IO，Java NIO）**：同步非阻塞。应用线程轮询内核，不断询问数据有没有就绪；数据就绪后，再发起read，**拷贝阶段依然阻塞**。只是数据准备阶段不卡线程。
  配套IO多路复用（select/poll/epoll），就是Reactor的基础。
- **AIO（异步非阻塞IO）**：异步。全程不阻塞线程，向内核注册回调；**数据准备+内核拷贝全部完成之后，内核主动通知应用，执行回调逻辑**。

一句话区分：
BIO：等；NIO：反复问好了没；AIO：好了内核喊我。

### 3、Nginx原理 & Nginx IO模型

Nginx核心是**多Reactor多进程模型**（Master + Worker进程）
- Master主进程：管理Worker、接收信号、加载配置；**不处理业务连接**
- Worker子进程：每个Worker内部是一套独立的Epoll（IO多路复用），也就是**单Reactor单进程**
Nginx用epoll多路复用，非阻塞IO。

>你之前混乱点：Reactor是**事件驱动设计模式**，NIO/AIO是IO系统调用API；Reactor是架构，NIO是底层IO能力。

### 4、Reactor 和 NIO 的关系（重点，你当时没答上来）

- NIO（epoll/select/poll）是操作系统提供的**IO多路复用API**，只是一个底层能力：可以一次性监听一堆fd，哪些就绪就返回哪些。
- Reactor是**事件驱动的设计模式**：把就绪的IO事件（accept、read、write）分发到对应的处理函数。
👉 **Reactor 是基于IO多路复用（NIO）实现的架构**，NIO是地基，Reactor是在地基上搭的事件分发框架。

### 5、Netty为什么拆Boss线程组、Worker线程组，accept和read/write分开？

Boss线程：只负责**Accept建立TCP连接**
Worker线程：负责连接上后续的read、write、编解码、业务事件
好处：
1. 连接建立（accept）和IO读写事件解耦；如果读写耗时、阻塞，不会影响新连接接入；
2. 新连接拿到之后，注册到Worker的Selector，连接负载分散到多个Worker；
3. 职责隔离，更容易做限流、监控。

### 6、A进程accept拿到socket，怎么交给B进程读写

Linux下：Unix域套接字，调用`sendmsg`，通过**辅助消息（ancillary data）传递文件描述符fd**。
不是简单传数字，fd是进程内编号；同一个数字在不同进程不代表同一个socket。必须内核帮忙传递fd，内核会给B进程新建fd指向同一个内核socket对象。
>你之前说的管道、共享内存只是IPC通信，**不能直接传递fd**，这是你当时的漏洞。

### 7、能不能子进程去accept创建连接？什么是惊群效应

可以让多个Worker进程都监听同一个listen fd，都注册epoll等待accept。
**惊群效应**：旧版本Linux，当一个新连接到来，内核会唤醒**所有阻塞在accept上的Worker进程**，但是最终只有一个进程能成功拿到连接，剩下全部唤醒之后发现抢不到，返回EAGAIN，白白唤醒、浪费CPU。
Nginx早期会碰到，现在内核已经有 `EPOLLEXCLUSIVE` 排他唤醒，解决惊群；也可以用锁，同一时间只有一个worker等待accept。

>一句话：多个进程等同一个listen fd，来了连接全部唤醒，就是惊群。

### 8、Java堆内存分配、分代管理（你的回答优化）

Java堆分为新生代（Eden + 2块Survivor S0/S1）、老年代。
- 新对象优先分配Eden；Eden满触发Minor GC；存活对象复制到Survivor，年龄+1；
- 对象年龄达到阈值（默认15）晋升到老年代；大对象直接进老年代；
- GC：新生代复制算法；老年代标记清除/标记整理（G1/ZGC是分区标记）。

### 9、操作系统内存管理（jemalloc）

jemalloc是用户态内存分配器（libc malloc的实现之一），底层向OS申请大块内存，再切小块分给应用。
它把内存分成不同size class（64B、128B…4KB、8KB、16KB）；申请内存时匹配最小满足的size类；大块用mmap；小块预分配、缓存，减少系统调用。

### 10、向操作系统申请内存：brk、mmap

>JVM：堆用brk；DirectByteBuffer堆外内存用mmap。

### 11、JVM分代内存管理 vs OS内存管理区别

1. 操作系统管理**整个机器所有进程的虚拟内存**，页式管理、缺页中断、换页，面向所有程序，通用性极强；
2. JVM内存管理器，是**进程内用户态内存管理器**，专门服务Java，基于GC自动回收；它把从OS拿到的内存，再按分代划分，针对Java对象生命周期（大部分朝生夕灭）做优化；
3. OS关注页、缺页、物理内存置换；JVM关注对象存活、GC回收、分代晋升。

### 12、MySQL事务隔离级别 + MVCC

四个隔离级别：读未提交、读已提交RC、可重复读RR、串行化。

- RC：每次select都生成新ReadView
- RR：事务第一次select的时候生成ReadView，全程复用，实现可重复读

### 算法：旋转有序数组，查找target（旋转排序数组搜索，LeetCode 33）

>比如 [4,5,6,7,0,1,2]，二分，O(log n)
思路：二分，判断左半段有序还是右半段有序，缩小搜索范围
```java
public int search(int[] nums, int target) {
    int l = 0, r = nums.length - 1;
    while(l <= r){
        int mid = (l + r) / 2;
        if(nums[mid] == target) return mid;
        // 左边有序
        if(nums[l] <= nums[mid]){
            if(target >= nums[l] && target < nums[mid]){
                r = mid - 1;
            }else{
                l = mid + 1;
            }
        }else{
            // 右边有序
            if(target > nums[mid] && target <= nums[r]){
                l = mid + 1;
            }else{
                r = mid - 1;
            }
        }
    }
    return -1;
}
```

#### 1. B+树索引 和 B树的区别

1. **关键字存储位置**：B树非叶子节点和叶子节点都存数据；B+树只有叶子节点存完整数据，非叶子节点只存索引键，不存真实行数据。

3. SQL层面优化：避免select *，避免索引失效（函数、隐式转换、like前缀%），减少join、子查询，拆分大SQL。
4. 索引优化：建立联合索引，遵循最左前缀；删除冗余索引；覆盖索引减少回表。
5. 架构层面：分库分表、读写分离。
6. 业务层面：缓存Redis拦截热点查询。

#### 2. 服务器负载均衡，算法有哪些

四层（LVS）、七层（Nginx）负载均衡
**负载均衡算法**
轮询、加权轮询、IP哈希、一致性哈希、最小连接数、最小响应时间。

#### 3. 一致性哈希原理

1. 把哈希值映射到0~2^32的环形哈希环；
2. 服务节点计算hash放到环上；请求key算hash，沿着环顺时针找到第一个节点；
3. 新增/下线节点，只影响一小部分key，不会全部重新映射（对比普通hash取模，扩容雪崩）；
4. 引入虚拟节点，解决节点少、数据倾斜问题。

#### 4. 怎么避免DDOS打到少数机器（结合一致性哈希的坑）

一致性哈希如果节点少，容易倾斜，流量集中到少数节点：
1. 增加**虚拟节点**，打散流量；
2. 前置清洗：在Nginx、LVS、WAF层做流量清洗，拦截恶意请求；
3. 多机房、多集群异地部署；
4. 限流、熔断、黑名单封禁恶意IP；
5. 配合加权策略，均衡负载。

#### 5. TCP三次握手、四次挥手，最后ACK的作用、TIME-WAIT、为什么2MSL

四次挥手：
1. 客户端FIN → 服务端ACK
2. 服务端FIN → 客户端ACK（这个就是最后一个ACK）
- 最后ACK作用：告诉服务端，我收到你的FIN关闭报文了；服务端收到ACK之后才彻底释放连接。
- TIME-WAIT是客户端收到FIN、发出ACK之后进入的状态，持续2MSL。
两个原因：
1. 防止最后这个ACK丢包：如果ACK丢了，服务端超时会重发FIN，TIME-WAIT状态下客户端还能重新补发ACK；
2. 等待本连接残留的报文在网络中消失，避免新连接收到旧的滞留数据包。
MSL是报文最大生存时间，2MSL就是两倍。

### 1. Java线程池（7参数、整体设计）

7个核心参数：
`corePoolSize`核心线程数、`maximumPoolSize`最大线程数、`keepAliveTime`空闲保活时间、`unit`时间单位、`workQueue`阻塞任务队列、`threadFactory`线程工厂、`handler`拒绝策略。

**任务执行流程**

1. 运行线程数＜核心线程数，新建核心线程执行任务；
2. 核心线程已满，任务放入阻塞队列排队；
3. 队列满，且运行线程＜最大线程数，创建非核心线程；
4. 线程数达到最大值，队列已满，执行拒绝策略。

**设计思想**

1. 线程复用，避免频繁创建销毁线程，减少CPU上下文切换开销；
2. 任务和执行解耦，任务放到队列；
3. 可控并发数，队列+拒绝策略保护系统，防止任务无限堆积OOM；> 
> 阿里规范：禁止直接使用`Executors`快捷方法，必须自定义`ThreadPoolExecutor`，队列要有界。

### 2. Redis持久化 RDB、AOF

#### RDB

定时把全量内存数据dump成二进制快照文件。

- 优点：文件紧凑，恢复速度快；适合全量备份。
- 缺点：两次快照之间宕机会丢失这段时间的数据；fork子进程会消耗CPU内存。

#### AOF

记录每一条写命令的日志文件，追加写入。

- 优点：数据安全性更高，可以配置刷盘策略；
  - `always`：每条写都刷磁盘，最安全性能差；
  - `everysec`：每秒刷盘，默认，最多丢1秒数据；
  - `no`：交给操作系统刷盘，不可控。
- 缺点：文件体积大，恢复慢；需要bgrewriteaof重写压缩日志。

> 
> 生产推荐：**RDB+AOF混合持久化**。

### 3. 布隆过滤器、缓存空对象、互斥锁 三者对比

> 
> 背景：都是用来**解决缓存穿透**的方案（查询数据库不存在的数据，缓存不命中，请求直接打数据库）

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 布隆过滤器 | 把所有合法key存进布隆过滤器；查询key不存在直接拦截，不去查缓存、DB；**只能判不存在，不能判一定存在** | 内存占用极小；拦截大量非法请求； | 存在误判；不能删除元素；需要预热数据； |
| 缓存空对象 | DB查询不到数据，往Redis存入这个key的空值，设置过期时间；下次请求直接返回空，不再访问DB | 实现简单；支持删除key； | 会占用Redis内存；大量非法key会占用大量内存； |
| 互斥锁 | 缓存失效时，加分布式锁，只有一个请求去查DB回写缓存，其他请求等待 | 防止大量并发穿透到DB； | 会带来等待，接口响应变慢；有死锁风险； |

口述总结：

- 布隆：适合海量非法key，内存小，有误判，不能删；
- 缓存空对象：简单，适合少量不存在key，消耗内存；
- 互斥锁：并发高的热点key，牺牲响应时间保护DB。

### 4. 缓存雪崩、缓存击穿、缓存穿透

1. **缓存穿透**：查询数据库根本不存在的数据，缓存查不到，请求直接打到数据库。
解决方案：布隆过滤器、缓存空对象、接口参数校验。
2. **缓存击穿**：**热点key过期，大量并发同时打到数据库**。
方案：互斥分布式锁；热点key永不过期。
3. **缓存雪崩**：大量缓存key**同时过期**，或者Redis整体宕机，大量请求全部涌向数据库。
方案：过期时间加随机偏移；Redis高可用哨兵/集群；多级缓存；限流熔断降级。

> 
> 区分记忆：
> 穿透：查不存在的数据；击穿：**一个热点key过期**；雪崩：**大量key同时失效/缓存整体挂掉**。

### 5. 分布式缓存架构设计

1. **高可用**：Redis哨兵Sentinel主从自动故障转移，或者Redis Cluster分片集群；主从复制，数据多副本。
2. **分片扩容**：Cluster 16384槽位，水平拆分海量数据，解决单实例内存上限。
3. **缓存问题防护**：处理穿透、击穿、雪崩；设置TTL过期时间；避免大key。
4. **缓存与数据库一致性**：更新策略：先更DB再删缓存； Canal监听binlog异步更新缓存；追求最终一致性。
5. **降级兜底**：Redis宕机，限流熔断，直接读数据库，返回兜底结果。
6. **序列化、内存优化**：控制大key，避免value过大；合理淘汰策略。

### 6. Redis事务 VS MySQL事务

1. **MySQL事务**：完整ACID；支持回滚；隔离级别；MVCC；保证原子、一致性、隔离、持久化。
2. **Redis事务(multi/exec)**

- 只保证**原子性（命令批量执行，要么全部执行，要么都不执行）**；
- ❗不支持回滚：如果中间命令执行报错，后面命令依旧执行，不会回滚前面成功命令；
- 没有隔离级别概念；不支持MVCC；> 
> 注意：Redis事务没有真正回滚，和数据库事务不一样；Redis想要真正原子操作，优先Lua脚本。

口述关键点：Redis事务不能回滚，只是批量排队执行；MySQL支持完整ACID、回滚、隔离级别。

#### span 是什么（面试口述版）

**Trace：一条完整请求链路，一个Trace包含多个Span** 

**Span：链路里一次独立的调用单元（一个最小的监控片段）**

举例子： 前端请求 → 网关 → A服务 → B服务 → MySQL 这一条整条是 **Trace（同一个traceId）** 里面拆分出来每一段就是 Span：

1. 网关收到请求 → 调用A服务：span1
2. A服务内部处理 → RPC调用B服务：span2
3. B服务里面执行SQL查询MySQL：span3

每个span自带信息：

- spanId：当前片段id
- parentSpanId：父调用的spanId（用来拼接调用树，知道谁调用谁）
- traceId：整条链路统一id
- 开始时间、耗时、状态（成功/异常）、调用类型（http / dubbo / mysql / redis）、标签（SQL语句、key）

一句话精简回答：

> Trace代表一次完整请求的整条调用链；Span是这条链路上的**单次操作/单次调用**，是链路追踪的最小单元，通过parentSpanId构建树形调用关系，记录这一段的耗时、状态。

补充区分，面试官很爱问：

- traceId：全局唯一，一条链路从头到尾不变
- spanId：每一段调用单独一个
- parentSpanId：上一层调用的spanId，用来还原调用层级

```
// 手写HashMap + 双向链表版本
class LRUCache {
    static class Node{
        int key,val;
        Node prev,next;
        Node(int k,int v){key=k;val=v;}
    }
    private HashMap<Integer,Node> map=new HashMap<>();
    private Node head,tail;
    private int cap;
    public LRUCache(int capacity) {
        cap=capacity;
        head=new Node(-1,-1);
        tail=new Node(-1,-1);
        head.next=tail;
        tail.prev=head;
    }
    private void remove(Node n){
        n.prev.next=n.next;
        n.next.prev=n.prev;
    }
    private void addFirst(Node n){
        n.next=head.next;
        n.prev=head;
        head.next.prev=n;
        head.next=n;
    }
    public int get(int key) {
        if(!map.containsKey(key)) return -1;
        Node node=map.get(key);
        remove(node);
        addFirst(node);
        return node.val;
    }
    public void put(int key, int value) {
        if(map.containsKey(key)){
            Node node=map.get(key);
            node.val=value;
            remove(node);
            addFirst(node);
        }else{
            Node newNode=new Node(key,value);
            map.put(key,newNode);
            addFirst(newNode);
            if(map.size()>cap){
                Node del=tail.prev;
                remove(del);
                map.remove(del.key);
            }
        }
    }
}
```

```java
public String multiply(String num1, String num2) {
    if ("0".equals(num1) || "0".equals(num2)) return "0";
    int m = num1.length(), n = num2.length();
    int[] res = new int[m + n];
    for (int i = m - 1; i >= 0; i--) {
        int a = num1.charAt(i) - '0';
        for (int j = n - 1; j >= 0; j--) {
            int b = num2.charAt(j) - '0';
            int sum = res[i + j + 1] + a * b;
            res[i + j + 1] = sum % 10;
            res[i + j] += sum / 10;
        }
    }
    StringBuilder sb = new StringBuilder();
    int idx = 0;
    while (res[idx] == 0) idx++; //跳过前导0
    for (; idx < res.length; idx++) {
        sb.append(res[idx]);
    }
    return sb.toString();
}
```

### 2. MySQL MVCC

MVCC：多版本并发控制，RC、RR隔离级别生效，**InnoDB特有**。
1. 每行记录两个隐藏列：`trx_id`（修改事务ID）、`roll_pointer`指向undo log历史版本链；

### 3. Spring AOP

AOP面向切面编程，把横切逻辑（日志、权限、事务、埋点）和业务代码解耦，不侵入业务。
**实现原理：动态代理**
1. 目标类实现接口：**JDK动态代理**，基于接口生成代理类；
2. 目标类没有实现接口：**CGLIB**，字节码生成子类代理；
核心概念：
- 切面Aspect：通知+切点；
- 切点Pointcut：匹配哪些方法；
- 通知Advice：before、after、around、after‑returning、after‑throwing。

### 4. JVM垃圾回收机制

GC回收堆中不再被使用的对象。
1. **GC Roots可达性分析**：从GC‑Root（栈局部变量、static静态变量、JNI引用等）出发，遍历，标记存活对象；不可到达判定垃圾。
2. 算法：复制算法（新生代）、标记‑清除、标记‑整理（老年代）。
3. 分代：新生代Eden+Survivor；老年代。新生代MinorGC；老年代MajorGC；整堆FullGC。

### 5. Redis实现分布式锁

核心命令：`SET key value NX EX`
- NX：key不存在才设置；EX设置过期时间，防止宕机死锁。
**安全问题**
1. 锁过期，业务还没执行完 → 看门狗续期（Redisson）；
2. 别人释放不属于自己的锁：存入uuid，释放的时候校验uuid，Lua脚本保证判断+删除原子；
3. Redis主从切换锁丢失：Redlock红锁（大部分业务不使用，复杂度高）。

>注意：简单`setnx+expire`两条命令不是原子，要用一条set指令；释放锁必须Lua脚本。

### 6. synchronized锁升级机制

JDK1.6优化，锁状态存储在对象头MarkWord，**只能升级，不能降级**
1. **偏向锁**：只有一个线程竞争；标记线程ID；消除CAS开销；适合单线程重复获取锁；
2. **轻量级锁**：多个线程交替抢锁，没有并发冲突；CAS自旋，用户态，不阻塞内核；
3. **重量级锁**：多线程同时竞争；向OS申请互斥锁；拿不到锁的线程阻塞，进入内核等待队列。

触发升级：偏向锁遇到另外线程竞争 →升级轻量级；轻量级自旋失败，竞争激烈 →升级重量级锁。

### 7. ConcurrentHashMap(JDK8)

底层：数组 + 链表 + 红黑树
1. 抛弃JDK7 Segment分段锁；
2. **CAS + synchronized锁哈希桶头节点**，锁粒度是单个桶；
3. put：空桶用CAS插入；桶已有元素，对桶头加synchronized；
4. get大部分无锁，依靠volatile保证数组、节点可见；
5. key、value都**不允许null**；
6. 链表≥8且数组≥64转为红黑树；节点变少退化为链表。

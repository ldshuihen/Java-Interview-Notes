## 宇视

### springboot和springcloud的区别

> 一句话核心：**SpringBoot 是快速开发单体微服务的开发脚手架；SpringCloud 是一套微服务分布式治理的全家桶规范**。 SpringCloud 里面每一个微服务，本身就是用 SpringBoot 来写的。

#### 1. 定位不同（最重要）

- Spring Boot：简化 Spring 应用开发，

  解决单体/单个服务快速搭建

  - 自动配置、starter起步依赖、内嵌Tomcat，不用大量XML配置
  - 作用：快速写一个独立可运行的Java服务
  - 关注点：开发效率、单体应用、快速启动

- Spring Cloud：一套分布式微服务治理框架集合（不是一个单独框架）

  - 包含服务注册发现、配置中心、熔断限流、网关、远程调用、分布式链路追踪等组件
  - 作用：把很多独立的 SpringBoot 服务组织起来，管理它们之间的通信、容错、治理
  - 关注点：分布式、服务之间协同

#### 2. 包含关系

✅ SpringCloud 依赖 SpringBoot； ✅ 可以只用 SpringBoot 写单体项目，**不使用 SpringCloud**； ✅ 不能脱离 SpringBoot 直接用 SpringCloud。

#### 3. 核心组件对照（SpringCloud Alibaba 版本，你项目常用）

Spring Cloud Alibaba（国内主流）：

- Nacos：注册中心 + 配置中心（替代Eureka、Config）
- Sentinel：熔断、限流、降级
- OpenFeign：远程接口调用
- Gateway：网关
- Seata：分布式事务
- RocketMQ：消息队列

#### 4. 对比表格（方便记忆）

| 维度         | SpringBoot                       | SpringCloud                      |
| ------------ | -------------------------------- | -------------------------------- |
| 本质         | 开发脚手架                       | 微服务治理规范套件               |
| 解决问题     | 简化Spring应用搭建，消除繁琐配置 | 分布式场景下多个服务的治理问题   |
| 最小单元     | 单个应用、单个服务               | 一整套微服务集群                 |
| 是否独立运行 | 可以独立运行                     | 不能独立运行，依赖SpringBoot服务 |
| 使用场景     | 单体项目、简单独立接口服务       | 大型系统，拆分成多个微服务       |

#### 5. 面试口述标准答案（直接背，1分钟版本）

> SpringBoot 是 Spring 的快速开发脚手架，通过自动配置和 starter 依赖，简化单个Spring应用的开发部署，内嵌容器，可以独立启动运行，主要用于快速开发单个服务。 SpringCloud 是一套微服务治理的解决方案，它本身不做业务开发，是用来管理多个微服务之间协作的，包含服务注册发现、配置中心、熔断限流、网关、远程调用、分布式事务等能力。 简单来说：**SpringBoot 用来写微服务，SpringCloud 用来管理一堆微服务；SpringCloud 基于 SpringBoot。**

#### 6. 高频追问提前准备

1. SpringBoot自动配置原理：`@EnableAutoConfiguration` + META-INF/spring.factories / spring-autoconfigure.imports，条件注解按需装配Bean
2. SpringCloud 和 SpringCloud Alibaba 的区别：原生SpringCloud组件很多停止维护（Eureka、Hystrix），Alibaba是阿里提供的替代生态，Nacos、Sentinel更适配国内业务
3. 什么时候不用微服务：业务简单、流量不大、团队小，直接SpringBoot单体更简单，避免分布式带来的复杂度

##### 追问 2：简历写了“数据库事务、缓存保障数据一致性”，在什么场景下用的？

* **场景 A：付款申请提交与流程引擎发起（本地事务 + 接口补偿）**

  >
  > 1. 利用 Redis 分布式锁拦截前端高频重复点击；

#### grep 相关指令

grep 是 Linux 文本检索命令，**在日志排查、过滤进程输出非常常用**，核心作用：按正则匹配文本行。
###### 常用参数

- `-n`：显示匹配行号（最常用，定位日志报错）
- `-i`：忽略大小写匹配
- `-v`：反向匹配，输出**不包含**关键词的行（过滤无用日志）
- `-r / -R`：递归检索目录下所有文件，`grep -r "Exception" ./logs`
- `-c`：只统计匹配到的行数，不打印内容
- `-o`：只输出匹配到的字符串，不是整行
- `-A n`：匹配行 + 后面n行（After）
- `-B n`：匹配行 + 前面n行（Before）
- `-C n`：匹配行 + 前后各n行（Context，排查堆栈很实用）

##### 示例

```bash
# 匹配到报错行，再打印后面5行
grep -A 5 "NullPointerException" app.log

# 匹配到报错行，打印前面5行
grep -B 5 "NullPointerException" app.log

# 最常用：前后各10行，看完整堆栈
grep -C 10 "Exception" app.log
```



##### 高频组合（面试必说，开发真实场景）

1. 实时日志过滤：`tail -f app.log | grep -n "error"`
2. 排除无关内容：`grep -v "INFO" app.log` 过滤掉INFO日志，只看异常
3. 看异常上下文：`grep -C 10 "NullPointerException" app.log` 打印异常前后10行
4. 多关键词（或）：`grep 'error\|Exception' app.log`
5. 和ps搭配查进程：`ps -ef | grep java`
> ✅ 加分提醒：`ps -ef | grep xxx` 本身这条grep命令也会被检索出来，一般再加 `grep -v grep` 过滤自身进程

##### 补充：egrep

`egrep = grep -E`，支持扩展正则，不用转义 `| () +`，写多条件更方便：
`egrep 'error|warn' app.log`

##### 1分钟精简口述版（AI面试）

grep用来文本过滤，常用参数有-n显示行号、-i忽略大小写、-v反向过滤、-r递归查文件，-A/-B/-C查看匹配行上下文。平时经常配合管道，tail -f实时过滤日志，ps检索进程，排查异常堆栈时会用-C打印前后日志；egrep等价grep -E，支持扩展正则。

##### 面试追问预演（常问）

问：`grep -A -B -C` 什么时候用？
答：看异常堆栈，报错关键字在一行，堆栈信息在前后，用-C抓取上下文，不用翻很多日志。

#### Linux 进程相关命令

##### 1. ps 查看进程快照（静态，不是实时刷新）

```bash
ps -ef
```
- `-e`：显示所有进程
- `-f`：全格式（UID、PID、PPID、CMD 等）
输出字段：
- UID：用户ID
- PID：进程ID
- PPID：父进程ID
- CMD：启动命令

常用变体：
```bash
ps aux   # 另一种高频，%CPU、%MEM、VSZ、RSS（CPU内存占比）
ps -ef | grep java   # 过滤Java进程，开发最常用
```
> 小坑：`grep` 自身这条进程也会被搜出来，可以 `grep -v grep` 过滤掉

##### 2. top 实时资源监控（动态刷新，默认3秒）

```bash
top
```
核心看点：
- 第一行：系统时间、运行时长、登录用户、负载（load average）
- 第二行：进程总数、运行/休眠/停止/僵尸进程
- 第三行：CPU 使用率（us用户、sy内核、id空闲、wa IO等待【重点！IO瓶颈看这个】）
- 第四、五行：内存、swap交换分区使用
- 下方列表：PID、USER、%CPU、%MEM、COMMAND

top 交互快捷键（实操常用）
- `P`：按CPU排序
- `M`：按内存排序
- `q`：退出
- `k`：在top内直接输入PID杀进程

> 同类轻量替代：`htop`（更友好，不是系统自带）

##### 3. kill 发送信号终止进程

```bash
kill PID
kill -9 PID
```
基础原理：kill 不是直接“杀死”，是给进程发信号
- `kill PID` 默认信号 `15(SIGTERM)`：优雅终止，进程可以捕获信号、清理资源、保存数据后退出（优先用这个！）
- `kill -9 PID` 信号 `9(SIGKILL)`：强制杀死，进程无法捕获、不能清理资源，容易丢数据、文件损坏，**生产尽量不要优先用**

常用信号补充（面试偶尔问）
```bash
kill -1 PID   # SIGHUP，重新加载配置（很多中间件热加载用，nginx等）
kill -2 PID   # SIGINT，等价Ctrl+C
```
批量杀进程辅助：
```bash
pkill java        # 按进程名杀
pgrep java        # 只查对应进程PID
```

---
##### ✅ 一句话速记

- `ps`：拍一张进程快照，`ps -ef` / `ps aux`，搭配grep过滤
- `top`：实时看CPU内存负载，wa高代表IO瓶颈
- `kill`：默认15优雅退出；`kill -9` 强制杀，慎用

##### 面试简答版（可以直接背）

ps 查看静态进程信息；top 实时监控服务器资源与进程；kill 默认15信号优雅关闭进程，kill -9是SIGKILL强制终止，进程无法做收尾工作，生产优先15，进程僵死无响应才考虑-9。

##### 1. grep：文本检索，过滤内容

参数说明

- `-r`：递归检索目录下所有文件（不用find也能搜代码/日志）
- `-A 5`：匹配行+后面5行（After）
- `-B 5`：匹配行+前面5行（Before）
- `-C 5`：匹配行前后各5行（Context，查堆栈报错首选）

示例合集
```bash
grep -n "Exception" app.log          # 带行号搜异常
grep -i "error" app.log              # 忽略大小写搜error
grep -v "debug" app.log              # 过滤掉debug日志
grep -r "orderService" /opt/project  # 递归在项目目录搜关键词
ps -ef | grep java | grep -v grep    # 查java进程，排除grep自身
```

##### 2. find：在系统中**查找文件/目录**（按文件名、大小、时间）

语法：`find 搜索路径 条件`
```bash
find /opt -name "*.log"
```
常用参数
- `-name`：按文件名匹配，支持通配符 `* ?`
- `-iname`：文件名忽略大小写
- `-type f`：只找普通文件；`-type d`：只找目录
- `-size`：按文件大小（`+100M`大于100M，`-10M`小于10M）
- `-mtime`：按修改时间（`-mtime -7` 7天内修改的文件）

高频示例
```bash
find ./ -name "*.java"                # 当前目录找所有java文件
find /var/log -type f -size +1G       # 查找大于1G的日志文件
find /opt -name "*.log" | xargs grep -n "timeout"
# 经典组合：find找到文件，传给grep检索内容
```
> 重点：`find | xargs grep` 和 `grep -r` 都可以递归搜；find适合先过滤文件（按大小/时间）再检索

##### 补充：管道 `|`

作用：把前一条命令**标准输出**，作为后一条命令的输入
```bash
cat app.log | grep "timeout"
# 等价 grep "timeout" app.log，管道适合串联多步过滤
```

---
##### ✅ 一句话速记

- grep：**文件里面搜文本内容**，-n行号、-v反向、-C看上下文，配合管道
- find：**在磁盘上搜文件本身**，按名字、类型、大小、时间查找；常搭配xargs+grep

##### 面试简答版

grep用于文本内容过滤检索，支持行号、反向匹配；find用于遍历文件系统查找文件，可按文件名、大小、时间筛选；管道`|`用来串联命令，把上一个命令输出交给下一个命令处理。

##### 1. 查看网卡IP

```bash
ip addr
```
- 新版Linux（CentOS7+、Ubuntu）**原生推荐 ip 命令**，功能强
- 输出：网卡名 `eth0/ens33/lo`、inet（IPv4地址）、inet6、MAC地址

- 老工具，属于 `net-tools`，**新版系统默认没有，需要安装**

##### 2. 端口监听

```bash
# ss（首选，替代netstat，自带，性能更高）
ss -tulnp

# netstat（老旧，需要装net-tools）

```
参数 `-tulnp` 回顾：
- `-t` TCP、`-u` UDP
- `-l` LISTEN 监听端口（重点！只看服务正在监听的）
- `-n` 数字形式，不解析域名，速度快
- `-p` 显示进程PID/程序名（需要root/sudo）

> 区分：不带 `-l` 会看到已经建立的连接；查服务有没有启动监听，一定要加 `-l`

##### 3. ping 测试连通性

```bash

ping 192.168.1.1
```
- 默认持续发包，`Ctrl+C` 停止
- `-c 4`：只发4个包（脚本里常用，不会卡死）
```bash
ping -c 4 127.0.0.1
```
⚠️ 注意：ping 基于ICMP协议；**能ping通不代表端口通**（防火墙放通ICMP，但拦截业务端口）

##### 4. curl 发起HTTP请求（后端调试接口神器，高频）

```bash
# GET请求（默认GET）
curl [http://127.0.0.1:8080/hello](http://127.0.0.1:8080/hello)

# POST + json参数
curl -X POST -H "Content-Type:application/json" -d '{"name":"test"}' [http://127.0.0.1:8080/api/user](http://127.0.0.1:8080/api/user)

# 只看响应头（排查302、状态码）
curl -I http://xxx

# 带超时（生产脚本必加，防止卡住）
curl --connect-timeout 3 http://xxx
```
常用参数：
- `-X` 指定请求方法：POST / PUT / DELETE
- `-H` 添加请求头
- `-d` 请求体数据
- `-I` 只拿header，不返回body
- `-o` 把响应写入文件

##### 补充小命令（面试偶尔顺带问）

- `telnet ip port`：老式端口连通测试；很多环境已不自带
- `wget url`：下载文件，也可简单测试网络

#### Linux 查看端口

> 场景：启动服务报 `Address already in use`，查端口占用、拿到PID

##### 1. lsof（最简单直观，优先用）

```bash
sudo lsof -i:8080
```
- `-i`：网络连接；后面跟 `:端口`
- 输出：COMMAND、PID、USER、协议、监听状态
- `-t`：只输出PID（脚本一键杀进程）
```bash
# 拿到PID直接杀（生产慎用！）
kill $(lsof -t -i:8080)
```
⚠️ 注意：很多最小化系统默认没装 lsof

##### 2. ss（现代推荐，netstat替代品，系统自带、速度快）

```bash
sudo ss -tulnp | grep :8080
```
参数解释：
- `-t` TCP、`-u` UDP
- `-l` 只看监听LISTEN端口
- `-n` 数字端口，不解析域名（快）
- `-p` 显示进程PID/名称（需要sudo）

##### 3. netstat（老命令，面试常问，新系统一般要装net-tools）

```bash
sudo netstat -tulnp | grep :8080
```
参数和ss完全一样；**CentOS7+/Ubuntu新版默认不带netstat**

###### 补充：参数速记

`tulnp`：TCP+UDP、监听、数字、进程

##### 4. 辅助排查

- 看所有监听端口：`ss -tuln`
- 端口连通性测试：`curl ip:port` / `telnet ip port`
- 进程反查端口：`ss -tulnp | grep PID`

##### ✅ 一句话速记

- `lsof -i:端口`：简洁直观，直接看占用进程
- `ss -tulnp | grep :端口`：首选、自带、性能好
- `netstat -tulnp`：老版本命令，面试要知道

##### 面试简答版

查看端口占用优先使用 `ss -tulnp | grep :端口`，也可以用 `lsof -i:端口`；netstat是旧工具。通过命令拿到PID后，先用 `kill PID`（15信号优雅关闭），必要时才 `kill -9`。



### 支付系统核心要点

> 定位：对接用户、商户、第三方支付渠道（微信/支付宝/银联），保证**资金准确、不丢单、不重复扣款、可对账、可退款**，核心原则：**资金安全优先、最终一致性**

#### 一、核心基础能力

1. **下单&支付单**
   - 订单和支付单解耦：一个业务订单可以对应多笔支付单（组合支付、分多次支付）；一笔支付单只能对应一笔成功流水
   - 支付单状态机（重点！面试高频）：待支付 → 支付中 → 支付成功 / 支付失败 / 已关闭
   - 状态流转严格单向，禁止随意变更；状态变更必须落库+日志
2. **渠道对接**
   - 上游：商户/业务系统；下游：微信、支付宝、银联、网联
   - 两类通知：**同步返回（前端展示）、异步回调（渠道异步通知，以回调为准！）**
   ✅ 关键点：**支付结果以第三方异步回调为准，不能信同步返回**
3. **幂等（重中之重）**
   - 防重复下单、重复回调、重复扣款
   - 方案：支付单号作为幂等键，数据库唯一索引 + 先查后写；回调收到重复请求直接返回成功，不重复执行业务

#### 二、三大核心难题（必背）

##### 1. 超时 & 结果不确定（支付中）

用户扫码后关掉页面，渠道不知道成功与否 → **轮询 + 渠道查单**
- 本地定时任务主动调用渠道查询接口，补偿状态
- 超时自动关单，释放额度，避免资金挂起

##### 2. 退款流程

- 原路退款：支付用什么渠道付，就退回哪里
- 状态：待退款 → 退款中 → 退款成功/退款失败
- 约束：只能退已成功的订单；退款金额 ≤ 原支付金额；支持部分退款、多次部分退款
- 退款也有异步回调，同样要做幂等

##### 3. 对账（资金防线）

- 对账对象：**本地支付流水 VS 渠道对账单**
- 时间：一般T+1日跑批
- 三类差异：
  - 本地有、渠道无：本地多账 → 核实，必要时做冲正
  - 渠道有、本地无：渠道多账 → 补单
  - 金额不一致：长短款，人工差错处理
- 对账结果生成差错单，人工复核，不能程序自动调账！

#### 三、高可用 & 安全

1. **防重、防篡改**
   - 请求签名：商户和支付系统、支付系统和渠道之间，请求参数签名验签，防止篡改
   - 敏感信息加密：银行卡、证件信息脱敏存储，不明文
2. **限流熔断**
   
   - 支付入口是流量高点，对商户、渠道做限流；渠道异常时熔断降级，避免雪崩
3. **事务一致性**
   支付属于分布式场景，不用强一致；常用**本地消息表 / RocketMQ事务消息 / Seata TCC**
   业务订单和支付单：支付成功后，可靠消息通知业务系统更新订单状态
   
   > 一般不用AT，资金场景TCC更可控

#### 四、延伸能力（加分项）

- 分账：支付成功后，按比例分给多个商户（平台、卖家）
- 手续费计算：渠道手续费，记账
- 资金账户体系：平台账户、商户余额账户（余额支付）
- 风控：限额、黑名单、高频支付拦截、异常设备风控

#### ✅ 1分钟精简口述版（AI面试直接背）

支付系统核心是保障资金准确安全。首先要维护支付单状态机，支付结果以渠道异步回调为准，全程做好幂等防止重复扣款；针对支付结果不确定的情况，通过主动查单补偿状态；支持原路退款、部分退款；每天T+1和渠道对账，处理长短款差错。分布式场景依靠可靠消息或者TCC保证业务和支付状态一致，同时通过签名验签、限流风控保障安全。

### 如何使用AI设计一个系统

核心结论：**用AI辅助系统设计，不是只让AI画图写表，整套过程要同步输出Skill（能力清单）和各类设计文档，AI只是辅助生成初稿，人负责评审定稿**。整体流程：需求输入 → 能力梳理（Skill） → 分层设计文档产出 → 评审校验 → 落地。

#### 1. 先梳理Skill（系统能力/服务能力，面试这里是加分点）

Skill就是系统对外暴露、内部模块具备的能力，区分**业务能力、技术能力**，用来对齐范围，避免设计跑偏。
- 业务Skill（以支付举例）：创建支付单、发起支付、接收渠道回调、主动查单、原路退款、部分退款、对账、差错处理
- 技术Skill：幂等校验、签名验签、分布式状态补偿、限流熔断、日志埋点、链路追踪
- 做法：我先和AI一起梳理Skill清单，区分核心能力、非核心能力、扩展能力；明确每个Skill的入参、出参、前置后置约束、异常场景。
> Skill的价值：后续接口、表、流程全部围绕这些能力展开，防止漏场景、过度开发。

#### 2. 再产出全套设计文档（AI生成初稿，人工复核）

文档分层，由粗到细：
1. **需求文档（PRD）**：业务背景、用户角色、主流程、异常场景、指标（QPS、时延、一致性要求）
2. **概要设计文档（HLD）**：整体架构图、模块划分、依赖中间件、领域模型、核心状态机、技术方案选型（TCC/可靠消息等）
3. **详细设计文档（LLD）**
    - 接口文档：每个Skill对应的接口、幂等号、签名、错误码
    - 数据库设计：表结构、索引、唯一键、字段注释、分库分表策略
    - 核心流程图：正常流程、异常补偿流程（Mermaid）
    - 重试策略、死信、降级、风控规则
4. **运维&测试文档**：部署清单、监控告警项、测试用例

#### 3. AI在Skill和文档里的角色

- 我给AI明确约束：业务背景、技术栈、流量、风险红线（比如资金系统不能自动调账）
- AI辅助：把Skill整理成结构化清单、生成文档初稿、绘制流程图、输出表结构、梳理异常case
- 我负责：**审定Skill是否完整合理、审核文档里的风险点**，比如幂等、资金流转、状态机，AI初稿很容易缺失边界case，不能直接作为上线依据

#### 4. 完整链路一句话串起来

先梳理系统需要提供哪些Skill，划定能力边界；再基于Skill驱动概要、详细设计文档编写；AI辅助产出初稿，我做风险评审和方案把关，文档和Skill作为后续开发、联调、测试的依据。

---
#### ✅ 1分钟精简口述版（AI面试）

是的，需要先梳理Skill，再输出设计文档。Skill用来定义系统的业务能力和技术能力，划定功能边界；之后基于Skill驱动概要设计、详细设计等文档。AI主要辅助生成Skill清单、文档初稿和流程图，但是像资金类场景的状态流转、幂等、对账这些核心逻辑，我会人工仔细审核文档，文档最终作为开发和联调的标准。

#### 面试追问预演

问：Skill和接口文档的区别？
答：Skill偏向**能力语义**，描述系统能干什么；接口文档是Skill的技术落地载体，定义怎么调用这个能力，一个Skill可以对应一个或者多个接口。

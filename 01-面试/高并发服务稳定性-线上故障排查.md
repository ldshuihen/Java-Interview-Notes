# 高并发下服务稳定性-线上故障排查

## 1 请求流量类问题

1. 突发流量（Traffic Spike）
2. 流量洪峰（Traffic Surge）
3. 流量倾斜（Traffic Skew）
4. 热点 Key / 热点数据
5. 热点接口
6. 爬虫 / 恶意请求
7. 瞬时并发过高
8. 大促 / 秒杀流量

请求流量类问题核心可以归纳为 **四类本质问题**：

| 类别         | 本质             |
| ------------ | ---------------- |
| 流量规模问题 | 流量超过系统容量 |
| 流量分布问题 | 流量集中         |
| 流量质量问题 | 恶意流量         |
| 并发问题     | 瞬间请求过多     |

最终表现为：

```
系统处理能力 < 请求流量
```

> 目标：研究生秋招Java岗20k+，面试要讲清楚：**现象→危害→根因→解决方案→Java落地实践→优缺点/注意点**，部分会带上秒杀、大促场景，面试可以直接口述。

### 1 突发流量（Traffic Spike）

#### 现象

短时间内流量突然暴涨，无规律，瞬间从日常QPS飙升数倍到数十倍，不是平缓上涨，是尖刺式流量。
> 和洪峰区别：突发流量是**意外、不可预期**；洪峰是预期内的峰值。

#### 危害

1. CPU、内存、线程池打满，服务卡顿、RT飙升
2. Tomcat/Jetty连接池耗尽，新请求直接拒绝
3. DB、Redis下游被打穿，级联故障
4. 大量请求堆积，GC频繁，OOM，服务宕机

#### 根因

运营活动突然推送、外部事件引爆、上游系统异常突推流量、用户行为突然爆发。

#### 解决方案（Java落地）

1. **限流**：Sentinel / Guava RateLimiter，网关层限流优先（Nginx、SpringCloud Gateway），接口层限流兜底。
2. **熔断降级**：Sentinel熔断，流量突增时，非核心接口直接返回兜底数据，放弃部分非核心流量。
3. **弹性扩容**：K8s HPA自动扩缩容，机器实例数随QPS自动上涨。
4. **队列削峰**：消息队列RocketMQ/Kafka异步削峰，同步转异步，把瞬时尖峰流量抹平。
5. **保护下游**：设置Feign/RestTemplate线程池、超时时间，不允许无限等待下游。

> 面试话术：突发流量优先网关拦截，再服务内限流，再异步削峰，最后扩容，不单纯靠堆机器。

### 2 流量洪峰（Traffic Surge）

#### 现象

**可预期的高峰期流量**，比如每天中午、晚上业务高峰，有规律，流量缓慢抬升到高点，维持一段时间再回落，不是瞬间尖刺。

#### 危害

整体资源水位持续高位，CPU、连接池长期满负载；慢查询堆积，DB压力大；长时间高负载容易引发服务雪崩。

#### 根因

业务固有的用户访问规律，定时任务集中执行，固定时段用户活跃。

#### 解决方案

1. **容量评估压测**：提前压测，算出单机最大QPS，提前预扩容，大促前预留机器。
2. **全链路压测**：构造线上量级流量，识别DB、缓存、中间件瓶颈。
3. **多级缓存**：本地Caffeine缓存 → Redis分布式缓存 → DB，尽量拦截流量到缓存层，少打数据库。
4. **资源隔离**：核心业务、非核心业务线程池隔离，洪峰到来，非核心不抢占核心业务资源。
5. **定时任务错峰**：把大量定时任务打散，避免同一时刻全部执行。

> 区分记忆：突发流量：**意外尖刺，靠限流熔断异步**；流量洪峰：**预期高峰，靠提前扩容+压测+缓存**。

### 流量突刺/突发洪峰

#### 核心成因

- 营销活动触发：秒杀、限时折扣、优惠券发放等活动，用户在活动开始瞬间集中涌入，流量短时间内暴涨（通常是日常流量的10-100倍）。
- 热点事件驱动：明星代言、热点话题、节日促销等，引发用户集中访问，导致流量突发激增，超出服务日常承载能力。
- 无流量预警与准备：未提前预判活动流量，未做扩容、限流准备，日常配置无法应对突发洪峰。
- 外部流量冲击：第三方平台引流、恶意流量集中发起，短时间内大量请求涌入，形成流量突刺。

#### 造成危害

流量瞬间超出服务承载上限，导致接口超时、请求失败、服务卡顿；核心依赖（如数据库、缓存）被打满，引发连锁故障；严重时导致服务崩溃、系统宕机，活动无法正常进行，造成用户流失和经济损失。

#### 解决方案

- 流量预判与扩容：提前评估活动流量，进行压测，根据压测结果扩容服务器、缓存集群、数据库，提升服务承载能力；采用弹性扩容（如K8s自动扩缩容），应对突发流量。
- 流量削峰：引入队列机制（如RabbitMQ、RocketMQ），将突发请求缓存起来，按服务处理能力匀速消费，避免流量直接冲击核心服务。
- 限流与排队：在网关层、接口层设置限流规则，超过阈值的请求直接拒绝或进入排队队列；前端增加排队、倒计时机制，引导用户有序访问。
- 多级缓存兜底：核心接口、热点数据部署多级缓存（本地缓存+Redis集群），减少数据库查询压力，提升响应速度，应对突发流量。
- 应急兜底：设置降级策略，流量突刺时，关闭非核心功能（如评论、分享），集中资源保障核心业务（如下单、支付）正常运行。

### 3 流量倾斜（Traffic Skew）

#### 现象

集群多实例部署，**流量没有均匀分配到各个节点**，部分机器负载极高，部分机器空闲。比如共10台机器，2台CPU打满，另外8台很闲。

#### 危害

部分节点CPU、线程耗尽，接口超时报错；整体集群能力没有发挥出来；个别节点宕机，故障扩散。

#### 根因

1. Nginx/gateway负载均衡策略问题：ip_hash固定hash，同一个客户端永远打到同一台机器；
2. 业务hash分片：根据用户id、订单id做hash路由，某些分片流量大；
3. 会话粘滞（sticky session），同一用户一直访问同一实例；
4. MQ消费：部分队列消息量巨大，消费实例分配不均。

#### 解决方案

1. 负载均衡策略调整：优先**轮询、加权轮询**，非必要不用ip_hash；必须会话保持，尽量用redis存session，去掉粘滞。
2. Hash算法增加虚拟节点：一致性hash，缓解hash倾斜。
3. MQ：合理分区数，分区尽量大于消费实例数，自动重平衡。
4. 监控单实例QPS、CPU，发现实例之间负载差距过大告警。
5. 网关层增加权重动态调整，对过载节点降权。

> Java面试坑：很多同学只知道负载均衡，不知道流量倾斜，面试官会问：集群部署了为什么部分机器负载很高？答这个。

### 4 热点Key / 热点数据

#### 现象

少数key被极高频率访问，几万QPS打在同一个Redis Key、同一条DB记录上。比如秒杀商品、爆款商品、热搜。

#### 危害

1. Redis热点key：Redis单实例CPU打满；Redis集群分片倾斜，某一个分片压力爆炸；
2. DB热点行：大量并发读同一行，行锁竞争，DBCPU飙升，大量慢SQL；
3. 缓存击穿：热点key失效瞬间，大量请求同时打到DB。

#### 根因

爆款商品、秒杀商品、热搜、大V信息，大量用户同时读取同一份数据。

#### Java解决方案

1. **本地缓存隔离热点**：Caffeine本地缓存，服务实例本地存热点key，绕过Redis，减少Redis访问；设置短过期时间。
2. **热点key打散**：同一个逻辑key拆成N个物理key，`goods_1001_0 ~ goods_1001_9`，请求随机取其中一个，分散到不同Redis分片。
3. **永不过期+后台主动刷新**：热点key不设置过期时间，后台线程定时更新缓存，避免缓存失效瞬间大量请求穿透DB。
4. **互斥锁 / 热点保护**：Sentinel热点参数限流，针对参数维度限流，同一个商品ID限制QPS。
5. DB热点行：读写分离，热点数据前置缓存，尽量少访问数据库；必要时分库分表打散。
6. Redis 4.0+支持热点key监控，监控报警。

> 高频面试题：热点key怎么解决？重点讲本地缓存Caffeine+key打散+后台主动更新，不要只说加锁。

### 5 热点接口

#### 现象

某一个接口QPS远高于其他接口，占整个服务80%以上流量，其他接口流量很小。比如商品详情接口。

#### 危害

该接口耗尽服务线程池、CPU资源，同一个服务下其他业务接口没有资源可用，整体服务雪崩。

#### 根因

业务高频访问接口，前端大量调用，爬虫集中调用该接口。

#### 解决方案

1. **线程池隔离**不同接口，使用Sentinel线程池隔离，热点接口独立线程池，耗尽后不会影响其他接口。
2. **接口维度限流降级**：Sentinel对热点接口设置限流阈值，超过阈值返回降级结果。
3. **多级缓存**：网关缓存、本地缓存、Redis缓存，尽可能拦截请求，少进入业务逻辑。
4. 接口单独部署：核心热点接口拆独立服务，和普通业务物理隔离，互不影响。
5. 前端优化：前端做缓存，减少重复请求，防抖节流。
6. 监控：接口QPS、RT、错误率监控告警，识别热点接口。

> 面试点：线程池隔离，注意区分**信号量隔离和线程池隔离**：线程池隔离有独立队列；信号量只是计数器共用线程。高并发优先线程池隔离。

### 热点单体压力

#### 核心成因

- 热点数据集中：单一商品（如爆款商品）、单一用户（如头部主播、高活跃用户）、单一接口（如首页推荐接口），吸引大量请求，导致流量集中在单个资源上。
- 节点负载不均：集群部署时，负载均衡策略不合理，导致大量流量集中在单个节点上，其他节点闲置，形成“单点过载”。
- 缓存热点问题：热点数据缓存集中在单个Redis节点，所有请求都访问该节点，导致Redis节点压力过大，甚至宕机。
- 无热点分流机制：未对热点资源进行分流、隔离，所有请求都直接访问热点单体，导致压力集中。

#### 造成危害

热点单体（节点、接口、缓存、商品）被大量请求冲击，导致响应缓慢、超时，甚至不可用；热点单体故障后，相关核心业务无法开展（如下单接口过载，导致用户无法下单）；集群资源利用率不均衡，浪费服务器资源。

#### 解决方案

- 热点数据分流：对热点商品、热点用户进行分片处理，分散流量；核心热点接口做集群部署，通过负载均衡分散请求，避免单点压力。
- 缓存优化：热点数据采用Redis集群分片存储，避免单一节点承载所有热点请求；使用本地缓存，减少对Redis热点节点的访问；热点数据预热，提前将热点数据加载到缓存，提升响应速度。
- 负载均衡优化：调整负载均衡策略（如轮询、权重、一致性哈希），确保集群节点负载均衡；对热点节点进行扩容，单独提升热点单体的承载能力。
- 热点隔离：将热点业务与非热点业务隔离部署，使用独立的服务器、缓存、数据库，避免热点业务影响其他业务；对热点请求进行限流、排队，避免热点单体被打垮。
- 热点监控与预警：实时监控热点资源的请求量、响应时间，设置预警阈值，及时发现热点单体压力异常，快速扩容或分流。

### 6 爬虫 / 恶意请求

#### 现象

大量非真实用户请求，爬虫、脚本、攻击请求，高频刷接口，占用大量服务器资源。

#### 危害

占满带宽、CPU，挤占真实用户流量；刷数据库，刷缓存；盗数据，接口被打垮。

#### 解决方案

1. **网关层防护（优先）**
    - Nginx/Gateway限流：IP限流，单IP最大QPS。
    - User‑Agent识别爬虫，拦截非法UA。
2. **验证码、滑块**：高频访问触发验证码，区分机器和人。
3. IP黑名单：短时间大量异常请求，加入黑名单，一段时间封禁；注意不要误封代理用户。
4. 请求签名、token校验：非法token直接网关拒绝，不转发后端Java服务。
5. 业务层Sentinel：IP维度限流。
6. 频率控制：同一个账号短时间访问次数限制。
7. WAF防火墙，拦截恶意攻击。

> 注意：单纯IP黑名单有缺陷，爬虫会大量换IP，需要结合UA、请求行为、token综合判断。

### 无效流量/爬虫/薅羊毛

#### 核心成因

- 恶意爬虫攻击：爬虫程序模拟正常用户请求，批量爬取网站数据（如商品信息、用户信息），消耗服务资源，甚至窃取敏感数据。
- 薅羊毛行为：恶意用户利用平台漏洞、活动规则，通过脚本批量注册账号、领取优惠券、下单薅羊毛，占用活动资源，导致正常用户无法参与。
- 无效请求泛滥：低频访问、重复请求、恶意刷新，以及测试、调试产生的无效请求，占用服务带宽和连接资源。
- 防护机制缺失：未做爬虫识别、账号风控，无无效流量过滤规则，无法区分正常流量与恶意流量。

#### 造成危害

无效流量占用服务器CPU、内存、带宽资源，导致正常用户请求被挤压，接口响应变慢、超时；爬虫窃取敏感数据，存在数据泄露风险；薅羊毛行为导致平台经济损失，活动规则失效，影响平台公信力；严重时导致服务资源耗尽，正常业务无法开展。

#### 解决方案

- 爬虫识别与拦截：使用爬虫识别工具（如UA识别、IP黑名单、行为分析），拦截异常爬虫请求；设置接口访问频率限制，禁止批量高频请求。
- 账号与行为风控：建立用户行为模型，识别异常账号（如批量注册、异地登录）；对薅羊毛行为进行监控，限制单个账号活动参与次数，校验账号真实性（如手机验证码、人脸识别）。
- 无效流量过滤：设置请求过滤规则，过滤低频访问、重复请求、恶意刷新等无效流量；对测试环境、调试请求进行标识，单独隔离，不占用核心服务资源。
- 接口防护：核心接口增加验证码、Token校验，防止脚本批量调用；对敏感接口（如优惠券领取、下单）增加风控校验，拦截异常请求。
- 监控与追溯：实时监控流量来源、请求频率、用户行为，及时发现无效流量和恶意行为；记录请求日志，便于后续追溯和排查。

### 7 瞬时并发过高

#### 现象

同一时刻大量请求同时到达服务，同一毫秒上千请求，并发突刺。和突发流量很像，更强调**同一时间点并发**，不是持续流量。

#### 危害

Tomcat accept队列打满，请求排队；线程瞬间创建耗尽；大量请求同时穿透缓存，打到DB；大量线程竞争锁，CPU上下文切换高；数据库连接池瞬间耗尽。

#### 根因

前端批量请求、定时任务同一时刻触发、用户同时点击、秒杀点击、MQ瞬间大量消息涌入。

#### Java解决方案

1. **队列缓冲**：网关、服务内部队列，超出队列长度直接拒绝。Tomcat调整accept‑count参数。
2. **限流**：令牌桶/漏桶，平滑流量，把瞬时并发抹平。Guava RateLimiter令牌桶；Sentinel。
3. **异步化**：同步改MQ异步处理，不要同步阻塞处理高并发请求。
4. **连接池大小合理设置**：Tomcat最大线程、数据库连接池不要设置过大，过大会上下文切换，一般tomcat线程200‑400，DB连接数十级别。
5. **锁优化**：减少synchronized重锁，使用CAS、分段锁，避免大量线程同时抢锁。
6. **请求合并**：多个小请求合并成一个批量请求，减少并发数量。
7. 避免热点失效带来的“缓存击穿”：大量并发同时来查同一个失效key。

> 面试坑：很多人把线程池设置很大，面试官会反问：线程是不是越大越好？答：线程太多，CPU上下文切换开销暴涨，性能反而下降。

### 8 大促 / 秒杀流量

#### 现象

秒杀属于**综合极端场景**，集合上面所有问题：突发流量、瞬时并发、热点key、热点接口、流量洪峰。短时间百万QPS涌入，大量用户抢有限库存。

#### 危害

Redis、DB被打垮；超卖；服务宕机；大量用户超时。

#### 完整解决方案（Java秒杀经典方案，面试高频）

1. **前端层**
    - 按钮置灰，防止重复点击；前端限流；页面静态化。
2. **网关层（第一层拦截）**
    - 限流、黑名单；过滤非法请求；粗粒度限流挡掉大部分无效流量。
3. **应用服务层**
    1. 多级缓存：Caffeine本地缓存 + Redis；商品信息预加载缓存。
    2. **库存前置到Redis**，不在DB直接扣库存；Redis预扣库存。
    3. **削峰异步**：抢到资格的请求发送MQ，异步做订单创建；前端返回排队中。
    4. Sentinel限流熔断，热点参数限流，针对商品ID做热点限流。
    5. 线程池隔离，秒杀接口独立线程池，不影响普通业务。
4. **Redis层**
    - 热点key打散；防止大key；分布式锁扣库存；Lua脚本保证原子扣库存，避免超卖。
5. **数据库层**
    - 最终一致性校验，DB扣库存做兜底；乐观锁防止超卖 `update stock set count=count‑1 where id=xx and count>0`；分库分表；读写分离。
6. 降级：Redis库存耗尽，直接返回“已抢完”，不再往下走。

#### 核心问题面试追问

> Q：为什么不能所有请求直接访问DB？
> A：DB扛不住秒杀瞬间并发，数据库TPS上限有限，大量请求直接打库会直接宕机，所以把库存放到Redis，MQ异步削峰。

> Q：Redis扣完库存，DB扣失败怎么办？
> A：消息重试、补偿任务回滚Redis库存，保证最终一致性。



### 上下游流量放大

#### 核心成因

- 分页查询不合理：上游服务分页查询时，不限制分页大小，全量拉取下游服务数据（如一次拉取10万条数据），导致下游服务压力骤增。
- 循环依赖与重复调用：上下游服务存在循环依赖，互相调用，形成闭环，导致请求量指数级放大；同一请求被多次重复调用，增加下游服务负担。
- 批量操作无限制：上游服务批量调用下游接口时，未限制批量大小，一次发起大量请求（如一次调用1000个接口），导致下游服务被瞬间打满。
- 重试机制叠加：上游服务超时重试，下游服务处理缓慢，导致重试流量叠加，进一步放大流量，形成恶性循环。

#### 造成危害

下游服务被放大的流量冲击，导致接口超时、响应缓慢，甚至服务崩溃；上下游服务互相影响，引发连锁故障，整个调用链路瘫痪；资源被无效占用，服务处理效率大幅下降，正常请求无法被及时处理。

#### 解决方案

- 规范分页查询：限制分页大小（如单次最多拉取100条数据），禁止全量拉取；采用游标分页、书签分页，优化分页查询性能，减少下游服务压力。
- 破除循环依赖：梳理服务调用链路，移除循环依赖，采用事件驱动、消息队列异步通信，替代同步循环调用；明确服务职责，避免重复调用。
- 限制批量操作：批量调用下游接口时，设置批量大小上限（如单次最多调用100个接口），分批处理批量请求，匀速发起，避免流量集中冲击。
- 优化重试与限流：规范上游服务重试策略，设置重试次数和间隔，避免无限重试；在上下游服务之间设置限流规则，防止流量放大；下游服务对上游请求进行限流，避免被过量请求打垮。
- 链路监控：监控上下游服务调用链路，跟踪请求量、响应时间，及时发现流量放大问题，优化调用逻辑。

## 2 资源耗尽类问题

1. CPU 资源耗尽
2. 内存耗尽
3. GC 频繁
4. 线程池耗尽
5. 连接池耗尽
6. 文件句柄耗尽
7. 磁盘 IO 打满
8. 网络带宽耗尽
9. Socket 资源耗尽
10. 临时对象暴增

资源耗尽问题的本质是：

```
系统资源 < 系统负载
```

资源可能包括：

- CPU
- 内存
- 线程
- 网络
- IO
- 连接

当某一种资源被耗尽，就会导致系统性能下降甚至不可用。

资源耗尽问题可以归为 **5 大类资源瓶颈**：

| 资源类型 | 典型问题           |
| -------- | ------------------ |
| 计算资源 | CPU、GC            |
| 内存资源 | 内存耗尽、对象暴增 |
| 线程资源 | 线程池耗尽         |
| IO资源   | 磁盘 IO、网络带宽  |
| 连接资源 | 连接池、Socket、FD |

本质规律：

```
系统资源 < 系统负载
```

最终会导致：

```
响应变慢 → 请求堆积 → 服务雪崩
```

> 面试标准答题结构：**现象 → 危害 → 根因 → Java落地排查+解决方案 → 面试踩坑点**，面向20k+Java后端，会带上排查命令、线上定位思路。

### 1 CPU资源耗尽

#### 现象

服务器CPU持续80%~100%，居高不下；接口RT飙升，响应变慢，大量超时；系统负载load远大于CPU核数。
> 区分：CPU高不一定是并发大，也可能死循环、频繁GC。

#### 核心成因

- 死循环：代码逻辑存在缺陷，出现无限循环、循环条件异常，导致CPU持续高负载运行，无法释放资源。
- 频繁GC：内存中短生命周期对象过多、大对象频繁创建与销毁，触发频繁的垃圾回收（尤其是Full GC），占用大量CPU资源。
- 序列化反序列化耗时：频繁对大对象进行序列化、反序列化操作（如JSON、ProtoBuf转换），序列化逻辑复杂，消耗大量CPU算力。
- 正则回溯：使用复杂正则表达式（如嵌套量词、回溯匹配），匹配过程中出现大量回溯操作，导致CPU占用飙升。

#### 造成危害

线程调度排队，请求处理变慢；下游超时，引发熔断雪崩；整机卡死，服务不可用。

CPU利用率持续处于100%，服务处理能力急剧下降，接口响应超时、请求堆积；频繁GC导致服务卡顿，业务逻辑执行中断；严重时CPU资源耗尽，服务进程被系统杀死，核心业务全面不可用。

#### 根因

1. 业务死循环、复杂算法、大量循环计算；
2. 大量锁竞争、CAS自旋消耗CPU；
3. 频繁FullGC，GC线程占满CPU；
4. 正则回溯、大量字符串处理；
5. 热点接口大量请求，业务逻辑太重；
6. 序列化/反序列化消耗大量CPU。

#### 排查手段（面试必说）

```shell
top          # 看CPU高的进程pid
jstack pid   # 打印线程栈，找占用CPU高业务线程
jstat -gc pid 1000  # 看GC情况，区分业务CPU还是GC导致CPU高
jmap‑histo pid # 看对象分布
```

#### 解决方案

1. 定位死循环、低效算法，优化业务代码；
2. 减少锁竞争，缩小锁粒度，避免空自旋；
3. 优化序列化：使用Hessian2/Protobuf替代JSON，减少序列化开销；
4. 缓存计算结果，避免重复计算；
5. 限流降级，拦截大流量，降低业务计算压力；
6. GC调优，如果是GC导致CPU高，优先优化内存对象。

> 面试追问：top看到CPU100%，你第一步做什么？
> 答：先区分是业务线程消耗，还是GC线程消耗。jstack看线程，jstat看GC指标。

#### 解决方案

- 排查并修复死循环：通过代码评审、线程分析工具（如JProfiler），定位死循环代码，修复逻辑缺陷；增加循环次数限制、超时控制，避免无限循环。
- 优化GC性能：减少短生命周期对象创建，使用对象池复用对象；合理配置JVM参数（如堆内存大小、GC策略），减少Full GC频率；避免大对象频繁创建与销毁，采用分批处理、压缩存储。
- 优化序列化操作：选择高效的序列化框架（如ProtoBuf替代JSON），减少序列化耗时；对大对象进行分片序列化，避免一次性序列化消耗过多CPU；缓存序列化结果，避免重复序列化。
- 优化正则表达式：简化复杂正则，避免嵌套量词、回溯匹配；使用预编译正则表达式（Pattern.compile），减少重复编译消耗；对高频正则匹配场景，采用字符串匹配替代正则。
- 监控与扩容：实时监控CPU利用率、GC频率，设置预警阈值；CPU长期高负载时，优化代码逻辑或对服务器进行水平扩容，分担CPU压力。

### 2 内存耗尽/溢出 OOM 

#### 现象

堆内存持续上涨不释放，最终抛出`java.lang.OutOfMemoryError`；服务直接崩溃重启。细分：堆OOM、元空间OOM、直接内存OOM。

#### 核心本质

应用内存资源耗尽，堆内存、元空间、直接内存、线程资源等达到上限，JVM 无法分配新内存，直接抛出 OOM 崩溃。

#### 分类&成因

1. **Java heap space**
   堆对象过多、大对象、内存泄漏、缓存无过期、集合无限扩容。
2. **Metaspace 元空间溢出**
   动态生成类过多、频繁热部署、反射/代理滥用、大量动态字节码。
3. **直接内存 OOM**
   Netty、NIO 未手动释放 DirectBuffer、堆外内存不回收。
4. **线程过多 OOM**
   无限制创建原生线程，线程栈内存耗尽。

#### 危害

服务宕机，业务中断；重启瞬间流量全部打过来，雪崩。

服务直接崩溃重启、业务中断、接口全部不可用。

#### 根因

1. 内存泄漏：集合List/Map长期持有对象，没有释放；静态集合不断add对象；
2. 一次性加载超大对象，大对象一次性进堆；
3. 缓存无过期淘汰，缓存无限膨胀；
4. Netty直接内存泄漏，NIO未释放Buffer；
5. 元空间溢出：大量动态生成类；
6. 堆设置过小，业务正常对象就占满堆。

#### 排查

`jmap -dump:format=b,file=xxx.hprof pid` 导出堆dump文件，MAT工具分析，找大对象、泄漏对象。

#### 解决方案

1. 集合用完及时清理，不要用static集合做缓存；
2. 使用带淘汰策略缓存：Caffeine设置maximumSize、过期时间，LRU淘汰；
3. 避免一次性查询全量数据库数据，分页查询；
4. Netty开发注意释放DirectBuffer；堆外内存手动释放，Netty 资源规范关闭；
5. JVM参数合理配置堆、元空间、直接内存大小；
6. OOM自动dump，方便事后排查；线上监控内存、堆快照排查，定位大对象/泄漏点。
7. 设置监控堆内存使用率告警，内存持续上涨提前预警。
8. 避免创建超大对象、批量分批处理数据；
9. 禁止无限制新建线程，统一使用线程池；

> 注意：内存泄漏是越跑内存越高；内存溢出是内存不够直接OOM。



### 内存泄漏

#### 核心本质

**无用对象无法被 GC 回收**，长期常驻内存，内存占用持续上涨，最终触发 OOM。

#### 常见成因

1. 静态集合（static Map/List）长期存放数据，不主动清理；
2. **ThreadLocal 使用后不 remove**，线程复用导致强引用残留；
3. 线程池核心线程常驻，绑定业务对象无法回收；
4. 数据库、Redis、MQ 等连接资源未关闭，连接持有对象；
5. 匿名内部类、回调、长生命周期对象短对象强引用绑定。

#### 危害

内存缓慢上涨、老年代塞满、FullGC 频繁、最终 OOM 宕机。

#### 解决方案

- 静态容器手动定时清理过期数据；
- ThreadLocal 使用完必须 `remove()`，避免内存泄漏；
- 资源使用 try-with-resources 自动关闭；
- 合理设置线程池参数，避免任务强引用堆积；
- 定期 dump 堆内存，MAT 分析泄漏对象。



### 内存占用过高

#### 核心成因

- 本地缓存无上限：使用HashMap等自定义本地缓存，未设置容量上限和淘汰策略，缓存数据持续堆积，占用大量堆内存。
- 大对象常驻内存：接口处理过程中创建超大对象（如超大JSON字符串、字节数组、批量查询结果集），且这些对象长期被引用，无法被GC回收。
- 缓存堆积：本地缓存与分布式缓存双重缓存，未做数据同步和淘汰，导致缓存数据冗余、堆积；缓存未设置过期时间，无用数据长期占用内存。
- JVM参数配置不合理：堆内存（Xms、Xmx）设置过大或过小，过大导致GC耗时增加，过小导致内存不足，频繁触发GC；元空间、栈内存配置不当，间接导致内存占用异常。
- 内存泄漏：集合类未及时清空、静态变量持有大对象、资源未关闭（如IO流、线程），导致对象无法被GC回收，长期占用内存。

#### 造成危害

内存占用持续升高，触发频繁GC，导致CPU占用飙升、服务卡顿；内存不足时引发内存溢出（OOM），服务进程崩溃；大对象占用内存导致内存碎片化，降低内存利用率，进一步加剧内存压力。

#### 解决方案

- 优化本地缓存：使用有淘汰策略的本地缓存框架（如Caffeine、Guava Cache），设置容量上限和过期时间，避免缓存堆积；核心缓存下沉至Redis，减少本地内存占用。
- 控制大对象：避免创建不必要的大对象；大对象拆分、分页处理，减少单次内存占用；使用压缩存储（如GZIP压缩字符串），降低大对象内存占用。
- 清理缓存冗余：统一缓存策略，避免本地缓存与分布式缓存数据冗余；定期清理无用缓存、过期缓存，释放内存资源；实现缓存数据同步，避免缓存不一致导致的冗余存储。
- 合理配置JVM参数：根据服务器内存大小，设置合适的堆内存（Xms=Xmx，避免内存抖动）；调整GC策略（如G1、ZGC），优化GC回收效率；根据业务需求配置元空间、栈内存大小。
- 排查内存泄漏：使用内存分析工具（如MAT、JProfiler），定位内存泄漏点；及时清空无用集合、释放静态变量引用；关闭所有打开的资源（IO流、数据库连接等），避免资源泄漏叠加内存压力。

### 3 GC频繁

#### 现象

`jstat‑gc`看到YGC频繁，YGC次数暴涨，GC时间占比高；STW停顿变长；RT抖动，偶发超时；CPU被GC线程吃掉。
> 分两种：YGC频繁、FullGC频繁。

#### 危害

STW停顿，业务线程暂停，接口随机抖动；CPU飙升；严重时OOM。

#### 根因

1. 大量短命临时对象疯狂产生（循环内创建对象、循环字符串拼接）；
2. 大对象过多，直接进入老年代；
3. 老年代碎片化，触发FullGC；
4. 内存泄漏，老年代持续涨；
5. 堆内存设置过小。

#### 排查

`jstat -gcutil pid 1000`，观察YGC、YGCT、FGC、FGCT。

#### 解决方案

1. 减少循环内创建对象，复用对象；
2. 字符串使用StringBuilder，不要循环+拼接；
3. 优化业务，减少临时对象；
4. 调整JVM新生代大小，适配业务对象生命周期；
5. 避免大对象，分批处理；
6. 修复内存泄漏；
7. 优先使用G1/ZGC降低STW停顿。

> 面试区分：YGC频繁大多是短命对象多；FullGC频繁优先排查内存泄漏、大对象、元空间。



### 频繁 Full GC / GC 长时间停顿

#### 核心本质

老年代内存持续不足、堆内存不合理、内存泄漏，导致频繁触发 Full GC；GC 标记整理耗时过长，STW 停顿严重。

#### 成因

1. 内存泄漏导致老年代持续被占满；
2. 大对象直接进入老年代，频繁触发扩容与回收；
3. 年轻代过小，MinorGC 频繁，晋升到老年代压力大；
4. 垃圾收集器选择不当，STW 时间过长；
5. 元空间、堆外内存占用过高，挤压堆空间。

#### 危害

- 业务线程长时间 STW 暂停；
- CPU 飙高、接口 RT 暴涨、超时、服务假死；
- 集群整体吞吐量暴跌，引发上游雪崩。

#### 解决方案

- 优化 JVM 参数：合理划分年轻代/老年代，调整晋升阈值；
- 改用低延迟收集器：G1、ZGC、Shenandoah；
- 杜绝内存泄漏、控制大对象产生；
- 优化代码：避免短生命周期大集合、对象频繁创建；
- 监控 GC 次数、停顿时间、GC 耗时告警。

### 4 线程池耗尽

#### 现象

线程池队列满，拒绝策略触发抛出`RejectedExecutionException`；任务堆积，大量任务排队；接口大量超时。
> 包含：Tomcat业务线程池、自定义业务线程池、Feign线程池。

#### 危害

新任务直接拒绝报错；任务堆积，内存上涨；下游慢会拖垮整个线程池。

#### 根因

1. 下游接口DB慢，线程阻塞等待，线程被占住无法释放；
2. 线程池核心/最大线程数设置过小；
3. 队列设置过大：任务堆积，内存暴涨，不会触发拒绝；
4. 没有设置超时时间，线程长时间阻塞；
5. 线程泄露：线程池任务里面无限阻塞，线程永不释放。

#### 排查

`jstack pid`，查看线程池线程状态，大量WAITING/BLOCKED。

#### 解决方案

1. **所有调用下游必须设置超时时间**（Feign、RestTemplate、MyBatis数据库）；
2. 合理线程池参数：队列不要设置无界队列！无界队列会直接导致线程数永远到不了max，任务无限堆积；
3. 线程池隔离：不同业务使用不同线程池，慢接口不占用核心业务线程池；
4. 拒绝策略自定义，记录日志告警，不要直接AbortPolicy抛异常就完事；
5. 监控线程池活跃线程数、队列长度，告警；
6. Sentinel线程池隔离，保护核心接口。

> ⚠️高频坑：很多同学写`new ThreadPoolExecutor`用`LinkedBlockingQueue()`无参构造，队列无限大，max线程完全失效，线上事故来源。

### 5 连接池耗尽

#### 现象

拿不到连接，获取连接超时；例如Druid数据库连接池、Redis连接池、http连接池，报错`wait millis xxx active:xxx max:xxx`。

#### 核心本质

核心线程+最大线程全部打满，阻塞队列塞满，新任务无法提交，触发拒绝策略，接口阻塞报错。

#### 成因

1. 线程池参数配置不合理：核心线程、队列过小；
2. 任务执行阻塞：包含慢SQL、第三方超时、同步等待；
3. 任务无超时，线程长时间卡死不释放；
4. 无界队列滥用，任务无限堆积，内存打爆；
5. 业务手动新建线程，资源不可控。

#### 危害

大量请求阻塞等待连接，接口超时；服务雪崩。

接口请求排队、大量超时、线程堆积、CPU 飙升、服务瘫痪。

#### 根因

1. 连接没有归还，连接泄漏；try‑with‑resource没写，异常场景连接没close；
2. max连接数设置太小，并发上来直接打满；
3. 下游DB/Redis慢，连接长时间占用不释放；
4. 没有设置空闲连接超时，坏连接残留在池子里。

#### 排查

Druid监控页面，查看活跃连接数；看连接池metrics指标。

#### 解决方案

1. 使用try‑with‑resource自动关闭资源，保证无论正常异常都归还连接；
2. 设置合理max连接，数据库连接池不要设置过大，一般20‑50；
3. 配置空闲连接超时、最大存活时间，剔除坏连接；
4. 业务SQL优化，减少DB执行时间，缩短连接持有时间；
5. 监控活跃连接数，打满告警；
6. 熔断降级，下游慢的时候不再继续拿连接访问。

> 面试追问：数据库连接池是不是越大越好？不是。数据库服务端能承载连接有限，连接太多会数据库上下文切换，性能下降。

#### 解决方案

- 严格自定义线程池，禁止使用 Executors 原生工具类；
- 合理配置核心线程、最大线程、阻塞队列、拒绝策略；
- 所有异步任务增加超时时间、熔断降级；
- 耗时任务隔离线程池，核心业务与非核心业务池隔离；
- 监控线程池活跃线程数、队列积压、拒绝次数。

### 6 文件句柄耗尽

#### 现象

报错`Too many open files`；无法创建socket、打开文件；新建连接失败。

#### 危害

无法建立网络连接，无法读写文件；服务大量异常。

#### 根因

1. 文件流、InputStream、OutputStream没有关闭，句柄泄漏；
2. Socket连接没有关闭；Netty连接泄漏；
3. linux系统ulimit‑n文件句柄上限设置过小。

#### 排查

```shell
lsof -p pid | wc -l #查看进程打开句柄数量
cat /proc/pid/limits #查看进程限制
```

#### 解决方案

1. IO流全部使用try‑with‑resource自动关闭；
2. Socket、网络连接使用连接池，不要每次新建；用完关闭；
3. 调高服务器ulimit‑n；
4. 监控进程打开文件句柄数，告警。

### 7 磁盘IO打满

#### 现象

iowait很高；磁盘读写100%；写文件、写日志很慢；数据库IO等待高。

#### 核心成因

- 日志疯狂打印：业务代码中无限制打印日志（如循环中打印日志、 debug级日志在线上环境开启），日志文件快速增大，占用大量磁盘空间，同时引发磁盘IO频繁读写。
- 慢日志堆积：数据库、Redis等中间件开启慢日志后，未及时清理，慢日志文件持续堆积；慢日志打印频率过高，超出磁盘IO处理能力。
- 临时文件堆积：服务运行过程中生成大量临时文件（如文件上传临时文件、导出报表临时文件），未及时删除，占用磁盘空间；临时文件读写频繁，加剧磁盘IO压力。
- 磁盘读写效率低：使用机械硬盘（HDD），读写速度慢，高并发场景下磁盘IO无法及时处理请求；磁盘分区不合理，核心业务磁盘与非核心业务磁盘共用，导致IO竞争。
- 批量读写操作：频繁进行大量文件读写、数据库批量写入，超出磁盘IO承载能力，导致IO队列堆积。

#### 造成危害

写日志阻塞；DB查询缓慢，RT暴涨；MQ刷盘慢消息堆积。

磁盘空间被占满，服务无法生成新的日志、临时文件，导致服务异常；磁盘IO读写阻塞，服务响应变慢、接口超时；数据库、中间件因IO阻塞无法正常读写数据，引发业务中断；严重时磁盘损坏，导致数据丢失。

#### 根因

1. 日志打印量巨大，大量debug日志线上开启；
2. 大量大文件写入；
3. 数据库大量刷盘、大量刷redo/undo log；
4. 磁盘慢盘，磁盘硬件故障。

#### 排查

```shell
iostat -x 1
iotop
```

#### 解决方案

1. 线上关闭debug日志，合理设置日志级别；日志异步输出；
2. 日志滚动策略，限制单文件大小，自动清理旧日志；
3. 减少不必要磁盘写入，尽量内存处理；
4. DB优化，减少刷盘压力；
5. 监控磁盘IO使用率、iowait告警。

#### 解决方案

- 规范日志打印：线上环境关闭debug级日志，仅保留info、warn、error级日志；避免循环中打印日志，控制日志打印频率；采用日志轮转策略（如按天、按大小轮转），自动清理过期日志。
- 清理慢日志与临时文件：定期清理数据库、Redis等中间件的慢日志，设置慢日志保留期限；及时删除服务生成的临时文件，设置临时文件自动清理机制（如定时任务删除）。
- 提升磁盘IO性能：更换为固态硬盘（SSD），提升读写速度；对磁盘进行分区，核心业务（如数据库）与非核心业务（如日志、临时文件）使用独立磁盘，避免IO竞争。
- 优化批量读写：批量文件读写采用异步化、分批处理，避免一次性占用大量IO资源；数据库批量写入采用批量插入语句，减少IO次数；使用缓存减少磁盘读写频率。
- 监控与预警：实时监控磁盘空间使用率、磁盘IO读写速度，设置预警阈值；磁盘空间不足时，及时清理无用文件或扩容磁盘；定期检查磁盘健康状态，避免磁盘损坏。

### 8 网络带宽耗尽/打满

#### 现象

网卡流量打满；网卡in/out接近上限；网络数据包丢包，RT高，大量超时。

#### 核心成因

- 大Key传输：Redis等缓存中存在大Key（MB级及以上），高并发场景下大量请求获取大Key，导致网卡带宽被占满；大Key序列化后传输，进一步增加带宽消耗。
- 批量传输：服务间批量传输大量数据（如批量同步数据、批量导出报表），单次传输数据量过大，超出网卡带宽承载能力。
- 频繁大报文交互：服务间频繁传输大报文（如超大JSON、字节流），交互频率高，叠加起来占用大量带宽；无数据压缩机制，报文体积过大。
- 无效流量占用：恶意爬虫、无效请求频繁发起，传输大量无用数据，占用网卡带宽；跨机房调用、公网传输，带宽损耗大，加剧带宽压力。
- 带宽配置不足：服务器网卡带宽配置过低，无法满足高并发、大数据量传输需求；多个服务共享网卡，带宽竞争激烈。

#### 造成危害

请求响应缓慢，数据包丢失，重试风暴，进一步加剧带宽压力。

网卡带宽被占满，服务间数据传输超时、中断，跨服务调用失败；请求无法正常接收和响应，用户访问卡顿、失败；带宽拥堵导致网络延迟飙升，引发服务连锁超时；严重时导致服务器与外界通信中断，服务彻底不可用。

#### 根因

1. 接口返回超大报文，一次性返回大量数据；
2. 大量文件下载；
3. 爬虫大量拉取数据；
4. 大量重试，流量放大。

#### 排查

`iftop / sar‑n DEV`

#### 解决方案

1. 接口不要返回大报文，分页返回；避免一次性返回全量列表；
2. 大文件走对象存储，不要应用服务直接输出；
3. 网关限流，限制单接口流量；
4. 开启压缩gzip；
5. 限制重试次数，关闭无效重试，防止重试风暴。

#### 解决方案

- 优化大Key：拆分Redis等缓存中的大Key，将大Value拆分为多个小Key，减少单次传输数据量；对大Key进行压缩存储，传输时采用数据压缩（如GZIP），降低带宽消耗。
- 控制批量传输：批量数据传输采用分批、异步传输，避免单次传输大量数据；核心批量传输场景，选择低峰期进行，减少带宽压力。
- 优化报文交互：减少服务间大报文交互频率，合并重复请求；对传输数据进行压缩，使用高效的序列化框架，减小报文体积；避免传输无用数据，精简传输字段。
- 过滤无效流量：拦截恶意爬虫、无效请求，减少无用数据传输；核心服务使用内网通信，避免公网传输的带宽损耗；对跨机房调用进行带宽控制，避免带宽滥用。
- 提升带宽配置与监控：根据业务需求，提升服务器网卡带宽配置；核心服务使用独立网卡，避免带宽竞争；实时监控网卡带宽使用率、网络延迟，设置预警阈值，及时排查带宽异常。

### 9 Socket资源耗尽

#### 现象

端口耗尽，`Cannot assign requested address`；无法新建出站连接；大量TIME_WAIT。

#### 危害

无法对外建立http、redis、db连接，大量请求失败。

#### 根因

1. 短连接：每次调用下游都新建Socket，调用结束进入TIME_WAIT状态，占用端口；
2. 没有使用连接池，每次http请求新建连接；
3. Linux内核tcp参数不合理。

#### 排查

`netstat ‑ant |grep TIME_WAIT |wc‑l`

#### 解决方案

1. **必须使用HTTP连接池，复用连接，不要每次新建Socket**；
2. Redis、DB全部使用连接池；
3. Linux内核调优：tcp_tw_reuse，复用TIME_WAIT端口；
4. 缩短重试次数，避免大量失败请求疯狂新建socket。

> 面试重点：TIME_WAIT是什么，为什么会耗尽端口，怎么解决。核心：不要频繁创建短连接，用连接池复用。

### 10 临时对象暴增

#### 现象

新生代大量对象创建，YGC频繁，GC停顿变长，CPU抖动；内存占用快速上升。

#### 根因

1. 循环内部不停new对象；循环字符串拼接 `+`；
2. 接口大报文序列化反序列化产生大量临时POJO；
3. 流式查询循环中创建大量对象；
4. 频繁装箱拆箱（Integer等自动装箱）。

#### 危害

GC频繁，STW，接口RT抖动，CPU高，极端情况OOM。

#### 排查

jstat‑gc观察YGC次数；MAT看新生代对象。

#### 解决方案

1. 循环外提前创建对象，循环内复用；
2. 循环拼接字符串用StringBuilder；
3. 减少自动装箱，优先使用基础类型；
4. 优化序列化，减少中间对象生成；
5. 大报文做分页，不要一次性加载全部数据；
6. 对象池复用重对象（例如Netty缓冲区）。

### 面试速记总结

1. **CPU耗尽**：死循环/锁自旋/GC频繁 → jstack+jstat定位，优化算法、缓存、GC
2. **内存耗尽OOM**：内存泄漏、缓存不淘汰、大对象 → dump+MAT分析，缓存加淘汰，分页查询
3. **GC频繁**：大量短命临时对象 → 减少循环new对象，调JVM参数
4. **线程池耗尽**：下游慢、无界队列、无超时 → 禁止无界队列、设置超时、线程池隔离
5. **连接池耗尽**：连接泄漏、max太小、下游慢 → try‑with‑resource，合理max，优化慢SQL
6. **文件句柄耗尽**：IO/Socket未关闭、ulimit小 → try‑with‑resource，调高ulimit
7. **磁盘IO打满**：日志过多、DB刷盘 → 调整日志级别，异步日志
8. **带宽耗尽**：大报文、下载 → 分页、gzip，大文件走对象存储
9. **Socket耗尽(TIME_WAIT)**：频繁短连接 → 使用连接池复用连接
10. **临时对象暴增**：循环new、装箱 → 对象复用，StringBuilder，避免装箱

## 3 服务调用类问题

1. 服务雪崩
2. 服务级联失败
3. 服务依赖故障
4. 下游服务不可用
5. 同步调用阻塞
6. 调用链过长
7. RPC 超时
8. RPC 重试风暴
9. 网络抖动
10. DNS 解析异常

服务调用类问题的本质是：

```text
服务之间存在依赖关系
```

当某个服务出现问题时，可能会通过 **调用链传播**，最终导致 **系统整体故障**。

典型链路：

```
用户请求
   ↓
网关
   ↓
服务A
   ↓
服务B
   ↓
服务C
   ↓
数据库
```

任何一个节点出现问题都可能影响整个系统。

服务调用类问题本质可以归纳为 **四大类风险**：

| 类别         | 本质问题            |
| ------------ | ------------------- |
| 依赖故障     | 下游服务异常        |
| 调用链问题   | 调用链过长          |
| 调用策略问题 | 同步阻塞 / 重试风暴 |
| 网络问题     | 网络抖动 / DNS异常  |

最终结果通常是：

```
服务响应变慢
↓
线程池耗尽
↓
服务雪崩
```

> 面试答题模板：**现象 → 危害 → 根因 → 解决方案 + Java落地实践 → 排查要点 + 面试坑点**，适配20k+后端面试，和前面流量、资源耗尽题目连贯。

### 1 服务雪崩

#### 现象

某个服务故障，故障一层层向外扩散，整个调用链路大面积瘫痪，大量接口报错、超时，集群大部分服务不可用。

#### 危害

整个业务系统瘫痪，大量用户请求失败，业务完全不可用。

#### 根因

1. 下游服务宕机，上游大量请求堆积，线程/连接池被占满；
2. 没有保护机制，上游不停调用故障下游；
3. 无超时、无熔断，故障向上传导；
4. 流量没有限流，故障后持续大量请求涌入，加速恶化。

#### 解决方案

1. **熔断**：Sentinel/Hystrix，下游失败达到阈值直接熔断，不再发起调用，返回降级结果；
2. **超时控制**：RPC、HTTP调用必须配置超时，不能无限阻塞；
3. **限流**：入口限流，阻止过量流量进入系统；
4. **线程/信号量隔离**，故障下游不耗尽本服务资源；
5. **降级**：非核心链路直接返回兜底数据，牺牲非核心保核心；
6. 监控告警，下游错误率异常及时告警。

> 面试区分：雪崩是**最终结果**；级联失败是故障传播的过程。

### 2 服务级联失败

#### 现象

A调用B，B调用C，C故障 → B大量超时堆积 → B故障 → 进而A也故障。故障沿着调用链一层层向上传递。

#### 危害

单个节点故障扩散到整条链路，多个服务相继异常，是服务雪崩的发生过程。

#### 根因

1. 没有熔断机制，下游报错依然持续发起调用；
2. 调用没有超时，线程被阻塞耗尽；
3. 资源没有隔离，下游慢把本服务线程、连接池耗尽；
4. 失败后不断重试，放大故障。

#### 解决方案

1. RPC必须配置合理超时时间；
2. 熔断机制：下游错误率到达阈值，快速失败，切断调用；
3. 资源隔离（线程池隔离优先），不同下游分配独立线程池；
4. 限制重试次数，关闭无效重试；
5. 强弱依赖梳理：区分强依赖、弱依赖，弱依赖失败直接降级，不阻塞主流程。

> 面试话术：级联失败本质是**故障向上传导**，核心手段就是：超时、熔断、隔离、降级，切断故障传播链路。

### 3 服务依赖故障

#### 现象

业务依赖的服务、中间件出问题，自身服务本身代码没问题，但因为依赖出问题，接口大量报错超时。

> 依赖可以是RPC服务、Redis、DB、MQ、第三方http接口。

#### 危害

自身服务CPU内存看起来正常，但业务大量失败；容易误判为本服务bug。

#### 根因

1. 依赖服务宕机、慢、抖动；
2. 依赖中间件集群故障；
3. 依赖接口变更，返回格式异常；
4. 没有做依赖可用性保护。

#### 解决方案

1. 梳理强弱依赖：
   - 强依赖：必须成功才能执行业务；
   - 弱依赖：失败不影响主流程，直接降级丢弃；
2. 对所有依赖配置超时、重试、熔断；
3. 弱依赖使用异步调用，不阻塞主流程；
4. 依赖健康监控：监控每个依赖的RT、错误率；
5. 核心依赖做多副本、多可用区；
6. 配置降级兜底逻辑。

> 面试坑：很多同学全部当成强依赖，所有调用都阻塞主流程，弱依赖一定要异步或者降级。

### 4 下游服务不可用

#### 现象

下游服务宕机、进程挂掉、实例全挂，RPC调用返回连接失败、no provider、连接拒绝。

#### 危害

本服务大量线程卡在调用下游，线程池耗尽，引发级联失败。

#### 根因

下游实例全部宕机；注册中心无可用提供者；网络不通；下游发布全量下线。

#### 解决方案

1. RPC框架（Dubbo）配置超时、失败重试，注意重试次数不能太大；
2. 熔断：下游不可用比例高，直接熔断，快速失败；
3. 注册中心及时剔除不健康实例；开启健康检查；
4. 降级兜底，下游不可用时返回缓存/默认数据；
5. 多实例部署，下游不能单节点；
6. 监控提供者数量、调用错误率告警。

> 注意：重试只适合读请求，写请求重试要注意幂等，防止重复写。

### 5 同步调用阻塞

#### 现象

同步等待下游返回，下游慢，本服务业务线程一直阻塞等待，线程被大量占用，新请求没有线程处理。

#### 危害

线程池快速耗尽；接口RT飙升；引发级联失败。

#### 根因

1. 同步RPC/HTTP调用，没有设置超时；
2. 下游响应慢，业务线程原地等待；
3. 一个主流程里面串行调用多个下游。

#### 解决方案

1. **强制设置调用超时时间**，不能无限等待；
2. 可以并行调用的使用CompletableFuture异步并行，减少耗时；
3. 非核心逻辑改成异步：RocketMQ/Kafka异步处理，不阻塞主链路；
4. 资源隔离，调用下游使用独立线程池；
5. 超时后快速失败，不继续阻塞。

> 面试重点：同步阻塞最大风险是**占住线程不释放**，线程是宝贵资源。

### 6 调用链过长

#### 现象

一次请求，串行跨多服务调用，A→B→C→D→E，链路很深；整体RT等于所有节点RT累加。

#### 危害

整体RT很高；链路任意一个节点抖动，整体就抖动；故障排查复杂；一处失败整条请求失败。

#### 根因

微服务拆分过细；接口设计不合理，串行嵌套调用；前端一次请求聚合大量数据。

#### 解决方案

1. 接口聚合层（BFF层），前端请求收敛，减少前端多次调用；
2. 能并行就不要串行，CompletableFuture并行RPC；
3. 部分场景本地缓存，减少跨服务远程调用；
4. 服务内聚合数据，不要把压力交给前端；
5. 适当做服务合并，避免过度拆分；
6. 链路追踪SkyWalking/Pinpoint，方便定位链路慢节点。

> 面试追问：微服务是不是拆的越细越好？不是，拆分过细会带来调用链变长，网络开销上升，维护复杂度上升。

### 7 RPC超时

#### 现象

Dubbo / SpringCloud OpenFeign调用抛出超时异常，`ReadTimeout`。

#### 危害

业务报错；如果没有处理，不断重试，放大流量；线程阻塞堆积。

#### 根因

1. 下游服务处理慢；
2. 网络延迟高；
3. 超时时间设置过小；
4. 下游线程池打满，请求排队。

#### 解决方案

1. 合理设置超时，不要设置过大也不要过小；超时时间结合业务可接受RT；
2. 区分读、写接口设置不同超时；
3. 超时一定要做异常捕获处理，不能直接抛给用户；
4. 配合熔断，大量超时触发熔断；
5. 优化下游性能，减少下游处理耗时；
6. 超时监控，超时占比告警。

> 面试坑：超时时间不是越大越好，超时设置太大，线程会长时间被占用，容易耗尽线程池。

### 8 RPC重试风暴

#### 现象

下游出现少量失败，上游开启重试，大量请求自动重试，瞬间流量放大几倍，把已经故障的下游压垮。

#### 危害

下游压力倍增，故障加剧；故障扩散，恶性循环。

#### 根因

1. RPC默认开启重试，重试次数设置大；
2. 超时就触发重试，大量请求同时重试；
3. 没有熔断，下游已经故障还继续重试；
4. 写接口没有做幂等，重试带来重复数据。

#### 解决方案

1. **写请求关闭重试，读请求有限重试**；
2. 重试次数控制1‑2次，不要设置很大；
3. 添加重试间隔、退避策略（指数退避），不要立刻并发重试；
4. 熔断优先：下游错误率高直接熔断，不再重试；
5. 接口保证幂等性，防止重试造成重复新增、重复扣款；
6. 禁止业务代码手动写for循环重试。

> 高频面试题：什么是重试风暴，怎么避免？

### 9 网络抖动

#### 现象

网络不稳定，偶发的超时、丢包，不是完全断网，时好时坏；偶现RPC超时，间歇性报错，复现困难。

#### 危害

偶发业务异常；日志大量零散超时；很难稳定复现，排查困难；容易误判为业务代码问题。

#### 根因

机房网络波动、交换机抖动、跨机房调用、网卡不稳定、网络拥塞。

#### 解决方案

1. 做好重试：只对读请求做有限次数重试，指数退避；
2. 熔断保护，抖动持续恶化就熔断；
3. 尽量同机房调用，避免跨机房跨地域；
4. 链路追踪记录网络耗时，区分是网络慢还是业务慢；
5. 监控网络丢包率、RT抖动指标告警；
6. 设置合理超时，不要过小，避免网络轻微抖动就大量失败。

### 10 DNS解析异常

#### 现象

域名解析失败、解析出错误IP、DNS解析超时；调用第三方域名服务偶发失败。

#### 危害

服务无法连接外部域名；偶发调用失败；大量请求报错。

#### 根因

DNS服务器故障、DNS缓存污染、DNS缓存过期、解析超时。

#### 解决方案

1. JVM开启DNS缓存，合理配置缓存时间，避免频繁解析；
2. HTTP客户端（OkHttp）自带DNS缓存；
3. 配置多DNS服务器，做容灾；
4. 核心第三方接口可配置hosts，绕过DNS解析；
5. 捕获解析异常，配置有限重试；
6. 监控域名解析异常告警。

### 面试速记背诵版

1. **服务雪崩**：多服务整体瘫痪结果 → 超时+熔断+限流+降级切断故障传播
2. **服务级联失败**：故障顺着调用链向上传递过程 → 隔离、熔断、强弱依赖
3. **服务依赖故障**：自身没问题，依赖挂了 → 梳理强弱依赖，弱依赖降级异步
4. **下游服务不可用**：下游实例挂掉无提供者 → 熔断降级、多实例、健康检查
5. **同步调用阻塞**：线程卡死等待下游 → 设置超时，非核心改异步、并行调用
6. **调用链过长**：微服务拆分太深，串行调用RT叠加 → BFF聚合、并行调用、本地缓存
7. **RPC超时**：调用超过指定时间失败 → 合理超时配置，捕获异常，配合熔断
8. **RPC重试风暴**：失败大量重试放大流量 → 写请求关闭重试，限制次数，熔断优先，接口幂等
9. **网络抖动**：网络偶发丢包超时 → 读请求有限重试，尽量同机房部署
10. **DNS解析异常**：域名解析出错 → DNS缓存、多DNS、核心可配置hosts

## 4 数据库问题

1. 慢 SQL
2. 大事务
3. 锁竞争
4. 行锁 / 表锁
5. 死锁
6. 连接数打满
7. 热点行
8. 写放大
9. 索引失效
10. 数据库主从延迟

数据库问题通常是 **高并发系统最容易成为瓶颈的一层**，因为数据库通常是：

```text
集中式资源
```

当访问量过高或设计不合理时，很容易成为 **系统性能瓶颈或故障源**。

> 答题范式：**现象 → 危害 → 根因 → 解决方案 + Java业务落地 → 排查手段 → 面试坑点**，20k+后端高频，MySQL为主，结合Java业务代码，不止讲数据库原理，还要讲应用层怎么做。

### 1 慢SQL

#### 现象

SQL执行时间长，数据库RT高；业务接口RT飙升；大量慢SQL堆积，DB CPU、IO飙升；慢查询日志大量记录。

#### 核心本质

SQL 未走索引、索引设计不合理、SQL写法糟糕，导致全表扫描、磁盘IO暴涨、CPU打满。

#### 产生原因

1. 字段函数运算、隐式类型转换、左右模糊查询，导致**索引失效**；
2. 索引区分度低、联合索引违背最左匹配原则；
3. 大表无索引、数据量百万级以上全表扫描；
4. limit 超大分页、多表关联无合理关联条件；
5. 批量批量in数据过多、order by/group by 无索引排序。

#### 危害

数据库连接被长时间占用，连接池耗尽；大量请求排队；拖垮整个数据库实例，引发业务雪崩。

- 数据库CPU、IO 100%，整体实例性能下降；
- 行锁等待、锁竞争加剧，引发阻塞；
- 单条慢SQL拖垮整个库，影响所有业务；
- 接口响应极慢，请求堆积。

#### 根因

1. 缺少索引、索引失效；
2. 查询返回大量数据，select *、未分页；
3. 复杂多表join、子查询；
4. 业务逻辑放到SQL里做，大量计算；
5. 大表扫描，全表扫描；
6. 事务过大，锁持有时间变长。

#### 排查

1. MySQL慢查询日志slow‑query‑log；
2. `explain`看执行计划，type、rows、Extra；
3. show processlist / show full processlist 看正在执行慢SQL；
4. 业务监控看DB RT。

#### 解决方案

1. explain分析SQL，合理建立索引；避免索引失效；
2. 禁止select *，只查需要字段；分页limit，避免一次性拉取全量数据；
3. 减少大表join，复杂逻辑放到Java应用层处理；
4. 大结果集分批查询，不要一次性加载到内存；
5. 上线前SQL评审，慢SQL拦截；
6. 读写分离，读压力走从库；
7. 热点查询走Redis缓存，减少DB查询；
8. 监控慢SQL数量告警。

> 面试坑：explain type从优到劣：`system>const>eq_ref>ref>range>index>ALL`，尽量避免ALL全表扫描。

#### 解决方案

1. 合理设计索引，遵循最左匹配、高频查询字段优先建索引；
2. 避免索引失效场景：禁止索引列函数、统一字段类型、避免%前缀模糊；
3. 开启慢查询日志，定时巡检、优化劣化SQL；
4. 大表分页优化、分批查询、避免大in；
5. 读写分离，复杂统计、报表查询走从库。

### 2 事务过大 / 长事务

#### 现象

事务执行时间很长，事务内执行多条DML，包含大量业务逻辑，事务迟迟不commit/rollback。
> Java常见坑：事务方法内部调用RPC、查询Redis、做网络IO，整个网络IO都包裹在事务中。

#### 核心本质

事务开启后，执行链路过长、耗时太久，迟迟不提交/回滚，长时间持有锁与MVCC快照。

#### 产生原因

1. 事务中包含大量查询、循环、文件IO、远程调用；
2. 批量操作不拆分，一次性放入同一个事务；
3. 异常未捕获，事务卡死不结束；
4. 错误使用全局事务，无关业务强行绑定事务。

#### 危害

1. **锁持有时间变长，锁冲突加剧，行锁等待、死锁概率上升**；
2. undo log、redo log膨胀，数据库磁盘暴涨、清理滞后；主从延迟变大；
3. 数据库连接长时间不释放，极易引发连接池耗尽、数据库阻塞。
4. 长事务会阻止MVCC快照回收，产生大量历史版本，占用磁盘导致数据库性能下降。

#### 根因

1. `@Transactional`注解范围过大，把RPC、http调用、大量业务逻辑包进事务；
2. 循环中批量处理大量数据，一次性在同一个事务；
3. 代码异常没有及时回滚；
4. 业务逻辑写在事务内部。

#### 解决方案

1. **事务尽量短小，只把DML数据库操作放在事务内**，RPC、外部调用移出事务，禁止事务内调用第三方接口、MQ、文件操作；
2. 大批量操作拆分，分批次小事务提交；
3. 避免在事务内做查询大结果集；
4. 编程式事务手动控制事务边界，不要无脑直接加@Transactional；
5. 监控长事务，及时拦截告警，监控事务执行耗时。
6. 设置事务超时时间，自动回滚卡死事务；

> 高频面试题：为什么事务里面不能调用RPC？答：RPC网络耗时不可控，拉长事务持有锁和连接时间，带来锁竞争、主从延迟、连接耗尽风险。

### 3 锁竞争

#### 现象

大量事务互相争夺锁；大量`lock wait timeout`；接口大量超时；数据库出现锁等待。

#### 危害

大量请求阻塞等待锁；RT飙升；业务报错；严重触发死锁。

#### 根因

1. 大事务，锁持有时间久；
2. 并发修改同一批数据（热点行）；
3. 更新没有走到索引，升级表锁；
4. 业务并发高，同时修改相同记录。

#### 解决方案

1. 缩小事务，尽快提交释放锁；
2. 更新语句必须命中索引，保证行锁；
3. 业务尽量避免并发修改同一行热点数据；
4. 调整业务，打散更新，排队、异步削峰；
5. 乐观锁替代悲观锁：版本号`version`；
6. 业务层限流，降低并发写压力；
7. 监控锁等待时间告警。

### 4 行锁 / 表锁

#### 现象

- **行锁**：只锁住符合条件的行；其他行可以正常读写；但并发修改同一行会等待锁。
- **表锁**：锁住整张表，整张表读写阻塞，性能极差。

#### 根因

InnoDB行锁是**索引锁**：更新/删除条件没有命中索引，InnoDB会退化成表锁；
DDL语句会加表锁；MyISAM默认表锁。

#### 危害

表锁：整张表所有DML阻塞，业务大面积不可用；
行锁：热点行并发修改出现锁等待。

#### 排查

`show engine innodb status;`看锁信息。

#### 解决方案

1. update、delete条件字段必须建立索引，避免退化成表锁；
2. 业务尽量少执行DDL，大表DDL用Online DDL；
3. 避免MyISAM引擎，全部使用InnoDB；
4. 热点行做业务层削峰，Redis预扣库存，减少DB并发更新；
5. 大事务及时提交，尽快释放行锁。

> 面试重点：InnoDB行锁不是锁记录，是锁索引！条件没索引，直接表锁，线上重大事故来源。

### 5 死锁

#### 现象

两个及以上事务，互相持有对方需要的锁，互相等待，谁都无法执行；MySQL直接检测死锁，回滚其中一个事务，业务抛出死锁异常。

#### 根因

1. 多个事务以**不同顺序更新多行记录**；
T1：update A，再update B
T2：update B，再update A → 产生死锁。
2. 大事务，锁持有时间长，加大死锁概率。

#### 排查

`show engine innodb status`，查看死锁日志，拿到发生死锁的SQL。

#### 解决方案

1. **统一更新行的顺序**，所有事务更新多行都按相同id顺序；
2. 缩小事务，尽早提交，减少锁持有时间；
3. 尽量避免一个事务同时更新多条竞争激烈记录；
4. 业务捕获死锁异常，做有限次数重试；
5. 降低并发写压力；
6. 监控死锁次数告警，死锁属于严重线上问题。

> 面试话术：死锁4个必要条件：互斥、占有且等待、不可剥夺、循环等待；解决核心破坏循环等待，统一更新顺序。

### 6 数据库连接池耗尽 / 连接数打满

#### 现象

报错`Too many connections`；无法获取数据库连接；Druid拿连接超时。

#### 核心本质

业务获取数据库连接后**长期不释放**，连接池最大连接数被占满，新请求无法获取连接，接口全部阻塞、报错。

#### 产生原因

1. 慢SQL执行时间过长，连接一直占用不归还；
2. **长事务/大事务**，事务迟迟不提交/回滚；
3. 代码异常未捕获，`Connection`、Session 未手动关闭；
4. 批量操作一次性抢占大量连接，无隔离限制；
5. 第三方接口阻塞嵌套在事务内，连接无限等待。

#### 危害

所有业务请求拿不到DB连接，业务全部失败。

- 服务大量请求卡死、超时、线程池积压；
- 全局服务不可用，引发上下游连锁雪崩；
- 数据库TCP连接数暴增，DB负载飙升。

#### 根因

1. MySQL服务端max_connections设置过小；
2. 应用连接池Druid最大连接设置过大，多个应用抢占MySQL服务端连接；
3. 长事务、慢SQL，连接长时间占用不释放；
4. 连接泄漏：代码异常没有归还连接。

#### 解决方案

1. MySQL服务端合理调大max_connections，但不要无限大；
2. 每个应用Druid最大连接不要设置过大，一般20‑50；**数据库服务端连接数是所有应用共享**；
3. 优化慢SQL、大事务，缩短连接占用时间；
4. 使用try‑with‑resource防止连接泄漏；Druid配置连接回收、空闲超时；
5. 多业务实例不要盲目调大连接池max；
6. 监控MySQL当前连接数告警。

> 面试高频坑：很多开发疯狂调大Druid最大连接数，多个实例一起把MySQL服务端连接打满。

#### 解决方案

1. 合理配置连接池参数：最大连接数、空闲超时、获取连接超时；
2. 杜绝慢SQL，设置SQL执行超时时间；
3. 事务尽量短小，避免事务中嵌套远程调用、复杂业务；
4. 统一异常处理，保证连接、资源**finally强制释放**；
5. 监控连接池活跃连接数、等待队列，及时告警。

### 7 热点行

#### 现象

大量并发更新数据库同一行记录，例如商品库存行、订单统计行。

#### 危害

行锁激烈竞争，大量锁等待；DB CPU升高；大量请求超时。

#### 根因

秒杀库存、爆款商品，大量用户并发修改同一数据库行。

#### 解决方案

1. **Redis前置，把大部分并发拦截在DB外面**，Redis扣库存，MQ异步落库；
2. 业务层限流削峰；
3. 行拆分：库存拆成多行，`goods_stock_1、goods_stock_2`，并发分散到多行；
4. 乐观锁：`update stock set num=num‑1,version=version+1 where id=? and version=? and num>0`；
5. 合并写请求，请求合并，减少对DB同一行的并发更新；
6. 避免直接DB并发扣减，把高频写下移到缓存层。

> 区分：热点key是Redis问题；热点行是MySQL数据库同一行并发写。

### 8 写放大

#### 现象

业务少量数据写入，数据库产生大量IO、redo/undo日志，磁盘IO压力很高。

#### 根因

1. 更新大字段，blob大文本；每次更新大字段，整页刷新；
2. 频繁更新同一条记录，频繁产生redo log；
3. 索引过多，写一条数据要更新多个二级索引；
4. 大事务，产生大量undo log；
5. 批量写入，binlog大量日志。

#### 危害

磁盘IO打满；写入QPS上不去；主从同步压力大。

#### 解决方案

1. 大字段拆分到独立表，不要放在高频更新表；
2. 控制索引数量，一张表索引不宜过多；
3. 减少对同一行高频更新；可以做缓存聚合，定时批量刷DB；
4. 拆分大事务，小事务提交；
5. 避免频繁更新；把多次小更新合并成一次更新。

### 9 索引失效

#### 现象

明明建了索引，explain显示全表扫描，索引没有生效。

#### 根因

1. where条件对索引列做函数运算、隐式类型转换；
2. like %xxx 前缀模糊查询；
3. or一侧条件无索引；
4. not in、!=、is not null 容易失效；
5. MySQL优化器判断全表扫描比索引更快，主动放弃索引；
6. 组合索引不满足最左前缀原则。

#### 危害

SQL变成全表扫描，扫描大量行，DB CPU、IO飙升，演变为慢SQL。

#### 解决方案

1. 索引列不要做函数计算，把计算移到Java业务层；
2. 避免隐式类型转换，字段类型和传入参数类型一致；
3. 遵守组合索引最左前缀；
4. 避免前缀%模糊匹配；需要全文检索使用ES；
5. 上线前用explain校验SQL执行计划。

### 10 数据库主从延迟

#### 现象

主库写入完成，从库数据同步有时间差；读写分离场景，刚写完读从库读不到刚插入的数据。show slave status查看Seconds_Behind_Master不为0。

#### 核心本质

主库写入数据后，Binlog同步到从库存在时间差，短时间内从库查询还是旧数据。

#### 产生原因

1. 主库写入QPS过高，Binlog生成速度 > 从库回放速度；
2. 从库机器配置低、SQL单线程回放（MySQL5.7之前）；
3. 大事务、大批量写入，单条Binlog体积过大；
4. 网络带宽不足、主从网络波动；
5. 从库存在慢SQL，占用资源拖累回放。

#### 危害

读写分离业务出现数据不一致；刚写马上读从库，读不到数据；大事务会加剧主从延迟。

- 写主库、立刻查从库，查询不到最新数据；
- 业务逻辑异常、数据展示不一致；
- 严重延迟会导致数据一致性大幅偏差。

#### 根因

1. 主库大事务，binlog一次性下发大量日志，从库回放慢；
2. 从库硬件性能弱于主库；
3. 主库写入QPS很高，从库单线程回放binlog（MySQL5.7开启并行复制）；
4. 大DDL，主库执行完，从库执行DDL耗时久。

#### 解决方案

1. 避免大事务，拆分为小事务，避免大批量一次性写入，减少单条binlog体积；
2. 升级MySQL8.0，开启**并行复制**，提升从库回放能力；
3. 从库硬件配置不能低于主库；优化从库配置、隔离从库慢查询；
4. 读写分离策略：**写后立即读强制走主库**；
5. 关键一致性查询走主库，普通非实时查询走从库；
6. 监控主从延迟时间告警；延迟过大自动切主库查询。
7. 中间件（Sharding-JDBC）实现动态路由。

### 超量行锁 / 表锁

#### 核心成因

- 更新、删除条件**无索引**，InnoDB 行锁升级为表锁。
- 事务执行时间过长，锁资源长期不释放。
- 批量更新范围过大，锁定大量数据行。
- 高并发争抢同一张表、同范围数据，锁竞争激烈。

#### 造成危害

锁等待、事务阻塞、接口响应超时，并发场景下容易引发死锁、数据更新排队，严重阻塞核心业务。

#### 解决方案

- 增删改条件必须命中索引，保证走行锁。
- 缩短事务粒度：事务内只保留核心DB操作，移除耗时业务逻辑。
- 缩小锁定范围：分批更新、缩小where条件范围。
- 合理使用乐观锁、悲观锁，控制并发更新冲突。

---

### 事务问题

包含：长事务、死锁、事务嵌套、隔离级别不合理

#### 核心成因

- **长事务**：事务中包含远程调用、文件IO、复杂计算，持有锁时间极长。
- **死锁**：多个事务互相持有对方需要的行锁，循环等待资源。
- **事务嵌套**：多层事务嵌套导致传播行为混乱，提交/回滚异常。
- **隔离级别不当**：级别过高（串行化）性能极差；级别过低（读未提交）出现脏读、不可重复读。

#### 造成危害

长事务阻塞锁资源、数据库undo日志膨胀、存储占用升高；死锁导致事务自动回滚、业务失败；隔离级别问题引发数据不一致、性能急剧下降。

#### 解决方案

- 严格控制事务大小，禁止长事务，异步剥离非DB操作。
- 统一更新资源顺序、避免循环加锁，降低死锁概率；开启死锁日志监控。
- 规范事务传播机制，禁止滥用事务嵌套。
- 业务按需选择隔离级别，主流业务默认 **RC 读已提交**。

---

### 读写压力失衡

#### 核心成因

- 架构单一：单库单表，所有查询、写入全部挤压主库。
- 读多写少场景无架构优化：大量查询请求消耗主库资源。
- 主从架构缺失，未做读写分离；主从延迟未做兼容处理。

#### 造成危害

主库负载过高，写入与查询相互争抢CPU、IO资源，整体数据库性能瓶颈明显，无法支撑业务增长。

#### 解决方案

- 引入主从复制，实现**读写分离**：写主库、读从库。
- 多从库横向扩展，分摊查询压力。
- 核心热点查询下沉至 Redis 缓存，减少DB查询量。
- 业务兼容主从延迟，非实时查询走从库。

---

### 6. 分库分表瓶颈

#### 核心成因

- 前期分片规则设计不合理：冷热数据未分离、分片键选择错误。
- 业务存在大量**跨库、跨分片**关联查询、join 查询。
- 分片扩容、数据迁移复杂，运维成本高。
- 分布式事务、多表聚合统计难以实现。

#### 造成危害

跨分片查询性能极差，SQL复杂度飙升；扩容困难无法应对数据量暴涨；分布式场景下数据一致性难以保障。

#### 解决方案

- 合理选择分片键，核心业务避免跨库关联。
- 冗余字段、宽表设计，规避join跨表查询。
- 引入中间件：Sharding-JDBC 管理分片、分页、聚合。
- 超大量表做冷热分离，历史数据归档。

### 面试速记总结

1. **慢SQL**：缺索引、全表扫描、查询大量数据 → explain优化索引，分页，走缓存
2. **大事务**：事务包裹RPC/IO，事务过长 → 缩小事务边界，外部调用移出事务，分批提交
3. **锁竞争**：并发抢锁，锁等待 → 短事务，命中索引，乐观锁，业务限流
4. **行锁/表锁**：索引失效退化成表锁 → update条件必须命中索引，避免MyISAM
5. **死锁**：事务更新顺序不一致 → 统一更新顺序、缩小事务、业务有限重试
6. **连接数打满**：max_connections耗尽 → 连接池不要乱调大，优化慢SQL长事务
7. **热点行**：并发修改同一行DB记录 → Redis前置、行拆分、乐观锁、请求合并
8. **写放大**：少量业务写产生大量磁盘IO → 少索引，拆分大字段，合并更新
9. **索引失效**：建索引不走索引 → 不做函数、避免隐式转换，遵守最左前缀
10. **主从延迟**：主从数据不同步 → 拆分大事务，并行复制，写后读强制走主库

## 5 缓存问题

1. 缓存击穿
2. 缓存穿透
3. 缓存雪崩
4. 热点 Key
5. 缓存失效风暴
6. Redis 单线程瓶颈
7. 大 Key
8. 缓存不一致
9. 缓存重建风暴

缓存层通常是 **高并发系统的第一道保护层**（尤其是 Redis），一旦设计不合理，问题会迅速传导到数据库甚至整个系统。

说明结构：**定义 → 典型场景 → 技术特征 → 风险影响 → 常见治理手段**

缓存层的核心目标是：

```text
减少数据库访问
提升系统吞吐能力
```

但如果缓存设计不合理，就会出现一系列稳定性问题。

缓存问题可以归纳为 **四大类核心问题**：

| 类别           | 问题                        |
| -------------- | --------------------------- |
| 缓存失效问题   | 击穿、雪崩、失效风暴        |
| 异常请求问题   | 缓存穿透                    |
| 性能问题       | 热点 Key、大 Key、Redis瓶颈 |
| 数据一致性问题 | 缓存不一致、缓存重建风暴    |

缓存问题在高并发系统中的典型演化路径：

```text
缓存失效
↓
请求回源 DB
↓
数据库压力暴增
↓
数据库崩溃
↓
系统雪崩
```

> 面试答题模板：**现象→危害→根因→解决方案→Java落地+坑点**，区分容易混淆概念，20k高频面试，和前面数据库、流量类题目联动。

| 问题         | 核心矛盾                  | 核心解法方向                   |
| :----------- | :------------------------ | :----------------------------- |
| **缓存雪崩** | 大量 Key 集体失效/宕机    | 加随机过期、高可用、熔断降级   |
| **缓存击穿** | 热点 Key 过期导致并发回源 | 永不过期/主动续期、互斥锁      |
| **缓存穿透** | 查询不存在的数据          | 布隆过滤器、缓存空值、参数校验 |
| **大 Key**   | 单个 Key 体积过大         | 拆分 Key、数据压缩、监控告警   |
| **缓存污染** | 内存不足，热点被逐出      | 扩容、合理逐出策略、缓存分层   |
| **并发竞争** | 高并发读写导致数据不一致  | 原子操作、分布式锁、延迟双删   |

**核心记住一句话**：缓存的本质是**平衡性能与一致性**，所有问题最终都要回归到**数据生命周期管理**和**高可用架构设计**上。

### 1 缓存击穿

#### 现象

**某一个热点key过期的一瞬间，大量并发请求同时打到数据库**。这个key是高访问热点，缓存失效瞬间，流量全部穿透到DB。

#### 本质

**单个热点 Key** 在某一时刻**精确过期**，此时高并发请求涌入，全部直接查 DB，把 DB 打“穿”。

> 和雪崩区别：雪崩是**大量 Key 一起挂**，击穿是**一个热点 Key 挂了引发海啸**。

#### 典型成因

- 热点商品/热点活动 Key，过期时间**没有续期**。
- 秒杀、直播弹幕等**瞬时高并发**打在单个 Key。

#### 直观危害

- 热点接口 DB QPS 暴增，**连接池打满**，慢查询激增。
- 其他业务也被拖慢，出现**线程池耗尽、超时**。

#### 危害

数据库瞬间压力暴涨，DBCPU飙升，可能打垮数据库。

#### 根因

热点访问的key设置了TTL过期；过期时刻大量请求同时进来。

> 区分：击穿：**热点key过期，打DB**；穿透：**数据本身不存在，一直查DB**；雪崩：**大量key同时过期**。

#### 解决方案

1. **互斥锁（分布式锁）**：缓存失效时，只放一个线程去更新缓存，其他线程等待或者直接返回旧缓存。Redis setnx / Redisson锁。
2. **永不过期（逻辑过期）**：不给key设置TTL过期时间；后台异步线程定时刷新缓存；请求直接返回缓存数据，不主动过期。适合热点key。
3. Sentinel热点参数限流，对该key做参数限流。

> 注意：分布式锁会带来少量性能损耗；逻辑过期不会自动过期，要后台线程维护。

#### 落地解法

1. **热点 Key 永不过期 / 主动续期**

   - 核心热点数据设置为**永久有效**，由后台线程异步更新缓存。
   - 采用“**延时双删**”或“**Canal 订阅 Binlog**”机制保证数据一致性。

2. **互斥锁（Mutex Lock）——经典方案**

   - 只有一个线程去 DB 查并回写缓存，其他线程等待或返回旧值。

   - 伪代码逻辑：

     ```java
     String get(String key) {
         String value = redis.get(key);
         if (value == null) {
             // 加锁，保证只有一个线程去查DB
             String lockKey = "lock:" + key;
             try {
                 Boolean locked = redis.set(lockKey, "1", "NX", "EX", 3);
                 if (locked) {
                     value = db.query(key);
                     redis.set(key, value, expireSeconds);
                 } else {
                     // 重试或短暂休眠，等其他线程写入
                     Thread.sleep(10);
                     return get(key); // 递归重试
                 }
             } finally {
                 redis.del(lockKey);
             }
         }
         return value;
     }
     ```

3. **异步更新 + 缓存预热**

   - 提前预热热点数据到缓存。
   - 采用**定时任务**异步刷新缓存，避免过期瞬间击穿。

### 2 缓存穿透

#### 现象

查询**数据库根本不存在的数据**，缓存永远不会命中，请求直接打到DB。比如传id=-1、非法ID。缓存里没有，每次都查数据库。

#### 典型成因

- 非法请求查询一个**不存在的 ID**，比如 `user_id = -1` 或随机乱 ID。
- 数据确实不存在，缓存没存，DB 也查不到。

#### 直观危害

- 大量无效请求**消耗 DB 资源**，导致正常请求被拖慢。
- 被恶意利用，发起**大流量空查询攻击**，直接拖垮数据库。

#### 危害

大量非法请求，DB持续被查询；爬虫恶意大量传无效id，压垮DB。

#### 根因

查询不存在业务数据；参数非法；恶意攻击。

#### 解决方案

1. **缓存空值**：查询DB为空，Redis存入一个空占位key，设置短TTL，下次请求命中缓存，不再访问DB；
2. **布隆过滤器BloomFilter**：把所有合法业务id预加载进布隆过滤器；请求先过布隆，不存在直接返回，不查缓存、不查DB；
3. 参数校验：接口层拦截非法参数，负数、非法格式直接拒绝；
4. 网关层限流，拦截恶意请求。

> 坑：缓存空值会产生大量无效key，要设置较短过期时间；布隆过滤器存在误判，不会误判不存在，只会误判存在。

#### 落地解法

1. **布隆过滤器（Bloom Filter）——终极防御**
   - 提前将所有**存在的 Key** 哈希映射到布隆过滤器中。
   - 请求先过过滤器，不存在则直接拦截，不查 DB。
   - 适合**写多读少、Key 固定**的场景（如商品 ID 列表）。

2. **缓存空值 + 短期过期**
   - DB 查不到数据，缓存中写入一个**空值**（`null` 或特定占位符），并设置**短过期时间**（如 1 分钟）。
   - 避免短时间内重复查询同一无效 Key。
   - 注意：空值缓存会占用内存，需控制总量。

3. **接口层校验与限流**
   - 对参数做**合法性校验**（如 ID 范围、格式）。
   - 对非法 IP/请求频率做**限流**，拦截恶意攻击。



### 3 缓存雪崩

#### 现象

**大量缓存key同一时间失效；或者Redis整体宕机**；大量请求全部落到数据库，数据库压力瞬间打爆。

#### 危害

DB压力陡增，数据库宕机，整个服务雪崩。

#### 根因

1. 大量key设置完全相同过期时间，同一时刻集体过期；
2. Redis集群故障、断电，整个缓存服务不可用。

#### 典型成因

- 过期时间**没有加随机偏移**，例如全用 `EXPIRE key 3600`，导致整点/整小时集体过期。
- Redis 实例集群**宕机/不可用**，缓存层“消失”。
- 机房断电、网络割接等**底层故障**。

#### 直观危害

- QPS 曲线呈**尖刺状**打穿 DB，服务级联超时、降级甚至宕机。
- 业务核心链路（下单、支付、详情）**全线不可用**。

#### 解决方案

1. **过期时间加随机偏移**，打散TTL，避免大批量key同时过期；`expireTime = baseTime + new Random().nextInt(300)`；
2. Redis高可用：主从、哨兵、Redis‑Cluster集群，避免单点故障；
3. 多级缓存：Caffeine本地缓存 + Redis分布式缓存；Redis挂掉，本地缓存兜底；
4. 服务限流、熔断降级，缓存失效后保护DB；
5. 不依赖TTL删除，后台异步更新缓存。



#### 落地解法（从治标到治本）

1. **过期时间加随机抖动**

   - 在原过期时间基础上加 ±10%~30% 随机偏移，避免集体过期。

   - 示例（伪代码）：

     ```java
     int expireSeconds = 3600;
     int randomOffset = new Random().nextInt(360); // ±10分钟
     redisTemplate.opsForValue().set(key, value, expireSeconds - randomOffset, TimeUnit.SECONDS);
     ```

2. **熔断 + 降级 + 本地缓存**

   - Redis 不可用时，前端/网关层**熔断**，直接返回兜底数据或降级逻辑。
   - 关键热点数据落地**本地缓存**（Caffeine/Guava），给 DB 加一层缓冲。

3. **Redis 高可用架构**

   - 主从 + 哨兵（Sentinel）或 Redis Cluster 集群，避免单点故障。
   - 结合**多 AZ 部署**，规避机房级灾难。

4. **数据库限流与保护**

   - 对 DB 做**读写分离 + 限流**（如 MySQL 慢查询日志、连接数限制）。
   - 必要时引入**服务端限流**（Sentinel/Resilience4j），削峰填谷。

> 面试区分记忆
- 击穿：**一个热点key过期**
- 穿透：**查不存在的数据**
- 雪崩：**大量key同时过期 / Redis整体挂掉**



### 4 热点Key

#### 现象

同一个Redis key超高QPS，几万并发访问同一个key；Redis某分片CPU打满。

#### 危害

1. Redis单实例CPU打满；集群分片流量倾斜；
2. 如果key失效，直接触发缓存击穿，打数据库。

#### 根因

秒杀商品、爆款、热搜，大量用户同时读取同一个key。

#### 解决方案

1. **本地Caffeine缓存**：服务实例本地缓存热点key，绕过Redis，减少Redis访问；设置短过期时间；
2. key打散：逻辑key拆分成多个物理key，`goods:1001:0 ~ goods:1001:9`，请求随机取一个，分散到不同Redis分片；
3. 逻辑永不过期，后台线程定时刷新，不走TTL过期；
4. Redis热点key监控；Sentinel热点参数限流；
5. 注意本地缓存带来的数据一致性问题，会短暂不一致。

> 坑：Caffeine本地缓存，多实例之间数据不一致，适合允许短暂不一致场景。

### 5 缓存失效风暴

#### 现象

一批缓存key集中到期，大量请求同时去回写缓存，大量线程同时执行查DB写Redis，DB压力飙升。
> 和雪崩很像，更侧重：过期后大量线程同时执行缓存重建的风暴。

#### 根因

批量key同时过期；没有控制缓存重建并发，每个请求都去查库重建缓存。

#### 危害

DB短时间大量查询压力，CPU IO飙升。

#### 解决方案

1. TTL加随机值打散过期时间；
2. 缓存重建加互斥锁，同一key只允许一个线程回源重建；
3. 后台异步任务主动刷新缓存，不等key过期；
4. 多级缓存，本地缓存兜底。

### 6 Redis单线程瓶颈

#### 现象

Redis核心命令执行是单线程；当QPS很高、大key、复杂命令，RedisCPU打满，RT升高，命令超时。Redis的CPU成为瓶颈，而不是内存、网络。

#### 根因

Redis主线程串行执行命令；大key操作、keys、hgetall等耗时命令占用主线程；热点key大量请求打在同一个分片。

#### 危害

Redis命令排队超时；业务大量RT抖动；整个Redis实例变慢。

#### 解决方案

1. 禁止耗时命令：`keys`、`hgetall`、`smembers`；用scan分批遍历；
2. 规避大key；
3. 热点key打散，或者下沉到本地缓存；
4. Redis Cluster做分片，压力分散到多个节点；
5. 读写分离，读请求走从节点；
6. 慢命令监控告警。

> 面试重点：Redis处理读写命令是单线程；持久化RDB/AOF是子进程，不占用主线程。

### 7 大Key

#### 现象

Redis某个key存储value体积巨大：比如超大String、百万元素的hash/list/set。
- 大value：String几十MB以上
- 大集合：hash/list 几十万上百万元素

#### 本质

某个 Key 的 **Value 体积过大**（如 String 超过 10MB，Hash/List 元素过多），导致**网络阻塞、IO 瓶颈、主线程卡住**。

#### 典型成因

- 一次缓存过大的**结构化数据**，如完整的商品详情页 HTML、大 JSON。
- 未做**分库分表/分片**，将大量数据塞到一个 Key 里。
- 日志、消息队列等**未压缩数据**直接写入 Redis。

#### 直观危害

- 单个 Key 操作耗时**远超正常阈值**（>10ms）。
- 阻塞 Redis 主线程，导致**整个实例延迟升高**，其他请求排队。
- 引发**网络带宽打满**，影响集群内其他节点。

#### 危害

1. 删除大key：del命令阻塞Redis主线程，造成Redis卡顿、命令超时；
2. 网络传输量大，带宽打满；
3. 集群迁移slot时，大key迁移很慢，阻塞集群；
4. 内存膨胀。

#### 根因

业务把大量数据全部塞到一个Redis key；没有做拆分。

#### 解决方案

1. **拆分大key**：把大集合拆成多个小key；
2. 集合不要用hgetall，改用hscan分批获取；
3. 删除大key不要直接del，使用异步渐进删除；Redis4.0+ unlink非阻塞删除；
4. 设置合理过期时间，避免数据无限膨胀；
5. 大key扫描工具，定期巡检，监控告警；
6. 超过阈值的数据不要放Redis，放数据库ES。

> 面试坑：del大key会阻塞主线程，线上事故常见。优先unlink。

#### 落地解法

1. **拆分大 Key（最核心）**
   - 把大 Value 拆成多个小 Key，例如按 ID 分片：`user:info:1`、`user:info:2`。
   - 针对 List/Hash，使用**分页查询**，避免一次获取全部元素。

2. **数据压缩**
   - 对 String 类型数据进行**压缩**（如 GZIP），再存入 Redis。
   - 读取时解压，平衡网络传输与内存占用。

3. **避免存储无关数据**
   - 清理缓存中**不必要的字段**，只缓存核心热点数据。
   - 对于大对象，考虑直接落盘到数据库，仅缓存关键索引。

4. **监控与告警**
   - 通过 Redis 命令 `MEMORY USAGE key` 或监控工具（如 Prometheus + Grafana）监控大 Key。
   - 设置阈值告警，及时发现并处理。

### 8 缓存不一致

#### 现象

数据库已经更新，但是缓存里面还是旧数据；DB和Redis缓存数据不一样。

#### 什么是缓存数据不一致

数据库中的真实数据 和 Redis（缓存）里面的数据不相同。数据库已经更新，但缓存还是旧值；或者缓存是新值，数据库是旧值。业务读取缓存拿到错误数据，出现脏数据。

#### 根因

1. 更新数据库和更新缓存两个操作，不是原子操作；中间发生异常；
2. 更新缓存失败；
3. 先更新缓存，后更新数据库，数据库更新失败，缓存是新的，DB旧；
4. 并发读写场景，更新时序错乱；
5. 本地Caffeine缓存和Redis缓存不一致。

#### 产生原因

1. **更新数据库之后，忘记删除/更新缓存**
   业务修改数据库，只操作DB，完全没有处理缓存。后续请求直接读取到老的缓存，不会主动去查数据库。

2. **删除缓存失败**
   程序执行「更新DB → 删除缓存」，数据库更新成功，但是删除缓存网络异常、Redis超时、报错，缓存没有删掉。缓存依旧保留旧数据。

3. **并发读写时序错乱（最经典场景）**

> 场景：读请求A，写请求B
> 1）读请求A，缓存失效，准备去查数据库
> 2）写请求B，更新数据库，删除缓存
> 3）读请求A拿到数据库旧数据，回写到缓存
> 结果：数据库是新数据，缓存被A写入旧数据，从此不一致。这就是延迟双删要解决的问题。

4. **MySQL主从复制延迟**
   读写分离架构，写操作写入主库，读请求走从库。更新主库成功，立刻删缓存；此时从库还没同步完新数据。后续请求读从库拿到旧数据，回写缓存，造成缓存脏数据。

5. **MQ异步更新缓存消息丢失**
   依靠MQ来做缓存删除补偿，如果消息丢失，缓存不会清理。

6. **缓存过期时间失效、版本逻辑异常**
7. **多服务同时写同一份数据，互相覆盖缓存**

#### 带来的危害

1. 页面展示错误数据，比如商品价格、商品库存、用户余额错误；
2. 库存场景：超卖、少卖，引发资损；
3. 订单、账户金额错乱，产生脏数据，需要人工修复；
4. 流量越大，脏数据被越多用户读到，影响面放大。



#### 解决方案

> 标准方案：**更新数据库，删除缓存（Cache‑Aside旁路缓存），而不是更新缓存**
1. Cache‑Aside模式：写：更新DB → 删除缓存；读：查缓存，未命中查DB，回写缓存。
2. 删除缓存失败的补偿：
   - 方案1：删除缓存失败，发送MQ消息，消费端重试删除缓存；
   - 方案2：给缓存设置TTL过期，兜底，最多容忍TTL时间不一致；
3. 延迟双删：更新DB，删除缓存；休眠一小段时间，再删一次缓存，解决并发读写时序问题；
4. 对于强一致性场景：不使用缓存，直接读DB；
5. 本地缓存：缩短过期时间，降低不一致窗口。

> 面试追问：为什么不先更新缓存，再更新数据库？
> 答：如果DB更新失败，缓存是新值，数据库旧值，永久不一致。

> 延迟双删不能完全解决并发问题，只能降低概率；最终兜底靠TTL过期。

#### 主流解决方案

##### 方案1：Cache‑Aside 旁路缓存（标准方案：先更新DB，再删除缓存）

流程：

1. 写请求：更新数据库 → 删除缓存
2. 读请求：查询缓存；命中直接返回；未命中查询数据库，把数据写入缓存返回。

> 注意：不要更新缓存，优先删除缓存。
> 原因：高并发下多次写，更新缓存会互相覆盖；删除缓存，让读请求按需加载最新数据更加安全。

##### 方案2：延迟双删，解决并发时序问题

流程：

1. 更新数据库
2. 删除缓存
3. **休眠一小段时间（几百ms，大于业务读请求的耗时），再次删除缓存**

作用：把上面并发读写时序问题里，晚来的旧写回缓存给清除掉。

> 注意：不能用sleep阻塞业务线程；生产环境要用线程池异步执行第二次删除。

缺点：不能100%彻底解决，属于降低概率。

##### 方案3：MQ异步补偿删除缓存

业务更新DB成功之后，发送一条消息到MQ，消费者收到消息执行删除缓存。

- 业务主线完成不受Redis删除结果影响；
- 如果第一次删缓存失败，可以依靠MQ重试做二次删除。

> 注意：要保证消息不丢失；需要处理重复消费，删除缓存幂等。

##### 方案4：设置缓存过期时间，兜底策略

无论如何，给缓存设置TTL过期时间。就算前面全部失效，最多过期时间窗口内是脏数据，到期自动失效重新加载。

> 这是兜底，不能当做主方案。

##### 方案5：定时任务兜底校验（最终防线）

定时任务，扫描热点业务数据，比对数据库与缓存的值；发现不一致，直接删除缓存。
适合库存、金额这类核心数据。
不建议全量扫描，只针对热点key。

##### 方案6：读写分离场景处理主从延迟

写完主库之后，不要立刻去读从库；或者对于写后立刻读的场景，强制读主库，避免读到旧数据回写缓存。

#### ❌不推荐方案

1. **先删缓存，再更新数据库**
   风险：删完缓存，还没更新DB，读请求过来读取旧DB数据回写缓存，直接不一致。

2. **每次写操作直接更新缓存**
   高并发多写场景，请求乱序，后发生的请求先执行，缓存被旧值覆盖。

### 9 缓存重建风暴

#### 现象

缓存失效后，大量并发请求同时回源，大量线程同时查询数据库，同时重建缓存，大量重复的DB查询，DB压力暴涨。
> 和缓存失效风暴高度重合，重点强调：大量线程同时做缓存重建动作。

#### 根因

缓存失效，没有保护，每一个请求都触发回源查询DB写缓存。

#### 危害

DB被大量重复查询压垮。

#### 解决方案

1. **互斥锁（分布式锁）**：同一个key，只放行一个线程回源重建缓存，其余线程等待或者返回旧缓存；
2. 逻辑过期，后台线程主动刷新，业务请求不触发重建；
3. TTL增加随机抖动，避免集中失效；
4. 多级缓存，本地缓存拦截大部分回源请求；
5. Sentinel热点参数限流，限制回源的并发。



### 缓存污染（Cache Eviction/Stale Data）

#### 本质

缓存内存不足，触发**逐出策略**（如 `allkeys-lru`），导致**热点数据被频繁淘汰**，缓存命中率骤降；或**低频脏数据长期占用**。

#### 典型成因

- 缓存**内存配置不足**，未根据业务增长扩容。
- 逐出策略配置不当，比如用了 `allkeys-lru` 但大量低频数据涌入。
- 未设置**合理过期时间**，导致垃圾数据长期堆积。

#### 直观危害

- 缓存**命中率下降**，大量请求被迫回源查 DB。
- 性能退化，响应时间变长，甚至引发**缓存雪崩**的前兆。

#### 落地解法

1. **合理配置内存与逐出策略**
   - 根据业务数据量预估，**扩容 Redis 内存**。
   - 针对热点数据，优先使用 `volatile-lru` 或 `volatile-ttl` 策略，只逐出带过期的 Key。

2. **设置合理过期时间**
   - 给所有 Key 设定**有意义的 TTL**，避免永久不过期的垃圾数据。
   - 对低频数据，适当缩短过期时间，主动清理。

3. **缓存分层**
   - 引入**多级缓存**：本地缓存（Caffeine）+ 分布式缓存（Redis）。
   - 本地缓存存储最热点数据，Redis 存储次热点数据，减少 Redis 内存压力。

4. **主动清理与数据治理**
   - 定期清理**无效/过期数据**，通过定时任务或 Binlog 订阅机制。
   - 监控缓存**命中率、内存使用率**等指标，动态调整策略。



### 缓存并发竞争（Cache Concurrency）

#### 本质

**高并发写场景**下，多个线程同时对同一 Key 进行**读写操作**，导致**数据不一致**或**覆盖更新**。

#### 典型成因

- 多线程同时更新同一缓存 Key，后写的覆盖先写的，导致**最终数据错误**。
- 读-改-写（Read-Modify-Write）操作**非原子性**，中间被其他线程打断。

#### 直观危害

- 缓存数据与数据库数据**不一致**，导致业务逻辑错误。
- 出现**脏数据、幻读**等问题，影响核心业务（如订单、支付）。

#### 落地解法

1. **原子操作（Redis 单线程特性）**
   - 尽量使用 Redis 原生**原子命令**，如 `SETNX`、`INCR`、`HSET` 等，避免多步操作。
   - 对于复杂逻辑，使用 **Lua 脚本** 打包操作，保证原子性。

2. **分布式锁**
   - 对关键业务逻辑加**分布式锁**（如 Redisson 锁），确保同一时间只有一个线程修改缓存。
   - 注意锁的**过期时间、可重入性**和**死锁处理**。

3. **写入策略优化**
   - 采用**延迟双删**：更新 DB 后，延迟一段时间再删除缓存，确保其他线程读取到旧值后能刷新。
   - 优先使用**Canal 订阅 Binlog** 异步更新缓存，减少业务代码耦合。

4. **读写分离与最终一致性**
   - 对于非强一致性要求的场景，可接受短暂数据不一致，通过异步机制保证最终一致。
   - 核心业务（如支付、订单）必须保证强一致性，采用上述锁或原子方案。



### 面试总结要点

1. 做缓存，做不到绝对强一致，大部分业务追求**最终一致性**；
2. Cache‑Aside核心：**先更新DB，再删缓存，不要更新缓存**；
3. 延迟双删缓解并发时序问题，异步线程执行，不能sleep业务线程；
4. MQ补偿解决删缓存失败；TTL+定时校验是兜底手段；
5. 读写分离要考虑主从延迟带来的不一致风险；
6. 没有方案可以做到100%完全杜绝，多个手段组合使用降低不一致窗口时间。

### 面试速记背诵

1. **缓存击穿**：单个热点key过期，大量请求打DB → 互斥锁、逻辑永不过期
2. **缓存穿透**：查询不存在的数据 → 缓存空值、布隆过滤器、参数校验
3. **缓存雪崩**：大量key同时过期 / Redis宕机 → TTL随机偏移、Redis高可用、多级缓存、限流降级
4. **热点Key**：同一个key超高QPS，RedisCPU打满 → Caffeine本地缓存、key打散、热点限流
5. **缓存失效风暴**：批量key过期，大量请求回源 → 打散TTL、互斥锁、后台主动刷新
6. **Redis单线程瓶颈**：主线程执行命令，耗时命令、热点key打满CPU → 禁止慢命令、分片、读写分离

8. **缓存不一致**：DB与缓存数据不同步 → Cache‑Aside更新DB删缓存、延迟双删、MQ重试、TTL兜底
9. **缓存重建风暴**：大量线程同时回源重建缓存 → 互斥锁、后台主动刷新、多级缓存

## 6 队列 / 异步系统问题

1. 消息堆积
2. 消息重复消费
3. 消息丢失
4. 消费速度慢
5. 分区热点
6. 队列阻塞
7. 顺序消费阻塞
8. Broker 宕机

在高并发系统中，消息队列（如 **Apache Kafka**、**Apache RocketMQ**、**RabbitMQ**）常用于：

```text
削峰填谷
系统解耦
异步处理
```

但 MQ 设计不合理也会成为系统瓶颈或故障源。

消息队列问题可以归纳为 **四大类核心问题**：

| 类别           | 问题                   |
| -------------- | ---------------------- |
| 消息可靠性问题 | 消息丢失、重复消费     |
| 消费能力问题   | 消息堆积、消费慢       |
| 架构问题       | 分区热点、顺序消费阻塞 |
| 基础设施问题   | Broker宕机、队列阻塞   |

消息队列问题在高并发系统中的典型演化路径：

```text
生产速度过快
↓
消费速度不足
↓
消息堆积
↓
队列存储耗尽
↓
系统无法写入消息
↓
业务系统崩溃
```

MQ 6 大问题核心口诀

1. **堆积**：加并发、隔离慢操作、快速跳过异常
2. **重复**：消费端必须做**幂等**
3. **丢失**：生产确认 + Broker 持久化 + 手动 ACK
4. **死信**：有限重试 + 死信隔离
5. **Broker阻塞**：集群高可用 + 磁盘/流量管控
6. **顺序错乱**：同ID同队列 + 单线程消费

> 以RocketMQ、Kafka为主，答题范式：**现象 → 危害 → 根因 → 解决方案 + Java业务落地 + 面试坑点**，适配20k+后端面试，和前面数据库、缓存、服务调用串联。

### 1 消息堆积

#### 现象

Broker队列消息数量持续上涨；消息消费offset不上涨；消息消费时间越来越滞后，消息延迟，生产远大于消费速度。

#### 本质

**消费速度 << 生产速度**，消息在 Broker 里越堆越多，最终导致队列阻塞、服务雪崩。

#### 核心原因

- 消费线程数太少，消费能力不足
- 消费逻辑里有**慢 SQL、慢接口、第三方调用超时**
- 消费线程**卡死/抛异常**，单条消息卡住整个队列
- 死信消息无限重试，占用消费线程

#### 危害

1. 消息处理严重延迟，异步业务时效性失效；业务实时性失效（订单、通知延迟）.
2. Broker磁盘持续上涨，磁盘打满  → 新消息无法写入；
3. 旧消息达到保留时间被直接删除，消息丢失风险；
4. 大量消息占用内存，Broker压力升高。
5. 消费延迟引发连锁超时、数据不一致

#### 根因

1. **消费端处理慢**：消费逻辑有慢SQL、调用下游阻塞，消费处理耗时久；
2. 消费失败大量重试，重复消费，消费进度不推进；
3. 生产者生产速度远大于消费能力；
4. 消费者实例太少，消费能力不足；
5. 消费异常，没有提交offset，offset不更新；
6. 消息失败进入死信队列没有处理。

#### 排查

查看消息堆积数量、消费offset、消费耗时、消费报错日志。

#### 解决方案

1. **优化消费业务逻辑**：消费内部移除慢SQL、同步RPC调用，避免消费阻塞；消费内部不要再做重量级IO；
2. 水平扩容消费者实例，增加消费并发；Kafka调大分区数；RocketMQ调消费线程数；
3. 流量削峰：生产侧限流，控制生产速率；
4. 失败消息区分：可重试业务正常重试；不可处理消息直接投递死信队列，不要无限重试，避免无限堆积；
5. 堆积告警，监控堆积数量，及时告警；
6. 堆积严重时，临时扩容消费组，紧急消费；不要直接丢弃业务消息。

> ⚠️面试坑：Kafka分区数决定最大消费并行度；消费实例数不能大于分区数，多余实例空闲。

#### 终极解决方案

1. **提高消费并发度**
   - 增加消费线程数（匹配队列分区/队列数）
   - 水平扩容消费实例（Kafka 分区数 = 最大并发消费数）
2. **异步化/批处理**
   - 非核心逻辑丢到线程池异步执行
   - 支持批量消费的 MQ 开启批量拉取
3. **慢操作隔离**
   - 禁止消费逻辑里执行慢 SQL、远程调用
   - 第三方接口必须加**超时控制 + 熔断**
4. **快速跳过异常消息**
   - 失败立即进入死信队列，不阻塞正常消费
5. **监控告警**
   - 监控堆积量、消费延迟、消费成功率

### 2 消息重复消费

#### 现象

同一条业务消息被消费者多次拿到，业务重复执行；比如订单多次创建、重复扣款。

#### 本质

MQ 为了**不丢消息**，默认开启**重试机制**，网络波动/异常都会重发 → 消费者收到多条相同消息。

#### 典型场景

- 消费成功但未提交 ACK
- 消费者超时、重启、抛异常触发重试
- 生产者重试发送

#### 根因

1. **消费成功，offset提交失败**：业务处理完成，还没提交offset，进程宕机，重启后重新消费；
2. Broker重试机制，消费异常触发重试投递；
3. 网络抖动，返回ACK丢失，Broker重新投递；
4. 生产者重试，产生重复消息；
> MQ本身不保证只消费一次，只保证**至少一次(At‑least‑once)**。

#### 危害

- 重复扣款、重复通知、**库存超卖**
- 脏数据、业务逻辑错乱

业务重复执行，产生脏数据，重复下单、重复扣款等严重问题。

#### 解决方案

**业务侧实现幂等，不要依赖MQ保证不重复**
1. 唯一业务id做幂等：消息携带msgId / 业务唯一id；消费前先查DB/Redis判断该id是否已经处理过，处理过直接跳过；
2. 数据库唯一索引：利用数据库唯一约束，重复插入直接报错拦截；
3. 状态机校验：只有业务当前状态允许执行，才执行业务逻辑；
4. 消费逻辑做成幂等，多次执行结果一致。

> 面试重点：MQ无法从根源杜绝重复消息，**幂等是业务必须做的**。

#### 核心原则

**MQ 不保证只投递一次，消费者必须保证【幂等性】**

#### 解决方案（通用且落地）

1. **数据库唯一索引**（最简单）
   - 用 `msgId`/`orderId` 建唯一键，重复插入直接报错
2. **Redis 分布式锁**
   - 消费前：`SETNX lock:msgId`
   - 加锁成功才执行业务
3. **状态机判断**
   - 订单状态：待支付 → 已支付，重复消息直接忽略
4. **全局唯一 ID + 消费记录表**
   - 记录已消费的 msgId，先查再处理

### 3 消息丢失

#### 现象

消息生产者发送成功，但是消费者永远收不到这条消息。消息在某个环节丢失。

#### 本质

消息在 **生产者 → Broker → 消费者** 三个环节任意一环弄丢。

#### 根因，分三个环节

1. **生产端丢失**：生产者发送消息，还没刷盘到Broker，Broker宕机；同步发送没有等待返回成功，直接认为发送完成。
2. **Broker端丢失**：消息还在PageCache，没有刷盘；主Broker宕机，还未同步到从节点；消息过期被清理。
3. **消费端丢失**：消息刚拿到，还没有执行业务，直接提交offset，之后消费进程挂掉；业务没做，offset已经前进，消息再也拿不到。

#### 解决方案

1. 生产端：使用同步发送，等待send返回成功；开启重试；不要单向发送oneway；
2. Broker：开启刷盘策略；主从复制，保证消息同步到从节点；合理设置消息保留时间；
3. 消费端：**先执行业务逻辑，业务处理完成之后，再提交offset**；禁止先提交offset再执行业务；
4. 重要业务开启消息轨迹，方便排查消息去向；
5. 关键业务可以业务层做消息落库，核对消息对账。

> 高频坑：消费先提交offset再执行业务，进程宕机直接消息丢失，线上高频事故。

#### 三大丢失场景 + 对应解决方案

1. **生产者丢消息**
   - 原因：网络闪断、Broker 未收到
   - 解决：**开启事务/确认机制（ACK）+ 重试**
2. **Broker 丢消息**
   - 原因：Broker 宕机、内存数据未刷盘
   - 解决：**持久化 + 主从同步 + 同步刷盘**
3. **消费者丢消息**
   - 原因：先提交 ACK，再执行业务，中途宕机
   - 解决：**先执行业务，再提交 ACK**

#### 一句话保证不丢消息

**生产者确认 + Broker 持久化 + 消费者手动 ACK**

### 4 消费速度慢

#### 现象

单条消息消费耗时长，消费TPS低，慢慢产生消息堆积。

#### 根因

1. 消费逻辑内部慢SQL、大事务；
2. 消费内部同步调用RPC、第三方接口，网络阻塞；
3. 消费线程数设置过小；
4. Kafka分区数太少，并发上不去；
5. 消息体过大，序列化反序列化耗时；
6. 消费逻辑有锁，串行执行。

#### 解决方案

1. 消费逻辑尽量轻量化，把重业务再次转发到二级MQ，拆成二次异步；消费端不要做耗时IO；
2. 调大消费线程，Kafka增加分区数量提升最大并发；RocketMQ调整consumeThreadNumber；
3. RPC调用设置超时，防止消费线程卡死；
4. 避免大消息，消息体不要携带大量数据；大数据只传id，业务自己查；
5. 去掉消费内部不必要锁；
6. 监控单条消息消费耗时告警。

### 5 分区热点（队列热点）

#### 现象

Kafka/RocketMQ，大量消息全部打到同一个partition，其他partition空闲；消费压力全部集中在一个消费实例，整体消费上不去，出现堆积。

#### 根因

1. 业务使用固定key做hash取分区，大量消息同一个key，全部落到同一个分区；
2. key分布极度不均匀，热点业务id；
3. 分区数量过少。

#### 危害

单分区压力大，消费能力瓶颈；整体集群资源无法充分利用。

#### 解决方案

1. 合理设计消息key，打散热点；热点业务id后面拼接随机后缀，打散到不同分区；
2. 增加partition数量，提高并行上限；
3. 不需要顺序的场景，可以不指定key，轮询发送；
4. 监控每个partition的生产、消费TPS，发现分区倾斜告警。

> 面试提醒：要顺序消费才指定key；key相同消息落到同一个partition，保证顺序，但会带来分区热点风险。

### 6 队列阻塞

#### 现象

消费线程卡住，不再处理消息，消费进度停滞，消息堆积持续上涨，消费线程不退出，也不处理新消息。

#### 根因

1. 消费逻辑内部无限阻塞：调用下游没有设置超时，线程卡死；
2. 死循环；
3. 获取锁一直等待永不释放；
4. 消息处理抛出异常，没有捕获，线程异常退出；
5. 大消息处理，IO阻塞。

#### 危害

消费线程卡死，该线程不再消费消息，堆积持续上涨。

#### 排查

jstack查看消费线程栈，大量BLOCKED / WAITING状态。

#### 解决方案

1. **消费内部所有外部调用必须设置超时时间，禁止无限阻塞**；
2. 全量捕获消费异常，异常消息投递死信队列，不要让消费线程卡死；
3. 设置消费超时，框架层面超时强制失败；
4. 监控消费线程存活状态，线程卡死告警；
5. 消费逻辑避免死锁、无限等待。

### 7 顺序消费阻塞

#### 现象

需要顺序消费场景，某一条消息处理失败，后续同key消息全部卡住不能消费，队列停滞堆积。

> 顺序消费：同一个key消息进入同一个partition，要求按生产顺序消费。

#### 根因

顺序消费模式下，消息必须一条一条处理；第一条消息失败，不允许跳过，后面同partition消息全部阻塞等待。如果失败消息一直重试失败，整个分区消费卡住。

#### 危害

同分区后续正常消息全部阻塞堆积，顺序消费一旦遇到坏消息，整个分区瘫痪。

#### 解决方案

1. 顺序消费中，失败消息不要无限重试；达到重试次数直接投递死信；
2. 区分业务：非强顺序场景，不要强行使用顺序消费；
3. 死信消息人工处理，处理完成恢复消费；
4. 顺序消费业务逻辑尽量简单，降低失败概率；
5. 监控顺序消费分区堆积告警。

> 面试坑：顺序消费的代价：一旦一条消息失败，整个分区阻塞，很多同学忽略这个风险。

### 8 Broker宕机

#### 现象

MQBroker节点宕机；生产者发送报错；消费异常。

#### 根因

机器故障、磁盘满、OOM、进程崩溃。

#### 危害

如果没有高可用，生产消费中断，消息丢失风险。

#### 解决方案

1. Broker集群部署，主从架构，RocketMQ主从；Kafka多副本；
2. 副本机制，消息至少同步到多个副本再返回生产成功；
3. 生产者开启重试，自动切换可用broker；
4. 监控Broker状态、磁盘使用率；
5. 不要单节点部署，生产环境禁止单机Broker。

### 死信队列泛滥

#### 本质

无法被正常消费的**异常消息**，一直重试 → 占用队列、拖慢正常消费。

#### 典型原因

- 数据格式错误、业务异常（如订单已取消）
- 依赖服务不可用，消息一直失败重试
- 重试次数无限制，无限循环

#### 危害

- 正常消息被“卡死” behind 异常消息
- 消费线程被占满，队列雪崩

#### 解决方案

1. **设置最大重试次数**
   - 重试 3~5 次失败 → 立即进入死信队列
2. **独立死信队列 + 监控告警**
   - 死信不影响主队列
   - 人工排查/脚本自动修复
3. **失败消息隔离**
   - 绝不允许失败消息阻塞队列

### MQ Broker 阻塞

#### 本质

Broker 本身不可用/性能暴跌 → 整个消息系统瘫痪。

#### 核心原因

- 磁盘空间写满
- 内存不足、GC 卡顿
- 主从同步延迟、网络拥堵
- 队列分区/队列卡死
- 消息体过大、并发过高

#### 危害

- 生产消息失败、服务超时
- 全线业务阻塞（订单、支付、通知）

#### 解决方案

1. **磁盘监控 + 定期清理**
   - 过期消息自动删除
2. **Broker 集群高可用**
   - 主从 + 多节点部署，避免单点
3. **流量控制**
   - 大消息拆分、禁止超大消息
   - 生产端限流削峰
4. **同步复制/异步复制合理配置**
   - 核心链路用同步复制保证可靠性

### 顺序消息错乱

#### 本质

业务要求**消息必须按发送顺序消费**（如订单创建→支付→物流），但并发消费导致乱序。

#### 原因

- 多线程并发消费
- 重试消息插队
- 多分区/多队列并行分发

#### 危害

- 先支付再创建订单 → 业务报错
- 数据状态错乱

#### 解决方案

1. **同一业务 ID 进入同一队列/分区**
   - 如按 `orderId` 哈希路由
2. **单线程消费**
   - 该队列只允许一个线程消费
3. **MQ 官方顺序消息机制**
   - Kafka：分区内有序
   - RocketMQ：严格顺序消息
4. **业务层面容忍最终有序**
   - 用状态机避免乱序影响

### 面试速记背诵

1. **消息堆积**：消费跟不上生产，offset不前进 → 优化消费逻辑、扩容消费、死信队列、堆积告警
2. **消息重复消费**：MQ至少一次投递 → **业务实现幂等**（唯一ID、唯一索引、状态机）
3. **消息丢失**：生产、Broker、消费三环节丢消息 → 同步发送、主从刷盘、业务处理完再提交offset
4. **消费速度慢**：消费逻辑重、并发不够 → 轻量化消费逻辑，增加分区/线程，二次转发异步
5. **分区热点**：大量消息hash到同一个partition → 打散key，增加分区，非顺序不指定key
6. **队列阻塞**：消费线程卡死不处理消息 → 调用加超时，捕获异常，死信队列
7. **顺序消费阻塞**：坏消息卡住整个分区 → 失败消息有限重试，超过次数进死信
8. **Broker宕机**：节点故障 → 集群+多副本高可用架构

## 7 分布式系统问题

1. 分布式锁竞争
2. 锁失效

5. 数据一致性问题

**定义 → 典型场景 → 技术特征 → 风险影响 → 常见治理手段**

分布式系统问题可以归纳为 **四大核心类型**：

| 类别     | 问题                       |
| -------- | -------------------------- |
| 协调问题 | 分布式锁竞争、锁失效       |
| 时间问题 | 时钟漂移                   |
| 事务问题 | 分布式事务失败、一致性问题 |

分布式系统经典故障链路：

```

```

> 答题范式：**现象→危害→根因→解决方案+Java落地+面试坑点**，围绕Redis/Zookeeper分布式锁、分布式事务、CAP、脑裂等20k高频考点，承接前面整套高并发故障体系。

### 1 分布式锁竞争

#### 现象

多个不同服务实例、不同进程，同时争抢同一把分布式锁；大量并发抢锁，抢锁失败，大量请求等待、重试。

#### 危害

大量请求阻塞；重试压力放大；获取锁失败业务报错；并发高时锁成为性能瓶颈。

#### 根因

多节点多线程并发争抢同一个资源；业务热点资源，需要分布式锁做互斥。

#### 解决方案

1. 使用成熟组件：Redisson（Redis）、Zookeeper实现分布式锁，不要自己手写setnx；
2. 锁粒度尽量小，锁持有时间尽量短，拿到锁尽快释放；
3. 非必要不使用分布式锁，优先业务方案规避锁：请求合并、资源拆分、乐观锁；
4. 设置抢锁等待时间，避免无限等待；
5. 抢锁失败不要无限循环重试，加入退避策略；
6. 监控锁等待时间、锁竞争次数告警。

> 面试坑：分布式锁性能不如本地锁；能不用就不用，优先乐观锁方案。

### 2 锁失效

#### 现象

分布式锁出现**多个客户端同时拿到同一把锁**，互斥失效，并发脏数据。

#### 根因（高频四大原因）

1. **锁超时，业务还没执行完，锁自动过期释放**；业务还在跑，其他线程拿到锁；
2. 没有锁续期；Redis锁过期，业务未完成；
3. 解锁不是自己的锁：A线程的锁，B线程把锁删掉；
4. Redis主从切换，锁还没同步到从节点；主宕机，从升级为主，锁丢失。

#### 解决方案

1. Redisson看门狗（watchdog）自动续期锁，业务未执行完自动延长过期时间；
2. 解锁必须校验锁持有者标识，只能解自己加的锁；Lua脚本保证加锁解锁原子性；
3. 锁过期时间大于业务最大执行时间；
4. Redis锁主从切换风险：强一致性场景改用Zookeeper锁；
5. 尽量缩短锁内业务执行时间，不要在锁内部做慢SQL、RPC调用。

> 高频面试题：Redis分布式锁会有哪些问题？看门狗原理是什么。

### 3 时钟漂移

#### 现象

服务器系统时间跳变、回拨；时间突然往前或者往后跳；依赖系统时间的业务逻辑异常。

#### 根因

NTP时间同步发生时间回拨；多台机器时钟不一致，各节点系统时间不同步。

#### 危害

1. Redis锁依赖过期时间，时钟回拨锁会提前过期；
2. 时间戳生成乱序；订单时间、日志时间错乱；
3. 定时任务、时间窗口统计逻辑出错；
4. Zookeeper依赖系统时间，时间漂移引发异常。

#### 解决方案

1. 业务尽量不要强依赖系统wall‑clock时间；优先使用单调递增时间（System.nanoTime）做内部计时；
2. NTP配置禁止时间回拨，只做渐进式时间校准；
3. 分布式场景不要用机器本地时间做全局唯一排序；使用数据库自增ID、雪花算法；
4. 雪花算法注意时钟回拨问题，雪花算法遇到时钟回拨直接抛出异常拒绝生成ID；
5. 集群机器定期做时钟同步。

> 面试重点：雪花算法最大坑点就是时钟回拨。

### 4 分布式事务失败

#### 现象

多个服务/多个数据库，一部分执行成功，一部分执行失败，出现部分成功部分失败，数据不一致。

#### 根因

跨服务、跨库操作，没有本地事务的ACID；网络抖动、服务宕机、调用超时，导致部分分支完成部分失败。

#### 危害

业务数据脏数据，资金、订单数据不一致。

#### 解决方案

1. **优先业务方案避免分布式事务**：尽量把业务收敛到一个数据库，避免跨库跨服务；
2. TCC（Try‑Confirm‑Cancel）：侵入业务代码，适合强一致性，开发成本高；
3. SAGA模式：长事务，补偿回滚，适合长链路业务；
4. 本地消息表/可靠消息最终一致性（RocketMQ），最终一致性，大部分业务场景；
5. Seata框架AT模式，无侵入，适合数据库事务；
6. 区分业务：大部分业务接受**最终一致性**，很少场景需要强一致性。

> 面试区分：

- AT：无侵入，基于undo_log，适合数据库；
- TCC：代码侵入，手动写try confirm cancel；
- SAGA：补偿，适合长事务；
- 可靠消息：MQ实现最终一致性。

### 5 数据一致性问题

#### 现象

分布式环境下，多节点数据副本、多库多服务数据不一致；写入成功，其他节点读取到旧数据。 包含：缓存DB不一致、主从延迟、分布式事务部分失败、多副本同步延迟。

#### 根因

网络延迟；副本同步异步；分布式节点之间无法瞬间同时完成数据更新；CAP理论，网络无法百分百可靠。

#### 解决方案

1. 分清业务需要：强一致性 / 最终一致性；绝大多数业务接受最终一致；
2. 强一致性场景：牺牲可用性，等待副本同步完成再返回；
3. 最终一致性：通过TTL、定时校对、对账任务补偿修复不一致数据；
4. 读写分离写后读强制走主库；缓存使用Cache‑Aside+延迟双删；
5. 定时对账补偿job，定期校验多端数据，修复差异；
6. 重要资金业务，增加对账校验机制。

> CAP：C一致性，A可用性，P分区容错；分布式系统P无法避免，只能在C和A之间取舍。

### 6 网络分区

#### 现象

集群节点之间网络断开，集群被切割成多个互相不可通信的子集群；但是每个子集群内部网络正常。也叫脑裂的前置条件。

#### 根因

交换机故障、防火墙、网络抖动，部分节点之间网络不通。

#### 危害

集群分裂；各子集群独立对外提供服务，数据错乱；写冲突，两份数据同时写入。

#### 解决方案

1. 集群选主算法引入多数派机制（Quorum），只有获得过半节点投票才能成为主节点；
2. 节点检测心跳，心跳超时判定节点失联；
3. 发生网络分区，少数派节点拒绝提供写服务，只提供读；
4. 依靠Zookeeper、etcd这类分布式协调组件，内部已经处理网络分区；
5. 监控集群节点之间网络连通性。

> 面试：网络分区就是P（Partition），分布式系统必须容忍网络分区。

### 7 脑裂问题

#### 现象

集群发生网络分区，**出现多个master主节点**；多个主节点同时接收写入请求；数据冲突、重复写入，数据严重错乱。

#### 根因

网络分区；老master没有感知网络断开，依旧认为自己是主；分区内新选出master，于是同时存在多个主。

#### 危害

多主同时写入，数据冲突，元数据错乱，集群严重损坏。

#### 解决方案

1. **Quorum多数派选举机制**，过半节点同意才可以选主；网络分区少数分区无法选出master；
2. 主节点租约机制（lease），主节点需要持续续约；心跳断了租约到期自动放弃主身份；
3. Zookeeper、Redis哨兵、etcd内部自带防脑裂；
4. Redis哨兵：min‑replicas‑to‑write配置，主节点至少要有N个从节点存活才允许写；
5. 禁止人工手动强制切换主节点。

> 面试高频：Redis哨兵脑裂怎么产生，如何解决。

### 8 节点失联

#### 现象

集群某节点心跳超时，其他节点收不到该节点心跳；节点进程可能挂掉，也可能只是网络断了。

#### 根因

进程OOM宕机、机器故障、网络隔离、CPU打满无法发送心跳。

#### 危害

1. 如果是主节点失联，触发重新选主；
2. 副本缺失，集群数据可靠性下降；
3. 部分分片没有可用节点，业务读写报错。

#### 解决方案

1. 集群心跳检测机制，合理设置心跳超时时间；超时区分节点是真宕机还是网络抖动；
2. 多副本部署，单节点失联副本还可对外服务；
3. 不要过快剔除节点，防止短暂网络抖动误判失联；
4. 节点下线之前做优雅下线，迁移分片；
5. 监控节点状态告警，节点失联及时告警。

### 面试速记背诵

1. **分布式锁竞争**：多实例抢锁 → 缩小锁粒度，优先乐观锁，抢锁加退避
2. **锁失效**：锁过期、误删锁、主从切换丢锁 → watchdog续期、Lua脚本、Zookeeper强一致锁
3. **时钟漂移**：系统时间回拨 → 避免依赖系统时间；雪花算法处理时钟回拨；NTP渐进同步
4. **分布式事务失败**：跨服务部分成功部分失败 → 尽量避免分布式事务；AT/TCC/SAGA/可靠消息
5. **数据一致性问题**：多节点数据不一样 → 区分强/最终一致性；定时对账补偿
6. **网络分区**：集群网络切割成多块 → Quorum多数派，少数派禁止写
7. **脑裂问题**：出现多个master主节点 → 多数派选举、租约机制，Redis哨兵配置min‑replicas‑to‑write
8. **节点失联**：心跳超时节点不可见 → 心跳检测、多副本，优雅下线

## 8 应用层问题

1. 代码死循环
2. 内存泄漏
3. 线程死锁
4. 对象创建过多
5. 不合理的同步锁
6. 大对象传输
7. JSON 序列化性能问题
8. 日志过多



应用层问题的本质是：

```text
业务代码 + JVM运行时 + 并发设计不合理
```

这类问题不会依赖外部系统，而是**代码本身导致系统崩溃或性能下降**。

应用层问题本质是：

```text
代码 + 并发 + JVM 使用不合理
```

可以归纳为 4 类核心问题：

| 类别     | 问题                     |
| -------- | ------------------------ |
| 并发问题 | 死锁、锁设计不合理       |
| 内存问题 | 内存泄漏、对象过多       |
| 性能问题 | JSON慢、大对象、循环问题 |
| IO问题   | 日志过多、大对象传输     |

应用层问题最终都会演化为：

```text
CPU升高 / 内存上涨 / GC频繁 / 响应变慢
```



> 答题范式：**现象 → 危害 → 根因 → 解决方案 + Java落地 + 面试坑点**，JVM、线程、代码层面故障，承接前面整套高并发故障排查体系。

### 1 代码死循环

#### 现象

CPU持续飙高，CPU 100%；线程一直跑无法退出；接口卡死、请求不返回；线程栈可以看到循环内逻辑反复执行。

#### 危害

CPU被占满，服务处理能力急剧下降；请求堆积；整体接口RT飙升；严重导致服务雪崩。

#### 根因

1. while/for循环缺少退出条件；
2. 循环内部条件永远不满足退出；
3. 集合遍历删除元素，ConcurrentModificationException处理不当进入死循环；
4. 异常捕获后没有break/return，循环永不退出。

#### 排查

jstack打印线程栈，定位到死循环线程，看循环代码。

#### 解决方案

1. 循环必须设计可靠退出条件；
2. 循环内部增加最大次数保护，防止无限循环；
3. 集合遍历避免一边遍历一边删除；
4. 异常分支要有退出逻辑；
5. 上线代码评审，重点检查循环逻辑；
6. 监控服务CPU使用率告警。

> 坑：死循环不一定必报错，就是CPU打满，业务变慢。

### 2 内存泄漏

#### 现象

服务内存持续上涨，不会释放；老年代持续占用走高；频繁Full GC；最后OOM崩溃。重启后恢复，运行一段时间复现。

#### 危害

频繁Full GC，STW停顿，接口抖动；OOM服务宕机。

#### 根因

1. 集合List/Map长生命周期对象，不断add元素，没有清理；
2. 静态集合持有对象引用；
3. 线程池线程无限持有任务对象，线程不销毁；
4. 外部资源未关闭：流、连接、数据库连接没有close；
5. ThreadLocal忘记remove，线程复用导致对象泄漏。

#### 排查

dump堆快照，MAT分析，查找大对象、无法回收对象。

#### 解决方案

1. 静态容器谨慎使用，及时清理不用对象；
2. ThreadLocal使用完必须remove，尤其线程池场景；
3. IO、连接使用try‑with‑resource自动关闭；
4. 线程池合理配置，不要无界队列；
5. 避免长生命周期对象持有大量短生命周期对象；
6. 监控JVM内存、FullGC频率告警。

> 高频坑：ThreadLocal泄漏，线程池复用线程，对象永远不会被GC。

### 3 线程死锁

#### 现象

多个线程互相持有对方需要的锁，互相等待，全部卡死不再执行；业务请求卡住不返回；CPU不一定高，线程全部BLOCKED。

#### 根因

死锁四个条件：互斥、占有且等待、不可剥夺、循环等待。
代码中多个synchronized锁，线程获取锁顺序不一致。
T1获取锁A，等待锁B；T2获取锁B，等待锁A。

#### 排查

jstack可以直接检测死锁，输出deadlock信息。

#### 解决方案

1. 统一锁获取顺序，所有线程按固定顺序申请锁；
2. 缩小锁粒度，减少锁持有时间；
3. 尽量避免嵌套锁；
4. 使用显式Lock，支持tryLock带超时时间，避免无限等待；
5. 代码评审，排查嵌套锁场景。

> 区分：线程死锁是JVM内部锁；分布式锁失效是跨进程锁问题。

### 4 对象创建过多

#### 现象

短时间大量创建大量小对象；YoungGC频繁，GC压力大；STW频繁，接口RT抖动。堆内存占用上涨。

#### 危害

频繁YGC，CPU消耗在GC上；业务接口出现随机抖动。

#### 根因

1. 循环体内频繁new对象；
2. 接口高并发，每次请求创建大量临时对象；
3. 字符串拼接产生大量中间对象；
4. 未复用对象，每次请求新建实体、DTO。

#### 解决方案

1. 循环外面创建对象，循环内复用；
2. 高并发热点路径减少对象创建；
3. 字符串拼接使用StringBuilder；
4. 对象池复用高频对象（谨慎使用，避免复杂度升高）；
5. 合理设置JVM新生代大小；
6. 监控YGC次数、GC耗时告警。

> 坑：大量短命小对象不会OOM，但是会GC频繁，带来业务抖动。

### 5 不合理的同步锁

#### 现象

并发不高但接口TPS上不去，大量线程等待锁；出现大量锁竞争，业务RT很高。

#### 根因

1. 锁粒度太大，把大段业务逻辑、IO、RPC放到synchronized锁内部；
2. 使用锁对象范围过大，锁整个类或者大对象；
3. 不该加锁的地方加锁，串行化并发逻辑；
4. 锁内部执行慢SQL、网络调用，锁持有时间很长。

#### 危害

并发退化成串行，吞吐量暴跌；大量线程阻塞等待锁。

#### 解决方案

1. 缩小锁粒度，只把真正需要互斥的代码放锁内；
2. 锁内部禁止RPC、数据库查询、IO操作；
3. 读写场景用ReentrantReadWriteLock读写锁；
4. 能使用CAS无锁（Atomic系列）就不用重量级锁；
5. 拆分锁，把一把大锁拆成多把细粒度锁；
6. 监控锁等待时间。

> 面试重点：锁里面不要做网络IO，锁持有时间要尽可能短。

### 6 大对象传输

#### 现象

RPC/HTTP接口传输超大对象，大JSON报文；报文几十MB甚至更大。

#### 危害

1. 序列化、反序列化耗时高；CPU上涨；
2. 网络传输慢，RT飙升；占用大量带宽；
3. 占用堆内存，容易触发GC；
4. RPC框架缓冲区溢出，报文截断、超时。

#### 根因

接口直接返回全量大列表，select *把数据库大量数据全部封装返回；直接传递大字节数组。

#### 解决方案

1. 禁止接口传输大对象；只传id，由接收方按需查询；
2. 分页返回，不要一次性返回全量集合；
3. 大文件、大数据不走RPC，走对象存储，传递下载url；
4. RPC框架调整报文最大限制，做好防护；
5. 接口报文大小监控告警。

### 7 JSON 序列化性能问题

#### 现象

高并发接口JSON序列化/反序列化CPU占用高；接口RT高；CPU被序列化逻辑占满。

#### 根因

1. 返回超大集合、大对象做JSON序列化；
2. 使用性能较差的序列化工具；
3. 对象字段极多，大量无用字段参与序列化；
4. 循环引用导致序列化栈溢出或者无限递归。

#### 危害

CPU打满；接口响应慢；出现序列化异常报错。

#### 解决方案

1. 接口DTO精简，只返回需要字段，不要直接返回数据库Entity；
2. 选择高性能序列化组件；
3. 避免循环引用，配置循环引用处理策略；
4. 大集合分页，不要一次性序列化大量数据；
5. 热点链路可以考虑二进制序列化；
6. 监控序列化耗时。

> 坑：直接把数据库实体Entity对外返回，字段多还容易泄露敏感字段。

### 8 日志过多

#### 现象

打印大量info/debug日志；QPS很高，日志量巨大。

#### 危害

1. 磁盘IO打满，磁盘空间快速占满；
2. 日志打印占用CPU，业务线程阻塞；
3. 磁盘写压力大，拖累整个机器性能；
4. 日志文件爆炸，磁盘被打满导致服务异常。

#### 根因

1. 线上开启debug级别；
2. 在循环、高并发热点路径打印大量日志；
3. 异常场景打印完整堆栈，高并发下大量异常栈输出。

#### 解决方案

1. 生产环境使用info级别，关闭debug；
2. 热点循环内减少打印日志；
3. 避免异常疯狂打印堆栈，必要时做限流打印；
4. 使用异步日志输出；
5. 配置日志滚动、自动清理策略；
6. 监控磁盘使用率。

### 面试速记背诵

1. **代码死循环**：缺少退出条件 → jstack定位，循环增加最大次数保护
2. **内存泄漏**：对象引用无法释放，内存持续上涨、FullGC/OOM → MAT堆分析；ThreadLocal用完remove；关闭资源；慎用静态集合
3. **线程死锁**：多线程嵌套锁，循环等待 → jstack检测死锁；统一锁顺序；避免嵌套锁；tryLock超时
4. **对象创建过多**：大量短命小对象，频繁YGC → 循环复用对象，减少循环内new，StringBuilder
5. **不合理的同步锁**：锁粒度大，锁内IO/RPC，并发变串行 → 缩小锁粒度，锁内不做IO，读写锁/CAS
6. **大对象传输**：RPC/HTTP超大报文 → 分页，传ID代替传数据，大文件传URL
7. **JSON序列化性能问题**：大对象序列化CPU高 → DTO精简，分页，避免返回Entity
8. **日志过多**：海量日志磁盘IO高 → 生产关闭debug，异步日志，滚动清理，热点减少打印

## 9 系统架构问题

1. 单点故障
2. 扩展性不足
3. 负载不均
4. 服务治理缺失
5. 容量规划不足
6. 限流缺失
7. 降级缺失
8. 熔断缺失

**系统架构问题（高并发系统稳定性中的顶层设计问题）** 的系统化说明。这一类问题本质不是代码问题，而是：

```text
架构设计是否具备“抗压能力 + 容错能力 + 可扩展能力”
```

仍然按统一结构：

> 定义 → 典型场景 → 技术特征 → 风险影响 → 常见治理手段

系统架构问题本质是：

```text
系统是否具备“抗压 + 容错 + 可扩展能力”
```

可以归纳为 4 大类：

| 类别         | 问题                         |
| ------------ | ---------------------------- |
| 高可用问题   | 单点故障                     |
| 扩展问题     | 扩展性不足、容量不足         |
| 流量治理问题 | 限流缺失、负载不均           |
| 容错问题     | 熔断缺失、降级缺失、治理缺失 |

------

#### 最终演化规律（非常重要）

架构缺陷的典型故障链：

```text
无限流
↓
流量暴涨
↓
无熔断
↓
依赖雪崩
↓
无降级
↓
核心服务崩溃
```

> 答题范式：**现象 → 危害 → 根因 → 解决方案 + 业务落地 + 面试坑点**，偏向架构设计、线上稳定性，承接前面8大故障模块。

### 1 单点故障

#### 现象

系统某个组件只有一个实例；该实例宕机后，整个链路直接不可用。可以是服务、DB、Redis、MQ、网关等。

#### 危害

单点挂掉，业务整体瘫痪；无备用节点，只能等待重启恢复，故障时间长。

#### 根因

架构设计只部署单实例；没有副本、没有集群；没有备份切换能力。

#### 解决方案

1. 所有核心组件无单点：应用多实例部署；数据库主从；Redis哨兵/Cluster；MQ集群；网关集群；
2. 故障自动转移：注册中心剔除故障节点，流量切到健康实例；
3. 异地/多可用区部署，规避机器、机房故障；
4. 关键链路做降级兜底，即使部分组件故障，保留核心业务可用；
5. 演练：定期做故障演练，模拟节点宕机验证高可用。

> 坑：做了集群不等于高可用，全部实例部署在同一台机器/同一个可用区，依然存在单点风险。

### 2 扩展性不足

#### 现象

业务上涨，系统扛不住流量；简单加机器也无法提升吞吐量；数据库QPS上不去，改代码改架构改动巨大。

#### 危害

流量上涨就雪崩；大促前需要大量改造，迭代慢，无法支撑业务增长。

#### 根因

1. 单体大应用，所有业务耦合在一起；
2. 数据库单库单表，没有分库分表；
3. 无缓存，所有请求直打DB；
4. 业务强同步，链路冗长，无法横向扩容；
5. 架构没有预留扩展设计。

#### 解决方案

1. 合理微服务拆分，按业务领域拆分，隔离不同业务；
2. 读写分离、分库分表，解决数据库存储与访问瓶颈；
3. 引入缓存、MQ异步解耦，把同步链路改为异步；
4. 设计支持水平扩展：增加实例即可提升能力；避免只能垂直扩容（换更强机器）；
5. 提前做架构评审，预估业务增长。

> 面试区分：水平扩展：加机器；垂直扩展：升级机器配置。优先水平扩展。

### 3 负载不均

#### 现象

集群各个实例压力差距很大；部分实例CPU、IO打满，其余实例空闲；整体集群资源没有充分利用。
可以出现在应用、Kafka/RocketMQ分区、Redis集群、数据库分片。

#### 危害

集群整体上不去，压力被少数节点限制；热点节点容易先宕机，引发连锁故障。

#### 根因
1. 请求hash策略不合理，热点key全部打到同一个节点；
2. 分库分表分片key选择不好，数据倾斜；
3. 流量分发策略缺陷；
4. 业务热点数据集中。

#### 解决方案

1. 合理设计分片key，打散热点；热点key增加随机后缀打散；
2. 负载均衡策略优化；避免固定hash带来倾斜；
3. 热点数据本地缓存，减轻集群节点压力；
4. 监控每个节点的CPU、内存、QPS，识别负载倾斜；
5. 必要时做分片重平衡。

### 4 服务治理缺失

#### 现象

服务数量变多之后：没有注册发现、没有监控、没有链路追踪；调用关系混乱；出问题很难定位；接口无管控，随便调用。

#### 危害

线上故障排查困难；不知道服务之间依赖关系；接口超时、重试乱配置，引发雪崩；没有版本管理，上线风险高。

#### 根因

早期业务简单，忽略服务治理；缺少注册中心、配置中心、链路追踪、接口管控。

#### 解决方案

1. 注册&配置中心：Nacos/Apollo，管理服务实例、配置；
2. 链路追踪SkyWalking/Pinpoint，完整记录调用链路；
3. 完善监控告警：QPS、RT、异常数、错误率；
4. 接口契约管理，接口版本控制；
5. 管控重试、超时参数，禁止无限重试；
6. 完善日志、异常埋点。

### 5 容量规划不足

#### 现象

大促、活动来临，流量突增，系统资源不足；CPU、内存、数据库连接、磁盘打满。平时正常，峰值直接崩。

#### 危害

峰值流量到来直接系统故障，业务不可用。

#### 根因

1. 没有评估峰值流量；只按日常流量设计；
2. 没有压测，不知道系统真实水位；
3. 没有预留安全余量；
4. 忽略数据库、中间件容量，只评估应用服务。

#### 解决方案

1. 梳理业务峰值，预估流量，评估QPS、TPS；
2. 全链路压测，测出系统瓶颈；
3. 预留安全水位，一般预留2‑3倍余量；
4. 不仅评估应用，同时评估DB、Redis、MQ、磁盘、带宽；
5. 大促前扩容，峰值过后缩容；
6. 设置水位告警，接近阈值提前预警。

> 坑：很多人只评估应用，忽略数据库、中间件，实际瓶颈经常出现在中间件。

### 6 限流缺失

#### 现象

突发大流量、恶意请求涌入，超出系统处理能力；大量请求涌入把DB、Redis打垮，引发雪崩。

#### 危害

正常用户请求也被拖垮；系统整体不可用。

#### 根因

没有流量保护机制，来了多少请求就处理多少；没有对接口、用户、IP做流量限制。

#### 解决方案

1. 多层限流：网关层限流、应用层限流；
2. 限流维度：全接口QPS、单用户、IP、热点参数限流；
3. 常用算法：令牌桶、漏桶；Sentinel实现；
4. 超过阈值直接拒绝，返回友好提示；保护下游资源；
5. 限流阈值根据压测结果设置，不是拍脑袋；
6. 监控限流触发次数告警。

> 面试：限流目的：保护系统，拒绝多余流量，保证有限资源给正常请求。

### 7 降级缺失

#### 现象

下游依赖服务故障，自身没有降级逻辑；依赖出问题，本服务全部接口报错，核心业务也受影响。

#### 危害

非核心业务故障拖垮核心业务；故障扩散。

#### 根因

没有区分核心、非核心业务；依赖出故障时没有兜底返回；全部链路强依赖第三方。

#### 解决方案

1. 业务区分核心链路、非核心链路；
2. 非核心功能故障时直接关闭，返回兜底数据；
3. 降级策略：返回缓存旧数据、返回默认值、直接关闭该功能；
4. 可以人工开关，也可以自动触发降级；
5. 大促主动关闭非核心功能，节约资源给到核心业务。

> 例子：商品详情页，推荐广告是非核心，广告服务挂了，直接关闭推荐，商品查询不能受影响。

### 8 熔断缺失

#### 现象

下游服务故障、大量超时报错；上游还持续大量调用故障下游；大量请求卡在等待下游返回，线程耗尽，拖垮自身服务，故障向上传导。

#### 危害

故障向上蔓延，级联雪崩；线程池被打满，本服务也不可用。

#### 根因

没有熔断机制；下游异常仍然不停调用；没有失败统计、断开逻辑。

#### 解决方案

1. 使用Sentinel/Hystrix实现熔断；
2. 统计失败率，失败达到阈值打开熔断；短时间内不再调用下游；直接走fallback兜底；
3. 熔断半开状态，少量请求探测下游是否恢复；恢复后关闭熔断；
4. 设置合理接口超时时间，避免线程无限等待；
5. 监控熔断触发告警。

> 面试区分：
- **限流**：挡住外部来的流量，保护自己；
- **熔断**：下游坏了，停止调用下游，保护自己；
- **降级**：主动关掉非核心业务，返回兜底结果。

### 面试速记背诵

1. **单点故障**：单实例宕机业务瘫痪 → 多实例集群、主从副本、多可用区、故障演练
2. **扩展性不足**：流量上涨无法扩容 → 微服务拆分、读写分离分库分表、缓存MQ异步、优先水平扩展
3. **负载不均**：部分节点压力极高，其余空闲 → 合理分片key、打散热点、监控各节点负载
4. **服务治理缺失**：调用混乱，故障难排查 → 注册配置中心、链路追踪、监控告警、管控超时重试
5. **容量规划不足**：峰值流量打垮系统 → 评估峰值、全链路压测、预留余量、中间件也要评估
6. **限流缺失**：突发流量压垮系统 → 网关+应用多层限流，令牌桶/漏桶，保护下游
7. **降级缺失**：非核心故障影响核心业务 → 区分核心非核心，返回兜底数据，大促主动降级
8. **熔断缺失**：下游故障，故障向上雪崩 → 统计失败率，熔断+半开探测，fallback兜底，设置超时

### 高频连环面试题

1. 限流、熔断、降级三者区别，分别什么场景使用？
2. 什么是水平扩展和垂直扩展？优先选择哪一个？
3. 什么是雪崩效应，如何从架构层面防止雪崩？
4. 容量规划怎么做，为什么不能只评估应用服务？
5. 负载不均一般会出现在哪些组件，怎么解决？

## 10 网络稳定性问题

1. 网络延迟
2. 网络丢包
3. TCP 连接积压
4. TIME_WAIT 过多
5. 带宽打满
6. 负载均衡故障
7. NAT 端口耗尽

 **网络问题（高并发系统稳定性中的底层基础问题）** 的系统化说明。

网络层问题的本质是：

```text
系统之间通信不可靠 + 不稳定 + 不均匀
```

它通常直接影响：

- RPC调用
- 微服务通信
- 分布式系统一致性
- MQ / DB访问

网络问题本质是：

```text
通信不稳定 + 资源有限 + 拓扑复杂
```

可以归纳为 3 大类：

| 类别         | 问题                        |
| ------------ | --------------------------- |
| 传输问题     | 延迟、丢包、带宽            |
| 连接问题     | TCP积压、TIME_WAIT、NAT耗尽 |
| 基础设施问题 | 负载均衡故障                |

------

**网络问题演化链**

典型故障传播路径：

```text
网络延迟上升
↓
RPC超时
↓
重试风暴
↓
连接积压
↓
服务雪崩
```



> 答题范式：**现象 → 危害 → 根因 → 解决方案 + Java业务落地 + 面试坑点**，承接前面9大模块，线上很多故障根源实际是网络层问题。

### 1 网络延迟

#### 现象

接口RT整体抬高；服务之间调用耗时变长，业务本身逻辑执行很快，但网络耗时占比很高；链路追踪看到大量时间消耗在网络等待。

#### 危害

接口响应慢；线程被长时间占用，并发吞吐量下降；容易触发调用超时，引发重试、雪崩。

#### 根因

1.跨机房、跨地域调用，物理距离远；
2.服务器CPU/网卡压力大，数据包处理慢；
3.带宽压力大，数据包排队；
4.网关、LB转发耗时；
5.系统内核、网卡缓冲区过小。

#### 解决方案

1.尽量同机房/同可用区部署，减少跨机房调用；
2.关键服务就近访问，避免跨地域远程调用；
3.引入缓存，减少远程调用次数；
4.设置合理RPC超时时间，避免线程长时间挂起；
5.监控链路各段耗时，区分是业务耗时还是网络耗时。

>坑：很多人直接认为慢是代码慢，实际是网络延迟拖慢整体RT。

### 2 网络丢包

#### 现象

请求偶发超时；调用时好时坏；TCP频繁重传；偶发报错，复现难；抓包看到大量retransmit重传包。

#### 危害

RT抖动、随机超时；大量重传进一步消耗带宽CPU；业务随机失败，很难复现排查。

#### 根因

1.网卡、交换机硬件故障；
2.带宽打满，队列溢出丢包；
3.内核缓冲区设置过小，数据包被丢弃；
4.防火墙、安全策略丢弃部分报文。

#### 解决方案

1.抓包分析确认是否存在TCP重传；
2.检查带宽水位，避免带宽跑满；
3.调大内核网卡缓冲区参数；
4.排查防火墙、安全组策略；
5.RPC做好重试，注意重试幂等，避免丢包后疯狂重试放大压力。



### 网络丢包、延迟高

#### 核心本质

物理网络、机房链路、带宽瓶颈导致数据包丢失、传输耗时暴涨，跨机房/跨区域调用体验极差。

#### 产生原因

- 跨机房、跨运营商、跨地域远程调用；
- 交换机/路由器硬件故障、链路抖动；
- 网卡带宽打满、流量挤占、大报文传输；
- 防火墙、安全策略、路由配置异常；
- 容器环境网络隔离、NAT转发损耗。

#### 危害

- 接口RT飙升、随机超时、报文重传；
- 分布式事务、MQ、RPC通信不稳定；
- 数据传输不完整、业务偶发异常。

#### 解决方案

- 核心服务**同机房部署**，就近调用，减少跨机房；
- 带宽扩容、大报文拆分、数据压缩传输；
- 优化路由、隔离业务网络与运维网络；
- 关键RPC/MQ开启重传机制+超时控制；
- 监控网络延迟、丢包率、带宽使用率。

### 3 TCP连接积压

#### 现象

服务端连接队列溢出；大量请求建立连接失败；客户端报connect timeout；服务能处理请求，但新连接建立失败。

#### 危害

客户端无法建立连接，业务大量报错。

#### 根因

1.服务端accept处理慢，新连接堆积在内核半连接/全连接队列；
2.内核tcp‑syn‑backlog、服务端backlog参数设置太小；
3.服务处理线程耗尽，来不及消费新连接。

#### 解决方案

1.调大内核`tcp_syn_backlog`，同时应用服务（Nginx、Tomcat、Netty）调大backlog；
2.保证服务线程池足够，不要耗尽线程，尽快accept新连接；
3.监控连接队列溢出计数；
4.不要短时间疯狂新建大量TCP连接，尽量复用连接。



### TCP 连接耗尽

#### 核心成因

- 短连接频繁创建：服务间采用短连接通信，频繁创建、销毁TCP连接，每次连接都需要经过三次握手、四次挥手，不仅消耗CPU资源，还会导致大量连接处于TIME_WAIT状态，无法快速释放。
- TIME_WAIT过多：TCP连接关闭后，会进入TIME_WAIT状态（默认2MSL），若短连接频繁创建，TIME_WAIT连接会持续堆积，占用大量端口资源，导致新连接无法建立。
- 连接池配置不合理：TCP连接池最大连接数设置过小，无法满足高并发请求；连接池空闲连接回收时间过长，导致闲置连接占用端口资源，无法释放。
- 请求量突增：高并发场景下，请求量暴涨，需要大量TCP连接支撑，超出服务器端口承载能力，导致连接耗尽。
- 连接未正常释放：代码逻辑缺陷，导致TCP连接创建后未正常关闭，出现连接泄漏，长期占用端口资源；网络异常导致连接中断，未触发正常关闭流程，形成无效连接。

#### 造成危害

TCP连接耗尽，新请求无法建立连接，接口直接报错、请求失败；TIME_WAIT连接堆积，占用大量端口和内存资源，导致服务器性能下降；服务间通信中断，跨服务调用失败，引发分布式系统链路断裂；严重时服务器无法对外提供任何网络服务，核心业务全面瘫痪。

#### 解决方案

- 优化连接方式：将短连接改为长连接（如HTTP/2、WebSocket），减少连接创建、销毁的频率，降低TIME_WAIT堆积；核心服务间采用长连接池管理，复用连接，提升连接利用率。
- 优化TIME_WAIT参数：调整系统内核参数，缩短TIME_WAIT超时时间（如net.ipv4.tcp_fin_timeout），加快连接释放；开启TIME_WAIT快速回收（如net.ipv4.tcp_tw_recycle），减少TIME_WAIT连接堆积。
- 合理配置连接池：根据业务并发量，设置合适的TCP连接池最大连接数、空闲连接回收时间；核心服务与非核心服务使用独立连接池，避免连接资源竞争。
- 控制请求量与连接泄漏：在网关层、服务层设置限流，避免请求量突增导致连接耗尽；规范代码逻辑，使用try-finally机制确保连接正常关闭，排查并修复连接泄漏问题。
- 监控与调优：实时监控TCP连接数、TIME_WAIT连接数、端口占用情况，设置预警阈值；定期调优系统内核参数，根据业务场景优化连接配置；当连接即将耗尽时，及时扩容服务器或调整连接策略。

### TCP 连接阻塞 / 全连接队列溢出

#### 核心本质

TCP 三次握手完成后，**全连接队列(accept队列)** 满，服务端消费连接太慢，新连接无法被 `accept` 处理，导致连接建立失败、SYN 超时。

#### 产生原因

- 服务端业务处理慢、消费连接能力弱，accept 不及时；
- 全连接队列、半连接队列内核参数配置过小；
- 瞬间高并发建连，TCP 队列承载不足；
- 服务线程阻塞、卡顿，无法及时取走连接。

#### 危害

- 客户端连接超时、握手失败、接口报错；
- 大量 SYN 重传，网络拥堵；
- 新流量无法接入，服务对外不可用。

#### 解决方案

- 调整内核参数：`somaxconn`（全连接队列）、`tcp_syncookies`；
- 优化服务端处理速度，避免IO阻塞、慢逻辑；
- 增加服务实例扩容，分摊建连压力；
- 接口层限流，防止突发海量连接冲击。

### 4 TIME_WAIT过多

#### 现象

服务器大量TIME_WAIT状态连接；占用大量端口资源；新建连接报端口不足。

#### 危害

端口被耗尽，客户端无法发起新TCP连接；业务报错。

#### 根因

TCP断开时主动关闭方进入TIME_WAIT，默认保持2MSL；短连接大量频繁创建销毁，每次客户端主动关闭，产生大量TIME_WAIT。

#### 解决方案

1.业务优先使用长连接连接池（Netty、HttpClient连接池、RPC框架长连接），减少频繁创建销毁TCP；
2.调整内核参数：`tcp_tw_reuse`开启，允许复用TIME_WAIT连接；
3.不要开启`tcp_tw_recycle`（NAT环境下会出问题）；
4.监控机器TIME_WAIT数量。

>面试坑：`tcp_tw_recycle`不建议线上开启，NAT环境会导致大量建连失败。



### 大量 TIME_WAIT / CLOSE_WAIT

#### 核心本质

- **TIME_WAIT**：主动关闭方需等待2MSL，短连接大量频繁关闭，导致套接字资源占满；
- **CLOSE_WAIT**：被动关闭，服务端收到FIN后**未主动close**，连接僵死挂起。

#### 产生原因

1. TIME_WAIT
   - 业务大量短连接，请求完立即断开；
   - 接口调用频繁，不断新建/关闭TCP连接；
2. CLOSE_WAIT
   - 代码未手动关闭流、连接、Response；
   - 对方提前断开，我方业务卡死不执行关闭逻辑；
   - 连接资源未使用 try-with-resources 自动回收。

#### 危害

- 系统**文件描述符FD耗尽**，无法新建TCP连接；
- 端口资源耗尽，服务无法对外通信；
- 接口大面积连接异常、服务瘫痪。

#### 解决方案

- 业务改用**长连接复用**，减少短连接；
- 优化内核：开启 `tcp_tw_reuse`、`tcp_tw_recycle`；
- 代码规范：所有网络连接、IO流自动关闭；
- 定时清理僵死连接，设置连接空闲销毁时间；
- 监控FD数量、TCP状态分布告警。

### 5 带宽打满

#### 现象

机器网卡带宽跑满；网络RT飙升、丢包；大报文传输场景尤为明显。

#### 危害

机器上所有业务的网络请求全部受影响，不是某一个接口，整机网络恶化。

#### 根因

1.大对象、大JSON、大消息体大量传输；
2.日志大量输出，占用网卡；
3.流量突增超过机器网卡上限。

#### 解决方案

1.限制报文大小，禁止传输大对象；大数据传ID或者url；
2.网卡带宽监控告警，提前发现水位；
3.业务拆分，大流量业务隔离机器；
4.必要升级网卡带宽；
5.MQ/RPC限制消息最大body大小。

### 6 负载均衡故障

#### 现象

Nginx/网关/LB故障；部分实例流量切不过去；流量全部打到少量后端节点；请求转发异常、报错、连接中断。

#### 危害

流量分发异常；部分机器过载，部分机器空闲；业务部分或者全部不可用。

#### 根因

1.LB节点本身单点故障；
2.健康检查配置错误，没有剔除故障后端；
3.负载均衡算法不合理，流量分配倾斜；
4.会话粘连导致流量不均。

#### 解决方案

1.LB高可用集群部署，避免单点；
2.配置正确健康检查，及时摘除异常后端实例；
3.合理选择负载均衡策略，尽量少用sticky会话粘连；
4.监控LB状态、后端节点连接数、QPS；
5.做好故障演练。

### 7 NAT端口耗尽

#### 现象

机器作为客户端向外大量发起连接，NAT源端口耗尽；新建连接失败，报cannot assign requested address。

#### 危害

对外请求大量失败，业务报错。

#### 根因

客户端大量短连接，每次使用不同NAT源端口；端口总数有限，大量TIME_WAIT占住端口，端口被耗尽。多出现在网关、代理、高并发客户端。

#### 解决方案

1.客户端务必使用连接池长连接，复用TCP连接，减少新建连接；
2.开启`tcp_tw_reuse`，复用TIME_WAIT端口；
3.调大ip_local_port_range扩大可用端口范围；
4.减少短连接使用。



### 连接池耗尽（HTTP/Dubbo/Feign/OkHttp）

#### 核心本质

短连接滥用或连接池参数不合理，**长连接数量打满**，新请求拿不到连接，全程阻塞、超时。

#### 产生原因

- 连接池最大连接数设置过小；
- 调用下游接口无超时、线程卡死占用连接不释放；
- 同步串行调用多依赖，连接占用时间过长；
- 未复用长连接，频繁创建销毁短连接；
- Dubbo/Feign 底层连接未合理回收。

#### 危害

- 连锁调用阻塞，服务雪崩；
- 大量请求排队、线程积压、CPU 飙升；
- 下游依赖不可用直接拖垮当前服务。

#### 解决方案

- 合理配置各类客户端连接池：最大连接、空闲超时、获取超时；
- 所有远程调用**强制加超时、熔断、降级**；
- 核心/非核心依赖**线程池隔离、连接池隔离**；
- 开启长连接复用，减少频繁建连断连；
- 监控连接池活跃数、等待队列、拒绝数。



### 超时风暴 / 重试风暴

#### 核心本质

下游服务卡顿超时 → 上游统一重试、批量重试 → 流量瞬间翻倍、放大，层层传导压垮整条调用链。

#### 产生原因

- 未做重试限制，超时、异常默认无限重试；
- 无退避策略，失败立即暴力重试；
- 集群所有实例同时重试，流量叠加；
- 缺少熔断、降级，故障无法快速隔离。

#### 危害

- 单节点故障扩散为**全链路雪崩**；
- 下游压力成倍暴增，彻底打挂依赖服务；
- 响应时间持续恶化，全线业务不可用。

#### 解决方案

- 禁止无条件重试，限制**最大重试次数**；
- 加入**指数退避+随机休眠**，避免同时重试；
- 引入熔断组件（Sentinel/Resilience4j），故障节点快速熔断；
- 超时、异常场景快速降级，拒绝无效流量；
- 网关层限流、削峰，控制入口流量。



### 跨服务调用连锁故障

#### 核心成因

- 服务降级缺失：下游服务出现异常（如超时、宕机）时，上游服务未配置降级策略，仍持续调用下游服务，导致自身线程阻塞，进而影响更上游服务，形成连锁故障。
- 调用链过长：分布式系统中，服务调用链层级过多（如A调用B、B调用C、C调用D），某一中间服务异常，会沿着调用链向上传导，导致整个调用链路瘫痪。
- 服务依赖过强：核心服务依赖多个下游服务，且无冗余依赖，某一下游服务故障，会直接导致核心服务无法正常运行，进而影响依赖核心服务的其他服务。
- 无熔断与隔离机制：下游服务失败率过高时，未触发熔断，上游服务持续重试，放大故障影响；服务间无隔离（如线程池隔离、进程隔离），某一服务异常会占用其他服务的资源，引发连锁崩溃。
- 监控与预警缺失：未实时监控服务调用链路，无法及时发现中间服务异常，导致故障持续扩散，形成连锁反应。

#### 造成危害

单个服务异常沿调用链快速传导，导致多个服务相继故障，形成“雪崩效应”；核心业务因调用链断裂无法正常开展，造成业务中断、用户流失；故障排查难度大，因调用链过长，难以定位异常源头；服务资源被异常调用占用，正常请求无法被处理，进一步加剧故障影响。

#### 解决方案

- 配置降级与熔断策略：使用Sentinel、Hystrix等框架，为下游服务配置熔断阈值，当失败率达到阈值时，触发熔断，暂停调用，避免故障扩散；设置降级逻辑，下游服务异常时，返回默认结果或缓存数据，保障上游服务正常运行。
- 缩短调用链：梳理服务调用链路，拆分过长的调用链，减少服务依赖层级；合并冗余调用，避免不必要的跨服务调用，降低故障传导风险。
- 冗余依赖与容错：核心服务对下游关键服务采用多实例、多链路冗余部署，某一实例故障时，切换至备用实例；避免核心服务强依赖单一下游服务，减少故障影响范围。
- 服务隔离：采用线程池隔离（为不同下游服务分配独立线程池）、进程隔离、机房隔离，避免某一服务异常占用其他服务的资源，防止故障扩散；核心服务与非核心服务隔离部署，保障核心业务稳定性。
- 完善监控与预警：部署分布式链路追踪工具（如SkyWalking、Zipkin），实时监控服务调用链路，快速定位异常源头；设置服务调用超时、失败率预警阈值，异常时及时告警，快速介入处理。

#### 解决方案

- 优化大Key：拆分Redis等缓存中的大Key，将大Value拆分为多个小Key，减少单次传输数据量；对大Key进行压缩存储，传输时采用数据压缩（如GZIP），降低带宽消耗。
- 控制批量传输：批量数据传输采用分批、异步传输，避免单次传输大量数据；核心批量传输场景，选择低峰期进行，减少带宽压力。
- 优化报文交互：减少服务间大报文交互频率，合并重复请求；对传输数据进行压缩，使用高效的序列化框架，减小报文体积；避免传输无用数据，精简传输字段。
- 过滤无效流量：拦截恶意爬虫、无效请求，减少无用数据传输；核心服务使用内网通信，避免公网传输的带宽损耗；对跨机房调用进行带宽控制，避免带宽滥用。
- 提升带宽配置与监控：根据业务需求，提升服务器网卡带宽配置；核心服务使用独立网卡，避免带宽竞争；实时监控网卡带宽使用率、网络延迟，设置预警阈值，及时排查带宽异常。

### 面试速记背诵

1. **网络延迟**：RT高，网络耗时占比大 → 就近部署、缓存减少调用、设置合理超时
2. **网络丢包**：偶发超时、TCP重传 → 抓包定位，调内核缓冲区，带宽告警，做好幂等重试
3. **TCP连接积压**：新建连接失败，队列溢出 →调大backlog，保证服务线程，复用连接
4. **TIME_WAIT过多**：大量TIME_WAIT占端口 →优先长连接连接池；开启tcp_tw_reuse，禁用tcp_tw_recycle
5. **带宽打满**：整机网络RT升高、丢包 →限制报文大小，带宽监控，隔离大流量业务
6. **负载均衡故障**：流量分发异常，负载不均 →LB集群高可用，正确健康检查，少用会话粘连
7. **NAT端口耗尽**：客户端新建连接失败 →长连接连接池；扩大端口范围；tcp_tw_reuse

### 高频连环面试题

1. TIME_WAIT是什么？大量TIME_WAIT怎么处理？tcp_tw_recycle为什么不建议开？
2. 线上偶发超时，怎么区分是业务慢、网络延迟、丢包还是服务端处理不过来？
3. NAT端口耗尽是什么场景，怎么解决？
4. backlog参数作用，连接队列溢出会出现什么现象？

## 11 运维 / 发布问题

1. 配置错误
2. 发布失败
3. 灰度策略错误
4. 回滚失败
5. 参数配置不合理
6. 监控缺失
7. 告警不及时

**运维 / 发布问题（生产环境稳定性中非常关键的一类问题）** 的系统化说明。这一类问题的特点是：

```text
代码可能没问题，但“上线/运维操作”直接导致事故
```

运维 / 发布问题本质是：

```text
人为操作 + 自动化不足 + 可观测性不足
```

可以归纳为 3 大类：

| 类别           | 问题                         |
| -------------- | ---------------------------- |
| 配置与发布问题 | 配置错误、发布失败、回滚失败 |
| 策略问题       | 灰度策略错误、参数配置不合理 |
| 可观测性问题   | 监控缺失、告警不及时         |

------

#### 核心规律（非常重要）

运维类事故典型演化链：

```text
配置错误
↓
发布失败 / 灰度错误
↓
线上异常
↓
监控缺失
↓
告警不及时
↓
事故扩大
```

> 答题范式：**现象 → 危害 → 根因 → 解决方案 + 业务落地 + 面试坑点**。线上故障很大一部分不是代码bug，而是发布、配置、运维操作引发。

### 1 配置错误

#### 现象

服务启动失败、运行异常；部分环境行为错乱；不同环境表现不一致；重启后故障复现。配置中心、yml、环境变量、数据库配置写错。

#### 危害

服务不可用；业务逻辑异常；线上脏数据；资源参数配置过小直接压垮服务。

#### 根因

1. 测试环境配置直接复制到线上，未核对；
2. 配置项key写错、大小写错误；
3. 配置推送未生效，服务未刷新配置；
4. 多环境混用配置。

#### 解决方案

1. 区分开发、测试、生产三套独立配置，禁止直接拷贝；
2. 配置变更走变更流程，双人核对；
3. 配置修改优先灰度推送，不全量下发；
4. 关键配置启动做校验，非法配置直接拒绝启动；
5. 配置版本留存，支持快速回退旧配置。

> 坑：配置改完不重启/不刷新，实际并未生效，误以为配置已经改好。

### 2 发布失败

#### 现象

版本打包错误、部署脚本异常；部分实例发布成功，部分实例失败；集群版本混杂，同时存在新旧版本。

#### 危害

集群同时跑多套版本，接口兼容问题；部分机器异常，业务随机报错。

#### 根因

1. 打包依赖冲突、编译报错；
2. 机器资源不足，部署脚本执行异常；
3. 发布过程网络中断；
4. 没有发布校验，失败实例没有自动停止。

#### 解决方案

1. 发布前流水线先跑编译、单元测试、集成测试；
2. 分批发布，先少量实例；发布后做健康检查；失败立即停止发布；
3. 禁止集群新旧版本长期共存；失败节点隔离；
4. 保留上一个稳定版本，支持一键回滚。

### 3 灰度策略错误

#### 现象

灰度放量节奏错误；本该小流量验证，直接全量上线；灰度规则写错，流量全部打到新版本；或者灰度切流异常，流量打不到新版本。

#### 危害

有bug的新版本直接接收全部线上流量，引发大规模线上故障。

#### 根因

1. 灰度比例配置错误；
2. 灰度标签、路由规则写错；
3. 没有先小流量，直接全量；
4. 灰度期间没有观察指标。

#### 解决方案

1. 灰度流程：少量实例 → 小比例流量 → 逐步放大；
2. 灰度期间紧盯QPS、RT、错误率、异常告警；
3. 设置熔断条件，指标异常自动停止灰度；
4. 灰度不通过，直接切回旧版本。

> 坑：很多故障来自“灰度没做，直接全量发布”。

### 4 回滚失败

#### 现象

线上出问题执行回滚，但是回滚之后故障依旧，甚至问题加重。

#### 危害

故障持续时间拉长，业务影响扩大。

#### 根因

1. 不仅代码变更，同时改了数据库表结构、缓存数据；只回滚代码，数据没有回滚；
2. 配置没有跟着回滚；
3. 中间件已经写入新格式消息，旧版本无法解析；
4. 发布工具回滚脚本异常。

#### 解决方案

1. 发布前评估：变更是否涉及DB、缓存、MQ数据；数据是否可回滚；
2. DB变更优先向前兼容，禁止破坏性变更；
3. 回滚需要同时回滚代码、配置；
4. 预演回滚流程，确认回滚路径可用；
5. 如果数据不可逆，回滚代码之外还要做数据修复补偿。

> 高频面试坑：只回滚代码，但是数据库结构、缓存、MQ消息已经被新版本修改，回滚无效。

### 5 参数配置不合理

#### 现象

JVM参数、线程池、连接池、中间件参数配置不合理；平时正常，流量上涨就出问题。例如线程池核心线程、最大线程、队列大小、JVM堆内存、数据库连接数。

#### 危害

流量上来线程耗尽、连接耗尽、OOM、GC频繁，服务雪崩。

#### 根因

1. 直接使用默认参数，没有根据业务压测调整；
2. 测试环境机器配置低，线上机器配置高，参数照搬测试；
3. JVM堆内存设置过大，导致GC停顿长，或者过小频繁GC。

#### 解决方案

1. 根据压测结果设置参数，不要拍脑袋；
2. 线程池、连接池不能无限大也不能过小；拒绝无界队列；
3. JVM堆内存根据机器内存合理分配；
4. 参数变更也要走变更流程；变更后观察GC、线程、连接指标。

### 6 监控缺失

#### 现象

故障发生后，不能及时发现；问题已经用户反馈过来才知道；缺少核心指标，出问题无从排查。

#### 危害

故障发现晚，故障持续时间变长；缺少指标，定位困难。

#### 根因

只关注业务功能，忽略监控建设；核心指标没有埋点；缺少JVM、中间件、机器层面监控。

#### 解决方案

1. 四层监控：机器层CPU、内存、磁盘、网络；JVM层GC、线程；业务层QPS、RT、错误率；中间件Redis/MQ/DB指标；
2. 核心接口、核心业务必须埋点；
3. 链路追踪，记录调用耗时、异常；
4. 上线新服务必须配套监控。

### 7 告警不及时

#### 现象

监控数据有采集，但是告警没触发；告警阈值设置不合理；告警风暴，大量告警淹没关键告警；告警无人接收。

#### 危害

故障发生但是收不到告警，等到用户投诉才发现；告警太多，人对告警麻木，真正故障被忽略。

#### 根因

1. 告警阈值设置过高/过低；
2. 告警渠道故障；
3. 没有告警收敛，瞬时大量告警刷屏；
4. 告警没有明确责任人。

#### 解决方案

1. 合理设置告警阈值，区分警告、严重告警；
2. 告警收敛、去重，抑制告警风暴；
3. 重要告警多渠道通知；值班机制；
4. 定期演练告警，验证告警是否正常触发；
5. 低优先级info类减少告警，只关注核心故障。

### 面试速记背诵

1. **配置错误**：配置写错、环境混淆 → 多环境隔离，配置变更双人复核，配置版本可回退
2. **发布失败**：部分实例发布失败，版本混杂 → CI流水线校验，分批发布，失败停止发布
3. **灰度策略错误**：错误直接全量发布 → 由小到大逐步放量，监控指标，异常终止灰度
4. **回滚失败**：只回滚代码，DB/缓存/MQ数据未回滚 → 变更评估数据兼容性，优先向前兼容，必要数据补偿
5. **参数配置不合理**：JVM、线程池、连接池参数不合理 → 依据压测配置，拒绝无界队列，变更观察指标
6. **监控缺失**：故障靠用户反馈 → 机器、JVM、业务、中间件四层监控，链路埋点
7. **告警不及时**：告警不触发、告警风暴 → 合理阈值，告警收敛，定期验证告警有效性

### 高频连环面试题

1. 线上发布之后故障，回滚完问题还在，会是什么原因？
2. 什么叫向前兼容，数据库变更为什么要向前兼容？
3. 线上一套完整监控包含哪些维度？
4. 灰度发布的流程是什么，灰度要观察哪些指标？

5. 分库分表不均
6. 热分片

**数据问题（高并发系统中“数据层治理与数据分布问题”）** 的系统化整理。这一类问题本质是：

```text
数据结构 / 数据分布 / 数据生命周期设计不合理
```

数据问题本质是：

```text
数据分布不均 + 生命周期设计不合理 + 缺乏治理策略
```

可以归纳为 4 大类：

| 类别           | 问题                   |
| -------------- | ---------------------- |
| 数据正确性问题 | 脏数据                 |
| 数据分布问题   | 数据倾斜、热分片       |
| 数据规模问题   | 数据膨胀、历史数据过大 |
| 架构设计问题   | 分库分表不均           |

------

#### 核心规律（非常重要）

数据问题的典型演化链：

```text
数据增长
↓
未归档
↓
查询变慢
↓
索引变大
↓
系统性能下降
```

> 答题范式：**现象 → 危害 → 根因 → 解决方案 + 业务落地 + 面试坑点**，聚焦数据库、存储层面的数据本身引发的故障，承接前面11大模块。

### 1 脏数据

#### 现象

数据库存在错误、不一致、重复、无效数据；业务逻辑执行结果不符合预期；部分记录异常，查库看到不合理的值。

#### 危害

业务逻辑错乱，订单、资金出错；统计报表错误；引发后续连锁业务异常。

#### 根因

1. 并发更新缺少锁/事务控制，多线程同时写同一行；
2. 分布式事务部分成功部分失败；
3. MQ重复消费未做幂等，产生重复数据；
4. 程序bug直接写入错误值；
5. 人为数据库误操作；
6. 缓存与数据库不一致。

#### 解决方案

1. 数据库层面：唯一索引、事务、行锁防止并发写异常；
2. 业务侧做好幂等，避免重复写入；
3. 缓存DB采用Cache‑Aside模式，配合延迟双删；
4. 增加定时对账任务，定期校验修复脏数据；
5. 数据库操作禁止直接手工改线上，变更走流程；
6. 关键业务增加状态机校验。

> 坑：脏数据一旦产生，单纯修复代码无法修复已经存在的旧数据，需要数据补偿。

### 2 数据倾斜

#### 现象

同一个库内，部分表数据量巨大，其他表很小；或者同一张表内部，部分字段值行数占比极高；SQL执行很慢。

#### 危害

大表查询更新慢；数据库CPU、IO被少数热点数据打满；索引失效，SQL全表扫描；整体数据库性能被拖垮。

#### 根因

1. 业务字段分布不均，大量记录同一个状态、同一个用户ID；
2. 统计SQL按热点值分组；
3. 索引设计不合理。

#### 解决方案

1. 优化SQL，避免对热点值做大结果集查询；
2. 拆分大表，冷热数据分离；
3. 热点数据做缓存，减少DB查询；
4. 调整业务逻辑，打散热点；
5. SQL优化，避免扫描大量倾斜数据。

### 3 数据膨胀

#### 现象

单表数据量持续暴涨；表体积越来越大；索引也同步膨胀；查询、更新、DDL执行耗时显著变长。

#### 危害

磁盘占用快速上涨；备份、迁移变慢；索引效率下降；alter表锁表时间变长；数据库性能持续下降。

#### 根因

1. 日志、流水、历史记录不断写入，没有清理；
2. 业务不断新增字段，大字段存储在主表；
3. 没有归档、删除策略。

#### 解决方案

1. 冷热分离：历史流水归档到归档库，主库只保留近期热数据；
2. 大字段独立拆分到附属表；
3. 设置过期清理策略，定时删除无用数据；
4. 分表，按时间拆分；
5. 监控表数据量、磁盘占用。

### 4 历史数据过大

#### 现象

线上业务表存放数年历史数据；绝大部分是很久不会访问的历史数据；日常业务只访问最近一小部分。

#### 危害

查询扫描数据量大；备份时间长；磁盘占用高；DDL变更风险高。

#### 根因

只写不删，没有历史数据生命周期管理。

#### 解决方案

1. 冷热数据分离，热数据在线业务库，历史数据归档至归档库；
2. 按时间分表；
3. 不需要的历史数据做清理；
4. 统计分析走归档库，不要在线业务库做统计；
5. 业务查询只查必要时间范围，禁止全表查询。

> 坑：很多系统直接把几年全部流水放在业务主库，越跑越慢。

### 5 分库分表不均

#### 现象

做了分库分表之后，部分分库分表数据量巨大，其他分片数据很少，分片数据分布不均衡。

#### 危害

某几个分片先到达容量上限；整体存储能力上不去；压力集中在部分库表，失去分库分表的效果。

#### 根因

1. 分片key选择不合理，业务数据分布不均匀；
2. 热点业务id全部hash到同一个分片；
3. 后期业务增长，原有分片策略不再适配。

#### 解决方案

1. 合理选择分片键，保证数据打散；避免使用热点ID直接做分片key；
2. 热点id拼接随机后缀打散；
3. 提前评估数据分布，上线前做数据模拟；
4. 监控每个分片的数据量、QPS；
5. 必要时做分片重拆分、平滑迁移。

> 面试坑：不是做了分库分表就万事大吉，分片key选错会带来分片倾斜。

### 6 热分片

#### 现象

分库分表场景，某一个分片QPS极高，CPU、IO打满，其余分片压力很低；整体系统瓶颈卡在这一个分片。

#### 危害

单分片成为瓶颈，整体TPS上不去；该分片数据库容易宕机，引发业务故障。

#### 根因

1. 分片key为热点业务ID，大量请求落到同一个分片；
2. 热点用户、热点商品全部落在同一个分片。

#### 解决方案

1. 热点key打散，增加随机后缀，拆分到多个分片；
2. 热点数据前置缓存，大量请求不走数据库；
3. 热点业务单独隔离，独立库；
4. 监控每个分片的QPS、CPU、IO，识别热分片；
5. 非强顺序场景避免固定分片key。

### 面试速记背诵

1. **脏数据**：错误不一致数据 → 唯一索引、事务、幂等、定时对账补偿
2. **数据倾斜**：部分数据占比极高 → SQL优化、热点缓存、打散热点
3. **数据膨胀**：表持续变大，索引膨胀 → 归档清理，冷热分离，拆分大字段
4. **历史数据过大**：主库堆积大量旧数据 → 冷热归档、按时间分表，统计走归档库
5. **分库分表不均**：分片数据分布不平衡 → 合理分片key，上线模拟数据，监控分片容量
6. **热分片**：单个分片压力拉满 → 热点打散、热点缓存、业务隔离

## 13 安全类问题

1. DDoS 攻击
2. CC 攻击
3. 恶意刷接口
4. 暴力登录
5. Token 滥用

**安全类问题（高并发系统中的攻击面与防护问题）** 的系统化整理。这一类问题的本质是：

```text
系统被“恶意流量 + 非法访问 + 滥用行为”消耗资源
```

安全类问题本质是：

```text
恶意流量 + 身份滥用 + 自动化攻击
```

可以归纳为 3 大类：

| 类别         | 问题             |
| ------------ | ---------------- |
| 流量攻击     | DDoS、CC攻击     |
| 业务滥用     | 刷接口、暴力登录 |
| 身份安全问题 | Token滥用        |

------

#### 核心规律（非常重要）

安全攻击的典型链路：

```text
恶意流量进入
↓
接口被刷爆
↓
资源耗尽
↓
正常用户无法访问
↓
系统瘫痪
```

> 答题范式：**现象 → 危害 → 根因 → 解决方案 + 业务落地 + 面试坑点**，承接前面12大模块，安全攻击也会造成系统雪崩、业务故障。

### 1 DDoS 攻击

#### 现象

大量异常流量涌入，来源分散海量IP；带宽被直接打满；整机网络拥塞；正常用户请求被淹没；服务整体访问卡顿或者完全不可用。

#### 危害

带宽耗尽，整机瘫痪；业务整体不可访问；普通用户无法使用业务。

#### 根因

攻击者控制大量傀儡机器，发送海量恶意数据包，消耗带宽、服务器网络资源。

#### 解决方案

1. 接入高防IP、云DDoS防护，底层清洗大流量攻击；
2. 机房侧黑洞、流量清洗，把攻击流量隔离；
3. 限制单IP连接数；
4. 业务层做限流，无法对抗大流量DDoS，主要依靠底层防护；
5. 带宽扩容，预留冗余带宽。

> 坑：业务应用层代码很难防御DDoS，主要靠机房/云厂商底层防护。

### 2 CC 攻击

#### 现象

大量看起来正常的HTTP请求，IP分散，模拟真实用户访问；接口QPS突增；CPU、数据库、Redis被打满；带宽不一定跑满，但是服务资源耗尽。

#### 危害

服务CPU、DB、Redis资源耗尽，正常用户请求处理不过来，业务雪崩。

#### 根因

攻击者使用大量代理IP，构造合法http请求，消耗业务层计算资源，不打带宽，消耗应用、数据库资源。

#### 解决方案

1. 网关层限流：IP限流、接口QPS限流；
2. 验证码、人机校验，高风险场景触发滑块/验证码；
3. 识别异常UA、异常请求特征；
4. 拦截高频异常IP；
5. 接入WAFWeb应用防火墙；
6. 做好接口限流熔断保护下游存储。

> 区分：DDoS打**带宽**；CC打**业务资源（CPU/DB）**。

### 3 恶意刷接口

#### 现象

恶意高频调用业务接口，比如领券、抽奖、注册、投票；大量重复请求；产生大量脏数据；消耗库存、优惠券等业务资源。

#### 危害

业务资源被恶意消耗；业务逻辑被刷坏；产生大量脏数据；挤占正常用户资源。

#### 根因

接口没有防护，没有频率限制；爬虫脚本批量调用业务接口。

#### 解决方案

1. 接口增加用户维度限流，单用户单位时间最大请求次数；
2. 业务操作增加幂等校验，防止重复领取；
3. 关键业务增加验证码、人机验证；
4. 业务层增加风控规则，识别异常行为；
5. 黑名单封禁恶意账号、IP。

### 4 暴力登录

#### 现象

大量登录请求，不断尝试账号密码；接口大量报错；接口QPS上涨；数据库、缓存压力上涨；存在账号被破解风险。

#### 危害

账号密码被爆破；大量登录请求压垮登录服务；占用系统资源。

#### 根因

登录接口没有防护，攻击者循环遍历账号密码。

#### 解决方案

1. 账号登录失败次数限制，失败多次锁定账号；
2. IP维度限流，同一IP短时间大量登录直接拦截；
3. 多次失败触发验证码；
4. 登录接口增加风控，识别异常设备、异地登录；
5. 密码复杂度要求，禁止弱密码。

### 5 Token 滥用

#### 现象

token泄露、被盗；攻击者使用窃取token冒充正常用户访问接口；token长期不失效；token被复用。

#### 危害

攻击者盗用用户身份，操作用户数据；盗刷权益、篡改用户信息。

#### 根因

1. Token有效期设置过长；
2. Token泄露；
3. 退出登录没有主动销毁token；
4. 没有校验token设备、IP；
5. token不做签名校验，可被篡改。

#### 解决方案

1. 设置合理token过期时间，access_token短有效期，refresh_token刷新；
2. 用户退出、改密码时主动作废token；维护token黑名单；
3. token做签名，防止篡改；
4. 增加设备指纹校验，token绑定设备；异地异常触发二次校验；
5. HTTPS传输，防止抓包窃取token。

### 恶意刷接口、爬虫、CC攻击

#### 本质

恶意客户端/脚本高频、伪造、批量请求，无节制冲刷业务接口，挤占正常用户资源，拖垮应用与数据库，属于**业务层流量攻击**。

#### 成因

- 接口无防刷、无频次限制、无身份校验；
- 爬虫批量爬取数据，高频遍历接口；
- CC攻击伪造大量正常请求，消耗连接、线程、带宽；
- 对外接口暴露过全，参数无校验、无拦截。

#### 危害

- 服务器CPU、带宽、连接池被打满；
- 数据库查询激增，引发慢SQL、库压力雪崩；
- 正常用户请求延迟、超时、服务瘫痪；
- 敏感数据泄露、活动福利被恶意薅羊毛。

#### 解决方案

1. **多层限流防刷**
   网关层 + 应用层，按**IP、用户ID、设备号**维度限流；
2. **人机识别**
   验证码、滑块、行为校验、接口签名、Token鉴权；
3. **爬虫防护**
   User-Agent校验、高频封禁、动态密钥、数据加密返回；
4. **CC攻击防护**
   黑名单封禁、异常流量清洗、网关WAF、恶意IP拉黑；
5. **接口加固**
   入参校验、请求体限制、非法参数拦截、内网接口隔离；
6. **监控告警**
   异常QPS、短时间重复请求、高频错误实时告警。

---

###  重复提交导致超卖、重复发奖/重复业务

#### 本质

同一操作短时间多次提交，无防重机制，并发+重复请求叠加，引发**重复业务执行**，破坏数据一致性。

#### 成因

- 前端未做按钮置灰、防抖；
- 后端无全局防重、无唯一幂等标识；
- 网络卡顿、用户频繁点击、页面回退重提；
- MQ重复消费、RPC重试、接口重试导致重复执行；
- 并发扣减业务无锁、无原子控制。

#### 危害

- 商品超卖、优惠券/积分/奖品重复发放；
- 重复下单、重复扣款、重复生成订单；
- 数据错乱、资损、业务纠纷。

#### 解决方案

1. **前端防抖**
   按钮禁用、定时冷却、禁止短时间连续提交；
2. **后端全局防重**
   唯一流水号/请求ID + Redis 分布式防重锁（SETNX 短过期）；
3. **数据库幂等**
   唯一索引、业务状态机判断（已完成直接拦截）；
4. **并发控制**
   库存扣减使用**SQL原子更新 / Redis+Lua**；
5. **全局幂等设计**
   所有写接口、领奖、下单、支付统一接入幂等组件；
6. **限制提交频率**
   单用户核心操作短时间内限制次数。

### 面试速记背诵

1. **DDoS攻击**：海量流量打满带宽 → 云高防、流量清洗，底层防护为主
2. **CC攻击**：大量模拟正常请求耗尽业务资源 → WAF、网关限流、人机验证码
3. **恶意刷接口**：脚本刷业务接口消耗资源 → 用户维度限流、幂等、风控、验证码
4. **暴力登录**：批量尝试账号密码爆破 → 失败锁定账号、IP限流、验证码
5. **Token滥用**：token被盗冒用身份 → 短有效期、主动作废token、签名校验、HTTPS

五、分布式 & 中间件稳定性——详细完整版

### 1. MQ 消息积压

#### 核心成因

- 消费能力不足：消费者实例数量过少、单消费者处理速度慢，消费速率远低于生产者发送速率，导致消息在队列中持续堆积。
- 消费阻塞：消费者处理消息时，存在同步阻塞、远程调用超时、死锁等问题，导致消费线程卡住，无法正常消费消息，消息堆积加剧。
- 消息重复投递：生产者重试机制不合理、MQ 自身重试策略触发，导致大量重复消息进入队列，增加消费负担，间接引发积压。
- 业务峰值冲击：生产者发送消息量突增（如活动峰值、流量暴涨），超出消费者日常处理能力，未提前扩容消费者，导致消息堆积。
- 消费异常：消费者抛出异常未做重试、死信队列配置不合理，失败消息无法及时处理，持续占用队列资源。

#### 造成危害

消息堆积过多导致 MQ 存储空间耗尽，无法接收新消息；消息处理延迟大幅增加，引发业务超时（如下单后延迟发货、通知延迟）；大量积压消息触发 MQ 性能下降，甚至引发 MQ 宕机；重复消息可能导致业务逻辑异常（如重复扣款），增加数据一致性风险。

#### 解决方案

- 提升消费能力：增加消费者实例数量，水平扩容；优化消费者处理逻辑，减少阻塞操作，提升单消费者处理速率；采用批量消费机制，提高消费效率。
- 解决消费阻塞：排查消费者阻塞问题（如远程调用超时、死锁），将耗时操作异步化；设置消费超时时间，超时则触发重试或进入死信队列，避免消费线程卡住。
- 控制消息重复：规范生产者重试策略，设置合理重试次数和间隔；消费者实现幂等性处理，避免重复消息引发业务异常；开启 MQ 消息去重机制（如基于消息 ID 去重）。
- 应对峰值流量：提前预判业务峰值，扩容消费者集群；采用流量削峰策略，生产者错峰发送消息；临时启动备用消费者，处理积压消息。
- 异常处理与监控：配置死信队列，失败消息进入死信队列后单独处理；实时监控消息堆积量、消费速率，设置预警阈值，及时发现并处理积压问题。

### 2. MQ 消息丢失/重复

#### 核心成因

- 消息丢失：生产者发送消息后未等待 MQ 确认（如未开启生产者确认机制），消息未成功投递到 MQ；MQ 集群宕机、队列异常，未持久化的消息丢失；消费者未提交消费 offset，消费过程中异常退出，导致消息重复消费或丢失。
- 消息重复：生产者发送消息超时，触发重试机制，导致同一消息多次投递；MQ 主从切换、集群故障恢复后，消息重放，引发重复投递；消费者消费消息后未及时提交 offset，重启后重新消费已处理的消息。
- 重试机制不合理：生产者无重试次数限制、重试间隔过短，导致消息重复投递；消费者异常时无重试策略，导致消息丢失；重试过程中未做幂等处理，加剧重复问题。
- 配置不当：MQ 未开启消息持久化（如 RabbitMQ 未设置 durable=true），MQ 重启后消息丢失；offset 存储异常（如 Kafka offset 未持久化），导致消费状态丢失。

#### 造成危害

消息丢失导致核心业务逻辑无法执行（如支付消息丢失，导致订单无法确认），造成业务中断、数据不一致；消息重复导致业务异常（如重复下单、重复扣款），引发用户投诉和经济损失；消息丢失/重复难以追溯，增加问题排查和数据修复成本。

#### 解决方案

- 防止消息丢失：        
  - 生产者：开启生产者确认机制（如 RabbitMQ 的 publisher-confirm-type=correlated，Kafka 的 acks=all），确保消息成功投递到 MQ。
  - MQ 端：开启消息持久化，队列和消息均设置为持久化，避免 MQ 重启后消息丢失；部署 MQ 集群，提升可用性，避免单点故障导致消息丢失。
  - 消费者：采用手动提交 offset 机制，确保消息处理完成后再提交 offset；消费异常时，将消息放入死信队列，避免消息丢失。
- 防止消息重复：        
  - 生产者：设置合理的重试次数和间隔，避免无限重试；发送消息时携带唯一消息 ID，便于后续去重。
  - 消费者：实现幂等性处理（如基于消息 ID、业务唯一键校验），确保重复消息不会执行重复业务逻辑；使用本地缓存或数据库记录已处理的消息 ID，避免重复消费。
  - MQ 端：开启消息去重机制，避免 MQ 自身原因导致的重复投递。
- 优化配置与监控：合理配置 MQ 持久化、offset 存储参数；实时监控消息发送、接收、消费状态，及时发现消息丢失/重复问题，快速排查修复。

### 3. 注册中心雪崩

#### 核心成因

- 心跳风暴：大量服务实例同时启动、重启，或网络波动导致服务与注册中心心跳异常，引发心跳请求暴增，超出注册中心承载能力。
- 服务上下线频繁：服务集群频繁扩缩容、版本迭代频繁，导致服务实例频繁上下线，注册中心需要频繁更新服务列表，消耗大量资源。
- 注册中心单点故障：未部署注册中心集群（如 Nacos 单节点、Eureka 单节点），单点故障后，所有服务无法注册、发现，整个分布式系统瘫痪。
- 配置不合理：注册中心心跳间隔设置过短、服务实例数量过多，未做分片处理，导致注册中心资源耗尽；服务端缓存配置不当，频繁请求注册中心获取服务列表。
- 网络异常：跨机房调用、网络抖动、防火墙限制，导致服务与注册中心通信异常，引发服务反复注册、心跳重试，加剧注册中心压力。

#### 造成危害

注册中心被心跳请求、服务注册/注销请求打满，响应缓慢、超时；服务无法正常注册、发现，跨服务调用失败，分布式系统链路断裂；注册中心宕机后，整个分布式系统无法提供服务，核心业务全面瘫痪；服务实例频繁上下线，导致服务列表不稳定，引发调用异常。

#### 解决方案

- 部署高可用集群：注册中心采用集群部署（如 Nacos 集群、Eureka 集群），避免单点故障；配置主从复制、数据同步，确保集群可用性。
- 优化心跳与注册配置：合理设置心跳间隔（如 Nacos 心跳间隔默认30s，根据服务规模调整）；服务实例启动时，采用分批注册，避免集中注册引发压力；设置服务健康检查阈值，减少无效心跳请求。
- 控制服务上下线频率：减少不必要的服务扩缩容、版本迭代；采用灰度发布，避免大量服务实例同时上下线；服务下线时，先注销再停止，避免注册中心异常。
- 本地缓存优化：服务端开启本地缓存，缓存服务列表，减少对注册中心的频繁请求；缓存过期时间合理设置，确保服务列表及时更新。
- 网络与监控：优化网络架构，减少跨机房调用，避免网络抖动；实时监控注册中心的请求量、响应时间、节点状态，设置预警阈值，及时扩容或排查异常。

### 4. 配置中心波动

#### 核心成因

- 配置推送频繁：开发、测试环境频繁修改配置，或动态配置更新过于频繁，导致配置中心频繁推送配置，服务频繁刷新配置，引发服务波动。
- 动态配置热更新报错：配置热更新机制不完善，配置更新后未做校验，存在语法错误、配置缺失，导致服务加载配置失败，引发服务异常。
- 配置中心集群不稳定：配置中心未部署集群，单点故障导致配置无法推送、获取；集群节点同步异常，配置数据不一致，服务获取到错误配置。
- 配置依赖不合理：服务配置存在强依赖，某一配置修改后，未同步更新关联配置，导致服务逻辑异常；配置项过多、过于复杂，维护困难，易出现配置错误。
- 权限管控缺失：未做配置访问权限控制，误操作、恶意修改配置，导致配置异常，引发服务波动。

#### 造成危害

配置频繁推送导致服务频繁刷新，响应变慢、接口超时；配置热更新报错导致服务加载配置失败，服务重启、不可用；配置数据不一致，导致不同服务实例运行逻辑差异，引发数据不一致、业务异常；误操作修改配置，可能导致核心业务崩溃，造成严重损失。

#### 解决方案

- 规范配置推送：减少不必要的配置修改，开发、测试环境与生产环境配置隔离；动态配置更新设置合理的间隔，避免频繁推送；配置更新前做灰度推送，观察服务状态，再全量推送。
- 完善配置校验机制：配置更新时，自动校验配置语法、格式、依赖关系，校验失败则禁止推送；配置热更新后，服务端做配置校验，校验失败则回滚至历史配置，避免服务异常。
- 保障配置中心高可用：部署配置中心集群，实现数据同步、故障转移，避免单点故障；定期备份配置数据，防止配置丢失。
- 优化配置管理：梳理配置依赖关系，避免强依赖；简化配置项，拆分复杂配置，便于维护；对配置进行分类管理（如核心配置、非核心配置），区分推送优先级。
- 加强权限管控：设置配置访问、修改权限，区分开发、测试、生产权限；配置修改后记录操作日志，便于追溯；禁止恶意修改、误操作，必要时设置配置修改审批流程。

### 5. 分布式锁失效

#### 核心成因

- 锁过期：分布式锁设置的过期时间过短，业务逻辑未执行完成，锁已自动释放，导致其他线程误获取锁，引发并发冲突。
- 续期失败：锁续期机制不完善（如未开启续期、续期线程阻塞、续期超时），锁过期后无法及时续期，导致锁失效。
- 主从切换锁丢失：分布式锁基于 Redis 主从架构实现，主节点持有锁后，未同步到从节点，主节点宕机后从节点切换为主节点，新主节点无锁信息，导致锁失效。
- 锁释放异常：业务逻辑执行异常、线程崩溃，未正常释放锁，导致锁长期占用，其他线程无法获取锁；释放锁时未校验锁的归属，误释放其他线程的锁。
- 锁实现不合理：使用的分布式锁框架存在漏洞，或锁的获取、释放逻辑不规范（如未使用原子操作），导致锁失效。

#### 造成危害

分布式锁失效导致高并发场景下并发冲突，出现数据脏写、重复操作（如超卖、重复扣款）；锁长期占用导致业务逻辑阻塞，接口超时、请求失败；锁失效引发的数据不一致，难以修复，影响业务正常开展；主从切换导致的锁丢失，可能引发核心业务并发安全问题。

#### 解决方案

- 合理设置锁过期时间：结合业务逻辑执行时间，设置略长于最长执行时间的过期时间；开启锁续期机制（如 Redis 的 Redisson 框架自动续期），确保业务未完成时锁不会过期。
- 优化锁的高可用架构：避免使用单一主从架构，采用 Redis 集群、哨兵模式，确保主从切换时锁信息同步；使用支持原子操作的锁实现（如 Redisson、ZooKeeper 分布式锁），避免锁失效。
- 规范锁的释放逻辑：使用 try-finally 机制，确保业务逻辑执行完毕后无论是否异常，都能正常释放锁；释放锁时校验锁的归属（如携带线程 ID、请求 ID），避免误释放。
- 异常处理与监控：监控分布式锁的获取、释放、续期状态，设置预警阈值，及时发现锁失效问题；锁失效时，触发降级策略或兜底逻辑，避免并发冲突；排查锁释放异常、续期失败的原因，及时修复。
- 选择可靠的锁框架：优先使用成熟的分布式锁框架（如 Redisson、Curator），避免自行实现分布式锁，减少锁失效隐患；定期升级锁框架，修复已知漏洞。

## 六、网关 & 中间件稳定性问题

1. **Gateway/Nginx 阻塞**
   worker 线程打满、backlog 满、upstream 超时
2. **注册中心（Nacos/Eureka）异常**
   服务发现失败、调用错误节点
3. **配置中心推送延迟**
   限流、降级规则不生效
4. **分布式锁死锁/阻塞**
   Redisson 锁竞争、超时、未释放

---

### 1. Gateway / Nginx 阻塞

#### 本质

网关层接入能力耗尽，请求排队、转发阻塞，成为全局流量瓶颈，导致所有下游接口超时。

#### 核心成因

1. Nginx worker 进程数不足、Gateway 业务线程池打满；
2. upstream 下游服务慢、超时、不可用，连接挂住不释放；
3. TCP 全连接队列 backlog 过小，连接排队溢出；
4. 缺少超时、重试、熔断，异常下游拖垮网关；
5. 大请求、大文件、长连接占用网关线程。

#### 危害

- 全局接口响应变慢、大面积超时；
- 网关层请求堆积，流量入口瘫痪；
- 单点网关故障引发全站不可用。

#### 解决方案

1. 合理配置 Nginx worker 数、连接数、backlog 队列；
2. Gateway 自定义线程池，隔离读写、快慢接口；
3. 给下游路由统一配置**连接超时、读取超时**；
4. 网关层熔断、降级、重试、负载均衡剔除故障节点；
5. 网关集群化部署，避免单点；
6. 限制单IPQPS、请求体大小，防恶意大流量攻击。

---

### 2. 注册中心（Nacos / Eureka）异常

#### 本质

服务注册、心跳、服务拉取异常，导致**服务列表不准**，调用到下线/故障节点。

#### 核心成因

1. 心跳超时、网络抖动，实例被错误剔除；
2. 注册中心集群单点故障、同步延迟；
3. 客户端缓存服务列表刷新不及时；
4. 健康检查机制不合理，误判健康状态；
5. 大批量服务上下线，推送风暴。

#### 危害

- 远程调用报错、连接失败、随机接口异常；
- 负载均衡路由到无效节点，报错率飙升；
- 微服务集群调用链路不稳定。

#### 解决方案

1. 注册中心集群高可用部署，避免单点；
2. 合理调整**心跳间隔、健康检查、剔除时间**；
3. 客户端本地缓存服务列表，降级容错；
4. 开启快速失败+重试，结合负载均衡故障剔除；
5. 限制批量上下线，避免推送风暴。

---

### 3. 配置中心推送延迟

#### 本质

限流、降级、开关、参数配置推送不及时，规则未实时生效，故障无法快速止血。

#### 核心成因

1. 配置长轮询拉取延迟、网络波动；
2. 客户端缓存配置、未及时监听刷新；
3. 配置中心节点同步延迟；
4. 未主动触发推送，依赖定时拉取；
5. 大配置、大批量配置推送阻塞。

#### 危害

- 线上突发问题：降级、限流、开关不能立即生效；
- 故障止血滞后，放大故障影响范围；
- 多环境配置不一致，业务逻辑异常。

#### 解决方案

1. 监听配置变更事件，**实时动态刷新**，无需重启；
2. 缩短长轮询间隔，保证配置秒级推送；
3. 配置中心集群部署，提高推送稳定性；
4. 核心限流/降级配置独立拆分，轻量化推送；
5. 本地配置兜底，配置中心不可用时降级。

---

### 4. 分布式锁死锁 / 阻塞

#### 本质

基于 Redis 的分布式锁，出现**锁无法释放、过期异常、锁竞争激烈**，导致业务串行阻塞、死锁。

#### 核心成因

1. 加锁后服务宕机、异常崩溃，**锁未主动释放**；
2. 锁过期时间设置过短，业务没执行完锁自动过期；
3. 无锁续期（看门狗），长任务提前释放锁；
4. 未保证原子性：加锁、解锁逻辑非原子；
5. 大量并发争抢同一把锁，严重锁竞争。

#### 危害

- 接口串行执行、吞吐量暴跌、大量阻塞等待；
- 锁永久残留形成**分布式死锁**，业务永久卡死；
- 并发控制失效，引发超卖、数据不一致。

#### 解决方案

1. 使用 Redisson 自带**可重入锁 + 看门狗自动续期**；
2. 锁必须设置过期时间，防止宕机死锁；
3. 保证解锁原子性：Lua 脚本比对 value 再删除；
4. 缩小锁粒度，只锁住临界资源；
5. 高并发场景分段锁、本地限流减少锁竞争；
6. 加锁等待超时，避免无限阻塞。

---

## 七、高并发流量类稳定性问题

1. **流量洪峰 / 秒杀压垮服务**
2. **接口限流未做导致被打满**
3. **级联故障（服务雪崩）**
   一个服务挂 → 整条调用链挂
4. **服务熔断未开启导致全盘阻塞**
5. **线程池、队列无界导致 OOM**

---

### 1. 流量洪峰 / 秒杀压垮服务

#### 本质

瞬时超大流量（秒杀、活动、热点事件）远超系统设计承载上限，各层组件资源快速耗尽，服务直接瘫痪。

#### 成因

- 未做流量预估、无压测，系统容量不足；
- 突发海量请求直达应用、数据库，无层层拦截；
- 秒杀热点商品、热点接口无特殊防护；
- 无削峰、无排队机制，瞬时并发打爆链路。

#### 危害

- CPU、内存、连接池、MQ、数据库全部打满；
- 接口大面积超时、报错、服务不可用；
- 活动崩盘、资损、用户体验雪崩。

#### 解决方案

- **多层削峰**：网关限流 + 队列削峰 + 令牌桶排队；
- **热点隔离**：秒杀独立集群、独立库表、隔离普通业务；
- **流量拦截**：页面静态化、CDN、本地缓存、Redis 拦截大部分请求；
- **异步化**：下单、扣库存、消息通知全部 MQ 异步解耦；
- **容量规划**：压测摸底、弹性扩容、定时扩容预案。

---

### 2. 接口限流未做导致被打满

#### 本质

无QPS限制、无访问控制，外部/内部无限请求涌入，线程、连接、资源被恶意/异常流量占满。

#### 成因

- 网关、应用、接口均未配置限流规则；
- 对内服务信任过度，未做内部调用限流；
- 爬虫、恶意刷接口、重复提交无拦截；
- 突发业务流量无管控，资源无保护。

#### 危害

- 核心接口被非核心流量挤占；
- 线程池、连接池快速耗尽；
- 正常用户请求被拖垮，全局响应变慢。

#### 解决方案

- **全链路限流**：网关全局限流 + 接口单机限流 + 分布式限流；
- 限流算法：令牌桶/漏桶，控制匀速流量；
- 接口分级：核心接口高阈值、非核心严格限制；
- 防刷控制：IP限流、用户维度限流、验证码防刷；
- 统一兜底：超限直接返回降级提示，不阻塞。

---

### 3. 级联故障 / 服务雪崩

#### 本质

下游单个服务故障、卡顿、超时，上游未做防护，大量请求堆积、线程卡死，逐级向上传导，整条调用链全部瘫痪。

#### 成因

- 微服务强依赖，同步调用链路过长；
- 下游异常无隔离、无快速失败；
- 无限重试、无超时，放大故障；
- 服务间没有强弱依赖划分。

#### 危害

- 单点故障演变为全站故障；
- 所有依赖方线程积压、连接耗尽；
- 分布式链路全部阻塞，系统整体宕机。

#### 解决方案

- **强弱依赖划分**：非核心依赖故障直接降级；
- 超时控制：所有RPC、HTTP调用强制超时；
- 集群隔离：业务拆分、机房隔离、集群隔离；
- 异步解耦：非强一致场景改用MQ异步调用；
- 故障演练：常态化压测、混沌工程，提前暴露薄弱点。

---

### 4. 服务熔断未开启导致全盘阻塞

#### 本质

下游服务持续异常、超时、报错，上游未熔断，仍持续大量调用，导致自身线程/连接一直阻塞等待。

#### 成因

- 未接入熔断组件（Sentinel/Resilience4j/Hystrix）；
- 异常阈值、失败率未配置，故障无法识别；
- 调用方无脑重试，持续打故障服务；
- 依赖服务长时间不可用，调用不终止。

#### 危害

- 故障服务持续拖垮所有调用方；
- 阻塞线程不断累积，服务假死；
- 小问题演变为大规模服务不可用。

#### 解决方案

- 接入熔断框架，基于**失败率、超时率、异常数**自动熔断；
- 熔断→降级→恢复半开，自动恢复机制；
- 故障节点负载均衡自动剔除；
- 熔断期间返回兜底数据、默认结果；
- 核心服务优先保障，非核心快速熔断。

---

### 5. 线程池、队列无界导致 OOM

#### 本质

使用**无界队列、无限创建线程**，高并发下任务无限堆积，对象持续膨胀，最终堆内存溢出。

#### 成因

- 错误使用 `Executors` 快捷创建线程池（无界队列/无限线程）；
- 自定义线程池队列设置为无界 `LinkedBlockingQueue`；
- 异步任务、定时任务无限提交，无拒绝策略；
- 消费速度远小于生产速度，任务持续堆积。

#### 危害

- 任务对象、上下文、大对象常驻内存；
- 老年代快速占满，频繁FullGC，最终OOM崩溃；
- 服务卡死、无法自动恢复。

### 解决方案

- **强制使用有界队列 + 自定义线程池**；
- 合理配置：核心线程、最大线程、队列容量、拒绝策略；
- 拒绝策略兜底：队列满时限流、丢弃、降级；
- 快慢任务线程池隔离，防止互相挤压；
- 监控线程池队列积压、拒绝次数、内存占用。

## 八、分布式事务 & 数据一致性问题

1. **分布式事务悬挂/超时**
2. **TCC 悬挂、空回滚、幂等失败**
3. **最终一致性不一致**
   订单/支付/库存不一致

---

### 1. 分布式事务悬挂 / 事务超时

#### 核心本质

分布式事务（Seata AT/XA）执行过程中**长时间未提交/未回滚**，事务处于悬挂状态，资源不释放；或全局事务超时强制结束，数据状态割裂。

#### 成因

1. 微服务调用链路过长，某节点阻塞、超时、宕机；
2. 分支事务执行卡住、第三方接口阻塞、慢SQL；
3. Seata TC 通信异常、网络抖动，全局事务无法决议；
4. 全局事务超时时间设置不合理，业务未跑完已过期；
5. 事务未正常结束，分支锁、行锁长期持有。

#### 危害

- 全局事务悬挂不结束，**行锁、全局锁持续占用**；
- 引发大量锁等待、接口阻塞、死锁；
- 回滚/提交错乱，出现中间态脏数据；
- 数据库连接池积压，性能急剧下降。

#### 解决方案

1. 合理配置**全局事务超时时间**，自动触发超时回滚；
2. 所有远程调用加超时、熔断，避免分支事务卡死；
3. 保证 TC 高可用集群部署，防止单点故障；
4. 增加定时补偿任务，扫描悬挂事务强制闭环；
5. 缩短业务事务周期，避免长分布式事务。

---

### 2. TCC 三大经典问题：悬挂、空回滚、幂等失败

#### （1）TCC 悬挂

##### 本质

**Try 未执行成功**，但远端收到 Cancel 请求，空 Cancel 先执行；后续 Try 又正常执行，数据无法回滚，导致数据悬挂不一致。

##### 原因

网络超时、重试、调用延迟，Cancel 先于 Try 到达。

##### 解决

- 业务事务状态表标记；
- Cancel 阶段先判断是否有 Try 记录，无则直接忽略。

---

#### （2）TCC 空回滚

##### 本质

分支事务**Try 完全没执行**，却收到 Cancel 回滚请求，错误执行无效回滚逻辑，引发异常。

##### 原因

半阶段网络异常、上游取消事务，分支未做任何操作却被要求回滚。

##### 解决

- 新增**事务控制表**，记录 Try 执行状态；
- 无 Try 记录时，Cancel 直接放行，不执行业务回滚。

---

#### （3）TCC 幂等失败

##### 本质

重试机制导致 Try / Confirm / Cancel 重复执行，出现重复扣款、重复扣库存、重复生成单据。

##### 原因

MQ 重试、RPC 重试、网络重传，TCC 三阶段无防重。

##### 解决

- 全局事务ID 作为唯一键，做**幂等控制**；
- 状态机判断：已完成阶段禁止重复执行；
- 操作前加分布式锁+唯一索引兜底。

---

### 3. 最终一致性不一致（订单/支付/库存）

#### 核心本质

本地事务无法跨多服务、多库生效，订单、支付、库存、优惠券、物流**多节点数据更新不同步**，部分成功、部分失败，最终数据割裂。

#### 成因

1. 微服务拆分后，跨库跨服务无原子事务；
2. 异步消息丢失、消费失败，补偿逻辑未执行；
3. 定时补偿任务漏扫、执行失败；
4. 缓存、DB、MQ 多组件状态不同步；
5. 业务异常未捕获，流程中断导致半截事务。

#### 典型业务乱象

- 订单已取消，库存未返还；
- 支付成功，订单未更新为已支付；
- 扣了库存，订单创建失败；
- 优惠券核销成功，订单关闭未退回。

#### 解决方案

1. **可靠消息最终一致性（主流）**
   半消息+本地事务+消息投递+消费回执，保证消息可靠收发。
2. **TCC 柔性事务**
   手动补偿，Try/Confirm/Cancel 三阶段手动控制正负业务。
3. **Seata AT 事务**
   无侵入分布式事务，适合短链路、低并发场景。
4. **定时对账+补偿任务**
   定时扫描异常数据、差异数据，自动修复兜底。
5. **状态机驱动业务**
   订单/支付全链路状态流转，异常自动回滚或重试。



## 八、业务逻辑稳定性

1. **超卖/超扣**

- 库存无锁、并发扣减无控制

2. **状态机混乱**

- 订单/支付/退款状态并发变更错乱

3. **定时任务扎堆**

- 整点集中执行、任务并发冲突、单机任务过载

4. **第三方依赖不稳定**

- 支付、短信、物流三方接口慢、不可用



### 1. 超卖/超扣

#### 核心成因

- 库存无锁控制：高并发场景下，多个请求同时查询库存、扣减库存，未加分布式锁或本地锁，导致库存查询与扣减非原子操作，出现“幻读”，最终库存扣减超出实际数量（超卖）。
- 并发扣减无控制：未设置库存扣减的并发控制策略，多个请求同时扣减同一库存，未校验扣减后库存是否为负，导致库存出现负数，引发超卖/超扣。
- 库存缓存与数据库不一致：库存缓存未及时同步数据库，缓存中库存大于实际数据库库存，请求基于缓存扣减后，数据库库存不足，导致超卖。
- 分布式事务异常：跨服务扣减库存（如下单+扣减库存）时，分布式事务未生效，下单成功但库存未扣减，或库存扣减成功但下单失败，进而引发后续重复扣减或超卖。
- 重试机制不合理：库存扣减超时后，未做幂等处理，直接重试扣减，导致多次扣减同一笔库存，引发超扣。

#### 造成危害

超卖导致实际库存不足但订单已生成，无法履约，引发用户投诉、退款纠纷，损害平台公信力；超扣导致用户账户余额、积分等资产异常减少，引发用户不满和经济损失；库存数据混乱，增加数据修复成本，影响业务正常开展；严重时导致平台资金损失、品牌口碑受损。

#### 解决方案

- 加锁控制：使用分布式锁（如Redisson）或数据库行锁，确保库存查询、扣减为原子操作，同一时间只有一个请求能操作同一库存。
- 并发扣减校验：扣减库存时，添加库存校验逻辑，确保扣减后库存不小于0，若库存不足则直接返回失败，禁止超扣。
- 同步库存数据：确保库存缓存与数据库实时同步，采用缓存预热、失效机制，避免缓存与数据库不一致；扣减库存时，先更新数据库，再更新缓存（或采用缓存删除策略）。
- 保障分布式事务一致性：使用分布式事务框架（如Seata），确保跨服务操作（下单+扣减库存）的原子性，要么全部成功，要么全部回滚。
- 幂等性与重试优化：库存扣减接口实现幂等性（如基于订单ID、请求ID），避免重复扣减；重试时先校验库存状态，确认未扣减后再重试，设置合理重试次数和间隔。

### 2. 状态机混乱

#### 核心成因

- 状态并发变更：高并发场景下，多个请求同时变更同一业务实例的状态（如下单、支付、退款同时操作同一订单），未做并发控制，导致状态变更错乱。
- 状态流转规则不清晰：未定义明确的状态流转路径（如订单状态只能从“待支付”→“已支付”→“待发货”，不能直接从“待支付”→“已完成”），存在非法状态跳转。
- 状态更新无校验：更新状态时，未校验当前状态是否符合流转条件，导致非法状态变更（如已退款的订单再次被支付）。
- 异步通知无序：第三方异步通知（如支付回调、物流回调）到达顺序混乱，导致状态被无序更新（如先收到物流完成通知，再收到支付成功通知）。
- 代码逻辑缺陷：状态更新未使用事务，部分逻辑执行失败后，状态未回滚，导致状态处于中间异常状态；状态存储不一致（如缓存与数据库状态不同步）。

#### 造成危害

订单、支付、退款等核心业务状态混乱，导致业务逻辑异常（如已退款订单被发货、未支付订单被确认完成）；用户查询业务状态时出现异常，引发投诉；业务数据不一致，增加数据修复难度和成本；严重时导致业务流程中断，无法正常履约。

#### 解决方案

- 并发控制：对同一业务实例的状态更新加锁（分布式锁、数据库行锁），确保同一时间只有一个请求能更新状态。
- 明确状态流转规则：定义清晰的状态机模型，明确每个状态的合法流转路径，禁止非法状态跳转；状态更新前，严格校验当前状态是否符合流转条件。
- 规范异步通知处理：对第三方异步通知进行排序、去重处理，基于业务时间戳或流水号确保通知顺序正确；通知处理后，校验状态是否符合预期，避免无序更新。
- 事务与状态同步：状态更新操作纳入数据库事务，确保逻辑执行失败时状态回滚；同步缓存与数据库状态，避免状态不一致。
- 监控与日志：记录状态变更日志，包括变更前状态、变更后状态、操作人、操作时间，便于追溯异常；实时监控状态机流转，及时发现非法状态变更，触发告警。

### 3. 定时任务扎堆

#### 核心成因

- 执行时间集中：多个定时任务均设置为整点、半点执行（如0点、1点、12点），导致任务集中触发，占用大量服务器资源，出现任务排队、执行超时。
- 任务并发冲突：多个定时任务操作同一资源（如同一数据库表、同一缓存Key），未做并发控制，导致任务执行冲突，出现数据脏写、任务执行失败。
- 单机任务过载：所有定时任务部署在同一台服务器，任务集中执行时，CPU、内存、IO资源被占满，导致任务执行延迟、超时，甚至任务丢失。
- 任务配置不合理：任务未设置执行间隔、超时时间，或执行间隔过短，导致任务频繁执行，叠加扎堆问题；任务未做分片处理，大数据量任务一次性执行，耗时过长。
- 任务依赖未处理：多个定时任务存在依赖关系（如任务A需在任务B执行完成后执行），未设置依赖顺序，导致任务无序执行，引发异常。

#### 造成危害

定时任务扎堆执行，导致服务器资源耗尽，任务执行超时、失败；任务并发冲突引发数据不一致、业务逻辑异常（如定时对账失败、订单超时未处理）；单机过载导致所有定时任务无法正常执行，核心业务（如自动退款、库存盘点）中断；任务延迟执行导致业务超时，引发用户投诉。

#### 解决方案

- 分散执行时间：调整定时任务执行时间，避免多个任务集中在同一时间点执行（如将部分任务调整为整点过5分、10分执行）；对大数据量任务，采用错峰执行策略。
- 解决并发冲突：对操作同一资源的定时任务加锁（分布式锁），确保任务串行执行；拆分任务，避免多个任务操作同一资源。
- 分布式部署任务：采用分布式定时任务框架（如XXL-Job、Elastic-Job），将任务分散到多台服务器执行，避免单机过载；根据任务优先级分配服务器资源，核心任务优先执行。
- 优化任务配置：为每个任务设置合理的执行间隔、超时时间，避免任务频繁执行；大数据量任务采用分片处理，分批执行，减少单次任务耗时；设置任务重试机制，失败后自动重试。
- 处理任务依赖：明确任务依赖关系，设置任务执行顺序（如通过任务调度框架配置依赖）；前序任务执行失败时，暂停后续任务执行，避免连锁异常。

### 4. 第三方依赖不稳定

#### 核心成因

- 第三方接口性能差：支付、短信、物流等第三方接口自身处理速度慢，响应超时，尤其是高并发场景下，接口性能下降明显，无法满足业务需求。
- 第三方服务不可用：第三方服务宕机、集群故障、维护升级，导致接口无法调用，业务流程中断；第三方服务限流，导致请求被拒绝。
- 接口调用无容错：未设置第三方接口超时时间、重试策略，接口超时后直接失败，未做兜底处理；无熔断、降级机制，第三方服务异常时，持续调用，导致自身服务阻塞。
- 依赖单一第三方：核心业务仅依赖单一第三方服务，无备用方案，第三方服务异常时，业务无法正常开展。
- 接口适配问题：第三方接口版本迭代、参数变更，未及时同步适配，导致接口调用失败；接口返回格式不规范，解析异常。

#### 造成危害

第三方接口慢、不可用，导致核心业务流程中断（如下单无法支付、短信无法发送、物流无法同步）；用户操作失败，引发大量投诉，流失用户；接口调用无容错，导致自身服务线程阻塞、请求堆积，引发连锁故障；依赖单一第三方，增加业务中断风险，造成经济损失。

#### 解决方案

- 接口容错配置：为第三方接口设置合理的超时时间，避免长期阻塞；配置重试策略（指数退避重试），失败后自动重试，减少偶发异常影响；引入熔断、降级机制，第三方服务失败率达到阈值时，触发熔断，返回兜底结果（如提示“服务暂时不可用”）。
- 多渠道冗余依赖：核心第三方接口采用多渠道部署（如支付接口同时对接支付宝、微信支付），某一渠道异常时，自动切换至备用渠道，保障业务连续性。
- 接口适配与监控：密切关注第三方接口版本迭代、参数变更，及时同步适配；规范接口返回格式解析逻辑，增加异常捕获，避免解析失败；实时监控第三方接口响应时间、失败率，设置预警阈值，及时发现异常。
- 异步化与缓存兜底：将第三方接口调用异步化（如通过消息队列），避免阻塞主线程；对高频、稳定的第三方接口返回结果进行缓存（如物流模板、短信模板），第三方服务异常时，使用缓存数据兜底。
- 沟通与应急：与第三方服务商建立常态化沟通机制，及时获取服务维护、故障通知；制定应急方案，第三方服务异常时，手动切换备用渠道或启动人工处理流程，减少业务损失。

## 九、基础架构 & 容器问题

1. **容器调度波动**

- K8s 频繁扩缩容、节点漂移、资源限制过低

2. **单机单点瓶颈**

- 无集群部署、单点故障整机不可用

3. **版本发布事故**

- 全量发布、灰度缺失、回滚机制不完善

### 1. 容器调度波动

#### 核心成因

- K8s 频繁扩缩容：扩缩容阈值设置不合理（如CPU、内存阈值过严），导致服务在高并发与低并发之间频繁触发扩缩容；扩缩容策略未做平滑控制，一次性扩容/缩容过多实例，引发调度压力。
- 节点漂移：K8s 节点资源不足、节点故障、节点维护，导致容器Pod频繁漂移至其他节点；节点亲和性、反亲和性配置不合理，无法固定核心服务Pod调度节点，引发漂移。
- 资源限制过低：容器CPU、内存资源限制设置不足，无法满足服务运行需求，导致容器频繁被K8s驱逐、重启；资源请求与限制配置不匹配，引发节点资源竞争，间接导致调度波动。
- 调度策略不合理：未配置Pod优先级，核心服务与非核心服务抢占资源，导致核心服务Pod调度失败或频繁漂移；调度算法未优化，节点负载不均衡，引发局部节点压力过大，触发Pod重新调度。
- 存储卷异常：容器挂载的存储卷（如PV/PVC）不稳定、挂载延迟，导致Pod启动失败、重启，引发调度波动；存储卷与节点绑定过紧，节点异常时无法快速迁移Pod。

#### 造成危害

容器频繁扩缩容、漂移，导致服务实例频繁启停，接口响应超时、请求失败；核心服务Pod漂移后，网络连接中断，跨服务调用异常；容器被驱逐、重启，导致业务逻辑中断，数据丢失或不一致；K8s集群调度压力增大，集群响应变慢，甚至引发调度器异常。

#### 解决方案

- 优化扩缩容策略：合理设置扩缩容阈值（基于CPU、内存使用率、请求量），增加扩缩容冷却时间，避免频繁扩缩容；采用平滑扩缩容，分批扩容/缩容实例，减少调度冲击。
- 减少节点漂移：为核心服务Pod配置节点亲和性、反亲和性，固定调度节点；定期巡检K8s节点，及时处理节点故障、资源不足问题；节点维护前，提前迁移Pod，避免被动漂移。
- 合理配置资源限制：根据服务实际运行需求，设置合适的容器CPU、内存请求与限制，避免资源不足导致驱逐；核心服务优先分配资源，设置资源保障策略，避免被非核心服务抢占。
- 优化调度配置：配置Pod优先级，核心服务设置高优先级，确保优先调度；优化集群调度算法，实现节点负载均衡，避免局部节点过载；开启Pod调度抢占机制，保障核心服务正常调度。
- 稳定存储卷：选用高可用存储卷（如分布式存储），优化存储卷挂载配置，减少挂载延迟；配置存储卷动态供给，避免存储卷与节点绑定过紧，提升Pod迁移灵活性；监控存储卷状态，及时排查异常。

### 2. 单机单点瓶颈

#### 核心成因

- 无集群部署：核心服务、中间件（如数据库、Redis、MQ）未部署集群，仅单机运行，存在单点故障，一旦单机宕机，服务直接不可用。
- 单点故障整机不可用：单机硬件故障（如CPU、内存、磁盘损坏）、系统崩溃、网络中断，导致整机无法提供服务，依赖该单机的所有业务中断。
- 资源集中过载：单机承担过多核心服务、中间件，CPU、内存、IO、带宽资源被占满，成为系统瓶颈，导致所有依赖该单机的服务响应变慢、超时。
- 无冗余备份：单机未配置数据备份、灾备方案，单机故障后，数据无法恢复，导致业务数据丢失；无备用节点，故障后无法快速切换，延长业务中断时间。
- 架构设计不合理：服务未做拆分，核心业务与非核心业务部署在同一单机，某一业务异常会导致整机资源耗尽，引发连锁故障。

#### 造成危害

单机单点故障直接导致核心服务、中间件不可用，整个业务流程中断，造成严重经济损失和用户流失；单机资源过载，导致服务响应缓慢、请求堆积，用户体验急剧下降；数据无备份，单机故障后数据丢失，难以修复，影响业务长期开展；故障排查、恢复时间长，进一步扩大业务损失。

#### 解决方案

- 部署高可用集群：核心服务、中间件（数据库、Redis、MQ）采用集群部署，避免单点故障；配置主从复制、故障转移机制，确保集群中某一节点故障时，自动切换至备用节点。
- 避免单点瓶颈：拆分单机部署的服务，将核心业务与非核心业务分离部署，分散资源压力；对高并发服务进行水平扩容，部署多实例，分担单机负载。
- 配置冗余备份：为单机配置数据定时备份、异地灾备方案，确保数据可恢复；部署备用节点，与主节点实时同步数据，故障时可快速切换，缩短业务中断时间。
- 硬件与系统保障：选用高性能、高可靠性的硬件设备，减少硬件故障概率；优化操作系统配置，定期更新系统补丁，避免系统崩溃；配置网络冗余链路，避免网络中断导致单机不可用。
- 监控与预警：实时监控单机资源使用率、服务状态，设置预警阈值，及时发现资源过载、节点异常；部署故障检测机制，单机故障时自动告警，快速介入处理。

### 3. 版本发布事故

#### 核心成因

- 全量发布：未做灰度发布、金丝雀发布，直接全量推送新版本，一旦新版本存在Bug、兼容性问题，会影响所有用户，引发大规模服务异常。
- 灰度缺失：未制定合理的灰度策略，灰度范围、灰度时间设置不合理，无法有效验证新版本稳定性；灰度过程中未监控服务状态，无法及时发现异常。
- 回滚机制不完善：未配置自动化回滚脚本，版本发布异常时，需手动回滚，回滚效率低，延长业务异常时间；回滚前未做数据校验，回滚后可能出现数据不一致。
- 发布前未充分测试：新版本未经过完整的单元测试、集成测试、压测，存在隐藏Bug、性能问题，发布后引发服务异常；测试环境与生产环境配置不一致，测试通过但生产发布失败。
- 发布流程不规范：未制定严格的发布审批流程，随意发布新版本；发布过程中未暂停相关业务，导致发布与业务操作冲突，引发数据异常。

#### 造成危害

全量发布异常导致所有用户无法正常使用服务，引发大量投诉、用户流失；版本Bug导致业务逻辑异常、数据脏写、数据丢失，增加数据修复成本；回滚不及时，延长业务中断时间，造成严重经济损失；发布事故影响平台公信力，损害品牌口碑。

#### 解决方案

- 采用灰度发布策略：新版本先在小范围灰度（如1%、5%用户），验证稳定性后，逐步扩大灰度范围，最终全量发布；灰度过程中实时监控服务响应时间、失败率，发现异常立即停止灰度。
- 完善回滚机制：配置自动化回滚脚本，版本发布异常时，一键触发回滚，缩短回滚时间；回滚前校验数据一致性，回滚后检查服务状态，确保回滚成功。
- 加强发布前测试：新版本必须经过单元测试、集成测试、压测，确保无Bug、性能达标；统一测试环境与生产环境配置，避免环境差异导致发布失败；新增功能采用Feature Flag（功能开关），异常时可快速关闭。
- 规范发布流程：制定严格的发布审批流程，新版本发布前需经过评审、测试确认；发布时间选择业务低峰期，发布过程中暂停相关业务操作，避免冲突；记录发布日志，便于追溯异常原因。
- 发布监控与应急：发布过程中实时监控服务状态、接口性能、数据一致性，设置预警阈值；制定发布应急方案，发布异常时，快速触发回滚、降级等兜底策略，减少业务损失。

作为双非研究生，想要在秋招中拿下 Java 后端 20k+ 的 SSP（Super Special Offer）级薪资，你必须要在面试中展现出**超越一般候选人的系统级思维和底层原理深度**。

对于 20k+ 的岗位，面试官不再满足于“八股文背诵”，而是倾向于通过**“链路题”**（即一个请求从头到尾的完整生命周期）来考察你的全局架构能力和细节深度。

以下是 Java 后端秋招 20k+ 面试中极高频且能定薪的**五大核心链路题**，附带考察点与答题骨架：

---

### 一、 HTTP 请求链路（网络与容器层）

**面试官提问：** *“在浏览器输入一个 URL 到最终页面渲染，或者一个外部 HTTP 请求打到你的后端服务，中间经历了哪些步骤？”*

**20k+ 采分点（需要往底层和网络协议靠）：**

1. **DNS 解析链路：** 本地缓存 -> 本地 DNS -> 根 DNS -> 顶级 DNS -> 权威 DNS。
2. **网络层链路：** TCP 三次握手（重点讲序列号、窗口大小协商）-> 如果是 HTTPS，讲 TLS 1.2/1.3 握手过程（非对称加密协商对称密钥）。
3. **反向代理层（Nginx）：** 请求到达 Nginx，负载均衡策略（轮询、IP Hash、一致性 Hash），动静分离。
4. **网关层：** 限流（令牌桶/漏桶）、鉴权（JWT 解析）、路由转发。
5. **Web 容器层：** 进入 Tomcat，讲清楚 Tomcat 的线程模型。Acceptor 线程接收 Socket -> Poller 线程监听 IO 事件 -> 交给 Worker 线程池执行。
6. **框架层：** 进入 Spring MVC 的 `DispatcherServlet` -> `HandlerMapping` 路由 -> `HandlerInterceptor` 拦截器前置处理 -> `HandlerAdapter` 参数解析与数据绑定 -> Controller。

**深挖陷阱：** 面试官可能会问：“如果 QPS 突然增高，Tomcat 线程池打满了，这条链路会怎样？”（考察拒绝策略、线程池参数动态调整、以及网关层熔断降级）。

---

### 二、 Spring Bean 生命周期与 AOP 链路（框架源码层）

**面试官提问：** *“讲讲 Spring 中一个 Bean 从创建到销毁的完整过程，以及 AOP 是在哪个环节介入的？”*

**20k+ 采分点（不能只背生命周期，要结合源码和循环依赖）：**

1. **实例化链路：** `createBeanInstance` -> 推断构造方法 -> 反射创建对象（此时对象在堆中，属性为空）。
2. **属性填充链路：** `populateBean` -> 依赖注入（此时触发三级缓存解决循环依赖）。
3. **初始化链路：** 
   - Aware 接口回调（`BeanNameAware`, `ApplicationContextAware`）。
   - `BeanPostProcessor#postProcessBeforeInitialization`（这里会处理 `@PostConstruct`）。
   - 自定义初始化方法（`InitializingBean#afterPropertiesSet`, `init-method`）。
   - `BeanPostProcessor#postProcessAfterInitialization`（**核心考点：AOP 代理就是在这里生成的，通过 `AbstractAutoProxyCreator` 包装 Bean**）。
4. **AOP 执行链路：** 代理对象调用方法 -> `CglibMethodInvocation` 责任链模式 -> 依次执行用户定义的 Aspect（`@Before`, `@Around`） -> 反射调用目标方法 -> `@AfterReturning` / `@AfterThrowing`。

**深挖陷阱：** “三级缓存为什么不能是两级？”（考察 `SmartInstantiationAwareBeanPostProcessor` 提前暴露代理对象的设计初衷，以及如果没有 AOP 确实两级就够，但为了统一逻辑 Spring 选择了三级缓存）。

---

### 三、 MySQL 事务更新与索引查询链路（存储层）

**面试官提问：** *“一条 Update 语句 `update user set age = 20 where id = 1` 在 MySQL 中是如何执行的？”*

**20k+ 采分点（结合 InnoDB 架构、Redo/Undo Log、MVCC）：**

1. **执行器与存储引擎交互：** 执行器调用存储引擎接口找 `id=1` 的行。如果在 Buffer Pool 中直接返回；否则从磁盘加载页到 Buffer Pool。
2. **记录旧值（Undo Log）：** 生成 Undo Log，记录修改前的镜像，用于事务回滚和 MVCC。
3. **更新内存数据：** 在 Buffer Pool 的数据页中更新记录。此时该页变为**脏页**。
4. **写 Redo Log（Prepare 状态）：** 将修改写入 Redo Log Buffer，按照 `innodb_flush_log_at_trx_commit` 策略刷盘到 Redo Log File（WAL 机制，保证持久性）。此时 Redo Log 处于 Prepare 状态。
5. **写 Binlog：** Server 层生成 Binlog 并刷盘（`sync_binlog` 参数控制）。
6. **两阶段提交（2PC）：** 将 Redo Log 状态改为 Commit。事务完成。
7. **后台异步刷盘：** Buffer Pool 中的脏页由后台线程异步刷入磁盘。

**深挖陷阱：** “如果在写入 Binlog 后、Redo Log 改为 Commit 前 MySQL 宕机了，重启后会怎么处理？”（考察 Crash-Safe 机制，通过 Redo Log 的 Prepare 状态和 Binlog 的完整性判断是提交还是回滚）。

---

### 四、 Redis 缓存一致性与高可用链路（中间件层）

**面试官提问：** *“在你的项目中，一个查询请求过来，你是如何设计缓存和数据库交互的？如果数据更新了如何保证一致性？”*

**20k+ 采分点（考察分布式系统的取舍和工程实践）：**

1. **读取链路：** 请求 -> 查询 Redis -> 命中则直接返回。未命中 -> 查询 DB -> 将结果写入 Redis（需设置随机超时时间防雪崩） -> 返回。
2. **更新链路（一致性保证）：**
   - **方案选择：** 先更新 DB，再删除缓存（Cache Aside Pattern）。解释为什么不用“更新缓存”（并发写容易导致脏写）。
   - **极端并发问题：** 先删缓存再更新 DB 存在线程 A 删除缓存 -> 线程 B 查 DB 旧值写入缓存 -> 线程 A 更新 DB，导致脏数据。
   - **解法：** 延迟双删（更新 DB 后休眠 1s 再删一次缓存），或者订阅 MySQL Binlog（Canal）异步删除缓存。
3. **分布式锁链路：** 如果有并发写同一行，讲讲 Redisson 分布式锁的底层：`set nx px` -> 看门狗机制自动续期 -> Lua 脚本保证原子性释放锁 -> Pub/Sub 实现锁的阻塞等待。

**深挖陷阱：** “Canal 同步删除 Redis 如果失败了怎么办？”（考察消息队列重试机制、或者引入 MQ 作为缓冲确保最终一致性）。

---

### 五、 分布式微服务调用与排查链路（架构层）

**面试官提问：** *“你的服务 A 调用服务 B，最后服务 B 报错了，整个调用链路是怎么样的？如果让你排查，你怎么定位？”*

**20k+ 采分点（RPC 原理 + 分布式链路追踪 + 排查思路）：**

1. **本地调用链路：** 服务 A 调用接口 -> 动态代理拦截 -> 负载均衡（Ribbon/LoadBalancer）选择节点 -> 
2. **网络传输链路：** 序列化（JSON/Protobuf） -> Netty 发送 TCP 请求（携带 TraceID、RPC 上下文）。
3. **服务端处理链路：** 服务 B 的 Netty 接收 -> 反序列化 -> 找到本地实现类 -> 反射执行业务逻辑。
4. **异常处理：** 服务 B 抛出异常 -> 捕获异常并序列化为统一错误码 -> 返回给服务 A -> 服务 A 根据错误码决定是否重试或熔断降级。
5. **监控与排查链路（SkyWalking/Zipkin 原理）：**
   - 讲讲 TraceID 是如何在微服务间透传的（ThreadLocal 保存上下文 -> 塞入 HTTP Header 或 RPC Attachments -> 下游解析并存入 MDC）。
   - 排查步骤：看监控大盘发现服务 A 错误率飙升 -> 通过 TraceID 查询链路拓扑图 -> 发现耗时卡在服务 B 的某个 Span 上 -> 看服务 B 的日志（ELK）和 DB 慢查询日志 -> 定位到是未命中索引导致全表扫描。

**深挖陷阱：** “TraceID 跨线程（比如使用线程池）会丢失吗？怎么解决？”（考察对 ThreadLocal 的理解，需要用阿里 TransmittableThreadLocal 或手动传递）。

# HTTP 请求完整链路（网络层 → Tomcat容器 → Spring/SpringBoot应用）
> 从用户在浏览器输入URL按下回车，一直到后端Java应用接收到请求、执行业务、返回响应，完整全链路拆解，包含网络、TCP、HTTP、Tomcat、Servlet、SpringMVC各层，面试高频。

整体链路顺序：
`浏览器DNS解析 → 建立TCP连接(TCP三次握手) → 发送HTTP请求 → 网络路由转发(Nginx) → Tomcat接收请求 → Tomcat线程处理 → Servlet容器 → SpringMVC DispatcherServlet → Controller执行业务 → 逐层返回响应 → TCP四次挥手断开连接`

## 1. 浏览器端：DNS域名解析
浏览器输入 `http://shturl./api/xxx`
域名不能直接通信，需要解析成IP地址。
1. 浏览器查**本地DNS缓存**
2. 查操作系统hosts文件
3. 向本地DNS服务器（运营商DNS）发起查询
4. 递归查询：根域名服务器 → 顶级域名服务器 → 权威DNS，拿到服务器公网IP。

> 追问：DNS协议基于UDP，53端口。

拿到目标IP之后，开始建立TCP连接。

## 2. TCP三次握手，建立连接
HTTP是**应用层协议，基于TCP传输层**。
浏览器客户端（随机端口） ↔ 服务端(80/443端口)
1. 客户端发送 SYN 报文（同步）
2. 服务端返回 SYN+ACK
3. 客户端返回 ACK
连接建立完成，**才可以发送HTTP请求报文**。

> HTTPS：TCP握手完成之后，还要进行TLS握手（证书校验、协商加密套件、生成会话密钥），之后HTTP报文被加密传输。

## 3. 客户端组装HTTP请求报文，发送
浏览器按照HTTP协议格式组装请求：请求行、请求头、请求体。
```
GET /api/user/list HTTP/1.1
Host: shturl.
User‑Agent: chrome
Cookie: xxx
……
```
通过已经建立好的TCP套接字，把二进制报文发给服务端IP。

> HTTP1.1：长连接keep‑alive，一次TCP连接可以多次HTTP请求；
> HTTP2：二进制帧、多路复用、头部压缩；
> HTTP3：基于QUIC(UDP)。

## 4. 网络转发：Nginx反向代理（网关层）
公网请求首先打到Nginx服务器。
Nginx工作模式：多进程模型：master主进程 + worker工作进程。
1. master管理worker；worker监听80/443端口。
2. worker进程accept拿到TCP连接，读取HTTP报文。
3. Nginx解析http请求，根据配置做：负载均衡、路由、限流、SSL解密、静态资源处理。
4. 如果是动态接口，Nginx作为反向代理，通过新的TCP连接，把请求转发给后端Tomcat（内网IP，如 `127.0.0.1:8080`）。

> 区分：
> - 正向代理：代理**客户端**（VPN）
> - 反向代理：代理**服务端**（Nginx，客户端无感知）

## 5. Tomcat（Servlet容器）接收请求【容器层重点】
> SpringBoot内置Tomcat，本质就是一个Servlet Web容器。
> Tomcat核心组件：
> `Endpoint → Processor → Adapter → Servlet容器`

### 5.1 Endpoint（网络端点）
Endpoint负责底层Socket网络通信。
- NIO模式：监听8080端口，接收来自Nginx的TCP连接。
- 接收TCP二进制流，读取网络数据。
> Tomcat NIO：Acceptor线程接收连接；Poller线程轮询socket事件；业务线程池处理请求。

1. Socket过来的是二进制字节流，Endpoint读取字节。
2. Processor解析字节流，封装成Tomcat内部的`Request`、`Response`对象（**不是HttpServletRequest**，是Tomcat原生对象）。

### 5.2 CoyoteAdapter 适配器
把Tomcat底层的Request/Response，**适配转换成Servlet规范的 `HttpServletRequest` / `HttpServletResponse`**，交给Servlet容器。

> 关键点：Tomcat底层对象 ≠ Servlet标准对象，Adapter做适配转换，解耦网络IO和Servlet规范。

### 5.3 Container引擎：Host → Context → Wrapper
- Engine：引擎，整个Tomcat
- Host：虚拟主机（域名）
- Context：一个web应用（对应SpringBoot应用）
- Wrapper：包装每一个Servlet。

请求进入Context，找到对应的Wrapper，拿到要执行的Servlet。

## 6. Servlet规范：Filter过滤器链
Servlet容器拿到请求后，**先执行Filter过滤器链**。
多个Filter按照配置顺序执行 doFilter()；
filter可以修改request、response；可以中断请求。
执行完所有Filter，才到达真正的Servlet。

> SpringBoot中 `OncePerRequestFilter` 就是Servlet Filter。

## 7. 进入SpringMVC：DispatcherServlet（核心Servlet）
DispatcherServlet是SpringMVC唯一的核心Servlet，继承HttpServlet。
`service() → doGet()/doPost()`。

DispatcherServlet内部九大组件处理请求：
1. **HandlerMapping**：根据请求URL，找到对应的处理器Handler（就是我们写的Controller方法）。
2. **HandlerAdapter**：适配调用Controller方法。
3. 执行拦截器Interceptor（SpringMVC拦截器，**在Filter之后，Controller前后执行**）
> Filter属于Servlet容器；Interceptor属于Spring框架内部。

4. 调用我们写的Controller业务方法；
5. Controller返回结果（String/Object）交给 **ModelAndViewResolver / ResponseBodyAdvice**；
6. 如果是@ResponseBody，通过消息转换器`HttpMessageConverter`把对象序列化为JSON字符串；
7. 把JSON数据写入 `HttpServletResponse`。

## 8. 响应原路逐层返回
1. DispatcherServlet把数据写入HttpServletResponse。
2. Filter链倒序执行完成。
3. Tomcat Adapter把Servlet Response再转回Tomcat内部Response对象。
4. Processor把响应组装成HTTP响应报文，通过Socket写出到TCP缓冲区。
5. 数据传回Nginx；Nginx把响应返回浏览器。

HTTP响应报文示例：
```
HTTP/1.1 200 OK
Content‑Type: application/json

{"code":200,"data":...}
```

## 9. TCP断开连接：四次挥手
- 如果HTTP是`keep‑alive`长连接：TCP连接不会立刻关闭，复用等待下一次HTTP请求；
- 如果短连接，双方执行TCP四次挥手释放socket连接。

# 高频面试追问（深挖考点）
## 1. Filter 和 Interceptor 的区别？
1. **Filter**：属于 **Servlet容器规范**，在Tomcat层面，在DispatcherServlet**之前执行**。
2. **Interceptor**：属于 **SpringMVC框架**，在DispatcherServlet内部，Controller方法前后执行。
执行顺序：`Filter → DispatcherServlet → Interceptor → Controller`

Filter可以拦截所有请求；Interceptor只进入SpringMVC的请求。

## 2. Tomcat的NIO模型，线程池做什么？
- Acceptor线程：接收TCP连接。
- Poller线程：监听socket读写就绪事件。
- Tomcat业务线程池：真正执行业务、Filter、Servlet、Controller。
> IO等待由NIO处理；业务逻辑在业务线程。
> SpringBoot可以配置 `server.tomcat.threads.max` 修改最大线程数。

## 3. HttpServletRequest 能不能在子线程拿到？
默认不行。原始request对象保存在Tomcat业务线程的ThreadLocal；异步子线程会丢失。
SpringMVC提供 `RequestAttributes` 或者使用 `ServletRequestAttributes` 拷贝上下文。

## 4. 为什么Nginx和Tomcat要分开？
Nginx擅长高并发网络IO、静态资源、负载均衡；Tomcat擅长执行Java业务逻辑。
Nginx扛外网，保护Tomcat，静态资源直接Nginx返回，不打到Java。

## 5. Keep‑Alive长连接作用？
复用TCP连接，避免每次HTTP都三次握手，减少开销。HTTP1.1默认开启。

## 6. HTTPS的TLS握手发生在哪一步？
TCP三次握手完成之后，HTTP报文发送**之前**做TLS握手，协商加密。

## 7. 请求过来，一次请求对应几个对象？
浏览器TCP → Nginx新建TCP → TomcatSocket；
Tomcat封装内部Request → Adapter转为Servlet HttpServletRequest → Filter链 → DispatcherServlet。

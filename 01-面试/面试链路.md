## 链路3：过期策略 + 内存淘汰策略（高频）
**起始问题：Redis key过期之后是怎么删除的？**
1. 惰性删除：访问的时候才删，弊端：大量过期key占内存
2. 定期删除：定时抽样扫描过期key；不会全部扫描，避免CPU打满
> 组合策略：**惰性删除 + 定期删除**
3. 追问：如果大量key过期，还是内存爆满怎么办？→引出**内存淘汰策略maxmemory‑policy**
4. 8种淘汰策略分两类：LRU、LFU、随机、ttl、不淘汰
    - volatile‑xxx：只对设置过期时间的key
    - allkeys‑xxx：全部key
5. LRU是真实LRU吗？Redis近似LRU实现；LFU是什么，冷热key统计
6. 线上一般配置什么策略？maxmemory必须设置吗？不设置会怎么样？（OOM）

> 完整追问链：
> key到期就立刻删掉吗？→两种删除策略优缺点？→大量过期key没被访问，内存占用高怎么办？→maxmemory不设置会发生什么？→各个淘汰策略区别？近似LRU原理？

## 链路4：缓存三大问题（缓存穿透、击穿、雪崩，面试必考整套）
**起始问题：说下缓存穿透、缓存击穿、缓存雪崩，怎么解决？**
1. 缓存穿透：查不存在的数据，直接打DB
    - 解决方案：布隆过滤器；缓存空值；参数校验
    - 追问：布隆过滤器原理？优缺点？误判？不能删除？
2. 缓存击穿：**热点key过期，大量请求打数据库**
    - 方案：互斥锁；热点key永不过期
3. 缓存雪崩：大量key同时过期 / Redis宕机，大量请求压DB
    - 方案：过期时间加随机偏移；集群高可用；多级缓存；服务限流熔断降级
> 连环追问：
> 击穿用分布式锁会有什么问题？性能下降？→热点key永不过期是时间不过期，后台异步更新？→雪崩和击穿的核心区别？布隆过滤器如果数据量大放在Redis还是本地？

## 链路5：Redis分布式锁（超级长链路，二面高频）
**起始：怎么用Redis实现分布式锁？会遇到哪些问题？**
1. 错误写法：setnx + expire 两条命令，原子性问题
2. 正确：`set key value NX EX` 一条命令保证原子
3. 问题1：锁过期了，业务还没执行完，锁提前释放
    - →看门狗续期（Redisson）；讲清楚看门狗逻辑：定时续期、默认30s、10s检查一次
4. 问题2：锁被别的客户端释放
    - →value存唯一标识（UUID），释放时判断value，Lua脚本保证释放原子性
5. 问题3：可重入怎么实现？Redisson怎么支持可重入？Hash结构计数
6. 问题4：主从切换锁丢失（主节点拿到锁，还没同步到从，主宕机，从变主，别的线程拿到锁）
    - 解决方案：Redlock红锁；缺点：复杂度高，生产很少用；业务补偿
7. 追问：Redlock的问题，业界怎么看待Redlock？
8. 追问：分布式锁选型对比：Redis、Zookeeper、数据库乐观锁各自优缺点？

# 分布式锁深挖面试链路

> 背景：单机锁`synchronized / ReentrantLock`只作用于一个JVM实例；多服务实例、多进程需要分布式锁。
> 面试链路：**分布式锁需要满足哪些特性 → Redis实现（原生缺陷） → Redisson实现完整方案 → 各种坑点（锁超时、误释放、可重入、主从锁丢失） → Redlock红锁争议 → Zookeeper分布式锁对比 → 数据库实现 → 选型对比 + 业务场景取舍**

## 起始问题：分布式锁需要具备哪些核心特性？
1. **互斥性**：同一时刻只有一个客户端拿到锁（最核心）
2. **可重入**：同一个线程拿到锁后可以再次获取锁，不会自己死锁
3. **防死锁**：锁一定要有过期时间，客户端宕机锁能自动释放
4. **安全性**：不能被其他客户端误释放别人的锁
5. **高可用**：锁服务宕机不能导致业务彻底卡死
6. **高性能**：加锁释放锁效率高

> 追问：单机ReentrantLock都具备上面哪些？哪些是分布式锁额外要解决？

---

## 链路1：Redis实现分布式锁（手写版本，层层踩坑）
**起始：用Redis怎么实现分布式锁？写下伪代码**

❌错误版本1：
```
setnx lock key
expire lock 30
```
> 追问：有什么问题？
> 两条命令，**不原子**。如果setnx成功，服务宕机，expire没执行 → 锁永远不会释放，死锁。

✅正确基础版本：原子加锁
```
SET lockKey uniqueValue NX EX 30
```
- `NX`：key不存在才设置，实现互斥
- `EX`：设置过期时间，防死锁
- `uniqueValue`：UUID，标识当前客户端，防止别人释放我的锁

> 继续连环追问1：释放锁直接`del lockKey`行不行？
> 不行！会误删别的客户端的锁。
> 场景：A拿到锁，锁超时；B拿到锁；A执行完业务直接del，把B的锁删掉。

❌错误释放：`del lockKey`

✅正确释放：**Lua脚本保证判断+删除原子性**
```lua
if redis.call('get',KEYS[1]) == ARGV[1] then
    return redis.call('del',KEYS[1])
else
    return 0
end
```
> 追问：为什么必须Lua？Java代码先get再del，两条命令，中间有时间窗口，不原子。

👉现在这套还有两大致命问题：
1. **锁过期，但业务还没执行完**。业务没跑完锁释放，其他线程抢占锁，并发安全失效。
2. **Redis主从切换锁丢失**：主节点set成功，锁还没同步给从节点，主宕机，从晋升为主，另一个客户端又拿到锁。

### 坑1：锁超时，业务未执行完毕
> 面试官：锁设置30s过期，如果业务执行要40s怎么办？
> 思路：**看门狗（WatchDog）自动续期**
- Redisson看门狗逻辑：拿到锁后，后台定时线程，每 `lockWatchdogTimeout/3`（默认10s）检查，如果线程还持有锁，就把锁过期时间重新刷回30s。
- 如果线程业务执行完毕，主动释放锁，看门狗停止。
- 如果客户端宕机，看门狗线程死亡，锁到期自动释放。

> 追问：看门狗是干什么？如果手动指定过期时间，看门狗还会生效吗？
> 答：**自己指定leaseTime过期时间，看门狗就不工作，不会自动续期**。只有不传过期时间，才启动看门狗。

### 坑2：分布式锁可重入怎么实现？
简单`set nx`结构不支持可重入。
Redisson使用**Hash结构实现可重入锁**：
- key：锁名称
- field：线程唯一标识
- value：重入计数。
- 同一线程再次加锁：field存在，计数+1；
- 释放锁：计数-1；计数为0才真正删除key。

> 追问：如果不用Redisson，自己Redis怎么手写可重入锁？也要Lua脚本完成判断、计数增减，保证原子。

### 坑3：主从切换锁丢失问题（最难高频）
场景：
1. 客户端A向Redis主节点成功拿到锁；
2. 锁还没异步同步到slave从节点；
3. master宕机，slave升级为新master；
4. 客户端B请求新master，可以成功拿到同一把锁；
👉**同一时刻两个客户端同时持有锁，互斥性被破坏，分布式锁失效！**

> 追问：怎么解决这个问题？引出 Redlock（红锁）

## 链路2：Redlock 红锁（Redis作者提出）
原理：
需要N个独立、无主从关系的Redis主节点；
客户端依次向所有N个节点加同一把锁；
超过半数节点加锁成功，才算获取锁成功。

> 连环深挖追问：
1. Redlock能不能解决主从锁丢失？
2. Redlock有什么缺陷？生产环境真的用吗？
- 需要多套独立Redis实例，成本高；
- 时钟漂移风险（系统时间跳变）；
- 加锁要依次请求多个节点，性能差；
- 大部分大厂生产**并不使用Redlock**。

> 业界共识：
- 如果业务允许极小概率锁失效，用普通主从+Redisson；
- 如果业务绝对不能出现锁失效，Redis分布式锁本身就不适合，改用Zookeeper或者数据库。

## 链路3：Zookeeper实现分布式锁
**起始：Zookeeper怎么实现分布式锁？对比Redis锁？**
原理：
1. 创建临时有序节点；
2. 抢锁：判断自己是不是最小序号节点；是则拿到锁；
3. 不是最小节点，监听前一个节点，等待watcher事件通知；
4. 客户端宕机，**临时节点自动删除，不会死锁**。

> ZK天然特性：
- 临时节点：宕机自动释放锁，**不需要设置过期时间，不需要看门狗**
- 有序节点 + watch监听，排队等待；原生支持可重入；
- ZK强一致性，不会出现主从切换锁丢失问题。

> 追问ZK缺点：
> ZK性能比Redis差；频繁创建删除节点，有Watcher事件压力；依赖ZK集群。

> Redis vs Zookeeper分布式锁对比
| 维度       | Redis(Redisson)            | Zookeeper         |
| ---------- | -------------------------- | ----------------- |
| 一致性     | 最终一致性，主从切换会丢锁 | ZAB强一致，锁可靠 |
| 性能       | 高                         | 较低              |
| 宕机释放锁 | 看门狗续期；宕机等过期     | 临时节点直接删除  |
| 可重入     | Hash实现                   | 原生支持          |
| 风险点     | 主从锁丢失、看门狗失效     | 性能、Watcher风暴 |

> 面试官经典提问：**为什么你项目选择Redis分布式锁，而不用ZK？**

## 链路4：数据库实现分布式锁
两种方案：**悲观锁、乐观锁**
1. 悲观锁：select ... for update；数据库行锁。
    - 问题：长事务占用连接；数据库宕机锁失效；集群分库环境不好用。
2. 乐观锁：版本号机制，update table set version=version+1 where id=xx and version=oldVersion
    - 无阻塞，基于CAS；适合并发不高场景；高并发大量重试。

# MQ消息队列深挖面试链路

> 面试提问逻辑：MQ作用 → 三大MQ架构对比 → 可靠性（消息不丢失）→ 重复消费&幂等 → 顺序消息 → 消息积压 → 事务消息 → 高可用 → 选型对比，**RocketMQ、Kafka为主，RabbitMQ简单了解**，连环追问。

## 起始问题：消息队列有什么作用？带来什么问题？
**作用**：异步解耦、削峰填谷、流量消峰、事件通知。
**引入MQ带来的问题**：系统复杂度上升；消息丢失；消息重复；消息顺序错乱；消息积压；运维成本。

> 追问链：
> 什么场景用异步解耦？什么场景削峰？业务如果不能容忍数据不一致还能用MQ吗？

---

## 链路1：三大MQ基础架构
### Kafka
架构角色：`Broker、Topic、Partition、副本Replica、ISR、Producer、Consumer、ConsumerGroup`
1. Topic逻辑概念，物理拆分为多个Partition；**Partition是Kafka并发最小单元**。
2. 每个Partition多副本，ISR集合：同步中的副本，不在ISR代表同步滞后过多。
3. 消费者组：同一个组，一个Partition只能被一个消费者消费；不同组互不干扰。
4. offset：消息位置，存在消费者端；offset可以重置。

> 追问链：
> Partition作用？分区越多性能一定越高吗？→ ISR是什么？OSR副本？leader副本挂了怎么选新leader？→ 消费者组概念，如果消费者数量大于partition数量会怎么样？多出的消费者空闲。

### RocketMQ
架构角色：`NameServer、Broker、Topic、Queue(消息队列)、Producer、Consumer、ConsumerGroup`
1. NameServer：注册中心，无状态；Broker向NameServer注册；客户端从NameServer发现Broker。
2. Broker：分为Master/Slave；CommitLog真实存储消息；ConsumeQueue是消息索引。
> 追问：CommitLog与ConsumeQueue区别？为什么要设计两层存储？

### RabbitMQ
模型：Exchange交换机、Queue队列、Binding绑定；四种交换机：direct、fanout、topic、headers。

> 面试官常问对比：Kafka、RocketMQ、RabbitMQ适用场景。

## 链路2：消息可靠性【最重要面试链：如何保证消息不丢失】
> 消息丢失发生在三个阶段：**生产者发送阶段、MQ服务端存储阶段、消费者消费阶段**。

### ① 生产者发送丢失
- Kafka：acks机制。acks=0（不等确认，可能丢）；acks=1(leader写成功返回)；acks=-1/all(leader+所有ISR副本落盘才返回，最高可靠)。
- RocketMQ：同步发送、异步发送；同步刷盘；发送返回状态判断，失败重试。

### ② MQ服务端丢失
- Kafka：副本机制；不能只有单副本；开启acks=-1；刷盘。
- RocketMQ：刷盘策略：**同步刷盘/异步刷盘；主从复制同步/异步**。
> 同步刷盘：消息落磁盘才返回；异步刷盘写pagecache就返回，操作系统定时刷盘，机器断电会丢消息。

### ③ 消费者消费丢失
> 核心：**消费offset提交时机**。
- Kafka：先消费消息，再提交offset。如果处理完业务还没提交offset进程宕机 → 重启重复消费；**如果先提交offset再执行业务，宕机消息直接丢失**。
- RocketMQ：consumer返回ACK，才标记消费成功；如果业务没执行完宕机，没有ACK，消息会重新投递。

> 完整连环追问：
> 一条消息从发送到消费，哪些环节会丢消息？分别怎么处理？
> Kafka acks三个值含义？RocketMQ同步刷盘异步刷盘区别？
> 为什么Kafka不能先提交offset再执行业务？

## 链路3：消息重复消费 & 幂等性（必考题）
**起始：MQ为什么会产生消息重复？**
根本原因：**至少一次投递(at‑least‑once)**，MQ不保证恰好一次exactly‑once。
场景：
1. MQ收到消息，返回给生产者的网络响应丢失，生产者重试，产生重复消息。
2. 消费者处理完业务，提交offset/ACK时网络异常，MQ未收到ACK，消息重新投递。

> 追问：怎么解决重复消费？**MQ本身不能解决，业务实现幂等**。

业务幂等常见方案：
1. 业务唯一ID，数据库唯一索引；
2. 数据库版本号乐观锁；
3. Redis记录已处理消息ID；
4. 状态机判断。

> 面试官坑：能不能让MQ保证消息只消费一次？Kafka的exactly‑once原理（生产者事务+offset事务），生产很少用。

## 链路4：顺序消息
**起始：如何保证消息的顺序性？**
> 问题根源：分区/队列内有序；跨分区全局无序。

### Kafka
- 同一个业务key，哈希取模，发送到**同一个Partition**，partition内部消息有序。
- 一个partition只能被一个消费者线程消费，消费保证顺序。
> 追问：开启多线程消费同一个partition，顺序还能保证吗？不能。

### RocketMQ
支持普通顺序消息、严格顺序消息；同一个队列queue有序。

> 追问链：
> 全局严格顺序会牺牲并发性能；什么业务需要顺序？订单状态流转；
> 如果业务大部分不需要顺序，少量需要顺序怎么做？按业务key落到同一个队列。

## 链路5：消息积压【高频场景题】
**起始：线上MQ消息大量积压怎么排查、怎么处理？**
积压根本原因：**消费速度 << 生产速度**。

排查步骤：
1. 看监控，确认堆积数量；定位哪个topic哪个队列。
2. 检查消费者是否挂掉；消费逻辑是否阻塞；消费线程太少；消费逻辑慢（IO、DB慢）。

处理手段：
1. 临时增加消费者实例，注意：**消费者数量不能超过partition/queue数量**。
2. 优化消费业务逻辑，减少耗时；同步改异步（注意业务幂等）。
3. 临时扩容分区（Kafka扩容分区不能迁移旧消息）。
4. 如果积压特别巨大，紧急方案：丢弃过期消息；或者新建topic，旧消息做离线处理。

> 连环追问：
> Kafka消息会永久保存吗？不会，有保留时间，默认7天。**积压太久，消息过期被删除 → 消息丢失！**

## 链路6：事务消息（RocketMQ重点，Kafka弱事务）
**起始：RocketMQ事务消息原理，解决什么问题？**
场景：本地数据库事务 和 MQ发送消息保持原子性；比如下单成功同时发送订单消息。

RocketMQ事务消息四阶段：
1. Producer发送半消息（half消息），消息对消费者不可见。
2. 执行本地事务。
3. Producer提交commit / rollback。commit消息可见；rollback消息删除。
4. 如果Producer宕机，Broker会回查本地事务状态（事务回查）。

> 连环追问：
> 回查次数有限制；本地业务需要提供查询事务状态接口；
> 事务消息能保证100%不丢消息吗？极端情况也会有边界；不是强一致性，是最终一致性。
> Kafka事务：生产者事务，适合流处理，业务很少用来做本地DB+MQ事务。

> 对比：本地消息表、可靠消息事务消息、最大努力通知。

- Master挂掉，RocketMQ4.5之前**不会自动主从切换**；5.x支持DLeger自动切换。

# Spring & SpringBoot 深挖面试链路

> 面试提问主线：IOC容器 → Bean生命周期 → Bean循环依赖 → AOP → Spring事务（重中之重）→ SpringBoot自动配置 → 常见坑、源码关键点，层层连环追问。

## 链路1：Spring IOC容器、Bean的完整生命周期
**起始问题：Spring中一个Bean完整生命周期讲一遍**
1. 资源定位（xml/注解扫描）
2. 解析、生成BeanDefinition
3. 实例化Bean（构造方法）
4. 属性填充 populateBean（setter、@Autowired注入）
5. Bean的前置处理：BeanPostProcessor#postProcessBeforeInitialization
6. 初始化：
    - @PostConstruct
    - InitializingBean#afterPropertiesSet
    - init‑method
7. BeanPostProcessor#postProcessAfterInitialization（AOP代理在这里生成！重点）
8. Bean放入单例池，对外提供使用
9. 销毁：@PreDestroy、DisposableBean、destroy‑method，容器关闭执行

> 追问链：
- `@PostConstruct` 和 `InitializingBean` 和 init‑method 执行顺序？
> @PostConstruct → InitializingBean → init‑method
- BeanFactory 和 ApplicationContext区别？
> BeanFactory是底层IOC容器，懒加载；ApplicationContext是子接口，更多能力，预初始化单例Bean。
- FactoryBean和BeanFactory区别？FactoryBean用来生成复杂对象，getObject返回真正bean。

> 高频坑：**AOP代理对象是在postProcessAfterInitialization这一步生成**。

## 链路2：循环依赖（超级高频深挖）
**起始问题：什么是循环依赖？Spring怎么解决循环依赖？哪些情况解决不了？**
> A依赖B，B依赖A。

三级缓存：
1. **一级缓存 singletonObjects**：完全初始化好的单例Bean
2. **二级缓存 earlySingletonObjects**：实例化完成，但还没填充属性的原始对象（未代理）
3. **三级缓存 singletonFactories**：ObjectFactory，lambda，用来生成早期代理对象

解决原理：
1. A实例化完成，把lambda工厂放入三级缓存；
2. A填充属性发现需要B，开始创建B；
3. B实例化完成，放入三级缓存；B填充属性需要A；
4. 从A的三级缓存执行lambda，得到A原始对象（如果需要代理就生成代理），放到二级缓存；
5. B完成属性填充、初始化，放入一级缓存；
6. A拿到B对象，完成属性填充、初始化，移入一级缓存。

> 连环追问：
1. **为什么需要三级，二级缓存行不行？**
> 如果全部提前代理，不需要三级；但大部分bean不需要代理，为了性能，把代理延迟到真正需要的时候，所以需要三级缓存。
2. **什么场景Spring解决不了循环依赖？**
    - **多例prototype Bean**：不缓存，直接报错；
    - **构造器注入循环依赖**：实例化阶段就要拿到对方对象，还没机会进三级缓存；
    - 循环依赖中需要AOP代理，早期代理出问题场景。
3. 三级缓存只针对**单例singleton**生效。

> 面试官坑：循环依赖不是万能，构造注入直接报错。

## 链路3：依赖注入 @Autowired @Resource
**起始：@Autowired 和 @Resource区别？**
1. @Autowired：Spring注解，**按类型注入**，可以配合@Qualifier按名称；默认需要对象，required=false允许null。
2. @Resource：JSR‑250标准，优先byName，其次byType。

> 追问链：
- @Autowired注入的流程，怎么处理多个同类型Bean？NoUniqueBeanDefinitionException。
- @Component、@Service、@Repository、@Controller。
- @Configuration 和 @Component区别？@Configuration里面@Bean会CGLIB代理，保证多次调用方法返回同一个单例对象；普通@Component不会代理。

> 坑：@Configuration如果不加，类内部调用@Bean方法会创建多个对象。

## 链路4：Spring AOP（面向切面编程）
**起始：AOP实现原理，JDK动态代理 vs CGLIB代理？**
1. JDK动态代理：**目标类必须实现接口**；生成接口实现类。
2. CGLIB代理：继承目标类生成子类；不需要接口；final类无法代理。

> Spring5.x / SpringBoot2.x 默认代理策略：
- 目标实现接口：JDK；否则CGLIB；
> SpringBoot2默认AOP使用CGLIB。

> AOP五大通知：
> @Before前置、@AfterReturning返回、@AfterThrowing异常、@After最终、@Around环绕。

> 追问链：
1. AOP什么时候生成代理对象？Bean生命周期 postProcessAfterInitialization。
2. **同一个类内部方法调用，AOP为什么不生效？（经典坑）**
> this调用的是原始对象，不是代理对象，切面不会执行。
> 解决方案：上下文拿代理对象；或者AopContext.currentProxy()。
3. @Around和其他通知区别，可以控制目标方法执行。

## 链路5：Spring事务【Spring面试最重要一大块，深挖长链】
**起始：Spring事务实现原理？AOP动态代理。**
> Spring事务本质：AOP，在方法执行前后开启、提交/回滚事务；基于数据库事务。

### @Transactional注解
> 追问链：
1. @Transactional哪些场景**事务失效（必背）**
    1. 方法不是public；
    2. 同类内部调用，this调用，不走代理；
    3. 异常被try‑catch捕获，没有抛出异常；
    4. 异常类型不对：默认只回滚RuntimeException & Error；普通Exception不会回滚，需要指定rollbackFor；
    5. 数据库引擎不支持事务（MyISAM）；
    6. 多线程，新线程里面操作，不属于同一个事务。

2. 事务传播行为7种（重点）
- REQUIRED（默认）：有就加入，没有新建
- SUPPORTS：有就加入，没有非事务执行
- MANDATORY：必须存在事务，否则抛异常
- REQUIRES_NEW：新建独立事务，挂起外层
- NOT_SUPPORTED：挂起事务，非事务运行
- NEVER：不能有事务，有则报错
- NESTED嵌套事务：保存点savepoint，只对DataSourceTransactionManager生效。

> 高频追问：REQUIRES_NEW 和 NESTED区别？
> REQUIRES_NEW：完全独立新事务；外层回滚不影响内层；
> NESTED：同一个物理事务，设置保存点；外层回滚内层一起回滚，内层回滚不影响外层。

3. 事务隔离级别5种，和数据库一一对应
DEFAULT(用数据库级别)、READ_UNCOMMITTED、READ_COMMITTED、REPEATABLE_READ、SERIALIZABLE。

4. 事务超时、只读readOnly。

> 经典场景题：外层REQUIRED，内层REQUIRES_NEW；内层抛异常，外层能不能回滚？内层已经提交。

# SpringCloud 深挖面试链路

> 主线：微服务核心组件 → Nacos注册配置中心 → Feign远程调用 → LoadBalancer负载均衡 → Sentinel熔断限流 → Gateway网关 → 分布式问题（分布式事务、配置、服务调用），区分SpringCloud、SpringCloud Alibaba。
> 注意：现在主流是 **Spring Cloud Alibaba(Nacos/Sentinel/Dubbo)**，旧Eureka/Hystrix基本淘汰。

## 链路1：SpringCloud vs SpringCloudAlibaba
**起始问题：Spring Cloud 和 Spring Cloud Alibaba是什么关系？**
1. Spring Cloud：一套微服务规范，不是具体实现；提供接口标准。
2. Spring Cloud Alibaba：阿里基于这套规范做的实现。
    - 注册配置中心：Nacos（替代Eureka+Config）
    - 流量防护：Sentinel（替代Hystrix）
    - RPC：Dubbo（可选，替代Feign底层http）
    - 分布式事务：Seata
> 旧版本组件：Eureka（已停更）、Hystrix（停更）、Ribbon（已被LoadBalancer替代）

> 追问链：
> Eureka为什么被淘汰？AP架构，无持久化，停更；Nacos支持CP/AP切换，同时做注册中心+配置中心。

## 链路2：Nacos 注册中心 + 配置中心（最高频）
### Nacos作为注册中心
**起始：Nacos服务注册发现原理？AP/CP模式？**
1. 服务提供者启动向Nacos注册实例；心跳上报（默认5s）；Nacos检测实例健康状态。
2. 消费者拉取服务实例列表，本地缓存，长轮询更新。
3. Nacos支持两种模式：
    - **AP（默认，服务注册用）**：优先可用性，弱一致性；适合微服务注册。
    - **CP**：强一致性，选主Raft协议；适合配置中心。

> 连环追问：
1. Nacos健康检查机制？
    - 客户端心跳：客户端主动上报；
    - 服务端主动探测（http/tcp）。
    心跳超时15s标记不健康，30s剔除实例。
2. Nacos集群怎么保证高可用？Raft协议，3节点/5节点集群。
3. Nacos实例有**临时实例、持久实例**区别：
    - 临时实例：依靠客户端心跳，客户端下线自动删除；AP模式；普通微服务。
    - 持久实例：不会因为下线删除；CP模式；比如网关、定时任务服务。

### Nacos作为配置中心
> 追问链：DataId、Group、Namespace作用
- Namespace：做环境隔离（dev/test/prod）
- Group：同一环境下业务分组
- DataId：配置文件名
配置动态刷新：`@RefreshScope`；变更推送，客户端长轮询感知配置变化。

> 坑：@RefreshScope只刷新被该注解修饰的Bean；@ConfigurationProperties不需要@RefreshScope也可以动态刷新。

> 经典问题：Nacos配置变更，哪些Bean可以自动刷新，哪些不行？

## 链路3：OpenFeign远程调用
**起始：OpenFeign原理？怎么实现接口就可以http调用？**
1. Feign是声明式客户端；基于接口+注解生成代理对象。
2. 启动时 `@EnableFeignClients` 扫描Feign接口，生成Feign代理Bean。
3. 调用接口方法，实际走Feign代理，组装请求，通过http客户端发送请求。
> 底层客户端：默认URLConnection；可以替换Apache HttpClient、OkHttp。

> 连环深挖追问
1. Feign和Dubbo对比：Feign基于HTTP；Dubbo基于TCP二进制，性能更高。
2. Feign超时时间：两个超时，**Feign自身超时 + LoadBalancer重试**，很容易超时混乱。
3. Feign请求头丢失问题：拦截器RequestInterceptor，统一添加token。
4. Feign默认不打印完整日志，需要配置日志级别。
5. Feign传参坑：GET请求传POJO对象会报错，要拆成参数。

> 坑：OpenFeign不会自动传递上下文token，需要手动拦截器透传。

## 链路4：负载均衡 LoadBalancer（Ribbon已废弃）
**起始：LoadBalancer负载均衡策略？**
1. SpringCloud2020之后移除Ribbon，使用LoadBalancer。
2. 内置策略：轮询、随机；支持自定义负载均衡算法。
> 追问：负载均衡分两种：
- **客户端负载均衡（LoadBalancer/Nacos）**：消费者本地选择实例；
- **服务端负载均衡(Nginx)**：网关层做。

> 场景题：同一服务多实例，权重怎么实现？Nacos支持实例权重配置，配合自定义LoadBalancer实现权重路由；灰度发布。

## 链路5：Sentinel 流量防护（替代Hystrix）
**起始：Sentinel和Hystrix对比？Sentinel核心概念：资源、规则、Slot责任链。**
1. Hystrix：线程池隔离，只支持熔断；停止维护。
2. Sentinel：滑动时间窗口，支持限流、熔断降级、热点参数限流、系统保护、授权规则。

### 两大隔离模式
- **线程池隔离(Hystrix)**：每个服务一组独立线程池，隔离度高，线程开销大。
- **信号量隔离(Sentinel)**：限制并发请求数量，不新开线程，轻量；不能隔离慢IO。

> 连环追问
1. 熔断三种状态：关闭、打开、半开。
    - 打开：拒绝请求；过时间进入半开，放行少量探测请求；成功则关闭熔断，失败继续打开。
2. 限流规则：直接限流、关联限流、链路限流。
3. 热点参数限流：针对接口入参限流。
4. Sentinel的滑动时间窗口原理：时间切片统计QPS。
5. Sentinel规则持久化：默认内存，重启丢失；配置Nacos存储规则。

> 坑：Sentinel默认只对SpringMVC接口生效；自定义方法需要手动埋点@SentinelResource。
> blockHandler处理限流；fallback处理业务异常。两者区别。

## 链路6：Spring Cloud Gateway 网关
**起始：Gateway核心架构，三大概念：Route、Predicate、Filter**
1. Route路由：id、uri、断言、过滤器。
2. Predicate断言：匹配请求路径、参数、header，匹配成功执行路由。
3. Filter过滤器：pre前置、post后置；修改请求响应。
> Gateway底层Netty+Reactor响应式编程；**不是Servlet，不能用Servlet相关API**。

> 连环深挖追问
1. Gateway和Zuul区别：Zuul1阻塞IO性能差；Gateway非阻塞Reactor，性能更好。
2. 过滤器执行顺序：pre过滤器按order从小到大；post从大到小。
3. 网关鉴权、限流怎么做：Gateway集成Sentinel；JWT校验写全局filter。
4. 网关跨域CORS配置。
5. 网关雪崩问题：网关层也要限流熔断。

> 高频坑：Gateway是响应式环境，不能用@Transactional，不能使用ThreadLocal，要用Reactor Context传递上下文。

## 链路7：Seata分布式事务【重点深挖】
> 微服务跨库、跨服务操作，本地事务失效，需要分布式事务。
> Seata四种模式：**AT、TCC、SAGA、XA**，业务最常用AT模式。

### AT模式（重点）
角色：TC事务协调器、TM事务管理器、RM资源管理器。
AT三阶段：
1. 一阶段：执行业务SQL，记录undo_log回滚日志；提交本地事务；释放锁。
2. 二阶段‑commit：删除undo_log，业务完成。
3. 二阶段‑rollback：读取undo_log，生成补偿SQL回滚数据。

> 连环追问
1. AT模式原理：**行锁，基于undo_log；无侵入，只需要注解@GlobalTransactional**。
2. AT的脏写问题：Seata全局锁机制。
3. TCC：Try‑Confirm‑Cancel；业务侵入高，自己写补偿逻辑；性能高。
4. SAGA：长事务，没有锁；适合长流程；补偿模式。
5. XA：数据库层面两阶段，性能差。

> 坑：@GlobalTransactional失效场景；非公共方法；内部调用；远程调用不是Seata RM；新开启线程。

## 链路8：微服务通用问题综合深挖
1. **服务雪崩、服务降级、服务熔断、服务限流概念区分**
- 雪崩：一个服务故障链式扩散拖垮整个集群
- 熔断：下游故障，不再调用下游服务，快速失败
- 降级：舍弃非核心业务，返回兜底数据
- 限流：限制请求QPS，保护系统

2. 灰度发布怎么做？Nacos权重 + Gateway灰度过滤器；header灰度标记。
3. 微服务上下文传递问题：Feign调用ThreadLocal丢失；
> 普通SpringMVC用RequestInterceptor；Gateway响应式用Reactor Context。

4. 配置中心优先级：本地配置、Nacos配置、bootstrap/application。

# 高并发系统设计深挖面试链路

> 面试主线：高并发指标 → 分层优化（前端→网关→应用→缓存→DB）→ 缓存全套问题 → 分库分表 → 限流/熔断/降级 → 异步削峰 → 分布式问题（一致性、幂等、分布式ID）→ 系统压测、故障演练，业务场景+实际取舍，不是堆砌技术名词。

## 起始问题：什么是高并发？衡量系统并发的核心指标
Q：衡量高并发系统看哪些指标？
- **QPS/TPS**：每秒请求数 / 每秒事务数
- **RT响应时间**：单次请求耗时，平均RT、P95、P99（非常重要，看慢请求）
- **并发连接数**：同时处理的请求连接
- **可用性**：SLA，几个9；比如99.99%代表一年允许52分钟不可用

> 追问：QPS高但RT很高代表什么？系统瓶颈，CPU/IO/DB阻塞。
> 高并发核心思路：**尽可能减少耗时；尽可能并行处理；把压力转移；保护核心链路**。

> 两大方向：**提升系统吞吐能力；保护系统不被打挂**。

## 链路1：高并发整体分层架构（自上而下）
访问链路：**前端 → CDN → Nginx/Gateway网关 → 微服务应用层 → 缓存层 → 数据库层**
每一层都可以做性能优化。

1. **前端层**
静态资源CDN；页面合并压缩；浏览器缓存；页面懒加载；按钮防重复点击。

2. **网关层（Nginx / Spring Cloud Gateway）**
- Nginx：负载均衡、长连接、限流、黑名单、静态资源。
- Gateway：路由、鉴权、网关限流、灰度、请求过滤。
> 追问：Nginx负载均衡策略：轮询、权重、ip_hash、least_conn最小连接。

3. **应用服务层**
- 水平扩容：多实例部署，无状态设计（**无状态！不能在服务器内存存用户会话**，会话放Redis）
- 异步化：MQ异步处理非核心流程
- 线程池优化：IO密集、CPU密集线程参数调优；避免同步阻塞
- 锁优化：减少锁粒度、读写锁、分段锁、避免大锁；乐观锁代替悲观锁
- 业务裁剪：非核心逻辑降级，去掉不必要的查询计算

4. **缓存层（高并发重中之重，80%问题在这里）**
多级缓存：本地缓存(Caffeine) → 分布式缓存(Redis)
> 连环深挖缓存整套问题
- 缓存模式：Cache‑Aside旁路缓存（业务最常用）、Read‑Through、Write‑Through、Write‑Back
> Cache‑Aside：读：先查缓存，miss查DB，回写缓存；写：先更新DB，再删除缓存。

> 经典坑：更新数据库是**删缓存而不是更新缓存，为什么？**
> 并发场景下更新缓存会出现脏数据；删除缓存，下次读自动重建更安全。

- **缓存穿透**：查询不存在的数据，直接打到DB。
解决方案：布隆过滤器；缓存空值；接口参数校验。
- **缓存击穿**：热点key过期，大量并发同时打到DB。
方案：互斥锁；永不过期。
- **缓存雪崩**：大量key同时过期 / Redis宕机，大量请求打数据库。
方案：过期时间加随机偏移；Redis高可用集群；多级缓存；服务限流熔断。
- **缓存与数据库双写不一致**
> 先更新DB再删缓存，依然存在极小概率不一致（读请求在DB更新完、缓存删除前读到旧数据写回缓存）。
> 解决方案：延迟双删；MQ异步重试删除缓存； Canal监听binlog删除缓存；最终一致性；强一致性场景不适合用缓存。

> 追问：本地缓存Caffeine优缺点？速度极快；多实例数据不一致；占用JVM内存。

5. **数据库层，DB扛并发手段**
1. 索引优化：避免回表，避免索引失效；覆盖索引。
2. 读写分离：主库写，从库读；一主多从分摊读压力。
> 坑：主从同步延迟；刚写完立刻读，读到旧数据；方案：重要查询强制走主库。
3. 分库分表：水平分表、垂直分表
> 水平：数据行拆分；垂直：大字段拆分。
> 分片策略：range范围分片；hash哈希分片。
> 中间件：Sharding‑Sphere。
> 分库分表带来新问题：分布式ID；跨库join；分页排序；分布式事务；扩容迁移麻烦。

## 链路2：流量防护三板斧：限流、熔断、降级
> 雪崩产生链路：某个服务故障 → 调用堆积线程耗尽 → 上游全部拖垮 → 整个系统雪崩。

### 限流：挡掉多余流量，保护系统，保证核心请求可用
**限流位置：网关层、应用层都可以做。**
限流算法深挖：
1. 计数器：简单，临界时间点会有突刺（临界问题）
2. 滑动窗口（Sentinel用）：解决临界问题；时间切片统计QPS
3. 漏桶算法：流出速率固定，削峰，无法应对突发流量
4. 令牌桶算法：可以允许突发流量，网关Guava RateLimiter

> 追问：分布式限流怎么做？单机限流只限制单实例；分布式用Redis+Lua全局限流。

### 熔断：下游服务故障，快速失败，不继续调用故障服务
状态机：关闭→打开→半开。Sentinel/Hystrix。
> 熔断≠降级；熔断针对**调用的下游服务**。

### 降级：牺牲非核心业务，保障核心业务
- 返回兜底数据；关闭非核心接口；关闭复杂计算；关闭推荐、统计等次要功能。
> 降级是针对**自己系统内部业务**。

> 面试高频辨析：雪崩、熔断、降级、限流四者区别。

## 链路3：异步化 & 削峰填谷（MQ）
把同步流程改成异步，提升接口响应速度，削峰。
> 例：下单：扣库存生成订单同步；短信、积分、日志走MQ异步。

> 代价：系统变成最终一致性；要处理消息丢失、重复消费、积压；业务需要幂等。

> 追问：什么业务不能异步？需要强一致性，要立刻拿到结果，不能异步。

## 链路4：分布式相关问题（高并发必然遇到）
### 分布式ID
需求：全局唯一；有序；高性能。
方案对比：
1. 数据库自增：简单，分库分表不好用；
2. UUID：无序，太长；
3. Redis INCR：性能高，依赖Redis；
4. Snowflake雪花算法：时间+机器id+序列号；趋势有序；**时钟回拨大坑**。
> 时钟回拨怎么处理？记录上一次时间，时间回拨直接拒绝或者等待。

### 幂等设计
高并发、重试、MQ重复消费、接口重复提交，都需要幂等。
方案：唯一索引；业务token；Redis记录请求id；状态机；乐观锁version。

## 链路5：热点问题（真实大厂高频场景）
1. **热点Key问题**：某个key超高QPS，把Redis单实例打满。
方案：本地缓存；key副本拆分；热点key识别；网关层拦截。
2. **热点商品秒杀场景深挖**
秒杀痛点：瞬间超大流量；超卖；库存并发竞争。
秒杀分层思路：
- 前端：按钮置灰，验证码；
- 网关：限流；
- Redis预扣库存；
- MQ异步下单；数据库最终扣减；
> 防超卖：Redis lua原子扣库存；数据库乐观锁/分布式锁。
> 坑：不要把全部压力打到DB；库存不能存在JVM内存。

## 链路6：高并发带来的各种取舍（面试官最爱问）
> 没有完美架构，都是取舍：CAP、BASE理论
1. CAP：分布式系统，**一致性C、可用性A、分区容错P，三者不可兼得；P必须有，只能选AP或者CP**。
2. BASE：基本可用、软状态、最终一致性；互联网高并发系统大多选择AP，接受最终一致性。

> 业务选型：
- 互联网大部分高并发业务：AP，最终一致性；
- 支付交易：偏向CP，保证数据一致。

> 经典问题：为什么互联网业务大多用最终一致性，不用强一致性？强一致性性能代价巨大，并发上不去。

2. 故障演练：Redis宕机、DB宕机、MQ故障，验证降级熔断是否生效。

# 设计模式 + 代码优化深挖面试链路
> 面试主线：23种设计模式重点（常用7‑8种）→ 创建型、结构型、行为型 → 手写场景 + Spring源码中模式体现 → 代码坏味道 → 代码优化手段 → OOP七大原则 → 重构技巧 → 性能优化，面试官喜欢结合业务代码提问，不是死背定义。

## 链路1：面向对象七大设计原则（所有模式的根基）
**起始：讲下面向对象设计七大原则**
1. **单一职责 SRP**：一个类只做一件事，只有一个变化原因。
2. **开闭原则 OCP**：对扩展开放，对修改关闭；新增功能尽量加代码，不修改旧逻辑。
3. **里氏替换 LSP**：子类可以替换父类，不能破坏父类原有逻辑。
4. **依赖倒置 DIP**：依赖抽象，不要依赖具体实现；面向接口编程。
5. **接口隔离 ISP**：接口尽量小，不要大而全，不要强迫实现不需要的方法。
6. **迪米特法则（最少知道）**：类尽量少依赖其他类，降低耦合。
7. **合成复用原则**：优先组合/聚合，而不是继承。

> 追问：继承有什么坏处？继承是强耦合；父类改动全部子类受影响；优先使用组合。

## 链路2：三大类设计模式（高频重点，结合Spring源码）
### 创建型模式（对象怎么创建）
1. **单例模式 Singleton【最高频】**
> 5种写法：饿汉、懒汉、双重检查锁DCL、静态内部类、枚举单例。
> DCL为什么加volatile：防止指令重排序，对象半初始化。
> 枚举单例：防止反射、序列化破坏单例，EffectiveJava推荐。
> Spring中Bean默认单例。

> 追问：破坏单例方式：反射、序列化、克隆；枚举可以抵御。

2. **工厂方法 & 抽象工厂 Factory**
- 简单工厂（不属于23种）：一个工厂生产所有产品；违反开闭。
- 工厂方法：一个工厂对应一个产品；扩展产品新增工厂类。
- 抽象工厂：生产一族相关产品。
> Spring BeanFactory就是工厂模式。

3. **建造者模式 Builder**
链式构建复杂对象，参数很多。
`User.builder().name().age().build()`；
Spring中`BeanDefinitionBuilder`；MyBatis SqlSessionFactoryBuilder。
> 和工厂区别：工厂侧重“生产对象”；Builder侧重**分步组装复杂对象**。

4. **原型模式 Prototype**
对象克隆；Spring scope=prototype。深拷贝、浅拷贝问题。

### 结构型模式（类/对象怎么组合）
1. **适配器模式 Adapter**
把一个接口转成另外需要的接口；做兼容适配。
SpringMVC `HandlerAdapter`适配不同Controller。

2. **装饰器模式 Decorator**
**增强原有对象功能，不改变原始对象；和继承相比更灵活**。
IO流`BufferedInputStream`；Spring `BeanWrapper`。
> 适配器：改变接口；装饰器：**不改变接口，增强功能**。

3. **代理模式 Proxy（重点）**
静态代理、动态代理（JDK/CGLIB）。
Spring AOP就是代理模式。
> 装饰器 vs 代理：装饰器侧重增强；代理侧重控制访问。

4. **桥接模式 Bridge**
多维度变化，避免类爆炸；拆分抽象与实现。

5. **组合模式 Composite**
树形结构，叶子节点、容器节点统一处理；比如菜单、部门树。

6. **外观模式 Facade 门面**
提供统一高层入口，屏蔽内部复杂子系统。
比如网关、工具Facade类，对外只暴露简单方法。

7. **享元模式 Flyweight**
复用对象，减少内存；池化思想。Integer缓存、线程池。

### 行为型模式（对象之间怎么交互）
1. **策略模式 Strategy【业务写代码最常用】**
> 同一套行为有多种算法，可互相替换。把不同算法封装成策略。
> 示例：支付方式（微信、支付宝）、运费计算、折扣算法。
> Spring `ResourceLoader`；`Comparator`。
> 消除大量if‑else/switch，用策略模式。

> 追问：策略模式怎么不用if拿到对应策略？Spring把所有策略Bean注入Map，key为类型，直接get。

2. **模板方法 Template Method**
父类定义算法骨架，步骤固定，部分步骤交给子类实现。
模板固定流程，子类重写部分逻辑。
Spring `JdbcTemplate`；Servlet。

> 策略模式：**整个算法替换**；模板方法：**流程骨架固定，部分步骤扩展**。

3. **观察者模式 Observer 发布订阅**
事件通知，一对多。
Spring事件监听`ApplicationEvent`；MQ本质思想。

4. **责任链模式 Chain of Responsibility**
请求沿着一条链依次处理；可以中断传递。
SpringMVC拦截器链、Sentinel Slot责任链、Filter过滤器。

5. **状态模式 State**
对象行为依赖自身状态，状态切换改变行为；大量if根据状态判断，适合改成状态模式。
订单状态：待支付、已支付、已取消。

> 状态模式 vs 策略模式：策略是外部传入算法；状态是对象内部状态驱动行为。

6. **命令模式 Command**
把请求封装成对象；可撤销、排队。

7. **迭代器模式 Iterator**
遍历集合，Java Iterator。

> 剩余：备忘录、中介者、访问者，面试很少考，了解概念即可。

## 链路4：代码坏味道 & 代码优化深挖链路
**起始：什么是代码坏味道？日常开发哪些代码要重构？**
常见坏味道：
1. 过长方法、过大类；一个方法几百行。
2. 过多if‑else、嵌套if，深度超过3层。
3. 魔数，没有常量。
4. 重复代码（复制粘贴）。
5. 大入参、长参数列表。
6. 实体类字段爆炸，一个DTO几十个字段。
7. 硬编码写死配置。
8. 注释泛滥：注释多往往代表代码写得差，优先优化代码可读性。
9. 上帝类，一个类干所有事情，违反单一职责。
10. 多余的临时变量，空判断泛滥。

> 追问：代码优化是不是越炫越好？优先可读性，不要过度设计，**拒绝过度设计！简单优先**。

### 代码重构优化手段
1. **提取方法**：大方法拆小方法，方法尽量短，一个方法做一件事。
2. **提取类**：上帝类拆分，遵循单一职责。
3. **替换魔法数字为常量、枚举**。
4. **消除if‑else**
    - 策略模式；
    - 表驱动Map；
    - 枚举内置逻辑；
    - 卫语句，提前return，减少嵌套层级。
> 卫语句：条件不满足直接return，减少if嵌套。
5. 合并重复逻辑，抽取公共工具/父类/组合。
6. 使用Builder模式处理多参数对象。
7. 尽量使用枚举代替字符串状态。
8. 入参太多，封装成DTO对象。

> 重要原则：**不要过早优化，不要过度设计；先能跑，再可读，再性能。简单优先。**

## 链路5：Java代码性能优化深挖
> 不是调JVM，是业务代码层面优化

1. **集合优化**
- ArrayList随机访问快；LinkedList随机访问慢，不要用fori遍历LinkedList。
- HashMap指定初始容量，避免频繁扩容；`new HashMap<>(size)`。
- 集合遍历：for‑each、迭代器；不要边遍历边remove，会ConcurrentModificationException，用迭代器remove。

2. **字符串优化**
大量拼接用`StringBuilder`；循环内不要用`+`。

3. **避免创建多余对象**
循环内部不要new对象；复用对象；使用享元、池化。

4. **异常优化**
异常很耗性能，不要用异常做业务逻辑判断；try‑catch不要放循环内。

5. **锁优化**
缩小锁范围；读写锁；乐观锁代替悲观锁；避免大锁。

6. **IO、数据库**
- 数据库：避免N+1查询；批量操作；合理索引；少select *；
- IO流必须关闭，try‑with‑resources自动关闭资源。

7. **Stream流**
简单集合可以用Stream提升可读性；不要过度嵌套Stream；大集合注意性能。

> 坑：Stream不是一定比for快，数据量小普通for可能更快，优先可读性。

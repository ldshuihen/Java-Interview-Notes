# 电商订单完整业务流程（从下单→支付→发货→确认收货→关闭/退款）

> 基于微服务：用户服务、订单服务、库存服务、优惠券服务、支付服务；Redis做预扣、RocketMQ异步、MySQL存真实数据、状态机流转。

## 一、下单流程（生成待支付订单）

1. **参数校验** 校验用户登录、商品、数量、地址；校验优惠券是否可用。

2. Redis Lua预扣库存

   原子操作：判断Redis可售库存，预扣库存；

   > ⚠️**只扣Redis，MySQL真实库存不变**

3. RPC调用优惠券服务‑TCC Try阶段

   冻结优惠券，优惠券标记已占用。

   > RPC调用放在事务外面，避免大事务。

4. **订单服务本地事务**

- 创建订单主表：状态 `WAIT_PAY(待支付)`

- 创建订单明细表（商品、数量、单价）

- 记录优惠金额、实付金额

  > 如果本地事务失败： ①释放Redis预扣库存；②RPC解冻优惠券，流程结束。

​    5.**返回下单成功，生成订单号（雪花ID），跳转到支付页面**

> 此时状态：订单=待支付；Redis库存被预扣锁定；优惠券冻结；MySQL库存不变。

> 兜底：30分钟超时未支付，需要关闭订单。

## 二、订单超时关闭（用户不付款）

两种触发：**RocketMQ延时消息（主） + XXL‑Job定时任务（兜底）**

1. 查询订单，状态机条件更新：

   ```
   update order_main set status=CLOSED where order_no=xxx and status=WAIT_PAY
   ```

   > affected_rows !=1，说明状态已经变更，直接结束。

2. 更新成功： 

   ①Lua脚本**释放Redis预扣库存**（MySQL库存不动！还没扣过） 

   ②RPC解冻优惠券，优惠券恢复可用

3. 订单终态：已关闭，流程结束。

## 三、支付成功流程（第三方支付回调）

1. 第三方支付平台回调我方接口，**HTTP只做验签，投递MQ后直接返回**，不做业务逻辑。
2. MQ消费端处理支付成功消息：
3. **本地事务**
   - 状态机更新订单：`update order_main set status=PAID where order_no=xxx and status=WAIT_PAY`，行数0直接return（幂等）
   - 插入支付流水记录payNo（唯一）

​    4.**RocketMQ事务消息发送消息** 通知库存服务扣真实库存、通知优惠券服务核销优惠券。

> 本地DB事务成功，消息才投递出去；本地失败消息不发送。

​    5.库存服务消费消息：执行MySQL真实库存扣减

```
update stock set count = count‑num where id=stockId and count>=num;
```

> MySQL行锁兜底，防止超卖。

> 当前状态：订单=已支付；MySQL真实库存扣减；优惠券核销完成。

> 兜底：如果MQ丢失消息，定时任务扫描：状态=已支付，但库存未扣的订单，补发消息补偿。

## 四、发货流程（商家操作）

1. 商家后台发货，传入物流单号
2. 状态机更新订单：`update order_main set status=SHIPPED where order_no=xxx and status=PAID`
3. 写入物流信息，发送MQ通知用户已发货。

## 五、确认收货（用户确认收货 / 系统自动确认）

1. 更新订单状态：`update order_main set status=FINISHED where order_no=xxx and status=SHIPPED`
2. 订单流转终态：已完成。

## 六、退款流程（全额退款 / 部分退款）

### ①全额退款

1. 用户申请退款，校验订单状态必须为`PAID / SHIPPED`

2. 创建退款单 order_refund，状态`REFUNDING退款中`；订单主状态改为退款中。

3. RPC调用支付平台退款接口。

   > 如果调用超时：退款单停留在退款中，**不判成功失败**，定时任务主动查询第三方退款接口，禁止重复调用退款。

4. 第三方退款回调，HTTP验签投递MQ。

5. MQ消费：

- 更新退款单状态为`REFUNDED已退款`（带旧状态条件更新，幂等refundNo）
- 更新订单主状态为已退款（终态）
- MQ发送消息通知库存服务**MySQL回补库存**；退回优惠券（判断是否过期）。

### ②部分退款

> 重点：**订单主状态不变，依旧PAID**，全部记录在退款子表。

1. 用户申请部分退款，校验累计退款金额不能超过实付。
2. 创建退款单子表，状态退款中。
3. 调用支付部分退款接口。
4. 退款回调成功，更新该退款单成功；**只回补对应数量MySQL库存**。
5. 多次部分退款；当全部金额退完，再将订单主状态改为REFUNDED。

## 七、异常兜底整套机制

1. **所有状态变更使用状态机条件update，禁止先select再update，防止并发错乱。**
2. MQ：至少一次投递，业务做幂等；消息丢失靠定时任务扫描补偿。
3. RPC超时不直接判定成功失败，以数据库订单状态为事实来源。
4. 库存定时对账任务：`DB可售库存 = Redis可售库存 + 待支付订单锁定库存`，不一致以MySQL修复Redis。
5. 延时消息+定时任务双重兜底关闭超时订单。

## 极简背诵版（面试口述）

> 用户下单，先Redis预扣库存，RPC冻结优惠券，数据库生成待支付订单，此时不扣真实库存；30分钟未支付则关闭订单，释放Redis库存和优惠券。 用户支付成功，支付回调投递MQ；消费端状态机更新订单为已支付，通过事务消息通知扣MySQL真实库存、核销优惠券。 商家发货，订单变为已发货；用户确认收货订单完成。 退款分为全额和部分退款，部分退款不修改主订单状态；退款成功后MySQL回补库存。 全程使用状态机条件更新；RPC超时不直接判结果，依靠MQ+定时任务做补偿，实现分布式最终一致性。

# 加入优惠券完整订单‑支付‑退款流程

> 微服务：订单、库存、优惠券、支付服务；优惠券支持：冻结、核销、退回（判断有效期）；下单TCC冻结、支付成功核销、订单关闭解冻、退款退回优惠券；部分退款做特殊处理。

## 一、下单流程（生成待支付订单 WAIT_PAY）

1. 参数校验：用户、商品、收货地址；校验**优惠券合法性**（是否可用、使用门槛、有效期），计算优惠、实付金额。

2. Redis Lua预扣商品库存（仅Redis，MySQL真实库存不变）。

3. **优惠券服务 TCC‑Try：冻结优惠券** RPC调用优惠券服务，把这张优惠券状态改为【已冻结】，标记关联orderNo；

   > RPC放在事务外面，防止大事务。 冻结失败，直接返回下单失败，释放Redis库存。

4. 订单服务本地事务：

- 创建订单主表：状态`WAIT_PAY`，记录使用的优惠券ID、优惠金额。

- 创建订单明细表。

  > 如果本地事务异常回滚： 
  >
  > ①Lua释放Redis预扣库存 
  >
  > ②RPC调用优惠券Cancel，**解冻优惠券，恢复可用**。

​    5.返回下单成功，跳转支付页面。

> 当前状态： 
>
> 订单：待支付；Redis库存锁定；**优惠券冻结**；MySQL库存不变。

## 二、订单超时关闭（30分钟未支付）

触发：RocketMQ延时消息 + XXL‑Job兜底定时任务

1. 状态机条件更新订单：

   ```
   update order_main set status=CLOSED where order_no=xxx and status=WAIT_PAY
   ```

   > affected_rows≠1直接结束。

2. 更新成功执行： ①Lua释放Redis预扣库存 ②**RPC调用优惠券Cancel：解冻优惠券，恢复可用**

3. 订单变为终态已关闭。

## 三、支付成功流程（支付回调）

1. 第三方支付回调接口，验签，把支付消息投递MQ，立刻返回。
2. MQ消费处理支付成功消息：
3. 订单本地事务：

- 状态机更新订单：`update order_main set status=PAID where order_no=xxx and status=WAIT_PAY`；行数0直接return（幂等）
- 插入支付流水payNo。

1. **RocketMQ事务消息发出两条通知消息**

- 消息1：库存服务 → 扣减MySQL真实商品库存
- 消息2：优惠券服务 → **TCC‑Confirm，核销优惠券，优惠券标记已使用，不可再用**

> 事务消息保证：订单本地事务成功，消息才对外投递；本地失败消息不发送。

> 兜底补偿：定时任务扫描，订单状态=已支付，但优惠券未核销 / 库存未扣，重新补发消息。

> 当前状态：订单已支付；MySQL库存扣减；**优惠券核销完成**。

## 四、发货、确认收货（和优惠券无关，不变）

1. 商家发货 → SHIPPED
2. 用户确认收货 → FINISHED（终态）

## 五、退款流程（全额退款 & 部分退款，优惠券退回逻辑）

> 优惠券退回规则：

1. **全额退款**：如果优惠券还在有效期内，退回优惠券，可以再次使用；已经过期，则不退回。
2. **部分退款**：电商通用逻辑：**不退回优惠券**（优惠已经分摊到商品，部分退款不返还券；业务也可配置按比例退回，面试讲通用方案）。

### 5.1 全额退款

1. 用户申请退款，校验订单状态 PAID / SHIPPED。

2. 订单服务创建退款单`order_refund`，状态`REFUNDING退款中`，订单主状态改为`REFUNDING`。

3. RPC调用第三方支付退款接口。

   > RPC超时：不判定成功失败；定时任务轮询第三方退款接口查询结果，禁止重复调用退款。

4. 第三方退款回调，验签投递MQ。

5. MQ消费退款成功消息： 

   1）退款单条件更新为`REFUNDED`（refundNo做幂等） 

   2）更新订单主状态为`REFUNDED`终态 

   3）发送MQ消息： 

   - 库存服务：MySQL回补商品库存 

   - **优惠券服务：执行优惠券退回逻辑**    

       判断优惠券当前时间是否在有效期：         

     ​      ✅未过期：恢复优惠券为可用状态，可以再次使用；         

     ​      ❌已经过期：不做退回，券直接作废。

### 5.2 部分退款

> 业务规则：部分退款**不退回优惠券**，订单主状态保持PAID不变，全部退款信息记录在退款子表。

1. 用户申请部分退款，校验累计退款金额不能超过订单实付金额。
2. 创建退款单子表，状态REFUNDING。
3. RPC调用支付部分退款。
4. 退款回调成功，MQ消费：
   - 更新该退款单状态为已退款
   - MQ通知库存：回补对应数量MySQL库存
   - **不操作优惠券，券依旧为已核销状态，不予退回**
5. 如果多次部分退款，累计退款等于订单实付金额，此时才把主订单状态修改为REFUNDED，再执行全额退款的优惠券退回逻辑（判断有效期）。

## 六、兜底补偿（优惠券相关）

1. 定时任务扫描：
   - 订单已支付，但优惠券还是冻结状态 → 补发核销消息；
   - 订单关闭，但优惠券仍然冻结 → 补发解冻；
   - 退款成功，但优惠券没有按规则退回 → 补偿处理。
2. 所有优惠券变更都记录操作日志（冻结、核销、解冻、退回），方便排查。

## 📝面试口述精简版（背诵）

> 下单的时候校验优惠券，通过TCC把优惠券冻结，数据库生成待支付订单，只预扣Redis库存，不扣真实库存。 如果30分钟没有支付，关闭订单，释放Redis库存同时解冻优惠券，券恢复可用。 支付成功回调进入MQ，更新订单为已支付；事务消息通知库存扣MySQL真实库存，同时确认核销优惠券，券标记已使用。
>
> 退款分全额和部分退款。全额退款成功之后回补库存，同时判断优惠券是否还在有效期，有效期内退回优惠券，过期就作废。 部分退款默认不退回优惠券，只回补对应库存；只有多次部分退款累计等于全部实付金额，才走全额退款逻辑处理优惠券。
>
> RPC超时不直接判定结果，定时任务扫描补偿优惠券异常状态，实现分布式最终一致性。

# 完整订单流程（新增菜鸟物流对接，含优惠券、库存、退款全链路）
微服务模块：订单服务、库存服务、优惠券服务、支付服务、**物流服务（对接菜鸟SDK）**

> 物流交互说明：
> 1. 商家在后台发起发货，调用我方物流服务；
> 2. 我方物流服务调用菜鸟开放平台API，**生成运单号、打印面单**；
> 3. 菜鸟推送物流轨迹回调到我方接口；
> 4. 我方存储物流轨迹，前端展示物流信息。

## 一、下单流程（WAIT_PAY 待支付）
1. 参数校验用户、商品、收货地址，校验优惠券合法性，计算优惠金额、实付金额。
2. Redis Lua预扣库存（仅Redis，MySQL库存不变）。
3. 优惠券TCC‑Try，RPC冻结优惠券，绑定orderNo；冻结失败直接返回，释放Redis库存。
4. 订单本地事务：创建订单主表、订单明细表，记录优惠券ID、优惠金额，状态`WAIT_PAY`。
> 事务回滚：释放Redis库存 + 优惠券Cancel解冻。
5. 返回下单成功，跳转支付页面。

## 二、订单超时关闭（延时消息+定时任务兜底）
1. 条件更新订单状态为`CLOSED`，行数不为1直接结束。
2. 释放Redis预扣库存；RPC解冻优惠券。
> 订单关闭，**不会触发物流，无运单**。

## 三、支付成功流程
1. 第三方支付回调，验签后投递MQ，直接响应支付平台。
2. MQ消费：
    - 本地事务：状态机更新订单为`PAID`，写入支付流水payNo。
    - RocketMQ事务消息发送两条消息：
      - 库存服务：扣减MySQL真实库存
      - 优惠券服务：TCC‑Confirm，核销优惠券
3. 兜底定时任务：扫描已支付但未核销券、未扣库存的订单，补发消息补偿。

## 四、商家发货 → 对接菜鸟物流（新增）
> 前置条件：订单状态必须为 **PAID（已支付）**
1. 商家后台点击【发货】，传入：快递公司编码、包裹商品信息、收件人地址（下单保存的收件信息）。
2. **我方物流服务调用菜鸟API接口**
    - 请求菜鸟接口：生成电子运单号、获取面单PDF（供商家打印快递面单）。
    - 菜鸟侧生成物流运单。
3. 调用成功后：
    1）订单服务状态机更新订单：
    ```sql
    update order_main set status=SHIPPED where order_no=xxx and status=PAID
    ```
    2）数据库新增物流运单记录：order_no、运单号、快递公司、收件地址、面单链接。
    3）向RocketMQ发送消息：通知用户端订单已发货。

> 两种获取物流轨迹方式：
> ① **菜鸟主动回调推送轨迹**：菜鸟平台物流节点更新，调用我方回调接口；我方解析轨迹存入数据库。
> ② 我方轮询：定时调用菜鸟接口拉取物流信息，做兜底，防止回调丢失。

> 异常：调用菜鸟接口失败（网络超时、参数错误），订单状态不变，不更新为已发货；记录异常，供商家重试发货。

## 五、确认收货（两种触发方式）
1. **用户手动确认收货**：前端触发接口。
2. **系统自动确认收货**：发货N天后（例如7天），定时任务自动执行确认收货。

执行逻辑：
```sql
update order_main set status=FINISHED where order_no=xxx and status=SHIPPED
```
订单流转终态【已完成】。

## 六、退款流程（全额退款 / 部分退款，含优惠券、库存，新增物流校验）
### 前置校验
> 如果订单状态是`SHIPPED(已发货)`：需要业务判断是否已经签收。
> - **未签收**：一般流程是商家拦截物流，拦截成功之后才允许退款；
> - **已经签收**：用户需要走退货流程（用户寄回商品，商家收到退货后再退款）。

> 下面分为：**未发货退款、已发货未签收、已签收退货退款**

### 6.1 全额退款
#### 场景A：未发货（订单状态PAID）
1. 用户申请全额退款，创建退款单`REFUNDING`，订单主状态改为`REFUNDING`。
2. RPC调用支付平台退款接口；超时不判结果，定时轮询第三方退款结果。
3. 支付退款成功回调，投递MQ。
4. MQ消费：
    - 更新退款单为`REFUNDED`；订单主状态更新`REFUNDED`终态。
    - MQ消息通知库存服务回补MySQL库存。
    - 优惠券服务：**全额退款，券未过期退回，过期作废**。

#### 场景B：已发货但未签收（SHIPPED）
1. 用户申请退款，系统调用**菜鸟API发起拦截运单**，通知快递公司拦截包裹。
2. 等待菜鸟回调拦截结果：
    - ✅拦截成功（包裹未发出/中途截回）：执行上面全额退款整套逻辑，回补库存、处理优惠券退回。
    - ❌拦截失败（包裹已经发出）：不允许直接退款，引导用户走退货流程。

#### 场景C：已签收（FINISHED，退货退款）
1. 用户提交退货申请，生成退货单；生成**退货运单**，用户线下把商品寄回商家。
2. 用户填写退货快递单号（用户自己找快递，也可调用菜鸟生成退货运单）。
3. 商家后台确认收到退回商品。
4. 才执行退款流程：更新退款单、回补库存、判断有效期退回优惠券。

### 6.2 部分退款
1. 未发货状态：支持部分退款，**不退回优惠券**，仅回补对应数量库存；多次部分退款金额等于实付时，执行全额退款逻辑。
2. **已发货SHIPPED状态：不支持部分退款**，只能走退货流程。

## 七、轨迹回调异常兜底
1. 菜鸟回调丢失：物流服务定时任务调用菜鸟API轮询运单轨迹，更新本地数据库。
2. 运单状态异常，记录日志，后台可人工修改物流信息。

## 八、完整状态流转回顾
`待支付WAIT_PAY`
├─超时关闭 → 已关闭CLOSED
└─支付成功 → 已支付PAID
  ├─未发货全额退款 → 退款中REFUNDING → 已退款REFUNDED
  └─商家调用菜鸟发货 → 已发货SHIPPED
    ├─未签收：调用菜鸟拦截运单，拦截成功再退款；拦截失败走退货
    └─用户确认收货/自动确认 → 已完成FINISHED
      └─已签收，走退货退款流程

## ✨面试口述精简版本

> 用户下单生成待支付订单，TCC冻结优惠券，只预扣Redis库存。超时未支付关闭订单，释放库存解冻优惠券。
> 支付成功更新订单为已支付，事务消息扣MySQL真实库存，核销优惠券。
> 商家发货时，物流服务调用菜鸟开放平台API生成运单号和打印面单；菜鸟回调推送物流轨迹，我方保存轨迹供前端展示；也做轮询兜底防止回调丢失，订单流转为已发货。
> 用户手动或者系统自动确认收货，订单变为已完成。
>
> 退款分多种场景：未发货可以直接退款；已经发货未签收，要调用菜鸟接口拦截包裹，拦截成功才能退款；拦截失败就要用户退货寄回，商家收到货之后再退款。全额退款看优惠券有效期决定是否退回，部分退款默认不退回优惠券。

### 1. 简述电商完整订单业务流程，各个状态流转？订单有哪些状态？

**完整业务流程**
1. 用户提交下单请求；
2. 校验参数、用户、商品、价格、库存；
3. 预扣库存；
4. 生成订单+订单商品明细；
5. 生成支付单，引导用户支付；
6. 用户发起支付，支付平台回调我方服务；
7. 更新订单为已支付，扣真实库存，触发发货通知；
8. 商家发货，更新物流；
9. 用户确认收货，订单完成；
10. 申请退款/售后，执行退款流程；
11. 订单关闭（超时未支付、手动取消）。

**订单核心状态**
- **待支付**：订单创建完成，还没付钱
- **已支付待发货**：支付成功，等待商家发货
- **已发货待收货**：商家已发货，等待用户签收
- **已完成**：用户确认收货，正常结束
- **已取消**：未支付状态下手动取消 / 超时关闭
- **已退款 / 部分退款**：发生售后退款

**状态流转关键点**
- 只有【待支付】可以走到已取消；
- 待支付 → 支付成功 → 已支付待发货；
- 已支付后不能直接取消，只能走退款流程；
- 状态机要做状态校验，禁止非法流转，例如已支付订单不能再被超时关闭。

> 面试加分：订单状态建议用**状态机**管理，硬编码if‑else容易写出bug。

### 2. 用户下单完整链路，从请求进来，到订单入库，中间会做哪些事情？

```
网关 → 应用服务 → 各个校验 → 库存预扣 → 生成订单 → 落库 → 返回支付链接
```
1. **网关层**：鉴权、token校验、限流、参数校验，非法请求直接拦截。
2. **订单服务接收请求**：获取用户ID、购物车选中商品、规格、数量、收货地址。
3. **业务校验**
    - 用户状态校验；
    - 商品合法性：商品是否上架、规格是否存在；
    - 价格校验：前端传的价格和后端数据库价格比对，**防止前端篡改价格**；
    - 购买数量校验，限购校验。
4. **库存预扣**：先预扣Redis库存（大促），后续再落DB；防止超卖。
5. **幂等校验**：判断该业务流水号是否已经处理过，防止重复下单。
6. **构建订单数据**：生成orderId、计算实付金额、优惠分摊（优惠券、积分、满减），组装订单主表、订单明细表。
7. **事务内写入订单主表、订单明细表**；
8. 调用支付服务生成支付流水；
9. 返回结果给前端，跳转支付页面；
10. 发送MQ消息：创建订单事件（用于积分、通知、统计），发送延时消息用于超时关闭。

> 注意：这里不会直接在同一个事务扣数据库库存，会产生大事务问题。

### 3. 订单超时未支付自动关闭，怎么实现？对比定时任务、延时队列、时间轮方案优缺点

需求：订单待支付，超过30min未支付，自动关闭订单，回滚库存，修改订单状态。

#### 方案1：定时任务扫描数据库

原理：定时任务每隔一段时间，扫描数据库，查询状态=待支付 && 创建时间超过30分钟的订单，执行关闭逻辑。
- ✅优点：实现简单，不需要中间件，稳定可靠。
- ❌缺点：
  1. 时间不精准，任务间隔5分钟，则最多延迟5分钟关闭；
  2. 大促订单量大，扫描数据库压力大；
  3. 容易重复处理，必须用状态机+分布式锁防止重复关闭。
适用：小流量系统。

#### 方案2：延时队列（RocketMQ延时消息 / Redis zset延时队列）

原理：下单成功发送一条30分钟延时消息；消息到期消费，执行关闭订单逻辑。
- ✅优点：触发时间相对精准；不轮询数据库；削峰；业务解耦。
- ❌缺点：
  1. RocketMQ延时消息等级固定，不能任意指定时间；
  2. 如果消息丢失，订单永远不会关闭，**必须定时任务做兜底扫描**；
  3. 消费失败需要重试。
适用：中大厂主流方案，延时消息 + 定时任务兜底。

#### 方案3：时间轮

原理：内存时间轮，将订单放到时间轮对应槽位，到期触发关闭。
- ✅优点：触发非常精准，性能高。
- ❌缺点：应用重启内存数据全部丢失；单机，不适合分布式；需要持久化兜底。
适用：单机本地任务，**不适合分布式订单系统**。

✅**生产选型**：RocketMQ延时消息作为主逻辑，定时任务扫库做兜底补偿。

### 4. 下单的时候，先扣库存还是先创建订单？为什么？会出现什么问题？

> 结论：**先预扣库存，再创建订单**（Redis预扣）；数据库层面是先创建订单，再扣真实库存。

#### 如果先创建订单，后扣库存

1. 创建订单成功，扣库存失败。产生大量无效待支付订单，订单存在但是没库存，用户无法支付。
2. 数据库大事务问题，如果把创建订单+扣DB库存放同一个事务，高并发下锁等待，数据库压力巨大。

#### 主流方案（电商生产）

1. Redis预扣库存：预扣成功，才往下走创建订单；预扣失败直接返回库存不足。
2. 数据库：先创建订单（待支付）；用户支付回调成功后，再扣数据库真实库存。

**风险点**：Redis预扣成功，用户一直不支付。需要超时关闭订单，把预扣库存释放回Redis。

> 一句话面试总结：Redis层先预扣，拦截无库存请求，避免生成大量无效订单；DB侧创建订单在前，支付成功后扣真实库存。

### 5. 什么是幂等？下单接口为什么要做幂等，如何实现下单幂等？

**幂等**：同一个请求重复提交多次，业务结果只能生效一次，不会生成多个订单。

**为什么下单要幂等**
1. 用户重复点击提交按钮；
2. 网络超时，前端重试；
3. 网关重试、RPC重试、MQ重复消费；
不做幂等会：同一个用户多次下单，生成多笔相同订单，库存多扣，超卖。

#### 下单接口幂等实现方案

1. **业务token方案（前端下单接口最常用）**
前端请求下单前，向服务获取唯一下单token；提交下单的时候带上token；服务端校验token，使用之后删除token。同一个token只能使用一次。适合前端页面提交。

2. **外部唯一业务流水号**
业务生成唯一requestId，客户端携带；服务端把requestId作为唯一键；处理前先判断该requestId是否处理过；可以存Redis或者数据库唯一索引。适合RPC调用、MQ消费。

3. **数据库唯一索引**
订单表增加业务唯一请求号，数据库唯一索引，重复插入直接报错拦截。

4. **状态机校验**
业务执行前先判断当前订单状态，只有待支付状态才允许执行对应操作，非法状态直接返回。

> 不推荐：单纯靠数据库select判断，并发场景会出现幻读，不能保证幂等。

### 7. 订单取消逻辑：手动取消、超时关闭，库存怎么回滚？

两种场景：**手动取消（用户主动取消）、超时系统关闭**，前提：订单状态必须是【待支付】。

1. **修改订单状态为已取消，状态机校验，防止重复关闭**
2. **Redis预扣库存回补**：把之前预扣掉的库存加回Redis。
3. 数据库库存此时不需要处理：因为还没有支付，数据库真实库存还没有扣减。
4. 如果已经走到支付成功，不能直接取消订单，走退款流程。

边界问题：
- 如果Redis回补失败怎么办？需要定时对账任务扫描异常订单，补偿库存。
- 要做幂等，避免多次回补库存，导致库存变多。

> 总结：待支付阶段取消，只回滚Redis预扣库存；DB库存还没扣，不用动。

### 8. 多规格商品，下单时怎么校验商品库存、价格？下单瞬间商品改价怎么办？

#### 校验库存

1. 根据product_id + product_spec_id拿到对应规格；
2. Redis拿到该规格剩余库存；判断购买数量不能大于库存；
3. Redis执行预扣库存；
4. DB作为兜底校验，防止Redis和DB不一致。

#### 价格校验（重点，防止前端篡改价格）

前端传过来的价格**不能直接信任**。
后端根据商品规格查询数据库的实时售价，和前端提交过来的价格对比，如果不一致直接拒绝下单。

#### 下单瞬间商品改价问题

场景：用户下单过程中运营修改商品价格。
1. 下单的时候，后端拿数据库实时价格做校验；
2. 将**下单时刻的价格存入order_item明细表作为快照**；后续商品改价不会影响历史订单；
3. 订单后续所有计算，都使用快照价格，不读现在商品表的价格。

> 面试踩坑点：不能后续查询订单的时候实时查商品表价格，商品价格变了老订单金额就错乱。

### 9. 购物车到下单，整个流程，购物车数据存在哪里？

#### 购物车存储方案

1. **登录用户：存MySQL数据库**，持久化，换设备数据不丢失。
2. **未登录游客：存浏览器LocalStorage，前端本地存储**；登录之后把本地购物车合并到后端数据库。

#### 购物车到下单完整流程

1. 用户勾选购物车内多个商品规格；
2. 前端把选中的购物项id传给后端订单服务；
3. 后端查询数据库购物车，拿到商品id、规格id、购买数量；
4. 校验商品是否上架、库存、价格；
5. 执行预扣库存；
6. 生成订单主表+明细表；
7. **下单成功之后清空对应购物车勾选的记录**；
8. 返回支付信息。

> 补充：购物车数据量大，不需要缓存全部购物车，下单时才读取校验。

### 10. 拆分订单：一个订单多个商品分不同仓库，如何拆单？拆单后支付、退款怎么处理？

业务场景：一个订单买A商品属于北京仓，B商品属于上海仓，需要拆成2个子订单。

#### 拆单逻辑

1. 用户提交一个原始请求；
2. 订单服务根据商品所属仓库，按仓库维度进行拆分；
3. 生成**1个父订单，N个子订单**；每个子订单对应一个仓库；每个子订单有自己order_id；
4. 每个子订单独立拥有订单明细；
5. 父订单只做聚合，不参与实际履约；真实业务操作全部操作子订单。

#### 支付处理

1. 用户只看到一次支付；用户支付一笔总金额；
2. 支付回调之后，把支付结果分发到每一个子订单；所有子订单同时更新为已支付；
3. 任意子订单库存扣减失败，要做补偿。

#### 退款处理

支持整单退款、部分子订单退款
1. 整单退款：全部子订单执行退款；
2. 只退其中一个子订单：只操作对应子订单，其他子订单正常履约；
3. 退款金额做聚合计算，返回给支付平台。

#### 业务难点

1. 子订单状态不一致问题，需要状态机控制；
2. 父订单状态要同步跟随子订单状态；
3. 幂等：支付回调要保证所有子订单只会处理一次。

> 面试一句话总结：按仓库拆分为父子订单，用户侧感知是一笔订单，后端拆成多个子订单独立履约；支付只调用一次第三方，业务层分发到各个子订单。

### 1. 订单表数据量大，千万级订单如何分库分表？按什么字段分片？用户id还是orderId？

#### 背景

订单数据很容易到千万、亿级别，单库单表查询慢、写入瓶颈，需要分库分表，一般用Sharding‑JDBC。

#### 分片字段选择：user_id vs order_id

1. **按 user_id（用户ID分片，生产最常用）**
- 逻辑：对`user_id`取模/哈希分片。同一个用户所有订单落到同一个库同一张表。
✅优点：**用户查询自己的订单（我的订单），直接路由到一个分片，不需要跨库跨表，查询性能极高**。这是C端用户最核心的查询场景。
❌缺点：
  - 商家后台查全部订单：商家要查所有用户订单，会**全分片扫描**，压力大；
  - 存在热点分片：某个大用户订单极多，出现单表数据倾斜。

2. **按 order_id（订单号）分片**
✅优点：数据分布均匀，不容易倾斜。
❌缺点：用户查自己订单，不知道orderId，只能全分片查询，性能很差，C端不可接受。

> ✅生产主流选择：**分片键使用 user_id**。C端用户查询是最高频场景，优先保证C端。商家后台统计查询走其他方案解决。

#### 分库分表方案

- 水平分库：拆多个库，分散写压力；
- 水平分表：每个库内部再拆多张表，控制单表数据量，一般单表控制在**2000w以内，建议500‑1000w**。
> 不建议垂直分表：订单主表、订单明细表本身已经拆分，订单主表字段不会特别多。

#### 遗留问题怎么解决

1. 商家后台、运营后台查询全部订单：**不能直接查分库分表订单库**
    - 方案1：同步数据到Elasticsearch，后台查询走ES；
    - 方案2：同步到数仓做统计分析；
2. 数据倾斜：对超大用户做特殊处理，或者做二次拆分。
3. 跨分片join尽量避免，订单主表和order_item明细使用相同分片键user_id，**父子表绑定分片**，保证同一用户订单和明细落在同一个分片，避免跨分片join。

> 面试一句话总结：C端订单优先按user_id分片，保证用户查自己订单性能；商家后台查询通过ES/数仓承担，不要直接查询分库分表业务库。

### 2. orderId订单号怎么生成？雪花算法？需要包含哪些信息？为什么不能用自增id当订单号

#### 订单号生成：雪花算法SnowFlake（业界主流）

雪花算法64位long结构：
1. 符号位：1bit，固定0；
2. 时间戳：41bit，毫秒时间戳；
3. 机器ID：10bit，机器/分片编号，分布式环境保证不同机器不重复；
4. 序列号：12bit，同一毫秒内自增，单机同一毫秒最多生成4096个ID。

**订单号包含信息：时间戳、机器编号、序列号**，可以解析出订单创建时间。

> 注意：雪花算法有时间回拨风险，机器时间回退会产生重复ID，生产要做时间回拨校验、拒绝生成ID。

#### 为什么不能直接使用数据库自增ID作为订单号

1. **暴露业务量**：自增id连续，竞争对手可以通过订单号轻易算出你的日订单量。
2. **分库分表场景冲突**：多个库都自增，会出现订单ID重复。
3. **安全性差**：容易被遍历爬取订单。
4. 自增ID只适合单库单表主键，不适合分布式订单号。

> 补充：也可以业务拼装订单号（时间+机器+业务编码），雪花long类型在Java、数据库存储更友好。orderId作为业务单号，数据库主键依然可以用普通bigint主键。

### 3. 订单表索引怎么设计？哪些查询条件需要建索引？为什么不能给所有字段建索引

#### order_main订单主表核心索引

1. **主键索引**：id（物理主键）
2. **普通索引：user_id + order_status**（联合索引，高频：用户查询我的订单，按状态筛选）
> `select * from order_main where user_id=? and order_status=? order by create_time desc`
3. **普通索引：order_id** 唯一索引，根据订单号查询订单。
4. **普通索引：create_time**：用于定时任务扫描超时订单、归档任务。

order_item订单明细表：
- order_id普通索引，通过订单查明细。

#### 哪些条件建索引总结

高频查询条件：user_id、order_id、order_status、create_time。
> 联合索引要遵循最左匹配，`user_id,order_status,create_time`，覆盖用户查订单+按状态过滤+按时间排序。

#### 为什么不能给所有字段建立索引

索引本质是B+树：
1. **占用磁盘空间**：每增加一个索引，就要维护一套B+树，占用大量存储。
2. **写性能下降**：订单新增、更新时，所有索引都要同步更新B+树。订单高并发写入场景，索引越多，insert/update越慢。
3. MySQL优化器会选错索引，索引多增加优化器开销。

> 原则：**只给查询高频字段建索引，减少写开销；避免冗余索引。**

### 4. 下单事务问题：创建订单、扣库存在一个事务会有什么问题？大事务危害

> 场景：伪代码
```java
@Transactional
public void createOrder(){
    //1 创建订单
    orderMapper.insert();
    //2 更新数据库库存
    stockMapper.update();
}
```
把创建订单、扣DB库存放在同一个本地事务。

#### 会出现什么问题

1. **大事务**：事务执行时间拉长，如果库存服务是远程调用，RPC网络耗时会把事务持有时间拉长。
2. **锁等待严重**：更新库存会加行锁，事务长时间不提交，行锁长时间持有，其他下单请求阻塞，数据库大量锁等待，TPS下降，出现死锁。
3. 数据库连接池耗尽：事务不释放，数据库连接被长期占用，新请求拿不到连接。
4. 回滚代价大，事务日志膨胀。

#### 电商正确做法

1. Redis做预扣库存，拦截大部分请求；
2. **创建订单事务只负责订单主、明细表落库，不操作库存DB**；
3. 用户支付回调成功之后，再单独小事务扣数据库真实库存。

> 面试重点：**拆分大事务，事务尽量小，事务内不要放RPC、网络IO。**

### 5. 超卖问题：数据库层面怎么防止超卖？`update stock set count=count‑1 where id=xx and count>0`原理

#### SQL

```sql
update stock set count = count - 1 
where id = #{stockId} and count > 0;
```
### 原理

1. MySQL InnoDB更新语句会加**行锁**；
2. `count>0`在SQL条件里面，数据库层面判断库存大于0才执行扣减；
3. 返回受影响行数：返回1代表扣减成功；返回0代表库存不足扣减失败。
> 多个并发请求排队获取行锁，串行执行这条update，不会出现count变成负数。

#### 优点

数据库原生能力，简单可靠，防止超卖。
#### 缺点

高并发大促场景，大量请求打到数据库，行锁竞争激烈，数据库压力大，性能差。

#### 生产使用方式

- **不能直接把大量请求打到数据库**；
- Redis预扣库存过滤大部分请求；只有预扣成功的请求，支付成功之后，才执行这条DB update做真实扣减，作为兜底。

> 重点：这条SQL可以防超卖，但扛不住大并发，只能做兜底，不能直接抗大促流量。

### 6. 订单表冷热数据分离，历史订单怎么处理？归档方案

业务现象：订单表，近3个月是热数据（频繁查询修改）；一年前历史订单几乎不会修改，查询少，属于冷数据。如果全部存在一张表，表越来越大，查询、更新性能持续下降。

#### 方案1：分冷热两张表

- order_main：热表，存放近3‑6个月订单，正常业务读写；
- order_main_history：归档冷表，存放历史订单。

归档逻辑：定时任务，把超过指定时间，并且订单状态终态（已完成/已取消/已退款）的数据迁移到history归档表；原热表删除。
> 注意：**只有终态订单才允许归档，还在履约的订单不能迁移。**

##### 查询怎么处理

1. C端用户查询订单：优先查热表；查不到再去归档表查询；业务层做聚合。
2. 统计分析：归档表、热表同步到ES/数仓。

#### 方案2：分区表（MySQL分区）

按时间范围做分区，按月分区。老分区直接卸载。
缺点：分区表有很多限制，分库分表场景下，分区表使用受限，**互联网生产用的不多**。

#### 方案3：同步到ES，业务库只保留热数据

业务库只存热数据；所有订单数据同步ES，用户查询可以走ES。

> 生产主流：冷热双表 + 定时任务迁移归档。

#### 7. 高并发下单，数据库锁问题，行锁、悲观锁、乐观锁在订单库存场景怎么选

##### 1.悲观锁

```sql
select * from stock where id=? for update;
```
获取数据的时候直接加行锁，其他线程阻塞等待。
- 优点：强一致性；
- 缺点：并发下锁竞争激烈，性能差，大促场景不适合。
> 场景：低并发、对一致性要求极高场景，**电商下单库存不推荐悲观锁**。

##### 2.乐观锁

不加锁，版本号机制，更新校验版本。
```sql
update stock set count=count‑1,version=version+1 
where id=? and version=#{oldVersion} and count>0;
```
- 优点：无锁，并发性能好；
- 缺点：并发高会大量更新失败，需要业务层重试；版本号要维护。

##### 3.普通update行锁（`count>0`）

就是上面第5题的SQL，update语句本身会加行锁，属于InnoDB隐式行锁。
> 区别：悲观锁是select for update先拿锁；这条update直接更新，where条件过滤。

##### 选型总结（订单库存场景）

1. **大促高并发：Redis预扣库存过滤流量，DB层使用`update ... count>0`作为兜底，不使用悲观锁。**
2. 普通业务场景可以乐观锁；
3. **悲观锁尽量避免，高并发下性能很差。**

> 一句话：库存DB不建议悲观锁；优先Redis拦截流量，DB使用update条件行锁兜底。

#### 8. 订单查询：用户查自己的订单、后台商家查全部订单，分表之后跨表查询怎么解决

前提：订单按user_id分库分表。

1. **C端用户查询自己的订单（高频）**
用户ID已知，直接路由到对应分片，单分片查询，没有跨分片问题，性能很好。

2. **商家后台、运营后台查询全部订单（难点）**
商家需要查询所有用户的订单，按照时间、状态筛选，按user_id分片就会需要查询所有分片，即全分片查询。
- 直接全分片查询：性能差，大量IO，业务库压力大，不能用于线上后台。

✅生产解决方案：
1. **数据同步到Elasticsearch**
通过canal监听order_main binlog，把订单数据同步ES。后台所有复杂条件查询、分页、筛选全部走ES；业务数据库只负责C端读写。
2. **同步到数据仓库**
报表、统计类需求直接查数仓，不碰业务库。
3. **中间表方案（不推荐）**：维护商家‑订单中间表，数据一致性难维护，容易不一致。

> 踩坑：千万不要在业务代码做循环查询所有分片然后内存分页，数据量大OOM，性能极差。

#### 9. 订单表为什么不建议做物理删除？逻辑删除怎么实现？

##### 为什么不物理删除

1. **数据溯源、对账需求**：订单是财务凭证，财务、退款、售后需要历史数据，物理删除后数据彻底丢失，无法对账排查问题。
2. **审计问题**：订单属于业务凭证，不能物理删除。
3. 分库分表场景，物理删除会产生碎片，影响索引性能。

##### 逻辑删除实现

增加字段 `is_deleted tinyint`；0未删除，1已删除。
- 删除不是执行delete，而是执行update set is_deleted=1。
- 查询的时候必须带上条件 `where is_deleted=0`。
- 索引设计：联合索引带上is_deleted，避免索引失效。

##### 注意坑

1. 写SQL的时候，忘记加is_deleted条件，查出已逻辑删除的数据；
2. 唯一索引：逻辑删除后，唯一索引会冲突。解决方案：可以使用 `delete_time`，删除时写入时间，未删除为null，利用mysql唯一索引null可重复特性。

> 补充：归档迁移的冷数据依然保留逻辑删除标记。

> Java秋招20k后端，电商订单库存高频面试题，偏生产落地，重点讲现象、问题、解决方案。

### 1. 库存为什么放Redis？Redis扣减库存完整流程

#### 为什么库存放到Redis

1. **扛高并发**：大促下单流量很大，如果全部打到MySQL，数据库行锁竞争激烈，会直接打垮DB；Redis内存操作，QPS很高，可以拦截绝大部分请求。
2. **快速拦截无库存请求**：库存不足直接在Redis层返回，不用走到数据库。
3. **支持预扣、超时释放库存的能力**，适配下单→等待支付的业务模型。
4. 削峰，过滤无效流量，只有Redis预扣成功的请求才会往下走创建订单、操作数据库。

> 注意：Redis库存只是**预扣库存**，真实库存还是以MySQL为准，Redis是前置拦截层。

#### Redis扣减库存完整流程

1. 用户发起下单请求，网关限流校验通过；
2. 拿到商品规格ID，先到Redis判断库存是否大于购买数量；
3. 使用`DECR`/`Lua脚本`执行预扣库存；
4. 如果返回剩余库存<0，预扣失败，直接返回“库存不足”，结束流程；
5. 预扣成功，继续往下执行业务：校验价格、生成订单落库；
6. 用户完成支付：支付回调，更新MySQL真实库存；
7. 用户超时未支付 / 手动取消订单：释放Redis预扣的库存。

> ⚠️生产必须用**Lua脚本**，保证判断库存和扣减库存是原子操作，不能分开多条命令。

### 2. Redis扣库存会出现哪些问题：超卖、少卖、库存和DB不一致，怎么解决？

#### ①超卖（库存扣成负数）

**原因**：分开执行判断库存、扣库存两条命令，没有原子性。
```redis
GET stock
if stock>num
DECR stock
```
并发下多个线程同时读到库存>0，同时扣减，出现负数。

✅解决：**Lua脚本把判断+扣减封装成原子脚本**，Redis单线程执行，避免并发问题。同时脚本内部做判断，如果扣完小于0直接拒绝。

#### ②少卖（Redis库存比DB库存小，明明DB还有库存，Redis显示没库存）

**场景1**：Redis预扣成功，订单创建成功，后续服务宕机，订单异常，库存没有回补；
**场景2**：延时消息丢失，超时未支付订单没有释放库存；
**场景3**：Redis宕机重启，数据丢失。

✅解决：
1. 定时对账任务，对比DB真实库存和Redis库存，发现差异自动补偿；
2. 延时消息 + 定时任务双重兜底释放库存；
3. Redis开启持久化RDB+AOF，降低宕机丢数据概率。

#### ③Redis与DB库存数据不一致

产生时机：
1. DB库存更新成功，Redis更新失败；
2. Redis库存释放成功，DB没有变化；

✅解决方案：
1. 不追求实时强一致，业务上接受**最终一致性**；
2. Canal监听数据库binlog，数据库库存变更，同步更新Redis；
3. 定时对账补偿，定时任务校对DB与Redis库存，以DB为准修复Redis。

> 面试总结：Redis做前置拦截，MySQL是库存数据源；Redis允许短暂不一致，靠对账兜底修复。

### 3. Redis库存预扣，下单成功但是支付失败，库存怎么释放？

场景：Redis预扣库存成功，订单创建为待支付；用户不付钱/支付失败，需要把预扣掉的库存归还Redis。

#### 三种释放方案

1. **RocketMQ延时消息（主方案）**
下单成功发送30分钟延时消息；消费消息执行关闭订单逻辑，如果订单依旧是待支付，则：修改订单状态为取消，执行Redis库存回补。

2. **定时任务兜底**
定时扫描数据库，查出待支付且超过超时时间的订单，做库存释放。**防止延时消息丢失的兜底**。

3. 用户手动取消订单：用户点击取消，直接同步释放Redis库存。

#### 重要坑点

- 释放库存必须做幂等！不能多次释放，不然Redis库存越补越多。
- 释放前先校验订单状态，只有待支付才允许回补库存。
- 如果此时用户刚好完成支付（并发：支付回调和超时关闭同时执行），靠订单状态机互斥，防止一边扣、一边回补。

> 面试话术：延时消息为主，定时任务兜底；状态机校验+幂等防止重复释放库存。

### 4. 缓存和数据库库存双写一致性问题，更新策略；先更DB还是先更缓存？

> 库存场景：DB是真实数据源，Redis是缓存。

#### 两种策略

1. **先更新数据库，再删除缓存（推荐）**
更新DB库存成功，再删除Redis库存；下次查询自动回写最新库存。
> 为什么是删除缓存，而不是更新缓存：高并发下更新缓存会有大量无效写，删除让它按需加载更合适。

2. 先删缓存，再更新数据库：会出现并发问题。
线程A删除缓存，还没更新DB；线程B读取旧DB数据写回缓存，造成缓存脏数据。**库存场景不推荐**。

#### 问题：更新DB成功，删除缓存失败怎么办？

Redis网络抖动，删缓存失败，缓存还是旧数据。
✅解决方案：
1. 删除失败发送MQ重试删除缓存；
2. Canal监听binlog，数据库库存变更，异步删除Redis缓存；
3. 定时对账任务兜底修复。

#### 库存场景特殊点

库存不是普通查询缓存，我们用Redis做**预扣计数**，不是简单查询缓存；
所以不会简单走普通缓存回写逻辑；DB库存变更，直接删除Redis库存，下次下单重新加载DB库存到Redis。

> 一句话面试：库存双写，优先**先更新DB，再删除缓存**；删除失败用MQ重试+Canal+定时对账兜底，追求最终一致性，不追求强一致。

### 5. 热点商品大量下单，缓存击穿、缓存穿透、缓存雪崩在下单场景如何防护

#### 缓存穿透：查询不存在的数据，直接打到DB

场景：恶意请求不存在的商品ID，绕过Redis直接访问数据库。
下单场景防护：
1. 参数校验，非法商品ID直接拦截；
2. Redis缓存空值；
3. 网关层限流。

#### 缓存击穿：热点key过期，大量并发请求同时打到数据库

场景：秒杀热点商品，Redis库存key过期，大量请求瞬间压到MySQL。
下单防护：
1. **热点key永不过期，不设置过期时间**，程序主动更新；
2. 互斥锁，缓存失效时只放行一个线程去DB加载数据；
3. 网关限流。

#### 缓存雪崩：大量key同时过期 / Redis宕机，大量请求打到DB

场景：大量商品缓存同一时间过期，或者Redis整体宕机。
下单防护：
1. 过期时间加随机偏移，避免大量key同时过期；
2. Redis集群高可用，主从+哨兵，避免单点故障；
3. 服务层熔断降级，Redis不可用的时候，直接返回“商品火爆，请稍后再试”，拒绝请求，不全部打到DB；
4. 网关限流削峰。

> 电商大促重点：秒杀热点商品库存key**禁止设置过期时间**，防止缓存击穿。

### 6. 订单信息要不要放Redis？什么场景适合缓存订单，什么不适合

订单数据：order_main订单主表。

✅适合放到Redis场景：
1. **高频查询，很少修改的订单**，例如查询订单详情；
2. 短时间内高频访问的新订单，刚下单用户马上查看订单；
3. 读多写少，提升查询性能。

❌不适合放Redis场景：
1. 订单状态频繁变更（支付、发货、退款），频繁更新缓存，一致性维护成本高；
2. 海量历史订单，全部存入Redis内存成本太高；
3. 对数据一致性要求极高，订单是财务凭证，不能接受缓存脏数据。

#### 实际生产做法

1. **不把全量订单放Redis**；
2. 新订单做短期缓存（例如1‑2小时），用户刚下单查详情走Redis；设置短过期时间；
3. 查询先查Redis，未命中查询MySQL；
4. 订单发生状态变更，直接删除对应订单缓存，防止脏数据。
5. 历史老订单直接查DB，不缓存。

> 面试总结：订单不会全量缓存，只缓存近期活跃订单；订单状态更新就删除缓存，不做更新。

### 7. Redis分布式锁在下单扣库存场景使用，会有什么坑？锁超时、锁误删，怎么解决

> 场景：很多同学想使用Redis分布式锁控制库存扣减并发。

#### 常见坑

1. **锁超时问题（业务执行时间 > 锁过期时间）**
业务还没执行完，锁过期自动释放；其他线程拿到锁，并发进入临界区，锁失效。

2. **锁被别的线程误删除**
线程A的锁过期，线程B拿到锁；线程A业务执行完，把B的锁删掉。

3. Redis单机问题：主从切换，锁还没同步到从机，主挂掉，锁丢失。

4. 性能问题：大量下单，抢锁会产生大量竞争，大量请求阻塞。

#### 对应解决方案

1. **避免误删：锁要带上唯一标识（UUID）**
释放锁的时候，判断value是自己的UUID，才允许删除；使用Lua脚本保证判断+删除原子性。

2. **锁超时问题：看门狗机制（Redisson）**
Redisson自动续期，业务没执行完，后台线程不断延长锁过期时间；业务执行完成关闭锁，停止续期。

3. 高可用：使用Redlock红锁（生产很少用，性能差）；更多使用Redis集群。

#### ⚠️非常重要面试加分点：库存扣减，**不推荐用分布式锁！**

为什么？
库存扣减完全可以用**Lua脚本原子扣库存**，不需要加锁。
分布式锁会带来大量抢锁竞争，降低吞吐量；锁是悲观的，会阻塞并发。
> 正确做法：库存判断+扣减全部交给Redis Lua脚本原子执行，不需要分布式锁。分布式锁更多用于防重复关闭订单、任务幂等场景。

> 面试话术：扣库存不要用分布式锁，Lua脚本直接原子完成；分布式锁适合执行时间较长的业务操作，比如订单关闭。

### 1. 订单系统哪些场景要用MQ？列举5个以上场景

MQ核心作用：**解耦、异步、削峰、延时**。订单系统典型场景：
1. **订单创建事件**：下单成功发送MQ，异步发送短信、站内通知、积分发放、用户统计，不阻塞主下单链路。
2. **订单超时关闭延时消息**：下单发送延时消息，到期执行关闭订单、回滚库存。
3. **支付回调解耦**：支付平台回调我方，把支付结果投递MQ，消费端更新订单状态、扣真实库存、触发发货。避免回调接口处理过重超时。
4. **退款异步处理**：退款申请发送MQ，调用第三方退款接口、更新订单退款状态。
5. **订单数据同步**：通过Canal+MQ，把订单库binlog同步到ES，供商家后台查询；同步数仓做报表统计。
6. **物流状态变更**：物流更新推送MQ，更新订单物流状态，推送物流通知给用户。
7. **大促削峰**：下单请求投递MQ，消费端慢慢消费，保护数据库，秒杀场景常用。

> 面试直接列举6‑7个，说出每个场景的目的，不要只罗列名字。

### 2. 下单发送MQ，如何保证消息不丢失？消息可靠性（生产者、Broker、消费者三端）

消息丢失分三段：生产者发送丢失、Broker存储丢失、消费者消费丢失，需要三端分别保障。

#### ①生产者端：消息发送到Broker丢失

问题：网络抖动，消息还没到达Broker就丢了。
RocketMQ方案：
1. 使用**同步发送 / 异步发送+回调**，不使用oneway单向发送（oneway不等待响应，丢失风险高，订单业务禁用）。
2. 发送失败开启重试机制；
3. 业务侧保存本地消息表，记录待发送消息，发送成功标记状态；发送失败定时任务重新投递。

#### ②Broker服务端：消息收到还没落盘，Broker宕机丢失

1. 设置刷盘策略：**SYNC_FLUSH同步刷盘**，消息写入磁盘才返回成功（性能下降，重要业务使用；普通业务用ASYNC_FLUSH异步刷盘）。
2. 开启主从复制，消息同步到从节点，主节点宕机从节点接管，避免单节点丢失。

#### ③消费者端：消息还没处理完，消费者宕机，消息丢失

问题：业务还没执行完，就提交offset，offset提交之后Broker认为消息已经消费完成，消息丢失。
✅解决：**先执行业务逻辑，业务处理成功之后，再手动提交offset**；不要自动提交offset。
如果业务异常，不提交offset，消息会重新投递。

> 完整生产级方案：**本地消息表 + 同步/异步发送 + Broker主从 + 手动提交offset**。
> 面试一句话：消息丢失要分段看，生产者、Broker、消费者每一段都要做保障，没有单一配置可以完全杜绝丢失。

#### 补充区分：RocketMQ事务消息，是解决「本地数据库事务和发送消息原子性」，不是单纯防止消息丢失。

### 3. MQ重复消费，订单业务如何做幂等？

#### 为什么会重复消费

1. Broker没有收到消费者offset提交，消息重新投递；
2. 网络超时，生产者重试发送；
3. 主从切换，部分消息重复推送。
> MQ设计保证**至少一次投递（At‑least‑once）**，不保证绝对不重复，业务必须实现幂等。

#### 订单场景幂等实现方案

1. **业务唯一流水号（最常用）**
每条消息携带唯一业务ID，例如orderId、payNo；消费开始先查询Redis/数据库，判断该ID是否已经处理成功；已处理直接跳过；未处理执行业务，处理完成标记已处理。
- 可以用Redis：key=orderId，value=处理状态；
- 也可以数据库建一张处理记录表，唯一索引。

2. **订单状态机校验（订单业务特有）**
执行业务前校验订单当前状态。
例：支付成功消息，只有订单状态=待支付，才执行更新订单、扣库存；如果已经是已支付，直接跳过。依靠状态流转防止重复执行。

3. **数据库唯一索引兜底**
执行更新、插入时利用唯一索引，重复插入直接报错，捕获异常忽略。

> ❌不推荐：先select再update不加锁，并发情况下会出现重复执行。

> 面试总结：MQ本身无法避免重复消费，业务层必须做幂等；订单优先使用「orderId状态机校验 + Redis标记」。

### 4. 订单超时关闭，用延时消息实现，RocketMQ延时消息优缺点，有什么局限？

RocketMQ延时消息：消息发送时指定延时等级，消息不会立刻投递，到达时间后才投递给消费者。

✅优点
1. 相比定时任务轮库，不用频繁扫描数据库，减少DB压力；
2. 时间相对精准；业务解耦。

❌缺点&局限（面试重点）
1. **不支持任意自定义时间，只支持固定延时等级**，例如1s 5s 10s … 30min、1h；不能比如27分30秒这种自定义时间。订单超时30分钟刚好匹配等级，够用；如果业务需要25分钟就不灵活。
2. **延时消息存储在Broker内部SCHEDULE_TOPIC，Broker重启，未到期延时消息会丢失（老版本）**；新版本有优化，但依然有风险。
3. **消息丢失风险**：延时消息丢失，订单永远不会关闭，库存不会释放。
4. 消息堆积，延时消息到期会出现集中消费压力。

✅生产最佳实践：
**延时消息为主，数据库定时任务兜底扫描**。即使延时消息丢了，定时任务扫描超时待支付订单，完成关闭。

> 对比：如果要支持任意时间延时，可以用Redis ZSet延时队列。

### 5. 下单同步扣库存 vs MQ异步扣库存，两种方案优缺点，适用场景

> 注意：这里说的扣库存是扣MySQL真实库存，不是Redis预扣。

#### 方案1：同步扣库存

下单主流程事务中，直接调用库存服务同步扣DB库存。
✅优点：实时性强，下单就扣掉数据库库存，一致性强。
❌缺点：
1. 下单链路变长，依赖库存服务；库存服务抖动、超时会直接导致下单失败；
2. 高并发场景大量RPC调用，数据库锁竞争，性能差；
3. 容易产生大事务。

适用场景：普通中小流量业务，对库存实时一致性要求高，并发量不大。

#### 方案2：MQ异步扣库存

下单成功，返回用户下单成功；发送MQ消息，消费端异步扣数据库真实库存。
✅优点：
1. 下单主链路短，响应快；不阻塞用户；
2. 削峰，消费端可控消费速度，保护库存数据库。
❌缺点：
1. 最终一致性，下单成功后有可能库存不足，消费扣减失败，订单需要回滚关闭；用户下单成功但是后续告知无货，业务体验差。
2. 需要处理扣减失败的补偿逻辑。

适用场景：**秒杀大促场景**，流量巨大，优先保证下单接口吞吐量。

> ⚠️电商普通订单生产主流做法：
> Redis预扣库存（同步拦截），**支付成功之后同步扣DB真实库存**；
> 秒杀场景才会使用MQ异步扣DB库存。

> 面试话术：普通电商订单不用MQ异步扣库存；秒杀大促才会使用，同时要做好扣减失败的补偿，通知用户取消订单。

### 6. 支付回调，用MQ解耦，流程是什么？

> 背景：第三方支付平台调用我方回调接口。回调接口有严格超时时间限制（一般几十ms）。
> 如果回调接口里面做更新订单、扣库存、发通知、记录日志一堆逻辑，处理慢，会导致第三方重复回调。

#### 使用MQ解耦完整流程

1. 第三方支付平台发起HTTP回调请求到我方回调接口；
2. **回调接口只做简单校验：验签、参数合法性校验**；
3. 参数校验通过，把支付消息发送RocketMQ；立刻返回success给支付平台；
4. MQ消费端异步执行业务逻辑：
    - 根据orderId查询订单，状态机校验；
    - 更新订单状态为已支付；
    - 扣减数据库真实库存；
    - 生成发货任务；
    - 发送支付成功短信通知；
5. MQ消费做好幂等，处理第三方重复回调。

#### 好处

1. HTTP回调接口处理极快，避免超时；
2. 业务逻辑异步，回调和业务解耦；
3. 重复回调转化为MQ重复消费，消费端做幂等即可。

> 关键点：回调接口**不要写重业务逻辑**，只做验签投递消息。

### 7. MQ消息积压，如果订单大量消息堆积如何排查处理？

消息堆积：Broker内部消息大量没有被消费，消息持续增加，消费进度不上涨。

#### 排查步骤

1. 查看Broker监控：查看topic的消息堆积数量、消费offset、生产速率、消费速率。
2. 判断消费端是否完全不消费，还是消费速度跟不上生产速度。
3. 定位原因：
    - 消费逻辑执行慢，数据库/IO慢，消费能力不足；
    - 消费抛出异常，不断重试，消费卡死；
    - 消费者组配置错误，没有消费者；
    - 消息量突增，消费实例数量不够。

#### 处理手段（生产实操）

1. **临时紧急扩容**
增加消费者实例，提高消费并行度；注意RocketMQ：并行度受topic队列数量限制，消费者数量不能大于队列数；队列不够先扩容队列。
2. 优化消费业务逻辑，减少DB慢查询，把非核心逻辑继续异步拆分。
3. 如果消息可以丢弃（订单消息不能丢）；订单业务不能丢弃，只能加速消费。
4. 积压特别严重，大量旧消息：
新建一个消费者组，把积压消息迁移到新实例消费；旧业务实例恢复对外处理新消息。
5. 定位根因修复bug，防止再次积压。

#### 订单业务特别注意

订单相关消息不能丢弃，不能直接重置offset跳过，否则会出现订单状态不更新、库存不扣、通知丢失等严重业务bug。

> 面试话术：先看监控确认堆积规模，看消费速率；优先扩容消费者提升消费能力；优化消费逻辑；订单消息严禁直接跳过。

> 秋招20k核心分水岭，订单跨服务场景：订单服务、库存服务、优惠券服务、积分服务，多服务数据库独立，本地Spring事务失效，需要分布式事务方案。

### 1. 分布式事务：下单、扣库存、扣优惠券、扣积分，多服务如何保证数据一致性？

#### 业务背景

用户下单，一次业务需要操作多个微服务：
1. 订单服务：创建订单（order库）
2. 库存服务：扣减库存（stock库）
3. 优惠券服务：扣优惠券，标记优惠券已使用（coupon库）
4. 积分服务：扣/发放积分（point库）

每个服务独立数据库，**Spring @Transactional本地事务只能管自己库，无法跨服务回滚**。
理想情况：全部成功，或者全部回滚；但是分布式网络不可靠，会出现部分成功部分失败。

#### 业务现实

电商订单**几乎不会追求强一致性**，选择**最终一致性**，允许短暂数据不一致，通过补偿机制最终达成一致。

#### 整体处理思路

1. 前置校验：下单前预先校验库存、优惠券、积分是否合法，提前拦截大部分失败。
2. 执行预扣：Redis预扣库存、预标记优惠券占用，不要直接真实扣DB。
3. 创建订单落库。
4. 通过分布式事务方案协调各个服务；
5. 如果部分服务失败，执行回滚/补偿；
6. 定时任务做兜底对账，修正不一致数据。

> 重点：下单阶段做**预占**，支付成功之后才做真实扣减；支付失败统一释放全部预占资源。

### 2. 2PC、TCC、SAGA、本地消息表、事务消息，在电商订单场景选型对比，各自优缺点

#### 1）2PC（两阶段提交）

- 阶段一：所有参与者准备；阶段二：协调者通知全部提交 / 全部回滚。
✅优点：强一致性。
❌缺点：协调者单点；长时间锁住资源，性能差；网络抖动会阻塞；**不适合高并发电商订单**。
> 电商几乎不用，多用于数据库内部。

#### 2）TCC Try‑Confirm‑Cancel

- Try：预占资源（预扣库存、冻结优惠券）
- Confirm：确认执行真实扣减（支付成功后执行）
- Cancel：取消，释放冻结资源（支付失败/超时关闭）

✅优点：最终一致性；性能较好；业务高度可控。
❌缺点：**业务侵入极强，每个服务要手写三套代码Try/Confirm/Cancel，开发成本高；要处理空回滚、幂等、悬挂问题**。
适用：资金、优惠券这类对一致性要求高的场景。
> 订单场景：优惠券、积分冻结经常用TCC。

#### 3）SAGA模式

把大事务拆成一串本地小事务；每一个本地事务有对应的补偿回滚逻辑。
如果某一步失败，反向依次执行前面步骤的补偿。
分为编排式（中心调度器）、编排式（服务之间互相调用）。

✅优点：没有资源锁，性能高；相比TCC，不需要预占Try阶段。
❌缺点：没有隔离性；补偿逻辑开发复杂；无法回滚已经提交的本地事务；容易出现数据不一致，需要兜底对账。
适用：长流程业务，订单履约、退款流程。

#### 4）本地消息表（可靠消息）

业务库新建一张消息表；业务操作和写消息在同一个本地事务；定时任务扫描消息表发送MQ；消费端执行业务；失败不断重试。

✅优点：实现简单，不依赖中间件特殊特性；可靠。
❌缺点：需要维护消息表；定时轮询有延迟。
适用：通知、积分发放、短信等场景。

#### 5）RocketMQ事务消息

本质是本地消息表的MQ封装，半消息机制。
✅优点：不需要自己维护消息表；代码简洁。
❌缺点：有回查机制，有局限；不适合长流程。

---

#### 电商订单场景选型总结（面试必背）

1. **下单冻结优惠券、积分：优先TCC**，资源需要预冻结，防止超用。
2. **下单后发通知、积分发放：RocketMQ事务消息 / 本地消息表**。
3. **订单履约、退款长流程：SAGA**。
4. **2PC基本不使用，性能太差，不适合互联网高并发**。

> 面试一句话：互联网电商基本不用强一致2PC；以TCC、SAGA、可靠消息实现最终一致性，外加定时对账兜底。

### 3. 什么场景用RocketMQ事务消息？下单场景适合吗？局限是什么？

#### RocketMQ事务消息原理

1. 发送半消息（Half Message），消息对消费者不可见；
2. 执行本地数据库事务；
3. 提交/回查：提交则消息可见；回滚消息直接丢弃；
4. 如果Broker收不到提交/回滚指令，Broker会回调生产者执行事务回查，查询本地事务执行状态，再决定提交还是回滚。

#### ✅适合场景

**本地DB事务 和 发送MQ消息需要原子性**。
例：订单创建成功，必须发送一条订单创建MQ；如果订单数据库插入失败，这条消息就不允许投递给消费者。

> 例子：创建订单（本地事务）和发送积分通知MQ，适合事务消息。

#### ❌不适合完整下单分布式事务

**不适合跨多个微服务的分布式事务（订单、库存、优惠券跨服务）**。
> 事务消息只能保证：**自己本地库事务 和 MQ发送的原子性**，不能直接帮你远程调用库存、优惠券服务做回滚。

#### 局限

1. 只能管控生产者本地事务，不能管理远程服务；
2. 回查有次数限制，回查全部失败消息会丢弃；
3. 回查要求生产者服务必须存活；
4. 没有隔离性，消息提交后消费者就可以消费。

> 面试话术：RocketMQ事务消息解决「本地事务与发消息原子性」，**不能直接解决跨服务分布式事务**；下单创建订单后发送事件消息适合；不能用它去协调库存、优惠券多个远程服务。

### 4. 分布式环境下，如何保证下单接口幂等？token方案、唯一业务流水号

分布式环境：前端、网关、RPC调用、MQ消费都可能重试，会产生重复请求。

#### 方案1：下单Token方案（前端页面调用）

流程：
1. 前端进入下单页，向订单服务申请一个唯一下单Token，存入Redis。
2. 用户提交下单请求时携带这个Token。
3. 服务端Lua脚本校验并删除Token；如果token不存在直接拒绝下单。
> 原子校验删除，防止并发下重复使用同一个token。

✅优点：拦截用户重复点击按钮，拦截前端重复提交。
❌缺点：只适合前端入口；不适合RPC调用、MQ消费场景。

#### 方案2：外部唯一业务流水号 requestId（通用全场景）

调用方生成全局唯一requestId；每次请求携带；
服务端：
1. 执行业务前先查询Redis/数据库，判断requestId是否已经处理成功。
2. 如果已处理，直接返回上次成功结果；
3. 如果未处理，执行业务逻辑；处理完成标记该requestId已处理。

可以存Redis，也可以建一张业务处理记录表，给requestId加唯一索引。
✅优点：**前端、RPC、MQ消费全部通用**。

##### 订单业务额外兜底：状态机校验

执行业务前校验订单状态，非法状态直接返回。
例：执行创建订单只允许未创建；支付处理只允许待支付订单。

> 注意：不能单纯依赖select判断，并发会有问题；Redis Lua /数据库唯一索引保证原子判断。

### 5. 服务调用超时：调用库存服务超时，订单状态该怎么处理？是成功还是失败？

场景：订单服务调用远程库存服务扣预占库存，RPC超时。
> RPC超时**不等于业务执行失败**，有三种可能性：
1. 请求没到达库存服务，库存没执行；
2. 请求到达库存，库存执行成功，网络返回超时；
3. 请求到达库存，库存执行失败，返回报文丢了。

**所以超时不能直接判定失败，不能直接把订单置为失败。**

#### 处理流程

1. 当前订单设置为**中间状态：处理中**，不要直接置成功/失败。
2. 通过TCC回查 / MQ回查 / 定时补偿任务，查询库存服务真实执行结果。
    - 如果库存预占成功：订单流转到待支付，继续走正常流程。
    - 如果库存预占失败：关闭订单，释放资源，返回下单失败。
3. 增加定时任务扫描长时间处于中间状态的订单，做状态核对。

> ❌错误做法：超时直接返回下单失败。如果库存已经预占成功，订单标记失败，库存资源被冻结无法释放，出现资源泄露。

> 面试一句话：RPC调用超时属于状态未知，不能直接判定成功或失败；设置中间状态，通过回查确认远端真实结果，再推进订单状态。

### 6. 最终一致性和强一致性在订单业务如何取舍？

#### 强一致性

所有参与服务同时成功或者同时失败，任何时刻所有节点数据完全一致；2PC属于强一致。
代价：锁资源、性能差、容易阻塞，高并发场景吞吐量低。

#### 最终一致性

允许短暂时间内数据不一致，经过一段时间，通过补偿、重试、对账，最终数据达成一致；TCC、SAGA、可靠消息都是最终一致性。

#### 电商订单业务取舍

1. **绝大部分业务场景选择最终一致性**
下单、扣库存、发积分、发短信，接受短暂不一致，追求高并发高性能。
> 例如：下单优惠券扣减短暂不一致，定时对账可以修复。

2. **什么场景要尽量接近强一致**
涉及资金、支付退款，资金不能出错，需要TCC冻结资源，尽量保证隔离性，同时还要兜底对账。

3. 为什么订单不用强一致？
电商大促流量大，强一致性方案会锁住资源，吞吐量下降，出现大量请求阻塞，无法承接大流量。

> 业务设计原则：
> 1. 能预占就预占，把冲突提前拦截；
> 2. 业务上接受短暂不一致；
> 3. 所有最终一致性方案，**必须配套定时对账兜底**，不能只靠分布式事务框架。

> 面试话术：互联网电商订单几乎不用强一致性；优先最终一致性，预占资源+补偿+对账兜底；只有资金相关业务提高隔离等级。

### 1. 秒杀下单场景，和普通订单有什么区别？秒杀完整架构链路

#### 秒杀和普通订单核心区别

1. **流量特征**：秒杀瞬间大流量，流量陡增，大量请求同一时间打同一个商品；普通订单流量平缓。
2. **热点冲突**：大量请求竞争同一个商品库存，数据库行锁冲突严重；普通订单商品分散，冲突小。
3. **读多写极多**：大量用户抢同一个有限库存，大部分请求都是无效抢不到；普通订单大部分请求都可以下单成功。
4. **资源竞争**：库存是最大瓶颈；普通订单瓶颈在订单写入。
5. 用户体验：秒杀大量请求直接返回“已抢完”；普通订单大多可以正常生成订单。

> 核心矛盾：**大量无效请求，不能全部透传到数据库层，必须在上层拦截过滤**。

#### 秒杀完整架构链路（从上到下）

1. **前端层**
按钮置灰、防重复提交；页面静态化；cdn缓存商品页面；减少重复点击。
2. **网关层**
网关限流、黑名单，拦截非法请求；限流熔断。
3. **应用前置过滤**
本地限流、分布式限流；校验商品是否开始、是否已经售罄。
4. **Redis层核心拦截**
预扣Redis库存，Lua脚本原子扣减；库存不足直接返回抢购失败。
> 绝大部分请求在这里直接失败，不会往下走。
5. **消息队列削峰**
Redis预扣成功的请求投递MQ，排队消费；不再同步生成订单。
6. **消费端消费MQ消息**
订单服务消费消息，创建订单落库；扣DB真实库存；生成支付单。
7. **兜底补偿**
延时消息处理超时未支付订单，释放Redis库存；定时对账Redis与DB库存。

> 一句话总结：**前端+网关过滤，Redis挡绝大部分流量，MQ削峰，数据库只处理真正抢到的少量请求。**

### 2. 下单接口如何限流？网关限流、本地限流、分布式限流；哪些位置做限流

限流目的：保护下游服务、数据库，防止大流量把系统打挂；拒绝多余流量，保证大部分正常请求可用。

#### 三层限流位置

##### 1）网关层限流（Nginx/Spring Cloud Gateway）

最外层第一道屏障，流量入口。
- 实现：网关限流，令牌桶、漏桶算法；按IP、用户ID、总QPS限流。
- 作用：拦截恶意请求，阻挡大流量，不让无效流量进入后端应用。
> 越早限流，消耗资源越少。

##### 2）应用本地限流（Sentinel，单机）

单机内存令牌桶，只对当前实例生效。
- 优点：速度快，不依赖中间件。
- 缺点：集群多实例情况下，总限流值 = 单机阈值 × 实例数；实例扩缩容阈值会变化。

##### 3）分布式限流（Redis + Lua / Sentinel集群模式）

全集群统一计数，所有实例共享同一个限流计数器。
- 适合：按用户维度限流，比如单个用户每秒只能下1单；全系统总QPS管控。
- 缺点：有Redis网络开销。

#### 下单接口限流策略

1. **网关：全量限流，防爬虫、防恶意刷接口。**
2. **应用层Sentinel本地限流：限制下单接口总QPS，保护订单服务。**
3. **分布式限流：限制同一个用户短时间重复下单，防止单用户疯狂刷。**

> 面试重点：限流分层，网关做第一层，应用本地限流做第二层，分布式限流做用户维度管控；不要只靠某一层。

> 注意：限流返回友好提示“访问过于频繁，请稍后重试”，不是直接抛异常。

### 3. 如何削峰填谷，高并发下单保护数据库？

削峰填谷：瞬时尖峰流量，转化成平缓的流量，避免瞬间大量写请求压垮数据库。

#### 手段

1. **Redis前置拦截**
绝大多数抢不到的请求直接在Redis返回，根本不访问数据库。

2. **MQ消息队列削峰（秒杀场景）**
预扣库存成功后，不同步写库，把请求丢进MQ；消费端以数据库可承受的速度消费消息，平缓写入订单。
> 尖峰流量变为队列的堆积，消费端匀速消费，数据库压力平稳。

⚠️注意：普通电商订单不建议用MQ异步下单，会出现下单成功但是库存扣减失败，用户体验差；**主要用于秒杀场景**。

3. **服务层限流熔断**
超过阈值直接拒绝请求，保护下游DB。

4. **分库分表**
订单分库分表，把写入压力分散到多个数据库实例，分散写压力。

5. **预过滤无效请求**
前端按钮控制、网关过滤，减少无效请求到达后端。

> 面试话术：Redis过滤无效请求，MQ做流量削峰，限流拒绝超额流量，分库分表分散压力，多手段共同保护数据库。

### 4. 下单接口优化，从网关、应用、缓存、数据库各个层面可以做哪些优化？

#### 网关层

1. 参数校验，非法参数直接拦截；
2. 网关限流、熔断；黑名单拦截恶意IP；
3. 请求协议优化，拒绝重复请求；
4. 静态页面走CDN，减少后端请求。

#### 应用服务层

1. 接口做幂等，防止重复请求产生脏数据；
2. 业务逻辑尽量同步链路变短，非核心逻辑异步交给MQ（短信、通知、积分）；
3. 使用Sentinel限流熔断，下游库存、优惠券服务超时熔断降级；
4. 避免大事务；事务尽量小，事务内部不要放RPC、网络IO；
5. 线程池隔离，下单接口独立线程池，避免被其他接口拖垮。

#### 缓存Redis层

1. 库存使用Redis预扣，拦截大部分请求；热点key禁止设置过期时间，防止缓存击穿；
2. 热点商品信息缓存，减少DB查询；
3. 使用Lua脚本保证原子操作；
4. 避免大key；合理设置缓存过期策略。

#### 数据库层

1. 合理设计索引，避免慢SQL；禁止大select；
2. 订单分库分表，分散读写压力；
3. 冷热数据分离归档，热表维持较小数据量；
4. 读写分离：查询走从库，写入走主库；
5. 避免行锁冲突：Redis拦截大部分并发，DB只做兜底；
6. 控制事务大小，杜绝大事务；
7. 禁止数据库层面做复杂计算，计算放到应用层。

> 总结：能在上层拦截就不上下层；能异步就不同步；事务尽量小；减少DB压力。

### 5. 大促的时候，订单系统会遇到哪些瓶颈？怎么应对？

#### 瓶颈1：流量突增，下单接口QPS暴涨

现象：CPU打满、线程池打满，接口超时。
对策：网关限流、应用限流；Redis拦截无效流量；非核心逻辑异步；扩容应用实例。

#### 瓶颈2：数据库写入压力大，行锁冲突、TPS上不去

现象：大量并发更新库存，行锁等待，数据库慢、超时。
对策：Redis预扣库存，减少DB压力；分库分表；读写分离；避免大事务；秒杀引入MQ削峰。

#### 瓶颈3：Redis热点key问题，大促热门商品，大量请求打同一个key

现象：RedisCPU飙升，单实例压力大。
对策：热点key拆分；永不过期；网关层限流；本地缓存做一层兜底。

#### 瓶颈4：MQ消息堆积

现象：生产速度大于消费速度，消息越积越多，订单处理延迟。
对策：扩容消费者；提升消费速度；业务逻辑继续拆分异步；扩容topic队列数量。

#### 瓶颈5：依赖服务抖动（库存、优惠券、支付）

现象：下游超时，导致下单大量失败。
对策：Sentinel熔断降级；前置校验；预占资源；超时设置中间状态，事后回查，不直接失败。

#### 瓶颈6：分库分表后的查询压力

商家后台大量复杂查询，查询业务库拖慢主库。
对策：数据同步ES，后台查询走ES；报表走数仓。

#### 瓶颈7：大促大量超时未支付订单，关闭订单压力大

对策：延时消息+定时兜底；定时任务分片执行，避免一次性扫库。

### 6. 流量削峰，为什么不能全部请求直接打到数据库？

1. **数据库性能上限有限**
MySQL单机TPS是有限的，几千TPS就算很高；瞬时上万、几十万QPS过来，数据库扛不住。大量并发写会导致锁等待、锁冲突、慢查询，CPU、IO飙升，数据库雪崩。

2. **大量请求是无效请求**
秒杀场景90%以上请求都是抢不到库存的，如果全部打到数据库，大量请求做无用的数据库查询、行锁竞争，严重消耗数据库资源，把真正能下单的正常请求也拖垮。

3. **行锁冲突严重**
大量请求争抢同一个商品库存，DB行锁排队，大量线程阻塞，连接池耗尽，大量超时。

4. **数据库故障影响面极大**
数据库一旦被打挂，整个订单业务不可用，恢复成本很高。

> 核心思想：数据库是整个链路最薄弱的一环，尽量把过滤、拦截工作放在网关、应用、Redis层，**只有真正有机会下单成功的请求，才允许到达数据库**。

> 面试官重点深挖业务故障，考察真实业务落地经验，不是背诵理论，重点讲现象、业务影响、处理方案、兜底。

### 1. 下单成功，数据库订单写入成功，但是Redis扣库存失败，怎么办？

#### 场景还原

下单流程：校验→Redis预扣库存；**Redis网络抖动/宕机，预扣失败**，但是后续流程异常，订单依然成功入库，订单状态=待支付。
> DB订单已经生成，Redis库存没有扣减。

#### 业务问题

Redis库存比真实可售库存偏大。后续用户继续下单，Redis显示有库存，大量请求放行，走到DB才发现库存不足，出现大量下单失败；严重情况下发生**超卖**。

#### 解决方案

1. **实时阶段**
Redis预扣失败时，业务要捕获异常，直接回滚数据库订单，不生成订单。
> 理想情况：Redis预扣是前置，预扣失败就不往下创建订单。

2. 如果已经发生异常，订单落库但Redis没扣：
① **Canal监听DB库存/订单变更，同步更新Redis库存**；订单创建成功，主动更新Redis预扣计数。
② **定时对账任务兜底**：比对DB真实库存、Redis预扣库存、待支付订单占用库存。
计算公式：
`DB可售库存 = Redis可售库存 + 待支付订单占用库存`
发现不一致，以数据库为准，修复Redis。

> 面试重点：Redis只是预扣层，数据源是MySQL；不能完全信任Redis，必须有对账兜底。

### 2. 用户下单成功，支付完成，但是扣库存失败，会出现什么业务问题？怎么兜底？

#### 场景

用户已经支付成功，订单状态更新为已支付；但是扣MySQL真实库存这一步异常（服务宕机、数据库异常），库存没有扣减。

#### 业务后果

1. 用户钱已经扣了，订单显示已支付，但是商品库存没有减少；
2. 商品可以继续被其他人下单购买，**严重超卖，多发货、库存错乱**；
3. 财务对账不平，订单已付款，库存未扣，产生脏数据。

#### 分层处理

1. **业务流程内即时处理**
支付回调消费逻辑中，更新订单状态和扣真实库存放在**同一个本地事务**。只要事务提交成功，订单和库存同时落库；扣库存失败，事务回滚，订单不会变成已支付。

2. 如果已经出现：订单已支付，库存未扣（极端宕机导致事务部分提交）
① **对账任务**：扫描状态为已支付，但是库存扣减记录不存在的订单，执行补扣库存。
② 建立库存变更流水表，每一次扣库存都落流水；对账对比订单和库存流水。
③ 告警：检测到异常订单直接告警通知运维开发，人工介入。

> 兜底思路：订单状态 + 库存流水做核对；已支付必须有对应的库存扣减记录，没有就要补扣。

### 3. 支付回调重复回调，订单怎么处理？

第三方支付平台，网络问题会多次推送同一个支付结果回调。如果不处理，会重复执行业务：重复扣库存、重复发积分、重复发货。

#### 处理流程

1. HTTP回调接口只做验签，校验参数合法，投递MQ，立刻返回success给支付平台；业务全部交给MQ消费。
2. MQ消费端做幂等，两个手段：
- **订单状态机优先校验**：如果订单不是【待支付】，直接结束，不做任何处理。
> 订单已经是已支付/已取消，直接跳过，这是订单业务最核心的防护。
- 使用支付流水号payNo做幂等标记，Redis或者数据库唯一索引，保证同一笔支付只处理一次。

3. 幂等必须做到：重复消费不会产生副作用，也不能报错，正常返回成功。

> 一句话：回调不处理业务，只投递MQ；消费端靠订单状态机+支付流水号实现幂等。

### 4. 订单状态机，状态流转异常，比如已支付订单又被关闭，如何防止？

订单状态举例：待支付 → 已支付 → 已发货 → 已完成；待支付 → 已取消。

故障场景：
两个并发线程，①支付回调线程；②超时关闭订单延时消息线程。
- 线程A：支付回调，准备把待支付改为已支付；
- 线程B：延时消息，准备把待支付改为已取消；
并发情况下，如果不加控制，极端会出现：订单已经支付成功，又被关闭。

#### 根因

多线程并发修改同一订单，没有做状态前置校验。

✅解决方案
1. **数据库更新时带上状态条件（状态机原子校验）**
```sql
-- 关闭订单：只有当前是待支付才允许关闭
update order_main set status='CLOSED' where id=#{orderId} and status='WAIT_PAY';
```
> 返回影响行数，等于1代表关闭成功；0代表状态不符合，不执行。

支付更新同理：
```sql
update order_main set status='PAID' where id=#{orderId} and status='WAIT_PAY';
```
> 依靠数据库行锁 + where条件，实现原子状态流转。只有符合前置状态，才允许流转。

2. 业务层不允许跨状态流转。例如已支付、已发货订单，不允许执行关闭订单逻辑。
3. 状态流转全部定义有限的状态图，不允许随意修改状态。
4. 监控告警：出现非法状态流转直接告警。

> 核心：不要先select查询判断状态再更新，并发下会有漏洞；**update语句where条件带上原始状态，数据库层面原子判断**。

### 5. 网络抖动、服务宕机，订单会出现哪些中间状态，如何做补偿？

#### 常见中间状态（状态未知）

1. **下单中**：调用库存/优惠券RPC超时，订单处于中间态，不知道远端服务成功还是失败。
2. **支付处理中**：收到支付回调，处理过程服务宕机，订单部分更新。
3. **关闭订单处理中**：延时消息消费一半宕机，订单没关闭，库存没有释放。
4. **扣库存处理中**：支付成功，扣真实库存时宕机，订单已支付库存未扣。

> 关键：遇到RPC调用超时、服务宕机，**不要直接把订单置成功或者失败，设置中间状态**。

#### 补偿方案

1. **回查机制**
对于RPC调用超时，不猜结果，主动调用远端服务查询真实结果，根据结果推进订单状态。

2. **MQ重试**
业务消费异常，抛出异常，MQ自动重试；做好幂等。

3. **定时补偿任务扫描中间状态订单**
扫描长时间停留在中间状态的订单（比如超过15分钟），回查依赖服务状态，完成状态推进或者回滚资源。

4. **资源一定要可回滚**
预占的库存、优惠券，中间状态下定时任务可以做释放。

> 面试话术：网络和宕机会造成大量状态未知的中间订单；不能凭超时就判定成功/失败；通过回查+定时任务扫描中间态订单做补偿。

### 6. 补偿机制：定时任务扫描异常订单做对账，对账怎么做？

对账核心：以数据源为准，比对多方数据，修复不一致，同时告警。

#### 1）订单‑库存对账

参与方：订单表、库存表、库存流水表、Redis。
核对逻辑：
1. 已支付订单，必须存在对应的库存扣减流水，没有则补扣库存。
2. 已取消/已退款订单，库存要已经回补。
3. 待支付订单：统计所有待支付订单占用库存，和Redis预扣库存对比，修复Redis。

#### 2）订单‑优惠券对账

已使用订单，优惠券状态必须为已使用；已取消订单，优惠券要恢复可用。

#### 3）订单‑支付对账

订单状态为已支付，必须存在支付流水；支付成功但订单未支付，修复订单。

#### 定时任务实现要点

1. **分片扫描，不要全表扫**：按id或者时间分片，分批查询，避免锁库、拖慢数据库。
2. **控制频率**：不要几秒跑一次，一般分钟级。
3. **加锁**：分布式锁，防止多实例同时执行对账任务，重复处理。
4. **区分修复与告警**：部分异常无法自动修复，只告警，人工介入。
5. **记录对账日志**：记录哪些订单异常，做了什么修复，方便排查。

> 重要：**定时对账是最终一致性的最后一道防线，任何分布式业务都不能省略，不能只依赖MQ、TCC**。

### 7. 什么是订单脏数据，如何发现和修复？

#### 什么是订单脏数据

业务规则矛盾、状态不一致的数据，由网络抖动、宕机、程序bug、重试重复执行产生。
典型脏数据举例：
1. 订单状态已支付，但是没有支付流水，库存没有扣减；
2. 订单已取消，但是优惠券已经扣掉没有归还；
3. 待支付订单，库存已经真实扣减；
4. 同一个orderId生成多条订单记录；
5. 状态非法，出现状态机不存在的值。

#### 如何发现脏数据

1. **定时对账任务检测**，比对订单、库存、支付、优惠券数据，发现逻辑矛盾。
2. **业务监控告警**：监控异常状态订单数量，一旦大于0触发告警。
3. **日志埋点**：捕获非法状态流转，输出异常日志告警。
4. 报表对账，财务层面核对订单金额、支付金额。

#### 修复脏数据

1. **能自动修复的自动修复**：例如订单已取消但优惠券未释放，定时任务执行回补。
2. **无法自动修复的，人工介入**：涉及资金，不能程序盲目自动修复，走人工工单，核对业务上下文后修正。
3. **修复记录日志**：每一条脏数据修复都保存记录，便于审计，不能直接偷偷update。
4. 定位产生脏数据的程序bug，修复代码防止持续生成脏数据。

> 面试话术：脏数据不可完全避免，分布式系统重点是尽早发现；能自动修复就修复，涉及资金类脏数据优先告警人工处理。

### 1. 设计一个电商订单系统，说出整体架构、核心服务、存储选型

#### 整体架构（微服务拆分）

采用微服务架构，各服务独立数据库，通过RPC、RocketMQ通信；网关统一入口。

#### 核心服务

1. **订单服务 order‑service**
负责创建订单、订单状态流转、查询订单、关闭订单、订单CRUD；核心表：order_main订单主表、order_item订单明细表、order_pay支付流水、order_log订单状态变更日志。
2. **库存服务 stock‑service**
库存查询、预扣库存、真实扣减库存、回补库存；stock主表、stock_log库存流水。
3. **优惠券服务 coupon‑service**
优惠券冻结、核销、退回优惠券。
4. **支付服务 pay‑service**
对接第三方支付，生成支付单，接收支付回调。
5. **用户服务 user‑service**
用户信息、积分处理。
6. **搜索/ES服务**
订单数据同步ES，商家后台、用户订单列表查询走ES，不查业务主库。

#### 中间件选型

- 网关：Spring Cloud Gateway
- RPC：Feign/Dubbo
- MQ：RocketMQ（事件、延时、事务消息）
- 缓存：Redis（库存预扣、分布式锁、限流、热点数据）
- 限流熔断：Sentinel
- 定时任务：XXL‑Job（对账、归档、异常订单扫描）

#### 存储选型

1. MySQL：业务主存储。订单做**分库分表**，按用户ID哈希分片；冷热分离。
2. Redis：库存预扣、分布式限流、分布式锁、短周期订单缓存。
3. ElasticSearch：订单查询，商家后台复杂条件检索。
4. 数仓Hive：历史订单统计、报表，不在线业务查询。

#### 保障机制

- 分布式一致性：TCC / SAGA / RocketMQ事务消息，最终一致性；
- 兜底：XXL‑Job定时对账任务，补偿异常订单；
- 监控：状态异常告警、MQ堆积告警、数据库慢SQL告警。

> 口述总结：订单系统核心是**服务拆分、分库分表、ES承担查询压力、全链路补偿对账**。

### 2. 设计订单超时自动关闭功能，给出3种方案，对比优缺点，给出选型

需求：订单待支付30分钟未付款，自动关闭订单，回滚库存、退回优惠券。

#### 方案1：定时任务轮询数据库（XXL‑Job）

逻辑：定时任务，每隔一段时间扫描数据库，查询`status=待支付 AND 创建时间 < 当前时间‑30min`的订单，批量关闭。
✅优点：实现简单，不依赖MQ；可靠性高，不会丢任务。
❌缺点：
1. 如果订单量巨大，全表扫描压力大；
2. 时间不精准，任务多久跑一次，就有多大延迟；
3. 分片、分页查询，要避免全表扫描；任务压力随订单量上涨。

#### 方案2：RocketMQ延时消息

下单成功发送30min延时消息；到期消费消息，执行关闭订单逻辑。
✅优点：触发时间相对精准；业务解耦，不频繁扫库。
❌缺点：
1. 只有固定延时等级，不能任意时间；
2. Broker故障存在消息丢失风险；消息堆积会延迟关闭；
3. 消息丢失订单永远不会关闭。

#### 方案3：Redis ZSet延时队列

下单把orderId+到期时间戳放入zset；后台线程轮询zset，取出到期订单执行关闭。
✅优点：支持任意自定义延时时间。
❌缺点：需要自己实现轮询逻辑；Redis宕机丢失数据；要做持久化；业务侵入大。

#### 选型（生产最佳实践）

**RocketMQ延时消息为主，定时任务轮库做兜底。**
> 延时消息保证大部分订单及时关闭；定时任务兜底处理消息丢失的极端情况。
> 不单独依赖任意一种方案。

### 3. 如何设计防超卖系统，完整方案

> 超卖根源：并发下库存扣减缺少原子；Redis与DB不一致；预占资源没有释放。

#### 完整分层方案（从上到下多层防护）

1. **前端层**
按钮防重复提交；页面显示库存仅做展示，不能作为下单依据。

2. **网关&应用层**
限流，拦截大量并发请求；参数校验。

3. **Redis层预扣（第一层防护）**
使用Lua脚本，**原子完成库存判断+预扣**。
脚本逻辑：判断剩余库存≥购买数量，执行扣减；不足直接返回失败。
> Redis只做预扣，真实数据源是MySQL。

4. **数据库层（最终兜底，绝对不能省略）**
支付成功才扣真实MySQL库存；更新SQL带上库存条件：
```sql
update stock set count = count‑num where id=#{stockId} and count >= #{num};
```
返回影响行数，如果为0，说明DB库存不足，扣减失败。
> 数据库行锁保证原子，这是最后一道防线，就算Redis出问题，数据库也不会超卖。

5. **资源释放机制**
- 用户手动取消订单：释放Redis预扣库存。
- 超时未支付：延时消息+定时任务兜底释放预占库存。释放必须做幂等，不能重复回补。

6. **对账兜底（最重要）**
定时对账任务：
对比DB真实库存、Redis预扣库存、待支付订单占用库存。
`DB可售库存 = Redis可售库存 + 待支付订单占用锁定库存`
发现不一致，以MySQL为准修复Redis，同时告警。

#### 关键总结

- Redis拦截大部分流量，**数据库是最终防超卖兜底**，不能只依赖Redis；
- 预占资源必须有释放逻辑；
- 定时对账修复不一致。

### 4. 大促千万订单，如何设计订单存储，分库分表+冷热归档

#### 问题

千万甚至亿级订单，单库单表：查询慢、写入压力大、索引膨胀。

#### 1）分库分表设计

中间件：Sharding‑JDBC
- **分片键：user_id**，按用户ID哈希分片。
同一个用户所有订单落在同一个分片，用户查询自己订单性能好。
- 水平分库：拆多个库；每个库再水平分表。
> 注意：不能用order_id直接分片；用户查询自己订单最多，user_id更合适。
> 缺点：商家按时间查全平台订单会跨分片，这类查询不走业务库，走ES。

#### 2）冷热分离

- **热数据**：近3个月订单，高频访问，存分库分表MySQL。
- **冷数据**：超过3个月历史订单，访问频率极低。

冷热归档流程：
1. XXL‑Job定时任务，把冷订单迁移到**冷库（独立MySQL实例）**；
2. 迁移完成后删除热库中的冷数据；
3. 用户查询历史订单：优先查热库；查不到再查询冷库；
4. 同时全部订单同步ES，复杂查询走ES。

> 不要把几年的历史订单一直放在业务热库，会导致表越来越大，写入、索引变慢。

#### 3）查询解耦

- 用户查自己订单：路由到对应分片MySQL。
- 商家后台、运营、报表：**禁止直接查询业务分库分表**，查询ElasticSearch；报表同步数仓。

#### 4）其他优化

1. 大表拆分为order_main主表 + order_item明细表；主表存订单核心信息，明细表存商品行。
2. 订单状态变更全部记录order_log日志表，不做物理删除订单，逻辑删除。

> 面试一句话：按user_id做水平分库分表；冷热归档分离历史数据；复杂查询全部下沉ES，保护业务库。

### 5. 设计下单接口，从请求到返回，完整的架构，要考虑并发、幂等、异常

> 手写完整流程，每一步带上异常处理。

#### 整体链路

前端 → 网关Gateway → 订单服务 → Redis → 各微服务（库存、优惠券） → MySQL → MQ

1. **前端**
防重复点击；携带前端token；参数校验。

2. **网关层Gateway**
- 参数合法性校验；黑名单IP拦截；
- 网关限流；非法参数直接拦截。

3. **订单服务接收请求**
① **幂等校验**：携带requestId；或者下单token。Lua校验删除token；重复请求直接返回。
② 参数校验：商品id、数量、地址；校验商品数量不能<=0。
③ Redis Lua脚本预扣库存；库存不足直接返回“库存不足”。
④ 预冻结优惠券（TCC Try）；校验优惠券是否可用。
⑤ **创建订单（本地事务）**：写入order_main、order_item，订单状态=待支付。
⑥ 发送RocketMQ事务消息，订单创建事件，异步做发短信、积分等非核心逻辑。
⑦ 返回前端：下单成功，返回订单号，提示用户去支付。

> ⚠️注意：这里只是预扣Redis，**没有扣MySQL真实库存**；真实扣库存放到支付回调之后执行。

#### 后续异步流程

1. 下单成功发送RocketMQ延时消息（30分钟），用于超时关闭订单。
2. 用户去支付；第三方支付回调过来：
   - http回调只验签，投递MQ立刻返回success；
   - MQ消费端做幂等+状态机校验；
   - 更新订单状态为已支付；同一个事务内扣减MySQL真实库存、核销优惠券；
   - 发送消息触发发货、通知。

#### 异常与兜底

1. Redis预扣失败：直接终止流程，不生成订单。
2. RPC调用库存/优惠券超时：设置订单为中间处理中状态，不直接判成功失败；后续回查远端服务状态推进订单。
3. 超时未支付：延时消息关闭订单；定时任务兜底；释放Redis库存、退回优惠券。
4. MQ重复消费：依靠orderId状态机 + requestId幂等。
5. 定时对账任务XXL‑Job：扫描异常、中间态订单，修复脏数据，告警。

#### 关键设计点总结

1. 幂等：token / requestId；
2. 预占思想：Redis预扣库存、TCC冻结优惠券，支付成功才真实扣；
3. 主链路尽量短，非核心逻辑全部MQ异步；
4. 状态流转update带上where status条件，数据库原子流转；
5. 所有分布式流程，必须有定时对账兜底。

### 1. 大事务的危害，下单场景如何避免大事务？

#### 什么是大事务

一个Spring事务内执行时间很长：包含RPC调用、MQ发送、大量DB操作、循环查询、网络IO等，事务长时间不提交。

#### 大事务危害

1. **占用数据库连接，连接池耗尽**，后续请求拿不到连接，接口大量超时。
2. **行锁持有时间变长**，并发下单争抢库存，锁等待变多，出现大量超时、死锁。
3. 主从同步延迟变大；undo log日志膨胀，数据库压力上升。
4. 容易产生长事务，数据库MVCC需要保存旧版本，拖慢查询性能。

> 下单场景典型错误：把RPC调用库存、优惠券服务放到`@Transactional`事务内部。

#### 下单场景如何避免大事务

1. **RPC、MQ发送移出事务**，事务只保留本地数据库操作。
2. 缩小事务范围：把`@Transactional`注解范围缩小，不要加在整个方法上，只包裹必要DB写操作。
3. 避免在事务中做循环批量处理，批量拆分成小批次提交。
4. 先做各种参数校验、RPC预校验，**校验全部通过之后，再开启事务写DB**。
5. 拆分业务：非核心逻辑（短信、通知、积分）交给MQ异步，不要放在主事务内。
6. 禁止在事务里面做sleep、等待网络返回。

> 面试一句话：事务只管本地DB；网络调用全部放事务外面；先校验，后开事务。

### 2. 线程池，下单场景异步任务如何设置线程池参数？

> 不要用`Executors.newFixedThreadPool()`，生产使用`ThreadPoolExecutor`手动创建，自定义线程池，防止OOM。

核心参数：核心线程数、最大线程数、队列、拒绝策略。

#### 下单业务场景分析

下单接口：CPU轻业务，大部分消耗在DB、RPC等待，属于**IO密集型**。
- IO密集型：最大线程数一般设置：`2 * CPU核心数 ~ 4 * CPU核心数`
- 队列不要设置无界队列！无界队列任务无限堆积会OOM。使用有界队列。
- 拒绝策略：下单业务适合`AbortPolicy`抛出异常，上层捕获返回“系统繁忙，请稍后重试”。

> 区分：CPU密集型才用CPU核心数附近；下单大量等待RPC、DB，是IO密集。

#### 下单异步任务线程池示例思路

```java
// 伪代码
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    8,                  // 核心线程
    16,                 // 最大线程 IO密集
    30L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(200), // 有界阻塞队列，不能无界
    new ThreadPoolExecutor.AbortPolicy()
);
```

#### 业务注意点

1. **线程池隔离**：下单接口独立线程池，不要和其他业务共用同一个线程池。防止其他业务打满线程池把下单拖垮。
2. 异步任务尽量不要处理核心下单流程；短信、通知这种非核心才交给线程池；**订单创建、扣库存等核心流程不要异步**，避免丢失。
3. 监控线程池：活跃线程数、队列长度、拒绝次数，指标告警。

> 面试坑：面试官问，队列设很大行不行？不行，任务堆积，请求超时，内存上涨。

### 3. Synchronized和分布式锁，下单场景能不能用本地锁？为什么？

- `synchronized`、`ReentrantLock`：**JVM本地锁，只在单个JVM实例生效**。
- 分布式锁（Redis/Zookeeper）：多实例集群环境生效。

#### 下单场景能不能用synchronized本地锁？

**集群部署下绝对不能用本地锁防止超卖。**

原因：订单服务部署多台实例。
请求1打到实例A，拿到synchronized锁；请求2打到实例B，实例B的JVM根本感知不到A的锁，两个请求同时进入临界区，并发扣库存，**会出现超卖**。

✅什么时候本地锁可以用？
单机测试；单实例应用；只限制同一个实例内并发，不能解决跨实例资源竞争。

✅下单正确做法：
- 优先用Redis Lua脚本做库存预扣，原子操作，尽量少用分布式锁；
- 如果必须锁资源，使用Redis分布式锁；设置过期时间，防止死锁；注意锁续期。

> 面试一句话：synchronized只在单个JVM有效；订单服务集群部署，多实例，本地锁无法锁住跨机器并发，不能用来防超卖。

### 4. 线程池耗尽，大量下单请求，系统会发生什么，如何监控告警？

#### 现象（线程池耗尽）

队列满，最大线程已经打满，触发拒绝策略。
1. 新提交任务执行拒绝策略，抛出`RejectedExecutionException`。
2. 下单接口大量报错、返回系统繁忙。
3. 如果拒绝策略不抛异常（比如DiscardPolicy丢弃任务），任务直接静默丢失，出现：消息没发、通知丢失、部分业务逻辑没执行。
4. Tomcat业务线程如果直接提交给满的线程池，Tomcat工作线程卡住堆积，最终**Tomcat线程池耗尽，整个服务接口全部无法响应**。

#### 如何监控告警

监控线程池核心指标：
1. 活跃线程数（activeThreads），接近最大线程数告警。
2. 队列任务大小（queueSize），队列积压过高告警。
3. **拒绝任务次数rejectedTaskCount，一旦大于0立刻告警**，最重要指标。
4. 完成任务数，观察任务处理速率。

监控工具：Prometheus + Grafana；Sentinel也可以观测线程池。

#### 处理方案

1. 使用有界队列，合理设置线程池参数，业务隔离。
2. 拒绝策略选AbortPolicy，抛出异常，上层捕获，友好返回，不静默丢任务。
3. 告警触发后紧急扩容实例；排查为什么任务暴涨。
4. 核心链路不要依赖自定义线程池，核心流程同步执行；非核心才异步。

### 5. Spring事务传播，订单多service调用事务失效场景

> 常考：A调用B，不同Service，事务传播、事务不生效坑。

Spring事务默认传播行为：`REQUIRED`：有事务就加入当前事务；没有就新建事务。

#### 场景1：同一个类内部调用，事务失效

```java
@Service
public class OrderService {
    public void createOrder(){
        insertOrder(); // 本类内部调用
    }
    @Transactional
    public void insertOrder(){
        //写数据库
    }
}
```
直接调用本类带@Transactional方法，不走AOP代理，**事务完全失效**。
> 下单场景踩坑：同一个service，普通方法调用本类带事务方法，不会开启事务。
> 解决：注入自己，通过代理对象调用，或者拆分到不同Service。

#### 场景2：try‑catch捕获异常，事务不会回滚

```java
@Transactional
public void biz(){
    try{
        //数据库操作抛异常
    }catch(Exception e){
        //捕获，没有抛出RuntimeException
    }
}
```
Spring事务默认只在抛出**运行时异常/Error**才回滚；如果你catch吃掉异常，不往外抛，事务不会回滚，数据错误。
> 下单场景：DB异常被catch吞掉，以为失败，实际数据已经提交。
> 解决：catch后手动设置`TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`，或者继续向外抛出异常。

#### 场景3：REQUIRED传播，A有事务，调用B，B异常被A捕获，整个大事务回滚

A Service开启事务，调用B Service（REQUIRED，加入A的事务）。B抛出异常。
即使A把B的异常catch住，**事务已经标记回滚，最后还是回滚，报Transaction rolled back because it has been marked as rollback‑only**。

> 业务含义：B属于A同一个大事务，B出错整个事务标记回滚，外层catch也救不了。
> 如果希望B失败不影响A，B需要使用`REQUIRES_NEW`：新建独立事务。

#### 场景4：REQUIRES_NEW使用坑

A在事务中调用B(REQUIRES_NEW)，B会挂起A的事务；B自己独立提交/回滚。
注意：不要循环频繁调用REQUIRES_NEW，频繁挂起恢复事务，数据库性能下降，下单不要滥用。

#### 订单业务实操总结

1. 避免同类内部调用事务方法；
2. 异常捕获要小心，不要吞掉异常导致不回滚；
3. 多个Service调用，想子方法失败不影响主流程，子方法用REQUIRES_NEW；
4. 大部分场景默认REQUIRED即可，不要乱改传播行为。



## 十、支付&退款&售后拓展（中大厂经常追问）

1. 支付回调流程，订单状态怎么流转，回调接口要注意什么？
2. 什么是订单状态机，用状态机管理订单有什么好处？
3. 退款流程：部分退款、全额退款，订单、支付、库存怎么处理？
4. 如何做订单对账：和支付平台对账，业务内部对账

> 面试经常顺着订单往下追问支付退款，重点流程、状态流转、边界异常、对账，区分全额退款、部分退款。

### 1. 支付回调流程，订单状态怎么流转，回调接口要注意什么？

#### 整体流程

1. 用户在第三方支付完成付款，支付平台主动HTTP回调我方服务。
2. **回调接口只做两件事：验签 + 参数校验，然后投递RocketMQ，立刻返回`success`给支付平台**。
> 绝对不要在HTTP回调接口执行业务逻辑（更新订单、扣库存、发短信）。回调接口一般有几十秒超时，业务处理慢会超时，第三方会重复回调。
3. MQ消费端处理真正业务逻辑：
    1. 获取`orderId、payNo、支付金额`；
    2. **状态机原子更新订单**：`update order set status=PAID where order_id=xxx and status=WAIT_PAY`；
    3. 如果update影响行数=0，说明订单状态已经不是待支付，直接结束（处理重复回调）；
    4. 更新支付流水表，记录支付单号、金额、支付时间；
    5. 同一个本地事务扣减MySQL真实库存、核销优惠券；
    6. 发送MQ事件消息：触发发货、推送支付成功通知。

#### 订单状态流转

`待支付(WAIT_PAY)` → `已支付(PAID)`

#### 回调接口重点注意事项

1. **验签！**，校验签名防止伪造回调请求；
2. 快速响应，业务全部异步交给MQ，避免HTTP超时；
3. 幂等，依靠数据库update带状态条件，拒绝重复处理；
4. 不要信任回调传过来的金额，业务侧可以做金额校验，防止篡改；
5. 返回格式严格遵循第三方文档；业务异常也不要随意返回失败，否则支付平台会疯狂重试回调；
6. payNo支付流水号全局唯一，作为幂等key。

> 异常场景：回调丢失，我方没有收到通知。需要**主动轮询支付平台查询订单支付结果做兜底补偿**。

### 2. 什么是订单状态机，用状态机管理订单有什么好处？

订单状态机：定义订单全部状态，以及**合法的状态流转路径**，不允许随意跳转。

示例订单状态：
```
待支付 → 已支付 → 已发货 → 已完成
待支付 → 已关闭（超时/手动取消）
已支付 → 退款中 → 已退款
```

#### 核心实现方式

数据库更新时`update ... where id=? and status=旧状态`，依靠数据库行锁实现原子流转，**禁止先select再update**。

#### 使用状态机好处

1. **防止并发状态错乱**，比如支付线程和超时关闭线程并发，不会出现已支付订单被关闭。
2. 约束非法流转，比如已完成订单不能再关闭；已关闭订单不能再支付。
3. 业务逻辑清晰，每一步只允许合法流转，减少脏数据。
4. 便于排查问题，配合订单状态变更日志表`order_log`，完整记录每一次状态变更来源、时间。
5. 易于扩展售后退款状态。

> 面试关键点：状态机不是写在代码里的枚举判断，**必须下沉到SQL的where条件，原子执行**，否则并发下会出bug。

### 3. 退款流程：部分退款、全额退款，订单、支付、库存怎么处理？

> 全额退款：整单退；部分退款：一笔订单多次退部分金额。

#### ①全额退款

业务场景：用户下单支付后，申请整单退款。
状态流转：`已支付 → 退款中 → 已退款`

处理流程：
1. 用户发起退款申请，生成退款单；订单状态变更为`退款中`；
2. 调用支付平台退款接口；
3. 第三方退款回调回来；
4. 回调投递MQ，消费端处理：
    - 更新退款单状态为退款成功；订单流转为`已退款`；
    - **恢复库存**：库存数量回加；写入库存回流水；
    - 退回优惠券（满足退回规则）；
5. 通知用户退款成功。

#### ②部分退款

一笔订单多件商品，只退其中一件；或者只退部分金额。
> **订单主状态不直接改为已退款，新增多条退款记录**。订单主状态依旧保持`已支付/已发货`，靠退款单子记录每一笔退款。

处理：
1. 创建退款单，记录本次退款金额、对应商品；订单主状态不变；
2. 调用支付平台部分退款接口；
3. 退款回调成功：
    - 更新退款单成功；
    - **只恢复对应商品数量的库存**，不是全部回滚；
4. 可以多次部分退款，总退款金额不能超过原订单实付金额；业务层做校验。

#### 关键注意点

1. 库存回补也要使用条件更新：`update stock set count=count+num where id=xxx`，防止重复回补；
2. 退款也要做幂等，依靠退款单号；
3. 部分退款不能修改订单主状态为已退款，用退款子表；
4. 退款调用第三方可能超时，设置退款中间状态，定时回查第三方退款结果。

### 4. 如何做订单对账：和支付平台对账，业务内部对账

对账分为两类：**外部对账（我方 ↔ 第三方支付平台）**、**业务内部对账（订单、支付、库存、优惠券互相核对）**。

#### 一、外部对账：和支付平台对账

1. 一般每日凌晨定时任务执行；下载支付平台对账单文件。
2. 我方本地拿账单内每一笔支付流水号`payNo`和我方支付流水表比对。

三类核对结果：
1. **双方都有记录，金额一致**：对账平，没问题。
2. **支付平台有，我方没有**：平台显示成功支付，但我方系统没有这笔支付记录。
> 原因：回调丢失、消息丢失。需要补单：查询订单，执行补支付逻辑，更新订单状态。
3. **我方有记录，支付平台没有**：我方标记支付成功，但第三方没有这笔记录。
> 属于我方脏数据，告警人工介入，大概率是bug，不能自动处理，涉及资金。

> 退款同样也要对账，下载退款账单核对退款流水。

### 二、业务内部对账（定时XXL‑Job执行）

#### 1）订单 ↔ 支付流水对账

- 订单状态=已支付，必须存在对应的支付流水；
- 订单状态=已退款，必须存在对应退款流水；
异常：订单已支付无支付流水、有支付流水订单未支付。

#### 2）订单 ↔ 库存对账

- 已支付订单：必须存在库存扣减流水；
- 已取消/已退款订单：对应库存必须已经回补；
- 待支付订单：统计全部待支付订单占用库存，和Redis预扣库存比对，修复Redis。

#### 3）订单 ↔ 优惠券对账

- 订单已支付：优惠券状态为已使用；
- 订单关闭/退款：优惠券已经退回（符合退回规则）。

#### 对账通用规范

1. 按时间分片处理，不要全表扫描，避免压垮数据库；
2. 分布式锁保证多实例不会重复跑对账任务；
3. **能自动修复的自动修复；资金类异常只告警，禁止程序盲目自动修复，人工处理**；
4. 保存完整对账日志，记录哪些订单异常，便于排查审计；
5. 对账是最终兜底，不能替代业务流程。

> 面试一句话：外部对账保证和第三方资金一致；内部对账保证订单、库存、优惠券状态闭环；资金类异常优先告警人工，不能无脑自动修复。

面试官通常会从 **订单 → 库存 → 支付 → 一致性 → 高并发** 一步一步深挖。

## 一、订单系统整体架构怎么设计？

> 整体思路：**微服务拆分 + 分层架构 + 分库分表存储 + 中间件解耦 + 全链路异常补偿兜底**，核心目标：高并发、高可用、数据一致性、可扩展。

### 1、整体分层

1. **接入层**：网关 SpringCloud Gateway
    做路由、鉴权、限流、黑名单、参数校验，拦截非法请求。
2. **API网关层之后 → 微服务业务层**
3. **中间件层**：Redis、RocketMQ、Sentinel、XXL‑Job、ElasticSearch
4. **存储层**：MySQL、Redis、ES、数仓Hive

### 2、微服务拆分（核心服务）

1. **订单服务 order‑service【核心】**
    职责：创建订单、订单状态流转、取消/关闭订单、查询订单、生成退款申请。
    核心表：
    - `order_main` 订单主表（核心状态、金额、用户）
    - `order_item` 订单商品明细表（一件订单多条商品）
    - `order_pay` 支付流水表
    - `order_refund` 退款单子表（支持部分退款）
    - `order_log` 订单状态变更日志，记录每一次状态流转

2. **库存服务 stock‑service**
    库存查询、Redis预扣库存、DB真实扣减、库存回补；库存流水记录。

3. **优惠券服务 coupon‑service**
    优惠券冻结TCC‑Try、核销、退回优惠券。

4. **支付服务 pay‑service**
    对接第三方支付，生成支付单，接收支付/退款回调。

5. **用户服务 user‑service**
    用户信息、积分发放扣减。

> 服务之间通信：Dubbo/Feign RPC同步调用；事件通知使用RocketMQ异步解耦。

### 3、中间件选型与作用

1. **Redis**
    - 库存预扣，拦截大部分并发请求；
    - 接口幂等token、分布式限流、分布式锁；
2. **RocketMQ**
    - 订单创建事件，异步发送短信、通知、积分；
    - 延时消息实现订单30分钟超时关闭；
    - 事务消息保证本地DB与消息发送原子；
    - 支付回调投递MQ，避免HTTP回调执行业务；
3. **Sentinel**：限流、熔断降级，保护下游服务；
4. **XXL‑Job定时任务**：对账任务、异常订单补偿、订单冷热数据归档；
5. **ElasticSearch**：存储订单数据；商家后台、运营复杂条件查询不走MySQL主库，查询ES。

### 4、存储设计（重点，大促千万/亿级订单）

1. **MySQL作为主数据源**
    - **分库分表 Sharding‑JDBC，分片键 user_id哈希分片**
      同一个用户全部订单落在同一分片，用户查自己订单性能高。
    - 禁止用order_id分片；商家跨用户查询全部订单走ES。
2. **冷热分离归档**
    - 热库MySQL：近3个月订单，高频读写；
    - 冷库MySQL：3个月以上历史冷订单，低频访问；
    - XXL‑Job定时迁移冷数据，热库删除，减小热表大小。
3. **ES：承担复杂检索，不做数据写入源**
4. **Hive数仓：做报表统计，不用于线上业务查询**

### 5、核心业务流程（下单）

1. 网关校验、限流；前端携带幂等token
2. 订单服务幂等校验；参数校验
3. Redis Lua脚本预扣库存；TCC冻结优惠券
4. **本地事务创建订单（order_main、order_item）状态=待支付**
5. RocketMQ事务消息发送订单创建事件，异步发短信通知
6. 发送30分钟延时消息，用于超时关闭订单，返回下单成功
7. 用户支付；第三方支付回调，回调接口仅验签投递MQ立刻返回success
8. MQ消费端：**数据库状态机原子更新订单状态为已支付**；同一事务扣真实库存、核销优惠券；发送事件触发发货。

### 6、一致性、异常兜底设计（面试官重点）

1. **一致性选型：互联网订单采用最终一致性，不使用2PC强一致**
    - 资源冻结用TCC；通知事件用RocketMQ事务消息；长流程退款履约使用SAGA。
2. **订单状态机**
    更新SQL带上`where id=#{orderId} and status=旧状态`，数据库原子状态流转，防止并发状态错乱。
3. **补偿对账机制（最后一道防线）**
    XXL‑Job定时任务：
    - 外部对账：和第三方支付平台对账；
    - 内部对账：订单‑库存‑优惠券‑支付流水互相核对；
    - 扫描中间态异常订单做回查补偿；
4. 超时、RPC调用超时不直接判成功失败，设置中间状态，事后回查。

### 7、高可用&大促防护

1. 网关+应用+Redis多层限流；
2. 避免大事务，事务只包含本地DB操作，RPC/MQ移出事务；
3. 线程池隔离，下单接口独立线程池；
4. MQ堆积监控、数据库慢SQL监控、异常订单告警。

### 8、可能被追问的点

1. 为什么分片键选userId，不用orderId？
> 用户绝大多数场景查询自己的订单，userId分片查询不走多分片；商家运营查询交给ES处理。

2. ES和MySQL数据怎么同步？
> Canal监听MySQL binlog，同步变更数据到ES。

3. 如果是秒杀订单，架构要做什么改动？
> Redis拦截、MQ削峰，预扣成功才入队列异步生成订单。

> 面试简短总结话术（可以直接背）：
> 订单系统采用微服务架构，拆分订单、库存、优惠券、支付等服务；网关做接入层；使用Redis做库存预扣，RocketMQ实现异步事件与延时关闭订单；MySQL分库分表按用户ID分片，冷热数据分离；复杂查询下沉ES；采用最终一致性，TCC、可靠消息实现分布式事务，依靠状态机控制订单流转，定时对账任务做全链路兜底补偿，保障大促下高并发和数据正确性。

## 二、订单号如何设计？

> 核心需求：**全局唯一、有序、查询友好、不能暴露业务量、分库分表友好、高并发不重复**。 禁止直接用数据库自增ID：分库分表多库会出现ID冲突；容易被爬虫猜订单量。

### 1、常见方案对比

#### 方案1：雪花算法Snowflake（互联网订单最常用）

结构（64bit Long）

```
符号位(1bit)｜时间戳(41bit)｜机器ID(10bit)｜序列号(12bit)
```

- 时间戳：毫秒级，整体趋势递增；
- 机器ID：区分不同服务实例，避免多机器重复；
- 序列号：同一毫秒内，最多支持4096个订单。

✅优点：

1. 全局唯一，趋势递增，数据库写入索引性能好；
2. 不依赖数据库，内存生成，性能极高，适合大促高并发；
3. 不会泄露每日订单总量。

❌缺点：

1. 依赖系统时间，

   时间回拨会产生重复ID

   ；

   > 解决：记录上一次生成ID的时间戳，如果发现时间回拨，要么等待时间追上，抛出异常拒绝生成订单。

2. 是Long类型，展示给用户是一串长数字。

> 生产：订单主键id用雪花ID；对外展示的order_no可以直接复用雪花ID，也可以再封装。

#### 方案2：数据库自增（单库可用，分库分表不能直接用）

多库分表场景，直接自增会ID冲突。 可以使用**步长自增**：例如4个库，步长4；库0从0，库1从1，库2从2，库3从3。 维护麻烦，扩容分库要改步长，现在很少用。

#### 方案3：时间+机器+业务编码（字符串订单号）

示例：`202608140112 + 机器号 + 随机数/序列号` ✅可读性好，肉眼能看到日期。 ❌缺点：字符串索引，插入性能比Long雪花差；高并发下随机数有极小概率重复；长度长。

#### 方案4：Redis自增生成订单号

利用Redis `INCR`生成序号，拼接时间。 ❌Redis宕机风险；大促高并发压力大，一般不做主方案。

### 2、结合分库分表！重点面试考点

我们订单分片键是 `user_id`，**order_no（订单号）不等于分片键**。

> 问题：只知道订单号，不知道user_id，想查订单怎么办？

两种处理方式：

1. **建立索引表**：`order_index`，存储 order_no → user_id。 根据order_no查询时，先查索引表拿到user_id，再根据user_id路由到对应分片查询订单。

   > 缺点：多一次DB写入，大促有写入压力。

2. **雪花订单号里面不存分片信息，通过ES解决** 订单数据同步ES，直接根据order_no查询ES拿到用户ID，再去MySQL分片查数据。生产更常用。

> ❌不要把userId编码到订单号里面：会泄露用户编号，不安全。

### 3、实际生产落地怎么做

1. **订单主键ID：雪花算法Long类型，作为内部主键**
2. **对外order_no：可以直接使用雪花ID字符串输出给前端用户**
3. 时间回拨防护：机器本地缓存上次生成ID的时间戳，检测时钟回拨，拒绝生成订单。
4. 分库分表按`user_id`分片；如果通过order_no查询订单，走ES或者order_index索引表。

### 4、面试官高频问题

#### Q：雪花算法时间回拨怎么解决？

> 记录上一次生成ID的时间。

1. 如果当前时间 > 上次时间：正常生成；
2. 如果当前时间 < 上次时间（时钟回拨）：
   - 小回拨：sleep等待时间追上；
   - 回拨较大：直接抛出异常，拒绝创建订单，不允许生成重复ID。

#### Q：为什么不用UUID做订单号？

UUID无序，数据库B+树索引插入乱序，大量写入产生页分裂，数据库性能很差；不适合订单高并发写入。

#### Q：订单号能不能带日期？

对外展示可以拼接日期，但是作为主键不推荐；字符串索引写入性能低于Long雪花。

### ✨面试简短背诵版本

订单号要求全局唯一、高并发、适合分库分表，优先选用雪花算法。雪花由时间戳、机器ID、序列号组成，趋势递增，数据库索引友好；需要处理时钟回拨问题，防止ID重复。 分库分表我们分片键是user_id，订单号本身不带分片信息；如果只有订单号查询订单，可以通过ES或者order_no‑user_id索引表拿到用户ID再路由分片。不推荐UUID，无序造成数据库索引性能差；分库场景不能直接用数据库自增。

## 三、如何防止重复下单

> 重复下单场景：用户快速多次点击提交、网络超时重试、前端重试、MQ重复消费，产生多笔相同商品的无效订单。
> 核心思路：**多层防护，前端做体验，后端做真正防重；幂等设计，保证同一个请求只能生成一笔有效订单**。



### 1. 前端层（仅体验层，不能作为安全依赖）

1. 提交之后按钮置灰，禁止重复点击；
2. 短时间内禁止重复提交；
> 缺点：可以绕过（抓包、postman直接调用接口），**前端只能优化用户体验，不能防恶意重复请求**。

### 2. 网关层

1. 对同一个用户短时间限流，限制下单接口QPS；
2. 拦截高频重复请求，做基础防护。

### 3. 应用层：下单Token机制（主流方案）

流程：
1. 用户进入下单页面，后端生成**唯一的下单token**，存入Redis（分布式锁），key：`order_token:{token值}`，设置过期时间（5‑10分钟），返回前端。
2. 用户提交下单请求时，必须带上这个token。
3. 后端通过**Lua脚本原子操作**：判断token是否存在，存在就删除token；
    - 删除成功：执行业务，正常下单；
    - token不存在：说明已经使用过/非法token，直接返回“请勿重复提交”。

> Lua保证：校验+删除是原子，防止并发下两个请求同时拿到token。
> 特点：一次下单消耗一个token，用过即作废。适合前端发起的下单。

⚠️局限：MQ重试、后台系统调用接口，没有前端token，该方案不起作用。

### 4. 业务幂等键 requestId（通用，覆盖所有场景）

生成全局唯一`requestId`，由调用方生成（前端/其他服务/MQ），每次业务请求携带。
Redis保存已经处理成功过的requestId。
- 请求到来，先判断Redis是否存在该`requestId`
- 不存在：执行业务，执行成功后把requestId写入Redis，设置过期时间；
- 已存在：直接返回成功，不重复创建订单。

> 适合：接口调用、MQ消费重复、内部服务调用；
> 注意：要在**业务执行成功之后再缓存幂等key**，不要提前缓存；业务失败要清理key，允许重试。

### 5. 数据库层面兜底（最可靠的最后防线）

#### 方案A：建立业务唯一索引

业务唯一索引：`(user_id, goods_id, create_time_day)`，或者用`requestId`建立唯一索引。
同一个业务维度，数据库不允许插入多条。重复插入直接报唯一索引冲突，捕获异常返回重复下单。
> 注意：不能太严格，用户同一天可以多笔正常下单；索引设计要合理。

#### 方案B：订单状态机约束

已经生成待支付订单，不要重复生成；
> 先根据用户、商品查询是否已有待支付订单，但是**不能单纯select判断**，并发会有漏洞，要结合上面token/requestId。

### 6. MQ消费导致的重复下单（消息重复消费）

RocketMQ至少一次投递，一定会出现重复消费。
解决：
1. MQ消息携带业务幂等`requestId`；
2. 消费时使用requestId做幂等；
3. 数据库唯一索引兜底；
消费到重复消息直接返回成功，不要重复生成订单。

### 7. 完整落地的组合方案（生产）

1. 前端：按钮置灰（体验）
2. 网关：限流
3. 用户页面获取下单token；提交携带token，Lua脚本校验删除token，防页面重复点击
4. 接口/MQ传入requestId，做通用幂等
5. 数据库唯一索引做最终兜底

### 面试高频追问

#### Q：token和requestId区别？

- **下单token**：前端页面使用，一次性，用一次就销毁，防止页面多次点击；
- **requestId**：通用幂等标识，接口、RPC、MQ都用，标识一次业务请求，可用于重试场景。

#### Q：为什么不能只靠select查询判断有没有订单？

> 高并发两个请求同时select，都查不到订单，两个请求都往下执行，生成两笔订单。
> select + 业务处理不是原子，必须依靠Redis Lua或者数据库唯一索引保证原子。

#### Q：Redis宕机，幂等失效怎么办？

数据库唯一索引作为兜底。即使Redis不可用，数据库唯一索引依然可以阻挡重复数据。

### ✨简短背诵版

防止重复下单采用多层防护。前端按钮置灰仅做体验，不能信任；网关增加限流；页面场景使用一次性下单Token，通过Lua脚本原子校验删除；接口与MQ场景传入requestId实现幂等；最后数据库唯一索引兜底，避免并发下产生重复订单。不能单纯依靠select查询判断，因为非原子会出现并发漏洞。

## 四、库存如何防止超卖？

> 超卖根本原因：并发场景下库存判断和扣减**不是原子操作**；Redis与MySQL数据不一致；预占资源没有正常释放。
> 思路：**多层防护，Redis做前置拦截，MySQL是最终兜底，再加上对账修复不一致**。

### 1、错误写法（面试一定要说出来）

```java
// 危险！查询+扣减分开，非原子，并发超卖
int stock = selectStockById(id);
if(stock > 0){
    updateStock(id, stock‑1);
}
```
select 查询和update扣减分为两步，并发请求同时读到同一个库存，都会执行扣减，发生超卖。

### 2、第一层：Redis预扣库存（拦截大部分并发）

使用**Lua脚本保证 判断库存 + 扣减预扣库存原子执行**。
Redis存可售库存，只做**预扣，不是真实扣减**。
Lua逻辑：
1. 判断当前可售库存 ≥ 购买数量
2. 如果足够，执行扣减；返回成功
3. 不足直接返回失败，下单直接拦截

> Redis只做预扣，真实库存数据源是MySQL，不能把Redis当作唯一真相源。

#### 问题：预扣之后订单超时未支付，Redis库存要释放

订单30分钟超时关闭，需要把预扣的库存回补。
> 回补也要使用Lua，防止重复回补，避免库存越回越多。

### 3、第二层 MySQL数据库兜底（最重要，最后一道防线）

用户支付成功后，才真正扣MySQL的库存，**update语句带上库存条件，数据库行锁保证原子**。
```sql
update stock 
set count = count - #{buyNum} 
where id = #{stockId} and count >= #{buyNum};
```
判断影响行数：
- `affected_rows = 1`：扣减成功；
- `affected_rows = 0`：真实库存不足，扣减失败，说明出现不一致，业务回滚，告警。

> 即使Redis出bug、Redis数据错乱，MySQL这一步依然不会超卖。**绝对不能省略数据库条件更新**。

### 4、预占资源释放（容易漏的点）

以下场景必须释放Redis预扣库存：
1. 用户手动取消订单
2. 订单超时未支付（RocketMQ延时消息）
3. 创建订单后业务异常回滚

> 释放操作要做幂等，不能多次回补，造成虚增库存。

### 5、第三层：定时对账任务，修复Redis与MySQL不一致

XXL‑Job定时执行库存对账：
公式：
`DB可售库存 = Redis可售库存 + 所有待支付订单锁定占用库存`
1. 统计数据库真实库存；
2. 统计全部待支付订单占用的库存；
3. 和Redis对比，如果不一致，**以MySQL为准修复Redis缓存，同时告警**。

> 为什么会不一致：Redis宕机、网络抖动、扣Redis成功DB回滚、消息丢失等。

### 6、秒杀场景额外优化

1. Redis做库存预热，把DB库存加载进Redis；
2. 前端、网关限流，削峰；
3. Redis过滤掉大部分请求，只有预扣成功的请求才到数据库；
4. DB条件更新兜底不变。

### 高频面试问题

#### Q：只靠Redis能不能防超卖？

不行。Redis会宕机、网络异常，Redis和MySQL会数据不一致。Redis是前置拦截，MySQL才是真实数据源和最终兜底。

#### Q：分布式锁能不能解决超卖？

可以，但不推荐优先用分布式锁。
分布式锁性能差；**Lua脚本直接原子判断扣减，不需要加锁，性能更高**。只有复杂库存逻辑才考虑分布式锁。

#### Q：会不会少卖？

会出现Redis有库存，支付扣DB时库存为0。这属于少卖，业务返回库存不足即可，比超卖危害小。靠对账修复缓存。

#### Q：为什么不能扣完Redis直接扣DB，中间网络失败怎么办？

Redis预扣成功，后面流程失败：订单没有生成或者支付失败，必须有释放逻辑，再加上对账兜底。

### ✨简短背诵版

防超卖采用三层防护。首先使用Redis+Lua脚本原子完成库存判断与预扣，拦截大部分并发请求；支付成功后执行MySQL条件update，利用数据库行锁做最终兜底，避免超卖；订单取消或超时要幂等释放预占库存；最后定时对账比对MySQL真实库存与Redis，以数据库为准修复缓存。不能先查询再扣减，该操作非原子会造成超卖。

## 五、下单流程如何设计？

> 核心要点：**预占思想、幂等、大事务规避、非核心逻辑异步、状态机、异常兜底**。
> 整体链路：前端 → 网关Gateway → 订单服务 → Redis → RPC调用库存/优惠券服务 → MySQL → RocketMQ

### 完整流程

#### 1. 前端

1. 用户选择商品、数量、收货地址；
2. 向后端**申请一次性下单Token**存入Redis；
3. 提交下单请求，携带：`下单token、requestId、商品、数量、地址、用户ID`。

#### 2. 网关层

1. 鉴权，校验登录；
2. 限流、黑名单拦截；参数基础校验。

#### 3. 订单服务接收请求

① **幂等校验（Lua脚本）**：校验并删除下单Token；Token不存在直接返回“请勿重复提交”。
> requestId同时携带，用于MQ、RPC场景幂等。

② **业务参数校验**：商品数量大于0，地址非空，商品状态校验。

③ **Redis预扣库存（Lua原子脚本）**
- 判断库存是否充足；库存不足直接返回库存不足；
- Redis只做**预扣锁定，不是真实扣减MySQL库存**。

④ **TCC Try冻结优惠券**（RPC调用优惠券服务）
冻结优惠券，防止被其他订单占用。
> RPC调用放在事务外面，避免产生大事务。

⑤ **开启本地事务，创建订单**
事务内只做数据库写操作：写入`order_main`订单主表、`order_item`订单明细表。
订单初始状态：**待支付 WAIT_PAY**。
> ❗RPC、MQ发送**放到事务外面**，缩小事务，防止大事务。

⑥ **发送RocketMQ事务消息（订单创建事件）**
异步处理短信、站内信、积分发放，不阻塞主流程。

⑦ **发送30分钟RocketMQ延时消息**
用于超时未支付自动关闭订单。

⑧ 返回前端：下单成功，返回orderNo，引导用户去支付。

> ⚠️此时仅仅是预扣库存，**MySQL真实库存还没有扣，需要用户支付成功之后才真正扣减**。

#### 4、支付回调异步流程

1. 用户完成支付，第三方支付平台发起HTTP回调；
2. **回调接口只做验签，投递MQ，立刻返回success，不执行业务逻辑**；
3. MQ消费端处理：
    1. 根据orderNo查询订单；
    2. **状态机原子更新订单**
    ```sql
    update order_main set status=PAID where order_no=#{orderNo} and status=WAIT_PAY;
    ```
    如果影响行数为0，代表订单状态已经变更，直接结束（处理重复回调）。
    3. **同一个本地事务：更新支付流水 + MySQL真实扣库存 + 核销优惠券**。
    4. 发送MQ事件消息，触发发货、支付成功通知。

#### 5、超时关闭订单流程（两条保障）

1. RocketMQ延时消息消费：执行关闭订单
```sql
update order_main set status=CLOSED where order_no=#{orderNo} and status=WAIT_PAY;
```
关闭成功则：释放Redis预扣库存、退回优惠券。
2. XXL‑Job定时任务兜底扫描超时待支付订单，防止MQ消息丢失。

### 各类异常处理

1. Redis预扣库存失败：直接终止流程，不创建订单。
2. RPC调用优惠券/库存超时：设置订单为**中间处理中状态**，不直接判成功/失败；后续回查服务状态再推进订单。
3. MQ重复消费：依靠`requestId`+数据库状态机做幂等。
4. 订单创建成功，后续支付失败：延时消息+定时任务释放预占资源。

### 关键设计要点（面试官爱追问）

1. **预占思想**：下单只预扣Redis库存，支付成功才扣DB真实库存；
2. 避免大事务：RPC、MQ全部移出事务，事务只保留本地数据库写入；
3. 幂等防护：前端token + requestId，数据库兜底；
4. 状态机：更新SQL带上旧状态条件，防止并发状态错乱；
5. 非核心逻辑全部MQ异步，主流程尽量简短；
6. 不能只依赖MQ，定时任务做兜底补偿。

### ✨面试简短背诵版

用户请求经过网关鉴权限流，请求携带一次性下单token和requestId做幂等防护；先做参数校验，通过Redis+Lua预扣库存，RPC冻结优惠券；之后开启本地事务创建待支付订单；把短信通知交给事务消息异步处理，发送延时消息用于超时关闭订单，返回下单成功。
用户支付后，第三方回调只验签投递MQ；MQ消费端通过状态机原子更新订单为已支付，同一个事务完成真实扣减数据库库存、核销优惠券。
超时未支付由延时消息关闭订单，释放预占库存优惠券，定时任务兜底补偿；RPC超时设置中间状态，通过回查+定时任务处理异常。

## 六、订单 30 分钟未支付如何取消？

需求：订单状态为**待支付**，超过30分钟没有付款，自动关闭订单；同时释放Redis预扣库存、退回优惠券；不能重复关闭。

> 生产一般采用**主方案+兜底方案**，不能只依赖单一方案，防止消息丢失。

### 方案一：RocketMQ延时消息（主方案）

1. 用户下单成功，生成订单，状态=待支付；
2. 发送一条**30分钟延时消息**到RocketMQ，消息体携带orderNo；
3. 30分钟后消息投递给消费者；
4. 消费逻辑：

```sql
update order_main 
set status=CLOSED 
where order_no=#{orderNo} and status=WAIT_PAY;
```

- **影响行数 = 1**：关闭订单成功。执行释放Redis预扣库存、退回优惠券；
- **影响行数 = 0**：说明订单已经支付 / 已经手动取消，直接返回，什么都不做（幂等）。

✅优点：大部分订单可以准时触发关闭；不用频繁扫数据库；业务解耦。
❌缺点：Broker故障、消息丢失、消息堆积，订单不会自动关闭；不能单独依靠它。

> 注意：RocketMQ延时只有固定等级，不能任意毫秒，只能选最接近30分钟的延时等级。

### 方案二：定时任务轮库兜底（XXL‑Job，兜底方案）

定时任务每隔一段时间（例如5分钟执行一次），扫描满足条件的订单：
`status = 待支付 AND create_time < 当前时间 - 30分钟`

> ⚠️大促订单量很大，禁止全表扫描！
> 优化：

1. 分页、分片查询，按时间范围分页；
2. 必须建立索引：`idx_status_createtime(status,create_time)`；
3. 分布式锁，防止多实例任务重复处理同一批订单；
4. 批量关闭，不要单条循环。

关闭之后同样释放库存、退回优惠券。

✅优点：可靠性高，弥补延时消息丢失，作为兜底。
❌缺点：执行间隔带来时间误差，不是刚好30分钟；任务压力随订单量变大。

### 方案三：Redis ZSet延时队列（一般不做生产主选）

下单把`到期时间戳 + orderNo`放入zset；后台线程不断zrangebyscore取出到期订单。
✅可以支持任意延时时间。
❌Redis宕机数据丢失；需要自己实现可靠性；生产很少用于订单，多用于小项目。

### 生产选型：延时消息为主，定时任务兜底

> RocketMQ延时消息处理绝大多数订单；XXL‑Job定时任务扫描，处理消息丢失的极端场景。

### 重要边界问题（面试官重点追问）

1. **幂等问题：重复触发关闭怎么办？**
   依靠SQL条件更新`where status=WAIT_PAY`，如果订单已经被关闭或者已经支付，update返回0行，直接跳过，不会重复释放库存优惠券。释放库存也要Lua幂等，防止多次回补导致库存虚增。

2. **订单分库分表场景，定时任务怎么扫？**
   不能跨所有分片全量扫描。

- 方式1：每一个分片单独执行定时任务，只扫描本分片数据；
- 方式2：订单数据同步ES，定时任务从ES查询出超时订单号，再路由到对应分片做关闭。

3. 如果刚好在第30分钟，用户正在支付？
   并发竞争：支付线程执行`update ... set status=PAID where status=WAIT_PAY`；关闭线程执行`update ... set status=CLOSED where status=WAIT_PAY`。
   数据库行锁保证只有一个执行成功，另一个update返回0，不会出现既支付成功又被关闭。

4. 释放资源要做什么？
   关闭成功才执行：
   ①Lua脚本释放Redis预扣库存；
   ②RPC调用优惠券服务退回优惠券；
   如果关闭失败（update返回0），不做任何资源释放。

### ✨简短背诵版

30分钟未支付关闭订单采用两套机制：下单成功发送RocketMQ延时消息作为主方案，到期消费通过状态机条件更新关闭待支付订单，同时释放预扣库存、退回优惠券；
为防止消息丢失，使用XXL‑Job定时任务做兜底，按时间分页扫描超时待支付订单；SQL带上`status=待支付`条件实现幂等，避免重复关闭。
分库分表下定时任务不能全表扫描，可以每个分片单独扫描或者借助ES查询超时订单。数据库行锁可以解决“用户刚好支付同时触发关闭”的并发冲突。

## 七、支付回调如何保证幂等？

支付平台例如：

- Alipay
- WeChat Pay

可能：

```
多次回调
```

解决方案：

数据库唯一约束：

```
orderId
```

代码：

```
if(order.status == PAID){
    return;
}
```

确保：

```
重复回调不会重复处理
```

> 问题背景：第三方支付平台会因为网络超时、重试，**多次发送同一个支付回调**。如果不做幂等，会重复更新订单、重复扣优惠券、重复发通知，产生脏数据。 核心：**同一个支付回调，多次调用，业务只处理一次，返回成功，不重复执行业务**。

### 支付回调整体处理原则

HTTP回调接口**只做验签、参数校验，直接投递MQ，立刻返回success**，不在http接口执行业务逻辑；真正业务逻辑放在MQ消费端做幂等。

幂等四层保障，层层兜底：

#### 1、第一层：支付流水号 payNo 作为业务唯一标识

每一笔支付都有第三方返回唯一`payNo`。

- 我方`order_pay`支付流水表，给`payNo`建立**唯一索引**。
- 如果重复回调，MQ重复消费，插入相同payNo，数据库唯一索引冲突，直接捕获异常，消费直接返回成功，不重复处理。

#### 2、第二层：订单状态机（最核心）

MQ消费执行业务更新订单：

```
update order_main 
set status = 'PAID', pay_no=#{payNo}, pay_time=now() 
where order_no=#{orderNo} and status = 'WAIT_PAY';
```

- `影响行数=1`：更新成功，执行后续逻辑（扣真实库存、核销优惠券、发送通知）。
- `影响行数=0`：说明订单已经不是待支付：已经支付成功 / 已经关闭。**直接return，不再执行任何业务逻辑，消费返回成功**。

> 这一步解决：同一个订单多次回调，不会重复执行业务。即使payNo不一样，只要订单已经支付，就不会重复处理。

> 关键点：依靠数据库行锁，并发场景下，支付回调和订单超时关闭并发竞争，只有一个操作成功。

#### 3、第三层：消费端幂等缓存（Redis，提升性能）

以`payNo`为key，处理成功写入Redis，设置过期时间。 消费收到消息：

1. 先查Redis，如果key已存在，直接返回成功，跳过业务；
2. 不存在才往下执行业务；
3. **业务处理成功之后再写入Redis**，业务失败不要写，允许重试。

> 作用：避免重复请求打到数据库，减轻DB压力。 注意：Redis只是缓存层，不能作为唯一依赖，Redis宕机，还要靠数据库兜底。

#### 4、第四层：MQ消费位点

RocketMQ至少一次投递，会重复投递消息。业务消费处理完成才提交offset；不要先提交offset再执行业务，否则业务失败消息丢失。

### 完整消费端流程

1. 获取消息：orderNo、payNo、支付金额；
2. 验签校验，校验回调金额；
3. Redis查询payNo，存在直接返回；
4. 执行状态机update更新订单；
5. 如果update返回0，直接返回；
6. update成功：开启本地事务，插入支付流水、扣数据库库存、核销优惠券；
7. 业务全部执行成功，把payNo写入Redis；
8. MQ提交消费offset。

### 高频面试问题

#### Q：为什么不直接在HTTP回调接口做幂等？

HTTP回调有超时限制，如果业务处理慢，第三方会重试回调。业务逻辑放到MQ异步处理，http只快速返回success。

#### Q：Redis挂了会不会出现重复处理？

不会。有**数据库唯一索引 + 订单状态机**兜底，即使Redis失效，数据库层面依然阻挡重复处理。

#### Q：回调丢失怎么办？

回调丢失，永远收不到通知。需要补偿机制：定时任务主动轮询第三方支付接口查询订单状态，补单。

#### Q：支付回调和30分钟关闭订单并发冲突？

数据库行锁保证互斥：

- 如果支付先执行update status=PAID成功，关闭订单update where status=WAIT_PAY 返回0，关闭逻辑直接跳过。
- 如果关闭订单先执行status=CLOSED成功，支付回调update返回0，不会把已关闭订单改成已支付。

### ✨简短背诵版

支付回调会被第三方多次重试，不能在HTTP接口执行业务，只做验签投递MQ。幂等依靠四层保障：

1. 使用第三方唯一`payNo`，支付流水表建立唯一索引；
2. **订单状态机条件更新SQL**：`update ... where status=待支付`，影响行数为0直接跳过业务，这是核心；
3. Redis缓存已处理的payNo，拦截重复消息，减轻数据库压力；
4. MQ正确管理offset。 Redis只做缓存，数据库作为最终兜底。同时要考虑回调丢失，定时轮询第三方接口做补偿；数据库行锁解决支付与订单关闭的并发竞争。

## 八、如何设计退款流程（面试口述）

> 分为**全额退款**、**部分退款**；重点：状态流转、幂等、库存回补、退款回调幂等、超时补偿、对账。
> 核心：订单主状态、退款单子表分离；部分退款不修改订单主状态；所有外部调用要考虑超时，设置中间状态，靠定时任务回查。

### 1、全额退款（整单退）

状态流转：`已支付(PAID)` → `退款中(REFUNDING)` → `已退款(REFUNDED)`

流程步骤：
1. 用户发起退款申请，传入`orderNo`；业务校验：订单状态必须是已支付，不能重复申请退款。
2. **生成退款单 order_refund**，退款单状态=退款中，记录退款单号`refundNo`、退款金额、订单号。更新订单主表状态改为`退款中`。
3. RPC调用第三方支付退款接口。
    - 如果调用成功：等待第三方退款回调。
    - 如果调用超时/网络异常：退款单停留在**退款中（中间状态）**，不判定成功失败，交给定时任务回查第三方退款结果。
4. 第三方退款回调过来：
    
    - HTTP回调只做验签，投递MQ，立刻返回success。
5. MQ消费端处理退款成功：
    1. 以`refundNo`做幂等；退款流水表对`refundNo`建立唯一索引。
    2. 状态机更新退款单：`update order_refund set status=SUCCESS where refundNo=? and status=REFUNDING`；行数0直接返回，不重复处理。
    3. 更新订单主状态为`已退款`。
    4. **回补库存**，条件更新SQL，防止重复回补：
    ```sql
    update stock set count = count + num where id = #{stockId};
    ```
    5. 退回优惠券（满足退回规则）。
    6. 发送MQ通知用户退款成功。

### 2、部分退款（一笔订单多次退）

> 关键点：**订单主表状态保持已支付，不改为已退款，全部依靠退款子表记录每一笔退款**。
> 例如订单买2件商品，退1件；还可以再退剩下1件。

流程：
1. 用户申请部分退款，填写退款金额、对应商品；
2. 业务校验：累计退款金额不能大于订单实付金额；
3. 创建退款单子表记录，状态=退款中；**order_main主表状态不变，依旧是PAID**；
4. 调用支付平台部分退款接口；
5. 退款回调MQ消费：更新该条退款单为成功；**只回补对应数量的库存**；
6. 允许多次部分退款；全部金额退完之后，可以把订单主状态更新为已退款。

### 3、退款回调的幂等设计

和支付回调思路一致：
1. http回调只验签投递MQ，不执行业务；
2. 以第三方返回的`refundNo`作为唯一key；退款流水表建立唯一索引；
3. 退款单子表做状态机条件更新：`update ... where refundNo=xx and status=退款中`，影响行数0直接跳过；
4. Redis缓存处理过的`refundNo`，减轻DB压力；
5. 数据库兜底，Redis不能作为唯一依赖。

### 4、退款调用第三方超时如何处理（高频追问）

调用支付退款接口网络超时，我方不知道第三方是否处理成功。
1. 退款单状态停留在`退款中`中间状态，**不能直接判定失败，也不能直接判定成功**。
2. XXL‑Job定时任务，扫描状态为退款中的退款单，拿`refundNo`主动调用第三方查询接口。
    - 如果第三方显示退款成功：走退款成功逻辑；
    - 如果第三方显示退款失败：更新退款单为失败，通知用户；
    - 如果依旧超时，下次任务继续轮询。

> 绝对不要重试调用退款接口，会重复发起退款，造成重复退款；只能**查询结果**。

### 5、边界问题

1. 库存回补必须条件更新，不能直接set，防止多次退款重复回补，库存虚高。
2. 优惠券退回要判断规则：过期优惠券不退回。
3. 退款也要参与对账：每日下载第三方退款账单，和我方退款流水核对。
4. MQ重复消费依靠refundNo+退款单状态机做幂等。

### ✨简短背诵版

退款分为全额退款和部分退款。全额退款订单状态流转为已支付→退款中→已退款；部分退款不修改订单主状态，通过退款子表记录每一笔退款。
用户发起退款生成退款单，调用支付平台退款接口，如果调用超时，退款单停留在退款中中间状态，定时任务主动查询第三方结果，不能盲目重试退款接口。
退款回调HTTP接口只验签投递MQ；使用refundNo唯一索引+退款单状态机实现幂等；退款成功后条件更新回补库存、退回优惠券。退款流水参与每日对账，保证资金一致。

## 八、库存扣减在哪一步做？

常见有三种模式。

### 1 下单扣库存

优点：

```
不会超卖
```

缺点：

```
库存锁定时间长
```

------

### 2 支付后扣库存

优点：

```
库存利用率高
```

缺点：

```
可能超卖
```

------

### 3 预扣库存（最常见）

流程：

```
下单 → 锁库存
支付 → 扣库存
取消 → 释放库存
```



> 核心区分：**Redis预扣库存、MySQL真实库存扣减，两步发生在完全不同阶段，千万不要混淆**

### 1、Redis预扣库存：【下单阶段】

用户提交下单请求，还没有付钱的时候。
- 时机：下单流程，参数校验通过之后，**创建订单之前执行Lua脚本预扣Redis库存**
- 作用：拦截大部分并发请求，做库存前置校验，防止大量无效请求打到数据库。
> ⚠️这只是内存里的预锁定，**不是真正扣数据库库存**。订单状态此时为「待支付」。

> 如果后续用户不支付，30分钟超时关闭订单，需要**释放Redis预扣的库存**。

### 2、MySQL真实库存扣减：【支付成功回调阶段】

> ✅真正扣数据库库存，是**支付回调MQ消费业务里面执行**，不是下单的时候！

时机：
用户完成支付，第三方支付回调，投递MQ，消费端执行：
1. 通过状态机更新订单状态从「待支付」→「已支付」（update带where status=WAIT_PAY）
2. **同一个本地事务里面执行MySQL真实库存扣减**
```sql
update stock set count = count‑#{num} where id=#{stockId} and count>=#{num};
```
同时做：插入支付流水、核销优惠券。

#### 为什么不在下单扣DB库存？

1. 下单后大量用户不付款（恶意下单、用户放弃支付），会造成数据库库存大量占用，库存被锁死，其他用户无法购买。
2. 需要做库存回滚，逻辑复杂；大量待支付订单堆积，数据库压力大。

### 3、各个场景下库存处理

1. ✅下单成功，未支付：Redis预扣，DB库存不变。
2. ✅支付成功：DB真实扣减库存。
3. ✅订单超时关闭 / 用户手动取消订单：**只释放Redis预扣库存，DB库存不动**。
4. ✅退款成功（全额/部分退款）：**MySQL数据库执行库存回补**。

### 4、容易出错的坑

1. ❌错误：下单直接扣MySQL库存。大量不付款订单占用库存。
2. ❌错误：支付成功只扣Redis，不扣MySQL。Redis只是缓存，会造成数据不一致。
3. ❌错误：关闭订单的时候回补MySQL库存。此时DB根本没有扣减，回补会造成库存虚增。

### 5、大促秒杀场景的小变化

秒杀流量极高，大量请求直接被Redis拦截；
只有Redis预扣成功的请求才往下走，生成订单，依旧**支付成功才扣DB真实库存**。

### 高频追问

#### Q：Redis预扣成功，但是支付回调丢失怎么办？

订单30分钟超时关闭，延时消息+定时任务兜底，释放Redis预扣库存。

#### Q：Redis预扣成功，扣DB库存发现库存不足，会发生什么？

出现缓存与数据库不一致。此时订单不能改为已支付，业务回滚，释放Redis库存，告警，后续定时对账修复缓存。属于少卖，业务返回库存不足，比超卖危害小。

### ✨简短背诵版

库存分为Redis预扣和MySQL真实扣减两步。
**Redis预扣发生在下单阶段**，用来前置拦截请求，此时数据库库存不变；用户未支付，订单关闭时释放Redis预扣库存。
**MySQL真实库存扣减发生在支付成功回调MQ消费阶段**，订单状态更新为已支付的同一个本地事务中执行。
退款的时候才对MySQL做库存回补。不要在下单时扣数据库库存，否则未付款订单会占用真实库存。

## 九、订单系统如何抗高并发？

> 高并发压力主要集中在**下单接口**，大促瞬间大量请求涌入。核心思路：**分层限流、请求前置拦截、缓存削峰、异步化、数据库保护、避免锁与大事务**。从接入层、应用、缓存、MQ、数据库多个层级做防护。

### 1、接入层（网关层）削峰限流

1. **限流**：Sentinel/网关限流，限制下单接口QPS；区分总限流、用户级限流，防止单用户疯狂刷接口。
2. 黑名单拦截恶意IP；鉴权校验，非法请求直接拦截，不打到后端服务。
3. 前端防护：按钮置灰，防重复提交；页面静态化。

> 目标：把无效请求直接挡在最外层，不要进到业务服务。

### 2、Redis前置拦截（核心，挡掉大部分请求）

1. **库存预扣**：使用Lua脚本原子做Redis库存预扣。库存不足直接返回，大量失败请求不会到达数据库。
2. **防重复下单**：一次性下单Token、requestId幂等，拦截重复请求。
3. 热点数据缓存，减少DB查询。

> 大促场景绝大部分请求在Redis层就直接返回，不会走到创建订单写库逻辑。

### 3、异步化，缩短主流程，MQ削峰

1. **非核心逻辑全部异步**：短信、通知、积分、日志，通过RocketMQ事务消息异步处理，不阻塞下单主流程。
2. 支付回调不做同步业务处理，回调只验签投递MQ，业务交给消费端异步执行。
3. 秒杀场景：Redis预扣成功后，请求进入MQ队列，**异步生成订单**，前端返回排队中，进一步保护数据库。

⚠️核心业务（创建订单、预扣）不能异步，必须同步。

### 4、应用层优化

1. **线程池隔离**：下单接口独立线程池，和其它业务线程池隔离，避免别的业务打满线程池拖垮下单。
2. 避免大事务：RPC调用、MQ发送移出事务，事务只保留本地DB写操作，缩短事务持有时间，减少行锁等待。
3. 避免使用分布式锁做库存扣减；优先Lua原子脚本，减少锁竞争。
4. 接口降级：大促可关闭非必要功能（如商品推荐、复杂统计），保障下单核心链路。

### 5、数据库层保护（最大瓶颈）

数据库是订单系统最大瓶颈，**要尽量减少写压力**。

1. **分库分表 Sharding‑JDBC**：订单按`user_id`哈希分片，分散读写压力，避免单表数据量过大。
2. 建立合适索引，避免慢SQL；禁止大促做复杂join、大查询。
3. 读写分离：查询走从库，创建订单写主库。商家复杂查询直接走ES，不访问MySQL。
4. 控制事务大小，减少行锁持有时间。
5. 冷热分离：历史订单迁移到冷库，热库只保留近几个月订单，保证热库性能。

### 6、中间件保障

1. MQ：消息堆积监控；合理设置分区数，提升消费并行度；避免消息丢失。
2. Redis：集群部署，主从+哨兵；热点库存做分片，避免大促热点key打单节点。

### 7、兜底补偿机制（高并发下必然会出现异常）

1. 定时对账任务，修复Redis与MySQL不一致。
2. 延时消息 + XXL‑Job处理超时未支付订单，释放预占库存。
3. 监控告警：接口RT、异常率、线程池队列、MQ堆积、数据库慢SQL、锁等待。

### 区分普通订单 vs 秒杀订单

普通电商订单：上面整套，同步创建订单； 秒杀：Redis拦截之后，请求入MQ，**异步生成订单**，前端返回排队中，进一步降低数据库瞬时压力。

### ✨简短背诵版

订单系统抗高并发做多层防护：网关层做鉴权、限流拦截无效请求；利用Redis Lua脚本做库存预扣、幂等校验，在缓存层挡掉大部分请求；非核心逻辑全部MQ异步化，缩短主链路；应用侧做线程池隔离，规避大事务，减少锁等待；数据库通过分库分表、读写分离、冷热数据分离分散压力，复杂检索下沉ES；同时做好监控告警与定时对账兜底。秒杀场景还可以通过MQ队列异步生成订单进一步削峰。

## 十、订单如何分库分表？

> 随着订单量上涨，单表千万以上，查询、写入性能下降，需要做分库分表；使用Sharding‑JDBC做客户端分片。

### 1、分片键选择：user_id（用户ID）

**分片键：user_id，哈希分片**

- 同一个用户的所有订单，都会落到同一个库的同一个分片。
- 用户最常见场景：查询自己的全部订单。只路由到一个分片，不需要跨库查询，性能很高。

❌为什么不用 order_no（订单号/雪花ID）做分片键？ 如果按orderNo哈希分片：查一个用户订单，需要扫描**全部分片**，性能极差。

> 缺点：只知道订单号，不知道user_id时，无法直接定位分片。 解决两种方案：

1. **索引表 order_index**：存储 `order_no → user_id`。根据order_no查询时，先查索引表拿到userId，再路由到对应分片查询订单。索引表也需要分表。
2. **通过ES查询**：binlog同步订单数据到ES，直接用order_no查询ES拿到userId，再查MySQL。生产更常用。

### 2、分库分表策略

示例：分成**4库，每库8张表，一共32分片**

1. 根据`user_id`做哈希取模： `分片编号 = hash(user_id) % 总分片数`
2. 根据分片编号路由到对应的库和表。

> 哈希分片：数据分布均匀，大促写入压力打散；缺点范围查询（按时间查全部用户订单）会跨分片。

### 3、相关配套表怎么处理

1. ```
   order_main
   ```

   订单主表、

   ```
   order_item
   ```

   订单明细表：

   都按user_id分片

   > 子表必须跟主表分片键一致，保证主、子数据落在同一个分片，可以做本地join，避免跨库join。

2. `order_pay`支付流水、`order_refund`退款单：同样跟随user_id分片。

3. 全局表（字典、配置）：广播表，每一个库都存一份。

### 4、分库分表带来的问题与解决方案

1. **根据order_no查询，缺少分片键** ES同步 or order_index索引表。
2. **跨分片分页、排序（后台商家查全部订单）** 不能直接MySQL分页；方案：查询走ES，MySQL只承担用户维度查询。后台运营、商家报表不要查MySQL。
3. **分布式主键** 不能用数据库自增；订单号使用雪花算法生成全局唯一ID。
4. **分布式事务** 分库之后跨库不能用本地事务；订单、库存、优惠券不在同一个库，采用**最终一致性**：TCC、RocketMQ可靠消息，不使用2PC。
5. **join限制** 禁止跨库join；同分片内可以本地join。复杂查询交给ES。
6. **扩容麻烦** 哈希分片后期扩容需要迁移数据；前期评估好数据量，预留分片。

### 5、冷热数据分离（配套）

热数据：近3个月订单，放在分库分表热库，正常读写。 冷数据：3个月以前历史订单。XXL‑Job定时迁移到冷库；热库删除。 用户查询历史订单优先查热库，查不到再查冷库。减轻热库压力。

### 6、DDL变更痛点

分库分表DDL改表，要所有分片全部执行；需要做好灰度发布。

### 7、简单落地流程总结

1. Sharding‑JDBC客户端分片，分片键`user_id`哈希分片；
2. 订单主表、明细表、退款表全部使用user_id分片；
3. 用户查自己订单，直接路由单个分片；
4. 通过order_no查询借助ES/索引表；
5. 商家、后台复杂查询不走MySQL，使用ES；
6. ID采用雪花算法；跨库采用最终一致性；做冷热数据分离。

### ✨简短背诵版

订单分库分表选用 **user_id哈希分片**，同一个用户所有订单落在同一个分片，满足用户查询自己订单的高频场景；订单明细表、退款流水等子表跟随user_id分片，保证同分片本地join。 只知道订单号查询时，通过ES或者order_no‑user_id索引表获取userId再路由。 后台商家复杂查询不访问MySQL，走ES；主键用雪花算法；跨库不用强一致事务，采用最终一致性；同时做冷热分离，历史订单迁移冷库。 缺点是扩容迁移成本高，不能跨分片join，分页排序受限。

> 下一题：十一、分库分表有哪些坑？

## 十一、分库分表有哪些坑

> 分库分表解决单库单表数据量大的问题，但会引入很多分布式问题，不要过早做分库分表。

### 1、分片键带来的问题

1. **非分片键查询，会触发全分片扫描**
我们分片键是`user_id`，如果只用`order_no`查询订单，不知道user_id，就需要遍历所有库表，性能极差。
解决：ES同步binlog，或者建立`order_index`索引表维护 order_no → user_id。

2. **分片键不能更新**
如果更新user_id，数据不会自动迁移到对应分片，数据就错位。业务上订单的user_id本身不允许修改。

3. **跨分片join不支持**
只能同一个分片内做本地join；跨库不能join。
解决：大表全部使用相同分片键；复杂查询交给ES。

### 2、分页、排序、聚合问题

1. **跨分片分页排序**
例如后台按时间查全部订单、`limit 10000,10`。每个分片都要查出对应数据，内存归并再排序，性能很差。
> 禁止MySQL做后台的大列表查询。
> 解决：商家、运营后台查询走ES，MySQL只服务C端用户查询自己的订单。

2. **count、sum聚合函数**
需要每个分片分别统计，再程序内存聚合，性能低。报表统计走数仓。

### 3、分布式主键问题

不能使用数据库自增ID，多库会ID冲突。
解决：雪花算法生成全局唯一ID。

### 4、分布式事务问题

数据分散多个库，**不能使用本地事务**。
比如订单在分片A，支付流水在分片B，本地事务失效。
- 不推荐2PC，性能差；
- 采用最终一致性：可靠消息、TCC、SAGA；
- 业务上尽量把关联数据放到同一个分片，减少跨库事务。

### 5、扩容迁移麻烦（哈希分片最大痛点）

我们用的是哈希取模分片，**新增库/表需要重新hash，大量数据要迁移**。
- 方案1：前期评估数据量，一次性分够分片，尽量避免后期扩容。
- 方案2：使用一致性哈希减少迁移数据量。
- 方案3：双写迁移，业务灰度切换，不能停机迁移。

### 6、DDL变更麻烦

一张表分几十上百个分片，改字段、加索引，所有库所有表都要执行DDL。
- 执行慢，容易锁表；
- 必须灰度执行，不能一次性全部执行。

### 7、本地约束失效

1. **唯一索引失效**：MySQL唯一索引只在单库单表生效；跨分片数据库无法保证唯一性。
比如想order_no唯一，直接建唯一索引无效，数据会分散不同分片。
解决：
- 在Redis做唯一性校验；
- 或者单独一张全局索引表维护唯一键。

> 重点：分库后数据库层面无法跨分片保证唯一约束。

### 8、业务复杂度提升

1. SQL要注意，不能写跨分片的SQL；开发要时刻注意分片键；
2. 联调、排错更麻烦；问题定位难度变大；
3. 本地单元测试很难模拟完整分库分表环境。

### 9、冷热数据如果没处理

老订单一直留在热分片，分片数据量持续上涨，分库分表也会慢慢变慢。
解决：定时迁移冷数据到冷库。

### ✨简短背诵版

分库分表常见坑：
1. 非分片键查询会全分片扫描，需要ES或索引表辅助查询；分片键不可更新。
2. 不支持跨分片join，跨分片分页、排序、聚合性能差，后台复杂查询建议走ES。
3. 数据库自增主键失效，要用雪花算法。
4. 产生跨库分布式事务，不推荐2PC，尽量同分片放关联数据，采用最终一致性。
5. hash分片扩容麻烦，需要数据迁移；DDL变更要操作全部分片，风险高。
6. 数据库唯一索引只能单分片生效，跨分片无法保证唯一性，需要上层业务或Redis保证。
7. 业务开发、排查问题复杂度提升。因此不要过早做分库分表，单表千万级别再考虑。

## 十一、订单状态如何设计？

> 订单状态是状态机模型，**只允许固定的状态流转，不允许任意状态跳转；靠数据库条件更新实现状态机，防止并发下状态错乱**。

### 订单核心状态

1. **WAIT_PAY 待支付**：下单成功，未付款。Redis预扣库存，DB库存不变。
2. **PAID 已支付**：用户付款成功。DB真实扣减库存。
3. **SHIPPED 已发货**：商家已经发货。
4. **FINISHED 已完成**：用户确认收货，订单正常结束。
5. **CLOSED 已关闭**：30分钟超时未支付 / 用户手动取消（仅待支付可关闭）。
6. **REFUNDING 退款中**：用户发起退款申请。
7. **REFUNDED 已退款**：退款完成。

### 合法状态流转（重点）

```
待支付(WAIT_PAY)
├─→支付成功 → 已支付(PAID)
└─→超时/手动取消 → 已关闭(CLOSED)

已支付(PAID)
├─→发货 → 已发货(SHIPPED)
└─→申请退款 → 退款中(REFUNDING)

退款中(REFUNDING)
├─→退款成功 → 已退款(REFUNDED)
└─→退款失败 → 退回已支付(PAID)

已发货(SHIPPED)
└─→确认收货 → 已完成(FINISHED)
```

> 关键约束：

1. **只有待支付，才可以关闭订单**；已经支付的订单不能直接关闭。
2. 已关闭、已完成、已退款属于终态，**不能再变更为其他状态**。

### 如何保证状态不会乱跳（状态机实现）

不能先查询状态，再做业务更新（select+update非原子，并发会出错）。 必须使用**条件更新SQL**：

```
update order_main 
set status = 'CLOSED' 
where order_no=#{orderNo} and status = 'WAIT_PAY';
```

- `affected_rows=1`：状态符合预期，更新成功，执行业务逻辑；
- `affected_rows=0`：状态已经变化，直接返回，不执行业务。

> 所有状态变更都用这种方式：带上**旧状态作为where条件**，数据库行锁保证原子。

### 典型并发场景

场景：订单刚好30分钟，一边支付、一边延时消息关闭订单。

1. 支付：`update set status=PAID where status=WAIT_PAY`
2. 关闭：`update set status=CLOSED where status=WAIT_PAY`

数据库行锁互斥，只有一个执行成功，另一个返回0行。不会出现既支付成功又被关闭。

### 部分退款对订单状态的影响

- **部分退款**：订单主状态仍然保持`PAID`，状态不改变；退款记录存在子表`order_refund`。多次部分退款，直到全部金额退完，再把主状态改为`REFUNDED`。
- **全额退款**：直接流转：PAID → REFUNDING → REFUNDED。

### 状态变更日志

维护`order_log`表，记录每一次状态变更：订单号、旧状态、新状态、操作类型、操作时间。便于排查问题。

### 高频面试问题

#### Q：为什么不能先select查询状态，再update？

并发下两个线程同时select读到WAIT_PAY，一个走支付、一个走关闭，select无法锁数据，会造成状态错乱。**必须把旧状态写在where条件里，依靠数据库原子更新**。

#### Q：订单状态可以直接枚举存储数字吗？

可以，例如：1待支付，2已支付…；代码中维护枚举，数据库存数字，节省存储空间；展示时转文字。

#### Q：终态订单还能修改吗？

CLOSED、FINISHED、REFUNDED是终态，业务不允许再流转；SQL条件会拦截。

### ✨简短背诵版

订单采用状态机设计，包含待支付、已支付、已发货、已完成、已关闭、退款中、已退款。严格限制流转路径；所有状态变更都通过SQL带上旧状态做条件更新，依靠数据库行锁保证原子，禁止先查询再更新，避免并发状态错乱。 部分退款不修改订单主状态，退款信息记录在退款子表，全部金额退完才更新主订单为已退款；同时记录订单变更日志方便排查。已关闭、已完成、已退款属于终态，不再流转。

> 下一题：十二、Redis和MySQL如何保证缓存一致性？



## 十二、Redis与MySQL缓存一致性（面试）

> 以订单库存场景为例。**不存在绝对强一致，互联网追求最终一致性**；缓存和数据库一定会出现短暂窗口不一致，我们做的是减少不一致时间，并且有兜底修复。

### 1、常见错误方案

❌先更新缓存，再更新数据库

> 如果DB更新失败，缓存已经是新值，数据永久不一致。

❌先更新数据库，再更新缓存

> 并发场景：线程A写DB新值，线程B写DB旧值；A更新缓存前，B把旧值写入缓存。缓存里面是旧数据，永久脏数据。

> **所以不建议更新缓存，采用删除缓存模式。**

### 2、标准方案：先更数据库，再删缓存（Cache‑Aside 旁路缓存）

1. 先操作MySQL，更新数据库；
2. 删除Redis缓存，而不是更新缓存；
3. 查询的时候：缓存命中直接返回；缓存未命中，查询DB，回写Redis。

#### 两个问题

##### 问题1：更新DB成功，删除Redis失败

数据库是新数据，缓存还是旧数据，产生脏缓存。 解决：

1. 删除缓存失败，把删除请求发送MQ，异步重试删除缓存；
2. Redis设置过期时间，就算删失败，到期自动失效。

##### 问题2（极小概率并发）：读请求在更新过程中产生脏缓存

1. 线程1读数据，缓存失效，准备读DB；
2. 线程2更新DB，完成，删除缓存；
3. 线程1拿到旧DB数据，回写到Redis。缓存存入旧值。

> 解决方案：**延迟双删**

- 第一步：更新MySQL；
- 第二步：删除缓存；
- 等待一小段时间（几百ms）；
- 第三步，再次删除缓存。 把上面并发场景写进去的旧缓存清理掉。

> 延迟时间大于业务读取数据回写缓存的时间。

#### 3、库存场景特殊：订单系统Redis是预扣缓存

库存场景Redis不是简单查询缓存：

- Redis保存**预扣锁定库存**；MySQL是真实库存。
- **不使用延迟双删**，不能随便删库存缓存。 流程：

1. 大促前把DB库存预热到Redis；

2. 下单Lua预扣Redis；

3. 支付成功才更新MySQL真实库存；

4. 超时关闭订单，Lua脚本释放Redis预扣库存；

5. 依靠定时对账任务修复不一致。

   > 库存不能直接删除Redis，删除会把预扣锁定全部丢掉，业务出错。 库存一致性主要靠定时对账：`DB可售库存 = Redis可售库存 + 待支付订单锁定库存`，不一致以MySQL为准修复Redis。

#### 4、兜底方案（最重要）

1. **给Redis设置TTL过期时间**，就算所有逻辑出错，缓存最多存活TTL时间，最终会失效。
2. **定时任务对账**，以MySQL为准，修复Redis；库存场景核心兜底手段。
3. MQ重试机制处理缓存删除失败。

#### 5、区分强一致和最终一致

- 更新数据库+删除缓存，中间存在短暂不一致窗口，属于**最终一致性**。
- 如果业务需要强一致性，不要用缓存，直接读数据库。

#### 高频面试追问

##### Q：为什么不先删缓存，再更新数据库？

先删缓存，大量并发读请求，缓存失效立刻把旧DB数据写回Redis，造成脏缓存。

##### Q：延迟双删能100%解决吗？

不能，只是极大降低概率，依然有极小窗口，需要TTL+定时任务兜底。

##### Q：库存为什么不能用延迟双删？

Redis里面存放了大量用户预扣锁定库存，如果直接删除Redis，所有锁定全部丢失，会出现超卖。库存靠对账修复。

#### ✨简短背诵版

通用查询缓存采用Cache‑Aside旁路缓存模式：**先更新MySQL，再删除缓存，而不是更新缓存**。 如果删除缓存失败，通过MQ异步重试；为解决并发脏写问题，可以使用延迟双删，同时设置Redis过期时间。 库存场景比较特殊，Redis保存预扣锁定库存，不能随意删除缓存，不使用延迟双删；依靠定时对账任务，以MySQL真实库存为准修复Redis缓存。 缓存方案只能做到最终一致性，无法做到完全实时强一致，强一致场景直接读取数据库。

## 十二、订单系统如何保证一致性？

> 订单系统涉及：订单、库存、优惠券、支付多个服务，数据分布在不同数据库，无法使用本地事务，追求**最终一致性**，不选用性能差的2PC。
> 一致性问题场景：下单成功扣了Redis预扣库存，优惠券冻结成功，但订单DB写入失败；或者支付成功，库存没扣、优惠券没有核销。

### 1、区分两类一致性

1. **本地库内一致性**：同一个数据库多张表，使用MySQL本地事务保证ACID。
例：同一分片内，更新订单状态、插入支付流水，放在同一个事务。

2. **跨服务/跨库最终一致性**：订单、库存、优惠券是不同服务不同数据库。
手段：可靠消息（RocketMQ）、TCC补偿、状态机+定时任务回查。

### 2、下单链路一致性（下单：订单、冻结优惠券、Redis预扣库存）

流程：
1. Redis Lua预扣库存（内存操作）
2. RPC调用优惠券服务做TCC‑Try冻结优惠券
3. 本地事务创建订单（状态：待支付）
> 如果上面任意一步失败，要做回滚：释放Redis库存、解冻优惠券。

> 注意：RPC调用放在本地事务外面，避免大事务。
- 如果订单DB写入失败：手动补偿，释放Redis库存，RPC解冻优惠券。

> 此时MySQL真实库存不变，只是Redis预扣+优惠券冻结。用户还没付钱。

### 3、支付成功链路一致性（最关键）

支付回调MQ消费：订单更新为已支付、扣MySQL真实库存、核销优惠券。
1. MQ收到支付成功消息；
2. **本地事务**：更新订单状态为已支付、插入支付流水；
3. 发送可靠消息，通知库存服务扣真实库存、通知优惠券服务核销优惠券。

> 问题：订单更新成功，消息发送失败 → 库存/优惠券不会处理。
> 解决：**事务消息（RocketMQ事务消息）**
1. 执行本地DB事务（更新订单、支付流水）；
2. 如果本地事务成功，才提交消息，消息投递出去；
3. 如果本地事务回滚，消息不会发出。
> 保证：本地数据库执行成功，则消息一定投递；本地失败，消息不发出。

#### 异常情况

- MQ消息丢失：库存服务收不到扣库存消息。
兜底：定时任务扫描状态=已支付，但库存未扣/优惠券未核销的订单，重新发送消息补偿。
- MQ重复消费：依靠幂等处理（payNo唯一索引、订单状态机update带旧状态）。

### 4、订单超时关闭链路一致性

延时消息触发关闭待支付订单：
1. 状态机把订单更新为CLOSED；
2. 关闭成功后：Lua释放Redis预扣库存；RPC解冻优惠券。

异常：订单关闭DB成功，释放库存/解冻优惠券RPC超时失败。
兜底：定时任务扫描**已关闭，但资源未释放**的订单，再次执行释放资源。

> 一定要判断订单状态，不能盲目重复释放资源。

### 5、退款链路一致性

退款成功：更新订单/退款单状态，回补MySQL库存，退回优惠券。
1. 退款单本地事务更新为退款成功；
2. MQ消息通知库存回补、优惠券退回；
3. 定时任务扫描退款成功但资源未回补的数据做补偿。

### 6、核心兜底手段（状态机+定时回扫）

订单系统最核心：**数据库状态机作为事实来源，定时任务扫描异常数据做补偿**。
不管MQ丢消息、RPC超时、网络抖动，定时任务以订单状态为准，校验关联资源是否匹配，不一致就补偿。

> RPC调用一律不相信返回结果；超时不要直接判定成功/失败，交给定时任务回查。

### 7、不要使用2PC

2PC性能差，同步阻塞，不适合电商高并发订单业务；业务上接受短暂不一致，通过消息+定时任务达到最终一致。

### 高频面试题

#### Q：RPC调用优惠券冻结超时，怎么办？

不要直接认为成功或者失败。订单创建成功，状态=待支付。定时任务回查优惠券冻结状态：
- 如果冻结成功：正常保留；
- 如果冻结失败：关闭订单，释放Redis库存。

#### Q：为什么要用状态机？

所有业务都落地到订单状态，定时任务只需要扫描数据库状态，就可以发现所有异常，做补偿。

### ✨简短背诵版

订单系统分为库内一致性与跨服务最终一致性。同分片内部使用MySQL本地事务保证；订单、库存、优惠券跨服务不使用2PC，采用RocketMQ事务消息保证本地数据库与消息的原子性。
RPC调用出现超时不直接判定结果，依靠订单状态机记录业务状态；通过状态机条件更新防止并发错乱。
利用定时任务扫描异常订单做补偿，处理消息丢失、RPC超时等问题，实现最终一致性。下单阶段只做Redis库存预扣和优惠券冻结；支付成功才扣真实数据库库存；订单关闭、退款场景同样通过消息+定时任务兜底。

## 十三、MQ消息丢失、重复消费、消息乱序如何解决（RocketMQ面试）

> MQ特性：**至少一次投递(at‑least‑once)**，保证消息不丢，但会出现消息重复；不默认保证顺序。

### 一、消息丢失（三个环节都可能丢：生产者、Broker、消费者）

#### 1. 生产者发送消息丢失

1. 使用同步发送，捕获发送异常；不要用单向发送（sendOneWay）。
2. 设置重试发送次数。
3. **事务消息**：半消息、回调检查，保证本地事务和消息发送原子。
> 如果发送返回失败，本地记录日志，定时任务重发。

#### 2. Broker端丢失

1. 开启刷盘机制：同步刷盘（SYNC_FLUSH），消息落盘才返回成功。
2. 集群部署主从，消息同步到从节点，主节点宕机从节点接管。
> 如果异步刷盘，机器断电，内存消息丢失。

#### 3. 消费端丢失（最常见）

错误：**先提交offset，再执行业务逻辑**。业务还没做完，offset提交，消息就算消费完成，如果应用宕机，这条消息丢失。

✅正确顺序：
**执行业务逻辑成功 → 再提交offset**。
业务执行失败，不提交offset，消息会重新投递。

> 注意：不要无限重试，失败要做死信队列处理。

### 二、消息重复消费（至少一次投递必然带来重复）

产生原因：网络抖动，Broker没收到消费成功回执，不断重投同一条消息。
**MQ本身无法杜绝重复，业务层做幂等。**

业务幂等实现手段：
1. **业务唯一ID做幂等key**（payNo、refundNo、requestId、orderNo）。
2. Redis：消费前查key，已存在直接返回成功；业务执行成功写入Redis。
3. **数据库唯一索引**：插入重复直接抛异常，捕获异常返回消费成功。
4. **状态机条件更新SQL（订单最常用）**
```sql
update order_main set status=PAID where order_no=xxx and status=WAIT_PAY
```
影响行数0，代表已经处理过，直接return。

> Redis只做拦截，数据库作为兜底，防止Redis宕机。

### 三、消息乱序

场景：同一个订单产生多条消息，消费顺序错乱，例如先收到退款消息，再收到支付消息，业务出错。

> RocketMQ分区内消息FIFO有序；不同partition之间无序。
> 如果消息分散到不同partition，就会乱序。

✅保证顺序方案：
1. **同一业务标识（orderNo）做哈希，发送到同一个partition**。
发送消息指定`messageQueueSelector`，根据orderNo取模，把同一个订单所有消息发送到同一个分区。
2. 消费端：该partition使用**单线程消费**，不要多线程并发消费同一个队列。

⚠️代价：顺序消息会降低并发能力，同一个业务key只能单线程处理。
> 不要全部消息顺序，只对需要顺序的业务做顺序消息。

### 四、死信队列

消息多次消费一直失败，进入死信队列，避免无限重试阻塞队列。人工排查处理死信消息。

### 高频追问

#### Q：为什么不能做到恰好一次（exactly‑once）？

MQ网络环境不可靠，做不到恰好一次；工业界通用做法：**保证至少一次投递 + 业务幂等**。

#### Q：事务消息解决什么？

解决本地DB事务和发送MQ消息的原子性：本地事务成功，消息一定发出；本地事务失败，消息不发出。不能解决消费端重复。

### ✨简短背诵版

MQ会出现消息丢失、重复、乱序。
1. **消息丢失**：生产者开启重试，不使用单向发送；Broker开启同步刷盘+主从集群；消费端先执行业务成功再提交offset，避免先提交offset后执行业务导致丢失。失败消息进入死信队列。
2. **消息重复**：MQ是至少一次投递，无法避免重复，业务做幂等；依靠业务唯一key、Redis、数据库唯一索引、订单状态机条件更新实现。
3. **消息乱序**：同一个业务orderNo哈希路由到同一个partition；消费端单线程消费该分区，保证消息顺序。
工业界不追求恰好一次，采用至少一次投递加业务幂等实现。

## 十四、秒杀系统如何设计（面试口述）

> 秒杀核心痛点：**瞬间超大流量、热点商品、超卖、数据库压力大；大量无效请求冲击系统**。
> 目标：挡掉绝大部分请求在上游，尽量少的请求落到数据库；保证库存不超卖，防作弊。

### 整体架构分层（由外向内层层拦截）

`前端 → 网关层 → Redis层 → MQ队列 → 后端服务 → MySQL数据库`

### 1、前端层（体验层，不能作为安全依赖）

1. 秒杀按钮时间控制：未到时间按钮置灰，禁止提交；
2. 页面静态化，页面资源放CDN，减轻后端压力；
3. 限制用户频繁点击，按钮点击后置灰防重复提交。

### 2、网关层（Nginx+Sentinel）

1. **限流**：全局限流、用户级限流，限制同一个用户的请求频率；
2. IP黑名单，拦截爬虫、恶意刷接口；
3. 非法参数直接拦截，请求过滤。
> 把大量恶意流量挡在服务外面。

### 3、Redis层（最核心，拦截绝大多数请求）

**秒杀前做库存预热**：提前把MySQL的秒杀商品库存加载到Redis。
使用**Lua脚本原子执行**：判断库存、预扣库存。
- 库存不足直接返回“已抢完”；
- 库存充足，执行预扣，返回成功。

> 绝大部分请求在这里直接返回，不会到后端和数据库。

同时在Redis做：
1. **防重复抢购**：记录用户是否已经抢到该商品；同一个用户不能多次抢到。
2. 热点key优化：库存分片，把一个热点商品拆成多个redis‑key，缓解单Redis节点CPU压力。

> ⚠️Redis这里只是**预扣库存**，不是真实扣数据库库存。

### 4、MQ削峰（异步排队）

Redis预扣库存成功后，并不直接创建订单。
把下单请求丢入RocketMQ队列，前端返回**“排队中，请稍后查看订单”**。
消费端**有限速度消费MQ**，控制数据库写入QPS，保护数据库。

> 作用：削峰填谷，把瞬时高流量变成平稳流量。

### 5、后端消费业务逻辑（MQ消费者）

消费消息执行下单逻辑：
1. 再次校验Redis：确认用户资格、库存；
2. 创建订单，订单状态=待支付；
3. 此时依然**不扣MySQL真实库存**。
4. 设置秒杀订单30分钟未支付自动关闭；超时关闭要释放Redis预扣库存。

### 6、MySQL数据库层（最后一道防线，防止超卖）

1. **支付成功之后，才真正扣减MySQL库存**；update条件扣减，行锁防止超卖。
```sql
update stock set count = count‑#{num} where id=#{id} and count>=#{num};
```
2. 分库分表：秒杀订单量大，订单做分库分表；
3. 禁止大事务，缩短行锁持有时间。

> 即使Redis出现bug，MySQL条件更新依然保证不会超卖。

### 关键问题处理

#### ①如何防止超卖

1. Redis Lua脚本原子预扣；
2. 支付成功MySQL条件update兜底；
3. 订单超时未支付，幂等释放Redis库存；
4. 定时对账：对比Redis预扣库存与MySQL真实库存，以MySQL为准修复Redis。

#### ②如何防少卖

用户抢到之后不付钱，占用Redis预扣库存；通过延时消息+定时任务，30分钟超时释放库存，库存回补Redis，给其他用户抢。

#### ③消息重复、幂等

MQ至少一次投递，消费端使用`requestId`做幂等，Redis记录用户抢购记录，数据库唯一索引兜底。

#### ④热点key问题

秒杀商品是热点key，所有请求打在同一个Redis分片。
解决：库存分片，一个商品拆成多个key；或者本地缓存+Redis两级缓存，避免RedisCPU打满。

#### ⑤超高峰下服务保护

1. 降级：关闭非核心业务（商品推荐、评价等），保障秒杀核心链路；
2. 隔离：秒杀服务独立部署，线程池隔离，不被普通业务拖垮；
3. 监控告警：RedisCPU、MQ堆积、数据库RT、异常率。

### 秒杀和普通下单区别

普通下单：Redis预扣，同步创建订单；
秒杀：Redis预扣成功之后进入MQ异步生成订单，前端返回排队中，平滑数据库写入压力。

### ✨简短背诵版

## 十五、项目线上问题（面试口述，订单/电商背景）

> 准备4‑5个真实感强的线上问题，包含：现象、原因分析、排查思路、解决方案、后续优化，不要只说bug，重点体现排查、复盘优化。

### 问题1：大促期间下单接口RT飙升，部分用户下单失败

**现象**：大促高峰期，下单接口响应时间变长，少量用户下单报错，错误率上升，数据库CPU不高，但数据库行锁等待时间很高。

**排查**
1. 看监控：数据库慢SQL不多，但是Innodb行锁等待时间持续走高；
2. 定位：下单流程RPC调用优惠券服务放在MySQL本地事务内部；RPC网络慢，导致事务长时间不提交，行锁持有时间变长，大量请求排队等待锁，接口RT上涨。

**原因**：把外部RPC调用放在数据库事务里面，造成**大事务**，锁占用时间过长。

**解决方案**
1. 紧急临时：调大线程池，限流保护核心接口；
2. 代码修改：把RPC优惠券冻结移到**事务外面**；事务里面只保留订单表、明细表DB操作；缩小事务范围；
3. 因为RPC在外，调用超时不直接判定失败；订单生成待支付，通过定时任务回查优惠券状态，异常订单关闭释放库存。

**后续优化**
- 增加大事务检测工具；代码评审禁止事务内调用RPC、MQ发送；监控增加行锁等待告警。

### 问题2：Redis缓存和MySQL库存不一致，出现少卖

**现象**：运营反馈有商品，Redis显示库存还有，但用户支付的时候扣DB库存返回库存不足，出现少卖。

**排查**
1. 下单Redis预扣库存成功；后续订单创建后业务异常回滚，只回滚数据库，**忘记释放Redis预扣库存**；Redis库存被锁住，没有释放。
2. Redis里面的可售库存没有回补，造成缓存和MySQL不一致。

**解决方案**
1. 紧急执行定时对账脚本，以MySQL真实库存为准修复Redis；
2. 代码修复：只要下单流程发生异常回滚，必须Lua脚本释放Redis预扣库存；
3. 加固定时对账任务，缩短执行周期，增加不一致告警。

**复盘**：Redis预扣之后，所有分支都要考虑资源释放，不能只考虑正常流程。

### 问题3：支付回调MQ重复消费，存在重复执行业务风险

**现象**：线上日志看到同一条支付消息被多次消费；虽然没有产生脏数据，但日志大量重复，CPU占用变高。

**排查**
第三方支付平台回调超时重试，导致MQ多次投递消息；消费端没有做完整幂等。虽然有状态机update，但是每次都执行全量业务逻辑。

**解决方案**
1. MQ消费端增加Redis以payNo做幂等拦截；
2. 核心依靠订单状态机条件更新SQL：`update ... where status=WAIT_PAY`，update影响行数为0直接return，不再往下执行业务；
3. 支付流水表payNo增加唯一索引，数据库兜底。

**优化**：监控MQ重复消费次数，超过阈值告警。

### 问题4：分库分表场景，后台查询订单接口很慢

**现象**：商家后台查询订单列表接口响应很慢，数据库CPU升高。

**排查**
订单按照user_id哈希分库分表；后台按时间查询全部商家订单，不带分片键user_id，导致**全分片扫描**，每个分片都执行查询，性能很差。

**解决方案**
1. 不通过MySQL做后台列表查询；把订单数据通过binlog同步到ES；
2. 商家后台查询全部订单直接查询ES，MySQL只用于C端用户查询自己的订单（带分片键user_id）；
3. MySQL禁止后台复杂分页、排序查询。

**后续**：上线规范，后台运营类查询一律走ES/数仓，禁止直接查询业务MySQL。

### 问题5：订单延时消息丢失，30分钟未支付订单没有自动关闭

**现象**：部分待支付订单超过30分钟没有关闭，Redis库存一直被占用，库存被锁死。

**排查**
RocketMQ延时消息Broker重启，少量延时消息丢失；只依赖延时消息，没有兜底。订单不会触发关闭逻辑，库存不会释放。

**解决方案**
1. 紧急执行脚本批量关闭超时待支付订单，释放Redis预扣库存；
2. 保留RocketMQ延时消息作为主流程；新增XXL‑Job定时任务作为兜底，每5分钟扫描超时待支付订单；
3. 分库分表环境，每个分片独立扫描或者通过ES查询超时订单；
4. 增加监控告警：待支付订单数量异常上涨告警。

## 十六、你做过哪些性能优化（电商订单项目，面试口述）

从**代码、数据库、缓存、中间件、架构、业务**六个维度来讲，结合前面订单、秒杀项目，有现象+怎么做+收益。

### 1、数据库优化

1. **索引优化**
对订单表`status、create_time、order_no`建立联合索引，消除慢SQL；避免回表；去掉无用索引，减少写入开销。
> 收益：部分查询RT从几百ms降到十几ms。

2. **大事务优化**
把事务内部的RPC调用、MQ发送挪到事务外部；只保留DB操作；缩短事务持有时间，减少行锁等待。
> 解决大促行锁等待高、下单RT抖动问题。

3. **分库分表 + 冷热分离**
订单量大，按`user_id`哈希分库分表；历史旧订单迁移到冷库，热库只保留近3个月数据。避免单表千万级数据带来性能下滑。

4. **读写分离**
C端查询走从库，创建订单、支付更新走主库；商家复杂查询不访问MySQL，同步到ES查询，减轻主库压力。

5. SQL优化：禁止大join、深分页；分页查询改成条件分页，避免`limit 100000,10`。

### 2、Redis缓存优化

1. **热点库存使用Lua脚本**，原子完成库存预扣，减少网络往返，防止超卖。
2. **热点key优化**：秒杀商品做库存分片，把一个热点key拆分成多个key，避免单节点CPU打满。
3. 合理设置过期时间；库存场景增加定时对账任务，修复缓存与DB不一致。
4. 避免大key，不存过大对象；序列化优化，减少网络传输。
5. 利用Redis实现接口幂等、防重复抢购。

### 3、MQ中间件优化

1. 异步化改造：短信、通知、积分等非核心逻辑使用RocketMQ异步，缩短下单主链路。
2. 消费端优化：合理设置分区数提升并行消费；消息堆积监控告警；失败消息进入死信队列。
3. 顺序消息：同一orderNo哈希路由到同一个partition，单线程消费，保证订单消息顺序。
4. 使用事务消息保证本地事务与消息投递原子性；消费逻辑：**先执行业务，后提交offset**，防止消息丢失。

### 4、代码 & JVM优化

1. **线程池隔离**：下单接口独立线程池，和普通业务隔离，避免一个业务耗尽线程池拖垮整个服务。
2. 减少对象创建，循环内不重复创建对象；使用StringBuilder，避免频繁字符串拼接。
3. JVM调优：根据服务内存调整堆大小；选择合适垃圾收集器；优化GC，降低Full GC频率；监控GC指标。
4. 接口降级：大促关闭非核心功能，保障下单核心链路。

### 5、架构层面优化

1. 网关层增加限流、IP黑名单，拦截无效请求，保护后端服务。
2. 秒杀场景增加MQ削峰；Redis预扣拦截大部分请求，异步生成订单，保护数据库。
3. 分库分表解决单库单表性能瓶颈；ES承接复杂检索，卸载MySQL压力。
4. 增加监控：接口RT、异常率、线程池队列、MQ堆积、数据库行锁等待、慢SQL告警。

### 6、业务层面优化

1. 订单30分钟未支付，延时消息+定时任务双重兜底，及时释放预扣库存。
2. 接口增加幂等处理，防止重复请求带来重复DB操作。
3. 冷热数据分离，归档历史订单，减少热库数据量。

## 十七、项目难点（电商订单秒杀项目，面试口述）

> 讲2‑3个核心难点，每个包含：**难点是什么、存在什么问题、我的解决方案、收获**，尽量贴合前面的业务，不要空洞。

### 难点一：高并发下订单、库存、优惠券跨服务的数据一致性问题

**难点**
下单、支付、退款链路，订单、库存、优惠券属于不同微服务，跨库不能使用本地事务。
RPC调用存在超时、网络抖动；MQ可能丢失、重复。不能用2PC，性能太低不适合大促高并发。如果处理不好，会出现：库存冻结了订单没生成；支付成功库存没扣；退款成功库存没有回补，造成超卖、少卖、资金异常。

**解决方案**
1. 采用**最终一致性方案**，RocketMQ事务消息保证本地DB事务和消息投递的原子性。
2. RPC调用超时不直接判定成功或者失败，不盲目回滚或者提交；以数据库**订单状态机作为唯一事实依据**。
3. 所有异常场景依靠定时任务扫描补偿：扫描已支付但库存未扣、已关闭但资源未释放、退款成功库存未回补的订单，重新发起补偿。
4. 业务上分层：下单只做Redis库存预扣、优惠券冻结；**支付成功才扣MySQL真实库存**；所有状态变更使用带旧条件的update，防止并发状态错乱。
5. MQ消费端做幂等，处理消息重复消费。

**收获**：分布式场景不要强依赖RPC返回值，以数据库状态机为基石，消息+定时任务兜底实现最终一致性。

### 难点二：秒杀场景流量削峰，防止超卖，同时避免少卖

**难点**
秒杀瞬间流量巨大，大量请求打到系统；热点商品是Redis热点key；要保证不能超卖；同时用户抢到不付款会占用库存，又不能出现少卖。如果全部请求直接写库，数据库会被打垮。单纯依靠Redis也会有缓存和DB不一致风险。

**解决方案**
1. 多层拦截：前端、网关限流过滤无效请求；秒杀前把库存预热到Redis。
2. 使用Lua脚本原子完成库存预扣，大部分请求在Redis层直接拦截。热点商品做库存分片，解决热点key打满单节点CPU。
3. Redis预扣成功之后请求进入MQ队列异步生成订单，前端返回排队中，削峰，控制数据库写入QPS。
4. **支付成功才执行MySQL条件update扣真实库存，数据库行锁兜底防超卖**。
5. 30分钟未支付订单，延时消息+定时任务双重兜底，释放Redis预扣库存，避免少卖。
6. 定时对账，以MySQL为准修复Redis，处理缓存不一致。

**收获**：高并发系统要层层拦截保护数据库；缓存只做前置，数据库作为最终真相源。

### 难点三：分库分表带来的各类问题改造

**难点**
订单量持续上涨，单表千万级别，需要做分库分表。分片键选`user_id`之后带来一堆问题：
1. 通过order_no查询不知道userId，无法定位分片；
2. 商家后台不带分片键查询订单，会全分片扫描，性能极差；
3. 跨分片不能join，数据库唯一索引失效；扩容、DDL风险大。

**解决方案**
1. 使用Sharding‑JDBC，按`user_id`哈希分片；订单主表、明细表、退款流水统一分片键，保证同分片本地join。
2. binlog同步订单数据到ES，**商家后台所有列表查询全部走ES**，业务MySQL只负责C端用户查询自己订单。
3. 通过order_no查询走ES获取userId再路由查询MySQL。
4. 做冷热分离，历史订单迁移冷库，热库只保留近3个月数据，减轻分片压力。
5. 跨分片不使用分布式事务，业务改成最终一致性；DDL灰度执行。

**收获**：分库分表不能只解决存储，还要配套检索方案；不是所有查询都放数据库。

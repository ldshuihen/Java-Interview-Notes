





### WebMvcConfigurer

#### 一、是什么

`WebMvcConfigurer` 是 **SpringMVC提供的接口**，用来**扩展、自定义SpringMVC的配置**，**不会覆盖SpringBoot MVC自动配置**（重点！）。

> Spring5之后全部是default默认方法，**不需要重写全部方法，想用哪个就重写哪个**。
> 旧版本 `WebMvcConfigurerAdapter` 已经废弃，**不要再用**。

> ⚠️ 关键区分：
>
>
> - `WebMvcConfigurer`：**扩展MVC**，保留Boot自动配置，推荐日常开发使用。
> - `WebMvcConfigurationSupport`：完全接管MVC，**会让SpringBoot的WebMvcAutoConfiguration自动配置失效**，谨慎使用。
> - 如果加了`@EnableWebMvc`，也会完全接管MVC，**丢失Boot自动配置**，业务项目一般不加。

一句话总结：**WebMvcConfigurer 是SpringMVC的扩展回调接口，用来添加自定义Web能力，不破坏Boot默认配置**。

#### 二、常用方法（面试必背，附场景）

```
@Configuration
public class MvcConfig implements WebMvcConfigurer {
```

1. **addCorsMappings(CorsRegistry registry)**
   全局跨域配置，就是刚才跨域那道题用到的，配置全局CORS响应头。

```
@Override
public void addCorsMappings(CorsRegistry registry) {
    registry.addMapping("/**")
            .allowedOriginPatterns("[http://localhost:8080](http://localhost:8080)")
            .allowedMethods("GET","POST","PUT","DELETE","OPTIONS")
            .allowCredentials(true)
            .maxAge(3600);
}
```

2. **addInterceptors(InterceptorRegistry registry)** ✅高频
   注册自定义拦截器（Interceptor），做登录校验、token校验、请求日志、接口限流。> 

> 注意：拦截器**不能拦截静态资源**，可以在这里配置excludePathPatterns排除路径。
> 区分：拦截器是SpringMVC层；Filter过滤器是Servlet层，优先级更高。

```
@Override
public void addInterceptors(InterceptorRegistry registry) {
    registry.addInterceptor(new LoginInterceptor())
            .addPathPatterns("/**")
            .excludePathPatterns("/api/login","/static/**");
}
```

3. **addResourceHandlers(ResourceHandlerRegistry registry)** ✅高频
   **静态资源映射**。自定义静态资源访问路径，比如图片、文件上传后的访问地址。
   例如：访问`/upload/**`映射到服务器本地磁盘路径。

```
@Override
public void addResourceHandlers(ResourceHandlerRegistry registry) {
    registry.addResourceHandler("/upload/**")
            .addResourceLocations("file:D:/upload/");
}
```

4. **addFormatters(FormatterRegistry registry)**
   注册自定义转换器、格式化器。比如字符串转日期、枚举转换，前端传字符串自动转Java实体类日期。
5. **addArgumentResolvers(List resolvers)**
   自定义**方法参数解析器**。最常用场景：自定义注解获取当前登录用户信息，把token解析后的用户对象直接注入Controller入参。
6. **addReturnValueHandlers(List handlers)**
   自定义返回值处理器，统一包装controller返回结果。
7. **addViewControllers(ViewControllerRegistry registry)**
   简单页面跳转，**不用写Controller**，直接URL映射到视图页面。
   例：访问`/`直接跳转到`index.html`。
8. **configureViewResolvers**：自定义视图解析器
9. **configureAsyncSupport**：配置异步请求
10. **configurePathMatch**：路径匹配规则（是否开启后缀模式匹配等）

#### 三、执行顺序 & 优先级（面试追问）

1. Filter（Servlet过滤器，CorsFilter属于这一层）
2. DispatcherServlet
3. Interceptor（WebMvcConfigurer注册的拦截器）
4. Controller> 

> 优先级：**CorsFilter过滤器 > @CrossOrigin注解 > WebMvcConfigurer#addCorsMappings全局跨域**

#### 四、面试高频坑点

1. 实现`WebMvcConfigurer`，**不要加@EnableWebMvc**，加了就会禁用SpringBoot自动MVC配置，很多默认功能失效。
2. 拦截器只能拦截Controller接口，**不能拦截静态资源**，静态资源由ResourceHandler处理；Filter可以拦截所有请求。
3. WebMvcConfigurer里面配置的是**MVC层面组件**，不属于Servlet。
4. SpringBoot2.4+跨域推荐 `allowedOriginPatterns`，而不是`allowedOrigins`，支持域名通配。

WebMvcConfigurer是SpringMVC的扩展接口，用来自定义MVC配置，**不会覆盖SpringBoot的Web自动配置**，Spring5后用default方法，不需要重写全部方法。
常用方法：addCorsMappings全局跨域；addInterceptors注册拦截器，做token登录校验；addResourceHandlers配置静态资源映射；addArgumentResolvers自定义参数解析器。

### CorsFilter

#### 一、是什么

`CorsFilter` 是Spring框架内置的**Servlet过滤器（Filter）**，包路径 `org.springframework.web.filter.CorsFilter`，专门用来处理CORS跨域。

> 继承 `OncePerRequestFilter`，保证**一次请求只会执行一次**。
> 属于**Servlet层**，在DispatcherServlet、拦截器、Controller**之前执行**。

✅ 核心优势：
预检OPTIONS请求**不需要走到Controller**，在Filter层直接返回跨域响应头，性能更好；
**Spring Security项目首选**，因为Security的认证过滤器在MVC层之前，MVC的addCorsMappings配置会被Security拦截器挡住，导致OPTIONS预检请求401，用CorsFilter可以**在认证过滤器之前处理跨域**。

#### 二、完整代码（SpringBoot）

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.cors.CorsConfiguration;
import org.springframework.web.cors.UrlBasedCorsConfigurationSource;
import org.springframework.web.filter.CorsFilter;

@Configuration
public class CorsConfig {

    @Bean
    public CorsFilter corsFilter() {
        // 1. 跨域配置对象
        CorsConfiguration config = new CorsConfiguration();
        // 允许的前端源，SpringBoot2.4+推荐allowedOriginPatterns支持通配
        config.addAllowedOriginPattern("[http://localhost:8080](http://localhost:8080)");
        // 允许所有请求头
        config.addAllowedHeader("*");
        // 允许所有请求方法
        config.addAllowedMethod("*");
        // 允许携带Cookie，开启后不能写*作为Origin
        config.setAllowCredentials(true);
        // OPTIONS预检请求缓存时间，单位秒
        config.setMaxAge(3600L);

        // 2. 注册URL映射关系
        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", config);

        // 3. 构建CorsFilter
        return new CorsFilter(source);
    }
}
```

> 如果想**强制CorsFilter优先级最高**，可以包一层`FilterRegistrationBean`设置`Ordered.HIGHEST_PRECEDENCE`。

#### 三、执行流程

1. 浏览器发来跨域请求（OPTIONS预检/真实请求）
2. 请求先进入Tomcat的Filter链，**CorsFilter最先执行**
3. 读取`UrlBasedCorsConfigurationSource`获取对应路径的Cors配置
4. 判断Origin是否放行；如果是OPTIONS预检，直接填充CORS响应头，**直接返回，不继续走后面过滤器和Controller**
5. 非预检请求，添加响应头，放行请求继续向后执行

> 关键点：OPTIONS预检请求**不会进入Controller**，在Filter直接返回。
> 而WebMvcConfigurer#addCorsMappings是在DispatcherServlet内部的HandlerMapping层面处理，请求会走到MVC层。

#### 四、三种跨域方式优先级（面试必背）

**CorsFilter（Servlet过滤器） > @CrossOrigin注解 > WebMvcConfigurer#addCorsMappings（MVC全局）**

> 同时配置多个，**优先级高的生效**。

#### 五、CorsFilter vs WebMvcConfigurer#addCorsMappings

| 对比项             | CorsFilter                       | WebMvcConfigurer addCorsMappings             |
| ------------------ | -------------------------------- | -------------------------------------------- |
| 所属层             | Servlet Filter层                 | MVC层（DispatcherServlet内部）               |
| 执行时机           | 更早，在DispatcherServlet之前    | DispatcherServlet内部，匹配handler之后       |
| OPTIONS预检        | 直接在Filter返回，不进Controller | 会走到MVC层处理                              |
| SpringSecurity场景 | 推荐，可在认证前处理OPTIONS      | 容易OPTIONS预检401，因为Security拦截器先执行 |
| 适用范围           | 全部请求，包括静态资源           | 仅进入SpringMVC的Controller请求              |

#### 六、面试高频坑点

1. `setAllowCredentials(true)`开启携带Cookie，**不能写addAllowedOrigin("*")**，必须指定具体域名或用`allowedOriginPatterns`。
2. Spring Security项目，**优先CorsFilter**，否则OPTIONS预检请求会被认证拦截直接401。
3. CorsFilter是**Servlet过滤器**，和普通Filter一样，是全局的，不属于MVC拦截器。
4. 不要同时配置多套跨域（CorsFilter+WebMvc+@CrossOrigin），容易出现配置冲突。

#### 注意

1. 包路径：`org.springframework.web.filter.CorsFilter`，来自**spring-web**包（SpringMVC 核心包），**不是 spring-security 包**。只要项目引入 spring-boot-starter-web，就自带这个类，不需要引入 Security 依赖。
2. 使用场景区分：
   - 无 Security 项目：CorsFilter 和 WebMvcConfigurer 的跨域两种方案任选其一都行。
     - CorsFilter：Servlet 层，更早执行；OPTIONS 预检直接在过滤器返回，不进入 MVC。
     - WebMvcConfigurer#addCorsMappings：MVC 层，在 DispatcherServlet 内部处理。
   - 有 Security 项目：**优先推荐 CorsFilter**，解决 OPTIONS 预检被安全拦截 401 的问题。
3. 注意：**不要同时启用两套全局跨域配置**（同时注册 CorsFilter + WebMvcConfigurer 的 addCorsMappings），会出现配置冲突，以优先级更高的 CorsFilter 为准，容易造成混淆。

#### 七、45秒口述背诵版

CorsFilter是Spring内置的Servlet过滤器，属于Servlet层，在DispatcherServlet、Controller之前执行，优先级最高。
它可以提前处理OPTIONS预检请求，直接返回跨域响应头，不用走到Controller。在整合Spring Security场景推荐使用，能在认证过滤器之前放行预检请求，避免OPTIONS报401。
对比WebMvcConfigurer的跨域配置，后者是MVC内部处理，执行时机靠后。三者优先级：CorsFilter > @CrossOrigin > WebMvcConfigurer全局跨域。

### 生产环境跨域方案选型 & 是否结合使用

> 核心结论先说：**生产优先 Nginx反向代理；其次后端CORS（CorsFilter）；严禁多套CORS配置同时叠加。不要结合CorsFilter + WebMvcConfigurer两套全局跨域**

#### 一、三种方案生产对比

##### 1. Nginx反向代理【生产首选，推荐】

原理：前端页面和接口**同源**，浏览器根本不会触发跨域，**完全规避CORS**，不需要后端写任何跨域代码。

- 适用：前后端分离项目，Vue/React打包静态资源放Nginx
- 优点：
  1. 不依赖后端代码，跨域问题在网关层解决；后端代码不用处理CORS，减少线上bug
  2. 统一做限流、ssl、gzip、静态资源缓存、路由分发
  3. OPTIONS预检请求不会到达后端服务，减轻后端压力
- 缺点：需要维护Nginx配置；多服务微服务场景要维护代理规则
- 典型Nginx配置：

```nginx
server {
    listen 80;
    server_name api.example.com;
    # 前端静态页面
    location / {
        root /data/frontend;
        index index.html;
        try_files $uri $uri/ /index.html;
    }
    # 接口转发
    location /api/ {
        proxy_pass [http://127.0.0.1:9090/](http://127.0.0.1:9090/);
    }
}
```

##### 2. 后端CORS方案（CorsFilter）【备选，无Nginx/微服务网关场景】

> 适用场景：没有Nginx、微服务直接暴露公网，没有网关。
> ✅ 推荐用 CorsFilter，**不要用WebMvcConfigurer全局跨域**

- 理由：
  - Servlet层处理，OPTIONS预检请求在过滤器直接返回，不会进入MVC、Controller，性能更好
  - 统一全局控制，支持统一域名白名单
  - 如果后续接入Spring Security，不用大改代码
- 缺点：后端服务要处理OPTIONS预检请求；多实例部署每个服务都要配置CORS

##### 3. WebMvcConfigurer#addCorsMappings【生产不推荐作为全局方案】

- 执行时机靠后，OPTIONS请求会走到DispatcherServlet；
- 如果项目有全局拦截器、全局异常处理器，很容易把OPTIONS预检请求拦截掉，出现401/403；
- 只对进入SpringMVC的Controller生效，静态资源的跨域不会处理。

> `@CrossOrigin`：只适合单个接口临时调试，**生产不要大面积使用**，配置分散，不好统一管理域名白名单。

#### 二、能不能结合使用？

##### ❌ 禁止：CorsFilter + WebMvcConfigurer 两套全局CORS一起写

两者都配置全局跨域，**CorsFilter优先级更高，WebMvcConfigurer的跨域配置直接失效**，代码冗余，容易造成维护混乱，后续改配置不知道哪套生效。

##### ✅ 允许的组合：Nginx + 后端保留最小CORS兜底

> 生产常用组合：Nginx做反向代理（主方案，消除跨域），后端**保留CorsFilter作为兜底**

- 什么时候生效：正常走Nginx代理，同源，CORS代码完全不触发；
- 当有场景绕过Nginx直接访问后端接口（比如内网调试、服务内部测试），后端CorsFilter兜底处理跨域；

> 注意：Nginx代理场景下，后端CORS配置**不要冲突**，域名白名单保持一致。

> ⚠️ 不推荐：Nginx上直接配置`add_header`响应头做CORS。
> 坑：Nginx的add_header默认只在2xx/3xx响应添加头；401/404/500错误响应不会带上跨域头，容易出现异常场景跨域失败。

#### 三、微服务场景补充（SpringCloud）

微服务架构优先**网关层（Gateway/SpringCloud Gateway）统一配置CORS**，所有微服务本身**不再配置任何跨域**。
Gateway底层也是类似CorsFilter，在网关统一处理跨域，所有下游微服务不用关心跨域。

#### 四、选型一句话总结

1. 单体项目有Nginx：**首选Nginx反向代理，从根源消除跨域；后端可保留CorsFilter兜底**
2. 无Nginx、直接暴露后端服务：**后端使用CorsFilter全局CORS，不要WebMvcConfigurer全局跨域**
3. 微服务：**网关统一处理跨域，业务微服务不配置跨域**
4. 禁止同时启用两套全局CORS配置（CorsFilter + WebMvcConfigurer）

#### 45秒面试口述版

生产环境优先Nginx反向代理，让前后端同源，直接避免跨域，不需要后端CORS代码。如果没有Nginx，直接暴露后端服务，就使用CorsFilter实现CORS，不推荐WebMvcConfigurer做全局跨域。
不建议CorsFilter和WebMvcConfigurer两套全局跨域一起配置，会冗余且容易混淆。可以Nginx做主方案，后端CorsFilter做兜底。微服务项目则在Gateway网关统一处理跨域，业务服务不配置跨域。

### Gateway网关跨域

Spring Cloud Gateway 默认是 **WebFlux（响应式、非阻塞）**，不是SpringMVC（Servlet阻塞模型）。
`WebMvcConfigurer` 是SpringMVC的接口，只适用于`spring-boot-starter-web`，**在WebFlux网关中直接写WebMvcConfigurer不会生效，甚至启动报错**（MVC和WebFlux冲突）。

#### 方案1：yml配置全局CORS（生产推荐，最简单）

Gateway自带`globalcors`全局跨域配置，**不需要写Java代码**。
```yaml
spring:
  cloud:
    gateway:
      globalcors:
        # 必须开启，OPTIONS预检请求才会被处理
        add-to-simple-url-handler-mapping: true
        cors-configurations:
          '[/**]':
            allowedOriginPatterns: "[http://localhost:8080](http://localhost:8080)"
            allowedMethods:
              - GET
              - POST
              - PUT
              - DELETE
              - OPTIONS
            allowedHeaders: "*"
            allowCredentials: true
            maxAge: 3600
```
> 核心：`add-to-simple-url-handler-mapping: true`，解决OPTIONS预检请求路由不匹配直接403的坑。

#### 方案2：Java代码方式：WebFlux对应的 `WebFluxConfigurer` 或者 `CorsWebFilter`

Gateway是WebFlux，对应的接口不是WebMvcConfigurer，而是**WebFluxConfigurer**；过滤器是`CorsWebFilter`（不是Servlet的CorsFilter）。
```java
@Configuration
public class CorsConfig {
    @Bean
    public CorsWebFilter corsWebFilter() {
        CorsConfiguration config = new CorsConfiguration();
        config.addAllowedOriginPattern("[http://localhost:8080](http://localhost:8080)");
        config.setAllowCredentials(true);
        config.addAllowedMethod("*");
        config.addAllowedHeader("*");
        config.setMaxAge(3600L);

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", config);
        return new CorsWebFilter(source);
    }
}
```
> ✅ `CorsWebFilter`：WebFlux响应式的跨域过滤器，**不是Servlet的CorsFilter**，包不一样，不要搞混。

#### 核心区分（面试必背）

1. **单体SpringBoot（Servlet MVC）**：
    - 接口：`WebMvcConfigurer`
    - 过滤器：`CorsFilter`（servlet的，spring-web）
2. **SpringCloud Gateway（默认WebFlux响应式）**：
    - 接口：`WebFluxConfigurer`（不是WebMvcConfigurer）
    - 过滤器：`CorsWebFilter`（webflux包）
    - 推荐：yml globalcors配置，最简单

#### 重要架构约定

> **网关统一处理跨域，下游所有微服务必须删掉全部CORS配置（CorsFilter、@CrossOrigin、WebMvcConfigurer跨域）**
> 如果网关和下游服务同时配置跨域，**响应头会重复，浏览器会报错**。

#### 45秒口述背诵版

SpringCloud Gateway默认基于WebFlux响应式，**不能用WebMvcConfigurer**，WebMvcConfigurer属于SpringMVC Servlet模型，放到网关里无效，还会冲突。
Gateway跨域优先用yml的globalcors全局配置；代码方式使用CorsWebFilter或者WebFluxConfigurer。
微服务架构中，跨域只在网关统一处理，下游业务微服务不要配置任何CORS，防止响应头重复引发浏览器跨域报错。

#### 面试官高频追问

1. WebMvcConfigurer 和 WebFluxConfigurer 的区别？
> WebMvcConfigurer是SpringMVC阻塞IO、Servlet模型；WebFluxConfigurer是WebFlux响应式非阻塞模型，Gateway默认WebFlux。两者不能混用。

2. Gateway的CorsWebFilter和普通SpringBoot的CorsFilter区别？
> CorsFilter是Servlet过滤器，属于spring-web；CorsWebFilter是WebFlux的响应式过滤器，属于spring-webflux，底层完全不一样，不能互换。

### Nginx跨域 vs Gateway CorsWebFilter / WebFluxConfigurer 跨域 

> 先明确：**CorsWebConfigurer不存在，是WebFluxConfigurer**，Gateway是WebFlux响应式，没有Servlet那套CorsFilter。
> 两种模式只能二选一，不能同时配置CORS响应头，否则重复header浏览器报错。

#### 一、Nginx层做跨域（Nginx add_header方式）

> 适用：请求 → Nginx → Gateway → 微服务
**流程：**
1. 浏览器发起跨域请求（非简单请求先发OPTIONS预检）
2. 请求到达Nginx
3. Nginx直接在**Nginx这一层**添加 `Access-Control-*` 响应头
4. Nginx把请求转发给Gateway，Gateway再转发给后端微服务
5. 业务处理完成，响应原路返回，**Nginx追加的跨域头返回给浏览器**
6. 浏览器校验响应头，通过则放行请求

⚠️ 重点坑：
Nginx `add_header` 默认**只对2xx/3xx成功响应添加头；4xx、5xx异常响应默认不带跨域头**，会出现接口报错时跨域失败。
> 此时 **Gateway、所有微服务必须关闭CORS配置**，不能输出跨域响应头，防止重复header。

> 注意区分：Nginx**反向代理同源方案**≠Nginx跨域。同源方案根本不触发跨域，不需要add_header。下面讲的是Nginx用add_header主动配置CORS的流程。

#### 二、Gateway层跨域（CorsWebFilter / WebFluxConfigurer / yml globalcors）

> 请求 → Nginx（只转发，不加任何跨域头） → Gateway → 微服务
**流程：**
1. 浏览器发起跨域请求，OPTIONS预检请求先到达Nginx
2. Nginx只做proxy_pass转发，**不添加任何Access-Control响应头**
3. 请求到达Gateway，Gateway的`CorsWebFilter`（WebFlux响应式过滤器，在网关最前面执行）
4. CorsWebFilter校验请求Origin：
   - 如果是OPTIONS预检：网关直接组装CORS响应头，**直接返回，不转发请求到下游微服务**
   - 如果是真实业务请求：校验Origin合法，在响应上添加跨域头，再转发请求到下游微服务
5. 下游微服务处理业务，返回结果
6. 响应回到Gateway，带上网关生成的CORS响应头，经过Nginx原样返回浏览器
7. 浏览器校验跨域头，放行

> WebFluxConfigurer本质和yml globalcors底层最终也是生成CorsWebFilter，只是配置写法不同，**执行流程完全一致**。

✅ 关键点：OPTIONS预检请求在Gateway层直接终止，**不会转发到业务微服务**，减轻下游压力。
> 此时：Nginx不能加add_header跨域头；下游微服务全部删除CORS代码。

#### 三、两者核心流程对比

|项目|Nginx add_header跨域|Gateway CorsWebFilter跨域|
| ---- | ---- | ---- |
|CORS头生成位置|Nginx|Gateway网关|
|OPTIONS预检处理|Nginx转发请求到后端，由后端处理OPTIONS|Gateway直接拦截OPTIONS，不转发下游|
|异常响应(401/500)|默认不带跨域头，容易失败|统一由网关处理，异常响应也能带上跨域头|
|适用场景|简单静态页面，错误码少的场景|微服务、统一鉴权、统一异常处理，生产更推荐|
|底层模型|Nginx七层|WebFlux响应式|

#### 四、45秒口述背诵版

Nginx做跨域，是请求到达Nginx后，Nginx通过add_header添加CORS响应头，再转发请求到网关，异常响应容易丢失跨域头。
Gateway使用CorsWebFilter跨域，Nginx只做转发，不添加跨域头。请求到达网关，CorsWebFilter最先执行；OPTIONS预检请求在网关直接返回跨域头，**不转发到下游微服务**。WebFluxConfigurer和yml全局跨域底层都是CorsWebFilter，执行流程一样。
两种方案只能选一层处理跨域，不能同时配置，否则会出现重复跨域响应头，浏览器报错。

> OPTIONS预检请求不需要走到下游微服务，网关直接返回，减少下游服务压力。Nginx add_header方案会把OPTIONS请求转发到网关。

> WebFluxConfigurer是配置接口；CorsWebFilter是过滤器Bean。yml的globalcors底层最终也是构建CorsWebFilter，执行流程一致，只是配置方式不同。

# Milvus 

完整详解（面试+RAG项目实战版）

Milvus 是 Zilliz 开源、LF AI 基金会毕业的**云原生分布式向量数据库**，Apache2.0协议，专门用于海量 Embedding 向量的近似最近邻检索ANN，支撑RAG、语义搜索、多模态检索、推荐系统，支持亿~万亿级向量规模。
> 你的HRMS项目：制度文档embedding存入Milvus，HNSW索引做向量检索，叠加标量过滤`access_level`实现职级权限隔离，同时做熔断降级到本地内存向量做容灾。



## 一、三大部署模式
|模式|适用场景|说明|
|---|---|---|
|Milvus Lite|原型开发、本地测试、边缘端|Python库，不需要额外服务，**不适合生产**，内存内运行|
|Milvus Standalone（单机）|中小规模生产、测试环境|Docker一键部署，组件打包，依赖MinIO+etcd；千万级向量够用|
|Milvus Distributed（分布式集群）|线上生产、亿级向量，K8s部署|存算分离，组件可独立水平扩缩容；依赖etcd、MinIO/S3、Pulsar/Kafka|

> 注意：单机不能直接在线升级分布式集群。

## 二、核心架构（2.x版本，存算分离）
整体分为四层：**访问层、协调层、工作节点层、持久化存储层**。
### 1）访问层：Proxy（无状态）
- 对外统一接入网关，接收SDK/HTTP请求；做鉴权、请求路由、结果聚合合并。
- 可以多实例水平扩容提升QPS。

### 2）协调层 Coordinator（集群大脑）
1. **RootCoord**：管理Collection、Partition元数据，DDL操作（建表、删表）。
2. **DataCoord**：管控数据分片segment，分配DataNode任务，管理flush、compaction、建索引任务。
3. **QueryCoord**：管理查询负载，分配segment给QueryNode，负载均衡，副本调度。

### 3）工作节点 Worker Nodes（实际干活）
1. **DataNode**：消费消息队列，把增量日志flush成segment，执行compaction合并小segment、构建向量索引，写入对象存储。
2. **QueryNode**：加载segment+索引到内存，**执行向量检索、标量过滤查询**；多副本实现高可用。
3. **IndexNode**：专门离线构建大索引，卸压查询节点。
4. **StreamingNode（2.6新增）**：独立处理实时增量流数据，读写解耦，故障恢复更稳。

### 4）持久化存储三组件（外部依赖）
1. **MetaStore(etcd)**：存储元数据：schema、分片信息、服务注册发现；强一致、少量数据。
2. **LogBroker（Pulsar/Kafka/RocksDB）**：WAL预写日志，所有插入删除先写消息队列；实现流、故障回放恢复；单机模式内置RocksDB。
3. **ObjectStorage（MinIO/S3）**：真正存储向量数据、索引文件、快照；大文件持久化。

> 核心设计理念：**Log‑as‑Data**，所有写入先走消息队列，再异步落盘对象存储。

### 写入流程
1. 客户端插入向量 → Proxy接收；
2. Proxy写数据到LogBroker（WAL日志，保证不丢）；
3. DataNode消费消息队列，攒批flush生成Segment；
4. DataNode后台compaction合并小segment，构建索引写入对象存储；
5. QueryNode加载segment+索引到内存对外提供检索。

> Segment：Milvus最小数据单元；数据不断写入会生成很多小segment，compaction合并大segment提升查询性能。

## 三、Milvus数据模型（核心概念）
1. **Collection集合**：相当于MySQL的Table，存放一批向量；定义Schema，包含多个字段。
    - 字段类型：主键、标量（int/bool/string/json/array）、**向量字段(FLOAT_VECTOR)**
2. **Partition分区**：Collection内逻辑分片，做数据隔离；可以按业务时间、租户划分，加速过滤。
3. **Entity实体**：相当于一行记录，包含主键、标量元数据、向量。
4. **Segment**：物理存储分片，只读；分为**增长段（growing，内存增量）、密封段(sealed，落盘构建索引)**。

> 你的项目：每个制度文档对应一条Entity；向量字段存embedding；标量字段存`access_level`（职级权限）、文档id、文件名；检索时`access_level <= userAccessLevel`做过滤。

## 四、索引体系（重点，面试高频）
索引分**向量索引（ANN近似检索）** + **标量索引（元数据过滤）**。
> ANN近似检索：牺牲少量召回率换取速度，**不做全量暴力比对**。

### 向量索引分类与选型
|索引类型|类别|核心特点|适用场景|
|---|---|---|---|
|FLAT|暴力全量|精确检索，100%召回，慢|十万以内小数据集|
|IVF_FLAT|倒排聚类|聚类分桶，内存适中|千万级，追求速度内存平衡|
|IVF_SQ8|倒排+标量量化|向量压缩，省内存|内存资源紧张，接受轻微召回损失|
|IVF_PQ|倒排+乘积量化|高压缩，速度快，召回下降|超大库，对精度容忍高|
|**HNSW**|分层图索引|查询极快，高并发；内存消耗大|✅**你的RAG生产首选**，百万‑千万，高QPS；缺点：建索引耗内存|
|DISKANN|磁盘索引|索引放磁盘，少占内存|十亿级超大向量，内存有限场景|

#### HNSW关键参数（你项目使用）
1. `M`：每层节点邻居数量；默认16；M越大图越稠密，召回越高，内存占用上升。
2. `efConstruction`：建索引阶段候选邻居数；越大索引质量越好，构建越慢。
3. 查询参数`ef`：检索时候选集大小，ef越大召回越高，延迟越高。

> 你的业务：HNSW做dense向量召回；再并发本地BM25关键词检索，RRF算法融合两路结果，解决纯向量对数字、专有名词召回差的问题。

### 标量索引
针对int、string、bool、json元数据字段，加速过滤条件，例如你的`access_level<=xxx`。
- `Trie`、`Sorted`、`Inverted倒排索引`；**建立标量索引后，filter过滤性能大幅提升**。

### 距离度量方式
1. **L2（欧氏距离）**：越小越相似；
2. **IP（内积）**：向量归一化等价余弦相似度；**RAG场景绝大多数使用IP**。

## 五、核心功能
1. **混合检索（Hybrid Search）**：向量ANN检索 + 标量过滤同时执行；`expr`表达式过滤元数据，你的权限隔离就是该能力。
> ⚠️坑：Milvus过滤逻辑：先向量召回候选集，再执行标量过滤；如果过滤条件筛掉大量候选，召回率会下降，需要调大TopK。
2. **多向量检索**：一个Entity支持多个向量字段，可以同时检索多组向量打分。
3. **稀疏向量检索**：原生支持BM25稀疏索引，不再需要外置Elasticsearch做关键词；2.4+支持。
4. **一致性级别**：4种：强一致、会话、有界过期、最终一致性；RAG一般选**Bounded Staleness有界过期**，兼顾性能与一致性。
5. **副本Replication**：同一个segment加载多份到不同QueryNode，实现查询高可用，节点故障自动切换。
6. **动态字段**：schema不用预先定义，直接写入JSON动态字段。
7. **备份恢复、TTL过期、分区、GPU索引加速**。

# ANN

（Approximate Nearest Neighbor，近似最近邻检索）

> 一句话面试版：
ANN 是向量检索的一类算法，**不暴力遍历全部向量找绝对最相似，而是找近似最相似的TopN**，用轻微召回损失，换取检索速度几个数量级提升，是 Milvus、FAISS 这类向量库的底层核心。

## 1. 先区分：精确最近邻 KNN vs ANN
- **KNN（Exact KNN，精确最近邻）**：拿到查询向量，和库里**所有向量逐一算距离**，排序选出TopK。
  ✅ 优点：召回100%，结果绝对准确
  ❌ 缺点：向量数量大时，计算量爆炸。比如100万条768维向量，一次查询就要做100万次向量距离计算；千万/亿级向量库完全没法线上使用。

> 问题：Embedding向量维度很高（768、1024维），**高维空间下距离计算成本极高**，这就是“维度灾难”。
> 解决方案：ANN，牺牲一点点精度，跳过大部分向量，只在一小部分候选集中做距离计算。

## 2. ANN 的核心思想
我们不需要**全局绝对最相似**，只要拿到**足够相似的候选文档**交给大模型做RAG。
ANN算法通过构建索引（图、聚类、量化等），预先组织向量空间；查询时只搜索向量空间里一小片区域，快速拿到近似TopK。

常见ANN索引方案（Milvus里都有）：
1. **图索引：HNSW**（你项目在用）：构建多层小世界图，通过节点跳转，快速定位候选区域；查询性能最强。
2. **倒排聚类索引：IVF**：提前聚类，查询先找到最近的聚类桶，只在桶内检索。
3. **量化索引：PQ/SQ**：压缩向量字节，降低内存占用，牺牲精度换存储和速度。
4. **磁盘ANN：DISKANN**：索引放磁盘，适合超大规模向量，内存有限场景。

## 3. ANN 关键指标（面试高频）
评估ANN索引好坏，看这4个：
1. **召回率 Recall@K**：真实最相似的K个向量，有多少被ANN检索出来。
   
   > 例：Recall@10 = 0.95，代表真实Top10里面平均能命中9.5个。
2. **查询延迟 Latency**：单次检索耗时（ms），线上高并发RAG核心指标。
3. **QPS**：每秒能处理多少次向量查询。
4. **内存开销**：索引+向量占用内存。

> 调参本质就是在这几个指标之间做权衡：**召回率 ↔ 延迟 ↔ 内存**。
> 比如HNSW调大`ef`参数：召回上升，但延迟、CPU消耗上升。

## 4. 放到你的HRMS项目理解
- 文档转为768维Embedding向量存入Milvus；
- 建立HNSW ANN索引；
- 用户提问转向量，走ANN检索，不用和全部制度文档向量计算相似度；
- ANN返回语义近似候选集；同时并发本地BM25关键词检索，两路结果RRF融合，弥补ANN对数字、专有名词召回漂移的问题；
- 再用`access_level`标量过滤，过滤掉当前用户无权查看的制度文档。

## 5. ANN 常见缺点（面试可以主动说）
1. **召回损失**：有可能漏掉真正相关的文档，参数不合适召回会明显下降；
2. **高维向量下效果衰减**：向量维度越高，ANN越难；
3. **过滤下的召回坑**：Milvus混合检索（ANN+标量filter），底层是先ANN召回候选集，再做标量过滤。如果过滤条件筛掉大量候选，会导致召回率下跌。解决办法：检索时放大TopK。

## 6. 45秒面试口述精简版
ANN全称近似最近邻检索，是向量检索的核心算法。和暴力KNN精确检索不同，ANN不会遍历全部向量，而是通过预构建索引，只搜索向量空间局部区域，牺牲少量召回率，大幅降低检索延迟，支撑百万、千万级向量的线上检索。
Milvus提供多种ANN索引，我们项目选用HNSW分层图索引，优势是高并发、低延迟。检索时ANN拿到语义相似候选，再配合标量过滤做职级权限隔离；同时和BM25关键词检索做RRF融合，弥补纯ANN向量检索对数字、专有名词召回不稳定的问题。

# HNSW 图索引

（Hierarchical Navigable Small Worlds，分层可导航小世界）

> 面试精简一句话：**HNSW 是多层有向图结构的 ANN 近似向量检索索引，上层粗定位、下层精细搜索；查询性能高，适合高并发线上RAG，Milvus/Qdrant 默认主推。**

## 一、核心思想：Small World（小世界图）
小世界特性：任意两个节点之间，只需要很少几步跳转就能到达。
- 每个向量就是图里的一个节点；
- 节点之间建立**邻居边**，邻居是向量空间上相似度高的向量。

如果只做单层图：数据量大时，搜索起点离目标很远，跳转次数会变多，速度下降。
👉 HNSW 的解决办法：**分层，多层图**。

### 分层结构
1. **高层（上层）**：节点稀疏。向量随机分配到高层，层数越高，节点越少。
    - 作用：**快速粗搜、长距离跳转**。从一个起点，快速跳到目标向量所在的大致区域，类似高速路。
2. **第0层（底层）**：**存放全部向量**，节点稠密，邻居更多。
    - 作用：精细搜索，在目标附近找到 TopK 最相似向量，类似城市内部道路。

> 每个向量只存在于 0 层；高层只是**部分向量的副本**，用来做快速导航。

## 二、构建索引流程（插入向量时）
1. 给新向量随机确定一个最大层数 `level`（服从指数分布，层数越高概率越低）；
2. 从 HNSW 的最高层开始搜索：找到每层中和当前向量最接近的节点，作为连接点；
3. 在每一层，为新向量挑选 `M` 个最近邻居，建立双向边；
4. 可选：对邻居做剪枝，保证图质量；
5. 下降到下一层重复上面操作，一直到 0 层。

> 两个核心建图参数：
> - `M`：每个节点最多的邻居数量；M越大，图越稠密，召回越高，内存占用越高。
> - `efConstruction`：建索引时，寻找邻居的候选集大小；越大索引质量越好，建索引越慢。

## 三、检索流程（查询向量进来）
1. 从 HNSW 的最高层随机选一个起点向量；
2. 在当前层不断向**更相似的邻居**移动，直到找不到更好的点；
3. 下沉到下一层，继续搜索；
4. 逐层下沉，直到第0层；
5. 在0层，在候选集 `ef` 范围内遍历邻居，收集最相似的 TopK，返回结果。

> 查询参数 `ef`：检索阶段候选集大小。`ef` 越大，召回率越高，延迟越高。

## 四、放到你的HRMS项目理解
- 节点：每一条制度文档 embedding；
- 查询向量：用户问题的 embedding；
- HNSW：快速在千万向量里找到语义相近制度文档，**不做全向量暴力比对**；
- 搭配 `access_level` 标量过滤：Milvus 在向量检索阶段附带权限过滤，只返回当前职级可见文档；
- 痛点：纯向量检索对数字、专有名词召回不稳，所以你额外并发本地 BM25，RRF融合两路结果。

## 五、优缺点（面试必背）
✅ 优点
1. **查询延迟低、并发性能好**，是线上RAG首选索引；
2. 支持动态新增向量，不需要像IVF那样重新聚类中心；
3. 召回表现稳定，调参简单。

❌ 缺点
1. **内存开销大**：索引本身要把图结构+向量加载进内存；百万768维向量会占用大量内存；
2. 建索引耗时，大批量导入时CPU压力高；
3. ANN近似检索，牺牲少量召回换取速度，不是100%精确。

## 六、HNSW vs IVF（面试高频对比）
- **HNSW：图索引**
  多层导航图；查询快；新增向量友好；内存消耗大；适合高并发RAG。
- **IVF（IVF_FLAT/IVF_SQ8）：倒排聚类索引**
  先聚类划分桶；查询先找最近聚类，只在桶内检索；内存占用更低；新增向量会破坏聚类中心，召回缓慢下降。

## 七、面试口述精简版本（45秒）
HNSW全称分层可导航小世界，是Milvus里常用的ANN向量索引。它采用多层图结构，高层节点稀疏，用来快速定位向量的大致区域；底层包含全部向量，做精细近邻查找。插入向量时，会随机分配层数，并为向量建立邻居关系。查询时，从顶层逐层往下跳转，在底层候选集中返回TopK相似向量。
优点是查询延迟低、高并发性能好，支持动态写入；缺点是内存占用较高。我们项目使用HNSW做制度文档的向量检索，同时叠加标量过滤实现职级权限隔离，并搭配BM25关键词检索做结果融合，弥补纯向量检索对数字、专有名词召回不足的问题。

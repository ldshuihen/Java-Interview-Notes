### Java17 模块化 & 强封装（JPMS+JEP‑403）

> 面试高频考点，本文从背景、原理、边界规则、报错根源、参数区别、Spring业务场景误区一次性讲透。

#### 一、先理清两个概念

1. **JPMS（Java Platform Module System）Java平台模块系统** Java9（2017）推出的底层架构，把庞大的JDK拆分成一个个独立**模块(module)**，最核心模块为 `java.base`，`java.lang`、`java.util`、`java.time` 全部放在这个模块里面。
2. **强封装 Strong Encapsulation（JEP‑403）** Java17正式强制执行的规则：**模块边界的权限 > Java访问修饰符（public/private/protected/default）**。

> Java8时代：只有一层权限控制：访问修饰符 `private`、`public`；反射 `setAccessible(true)` 可以绕过private权限，暴力访问任意类私有成员，没有任何其他阻拦。 Java17时代：两层权限校验：**第一层：模块封装校验；第二层：访问修饰符校验**。哪怕你写上`setAccessible(true)`，模块没开放，直接拦截。

#### 二、为什么要推出强封装？（历史痛点）

Java8没有模块化，所有Jar都放在扁平的classpath下。大量框架、工具库疯狂反射JDK内部私有API：

- `sun.misc.Unsafe` 底层操作内存
- 反射 `ArrayList.elementData` 私有数组字段
- 读取`LocalDateTime`内部私有属性

**带来3个致命问题**：

1. **兼容性枷锁**：JDK团队不敢修改内部代码，一旦改动，Spring、序列化框架、第三方工具库直接崩溃，Java很难迭代升级；
2. **安全隐患**：反射绕过封装，篡改虚拟机内部状态；
3. **API混乱**：开发者大量使用没有文档、随时会删的内部API，而非官方标准公开API。

> 强封装目标：**禁止外部代码依赖JDK不稳定的内部实现，让JDK可以自由重构内部代码**。

#### 三、JDK版本推进路线（逐步收紧）

| JDK版本     | 强封装状态                                                 | `--illegal-access`参数                                       |
| ----------- | ---------------------------------------------------------- | ------------------------------------------------------------ |
| 8及更早     | 无模块化、无强封装                                         | 不存在，反射畅通无阻                                         |
| 9‑15        | 模块化上线，兼容过渡期，非法反射打印警告日志，**仍然放行** | 默认 `permit`（允许非法反射）                                |
| 16          | 默认拒绝非法反射，打印报错警告                             | 默认`deny`                                                   |
| **17(LTS)** | **正式强制执行强封装！焊死后门**，非法反射直接抛异常       | 参数彻底删除、失效，不再生效。唯一放行手段：`--add‑opens` / `--add‑exports` |

#### 四、模块化4条核心基础指令(module‑info.java)

当你编写一个模块化项目，需要在根目录创建`module‑info.java`描述文件，4个关键字：

```
module demo.myapp {
    requires java.base;        //依赖另一个模块
    exports com.demo.api;      //导出包
    opens com.demo.entity;     //开放包，允许反射访问私有
}
```

##### exports VS opens（重中之重，面试必背）

| 指令           | 权限范围                                                     | 能否反射访问private              | 使用场景                              |
| -------------- | ------------------------------------------------------------ | -------------------------------- | ------------------------------------- |
| `exports 包名` | 仅开放包里面所有 **public** 的类/方法/字段                   | ❌不行                            | 普通代码调用公开API，编译期即可引用   |
| `opens 包名`   | 开放整个包；运行时**所有成员（public+private）都允许被反射** | ✅可以，`setAccessible(true)`生效 | Spring、Jackson等反射框架读写私有字段 |

> 一句话口诀：**导出看公开，开放可反射**

#### 五、强封装拦截范围【最关键边界！！】

##### ✅强封装**只管控JDK内置模块**！！！

例如模块 `java.base`、`java.sql`、`java.net`、`jdk.unsupported`

> 只有你**反射JDK内置模块里面的未导出包、私有成员**的时候，才会触发拦截，抛出异常：

```
java.lang.reflect.InaccessibleObjectException:
Unable to make private xxx accessible:
module java.base does not "opens xxx.xxx" to unnamed module
```

##### ❌不受强封装管控的代码（永远不会被拦截）

1. **你自己业务项目写的所有类**（`com.xxx.entity.User`）；
2. Maven引入第三方Jar包，例如Spring、Mybatis、Redis客户端；

> 绝大多数SpringBoot项目都跑在**未命名模块(Unnamed‑Module)**：项目没有写`module‑info.java`，全部classpath下的代码，统一归类为「未命名模块」。 👉未命名模块之间反射私有字段，`setAccessible(true)`行为和JDK8**完全一模一样，不受任何限制！！** 也就是：你给`@Data`实体类私有字段做反射赋值，不会报错的根本原因。

##### 一张对照表彻底分清会不会报错

| 被反射的目标类                                             | 所属模块            | JDK17是否拦截暴力反射（setAccessible(true)访问private） |
| ---------------------------------------------------------- | ------------------- | ------------------------------------------------------- |
| `com.xxx.entity.User`（自己实体）                          | 未命名模块          | ❌放行，无限制                                           |
| `com.fasterxml.jackson.databind.ObjectMapper`（第三方Jar） | 未命名模块          | ❌放行，无限制                                           |
| `java.util.ArrayList`、`java.time.LocalDateTime`           | JDK模块 `java.base` | ✅拦截；需要`--add‑opens`放行                            |

#### 六、两个JVM启动放行参数详解

> `--add‑opens` 和 `--add‑exports` 属于**JVM启动参数**！**程序运行起来之后代码层面无法动态开启，只能在启动java命令的时候传入**，Spring、任何框架代码都绕不开。

##### 1. --add‑opens（反射放行，Spring/Jackson最常用）

语法：

```
--add-opens <源模块>/<包名>=<目标模块>
```

示例：

```
--add-opens java.base/java.util=ALL-UNNAMED
```

含义：

> 将`java.base`模块下`java.util`包，开放给**所有未命名模块**（SpringBoot普通项目），允许反射访问该包下所有私有字段、私有方法。

`ALL‑UNNAMED` 固定标记，代表所有classpath上没有模块化的项目（99%SpringBoot项目）。

##### 2. --add‑exports

```
--add-exports java.base/sun.misc=ALL-UNNAMED
```

仅开放包里面**public成员**，**不能反射访问私有**，很少用来解决Spring反射报错。

##### 二者对比总结

| 参数          | public访问 | 反射访问private(setAccessible(true)) |
| ------------- | ---------- | ------------------------------------ |
| --add‑exports | ✅支持      | ❌不支持                              |
| --add‑opens   | ✅支持      | ✅支持                                |

#### 七、高频误区澄清（业务开发最容易踩坑）

##### 误区1：SpringBoot3适配JDK17，框架自带绕过强封装的魔法

> ❌错。Spring代码无法修改JVM模块权限校验。SpringBoot3只是**删除了老版本中反射JDK内部私有字段的代码，不去踩雷**；一旦你的第三方依赖去反射JDK内部类，依旧报错，还是得手动加`--add‑opens`。

##### 误区2：只要代码用了反射+setAccessible(true)，JDK17就报错

> ❌错。反射你自己项目类、第三方Jar类完全不受限制。报错的唯一条件：**反射JDK内置模块中非公开成员**。

##### 误区3：@Data实体类私有字段被Spring反射赋值，一定会报错

> ❌错，实体类属于你自己项目未命名模块，模块化强封装完全不会拦截。

#### 八、生产环境遇到报错的标准排查步骤

1. 看报错栈 `module xxx does not opens xxx`，看报错的模块，是不是 `java.base`；

2. 判断：被反射的类是不是 

   ```
   java.*
   ```

    JDK自带类；

   - 如果是自己项目类 → 和强封装无关，排查其他问题；
   - 如果是JDK自带类 → 添加对应`--add‑opens`启动参数；

3. 优先升级第三方依赖（Jackson、序列化工具）到适配JDK17的新版本；**加启动参数只是临时兼容方案，治标不治本，官方不推荐长期使用**。

#### 九、面试精简背诵版答案

> Java9推出JPMS模块系统，JDK17通过JEP‑403强制执行强封装。它新增一层模块边界校验，优先级高于Java访问修饰符。强封装仅限制外部代码暴力反射访问JDK内置模块内部私有API，防止框架依赖不稳定的JDK内部实现；而业务代码、第三方Jar包之间反射不受管控。Spring操作开发者自己实体类私有字段时反射不会报错；如果第三方库反射JDK内部类抛出`InaccessibleObjectException`，可添加`--add‑opens`JVM启动参数临时开放包反射权限。





### JDK21 虚拟线程 Virtual Threads（JEP‑444）

> 虚拟线程是 **Project Loom** 历经多年孵化，在JDK21正式转正的重磅LTS新特性。也是后端秋招高频面试题。

#### 一、背景：传统平台线程的痛点

##### 传统Java线程（平台线程 Platform Thread）

> **1:1映射模型**：1个Java线程 严格绑定 1个操作系统内核线程。

1. **内存开销大**：每个平台线程默认栈内存1MB；开1万线程就要消耗10GB栈内存，极易OOM
2. **创建销毁成本高**：需要操作系统内核分配线程资源，开销重
3. **上下文切换开销大**：内核态切换CPU，开销昂贵
4. **单机并发上限低**：常规服务最多几千条平台线程；高IO并发场景，只能靠**线程池限流**
5. 催生了Spring‑WebFlux响应式编程，但响应式要全链路改成异步非阻塞，业务代码复杂度飙升，调试困难

> 所以诞生了虚拟线程，目标：**回归「一请求一线程」的同步简单写法，同时拥有百万级并发能力**

#### 二、什么是虚拟线程

> **由JVM管理的轻量级线程，属于用户态线程（协程），不和操作系统线程1:1绑定**

- 调度权：**JVM调度，不是操作系统调度**

- 映射模型：

  M:N多路复用模型

  - M = 大量虚拟线程（几十万、上百万）
  - N = 少量载体线程 Carrier Thread（底层就是平台线程，默认由`ForkJoinPool`提供，数量≈CPU核数）

##### 核心概念：挂载(Mount) & 卸载(Unmount)

1. **挂载**：虚拟线程需要执行代码时，分配到一条空闲载体线程上运行

2. 卸载

   ：当虚拟线程遇到阻塞操作（

   ```
   sleep
   ```

   、DB查询、HTTP调用、Socket IO）

   - JVM**自动把虚拟线程从载体线程上摘下来**，保存当前执行栈状态
   - **立刻释放载体线程**，载体线程可以去执行别的虚拟线程任务
   - IO等待完成后，虚拟线程再重新挂载到任意一条空闲载体线程继续执行

> ✨最强大一点：**阻塞不再占用操作系统线程！！**

#### 三、平台线程 VS 虚拟线程对比表

| 对比维度   | 平台线程(Platform Thread)          | 虚拟线程(Virtual Thread)                 |
| ---------- | ---------------------------------- | ---------------------------------------- |
| 调度者     | 操作系统内核                       | JVM虚拟机                                |
| 映射关系   | 1:1 绑定OS线程                     | M:N多路复用载体线程                      |
| 栈内存     | 固定1MB左右                        | 动态栈，按需伸缩，开销KB级别             |
| 创建上限   | 数千‑数万条                        | 单机轻松百万条                           |
| 阻塞行为   | 阻塞时一直占用OS线程               | 阻塞自动卸载，释放载体线程               |
| 上下文切换 | 内核切换，开销高                   | 用户态切换，开销极低                     |
| 线程池理念 | **必须池化复用线程，减少创建销毁** | **无需池化！一个任务新建一条虚拟线程**   |
| 守护线程   | 默认非守护，可修改daemon           | **永远是守护线程，不可关闭守护属性**     |
| 优先级     | 支持设置优先级                     | 优先级固定为NORMAL，设置无效             |
| 适用场景   | CPU密集型任务                      | **IO密集型任务（Web请求、RPC、DB调用）** |

> ⚠️ 重大结论：**虚拟线程不是用来加速CPU计算，而是解决IO阻塞浪费线程资源问题！**

#### 四、基础代码使用示例

##### 方式1：直接启动虚拟线程

```
// 方式1
Thread vt = Thread.ofVirtual().start(() -> {
    System.out.println("虚拟线程运行");
    try {
        Thread.sleep(1000); //阻塞，会自动卸载载体线程
    } catch (InterruptedException e) {
        e.printStackTrace();
    }
});

// 方式2，先创建后启动
Thread vThread = Thread.ofVirtual().unstarted(() -> {});
vThread.start();
```

##### 方式2：线程执行器（官方推荐！一任务一线程）

```
// 每提交一个任务，自动创建一条全新虚拟线程
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()){
    for(int i=0; i< 100000; i++){
        executor.submit(() -> {
            // 数据库查询、http远程调用等IO阻塞业务
        });
    }
}
```

> ❗**不要使用线程池复用虚拟线程！！虚拟线程设计初衷就是用完即扔，池化虚拟线程属于反模式**

#### 五、两大经典坑点（面试必问高频陷阱）

##### 坑1：Pinning（锚定/钉住效应）【重中之重】

当虚拟线程进入 **`synchronized`同步块 / synchronized方法** 时：

> JVM**无法卸载该虚拟线程**！虚拟线程会被钉死在当前载体线程上；即使里面发生IO阻塞，载体线程也不能释放，失去虚拟线程调度优势。

**解决方案**：

1. 将 `synchronized` 替换成 `java.util.concurrent.locks.ReentrantLock`；ReentrantLock不会触发Pinning，可以正常卸载。
2. 缩小synchronized代码块范围，块内不要放耗时IO操作。

> 补充：`LockSupport.park()` 也会触发Pinning。

##### 坑2：ThreadLocal（线程本地变量）

虚拟线程生命周期短、数量极多； `ThreadLocal`会跟随虚拟线程；如果海量虚拟线程频繁创建使用ThreadLocal，容易造成内存泄漏、GC压力上涨。

> 推荐优先使用 **`ScopedValues`（JDK20+新API）**，作为虚拟线程场景下ThreadLocal的替代品，作用域可控，自动清理。

#### 六、适用场景 & 不适用场景

##### ✅适合使用虚拟线程（IO密集）

1. Web后端微服务接口，大量数据库查询、Redis、RPC远程调用（SpringBoot3.2+已原生支持虚拟线程）
2. 批量发起大量HTTP请求、文件IO任务
3. 替代响应式WebFlux；同步阻塞写法实现高并发，代码可读性大幅提升，调试简单
4. 网关、代理服务，大量等待下游返回的场景

##### ❌不适合（CPU密集任务）

1. 长时间纯CPU计算，大数据运算、复杂加解密；

   > CPU密集任务会一直占用载体线程，虚拟线程没有收益，此时优先使用平台线程+ForkJoinPool。

#### 七、常见误区澄清

1. **误区：虚拟线程等于Go协程**

   > 很像，但不完全一样。Go协程是抢占式调度；**目前Java虚拟线程不支持时间片抢占（没有分时抢占）**。如果一个虚拟线程一直占用CPU，不会被JVM强制切走，会占住载体线程不放。

2. **误区：虚拟线程运行速度比平台线程快**

   > **CPU执行阶段速度几乎一样！** 性能收益来自阻塞时载体线程资源复用；纯CPU任务没有加速效果。

3. **误区：虚拟线程可以抛弃所有线程池**

   > 普通IO任务不需要池；但是**数据库连接池、HTTP连接池依旧必须保留！** 虚拟线程只是执行单元，数据库连接是稀缺资源，不能开十万条数据库连接。

#### 八、SpringBoot 如何开启虚拟线程

SpringBoot 3.2 + JDK21，可以一键开启，Tomcat处理每个请求使用一条虚拟线程：

```
# application.yml
spring:
  threads:
    virtual:
      enabled: true
```

开启之后，Controller同步阻塞写法即可享受高并发能力，**不需要改造任何业务代码**。

#### 九、面试精简背诵版答案

> JDK21正式转正的虚拟线程是Project‑Loom项目成果。它属于JVM层面管理的轻量级线程，采用M:N多路复用调度模型，大量虚拟线程复用到少量载体线程（OS平台线程）。当虚拟线程遇到IO阻塞时会自动卸载载体线程，释放操作系统线程资源，单机可创建数十万虚拟线程。它非常适合IO密集的微服务业务，可以使用传统同步阻塞编程模型实现高并发，降低响应式代码复杂度。使用虚拟线程需要注意`synchronized`带来的Pinning锚定问题，不建议池化虚拟线程；CPU密集场景不推荐使用。

## 前端导出 PDF 

前端导出 PDF 是一个非常经典的需求，但受限于浏览器的沙箱环境，实现方案呈现出多样化的特征。没有一种方案是完美的，需要根据**内容类型（文本为主 vs 视觉为主）**、**分页需求**以及**是否需要保留交互**来选择。

以下是前端导出 PDF 的 4 条主流实现路径：

---

### 路径一：截图派 —— HTML 转 Canvas 转 PDF（最常用）

这是目前前端最常用的方案，核心思想是“对网页截图，然后把图片塞进 PDF”。

*   **核心库**：`html2canvas` + `jsPDF` (或 `pdf-lib`)
*   **实现原理**：
    1. 使用 `html2canvas` 遍历 DOM 节点，在内存中用 Canvas 重绘，生成 base64 图片。
    2. 使用 `jsPDF` 创建 PDF 文档，将图片按 A4 比例计算宽高，贴入 PDF。
    3. 如果内容超过一页，通过计算图片高度，进行裁剪和分页添加。
*   **优点**：CSS 还原度极高，所见即所得，前端可独立完成。
*   **缺点**：
    *   **文字失真**：生成的 PDF 文字实际上是图片，无法选中、复制，且文件体积较大。
    *   **分页灾难**：跨页时容易把文字、图片截断成两半，需要手动写逻辑避免元素被切割。
    *   不支持跨域图片（需配置 `useCORS: true` 或后端代理）。
*   **适用场景**：试题试卷、可视化大屏报表、高度自定义的简历、电子发票。

<details>
<summary>点击查看核心代码示例</summary>

```javascript
import html2canvas from 'html2canvas';
import jsPDF from 'jspdf';

export const exportPDF = (dom, fileName = 'download.pdf') => {
  html2canvas(dom, {
    scale: 2, // 提升清晰度
    useCORS: true, // 允许跨域图片
    backgroundColor: '#ffffff'
  }).then((canvas) => {
    const pdf = new jsPDF('p', 'mm', 'a4'); // A4纸，纵向
    const ctx = canvas.getContext('2d');
    const a4Width = 210; // A4宽度mm
    const a4Height = 297; // A4高度mm
    // 按A4宽度比例缩放Canvas生成的图片
    const imgHeight = canvas.height * a4Width / canvas.width;
    let pageData = canvas.toDataURL('image/jpeg', 1.0);
    
    // 分页处理逻辑
    let renderedHeight = 0;
    while (renderedHeight < imgHeight) {
      // 截取剩余部分生成图片
      let sliceCanvas = document.createElement('canvas');
      sliceCanvas.width = canvas.width;
      sliceCanvas.height = Math.min(canvas.height - renderedHeight * (canvas.width / a4Width), a4Height * (canvas.width / a4Width));
      let sliceCtx = sliceCanvas.getContext('2d');
      sliceCtx.drawImage(canvas, 0, renderedHeight * (canvas.width / a4Width), canvas.width, sliceCanvas.height, 0, 0, canvas.width, sliceCanvas.height);
      
      let slicePageData = sliceCanvas.toDataURL('image/jpeg', 1.0);
      
      if (renderedHeight > 0) pdf.addPage();
      pdf.addImage(slicePageData, 'JPEG', 0, 0, a4Width, sliceCanvas.height * a4Width / canvas.width);
      
      renderedHeight += sliceCanvas.height * a4Width / canvas.width;
    }
    pdf.save(fileName);
  });
};
```
</details>

### 路径二：矢量派 —— 直接构建 PDF 文档（适合报表数据）

不依赖 DOM，直接通过 API 调用把文本、表格、图片画进 PDF。

*   **核心库**：`jsPDF`（配合 `jspdf-autotable` 画表格）、`pdfmake`
*   **实现原理**：使用库提供的坐标 API，手动设置字体、大小、位置，将 JSON 数据渲染成 PDF。
*   **优点**：
    *   生成的 PDF 是**矢量图**，文字清晰可复制、可搜索。
    *   文件体积小。
    *   库自带完美的分页逻辑，绝对不会切断单行文字。
*   **缺点**：纯手工绘制，排版极其痛苦。写复杂的样式（如浮动、圆角、渐变）非常困难。中文字体支持麻烦（需要引入巨大的中文字体包，通常几 MB 起步）。
*   **适用场景**：后端返回的 JSON 数据直接生成结构化报表、对账单、发票。

#### `pdfmake` 

一句话概括：**`pdfmake` 是一个纯 JavaScript 的 PDF 打印库，它允许你通过 JSON 数据结构来声明式地构建 PDF 文档。**

如果说 `jsPDF` 是“拿笔在纸上画”（基于坐标系，画一行字写一个坐标），那么 `pdfmake` 就像是“写 HTML/Markdown 让浏览器去排版”（基于文档流，你只管提供内容和层级，它帮你处理排版）。

---

##### 一、 pdfmake 的核心特点（底层原理）

`pdfmake` 的底层其实是基于 `PDFKit` 封装的，但它将复杂的底层 API 封装成了更符合前端直觉的声明式 API。

它的核心概念是 **Document Definition Object (DDO)**。你只需要构建一个普通的 JSON 对象，描述文档的结构（如段落、表格、列表、列布局），`pdfmake` 就会自动帮你计算位置、换行、分页，最终生成 PDF。

---

##### 二、 pdfmake 有什么用？（核心优势）

在以下场景中，`pdfmake` 非常有用：

###### 1. 生成真正的“矢量文字”（文字可选、可搜索、可复制）

与 `html2canvas` 截图生成的图片型 PDF 不同，`pdfmake` 生成的是标准的矢量文字。这意味着生成的 PDF 文件体积极小，且用户可以在 PDF 中 `Ctrl+F` 搜索文字，复制文字内容。

###### 2. 强大的表格排版能力

这是 `pdfmake` 最被推崇的功能之一。在 `jsPDF` 里手动画一个跨页且自动对齐的表格简直是灾难，但在 `pdfmake` 中，你只需要定义好行和列的 JSON 结构，它就能自动渲染，甚至在跨页时自动重复表头。

###### 3. 自动分页与文档流排版

你不需要计算一页 A4 纸能放多少行字，也不需要手动写 `addPage()`。你把所有的内容丢给 `pdfmake`，它会像 Word 一样，内容填满一页后自动开启下一页，绝不会把一行文字切成上下两半。

###### 4. 客户端/服务端双端运行

它是同构的。你既可以把它放在浏览器端直接生成 PDF 给用户下载，也可以放在 Node.js 后端生成 PDF 文件存到服务器或发给用户。

---

##### 三、 基本用法示例

来看看它是如何通过 JSON 定义文档的：

```javascript
import pdfMake from 'pdfmake/build/pdfmake';
// 如果在浏览器端，通常需要引入字体相关的 vfs 文件
import pdfFonts from 'pdfmake/build/vfs_fonts';
pdfMake.vfs = pdfFonts.pdfMake.vfs;

// 1. 定义文档结构 (这就是一个普通的 JSON)
const docDefinition = {
  content: [
    // 普通文本
    '这是一段普通文字，会自动换行和分页。',
    
    // 带样式的文本
    { text: '这是红色的加粗大标题', style: 'header' },
    
    // 列表
    {
      ul: [
        '列表项 1',
        '列表项 2',
        '列表项 3',
      ]
    },
    
    // 表格
    {
      table: {
        widths: ['*', '*', '*'], // 三列等宽
        body: [
          [ { text: '表头1', style: 'tableHeader' }, { text: '表头2', style: 'tableHeader' }, { text: '表头3', style: 'tableHeader' } ],
          [ '内容1', '内容2', '内容3' ],
          [ '内容4', '内容5', '内容6' ],
        ]
      }
    }
  ],
  // 2. 定义样式表（类似 CSS）
  styles: {
    header: {
      fontSize: 18,
      bold: true,
      color: 'red',
      margin: [0, 10, 0, 10] // [left, top, right, bottom]
    },
    tableHeader: {
      bold: true,
      fontSize: 13,
      color: 'black'
    }
  }
};

// 3. 生成并下载 PDF
pdfMake.createPdf(docDefinition).download('my-document.pdf');
```

##### 四、 pdfmake 的“坑”与局限

虽然 `pdfmake` 在结构化排版上很强，但使用时必须注意以下几点：

###### 1. 致命痛点：中文字体支持非常麻烦

`pdfmake` 默认内置的字体（Roboto）**不支持中文**。如果你的内容包含中文，默认情况下会显示成一个个方框。
**解决办法**：你需要自己下载一套中文字体文件（如思源黑体、微软雅黑），使用官方提供的工具将其转换成 Base64 编码的 JS 文件，然后挂载到 `pdfMake.vfs` 中，并在 `fonts` 配置项里声明它。这会导致你的前端打包体积**暴增几 MB 到十几 MB**。

###### 2. 不能复用现有 HTML/CSS

如果你已经写好了一个非常精美的 HTML 页面，想把它转成 PDF，`pdfmake` **做不到**。你必须用它的 JSON 格式把页面内容重新写一遍。它不支持把现有的 DOM 转成 PDF。

###### 3. 不支持复杂的 CSS 效果

它只支持基础的排版样式（边距、对齐、颜色、边框、圆角等）。如果你想画一个复杂的渐变背景、阴影、或者绝对定位的悬浮层，`pdfmake` 无能为力。

---

##### 总结：什么时候用 pdfmake？

*   **推荐使用**：后端返回一堆 JSON 数据（如订单明细、对账单、财务报表），你需要把这些数据排成表格、列表输出成清晰、文件小、可复制的 PDF。这个时候 `pdfmake` 是极佳选择。
*   **不推荐使用**：你想把前端已经画好的图表、复杂的可视化大屏、或者带有复杂背景图的网页导出成 PDF（这种请老老实实用 `pdfmake` 处理中文`html2canvas` + `jsPDF`）。

#### `pdfmake` 处理中文

`pdfmake` 处理中文的核心痛点在于：**它默认只内置了英文字体，且它需要读取字体的二进制 Base64 编码。** 中文字体文件通常非常大（几兆到十几兆），如果处理不好，会导致前端打包体积严重膨胀、页面加载卡顿。

目前业界常见的 `pdfmake` 中文方案有以下三种，根据项目架构（纯前端还是 Node 服务）可选择不同方案：

---

##### 方案一：静态打包法（传统方案，适合小型/内部项目）

这是官方文档最基础的思路，把中文字体转换成 JS 文件，直接和业务代码打包在一起。

**实现步骤：**

1. **下载字体文件**：去下载一个开源的中文字体（如思源黑体 `SourceHanSansCN-Regular.otf` 或 阿里巴巴普惠体）。
2. **转换成 Base64**：
   使用 `pdfmake` 官方提供的在线工具或 Node 脚本，将 `.ttf`/`.otf` 文件转换成 `vfs.js` 文件。
   ```javascript
   // 官方提供的构建工具 pdfmake-font-builder
   // 或者自己写个 Node 脚本读取文件转 base64
   const fs = require('fs');
   const font = fs.readFileSync('SourceHanSansCN-Regular.otf');
   const base64 = font.toString('base64');
   fs.writeFileSync('vfs-font.js', `export default "${base64}";`);
   ```
3. **引入到代码中**：
   ```javascript
   import pdfMake from 'pdfmake/build/pdfmake';
   import vfsFont from './vfs-font'; // 刚才生成的 base64 字符串

   // 挂载字体
   pdfMake.vfs = {
     'SourceHanSansCN-Regular.otf': vfsFont
   };

   // 注册字体
   pdfMake.fonts = {
     SourceHanSansCN: {
       normal: 'SourceHanSansCN-Regular.otf',
       bold: 'SourceHanSansCN-Regular.otf', // 如果没有单独的粗体，可以用同一个
       italics: 'SourceHanSansCN-Regular.otf',
       bolditalics: 'SourceHanSansCN-Regular.otf'
     }
   };

   // 使用时指定字体
   const docDefinition = {
     content: ['这是一段中文测试'],
     defaultStyle: { font: 'SourceHanSansCN' } // 关键：指定默认字体
   };
   pdfMake.createPdf(docDefinition).download();
   ```

**缺点：**
*   **打包体积灾难**：一个常规中文字体大概 5-10MB，转成 Base64 字符串后体积还会增加约 33%。这会导致你的前端 bundle 直接变大十几 MB，严重影响首屏加载速度。

---

##### 方案二：动态异步加载法（Web 前端推荐方案）

为了解决打包体积过大的问题，可以利用 `pdfmake` 的 `vfs` 支持动态赋值的特性。把字体文件放在服务器或 CDN 上，**只有在用户点击“导出 PDF”按钮时，才去拉取字体文件**。

**实现步骤：**

1. 将转换好的字体 Base64 字符串，或者原始的 `.ttf` 文件，放到服务器/CDN 上。
2. 前端在需要导出时，动态请求该文件：

```javascript
import pdfMake from 'pdfmake/build/pdfmake';

// 标记是否已加载字体，避免重复请求
let isFontLoaded = false;

async function loadFontAndExport() {
  if (!isFontLoaded) {
    // 1. 异步获取字体文件（这里以获取原始 ttf 文件为例）
    const response = await fetch('https://your-cdn.com/fonts/SourceHanSansCN-Regular.ttf');
    const blob = await response.blob();
    
    // 2. 转成 base64
    const reader = new FileReader();
    reader.readAsDataURL(blob);
    reader.onloadend = () => {
      const base64data = reader.result.split(',')[1]; // 去掉 data:font/ttf;base64, 前缀
      
      // 3. 挂载到 pdfmake
      pdfMake.vfs = {
        'SourceHanSansCN-Regular.ttf': base64data
      };
      pdfMake.fonts = {
        SourceHanSansCN: {
          normal: 'SourceHanSansCN-Regular.ttf',
          bold: 'SourceHanSansCN-Regular.ttf',
          italics: 'SourceHanSansCN-Regular.ttf',
          bolditalics: 'SourceHanSansCN-Regular.ttf'
        }
      };
      
      isFontLoaded = true;
      generatePDF(); // 字体加载完成后生成
    };
  } else {
    generatePDF();
  }
}

function generatePDF() {
  const docDefinition = {
    content: ['这是一段异步加载字体后的中文测试'],
    defaultStyle: { font: 'SourceHanSansCN' }
  };
  pdfMake.createPdf(docDefinition).download();
}

// 绑定到按钮事件
// button.addEventListener('click', loadFontAndExport);
```

**优点：**
*   不影响前端主包大小，首屏加载极快。
*   只有真正需要导出 PDF 的用户才会下载字体。

##### 方案三：服务端生成法（Node.js / 后端方案）

如果前端实在不想处理字体加载的卡顿问题，或者生成的 PDF 非常复杂，可以将 `pdfmake` 放到 Node.js 后端去执行。

**实现步骤：**
1. 后端安装 `pdfmake`。
2. 直接使用 `fs.readFileSync` 读取本地字体文件并挂载（在服务端没有打包体积限制的烦恼）。

```javascript
// Node.js 后端代码
const pdfMake = require('pdfmake');
const fs = require('fs');

// 1. 直接同步读取字体文件转 base64
const fontData = fs.readFileSync('./fonts/SourceHanSansCN-Regular.ttf').toString('base64');

const fonts = {
  SourceHanSansCN: {
    normal: 'SourceHanSansCN-Regular.ttf',
    bold: 'SourceHanSansCN-Regular.ttf',
    italics: 'SourceHanSansCN-Regular.ttf',
    bolditalics: 'SourceHanSansCN-Regular.ttf'
  }
};

const printer = new pdfMake(fonts);

const docDefinition = {
  content: ['这是服务端生成的中文 PDF'],
  defaultStyle: { font: 'SourceHanSansCN' }
};

const pdfDoc = printer.createPdfKitDocument(docDefinition);
// 通过 HTTP 响应返回给前端下载
res.setHeader('Content-Type', 'application/pdf');
res.setHeader('Content-Disposition', 'attachment; filename=download.pdf');
pdfDoc.pipe(res);
pdfDoc.end();
```

##### 💡 附：中文字体优化建议（重要）

不管你用哪种前端方案，中文字体太大始终是个问题。建议在把字体放到项目之前，先对字体进行**“子集化（Font Subsetting）”**处理。

**什么是子集化？**
中文字体通常包含几万个汉字，但你的项目可能只用到了其中的几千个（比如只打印报表中的固定字段）。可以通过工具把不需要的字从字体文件中剔除。

**常用工具：**
*   **Fontmin**：Node.js 的字体子集化工具，可以通过提取你项目中的所有中文文本，生成一个只包含这些文字的小体积字体（可能从 10MB 压缩到 1MB 以内）。
    ```bash
    npm install -g fontmin
    fontmin --text "只保留这些需要用到的文字" --dest ./output-dir SourceHanSansCN-Regular.ttf
    ```
*   **字蛛**：也是类似的原理，可以自动分析 HTML/CSS 中的文字并压缩字体。

如果你的 PDF 内容是动态的（用户输入的文字），无法做子集化，那么**强烈建议使用方案二（异步动态加载）**。

### 路径三：组件派 —— React/Vue 组件直出 PDF（现代化方案）

如果你使用现代前端框架，希望用写组件的方式写 PDF，这是最佳方案。

*   **核心库**：`@react-pdf/renderer`（React 生态），Vue 中可考虑类似思想的库。
*   **实现原理**：提供一套专属的 PDF 标签（如 `<Document>`, `<Page>`, `<View>`, `<Text>`），它在内部维护了一个虚拟 DOM，最后直接渲染成标准的 PDF 文件流，**完全不经过浏览器页面渲染**。
*   **优点**：
    *   **真正的矢量 PDF**，文字可选、支持跨页排版。
    *   React 组件写法，支持 Flexbox 布局，开发体验好。
    *   可以直接在浏览器下载，也可以在 Node.js 后端生成。
*   **缺点**：
    *   不能复用现有的 HTML/CSS，必须用它提供的组件重写一遍 UI。
    *   中文字体依然需要手动注册。
*   **适用场景**：需要生成结构化且排版复杂的报表、合同、简历。

<details>
<summary>点击查看 @react-pdf/renderer 示例</summary>

```javascript
import { Document, Page, Text, View, StyleSheet, PDFDownloadLink } from '@react-pdf/renderer';

// 1. 注册中文字体 (如果需要中文)
// Font.register({ family: 'SimSun', src: '/fonts/SimSun.ttf' });

const styles = StyleSheet.create({
  page: { flexDirection: 'row', backgroundColor: '#E4E4E4' },
  section: { margin: 10, padding: 10, flexGrow: 1 }

const MyDocument = () => (
  <Document>
    <Page size="A4" style={styles.page}>
      <View style={styles.section}>
        <Text>Section #1</Text>
      </View>
      <View style={styles.section}>
        <Text>Section #2</Text>
      </View>
    </Page>
  </Document>
);

// 在组件中使用
const App = () => (
  <div>
    <PDFDownloadLink document={<MyDocument />} fileName="somename.pdf">
      {({ blob, url, loading, error }) =>
        loading ? 'Loading document...' : 'Download now!'
      }
    </PDFDownloadLink>
  </div>
);
```

### 路径四：原生派 —— 浏览器打印转 PDF（兜底大杀器）

放弃在前端生成文件，直接调用浏览器的打印功能，让用户在打印对话框中选择“另存为 PDF”。

*   **核心技术**：`window.print()` + CSS `@media print`
*   **实现原理**：通过 CSS 媒体查询，在打印时隐藏不需要导出的元素（如导航栏、按钮），调整打印布局，然后触发浏览器原生的打印功能。
*   **优点**：
    *   **零依赖**，不需要任何第三方库。
    *   **排版完美**，支持原生分页，文字完全可复制。
    *   清晰度极高，原生支持矢量渲染。
*   **缺点**：
    *   **无法直接下载**，需要用户手动点击“保存为 PDF”。
    *   不同浏览器的打印引擎略有差异（Chrome、Safari、Firefox 渲染效果可能不同）。
    *   难以通过 JS 控制文件名和路径。
*   **适用场景**：文章详情页、电子合同、内部审批表单打印。

<details>
<summary>点击查看打印 CSS 示例</summary>

```css
/* 正常页面显示样式 */
.no-print { display: block; }
.print-only { display: none; }

/* 打印时的样式 */
@media print {
  /* 隐藏不需要打印的元素 */
  .no-print { display: none !important; }
  
  /* 显示只在打印时出现的元素 */
  .print-only { display: block !important; }
  
  /* 避免元素被截断（尽量不切分块级元素） */
  p, h1, h2, h3, div { 
    page-break-inside: avoid; 
  }
  
  /* 强制在新的一页开始 */
  .new-page { 
    page-break-before: always; 
  }

  @page { 
    margin: 0; 
    size: A4; 
  }
}
```

### 路径五：服务端派 —— 后端渲染生成 PDF（企业级方案）

如果前端处理大体积 PDF 容易导致浏览器崩溃，或者对排版、字体要求极高，应考虑将渲染逻辑移至后端。

*   **核心技术**：后端 Node.js (Puppeteer / Playwright) 或 Java (iText / Flying Saucer) / Go (wkhtmltopdf)
*   **Node.js 方案实现**：前端传递数据或 HTML 给 Node 服务，Node 服务启动无头浏览器打开指定模板页面，利用无头浏览器的 `page.pdf()` 方法生成 PDF 并返回给前端流。
*   **优点**：前端零压力，不卡顿；CSS 还原度极高；支持完美的矢量文字和分页。
*   **缺点**：增加服务器开销（无头浏览器非常吃内存），需要前后端配合设计模板。
*   **适用场景**：复杂的长篇报告生成（如财务年报、几百页的标书）。

---

### 总结与技术选型建议

| 需求场景 | 推荐方案 | 核心库/技术 |
| :--- | :--- | :--- |
| **需要高度还原复杂CSS页面，不在意文字能否复制** | HTML转Canvas转PDF | `html2canvas` + `jsPDF` |
| **后端给了一堆JSON数据，要求生成表格报表** | 直接构建PDF | `jsPDF` + `jspdf-autotable` 或 `pdfmake` |
| **使用React，希望用组件化方式写PDF** | 组件直出PDF | `@react-pdf/renderer` |
| **只需简单排版，要求文件小、文字清晰** | 浏览器原生打印 | `window.print()` + `@media print` |
| **前端容易卡死，或需极其严苛的排版还原** | 后端渲染生成 | Node.js + `Puppeteer` |

**最佳实践提示**：
如果使用 `html2canvas`，生成的图片往往会有模糊的问题，记得把 `scale` 参数设置为 `2` 或 `window.devicePixelRatio`；如果遇到分页切断文字，可以考虑通过遍历 DOM 节点，在每个块级元素前插入分页符判断逻辑。

## 单个文件下载

我按照**文件存储位置、流量走向、触发端、高级特性**四层维度做清晰归类，每一类包含适用场景、实现方案、代码思路、优缺点、生产优先级，结构清晰方便你做技术选型。

### 后端流式输出下载（文件流量经过Java服务）

> 本质：Java读取文件二进制流，写入 HttpServletResponse 输出流，业务服务承担IO、带宽压力
#### 类别1‑1：本地服务器磁盘文件

1. 原生Servlet IO流读取 FileInputStream
2. Spring Resource 工具（FileSystemResource）

**适用**：文件部署在服务器本地磁盘、内网附件服务器
优点：简单、不需要第三方对象存储
缺点：服务器磁盘故障丢失文件、大文件占用服务带宽

#### 类别1‑2：项目内置资源文件（resources目录模板）

- ClassPathResource 读取模板文件(excel、word模板)

#### 类别1‑3：内存动态生成文件，无磁盘实体文件

> 报表导出、动态PDF、动态Excel
- ByteArrayOutputStream → ByteArrayInputStream 输出response

#### 类别1‑4：文件二进制存储数据库Blob字段

- 读取blob字节数组，直接写出response输出流
适用：KB级小型附件；**禁止存储GB级大文件**

#### 类别1‑5：对象存储中转流下载（MinIO、阿里云OSS、腾讯云COS）

后端获取OSS文件输入流，中转输出给浏览器
适用：小文件；
缺点：所有下载流量经过Java服务，挤占服务带宽、tomcat线程资源

> 小结：**后端中转流只适合小文件，不适合高频、大文件下载**

---

### 旁路直连下载（流量绕过Java业务服务，生产最优）

Java只负责**鉴权、权限校验**，文件数据流直接由对象存储/Nginx返回浏览器，业务服务无IO压力

#### 类别2‑1：OSS预签名URL下载（企业项目首选）

执行流程
1. 前端调用下载接口携带token
2. 后端校验登录、文件访问权限
3. 生成一段短时有效的签名下载地址返回前端
4. 前端window.open直接跳转OSS地址下载

优点：
- 下载流量不走Java服务
- 支持断点续传、CDN加速
- 可设置链接过期时间防止盗链

#### 类别2‑2：Nginx静态资源直下

细分两种：
1. 无权限：Nginx直接映射文件目录，对外提供下载
2. 需要鉴权：Nginx auth_request 回调Java接口校验token，校验通过之后返回文件流

适用：公共静态资源、不需要复杂业务权限的附件

---

### 按照请求方式分类（前端侧方案）

#### 类别3‑1：GET方式下载

1. a标签 href
2. js window.open()
适合：不需要携带token、参数简单的下载接口

#### 类别3‑2：POST方式下载（业务最常用）

适用场景：接口需要携带token、复杂表单参数、参数加密、参数过长无法放在url
1. Axios + Blob 二进制接收（主流方案）
2. JS动态创建form表单提交

> 重点坑点：axios必须配置 `responseType: "blob"`；需要处理后端报错返回JSON的兼容逻辑

#### 类别3‑3：纯前端生成文件下载（完全不需要后端）

Blob + 动态a标签下载
适用：前端表格导出csv、前端生成文本文件

---

### 按文件大小 & 传输能力（普通下载 / 高级分片下载）

#### 类别4‑1：普通一次性全量流下载

适合：文件 ≤ 100M，绝大多数业务附件、报表、合同、模板

#### 类别4‑2：大文件分片 / 断点续传下载（＞100MB、视频、压缩包）

原理依靠HTTP请求头 `Range` 实现字节区间请求
1. 前端先请求获取文件总长度
2. 分块请求字节片段
3. 全部分片下载完毕，前端合并Blob
4. 暂停之后可以从已经下载完成的字节位置继续下载

> 生产最佳实践：超大文件放到OSS，依靠OSS原生支持Range断点续传，业务层只返回签名URL

---

#### 总览选型层级（优先级从高到低）

1. 文件存对象存储 → **鉴权 + OSS预签名直链下载（首选）**
2. 公共静态资源 → Nginx直接下载
3. 本地小附件 → Spring Resource 流下载
4. 动态导出报表 → ByteArrayOutputStream 内存流下载
5. 数据库极小附件 → Blob字节数组输出
6. 大文件禁止Java服务中转IO，一律OSS直链+断点续传

---

#### 一张对照表

| 大类             | 流量是否经过Java服务 | 适用场景                                      |
| ---------------- | -------------------- | --------------------------------------------- |
| 后端流式中转下载 | 是                   | 本地文件、动态导出、数据库附件、小文件OSS中转 |
| 旁路直连下载     | 否                   | OSS‑预签名URL、Nginx静态资源，正式环境首选    |
| 前端请求方案     | 看后端               | GET简单下载、POST带参下载、前端Blob导出       |
| 分片高级下载     | 可选                 | 百MB以上大文件、需要断点续传场景              |

## 多文件下载全套方案

先抛出核心结论：**HTTP单次响应只能返回一个流**，原生浏览器并不支持一次性返回多个独立文件；所有多文件下载本质只有两大类思路
1. 后端实时打包ZIP压缩包一次性下载（最常用）
2. 前端循环发起多次请求，逐个下载文件（无需打包）

下面做结构化分类、场景、完整代码、优缺点、生产方案、坑点、优化策略。

### 一、整体方案分类

#### 分类1：后端打包 ZIP 一次性下载（主流方案）

> 多个文件合并成一个压缩包输出流给到浏览器
> 再细分为3种实现方式
##### 方式1‑1：流式实时打包（无本地临时文件，生产推荐）

边读取文件流、边写入ZipOutputStream、边响应输出到浏览器；
不在服务器磁盘生成临时zip，不会造成磁盘堆积，占用内存低。
SpringBoot 示例代码

```java
@GetMapping("/download/batch")
public void batchMultiFile(HttpServletResponse response) throws IOException {
    response.setContentType("application/zip");
    // 设置下载压缩包名称
    String zipName = URLEncoder.encode("批量附件.zip", StandardCharsets.UTF_8);
    response.setHeader("Content‑Disposition", "attachment;filename*=utf-8''" + zipName);

    List<String> filePathList = Arrays.asList("/opt/upload/a.pdf","/opt/upload/b.xlsx");

    try (ZipOutputStream zipOut = new ZipOutputStream(response.getOutputStream())){
        // 解决zip包内中文文件名乱码
        zipOut.setEncoding("UTF-8");

        for (String path : filePathList) {
            File file = new File(path);
            if(!file.exists()) continue;
            ZipEntry entry = new ZipEntry(file.getName());
            zipOut.putNextEntry(entry);

            // 文件拷贝进zip流
            try(InputStream in = new FileInputStream(file)){
                IOUtils.copy(in,zipOut);
            }
            zipOut.closeEntry();
        }
        zipOut.finish();
    }
}
```

##### 支持文件夹结构
```java
// 子文件夹文件
ZipEntry entry = new ZipEntry("合同文件夹/" + file.getName());
```

##### 方式1‑2：先生成本地临时ZIP文件再下载

1. 后端先在磁盘生成完整zip压缩包
2. 读取本地zip流响应下载
- 缺点：并发量大容易磁盘爆满、需要定时清理临时文件
- **不推荐线上使用**

##### 方式1‑3：OSS文件打包下载

1. 方案A（不推荐）：循环读取每个OSS文件输入流，内存打包zip输出response；流量经过Java服务，压力大
2. 方案B（优化）：服务端异步任务预打包zip上传OSS，前端轮询打包状态，完成之后下载OSS预签名地址

> 适合文件数量多、文件体积大，实时打包CPU负载过高场景

---

#### 分类2、前端循环逐个下载，无需后端打包

原理：js循环调用下载接口，连续触发多次文件下载
```js
// 文件id数组
const fileIdList = [1,2,3];
fileIdList.forEach(id=>{
    window.open(`/download/single?fileId=${id}`,"_blank")
})
```
#### 优缺点
✅ 优点
1. 后端无需消耗CPU进行压缩
2. 支持断点续传、单个文件失败不会影响其余文件
3. 视频、已经压缩过的资源不需要打包

❌ 缺点
1. 浏览器弹窗拦截，一次性多个弹窗会被拦截
2. 下载列表杂乱，用户体验差

#### 改良方案：iframe 静默下载，规避弹窗拦截

```js
fileIdList.forEach(id=>{
    const iframe = document.createElement('iframe');
    iframe.style.display = 'none';
    iframe.src = `/download/single?fileId=${id}`;
    document.body.appendChild(iframe);
})
```

---

### 二、分存储源对应多文件下载方案

#### 1. 文件存本地磁盘

优先：**ZipOutputStream 流式打包下载**

#### 2. 文件存 MinIO/OSS

1. 文件数量少、体积小：Java读取各个文件流实时打包zip输出
2. 文件数量多、单文件很大：
    - 异步服务预先打包ZIP → 上传OSS
    - 前端轮询打包进度，完成获取临时签名URL下载
3. 视频、图片（已压缩格式）：前端循环逐个下载，拒绝打包

#### 3. 文件为数据库Blob附件

读取每一条blob字节数组，写入ZipOutputStream流式返回

### 三、前端 POST‑参数携带token批量下载ZIP

axios blob接收压缩包流
```js
async function batchDownload(fileIdArray){
    const res = await axios.post("/download/batch",{
        fileIdList: fileIdArray
    },{
        responseType:"blob"
    })
    // 捕获后端报错json
    if(res.data.type === "application/json"){
        const reader = new FileReader();
        reader.onload = e=>{
            let err = JSON.parse(e.target.result);
            ElMessage.error(err.msg);
        }
        reader.readAsText(res.data);
        return;
    }
    // 触发zip下载
    const blob = new Blob([res.data]);
    const url = URL.createObjectURL(blob);
    const a = document.createElement("a");
    const dis = res.headers["content-disposition"];
    let fileName = decodeURIComponent(dis.split("filename*=utf-8''")[1]);
    a.download = fileName;
    a.href = url;
    a.click();
    URL.revokeObjectURL(url);
}
```

### 四、方案对比表

| 方案             | 实现思路                     | 优点                                 | 缺点                                      | 适用场景                             |
| ---------------- | ---------------------------- | ------------------------------------ | ----------------------------------------- | ------------------------------------ |
| 后端流式Zip打包  | 边压缩边输出流               | 一次下载、体验好、支持自定义目录结构 | 消耗服务器CPU；超大压缩包失败需要从头下载 | 普通数量附件、word、excel、pdf文档   |

| 预打包Zip上传OSS | 异步任务生成压缩包存对象存储 | 不占用业务服务IO、支持CDN加速        | 需要异步任务、轮询状态                    | 几十上百个文件、GB级批量资料包       |

### 五、生产环境选型标准（优先级）

1. 文件均为文档、数量2~50个 → **流式zip打包下载（首选）**
2. 文件是视频、jpg、mp4等已经压缩资源 → 前端循环下载，禁止打包
3. 文件总量多、整体体积巨大 → 异步预打包上传OSS，签名直链下载
4. 公共静态多文件资源：Nginx + 前端循环下载

### 六、高频坑点

1. zip压缩包内部中文文件名乱码
```java
zipOut.setEncoding("UTF-8");
```
2. 大文件实时打包，高并发压垮服务器CPU
> 解决方案：异步预打包、OSS直链
3. POST下载忘记 blob，得到乱码文本
> axios 设置 `responseType:"blob"`
4. 压缩包体积过大，浏览器下载中断；
> 超大文件拆分为多个压缩分包
5. 不要先生成本地临时zip文件，容易磁盘溢出，永远优先流式输出

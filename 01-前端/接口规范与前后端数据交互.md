# 接口文档规范

> **企业级 RESTful API 接口开发文档完整规范（含完整多环境配置、失败响应分类、统一错误码、全套 CRUD 模板、外部第三方签名规范、Java 签名算法实现及微服务落地指南）**


## 一、文档总则

### 1.1 文档目的

统一公司所有微服务、前后端对接、对外开放平台接口的开发、联调、测试、运维标准，解决接口格式不统一、错误返回混乱、联调成本高、问题难以排查等问题，作为所有接口开发的强制规范。

### 1.2 通用强制约定

- **请求协议**：开发/测试 HTTP，预发/生产 HTTPS
- **编码格式**：统一 UTF-8
- **数据格式**：所有请求、响应统一 JSON，禁止 XML、表单混合返回
- **接口风格**：严格遵循 RESTful 设计规范
- **版本控制**：URL 路径版本 /api/v1/、/api/v2/，禁止 Header 传版本
- **分页规范**：pageNum(默认1)、pageSize(默认20，最大100)
- **时间格式**：统一 yyyy-MM-dd HH:mm:ss，时间戳为毫秒级

### 1.3 多环境统一配置规范

为适配项目开发、联调、测试、上线全流程，统一全环境接口域名、协议、鉴权、日志、调试规则，杜绝环境差异化导致的联调、上线问题，所有接口严格遵循本环境规范。

#### 1.3.1 环境划分与基础配置

| 环境名称         | 接口域名前缀     | 请求协议 | 环境用途 & 约束说明                                          |
| ---------------- | ---------------- | -------- | ------------------------------------------------------------ |
| 开发环境（dev）  | dev-api.xxx.com  | HTTP     | 本地开发、代码调试、功能自测；开启完整日志、参数打印、SQL打印，允许跨域，不对外暴露 |
| 测试环境（test） | test-api.xxx.com | HTTP     | 测试人员功能测试、回归测试、联调测试；保留完整错误日志，关闭冗余调试输出，模拟生产校验规则 |
| 预发环境（pre）  | pre-api.xxx.com  | HTTPS    | 生产上线前预验证、性能压测、兼容校验；配置与生产完全一致，仅数据隔离，禁止测试脏数据 |
| 生产环境（prod） | api.xxx.com      | HTTPS    | 正式对外提供服务；关闭调试日志、禁止跨域、严格鉴权、严格参数校验，保障接口安全稳定 |

#### 1.3.2 全环境统一强制规则

- **接口路径统一**：四个环境接口URL路径、请求方式、参数结构、响应结构体完全一致，仅域名与协议不同，无需适配接口代码
- **签名鉴权统一**：开发/测试/预发/生产环境，均使用同一套AK/SK签名算法、防重放规则、请求头规范，仅密钥区分环境
- **错误码体系统一**：全环境复用同一套成功、参数错误、权限错误、业务错误、外部接口错误码规则，无环境差异化错误码
- **数据隔离规则**：各环境数据完全独立，禁止开发、测试数据流入预发、生产环境，避免数据污染
- **调试权限管控**：仅开发、测试环境开启接口调试、参数打印；预发、生产环境关闭所有调试入口，隐藏敏感报错信息

### 1.4 HTTP 请求方法规范

| 请求方法 | 使用场景                     | 约束                                |
| :------- | :--------------------------- | :---------------------------------- |
| GET      | 查询数据、列表、详情         | 无请求体，参数使用路径参数/查询参数 |
| POST     | 新增资源、复杂查询、提交表单 | 必须带 JSON 请求体                  |
| PUT      | 全量更新资源                 | 全字段覆盖更新                      |
| PATCH    | 局部更新资源                 | 只更新传入字段                      |
| DELETE   | 删除资源                     | 逻辑删除/物理删除统一使用           |

### 1.5 公共请求头规范（全场景通用）

| 请求头（Header） | 是否必传 | 字段说明 | 示例值 |
| :--- | :--- | :--- | :--- |
| `Authorization` | 是（公开免登录接口除外） | 用户身份认证凭证，采用标准 Bearer Token 规范 | `Bearer eyJhbGciOi...` |
| `Content-Type` | 是 | 统一请求与响应数据格式，固定为 JSON | `application/json` |
| `Trace-Id` | 推荐 | 全链路追踪ID，若前端未传则由网关层自动生成 | `TRACE-20260626-0001` |
| `AppId` / `appKey` | 对外开放 / 第三方接口必填 | 平台分配的应用唯一标识，用于调用方身份识别 | `EXTERNAL_APP_202606` |
| `Sign` / `signature` | 对外开放 / 第三方接口必填 | 请求签名，基于AK+SK+时间戳加密，防参数篡改 | `a1b2c3d4e5f67890abcd...` |
| `Timestamp` / `timestamp` | 对外开放 / 第三方接口必填 | 客户端毫秒级时间戳，服务端校验时差，防重放（5分钟有效） | `1719358000000` |

## 二、全局统一返回结构（核心：含完整失败响应）

### 2.1 通用返回结构体（成功/失败通用）

**所有接口 100% 统一该结构，禁止自定义返回字段**

```Plain
{
  "code": 200,        // 业务状态码
  "msg": "操作成功",   // 前端展示文案
  "data": {},         // 成功数据/失败为null
  "error": null,      // 【重点】失败详情对象（成功时为null）
  "traceId": "",      // 【重点】链路追踪ID，用于日志排查
  "timestamp": 1719357000000
}
```

### 2.2 字段详细说明

| 字段名    | 类型    | 说明                                                 |
| :-------- | :------ | :--------------------------------------------------- |
| code      | Integer | 业务状态码，200=成功，非200=各种失败                 |
| msg       | String  | 用户友好提示文案，可直接前端弹窗展示                 |
| data      | Object  | 成功返回业务数据，所有失败场景统一返回 null          |
| error     | Object  | 失败详情，参数校验/业务错误/系统错误详情，成功为null |
| traceId   | String  | 全局链路ID，线上问题精准排查                         |
| timestamp | Long    | 毫秒级时间戳                                         |

## 四、完整统一错误码对照表（企业级）

| 业务码 | 含义               | 使用场景                               |
| :----- | :----------------- | :------------------------------------- |
| 200    | 操作成功           | 所有正常业务返回                       |
| 400    | 参数校验失败       | 参数空、格式错、长度错、不合法         |
| 401    | 未登录/Token失效   | 未授权访问、登录过期                   |
| 403    | 权限不足           | 已登录但无操作权限                     |
| 404    | 接口不存在         | 请求地址错误                           |
| 500    | 系统内部异常       | 代码BUG、数据库异常、服务熔断          |
| 6001   | 数据不存在         | 查询/操作不存在的数据                  |
| 6002   | 数据重复           | 账号重复、订单重复、重复提交           |
| 6003   | 业务状态不允许操作 | 订单已支付不可取消、用户已禁用不可修改 |
| 6004   | 资源不足           | 库存不足、额度不足                     |

### 接口信息

接口名称：根据ID查询用户信息

接口描述：根据用户主键ID获取用户基础信息

### 路径参数

### 成功响应示例（code=200）

```Plain

  "msg": "操作成功",
  "data": {
    "userId": 10001,
    "username": "zhangsan",
    "realName": "张三",
    "phone": "138****1234",
    "status": 1,
    "createTime": "2026-05-01 14:20:30"
  },
  "error": null,
  "traceId": "TRACE-20260626-123462",
  "timestamp": 1719357000000
}
```

#### 返回字段详细说明

| 字段名 | 数据类型 | 字段说明 | 示例值 |
| :--- | :--- | :--- | :--- |
| userId | Long | 用户唯一主键ID | 10001 |
| username | String | 系统登录账号 | zhangsan |
| realName | String | 用户真实姓名 | 张三 |
| phone | String | 脱敏后的手机号（中间4位隐藏） | 138****1234 |
| status | Integer | 账号状态：0-禁用，1-正常 | 1 |
| createTime | String | 账号创建时间（yyyy-MM-dd HH:mm:ss） | 2026-05-01 14:20:30 |

#### 业务约束与安全规则

1. **敏感数据脱敏**：用户手机号、身份证、银行卡等个人敏感信息对外输出时必须按业务规则进行掩码脱敏。
2. **软删除过滤**：逻辑删除状态（is_deleted = 1）的用户数据禁止对外返回，直接返回业务错误码 6001（用户不存在）。
3. **字段级权限隔离**：密码哈希、密码盐值、内部私密配置等字段严禁在对外 DTO / VO 中暴露。

#### 接口测试用例集

| 用例编号 | 测试场景 | 请求参数 | 预期 HTTP 状态码 | 预期业务状态码 code | 预期响应描述 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| TC_USER_001 | 正向用例：查询已存在用户 | `userId = 10001` | 200 OK | 200 | 成功获取完整脱敏用户信息 |
| TC_USER_002 | 异常用例：主键入参为空 | `userId = null` | 400 Bad Request | 400 | 返回参数校验失败提示与字段定位 |
| TC_USER_003 | 异常用例：查询不存在用户 | `userId = 99999` | 200 OK | 6001 | 返回业务异常“用户不存在” |
| TC_USER_004 | 异常用例：未携带 Token 访问 | Header 缺失 Authorization | 401 Unauthorized | 401 | 拦截并提示登录已过期 |

## 七、外部第三方接口完整CRUD规范（带签名请求头）

本章为系统**调用外部第三方接口**专属规范，独立于本地业务CRUD接口。所有外部对接接口统一强制携带鉴权请求头：appKey、timestamp、signature，遵循统一签名加密、防重放、防篡改校验规则，适用于支付、短信、第三方数据同步等所有外部对接场景，接口CRUD风格、响应结构、错误码体系统一标准化。

### 7.1 外部接口通用强制约定

所有第三方对外接口，无论增删改查，均强制执行以下规范，不允许自定义适配：

1、请求头强制必传：appKey、timestamp、signature、Content-Type

2、统一签名规则：appKey + timestamp + appSecret 拼接后 MD5 32位小写加密

3、时间戳防重放：timestamp 有效期5分钟，超时直接拒绝请求

4、响应结构完全复用全局统一结构体，成功/失败格式与本地接口一致

5、外部专属异常使用6000+业务错误码，区分本地业务异常

\1. 拼接规则：**appKey + timestamp + appSecret**（appSecret为平台私密密钥，不对外传输）

\2. 加密方式：MD5 32位小写加密

\3. 校验逻辑：服务端接收请求后，按照相同规则重算签名，与传入signature对比，不一致则拒绝请求

## 九、附录：签名获取完整实现方法

### 9.1 签名拼接加密规则

外部接口请求签名统一采用**AK+SK+毫秒级时间戳**顺序拼接方式，整体字符串进行MD5 32位小写加密，生成最终signature签名，是所有第三方接口鉴权的核心依据。

**加密公式**：`md5(AK + SK + timestamp)`

**拼接强制要求**：严格按照AK、SK、timestamp顺序拼接，无任何分隔符，字符编码统一为UTF-8，加密结果统一32位小写。

### 9.2 核心参数说明

- **AK（appKey）**：平台分配的公开应用唯一标识，对外传输
- **SK（appSecret）**：平台分配的私密密钥，禁止对外传输、禁止前端存储，仅服务端留存使用
- **timestamp**：当前系统毫秒级时间戳，与请求头传入时间戳保持一致，用于防重放校验

### 9.3 Java完整实现示例

提供可直接复用的工具代码，包含参数定义、签名生成、标准MD5加密方法，适配所有企业级外部接口签名场景。

```Java
/**
 * 外部接口签名生成工具类
 * 加密规则：md5(AK + SK + 毫秒级时间戳)
 */
public class ExternalSignUtil {

    /**
     * 【MD5加密核心方法】
     * @param sourceStr 待加密原始字符串
     * @return 32位小写MD5加密结果
     * @Description: 统一UTF-8编码加密，适配接口签名规范
     */
    protected static String md5(String sourceStr) {
        String result = "";
        try {
            MessageDigest md = MessageDigest.getInstance("MD5");
            md.update(sourceStr.getBytes("utf-8"));
            byte[] hash = md.digest();
            int i;
            StringBuffer buf = new StringBuffer(32);
            for (int offset = 0; offset < hash.length; offset++) {
                i = hash[offset];
                if (i < 0) {
                    i += 256;
                }
                if (i < 16) {
                    buf.append("0");
                }
                buf.append(Integer.toHexString(i));
            }
            result = buf.toString();
        } catch (Exception e) {
            // 日志记录异常，实际项目可替换为项目日志工具
            e.printStackTrace();
        }
        return result;
    }

    /**
     * 生成外部接口请求签名
     * @return 最终signature签名
     */
    public static String generateSign() {
        // 1. 配置平台分配的AK、SK
        String ak = "ak-eAU25mrMxhtaZsyS";
        String sk = "rjxMqB6YyUXpSHAz4DCIz8vZ5aozQQiV";
        // 2. 获取当前毫秒级时间戳
        long timestamp = System.currentTimeMillis();
        // 3. 按规则拼接并MD5加密
        String signature = md5(ak + sk + timestamp);
        System.out.println("timestamp:" + timestamp);
        System.out.println("signature:" + signature);
        return signature;
    }
}
```

### 9.4 签名使用注意事项

- SK密钥严禁硬编码在前端代码、配置文件对外暴露，仅允许后端服务内部读取使用
- 签名生成后需与timestamp同步传入请求头，时间戳有效期严格遵循5分钟规范
- 加密必须固定UTF-8编码，避免因编码不一致导致签名校验失败
- 禁止打乱AK、SK、timestamp的拼接顺序，顺序错误会直接导致签名非法
- 所有外部接口统一使用该签名算法，不允许自定义加密、拼接规则

```
六、全局错误码与状态码附录
七、安全、限流与性能约束
```

### 10.2 微服务内部 RPC 接口补充规范（Dubbo / OpenFeign）
内部 RPC 调用与面向外部/前端的 HTTP RESTful 接口存在通信协议与上下文差异，需遵循以下约束：
1. **接口入参/出参对象化**：禁止使用平铺的基本类型多参数传参，一律封装为标准的 RequestDTO / ResponseVO POJO 对象，便于后续平滑扩展版本兼容。
2. **字段注释与强校验**：所有 DTO/VO 实体类字段必须书写清晰 Javadoc 注释；非空字段必须标注 JSR-303 注解（`@NotNull`、`@NotBlank`、`@Size` 等）。
3. **统一分页对象**：微服务 RPC 分页入参统一使用 `PageDTO`（包含 `pageNum`、`pageSize`、排序规则），出参统一使用 `PageVO<T>`（包含 `total`、`list`、`pages`）。
4. **统一异常体系**：RPC 调用禁止向外抛出未受检的底层技术异常（如 `SQLException`、`NullPointerException`），必须由 Provider 统一拦截并包装为标准的 `BizException`（包含错误码与业务信息），或者通过标准化 `Result<T>` 结构体返回。
5. **版本兼容与平滑发布**：RPC 接口的修改必须遵循向上兼容原则，严禁直接删除已有字段或修改字段数据类型；涉及破坏性变更时需升级接口版本（如 Dubbo `version = "2.0.0"`）。

### 10.3 接口工程化交付物标准（企业落地实践）
一套合格的接口文档在研发各阶段应对应标准化的交付物：
1. **在线自测文档（Swagger / Knife4j）**：
   - 后端开发阶段必须集成 Knife4j 或 Springdoc-OpenAPI，保证接口代码与文档 100% 同步更新。
   - 每个 Controller 和方法必须正确标注 `@Tag`、`@Operation`、`@Schema` 或 `@Api`、`@ApiOperation`。
2. **正式交付归档文档**：
   - 团队内部维护一份最新的 Markdown 版本（纳入 Git 版本受控）并可导出为 PDF/HTML/Word 用于跨团队或甲方交付。
3. **联调与测试套件（Postman / Apifox / ApiPost）**：
   - 随文档配套提供导出的接口集合 JSON（Postman Collection），包含预设的环境变量（dev/test）、全局 Token 提取脚本和单用例断言。
4. **对外开放开放平台配套交付**：
   - 针对外部机构或第三方合作方，必须额外提供：
     - AK/SK 分配及签名验签示例工程（Java/Python/Go/PHP 等多语言 Demo）
     - IP 白名单准入策略文档
     - 接口 QPS 限流阈值与熔断降级策略说明

### 10.4 接口安全性与性能约束准则
1. **防重放攻击与时效性**：外部写请求与关键金融/支付操作必须携带 `timestamp` 与 `nonce`，服务端严格校验时间差（默认不超过 5 分钟），且同一 `nonce` 在 Redis 中缓存 5 分钟防止重复重放。
2. **接口幂等性保障**：
   - 支付、下单、提现等关键 POST 操作必须由调用端生成或向服务端申请唯一的 `Idempotency-Key`。
   - 服务端基于 Redis 分布式锁 + 业务唯一索引保证同一请求重试时不会产生重复数据或重复扣款。
3. **敏感信息脱敏与权限隔离**：
   - 手机号（保留前3后4，如 `138****1234`）、身份证号、银行卡号在接口返回前统一通过脱敏工具类或 Jackson 序列化器处理。
   - 禁止在公开响应中泄露密码哈希、盐值、内网 IP 等敏感元信息。
   - 严格进行行级数据权限隔离（数据越权水平越权、垂直越权校验）。
4. **性能与高可用指标**：
   - **响应耗时**：P99 响应耗时必须控制在 500ms 以内，P95 控制在 200ms 以内。
   - **限流防护**：单应用对外接口必须在网关层配置 Sentinel / Spring Cloud Gateway 限流策略，防止恶意高频爬取或流量冲击。

# 前端后端数据交互

> **前后端数据交互核心技术全景解析（涵盖 HTTP 请求与响应报文底层结构、接口签名鉴权防重放、前端传参方式与 Spring 接收注解、Vue 3 / TypeScript / Axios 企业级响应解析）**

## 一、HTTP 报文规范与结构

### 1.1 HTTP 请求报文

HTTP 请求报文是客户端（如浏览器、移动端 App、或者 Postman 等工具）发送给服务器的纯文本格式数据块。理解它的结构对于前后端开发、网络抓包和接口调试至关重要。

一个完整的 HTTP 请求报文由 **4 个部分**组成：**请求行、请求头、空行、请求体**。

HTTP 请求报文由**起始行、请求头、空行、请求体**四部分组成，每一部分用回车换行 `CRLF(\r\n)` 分隔。
整体格式：

```
请求行\r\n
请求头部字段\r\n
请求头部字段\r\n
\r\n
请求体（可选）
```

下面为您详细拆解这 4 个部分：

---

#### 一、 请求行

请求行位于报文的第一行，用来说明**当前请求的最基础信息**。它由三个部分组成，用空格分隔，格式如下：

```text
[请求方法] [请求URL/URI] [HTTP协议版本]
```

**详细说明：**常用8种。

1.  **请求方法**：告诉服务器客户端的动作意图。
    *   `GET`：请求获取资源（最常见，通常用于查数据）。
    *   `POST`：向服务器提交数据（如提交表单、上传文件）。
    *   `PUT`：更新服务器上的整个资源。
    *   `DELETE`：删除服务器上的指定资源。
    *   `PATCH`：对资源进行局部更新。
    *   `HEAD`：只请求资源的响应头，不要响应体。
    *   `OPTIONS`：预检请求，询问服务器支持哪些请求方法（常用于 CORS 跨域预检）。
    *   **TRACE**：追踪请求链路，一般服务器默认关闭。
2.  **请求 URL/URI**：指明请求的服务器资源路径。
    *   可以是绝对路径：`http://www.example.com/api/users`
    *   通常是相对路径：`/api/users?page=1&limit=10`（包含查询参数 Query String）。
3.  **HTTP 协议版本**：指定客户端使用的 HTTP 版本。
    *   常见的有：`HTTP/1.0`、`HTTP/1.1`（目前最广泛使用）、`HTTP/2.0`。
    *   HTTP/1.0：短连接，一次请求一次TCP断开。
    *   HTTP/1.1：默认长连接，支持持久连接、管线化。
    *   HTTP/2：二进制帧、多路复用、头部压缩。

**示例：**

```http
POST /api/login HTTP/1.1
```

---

#### 二、 请求头

请求行之后就是请求头。请求头是一系列键值对（`字段名: 值`），每行一个，用于向服务器传递**客户端的环境信息、认证凭证、以及请求体的附加说明**等。

常见的请求头字段可以分为以下几类：

##### 1. 通用信息类

*   `Host`：**（HTTP/1.1 强制要求）**指定目标服务器的域名和端口号（如 `www.example.com:80`）。一台服务器上可能托管多个网站，Host 字段告诉服务器客户端要访问哪一个。
*   `Connection`：连接管理。常见值为 `keep-alive`（保持 TCP 连接不断开，复用连接）或 `close`（请求完成后关闭连接）。
*   `User-Agent`：**UA**，客户端的身份标识。告诉服务器客户端的操作系统、浏览器型号、版本等信息（服务器常据此做 PC 端/移动端适配或反爬虫）。

##### 2. 内容协商与实体信息类

如果请求带有**请求体**（如 POST 请求），以下头部必不可少：

*   `Content-Type`：**极其重要**。告诉服务器，请求体里的数据是什么格式，服务器才知道怎么解析。
    *   `application/json`：JSON 格式（现代前后端分离最常用）。
    *   `application/x-www-form-urlencoded`：表单默认格式（`key1=value1&key2=value2`）。
    *   `multipart/form-data`：文件上传格式。
*   `Content-Length`：请求体的字节长度。
*   `Accept`：告诉服务器，客户端能接收什么格式的响应数据（如 `application/json, text/html`）。
*   `Accept-Encoding`：告诉服务器，客户端支持的压缩算法（如 `gzip, deflate`），服务器据此压缩响应体以节省带宽。
*   `Accept-Language`：客户端期望的自然语言（如 `zh-CN, en-US`）。



##### 3. 缓存与安全认证类

*   `Cache-Control`：缓存控制策略（如 `no-cache`）。
*   `Cookie`：如果客户端有该域名的 Cookie，会自动通过此头发送给服务器，用于维持会话状态。
*   `Authorization`：用于携带身份认证令牌，最常见的是 Bearer Token（如 `Authorization: Bearer <token>`，用于 JWT 认证）。官方标准头，存放Token（首选），身份令牌，Basic / Bearer Token 该类请求头主要用于**标识请求来源、传递用户身份凭证、解决跨域权限校验**，是前后端认证、跨域请求的核心字段。

###### 2. Cookie

- **性质**：服务端通过 `Set-Cookie` 写入浏览器的**自动携带会话凭证**
- **场景**：传统 Session 登录体系
- **特点**
  1. 同源请求**自动携带**，无需前端手动处理
  2. **跨域默认不携带**，需要后端开启 `Access-Control-Allow-Credentials: true`
  3. 开启凭据后，跨域 Origin **不能为 `*`**
- **格式**

```http
Cookie: JSESSIONID=abc123; token=xxxx
```

###### 3. Token（核心概念）

- **Token 是【身份凭证数据】**，不是请求头字段！
- 前后端分离主流登录凭证（JWT / 随机令牌）
- 前端手动携带，**不受浏览器同源策略限制**，天然适合跨域
- 存放位置只有两种：
  1. 标准请求头 `Authorization`（推荐）
  2. 自定义请求头 `Access-Token`



###### 4. Authorization（标准权限请求头）

HTTP 官方标准认证头部，**专门用来存放 Token**
两种用法：

**（1）Bearer 模式（企业99%在用）**

存放 JWT / AccessToken

```http
Authorization: Bearer eyJhbGciOiJIUzI1Ni...
```

**（2）Basic 模式**

账号密码 Base64 编码，多用于接口基础认证

```http
Authorization: Basic YWRtaW46MTIzNDU2
```

###### 5. Access-Token（自定义权限头）

- **非 HTTP 标准头**，是企业项目自定义字段
- 很多项目单独用该字段存放令牌，不和 Authorization 混用

```http
Access-Token: xxxxx-xxxx-xxxx
```

###### ⚠️ 跨域致命考点

**自定义请求头（Access-Token）会触发 OPTIONS 预检请求**
后端必须手动放行该头部，否则浏览器直接拦截跨域请求：

```http
Access-Control-Allow-Headers: Access-Token,Content-Type
```

---



##### 4. 跨域与来源类

*   `Origin`：跨域请求时携带请求源域名，指示请求来自于哪个站点（仅包含协议、域名、端口），主要用于 CORS 跨域请求。
*   `Referer`：指示当前请求是从哪个页面链接发起的。服务器常用于防盗链和统计分析。

###### Origin

- **作用**：浏览器**跨域请求自动携带**，同源请求不携带
- **含义**：标识请求来源 = 协议 + 域名 + 端口
- **用途**：服务端通过 Origin 判断请求是否合法、是否允许跨域放行
- **格式**

```http
Origin: shturl.cc/I6j2g8PYd
```



**示例：**

```http
-- 示例1
Host: api.example.com
Connection: keep-alive
Content-Type: application/json
Content-Length: 46
Authorization: Bearer eyJhbGciOiJIUzI1Ni...
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)...
----------------------------
-- 示例2
Host: localhost:8080
User-Agent: Mozilla/5.0
Accept: application/json
Content-Type: application/json
Content-Length: 36
Cookie: sid=abc123
Connection: keep-alive
```

##### Accept 头部

###### 一、Accept 头部作用

`Accept` 是客户端发给服务器的请求头，用来**声明客户端能够解析、处理哪些MIME数据类型**，服务器根据这个字段，选择最合适的数据格式返回给客户端，这一整个机制就叫**内容协商**。

简单一句话：

> Accept = 我浏览器能看懂哪些格式，你尽量返回我能看懂的。

---

###### 二、基本语法

```http
Accept: MIME类型1, MIME类型2;q=权重, ...
```

**1. MIME类型（资源类型）**

格式：`大类/子类`
常见值：

- `text/html`：HTML网页
- `text/plain`：纯文本
- `application/json`：JSON接口数据
- `application/xml`：XML
- `image/png`、`image/jpeg`：图片
- `*/*`：接受所有类型（浏览器默认都会带上）

**2. q（quality factor）权重**

取值范围：`0 ~ 1`，默认值 `q=1`，数值越高优先级越高。

- q=1：首选
- q=0.5：次要选择
- q=0：拒绝接收该类型

---

###### 三、完整示例

```http
Accept: application/json;q=0.9,text/html;q=0.6,*/*;q=0.1
```

解读优先级：

1. 优先返回 JSON
2. 其次返回 HTML
3. 其他格式勉强接受

---

###### 四、通配符写法

1. `text/*`
   匹配 text 下所有子类型：text/html、text/plain、text/css。
2. `*/*`
   匹配任意所有数据类型，浏览器默认请求都会携带。

示例：

```http
Accept: text/*;q=0.8,image/*
```

---

###### 五、浏览器默认原生 Accept

普通网页访问：

```http
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
```

AJAX / axios 请求：

```http
Accept: application/json, text/plain, */*
```

---

###### 六、服务端协商逻辑（面试考点）

服务器拿到Accept之后执行逻辑：

1. 解析所有MIME类型与对应的q权重；
2. 把客户端支持的格式按权重从高到低排序；
3. 在自己能提供的格式里选出优先级最高的一种；
4. 在响应头 `Content-Type` 告知客户端本次实际返回的数据类型。

---

###### 七、易混区分

- **Accept（请求头）**：客户端：我能接收什么
- **Content-Type（请求/响应头）**：告诉对方：我本次发送的数据是什么格式

---

#### 三、 空行

单独一行 `\r\n`，作用：**分隔请求头与请求体**。
即使没有请求体，这一行也必须存在。换行符严格为 `CRLF(\r\n)`，只写 `\n` 会造成报文解析失败。

在所有的请求头字段之后，紧跟着一个**空行**（即连续的回车符 `\r` 和换行符 `\n`，即 `CRLF`）。

**它的作用极其重要**：
HTTP 协议是基于文本流的，服务器读取报文时，遇到这个空行，就知道：**“请求头到此结束，接下来如果有数据，那就是请求体了”**。如果没有这个空行，服务器会把后面的内容继续当成请求头来解析，从而导致报错。



---

#### 四、 请求体

空行之后的所有内容都是请求体。它包含了要发送给服务器的实际数据。

**注意**：并非所有请求都有请求体。

*   `GET`、`DELETE`、`HEAD` 请求通常**没有**请求体（参数一般放在 URL 的 Query String 中）。
*   `POST`、`PUT`、`PATCH` 请求**通常有**请求体。

请求体的内容格式必须与请求头中的 `Content-Type` 声明的一致。

**常见格式示例：**

1.  **JSON 格式** (`Content-Type: application/json`)

```json
{
  "username": "admin",
  "password": "123456"
}
```

2.  **表单格式** (`Content-Type: application/x-www-form-urlencoded`)

```text
username=admin&password=123456
```

3.  **文件上传格式** (`Content-Type: multipart/form-data; boundary=----WebKitFormBoundary...`)
    （这种格式比较特殊，会包含一段随机的 boundary 分隔符，用来分隔普通的文本字段和二进制文件内容，篇幅较长不在此展开）。

---

#### 完整报文示例大览

把以上四部分拼起来，就是一个完整的 HTTP 请求报文。以下是一个 POST 登录请求的完整抓包示例：

```http
POST /api/v1/login HTTP/1.1
Host: api.example.com
Connection: keep-alive
Content-Length: 46
Accept: application/json
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36...
Content-Type: application/json
Origin: http://www.example.com
Referer: http://www.example.com/login.html
Accept-Encoding: gzip, deflate
Accept-Language: zh-CN,zh;q=0.9

{"username":"admin","password":"123456"}
```

*解读：*

1. 第 1 行是**请求行**：用 POST 方法请求 `/api/v1/login`，使用 HTTP/1.1 协议。
2. 第 2-11 行是**请求头**：包含了目标域名、数据长度、数据类型(JSON)、客户端环境等。
3. 第 12 行是**空行**：标志着头部结束。
4. 第 13 行是**请求体**：包含了具体的 JSON 登录账号密码数据。

*(补充说明：以上是 HTTP/1.1 的文本结构。在 HTTP/2 中，报文结构被改为了二进制帧分装，逻辑上依然包含这些信息，但不再是明文纯文本的形式，以便于多路复用和提高传输效率。)*

### 1.2 HTTP 响应报文

HTTP 响应报文是服务器在接收到客户端的请求后，处理完毕并返回给客户端的纯文本数据块。它的结构与请求报文非常相似，同样由 **4 个部分**组成：**状态行、响应头、空行、响应体**。

响应报文分为四部分，同样使用 `\r\n` 分隔：

1. 状态行（起始行）
2. 响应头字段
3. 空行（`\r\n`）
4. 响应体（可选）

格式模板：

```
状态行\r\n
响应头键值对\r\n
响应头键值对\r\n
\r\n
响应体数据
```

下面为您详细拆解这 4 个部分：

---

#### 一、 状态行

状态行位于响应报文的第一行，用来说明**服务器对当前请求的处理结果**。它由三个部分组成，用空格分隔，格式如下：

```text
[HTTP协议版本] [状态码] [状态码描述]
```

**详细说明：**

1.  **HTTP 协议版本**：服务器使用的 HTTP 协议版本，如 `HTTP/1.1` 或 `HTTP/2.0`。
2.  **状态码**：一个三位数字，表示服务器对请求的处理结果。这是前端开发排查问题的重要依据。
3.  **状态码描述**：对状态码的简短文字说明。

**示例：**

```http
HTTP/1.1 200 OK
```

##### 💡 扩展：常见 HTTP 状态码分类

*   **1xx（信息性状态码）**：接受的请求正在处理，较少见。（如 `101 Switching Protocols`，常用于 WebSocket 升级）。
*   **2xx（成功）**：请求被成功处理。
    *   `200 OK`：请求成功（最常见，GET 请求通常返回此状态）。
    *   `201 Created`：请求成功并创建了新资源（常用于 POST 请求创建数据）。
    *   `204 No Content`：请求成功，但没有返回任何内容（常用于 DELETE 请求删除数据）。
*   **3xx（重定向）**：需要客户端进行额外操作才能完成请求。
    *   `301 Moved Permanently`：永久重定向。请求的资源已分配了新的 URL。
    *   `302 Found`：临时重定向。
    *   `304 Not Modified`：协商缓存命中。客户端发送了带有缓存验证条件的请求，服务器告诉客户端“你本地的缓存还能用，不用重新下载了”。
*   **4xx（客户端错误）**：客户端发送的请求有误，服务器无法处理。
    *   `400 Bad Request`：请求语法错误（如参数格式不对、缺少必填字段）。
    *   `401 Unauthorized`：未认证。请求需要身份验证（如没带 Token 或 Token 过期）。
    *   `403 Forbidden`：无权限。服务器拒绝执行请求（如普通用户访问管理员接口）。
    *   `404 Not Found`：服务器找不到请求的资源（URL 错误）。
    *   `405 Method Not Allowed`：请求方法不被允许（如接口只允许 POST，但客户端发了 GET）。
*   **5xx（服务器错误）**：服务器在处理请求时发生了内部错误。
    *   `500 Internal Server Error`：服务器内部错误（通常是后端代码报错，如空指针异常）。
    *   `502 Bad Gateway`：网关错误。服务器作为网关或代理，从上游服务器收到了无效响应。
    *   `503 Service Unavailable`：服务不可用。服务器超载或停机维护。
    *   `504 Gateway Timeout`：网关超时。服务器作为代理，等待上游服务器响应超时。

---

#### 二、 响应头

多条 `键: 值`，用来告诉客户端如何处理本次结果。

响应头是一系列键值对，每行一个，用于向客户端传递**服务器的环境信息、以及返回数据（响应体）的附加说明**等。

常见的响应头字段可以分为以下几类：

##### 1. 服务器信息类

*   `Server`：包含服务器软件信息（如 `nginx/1.18.0`、`Apache`）。（出于安全考虑，生产环境有时会隐藏此字段）。
*   `Date`：服务器生成并发送该响应报文的时间。

##### 2. 实体内容描述类（极其重要）

与请求头类似，如果响应带有**响应体**，以下头部必不可少：

*   `Content-Type`：告诉客户端，返回的响应体是什么格式，浏览器据此决定如何渲染或解析。
    *   `text/html; charset=utf-8`：HTML 网页。
    *   `application/json; charset=utf-8`：JSON 数据（前后端分离 API 最常用）。
    *   `image/jpeg`：JPEG 图片。
    *   `application/javascript`：JS 脚本文件。
*   `Content-Length`：响应体的字节长度。
*   `Content-Encoding`：响应体的压缩编码方式（如 `gzip`）。服务器压缩数据，浏览器解压数据。
*   `Content-Disposition`：指示客户端将响应体作为附件下载，并指定默认文件名（如 `attachment; filename="report.xlsx"`）。

##### 3. 缓存控制类

用于控制浏览器和 CDN 的缓存策略。

*   `Cache-Control`：缓存策略指令（如 `max-age=3600` 表示缓存 3600 秒，`no-cache` 表示不直接使用缓存需重新验证）。
*   `Expires`：缓存的绝对过期时间（HTTP/1.0 遗留，优先级低于 Cache-Control）。
*   `Last-Modified`：资源在服务器上的最后修改时间（用于协商缓存）。
*   `ETag`：资源的唯一标识符（通常是哈希值，用于协商缓存，比 Last-Modified 更精准）。

##### 4. 安全与跨域类

*   `Set-Cookie`：服务器向客户端发送 Cookie。客户端下次请求时会自动带上。
*   `Access-Control-Allow-Origin`：允许跨域请求的来源（如 `*` 或 `http://www.example.com`），是解决 CORS 跨域的核心响应头。
*   `Strict-Transport-Security` (HSTS)：强制客户端使用 HTTPS 与服务器通信。

##### 5. 重定向指示类

*   `Location`：配合 3xx 状态码使用，告诉客户端跳转到的新的 URL 地址。

**示例：**

```http
Server: nginx/1.18.0
Date: Wed, 25 Oct 2023 07:28:00 GMT
Content-Type: application/json; charset=utf-8
Content-Length: 88
Connection: keep-alive
Access-Control-Allow-Origin: *
```

---

#### 三、 空行

单独一行 `\r\n`，分隔头部和响应体。
哪怕没有响应体，这一空行依然不能省略。换行符严格为 `CRLF(\r\n)`，只写 `\n` 会造成报文解析失败。

在所有的响应头字段之后，紧跟着一个**空行**（连续的回车符和换行符 `CRLF`）。

**它的作用与请求报文中的空行完全一样**：
告诉客户端（浏览器或 HTTP 库）：**“响应头到此结束，接下来如果有数据，那就是响应体了”**。这是 HTTP 解析器切分头部和实体的边界标记。

---

#### 四、 响应体

空行之后的所有内容都是响应体。它包含了服务器返回给客户端的实际数据。

**注意**：并非所有响应都有响应体。

*   `204`、`304` 响应通常**没有**响应体。
*   `HEAD` 请求的响应也**没有**响应体。

响应体的内容类型必须与响应头中的 `Content-Type` 声明的一致。

**常见格式示例：**

1.  **JSON 格式** (`Content-Type: application/json`) —— 最常见的 API 响应

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "id": 1,
    "name": "Tom"
  }
}
```

2.  **HTML 格式** (`Content-Type: text/html`)

```html
<!DOCTYPE html>
<html>
<head><title>Home</title></head>
<body><h1>Hello World</h1></body>
</html>
```

---

#### 完整报文示例大览

把以上四部分拼起来，就是一个完整的 HTTP 响应报文。以下是一个典型的 GET 请求数据成功的完整响应抓包示例：

```http
HTTP/1.1 200 OK
Server: nginx/1.18.0
Date: Wed, 25 Oct 2023 07:28:00 GMT
Content-Type: application/json; charset=utf-8
Transfer-Encoding: chunked
Connection: keep-alive
Cache-Control: no-cache
Access-Control-Allow-Origin: *

{"code":200,"message":"success","data":{"id":1,"name":"Tom"}}
```

*解读：*

1. 第 1 行是**状态行**：使用 HTTP/1.1 协议，返回 200 OK 表示成功。
2. 第 2-9 行是**响应头**：包含了服务器软件(nginx)、时间、返回数据格式(JSON)、缓存控制(不缓存)、跨域允许等信息。
3. 第 10 行是**空行**：标志着头部结束。
4. 第 11 行是**响应体**：包含了后端返回的实际 JSON 业务数据。

*(补充：在第一个问题中提到的 Axios 响应结构里，`response.status` 对应状态行中的状态码，`response.headers` 对应响应头，`response.data` 对应响应体。理解 HTTP 报文结构有助于我们更好地使用 HTTP 客户端库和排查网络问题。)*



## 二、接口签名鉴权方案

### 2.1 请求头 appKey、timestamp、signature 接口鉴权

这是后端非常通用的**接口签名鉴权方案**，防止接口被非法调用、重放攻击，常见于开放平台、对外API。

#### 三个参数含义

| 参数          | 说明                                                         |
| ------------- | ------------------------------------------------------------ |
| **appKey**    | 应用唯一标识，服务端分配给调用方，相当于账号                 |
| **timestamp** | 当前时间戳，一般毫秒级，用于防重放攻击                       |
| **signature** | 签名，把参数+密钥加密算出的摘要，服务端校验签名判断请求是否合法 |

> 密钥 `appSecret` **不放在请求头**，客户端/调用方本地保存，不网络传输。

#### 签名通用流程

##### 1. 客户端

1. 获取当前时间戳 `timestamp`（毫秒）
2. 将业务参数、`appKey`、`timestamp` 按规则排序拼接字符串
3. 拼接上密钥 `appSecret`
4. 使用 MD5 / SHA256 / HMAC‑SHA256 加密得到 `signature`
5. 三个字段放到 Http Header 发起请求

```
Headers:
appKey: "xxx"
timestamp: "1756123456789"
signature: "xxxxxxxxxxxxxx"
```

##### 2. 服务端校验步骤

1. 从 header 获取 `appKey`，查询数据库拿到对应的 `appSecret`
2. 获取请求头的 `timestamp`，**校验时间差**：比如和服务器时间相差超过5分钟直接拒绝，抵御重放攻击
3. 使用和客户端**完全一样的拼接算法**，本地重新计算签名
4. 对比本地算出的签名 和 请求头的 `signature` 是否一致
5. 全部校验通过才执行业务逻辑，失败返回401/403

#### 典型签名算法示例（Java 常用，HMAC‑SHA256）

> 关键点：**参数key字典序排序，拼接key=value，再拼接secret，加密后转大写/小写**

伪代码逻辑：

```
// 1. 组装待签名参数，包含appKey、timestamp，以及query、body业务参数
Map<String, String> params = new TreeMap<>(); // TreeMap自动字典排序
params.put("appKey", appKey);
params.put("timestamp", timestamp);
// put 其他业务参数...

// 2. 拼接成 a=xxx&b=xxx&c=xxx
StringBuilder sb = new StringBuilder();
for(Map.Entry<String,String> entry : params.entrySet()){
    sb.append(entry.getKey()).append("=").append(entry.getValue()).append("&");
}
String source = sb.toString();

// 3. HMAC‑SHA256，使用appSecret作为密钥加密，得到signature
String signature = hmacSha256(source, appSecret);
```

> ⚠️坑点：

1. 客户端服务端排序规则必须一致；
2. null值如何处理（要不要参与签名）要约定；
3. 时间戳单位：毫秒/秒，前后端必须统一；
4. url编码问题，参与签名要用原始值，不要用urlencode之后的值；
5. appSecret 严禁在前端浏览器暴露，浏览器端需要后端中转。

#### 防重放攻击原理

攻击者抓包拿到完整header，直接复制重放请求；服务端校验timestamp，如果请求时间距离现在已经超过阈值（例如300s），直接拦截。

#### 面试常问

1. 为什么不直接传appSecret？

   > secret放在请求头会被抓包泄露；signature是摘要，secret只参与加密，不传输。

2. timestamp作用？

   > 防重放攻击。

3. signature作用？

   > 校验请求参数没有被篡改、调用方拥有合法密钥。

4. 如果参数是JSON body怎么签名？

   > 将整个json字符串作为一个参数参与签名，或者把json内部字段解析出来排序参与签名，前后端约定。

#### 常见返回码

- 401：appKey不存在 / 签名错误
- 403：timestamp过期，请求重放



####  使用场景

> 方案一：带随机串nonce完整版签名鉴权，安全性最高，**有状态（依赖Redis存nonce）**，防篡改+身份认证+强防重放。

##### ✅ 适合使用的场景

###### 1. 企业对外开放平台（最典型）

第三方公司调用我方API做业务对接：支付回调、订单同步、数据推送、供应链接口。

- 例如：供应商系统推送订单到我方ERP；第三方服务商拉取业务数据。
- 特点：调用方是**服务端程序**，不是浏览器；第三方会保管好appSecret；不面向普通用户。
- 为什么选它：
  - 第三方系统时间可能有偏差，timestamp时间窗口兼容；
  - nonce+Redis彻底阻止抓包重放攻击；
  - 可以识别调用方身份(appKey)，做限流、权限管控、调用日志统计。

###### 2. 高安全要求的B2B接口、资金/支付相关接口

涉及金额、账务、支付回调、退款、扣费类接口。

> 支付类接口最怕重放：抓包后重复调用退款接口，造成资损。

- timestamp控制时间窗口，nonce保证同一个请求只能执行一次；
- 即使HTTPS被破解，篡改参数签名校验失败；重放请求Redis识别nonce重复直接拦截。

###### 3. 内部系统跨业务系统对接（集群环境）

公司内部多个独立系统互相调用：PMS、ERP、财务系统。

> 集群部署，单机内存缓存不行，必须Redis校验nonce。 例：ERP系统调用支付系统的扣款接口；PMS推送数据给财务。

- 内部各个服务分配独立appKey/appSecret；
- 网关统一验签，业务服务不用关心鉴权逻辑；
- 可以做调用审计日志，记录哪个系统调用。

###### 4. 设备端、IoT设备后端接口

硬件设备后端服务调用，设备作为调用方，设备内置appSecret。

> 设备时间可能不准，依靠5分钟时间窗口容错；nonce防止设备报文被抓包重放。

------

##### ❌ 不适合使用的场景

###### 1. 浏览器前端直接调用（网页JS）

❌ 绝对不能：浏览器JS代码里面写appSecret。

> secret会暴露在前端代码，被扒取，攻击者就可以伪造任意签名。 如果网页需要调用该API：必须走**后端代理**，前端请求自己后端，由我方服务端完成签名再去调用第三方接口。

###### 2. APP客户端原生

移动端apk可以被反编译抓代码，secret很容易泄露。

> APP场景不建议直接用这套签名；一般方案：APP请求自己服务端获取JWT token，后端之间才用appKey签名。

###### 3. 普通用户登录会话场景

普通用户登录，获取个人资源，优先JWT。

> 签名鉴权每次请求都要组装排序、计算签名，开销更大；用户会话不需要强防重放。

###### 4. 单机小项目、对安全要求很低的内部工具

如果只是简单内部调试，集群都没有，不需要Redis，就用**简化版（去掉nonce）**，只保留 appKey+timestamp+signature，减少Redis依赖。

------

##### 🆚 （带nonce完整版） vs 简化版（无nonce）场景区分

| 版本                             | 依赖       | 适用场景                                            | 不适用场景                     |
| -------------------------------- | ---------- | --------------------------------------------------- | ------------------------------ |
| 完整版 nonce+timestamp+signature | Redis      | 资金接口、对外开放平台、B2B对接、集群内部高安全接口 | 单机小工具、前端浏览器直接调用 |
| 简化版 无nonce                   | 无中间存储 | 低风险内部对接，非资金类接口，单机部署              | 支付、退款等资损风险接口       |

##### 面试考点：为什么支付回调接口要用带nonce的完整版？

1. 只靠timestamp：5分钟时间窗口内，如果抓包拿到请求，可以反复发送同一个退款请求，造成多次退款资损。
2. nonce+Redis：`appKey+timestamp+nonce`存入Redis，过期时间等于时间窗口，同一个请求只能执行一次；即使抓包重放，nonce命中Redis直接拒绝。
3. 同时签名校验参数，防止中间人篡改退款金额。

##### 补充落地注意

1. 该方案**不能替代HTTPS**：HTTPS防止网络窃听；签名解决篡改、重放、身份校验；两者配合使用。
2. nonce由调用方生成：随机UUID即可，不需要业务含义。
3. Redis key：`sign:nonce:{appKey}:{timestamp}:{nonce}`，过期时间设置300s（和timestamp时间窗口一致）。

如果你需要，我可以对比：网关层做验签 VS 业务服务做验签各自适用场景。

### 2.2 接口签名鉴权完整方案与生产落地

接口签名鉴权主要解决3个安全问题：
1. **身份认证**：确认调用方是合法客户端
2. **防篡改**：请求参数在传输过程没有被修改
3. **防重放**：抓包拿到请求后不能重复恶意调用

> 适用场景：开放API、第三方对接、内部微服务对外暴露接口；**不适合浏览器前端直接使用（secret不能暴露）**，浏览器需要后端代理转发。

#### 主流方案对比

|方案|核心要素|优点|缺点|适用场景|
|---|---|---|---|---|
|**appKey+timestamp+signature**|appKey、时间戳、签名，secret本地保管|实现简单，无中间存储，性能好|需要前后端严格对齐签名算法|第三方开放平台、HTTP接口对接（最常用）|
|**JWT Token**|header存token，服务端无状态|无需每次计算签名，携带业务信息|无法主动作废token；重放风险|登录态、用户端接口|
|**AK/SK（阿里云风格）**|accessKey、secret，签名包含header、body|安全性高，支持复杂请求|算法复杂|云服务商OpenAPI|
|**OAuth2.0**|access_token|标准授权，第三方授权登录|流程重，需要token管理|第三方登录授权场景|

> 你前面问的 `appKey+timestamp+signature` 属于第一种，企业内部对接用的最多。

---

#### 方案一：appKey + timestamp + nonce + signature（生产推荐完整版）

##### 请求头约定

```http
appKey: 分配给调用方的标识
timestamp: 毫秒时间戳
nonce: 随机字符串，防重放增强
signature: 签名值
Content-Type: application/json
```
- `appSecret`：**绝不传输**，调用方、服务端本地保存。
- `nonce`：随机串，结合timestamp双重防重放。

##### 签名生成规则（核心，前后端必须完全一致）

1. **收集所有参与签名参数**
    - 请求头：`appKey`、`timestamp`、`nonce`
    - GET：所有query参数
    - POST JSON：**完整原始JSON body字符串**（不要解析字段）
2. 把所有参数按照 **key字典升序排序**（TreeMap）
3. 拼接成 `key1=value1&key2=value2&key3=value3`，末尾不要多余&
4. 拼接 `&appSecret=xxxx`
5. 使用 HMAC‑SHA256 加密，转十六进制小写/大写，得到 `signature`

> 坑：body一定要用原始字符串；不要使用url编码后的值参与签名；null值处理提前约定，一般null不参与签名。

##### 服务端完整校验流程

1. 获取header：appKey、timestamp、nonce、signature
2. 根据appKey查询，获取appSecret；appKey不存在直接返回401
3. **时间戳校验**：服务器时间与timestamp差值，允许偏差 ±5分钟（300s），超出直接拒绝，防重放
4. **nonce去重校验**：将 `appKey+timestamp+nonce` 存入Redis，设置过期时间等于时间偏差窗口（300s）；如果已存在，说明请求重复，拒绝。
> nonce可以防止同一秒内被重复重放，timestamp防止跨时间窗口重放。
5. 拿到请求原始query、原始body，**完全复刻客户端签名逻辑，本地计算signature**
6. 对比本地计算值与请求头signature是否相等；不相等返回401签名错误
7. 全部校验通过，执行业务逻辑

##### 常见异常返回码

|码|含义|
|---|---|
|40101|appKey无效|
|40102|签名signature错误|
|40103|timestamp时间戳过期|
|40104|nonce重复，请求重放|
|403|无访问权限|

##### Java工具类（HmacSHA256）

```java
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.nio.charset.StandardCharsets;
import java.util.Base64;

public class SignUtil {
    /**
     * HMAC‑SHA256 签名
     * @param source 待签名字符串
     * @param secret appSecret密钥
     * @return 签名
     */
    public static String hmacSha256(String source, String secret) throws Exception {
        Mac mac = Mac.getInstance("HmacSHA256");
        SecretKeySpec keySpec = new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256");
        mac.init(keySpec);
        byte[] bytes = mac.doFinal(source.getBytes(StandardCharsets.UTF_8));
        StringBuilder sb = new StringBuilder();
        for (byte b : bytes) {
            String hex = Integer.toHexString((b & 0xFF));
            if(hex.length() ==1){
                sb.append("0");
            }
            sb.append(hex);
        }
        return sb.toString();
    }
}
```

#### 方案二：简化版（无nonce，小项目快速落地）

去掉nonce，只依靠timestamp时间窗口防重放。
> 缺点：同一毫秒内抓包可以多次重放，安全性弱于带nonce版本；内部可信对接可以使用。

请求头：`appKey、timestamp、signature`

---

##### 关键风险点 & 避坑点（面试高频）

1. ❌ **appSecret不能放在请求头/参数传输**，抓包直接泄露；只本地参与签名计算。
2. ❌ 签名时不要使用URL编码后的参数值，使用原始值，否则前后端签名不一致。
3. ❌ POST JSON请求不要解析JSON字段再签名；直接拿原始request body字符串。
> Spring中读取body只能读取一次，需要封装RequestWrapper缓存body流。
4. ❌ 排序规则不一致：大小写、下划线，key必须字典序升序。
5. ❌ 时间戳单位：毫秒/秒，前后端必须统一。
6. ✅ nonce去重依赖Redis；单机可以用本地缓存，集群环境必须Redis。
7. ✅ HTTPS是基础；签名不能替代HTTPS，HTTPS防窃听，签名防篡改+身份校验。

#### 面试问题整理

##### Q1：签名鉴权和JWT区别？

- 签名鉴权：每次请求都根据请求参数实时计算签名；适合第三方服务对接；服务端需要保存appSecret。
- JWT：token生成后一段时间不变；适合用户会话；不需要服务端存储密钥，但很难主动作废token。

##### Q2：timestamp为什么设置5分钟时间窗口？

网络存在时间误差，给客户端服务器时间偏差留余量；窗口越大重放风险越高；窗口太小网络抖动会导致合法请求失败。

##### Q3：nonce作用是什么？

即使时间戳没有过期，相同nonce只能使用一次；防止攻击者在5分钟窗口内反复重放同一个请求。

##### Q4：参数被中间人篡改，签名会发生什么？

参数改变，待签名字符串改变，服务端算出的signature和客户端不一致，校验失败拦截请求。

##### Q5：如果是微服务之间调用，怎么做签名鉴权？

两种方案：
1. 沿用appKey+signature；每个微服务分配AK/SK；网关层统一做签名校验。
2. Spring Cloud：Gateway网关 + 请求头传递token，内部服务之间不用重复验签。

#### 架构落地建议

1. **网关层统一验签**（Spring Cloud Gateway），不要每个业务接口重复写验签逻辑；验签通过后转发给后端服务。
2. 封装全局过滤器，拦截所有对外API。
3. appKey、appSecret管理后台，支持密钥轮换。
4. Redis保存nonce，过期时间等于timestamp时间窗口。

## 三、前端向后端传递参数

### 3.1 常见四类传参方式详解

前端向后端传递参数，本质上是通过 HTTP 请求携带数据。根据 HTTP 协议规范和后端接收方式的不同，前端传参主要分为 **4 大核心类型**。

以下是详细分类及在 Axios（Vue/React 常用）中的实现方式，并附带后端（以 Java/Spring Boot 为例）的接收方式，方便对照理解：

---

#### 一、 查询参数

**特点**：拼接在 URL 问号 `?` 后面，格式为 `key=value`，多个参数用 `&` 连接。明文传输，有长度限制（通常 2KB），适合传递简单的筛选条件。

- **1 KB = 1024 字节**
- **2 KB = 2048 字节**
- 在 URL 编码中，**1个英文字母、数字或常见符号（=、&、?）占 1 个字节**。
- **1个中文字符**在 UTF-8 编码下占 3 个字节，但在 URL 传输时通常会被转义（如“张”变成 `%E5%BC%A0`），此时**1个中文字符会占用 9 个字节**。

**开发建议**

虽然理论上能放几十上百个参数，但在实际开发中：

1. **不要逼近极限**：如果 URL 长度超过 1KB，部分老浏览器或网关（如旧版 Nginx 默认配置）可能会直接截断或报 `414 URI Too Long` 错误。
2. **敏感数据不要放 Query**：Query 参数会明文出现在浏览器地址栏、服务器访问日志、浏览器历史记录中。
3. 何时该换用 POST 和 Body：
   - 当参数非常多（比如批量删除传了 500 个 ID 数组）。
   - 当参数值很长（比如富文本内容、复杂的 JSON 结构）。
   - 当包含敏感信息（如密码、密钥）。 此时应该使用 `POST` 请求，将这些数据放在**请求体**中。请求体没有 2KB 的硬性限制（通常默认支持几 MB 到几十 MB）。

**场景**：GET 请求、分页、搜索条件。

- **适用场景**：传递简单的键值对数据，如分页查询、条件筛选等（通常使用 GET 请求）。
- Vue 前端：通过 `params`属性传递参数。
- Java 后端：使用 `@RequestParam`注解逐个接收参数。

##### 1. 前端实现
*Axios 会自动将 `params` 对象拼接成 URL 查询字符串。*
```javascript
axios.get('/api/users', {
  params: {
    page: 1,
    size: 10,
    keyword: '张三'
  }
});
// 实际发送的 URL: /api/users?page=1&size=10&keyword=张三
```

##### 2. 后端接收

```java
@GetMapping("/users")
public Result getUsers(@RequestParam("page") int page, 
                       @RequestParam("size") int size, 
                       @RequestParam("keyword") String keyword) { ... }
```

###### 将多个零散的 `@RequestParam` 替换为一个实体类（DTO）

**是的，完全可以！而且这是非常推荐的做法。**

将多个零散的 `@RequestParam` 替换为一个实体类（DTO），不仅能极大简化后端代码，还能提升代码的可读性和可维护性。

**1. 替换后的后端代码**

**第一步：定义一个实体类（DTO）**
将之前的 `page`、`size`、`keyword` 作为类的属性。

```java
// 定义查询参数实体类
public class UserQueryDTO {
    private Integer page;
    private Integer size;
    private String keyword;

    // 必须要有 Getter 和 Setter，Spring 底层要靠它们来注入值
    // 省略 getter/setter...
}
```

**第二步：改造 Controller 方法**
去掉所有的 `@RequestParam`，直接用这个实体类作为方法参数。

```java
@GetMapping("/users")
public Result getUsers(UserQueryDTO queryDTO) { 
    // 在这里直接使用 queryDTO.getPage(), queryDTO.getSize() 等
    // ... 
}
```

---

**2. 前端需要改动吗？**

**前端完全不需要任何改动！**

前端依然按照原来的方式，把参数拼在 URL 的 Query String 上：

```javascript
// 前端 Axios 调用
axios.get('/api/users', {
  params: {
    page: 1,
    size: 10,
    keyword: '张三'
  }
});
```

实际发出的 HTTP 请求依然是：
```http
GET /api/users?page=1&size=10&keyword=张三
```

---

**3. Spring 是如何自动解析的？**

当 Spring MVC 发现方法参数是一个 **POJO（普通 Java 对象）且没有加任何注解**时，它会默认启用 `@ModelAttribute` 机制：

1. Spring 先实例化一个 `UserQueryDTO` 对象。
2. 它去 HTTP 请求的 URL 中找 Query 参数。
3. 它发现 URL 中有 `page=1`，而 `UserQueryDTO` 类中正好有 `setPage(Integer)` 方法，于是调用它把 1 赋值进去。
4. 同理，把 `size` 和 `keyword` 也赋值进去。
5. 最终将组装好的 `queryDTO` 对象传给 `getUsers` 方法。

---

**4. 为什么要强烈推荐这种做法？（优势对比）**

| 对比项         | 写多个 `@RequestParam`                                       | 写一个实体类 (DTO)                                           |
| :------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **代码整洁度** | 方法参数会越来越长，显得臃肿。                               | 方法签名简洁清晰，只有一个参数。                             |
| **可扩展性**   | 如果以后新增了 `status`, `startDate` 等筛选条件，**必须修改 Controller 方法签名**，这可能引发兼容风险。 | 只需在 DTO 类中加个字段即可，**Controller 方法签名完全不用改**。 |
| **复用性**     | 无法复用。                                                   | 这个 `UserQueryDTO` 可以传递给后面的 Service 层、DAO 层继续使用。 |

**⚠️ 唯一需要注意的区别：参数必填校验**

*   **使用 `@RequestParam` 时**：默认情况下，如果前端不传 `keyword`，Spring 会直接报 400 错误（参数缺失）。如果允许不传，需写成 `@RequestParam(required = false)`。
*   **使用实体类时**：前端如果不传某个参数，Spring 不会报错，而是会将实体类中对应的属性保持为 `null`（或基本类型的默认值，如 0）。这通常在查询场景下更符合业务需求（不传代表不限制该条件）。

---

###### 直接替换为两个（甚至多个）实体类

在 Spring MVC 中，你不仅可以替换为一个实体类，**也可以直接替换为两个（甚至多个）实体类**。Spring 会自动将 URL 上的 Query 参数分别“对号入座”到这两个实体类中。

结合你提到的“增加字段”，我们来看看具体的实现方式和需要注意的“坑”。

**1. 后端代码实现**

假设你把参数拆分为两个实体类：一个专门负责分页（`PageDTO`），一个负责业务查询条件（`UserQueryDTO`，并增加了 `status` 字段）。

**实体类定义：**
```java
// 实体类 1：分页参数
public class PageDTO {
    private Integer page;
    private Integer size;
    // getter/setter...
}

// 实体类 2：业务查询参数（增加了 status 字段）
public class UserQueryDTO {
    private String keyword;
    private String status; // 新增的字段
    // getter/setter...
}
```

**Controller 改造：**
```java
@GetMapping("/users")
// 直接传入两个实体类，不需要任何注解
public Result getUsers(UserQueryDTO queryDTO, PageDTO pageDTO) { 
    // 可以分别从两个对象中取值
    // queryDTO.getKeyword(), queryDTO.getStatus()
    // pageDTO.getPage(), pageDTO.getSize()
    ... 
}
```

**2. 前端如何传参？**

前端**完全不需要管后端是一个对象还是两个对象**，依然是把所有参数平铺在 URL 的 Query String 上即可：

```javascript
axios.get('/api/users', {
  params: {
    page: 1,
    size: 10,
    keyword: '张三',
    status: 'ACTIVE'  // 传递增加的字段
  }
});
```

**3. Spring 是如何解析的？**

Spring MVC 遇到两个没有注解的 POJO 参数时，执行逻辑如下：
1. 实例化 `UserQueryDTO` 和 `PageDTO`。
2. 遍历 URL 上的参数（`page`, `size`, `keyword`, `status`）。
3. 对于参数 `page=1`，它检查 `UserQueryDTO` 有没有 `page` 属性？如果没有，它再检查 `PageDTO` 有没有 `page` 属性？有，则注入。
4. 对于参数 `status=ACTIVE`，发现只有 `UserQueryDTO` 有 `status` 属性，则注入到 `UserQueryDTO` 中。

---

**4. ⚠️ 核心警告：必须注意“字段重名冲突”**

把参数拆分成多个实体类虽然语法上完全支持，但在实际开发中有一个**非常大的隐患：字段重名**。

假设某天，你的 `UserQueryDTO` 和 `PageDTO` 中**都有一个名为 `status` 的字段**（比如分页状态和用户状态）。

前端传：`?status=SUCCESS`

此时 Spring 会怎么做？
**Spring 会把 "SUCCESS" 同时注入到 `UserQueryDTO.status` 和 `PageDTO.status` 中！** 它无法区分这个 `status` 到底是给谁的。这在业务上会导致严重的数据混乱。

**5. 最佳实践建议**

虽然在 GET 请求中写两个实体类不报错，但为了避免上述的重名冲突和逻辑混乱，业界通常有以下两种推荐做法：

**推荐做法一：合并为一个 DTO（最常用）**
把分页参数和业务参数放在同一个 DTO 里，即使它们在业务上属于不同模块。
```java
public class UserQueryRequestDTO {
    private Integer page;
    private Integer size;
    private String keyword;
    private String status;
}
```

**推荐做法二：使用继承（如你之前遇到的代码）**
让业务 DTO 继承分页 DTO，这样在 Controller 层面依然只接收一个对象，但代码结构上做到了分离。

```java
// 基类
public class BasePageDTO {
    private Integer page;
    private Integer size;
}

// 子类继承基类
public class UserQueryDTO extends BasePageDTO {
    private String keyword;
    private String status;
}

// Controller 只需要一个参数
@GetMapping("/users")
public Result getUsers(UserQueryDTO queryDTO) { ... }
```

**总结**

后端方法参数可以直接写两个实体类，Spring 能自动解析并分发参数。但为了避免字段名冲突带来的隐蔽 Bug，**强烈建议在 GET 请求中，无论有多少种类型的参数，尽量合并成一个 DTO 对象来接收**。

#### 二、 路径参数

**特点**：参数直接嵌入在 URL 路径中，作为路径的一部分。通常用于定位某个具体的唯一资源。
**场景**：RESTful 风格的 GET 请求（如获取某个详情）。

- **适用场景**：RESTful 风格 API，用于获取特定资源的标识符，如根据 ID 获取用户详情。
- Vue 前端：通过字符串拼接或模板字符串将 ID 嵌入到 URL 路径中。
- Java 后端：使用 `@RequestParam`注解逐个接收参数。

##### 1. 前端实现
*通常使用模板字符串将变量拼入 URL，或者使用 Axios 的动态路由配置。*
```javascript
const userId = 123;
axios.get(`/api/users/${userId}`);
// 实际发送的 URL: /api/users/123
```

##### 2. 后端接收
```java
@GetMapping("/users/{id}")
public Result getUserById(@PathVariable("id") Long userId) { ... }
```

---

#### 三、 请求体参数
**特点**：数据放在 HTTP 请求的 Body（正文）中发送，不会显示在 URL 上。没有长度限制（理论上），适合传递复杂、大量、敏感的数据。
**场景**：POST（创建）、PUT（更新）请求。

根据 `Content-Type` 的不同，Body 传参分为三种常见格式：

##### 1. JSON 格式 (最常用，`application/json`)

将 JavaScript 对象序列化为 JSON 字符串发送。

- Vue 前端：使用 `axios.post`直接将对象作为第二个参数传递。

  ```javascript
  axios.post('/api/user', { username: 'john', age: 30 })
  ```

- Java 后端：使用 `@RequestBody`注解将 JSON 自动映射为 Java 对象。

* **前端实现**：Axios 默认会将 `data` 对象转为 JSON。
  ```javascript
  axios.post('/api/users', {
    name: '李四',
    age: 25,
    roles: ['admin', 'editor']
  });
  // 请求头: Content-Type: application/json
  // 请求体: {"name":"李四","age":25,"roles":["admin","editor"]}
  ```
* **后端接收**：
  ```java
  @PostMapping("/users")
  // 使用 @RequestBody 接收 JSON 并映射为对象
  public Result createUser(@RequestBody UserDTO userDTO) { ... } 
  ```

##### 2. 表单格式 (`application/x-www-form-urlencoded`)

键值对形式，类似查询参数，但放在 Body 中。传统 HTML 表单默认的提交方式。
* **前端实现**：需要使用 `URLSearchParams` 或 `qs` 库转换数据。
  ```javascript
  const params = new URLSearchParams();
  params.append('username', 'admin');
  params.append('password', '123456');
  axios.post('/api/login', params);
  // 请求头: Content-Type: application/x-www-form-urlencoded
  // 请求体: username=admin&password=123456
  ```
* **后端接收**：
  ```java
  @PostMapping("/login")
  // 不加 @RequestBody，Spring 会默认按表单解析
  public Result login(String username, String password) { ... } 
  ```

##### 3. 复杂表单/文件上传 (`multipart/form-data`)

将数据分隔成多个部分发送，可以同时传递普通文本字段和文件（图片、文档等）。

Vue 前端：构建 `FormData`对象，并设置请求头为 `multipart/form-data`。

Java 后端：普通字段用 `@RequestParam`接收，文件用 `MultipartFile`接收。

* **前端实现**：需要构造 `FormData` 对象。
  ```javascript
  const formData = new FormData();
  formData.append('name', '王五');
  formData.append('avatar', fileInput.files[0]); // file 对象

  axios.post('/api/upload', formData, {
    headers: { 'Content-Type': 'multipart/form-data' }
  });
  ```
* **后端接收**：
  ```java
  @PostMapping("/upload")
  public Result upload(String name, @RequestPart("avatar") MultipartFile file) { ... }
  public Result upload(String name, @RequestParam("avatar") MultipartFile file) { ... }
  ```

###### `@RequestParam("file")` 和 `@RequestPart("avatar")` 

在 Spring MVC 中，`@RequestParam("file")` 和 `@RequestPart("avatar")` 都可以用来接收前端上传的文件（`MultipartFile`），但它们在**底层机制、数据转换能力以及对 `Content-Type` 的要求**上有明显的区别。

简单来说：**`@RequestParam` 适合简单的表单字段和文件，而 `@RequestPart` 功能更强大，不仅能处理文件，还能利用 HTTP 消息转换器处理复杂的 JSON/XML 等结构化数据。**

**1. 底层机制不同**

*   **`@RequestParam("file")`**：
    *   它主要依赖 Spring 的 `WebDataBinder` 进行简单的类型转换。
    *   它把请求中的参数（包括表单字段和 `MultipartFile`）当作普通的键值对来处理。
    *   当它遇到 `MultipartFile` 类型的参数时，Spring 会自动识别并获取对应 name 的上传文件。
*   **`@RequestPart("avatar")`**：
    *   它依赖于 Spring 的 `HttpMessageConverter`（消息转换器）。
    *   它的设计初衷是处理 multipart 请求中的**每一个独立部分（Part）**。它不仅能获取文件，还能根据该部分声明的 `Content-Type`，将其反序列化为复杂的 Java 对象（比如 POJO）。

**2. 对复杂对象（如 JSON）的支持（核心区别）**

*   **`@RequestParam`** 只能处理简单的类型（String, Integer, Boolean）和 `MultipartFile`。**它无法直接将一个 JSON 字符串部分转换为 Java POJO**。
*   **`@RequestPart`** 可以处理复杂的结构化数据。如果前端通过 FormData 发送一个 Blob，并指定其 `Content-Type` 为 `application/json`，后端可以使用 `@RequestPart` 直接将其映射为一个 Java 对象。

**`@RequestPart` 处理 JSON 的例子：**
```java
// 前端 FormData 中包含一个 JSON 格式的 user 信息和一张头像图片
@PostMapping("/upload")
public Result upload(@RequestPart("user") User user, 
                     @RequestPart("avatar") MultipartFile avatar) { 
    // user 参数会被 Jackson 等转换器直接反序列化为 User 对象
    // avatar 参数接收图片文件
    return Result.ok();
}
```
在这个场景下，`@RequestParam` 是做不到直接转换成 `User` 对象的。

**3. 对 Content-Type 的严格程度**

*   **`@RequestParam`**：对于 `multipart/form-data` 表单中的文件，它通常不关心该文件部分的 `Content-Type` 是什么，只要能拿到二进制流和文件名即可。
*   **`@RequestPart`**：因为它要使用 `HttpMessageConverter`，所以它**对 `Content-Type` 比较敏感**。
    *   如果用 `@RequestPart` 接收一个 JSON 对象，前端必须在该 Part 设置正确的 `Content-Type: application/json`，否则 Spring 会找不到合适的 Converter 从而抛出异常。
    *   当用它接收 `MultipartFile` 时，通常无需额外设置，浏览器会自动为文件流加上 `application/octet-stream` 等类型。

**4. 总结与使用建议**

| 特性               | `@RequestParam`                            | `@RequestPart`                                            |
| :----------------- | :----------------------------------------- | :-------------------------------------------------------- |
| **适用场景**       | 简单的表单字段、简单的文件上传             | 需要将 Part 转换为复杂对象（JSON/XML）、文件上传          |
| **底层转换器**     | `WebDataBinder` (简单类型转换)             | `HttpMessageConverter` (消息转换，如 Jackson)             |
| **接收 JSON 对象** | 不支持（只能接收 String 然后自己手动解析） | 支持（自动反序列化）                                      |
| **前端配合**       | 普通的 `<form>` 表单或简单的 `FormData`    | 需要将特定 Part 的 `Content-Type` 设为 `application/json` |

**实际开发中怎么选？**
1.  **只是上传文件 + 简单的字符串参数**：两者皆可，但 `@RequestParam` 更常见，写法也更简洁。
2.  **前端传递复杂的表单数据（混合文件和 JSON 对象）**：必须使用 `@RequestPart`，它能让你的后端接口直接接收强类型的 Java 对象，代码更优雅。

#### 四、 请求头参数

**特点**：数据放在 HTTP Headers 中，与请求体和 URL 分离。
**场景**：传递鉴权 Token（如 JWT）、客户端版本号、语言环境等全局附加信息。

- **适用场景**：传递身份验证凭证（如 Token）、语言偏好等元数据信息。
- Vue 前端：在请求配置的 `headers`中自定义字段。
- Java 后端：使用 `@RequestHeader`注解获取。

##### 1. 前端实现
*可以在单次请求设置，也可在 Axios 拦截器中全局设置。*
```javascript
axios.get('/api/users', {
  headers: {
    'Authorization': 'Bearer eyJhbGciOiJIUzI1...',
    'X-Client-Version': '1.0.0'
  }
});
```

##### 2. 后端接收
```java
@GetMapping("/users")
public Result getUsers(@RequestHeader("Authorization") String token, 
                       @RequestHeader("X-Client-Version") String version) { ... }
```

---

#### 总结速查表

| 传递位置        | HTTP Method 常用 | Content-Type            | 前端 Axios 写法              | 后端 Spring 注解                 | 典型场景                    |
| :-------------- | :--------------- | :---------------------- | :--------------------------- | :------------------------------- | :-------------------------- |
| **URL Query**   | GET              | 无                      | `{ params: {id: 1} }`        | `@RequestParam`                  | 筛选、分页                  |
| **URL Path**    | GET / DELETE     | 无                      | `` `/api/user/${id}` ``      | `@PathVariable`                  | 获取/删除指定 ID 资源       |
| **Body (JSON)** | POST / PUT       | `application/json`      | `axios.post(url, {name: 1})` | `@RequestBody`                   | 提交复杂表单、创建/更新资源 |
| **Body (Form)** | POST             | `x-www-form-urlencoded` | `URLSearchParams` 处理       | 无注解 / `@ModelAttribute`       | 传统表单提交、老接口兼容    |
| **Body (File)** | POST             | `multipart/form-data`   | `FormData` 对象              | `@RequestPart` / `MultipartFile` | 上传文件、图文混排提交      |
| **Header**      | 所有             | 无                      | `{ headers: {token: xxx} }`  | `@RequestHeader`                 | 身份验证、全局参数          |

**实际开发中最常用组合**：
* GET 请求：用 **Query 参数** 和 **Path 参数**。
* POST/PUT 请求：用 **JSON Body** 传递业务数据，用 **Header** 传递 Token。



### 3.2 Spring 核心注解：@ResponseBody 与 @RequestBody 深度剖析

不过需要先纠正一个小概念：`@ResponseBody` 是作用在**方法返回值**上的（或者放在类级别），而不是作用在**参数**上的。对于**参数**，用来接收 JSON 的注解是 `@RequestBody`。

我们分两种情况详细说明：

#### 1. 关于返回数据（`@ResponseBody`）
如果你的类上使用了 `@RestController`，那么你**不需要**再在方法上添加 `@ResponseBody` 了。

**原因：**
`@RestController` 是一个组合注解，它的源码相当于 `@Controller` + `@ResponseBody`。
这意味着，被 `@RestController` 标记的类中，**所有的方法默认都会将返回值直接写入 HTTP 响应体中**（通常会被自动转换为 JSON 格式返回给前端）。

**对比示例：**
```java
// 旧写法：返回 JSON 需要加 @ResponseBody
@Controller
public class UserController {
    @GetMapping("/user")
    @ResponseBody // 必须加
    public User getUser() { ... }
}

// 新写法：使用 @RestController
@RestController
public class UserController {
    @GetMapping("/user")
    // 不需要加 @ResponseBody，默认就会返回 JSON
    public User getUser() { ... } 
}
```

---

#### 2. 关于接收参数（`@RequestBody`）

如果你说的“参数”是指前端传过来的 JSON 格式的请求体，那么即使使用了 `@RestController`，**参数上的 `@RequestBody` 依然不能省略**。

**原因：**
`@RestController` 只决定了“怎么返回数据”，并没有决定“怎么接收数据”。如果要接收前端传来的 JSON 数据并映射为 Java 对象，必须使用 `@RequestBody` 告诉 Spring 去请求体中解析数据。

**示例：**
```java
@RestController
public class UserController {
    
    // @RequestBody 不能省略！
    @PostMapping("/user")
    public Result createUser(@RequestBody User user) { 
        // ... 
    }
}
```

**总结：**
*   使用了 `@RestController` 后：方法上的 `@ResponseBody` 可以省略（返回值自动转 JSON）。
*   使用了 `@RestController` 后：参数上的 `@RequestBody` 不能省略（如果需要接收 JSON 参数的话）。

#### 1. `@RequestBody`（管“收”数据）

*   **作用方向**：**入参**（前端 -> 后端）。
*   **作用**：用于接收前端通过 HTTP 请求体传过来的数据（通常是 JSON 格式），并自动转换为 Java 对象。
*   **位置**：写在**方法参数**的前面。
*   **场景**：前端用 POST 请求发送了一段 JSON 数据，后端需要把它解析成 User 对象。

#### 2. `@ResponseBody`（管“发”数据）
*   **作用方向**：**返回值**（后端 -> 前端）。
*   **作用**：将后端方法返回的 Java 对象，直接写入 HTTP 响应体中，通常自动转换为 JSON 格式返回给前端。（如果不加它，Spring 会默认把返回值当作视图名称去寻找页面）。
*   **位置**：写在**方法**上，或者**类**上。
*   **场景**：后端查出一个 User 对象，直接转成 JSON 给前端。

---

#### 3. 代码对比演示

在一个普通的 `@Controller` 中，两者的配合使用如下：

```java
@Controller
public class UserController {

    // 前端传来 JSON，后端用 @RequestBody 接收
    @PostMapping("/save")
    @ResponseBody  // 加上这个，返回的 User 对象才会变成 JSON 给前端
    public User saveUser(@RequestBody User user) {
        // 业务处理...
        user.setId(1L);
        return user; 
    }
}
```

**记忆口诀：**
*   **Body** 指的是 HTTP 的报文_body_（数据体）。
*   **Request**（请求）+ **Body** = 前端发来的请求体数据，所以是**收参数**。
*   **Response**（响应）+ **Body** = 后端返回的响应体数据，所以是**回结果**。

*(注：如果你使用了 `@RestController`，因为里面已经包含了 `@ResponseBody`，所以方法上就不需要再写了，但接收 JSON 参数的 `@RequestBody` 依然必须要写。)*

### 3.3 后端 DTO 继承分页参数实战

在 JSON 格式（`application/json`）的请求中，HTTP 协议和后端的解析器（如 Spring Boot 默认的 Jackson）有一个核心原则：**一个 HTTP 请求体只能对应一个 JSON 对象，后端只能用一个 `@RequestBody` 来接收。**

既然你的后端 DTO 已经继承了分页参数，那么在解析时，**最标准、最正确的做法是将 DTO 和分页参数的属性“扁平化”合并成一个 JSON 对象传给后端。**

以下是具体的解析过程和前后端代码对照：

#### 1. 后端的数据结构 (假设)

假设后端代码如下：
```java
// 1. 分页基类
public class PageParam {
    private Integer pageNum;
    private Integer pageSize;
}

// 2. 业务 DTO 继承了分页类
public class UserDTO extends PageParam {
    private String username;
    private Integer age;
}

// 3. Controller 接收
@PostMapping("/users/list")
public Result getList(@RequestBody UserDTO userDTO) {
    // 此时 userDTO 里面既有 username、age，也有 pageNum、pageSize
    return Result.success(userService.getList(userDTO));
}
```

#### 2. 前端该如何传递和解析？

因为后端的 `UserDTO` 继承了 `PageParam`，在前端看来，它们并不需要分拆成两个独立的参数，而是应该**组合成一个扁平化的 JSON 对象**。

##### 前端代码实现 (Vue/React + Axios):
```javascript
// 前端定义的请求参数（合并在一起）
const params = {
  // 来自分页参数
  pageNum: 1,
  pageSize: 10,
  
  // 来自 DTO 参数
  username: '张三',
  age: 25
};

// 发送请求
axios.post('/api/users/list', params)
  .then(res => {
    console.log(res);
  });
```

##### 实际发送的 HTTP 报文:
```http
POST /api/users/list HTTP/1.1
Content-Type: application/json

{
  "pageNum": 1,
  "pageSize": 10,
  "username": "张三",
  "age": 25
}
```

#### 3. 后端是如何解析这个 JSON 的？

当这个 JSON 到达后端时，Spring Boot 的 Jackson 解析器会执行以下逻辑：

1. 识别到 `@RequestBody UserDTO` 注解。
2. 开始遍历 JSON 中的键值对 (`pageNum`, `pageSize`, `username`, `age`)。
3. 利用 Java 的**反射机制**，去 `UserDTO` 类及其父类 `PageParam` 中寻找同名的 setter 方法或字段。
4. 发现 `username` 和 `age` 是 `UserDTO` 自身的属性，赋值成功。
5. 发现 `pageNum` 和 `pageSize` 是父类 `PageParam` 的属性，同样赋值成功。
6. 最终生成一个完整的 `UserDTO` 对象交给 Controller 方法使用。

---

#### 4. 常见误区与坑点 (重要)

##### 误区一：前端强行传两个对象（嵌套 JSON）
有的前端开发者可能会想：既然是两个概念，我包成两层传过去行不行？
```json
// ❌ 错误的 JSON 结构
{
  "pageParam": {
    "pageNum": 1,
    "pageSize": 10
  },
  "dto": {
    "username": "张三",
    "age": 25
  }
}
```
**结果**：后端解析失败！因为 `UserDTO` 类中没有 `pageParam` 和 `dto` 这两个字段。Jackson 默认会忽略未知字段（或者根据配置抛出异常），导致 `pageNum` 和 `username` 都为 `null`。

##### 误区二：后端 Controller 写了两个 `@RequestBody`
```java
// ❌ 错误的后端写法
public Result getList(@RequestBody UserDTO userDTO, @RequestBody PageParam pageParam)
```
**结果**：直接报错！Spring MVC 不允许一个请求体被多次读取解析。前端不管怎么传，这个接口都会报 `HttpMessageNotReadableException`。后端开发者通常不会犯这个错，如果遇到这种情况，请让后端修改接口。

##### 误区三：字段重名冲突
如果 `UserDTO` 中有一个字段叫 `status`，父类 `PageParam` 中也有一个字段叫 `status`，并且 JSON 中传了 `"status": 1`。
**结果**：解析会发生歧义，通常子类的属性会覆盖父类的属性（取决于具体配置）。因此在设计继承关系时，应尽量避免字段重名。

#### 总结

当遇到 DTO 继承分页参数的场景时：
前端不需要关心后端的继承关系，**只需要把所有查询条件、分页参数平铺在一个 JSON 对象中，通过 `POST` 请求的 Body 发送给后端即可**。后端会自动利用面向对象的特性完成数据的组装。

### 3.4 复杂组合传参场景与解决方案

前端向后端传参并不是“非此即彼”的，HTTP 协议本身就允许在**一个请求中同时通过多种方式传递参数**。不同的参数位置各司其职，互不冲突。

在实际的企业级项目中，**“组合传参”**几乎是标配。以下是具体的组合方式和应用场景：

#### 最经典的组合场景：路径参数 + 查询参数 + 请求头 + 请求体

假设有一个业务场景：**“管理员更新某个指定用户的信息”**。

前端可以同时这样发送请求：

##### 1. 前端 Axios 代码实现
```javascript
const userId = 123; // 要修改的用户ID

axios.put(`/api/users/${userId}`, // 1. 路径参数：放在url里
  {
    // 2. 请求体参数：放在 JSON Body 里
    name: '张三',
    age: 25,
    role: 'editor'
  }, 
  {
    // 3. 查询参数：拼在 url 问号后面
    params: { 
      forceUpdate: true 
    },
    // 4. 请求头参数：放在 Headers 里
    headers: { 
      'Authorization': 'Bearer xxx-yyy-zzz',
      'X-Client-Version': '2.1.0'
    }
  }
);
```

##### 2. 实际发出的 HTTP 报文
```http
PUT /api/users/123?forceUpdate=true HTTP/1.1
Host: www.example.com
Authorization: Bearer xxx-yyy-zzz
X-Client-Version: 2.1.0
Content-Type: application/json

{
  "name": "张三",
  "age": 25,
  "role": "editor"
}
```

##### 3. 后端 Spring Boot 如何接收
后端可以通过不同的注解，精准地将这些不同位置的参数“各取所需”地注入到方法参数中：

```java
@PutMapping("/users/{id}")
public Response<?> updateUser(
    @PathVariable("id") Long userId,                              // 接收路径参数
    @RequestParam("forceUpdate") Boolean isForce,                 // 接收查询参数
    @RequestBody UserDTO userDTO,                                 // 接收请求体 JSON
    @RequestHeader("Authorization") String token,                 // 接收请求头
    @RequestHeader("X-Client-Version") String version             // 接收请求头
) {
    // 在这里同时拥有了 userId, isForce, userDTO, token, version
    // 执行业务逻辑...
}
```

---

#### 为什么要组合传参？（分工不同）

不同的参数位置有不同的物理特性和业务语义，组合使用能让接口更清晰、更安全：

1. **路径参数 (`@PathVariable`)**：表达**资源定位**。比如 `/users/123` 明确指代 ID 为 123 的用户。
2. **查询参数 (`@RequestParam`)**：表达**筛选、排序或控制行为**。比如 `?forceUpdate=true` 或 `?page=1`。
3. **请求体 (`@RequestBody`)**：表达**资源的具体内容**。用于传输大量、复杂的数据结构（如提交整个表单）。
4. **请求头 (`@RequestHeader`)**：表达**全局元数据**。用于传输鉴权信息、语言环境、客户端版本等，与具体业务数据解耦。

#### 总结
前端在一个请求中同时组合使用 `params` (Query)、`data` (Body)、URL 拼接 和 `headers` 是完全合规且标准的做法。这能让接口的设计符合 RESTful 规范，同时保持业务数据与控制参数的清晰分离。

**不可以。**

在 Spring MVC（Java 后端）中，**一个请求方法中绝对不能同时使用两个 `@RequestBody` 注解。**

#### 为什么不可以？

这涉及到 HTTP 协议和 Servlet 底层的机制：

1. **HTTP 请求体只有一份**：一个 HTTP 请求（如 POST/PUT）只能有一个请求体。请求体是一段连续的字节流（比如一个 JSON 字符串）。
2. **流只能读取一次**：Spring 底层通过 `HttpServletRequest` 的输入流来读取请求体。Java 中的流是单向的，**只能被读取一次**。当 Spring 读取完请求体并交给 Jackson 尝试映射给第一个 `@RequestBody` 参数后，流就关闭了。
3. **无法分割**：Spring 无法自动将一个 JSON 字符串拆分成两半，分别映射给两个不同的对象。

如果你强行在后端代码中写两个 `@RequestBody`：
```java
// ❌ 错误写法，绝对会报错
@PostMapping("/save")
public Result save(@RequestBody UserDTO user, @RequestBody OrderDTO order) {
    // ...
}
```
**结果**：项目可以启动，但一旦前端调用该接口，Spring 会直接抛出 `HttpMessageNotReadableException` 或 `IllegalStateException`（提示 `request body` 已经被读取过），导致接口直接 400 或 500 报错。

---

#### 如果前端确实需要传两个复杂的对象，该怎么解决？

如果业务场景确实需要同时提交两个复杂的结构化数据，后端通常有以下几种解决方案：

##### 方案一：包装成一个外层对象（最推荐、最标准）

后端新建一个专门的 DTO 类，将这两个对象作为它的属性。

**后端代码：**
```java
// 1. 创建包装类
public class SaveRequestDTO {
    private UserDTO user;
    private OrderDTO order;
    // getter / setter ...
}

// 2. Controller 接收
@PostMapping("/save")
public Result save(@RequestBody SaveRequestDTO request) {
    UserDTO user = request.getUser();
    OrderDTO order = request.getOrder();
    // ...
}
```

**前端对应的传参格式：**
前端需要把数据包装成嵌套的 JSON 结构。
```javascript
axios.post('/api/save', {
  user: {
    name: '张三',
    age: 20
  },
  order: {
    orderId: 'ORD123',
    amount: 100.5
  }
})
```

##### 方案二：扁平化合并（如果两个对象没有重名字段）

如果两个对象的字段没有冲突，前端可以直接把所有字段平铺在一个 JSON 里传给后端，后端依然用两个对象接收，但**只有一个加 `@RequestBody`**，另一个通过 `@ModelAttribute` 或者默认绑定接收（不过这在 JSON 交互中不太常见，更适用于表单提交）。

对于 JSON 交互，最稳妥的还是**方案一**。

##### 方案三：一个走 Body，一个走 Query

如果其中一个对象数据量很小，前端可以把小对象拆解成 Query 参数拼在 URL 上，大对象放在 Body 里。

**后端代码：**
```java
@PostMapping("/save")
// order 作为简单参数拼接在 url 上，user 作为 JSON body 传过来
public Result save(@RequestBody UserDTO user, @RequestParam("orderId") String orderId, @RequestParam("amount") Double amount) {
    // 手动组装 OrderDTO
}
```

#### 总结
记住一个铁律：**一个 HTTP 请求，对应一个请求体，后端只能用一个 `@RequestBody` 接收。** 如果要传多个对象，请让前端把它们组装成一个大的 JSON 对象传过来。

## 四、前端解析后端响应数据

### 4.1 前端解析后端 Controller 返回数据通用流程

前端解析后端 Controller 返回的数据，通常是一个**“发起请求 -> 接收响应 -> 提取核心数据 -> 处理特殊类型 -> 绑定到视图”**的过程。

虽然后端可能用 Java、Go、Python 等语言编写，但它们返回到前端的数据格式通常是 **JSON**。

以下是前端解析后端数据的完整流程和常见方法：

---

#### 第一步：理解后端的标准响应结构

在企业级开发中，后端 Controller 通常不会直接返回裸露的业务数据，而是包裹在一个统一的标准格式中。例如：

```json
{
  "code": 200,           // 状态码，200通常表示成功
  "message": "success",  // 提示信息
  "data": {              // 真正的业务数据
    "id": 1,
    "name": "张三"
  }
}
```

前端的核心任务就是：**判断 `code` 是否成功，并提取 `data` 中的数据。**

---

#### 第二步：使用 HTTP 库接收数据

前端通常使用 `Axios` 或原生的 `Fetch` 来请求数据。

##### 1. 使用 Axios（最常用）

Axios 会自动将后端返回的 JSON 字符串解析为 JavaScript 对象。

```javascript
axios.get('/api/user/1')
  .then(response => {
    // response 是 Axios 包装的响应对象
    // response.data 才是后端 Controller 返回的真正 JSON 数据
    const res = response.data; 
    
    if (res.code === 200) {
      console.log('解析出的业务数据:', res.data);
      // 将数据渲染到页面上...
    } else {
      alert('错误: ' + res.message);
    }
  })
  .catch(error => {
    console.error('网络请求失败', error);
  });
```



###### 第一层：`response`（Axios 包装的响应对象）

当你发起 `axios.get` 请求后，Axios 并不会直接把后端的 JSON 扔给你，而是包装在一个 HTTP Response 对象里。这个 `response` 包含了很多网络请求的信息：

*   `response.status`：HTTP 状态码（如 200 OK, 404 Not Found）
*   `response.headers`：响应头信息
*   `response.config`：请求的配置信息
*   **`response.data`**：后端返回的 HTTP Body（响应体），Axios 会自动将 JSON 字符串转为 JS 对象。

###### 第二层：`response.data`（被赋值给了 `res`）

因为前端只关心后端返回的报文内容，所以代码做了这一步：

```javascript
const res = response.data; 
```

此时，`res` 拿到的是后端 Controller 返回的**完整 JSON 对象**：

```javascript
{
  "code": 200,
  "message": "success",
  "data": {
    "id": 1,
    "name": "张三"
  }
}
```

###### 第三层：`res.data`（你要找的答案）

代码接着判断 `if (res.code === 200)`，确认业务成功后，去取真正的业务数据：

```javascript
console.log('解析出的业务数据:', res.data);
```

因为 `res` 就是上面那个包含 `code`、`message`、`data` 的大对象，所以 `res.data` 就是取大对象里的 `data` 属性。

最终，`res.data` 就得到了纯净的用户信息：

```javascript
{
  "id": 1,
  "name": "张三"
}
```

###### 总结

在前后端分离的开发中，经常会出现这种“双层 data”的现象：

1. **第一个 `data`**（`response.data`）：是 Axios 框架用来存放 HTTP 响应体的固定属性。
2. **第二个 `data`**（`res.data`）：是后端开发人员自定义的 JSON 规范中，用来存放业务数据的字段名。

所以在实际写代码时，经常看到 `response.data.data` 这种看似奇怪的写法，其实就是这两者叠加的结果。

##### 2. 使用 Fetch

Fetch 需要手动调用 `.json()` 方法来解析 JSON。

```javascript
fetch('/api/user/1')
  .then(response => {
    if (!response.ok) throw new Error('网络响应异常');
    return response.json(); // 手动解析 JSON
  })
  .then(res => {
    // 这里的 res 就等同于上面 Axios 里的 response.data
    if (res.code === 200) {
      console.log('业务数据:', res.data);
    }
  });
```

---

#### 第三步：最佳实践 —— 使用 Axios 响应拦截器统一解析

在实际项目中，如果每次请求都写 `if (res.code === 200)` 会非常冗余。通常会在 Axios 拦截器中统一解析数据，前端页面直接拿到纯净的业务数据。

```javascript
// 配置 Axios 响应拦截器
axios.interceptors.response.use(
  (response) => {
    const res = response.data; // 获取后端返回的完整 JSON

    // 根据后端约定的 code 进行判断
    if (res.code !== 200) {
      // 统一处理错误提示
      alert(res.message || '系统异常');
      return Promise.reject(new Error(res.message || 'Error'));
    } else {
      // 核心：直接返回剥离后的业务数据 res.data
      // 这样在前端业务代码中，接收到的就是干净的数据，不再包含 code 和 message
      return res.data; 
    }
  },
  (error) => {
    // 处理 HTTP 状态码错误 (如 404, 500)
    console.log('请求错误', error.message);
    return Promise.reject(error);
  }
);

// ================= 前端业务代码调用 =================
// 此处接收到的 user 就是后端 res.data 里的内容，可以直接使用
axios.get('/api/user/1').then(user => {
  console.log(user.name); // 直接输出 "张三"
});
```

---

#### 第四步：处理特殊数据类型

JSON 原生只支持基本类型（String, Number, Boolean, Array, Object, null）。有些后端的数据类型前端需要特殊解析：

##### 1. 日期时间解析

后端返回的日期通常是时间戳（如 `1698765432000`）或 ISO 字符串（如 `"2023-10-31T10:00:00Z"`）。

```javascript
// 将时间戳转为本地可读格式
let timestamp = 1698765432000;
let dateObj = new Date(timestamp);
console.log(dateObj.toLocaleString()); // "2023/10/31 18:17:12"
```

##### 2. Long 类型精度丢失问题（大坑）

JavaScript 的 Number 类型最大安全整数是 `2^53 - 1`（即 `9007199254740991`）。后端 Java 的 Long 类型如果超过了这个值（如雪花算法生成的 ID），前端解析会丢失精度（末尾变成 0）。

*   **解决办法**：后端通常会将 Long 转为 String 返回，前端直接当字符串处理即可。如果后端没转，前端可以使用 `json-bigint` 库解析。

##### 3. 文件流数据

如果后端返回的是文件（如导出 Excel、验证码图片），前端需要设置响应类型为 `blob`。

```javascript
axios.get('/api/export', { responseType: 'blob' })
  .then(response => {
    // response.data 此时是一个 Blob 对象
    const url = window.URL.createObjectURL(response.data);
    const a = document.createElement('a');
    a.href = url;
    a.download = '统计表.xlsx';
    a.click();
    window.URL.revokeObjectURL(url);
  });
```

---

#### 第五步：结合 TypeScript 进行数据类型校验（进阶）

在大型项目中，为了避免后端少传字段或字段名拼错，前端会定义 TypeScript 接口来约束解析出来的数据。

```typescript
// 1. 定义后端返回的数据类型
interface User {
  id: number;
  name: string;
  age: number;
}

// 2. 在请求时指定泛型
function getUser(): Promise<User> {
  return axios.get('/api/user/1'); // 假设已经配置了拦截器返回 res.data
}

// 3. 使用数据
getUser().then((user: User) => {
  // 这里的 user 会有 TS 类型提示，如果拼错字段名会报错
  console.log(user.name); 
});
```

#### 总结

1. 用 `Axios` 或 `Fetch` 发起请求。
2. 拿到后端返回的 JSON 字符串（Axios 自动转对象，Fetch 需调 `.json()`）。
3. 判断外层 `code` 是否成功，成功则提取内层 `data`。
4. 推荐使用**Axios响应拦截器**全局处理提取过程，让业务代码只关心 `data`。
5. 注意日期格式化、大数字精度丢失、文件流等特殊数据的解析。

### 4.2 Vue 3 解析后端数据最佳实践（setup + TS + Pinia）

在 Vue 3 中，解析后端 Controller 数据的**底层逻辑（JSON转对象、提取 `data`、处理精度等）与普通前端完全一样**。

Vue 3 的独特之处在于：它使用 **Composition API（组合式 API）** 和 **响应式系统（`ref`、`reactive`）** 来接收解析后的数据，并自动更新到视图上。

以下是在 Vue 3 中解析和接收后端数据的标准流程和最佳实践：

---

#### 第一步：全局配置 Axios 拦截器（剥离核心数据）

在 Vue 3 项目中，通常会在 `src/utils/request.js` 中统一配置 Axios。这一步的作用和前面讲的一样：**把后端返回的 `{ code, message, data }` 中的 `data` 剥离出来**。

```javascript
// src/utils/request.js
import axios from 'axios';

const service = axios.create({
  baseURL: '/api', 
  timeout: 5000
});

// 响应拦截器：在这里解析后端的统一格式
service.interceptors.response.use(
  (response) => {
    const res = response.data; // 获取后端返回的完整 JSON
    
    // 假设后端约定 code 为 20000 表示成功
    if (res.code !== 20000) {
      // 可以结合 Vue 3 的组件库 (如 ElMessage) 弹出错误提示
      ElMessage.error(res.message || '请求失败');
      return Promise.reject(new Error(res.message || 'Error'));
    } else {
      // 核心：只返回纯净的业务数据 (res.data)
      return res.data; 
    }
  },
  (error) => {
    ElMessage.error('网络异常');
    return Promise.reject(error);
  }
);

export default service;
```

---

#### 第二步：在 Vue 3 组件中接收并解析数据 (`<script setup>`)

这是 Vue 3 最常用的写法。我们使用 `ref` 来定义响应式变量，并在 `onMounted` 生命周期钩子中发起请求。

```vue
<template>
  <div>
    <!-- 3. 视图层直接使用解析好的数据 -->
    <div v-if="loading">加载中...</div>
    <div v-else-if="userInfo">
      <p>ID: {{ userInfo.id }}</p>
      <p>姓名: {{ userInfo.name }}</p>
      <p>注册时间: {{ formatTime(userInfo.createTime) }}</p>
    </div>
  </div>
</template>

<script setup>
import { ref, onMounted } from 'vue'
import request from '@/utils/request' // 引入配置好的 axios

// 1. 定义响应式状态
const userInfo = ref(null) // 用于存放解析出来的业务数据
const loading = ref(false)

// 2. 定义获取数据的方法
const fetchUserInfo = async () => {
  loading.value = true
  try {
    // 这里的 data 就是拦截器剥离后返回的 res.data
    const data = await request.get('/user/1')
    
    // 将解析出的数据赋值给 ref 的 .value
    userInfo.value = data 
  } catch (error) {
    console.error('解析数据失败:', error)
  } finally {
    loading.value = false
  }
}

// 生命周期：组件挂载后执行
onMounted(() => {
  fetchUserInfo()
})

// 处理特殊数据：比如时间戳转格式
const formatTime = (timestamp) => {
  return new Date(timestamp).toLocaleString()
}
</script>
```

---

#### 第三步：进阶实践 —— 使用 TypeScript 定义数据结构

Vue 3 对 TypeScript 支持极好。在解析后端数据时，强烈建议定义 `interface`，这样在写模板和逻辑时都有完整的类型提示，防止拼错字段。

```vue
<template>
  <div v-if="userInfo">
    <!-- 这里的 .id .name 会有 TS 智能提示 -->
    {{ userInfo.name }} ({{ userInfo.age }}岁)
  </div>
</template>

<script setup lang="ts">
import { ref, onMounted } from 'vue'
import request from '@/utils/request'

// 1. 定义后端返回数据的类型
interface User {
  id: number
  name: string
  age: number
  createTime: number
}

// 2. 给 ref 指定泛型 <User>
// 初始值为 null，所以类型是 User | null
const userInfo = ref<User | null>(null)

const fetchUserInfo = async () => {
  try {
    // 3. 接收数据时，TS 会自动校验返回的数据结构是否符合 User
    const data = await request.get<any, User>('/user/1')
    userInfo.value = data
  } catch (error) {
    // ...
  }
}

onMounted(fetchUserInfo)
</script>
```

---

#### 第四步：结合 Pinia (状态管理) 解析全局数据

如果后端返回的数据（如用户登录信息、权限菜单）需要在多个组件中共享，Vue 3 通常会将解析逻辑放在 Pinia 的 `actions` 中。

```typescript
// src/store/user.ts
import { defineStore } from 'pinia'
import { ref } from 'vue'
import request from '@/utils/request'

export const useUserStore = defineStore('user', () => {
  const token = ref('')
  const roles = ref<string[]>([])

  // 登录并解析后端返回的 Token 和权限
  const login = async (loginForm) => {
    try {
      // 后端返回: { token: "xxx", roles: ["admin"] }
      const data = await request.post('/login', loginForm)
      
      // 解析并存储到状态管理中
      token.value = data.token
      roles.value = data.roles
      
      // 可选：存入 localStorage
      localStorage.setItem('token', data.token)
    } catch (error) {
      console.error('登录失败', error)
    }
  }

  return { token, roles, login }
})
```

#### 总结：Vue 3 解析后端数据的模式

1. **拦截器层**：在 Axios 拦截器中完成 JSON 提取和 `code` 判断，把纯净的 `data` 抛给组件。
2. **逻辑层 (`script setup`)**：使用 `async/await` 接收 `data`，赋值给 `ref` 或 `reactive` 定义的变量。
3. **类型层 (TS)**：使用 `interface` 约束接收的数据，让开发更安全。
4. **视图层 (`template`)**：无需关心怎么解析的，直接通过 `{{ 变量.字段 }}` 绑定数据，Vue 的响应式系统会自动更新 DOM。

这段代码展示的是一种**“手动层级解包 + 数组字段映射”**的解析方式。

### 4.3 Vue 2 与 Vue 3 数据解析写法演进与对比

但需要首先纠正一个关键点：**这段代码严格来说并不是 Vue 3 推荐的 `<script setup>` (Composition API) 写法，而是 Vue 2 (Options API) 的典型写法，或者是 Vue 3 中依然兼容的 Options API 写法。**

下面为您详细拆解这种解析方式的具体含义和特点：

#### 1. 代码拆解分析

```javascript
queryLineAccountingList(params).then((res) => {
  // 1. 手动安全校验：判断后端返回的业务状态
  if (res.data && res.data.success) {
    
    // 2. 逐层解包与容错处理：
    // res.data.info?.result 使用了可选链操作符 (?.)
    // 如果 info 为空，不会报错，而是返回 undefined
    // || [] 表示如果前面取不到值，就默认给一个空数组，防止后续 .map 报错
    const list = res.data.info?.result || [];
    
    // 3. 数据清洗与字段映射：
    // 遍历后端返回的数组，将后端的字段名重命名为前端页面需要的字段名
    this.tableData.list = list.map(item => ({
        erpId: item.erpId,
        receiveNo: item.rcvNo,               // 后端叫 rcvNo，前端叫 receiveNo
        receiveApprovalDate: item.requestDate, // 后端叫 requestDate，前端叫 receiveApprovalDate
        budgetCode: item.budgetName,
        rcmpId: item.rcmpId,
        receiveCurrency: item.currencyCode,
        receiveAmountByRcmpId: item.lineAmountInc
    }));
  }
})
```

#### 2. 为什么说它不是纯正的 Vue 3 写法？

代码中出现了 `this.tableData.list = ...`。

*   **在 Vue 2 中**：`this` 指向当前组件实例，`tableData` 定义在 `data()` 中，所以可以通过 `this.tableData` 赋值。
*   **在 Vue 3 的 `<script setup>` 中**：是不存在 `this` 的。数据通常使用 `ref` 或 `reactive` 定义，赋值时应该是 `tableData.value.list = ...` 或 `tableData.list = ...`（如果是 reactive）。

#### 3. 这种解析方式的优缺点

这是前端开发中**非常经典且常用**的一种业务数据处理模式。

**优点：**

1.  **前后端解耦（字段映射）**：后端的数据库字段命名规则（如 `rcvNo`）可能和前端页面展示要求的语义不一致。通过 `map` 映射，前端代码只关心 `receiveNo`，即使后端以后改字段名，前端只需改这一处映射关系即可。
2.  **极高的容错性**：`res.data && res.data.success` 和 `?.result || []` 这种防御性编程，保证了即使后端返回空数据或异常结构，前端代码也不会因为报错而白屏。

**缺点：**

1.  **没有利用 Axios 拦截器统一处理**：代码里还保留了 `res.data.success` 这种判断，说明 Axios 响应拦截器没有做全局的剥离工作，导致每个业务组件里都要写一遍 `if (res.data.success)`，比较冗余。
2.  **不够优雅**：如果有大量类似接口，每个地方都写一遍 `map` 映射会很麻烦。

#### 4. 如果改写成纯正的 Vue 3 (`<script setup>`) 写法，应该是这样：

```vue
<script setup>
import { ref, onMounted } from 'vue'
import { queryLineAccountingList } from '@/api/xxx' // 假设接口已封装

// 定义响应式数据 (取代了 Vue2 的 data() 和 this)
const tableData = ref({
  list: []
})

const getList = async (params) => {
  try {
    const res = await queryLineAccountingList(params)
    
    // 业务状态判断
    if (res.data && res.data.success) {
      const list = res.data.info?.result || []
      
      // 字段映射 (注意这里去掉了 this)
      tableData.value.list = list.map(item => ({
        erpId: item.erpId,
        receiveNo: item.rcvNo,
        receiveApprovalDate: item.requestDate,
        budgetCode: item.budgetName,
        rcmpId: item.rcmpId,
        receiveCurrency: item.currencyCode,
        receiveAmountByRcmpId: item.lineAmountInc
      }))
    }
  } catch (error) {
    console.error('获取列表失败', error)
  }
}

onMounted(() => {
  getList({ page: 1 })
})
</script>
```

#### 总结

这段代码使用的是**防御性解包 + 自定义字段重命名映射**的解析方式。逻辑上非常严谨且实用，但从语法特征来看，它基于 Vue 2 的 Options API (`this` 关键字），如果在 Vue 3 项目中，建议迁移到 Composition API (`ref` / `reactive`) 的写法。

### 4.4 Axios 企业级封装与全场景用法

**Axios** 是目前前端开发中最流行、最主流的 HTTP 请求库。无论是 Vue、React 还是 Angular 项目，它几乎是发送网络请求的标配。

简单来说，它的作用就是：**让前端能够轻松地向后端发请求（要数据 / 传数据），并处理后端返回的数据。**

为了让你全面了解 Axios，我们可以从以下几个核心方面来看：

---

#### 一、为什么都用 Axios？（对比原生 Fetch）

浏览器原生自带 `fetch`，为什么我们还要用 Axios？

1. **自动转换 JSON**：`fetch` 需要你手动调 `response.json()` 才能拿到对象；Axios 会自动把后端返回的 JSON 字符串转为 JS 对象。
2. **更友好的错误处理**：当后端返回 404 或 500 时，`fetch` 不会报错，依然走 `.then()`，需要你自己判断；**Axios 只要 HTTP 状态码不是 2xx，就会自动进入 `.catch()`**，方便统一处理错误。
3. **拦截器机制**：这是 Axios 最强大的功能。可以在请求发出前、响应到达前，统一做一些操作（比如加 Token、统一剥离外层数据）。
4. **超时控制与取消请求**：Axios 只需配一个 `timeout: 5000` 就能搞定超时，而 `fetch` 实现起来非常麻烦。
5. **防 XSRF（跨站请求伪造）攻击**：内置了防御机制。

---

#### 二、基础用法（CRUD 增删改查）

Axios 支持 Promise，所以可以用 `.then()` 也可以用 `async/await`。

##### 1. GET 请求（查询数据）

通常用来获取数据，参数拼在 URL 上。

```javascript
// 传统写法
axios.get('/api/users', {
  params: { id: 1 }  // 会被拼接成 /api/users?id=1
}).then(res => console.log(res.data));

// async/await 写法（推荐）
const res = await axios.get('/api/users', { params: { id: 1 } });
console.log(res.data);
```

##### 2. POST 请求（提交数据）

通常用来创建新数据，数据放在 Body 里（JSON 格式）。

```javascript
const res = await axios.post('/api/users', {
  name: '张三',
  age: 25
});
```

##### 3. PUT / DELETE 请求（更新 / 删除）

```javascript
// 更新 id 为 1 的用户
await axios.put('/api/users/1', { name: '李四' });

// 删除 id 为 1 的用户
await axios.delete('/api/users/1');
```

---

#### 三、企业级标准用法（重点）

在实际项目（如 Vue3）中，我们**绝不会**在每个组件里直接写 `axios.get()`，而是会进行封装。

##### 1. 创建实例

避免把基础地址写死在各个地方。

```javascript
// src/utils/request.js
import axios from 'axios';

const service = axios.create({
  baseURL: 'https://api.example.com', // 基础路径
  timeout: 5000                       // 超时时间 5秒
});
```

##### 2. 配置请求拦截器

在请求**发出去之前**，统一做一些手脚。比如：带上登录 Token。

```javascript
service.interceptors.request.use(
  (config) => {
    // 从本地取出 Token
    const token = localStorage.getItem('token');
    if (token) {
      // 统一塞到请求头里
      config.headers['Authorization'] = 'Bearer ' + token;
    }
    return config;
  },
  (error) => Promise.reject(error)
);
```

##### 3. 配置响应拦截器

在响应**到达组件之前**，统一做数据剥离和错误提示。

```javascript
service.interceptors.response.use(
  (response) => {
    const res = response.data; // 拿到后端真正的 JSON

    // 假设后端规定 code=200 是成功
    if (res.code !== 200) {
      alert(res.message); // 统一弹错误提示
      return Promise.reject(new Error(res.message));
    } else {
      return res.data; // ⭐ 核心：直接把纯净的业务数据抛给组件
    }
  },
  (error) => {
    // 处理 HTTP 网络错误 (如 401, 404, 500)
    if (error.response.status === 401) {
      alert('登录过期，请重新登录');
    }
    return Promise.reject(error);
  }
);
export default service;
```

##### 4. 组件中调用封装好的实例

```javascript
// src/api/user.js
import request from '@/utils/request';

export function getUserInfo(id) {
  return request.get(`/users/${id}`); // 这里返回的已经是剥离后的纯数据了
}
```

#### 四、Axios 传参的 3 个核心位置

在写 Axios 时，经常容易混淆参数该放哪里，记住这 3 个位置：

```javascript
axios({
  method: 'POST',
  url: '/api/users/1',
  
  // 1. params: 会拼接在 URL 问号后面 (?type=admin)
  // 后端用 @RequestParam 接收
  params: { 
    type: 'admin' 
  },
  
  // 2. data: 放在请求体 里
  // 后端用 @RequestBody 接收
  data: { 
    name: '张三' 
  },
  
  // 3. headers: 放在请求头里
  // 后端用 @RequestHeader 接收
  headers: { 
    'X-Token': 'xxx' 
  }
})
```

#### 总结

Axios 就是前端与后端沟通的**“快递员”**。你把参数交给它，它帮你打包成 HTTP 请求发给后端；后端把数据返回给它，它再把数据整理好交给你（前端组件）。它提供的拦截器机制，让前端能够极其优雅地统一处理 Token 注入、错误提示和数据清洗。

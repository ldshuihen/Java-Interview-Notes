## 一、对象转换、序列化与工程通用规范

### 1.1 对象属性拷贝（VO / DTO / DO / BO 转换全攻略）

在 Java 分层架构开发中，不同层级的对象转换是日常高频操作。

#### 一、核心概念定位与方案总览

##### 1. 分层对象定位

| 对象类型 | 作用 | 典型场景 |
| :--- | :--- | :--- |
| **Entity / DO** | 映射数据库表结构，与 DAO 层交互 | 数据库 CRUD 操作 |
| **DTO** | 跨服务/跨层传输数据（如 Controller ↔ 前端、Feign 调用） | 接口入参/出参、微服务间数据传递 |
| **VO** | 前端展示专用，定制化字段格式 | 接口返回给前端的最终数据（如日期格式化、字段别名、敏感字段屏蔽） |
| **BO** | 业务层封装的对象，聚合多个 DO/DTO 承载业务逻辑 | 服务层内部复杂业务处理（如分类+标签聚合 BO） |

##### 2. 主流转换方案对比（按推荐优先级排序）

| 方案 | 实现原理 | 性能 | 易用性 | 支持深拷贝 | 支持不同名/异构属性 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **MapStruct** | 编译期生成 `set/get` 代码（无反射） | **极高** | 中 | 需配置嵌套转换 | ✅ 完美支持 | **企业级中大型项目、高并发生产环境首选** |
| **Hutool BeanUtil** | 反射 + 缓存优化 | 中高 | **极高** | ✅ 支持（结合 JSON/Map） | ✅ 支持（别名映射） | 国产全能工具、中小项目快速开发 |
| **Spring BeanUtils** | 反射 + 内省缓存 | 高 | **极高** | ❌ 不支持 | ❌ 不支持 | 快速开发、简单同名同类型属性拷贝 |
| **手动 set/get** | 原生硬编码调用 | **极高** | 低 | ✅ 支持 | ✅ 支持 | 字段极少、转换逻辑高度定制化 |
| **ModelMapper / Orika** | 运行时反射 / 字节码生成 | 中 | 高 | ✅ 支持 | ✅ 支持 | 原型开发（生产使用较少） |
| **Apache BeanUtils** | 反射 + 大量日志校验与类型转换 | **极低** | 中 | ❌ 不支持 | ❌ 不支持 | ❌ **严禁使用**（性能极差，高并发易引发故障） |

#### 二、方案 1：【企业级首选】MapStruct（编译期生成代码，性能天花板）

##### 1. 核心优势
1. **零反射损耗**：编译期自动生成纯手写级别的 `set/get` 代码，性能与手写完全一致。
2. **编译期类型安全**：字段名写错或类型不兼容在编译期直接报错，杜绝线上运行时隐患。
3. **支持复杂映射**：异名字段、嵌套对象、集合批量转换、枚举转换、日期格式化、多源合并、自定义表达式。
4. **Spring 无缝集成**：配置 `componentModel = "spring"` 后可直接通过 `@Resource` / `@Autowired` 注入使用。

##### 2. Maven 依赖配置（SpringBoot + Lombok 环境）

> **注意**：`mapstruct-processor` 必须配置在 `annotationProcessorPaths` 中；若项目同时使用 Lombok，需将 `lombok` 与 `lombok-mapstruct-binding` 一并声明，否则 MapStruct 找不到 Lombok 生成的 `getter/setter`。

```xml
<dependencies>
    <!-- MapStruct 核心 API -->
    <dependency>
        <groupId>org.mapstruct</groupId>
        <artifactId>mapstruct</artifactId>
        <version>1.5.5.Final</version>
    </dependency>
</dependencies>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.8.1</version>
            <configuration>
                <source>1.8</source>
                <target>1.8</target>
                <encoding>UTF-8</encoding>
                <annotationProcessorPaths>
                    <!-- MapStruct 注解处理器 -->
                    <path>
                        <groupId>org.mapstruct</groupId>
                        <artifactId>mapstruct-processor</artifactId>
                        <version>1.5.5.Final</version>
                    </path>
                    <!-- 若使用 Lombok，需同时配置以下两项 -->
                    <path>
                        <groupId>org.projectlombok</groupId>
                        <artifactId>lombok</artifactId>
                        <version>1.18.30</version>
                    </path>
                    <path>
                        <groupId>org.projectlombok</groupId>
                        <artifactId>lombok-mapstruct-binding</artifactId>
                        <version>0.2.0</version>
                    </path>
                </annotationProcessorPaths>
            </configuration>
        </plugin>
    </plugins>
</build>
```

##### 3. 标准实体定义（DO / DTO / 嵌套对象）

```java
@Data
public class UserDO {
    private Long id;
    private String username;
    private String password;          // 敏感字段，DTO 需屏蔽
    private Integer age;
    private String userEmail;         // 与 DTO 不同名字段
    private RoleDO role;              // 嵌套对象
    private LocalDateTime createTime; // 时间类型转换
}

@Data
public class RoleDO {
    private Long roleId;
    private String roleName;
}

@Data
public class UserDTO {
    private Long id;
    private String username;
    private Integer age;
    private String ageDesc;           // 自定义转换逻辑字段
    private String email;             // 对应 DO 的 userEmail
    private RoleDTO role;             // 嵌套 DTO
    private String createTime;        // 格式化后的时间字符串
}

@Data
public class RoleDTO {
    private Long roleId;
    private String roleName;
}
```

##### 4. 编写 MapStruct 转换接口（万能模板）

> **最佳实践**：要么统一使用 **Spring 注入模式**（`componentModel = "spring"`，推荐），要么统一使用 **`INSTANCE` 单例模式**（无 Spring 环境），不要混用。

```java
import org.mapstruct.*;
import org.mapstruct.factory.Mappers;
import java.util.List;

@Mapper(
    componentModel = "spring",
    unmappedTargetPolicy = ReportingPolicy.IGNORE // 忽略未映射的目标字段，避免编译警告
)
public interface UserConverter {

    // 非 Spring 环境下的单例实例（使用 Spring 注入时可省略）
    UserConverter INSTANCE = Mappers.getMapper(UserConverter.class);

    // ==================== 1. 单个对象正向映射 ====================
    @Mapping(source = "userEmail", target = "email")
    @Mapping(source = "createTime", target = "createTime", dateFormat = "yyyy-MM-dd HH:mm:ss")
    @Mapping(source = "age", target = "ageDesc", qualifiedByName = "ageToDesc")
    UserDTO doToDto(UserDO userDO);

    // ==================== 2. 反向映射 ====================
    @InheritInverseConfiguration(name = "doToDto")
    @Mapping(target = "password", ignore = true) // 显式忽略敏感字段
    UserDO dtoToDo(UserDTO userDTO);

    // ==================== 3. 集合批量映射（自动循环调用 doToDto） ====================
    List<UserDTO> doListToDtoList(List<UserDO> userDOList);

    // ==================== 4. 嵌套对象映射（自动被 doToDto 调用） ====================
    RoleDTO roleDoToDto(RoleDO roleDO);

    // ==================== 5. 多个源对象合并为一个目标对象 ====================
    @Mapping(source = "user.id", target = "id")
    @Mapping(source = "user.username", target = "username")
    @Mapping(source = "role", target = "role")
    UserDTO mergeToDto(UserDO user, RoleDO role);

    // ==================== 6. 常量与 Java 表达式默认值 ====================
    @Mapping(target = "ageDesc", constant = "默认成年")
    @Mapping(target = "createTime", expression = "java(java.time.LocalDateTime.now().toString())")
    UserDTO doToDtoWithDefault(UserDO userDO);

    // ==================== 7. 自定义复杂转换方法 ====================
    @Named("ageToDesc")
    default String ageToDesc(Integer age) {
        if (age == null) return "未知";
        return age >= 18 ? "成年" : "未成年";
    }
}
```

##### 5. 业务层注入使用与生成代码验证

```java
@Service
@RequiredArgsConstructor
public class UserService {

    private final UserConverter userConverter;

    public UserDTO getUser(Long userId) {
        UserDO userDO = userMapper.selectById(userId);
        return userConverter.doToDto(userDO);
    }

    public List<UserDTO> listUsers() {
        List<UserDO> userDOList = userMapper.selectList(null);
        return userConverter.doListToDtoList(userDOList);
    }
}
```

执行 `mvn compile` 后，可在 `target/generated-sources/annotations/.../UserConverterImpl.java` 中查看生成的实现类，本质是带判空保护的纯 `set/get` 调用：

```java
@Generated(value = "org.mapstruct.ap.MappingProcessor")
@Component
public class UserConverterImpl implements UserConverter {
    @Override
    public UserDTO doToDto(UserDO userDO) {
        if (userDO == null) {
            return null;
        }
        UserDTO userDTO = new UserDTO();
        userDTO.setEmail(userDO.getUserEmail());
        if (userDO.getCreateTime() != null) {
            userDTO.setCreateTime(DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss").format(userDO.getCreateTime()));
        }
        userDTO.setAgeDesc(ageToDesc(userDO.getAge()));
        userDTO.setId(userDO.getId());
        userDTO.setUsername(userDO.getUsername());
        userDTO.setAge(userDO.getAge());
        userDTO.setRole(roleDoToDto(userDO.getRole()));
        return userDTO;
    }
}
```

##### 2. 高频业务场景速查

```java
// 1. 基础同名属性拷贝（创建新对象）
UserDTO dto = BeanUtil.copyProperties(userDO, UserDTO.class);

// 2. 拷贝到已有对象
UserDTO existDto = new UserDTO();
BeanUtil.copyProperties(userDO, existDto);

// 3. 忽略指定字段（如不拷贝 id、password）
UserDTO ignoreDto = BeanUtil.copyProperties(userDO, UserDTO.class, "id", "password");

// 4. 集合批量拷贝
List<UserDTO> dtoList = BeanUtil.copyToList(doList, UserDTO.class);

// 5. 忽略源对象中的 null 值（增量更新场景：源字段为 null 时不覆盖目标对象原有值）
BeanUtil.copyProperties(
    userDO,
    existDto,
    CopyOptions.create().setIgnoreNullValue(true)
);

// 6. 自定义字段名映射（userEmail -> email）
Map<String, String> fieldMapping = Collections.singletonMap("userEmail", "email");
BeanUtil.copyProperties(
    userDO,
    existDto,
    CopyOptions.create().setFieldMapping(fieldMapping)
);

// 7. 对象 ↔ Map 互转
Map<String, Object> map = BeanUtil.beanToMap(userDO);
UserDTO fromMap = BeanUtil.toBean(map, UserDTO.class);
```

##### 3. 企业级通用工具类封装（含浅拷贝、列表拷贝、忽略 Null、JSON 深拷贝）

```java
import cn.hutool.core.bean.BeanUtil;
import cn.hutool.core.bean.copier.CopyOptions;
import cn.hutool.json.JSONUtil;
import java.util.Collections;
import java.util.List;

/**
 * 通用对象属性拷贝工具类（基于 Hutool）
 */
public final class BeanConvertUtils {

    private BeanConvertUtils() {}

    /**
     * 单个对象浅拷贝
     */
    public static <T> T copy(Object source, Class<T> targetClass) {
        if (source == null) {
            return null;
        }
        return BeanUtil.copyProperties(source, targetClass);
    }

    /**
     * 集合列表浅拷贝
     */
    public static <T> List<T> copyList(List<?> sourceList, Class<T> targetClass) {
        if (sourceList == null || sourceList.isEmpty()) {
            return Collections.emptyList();
        }
        return BeanUtil.copyToList(sourceList, targetClass);
    }

    /**
     * 增量拷贝（忽略源对象中的 null 值，不覆盖目标对象已有属性）
     */
    public static void copyIgnoreNull(Object source, Object target) {
        if (source == null || target == null) {
            return;
        }
        BeanUtil.copyProperties(source, target, CopyOptions.create().setIgnoreNullValue(true));
    }

    /**
     * 深拷贝（基于 JSON 序列化，源对象与目标对象引用完全独立）
     */
    public static <T> T deepCopy(Object source, Class<T> targetClass) {
        if (source == null) {
            return null;
        }
        return JSONUtil.toBean(JSONUtil.toJsonStr(source), targetClass);
    }
}
```

#### 四、方案 3：Spring BeanUtils 与方案 4：手动 Convertor

##### 1. Spring `BeanUtils.copyProperties`
Spring 自带工具类，零额外依赖，适合简单同名同类型属性浅拷贝：
```java
import org.springframework.beans.BeanUtils;

UserDTO dto = new UserDTO();
// 注意参数顺序：(source, target)，还可以传第 3 个可变参数 ignoreProperties
BeanUtils.copyProperties(userDO, dto, "password");
```
> **局限性**：仅支持同名同类型属性；不支持嵌套对象转换；属于**浅拷贝**。

##### 2. 手动 Convertor 静态工具类
适合字段少、包含复杂计算或脱敏规则、追求极致可控的场景：
```java
public final class UserManualConverter {
    public static UserDTO entityToDTO(UserDO entity) {
        if (entity == null) {
            return null;
        }
        UserDTO dto = new UserDTO();
        dto.setId(entity.getId());
        dto.setUsername(entity.getUsername());
        dto.setEmail(entity.getUserEmail());
        // 屏蔽 password，手动格式化时间
        if (entity.getCreateTime() != null) {
            dto.setCreateTime(DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss").format(entity.getCreateTime()));
        }
        return dto;
    }
}
```

#### 五、浅拷贝 vs 深拷贝核心避坑

1. **浅拷贝（默认行为）**：`Spring BeanUtils`、`Hutool BeanUtil.copyProperties` 默认均为浅拷贝，只复制基本数据类型和 `String`，对于嵌套引用对象或 `List` 集合**只复制内存地址**。修改目标对象的嵌套属性会同步污染源对象。
2. **深拷贝（完全隔离）**：
   - **MapStruct 方案**：为所有嵌套子对象也定义对应的转换方法（如 `RoleDTO roleDoToDto(RoleDO roleDO)`），MapStruct 会生成新建子对象的深拷贝代码。
   - **JSON 序列化方案**：通过 Jackson / FastJSON / Hutool `JSONUtil` 将源对象序列化为 JSON 字符串再反序列化为目标类。
3. **通用注意事项**：
   - 严禁将 `Long` 强转映射到 `Integer`（谨防精度溢出）；
   - DTO/VO 严禁包含 `password`、`salt`、`secretKey` 等敏感字段；
   - 所有转换入口必须优先做 `null` 判空保护。

### 1.2 日期时间 JSON 序列化与反序列化（Jackson & FastJSON2）

#### 一、核心痛点与类型选型建议

##### 1. 四大常见痛点
1. **默认格式不友好**：`java.util.Date` 默认序列化为毫秒时间戳（如 `1704067200000`），`LocalDateTime` 默认带 `T`（ISO 格式 `2025-01-01T12:00:00`）或因缺少模块直接报错 `No serializer found for class java.time.LocalDateTime`。
2. **反序列化失败**：前端传 `"2025-01-01 12:00:00"`，Jackson 默认只识别 ISO 格式，抛出 `InvalidFormatException`。
3. **时区偏差 8 小时**：未显式指定东八区 `GMT+8` / `Asia/Shanghai`，导致按 UTC 解析或输出相差 8 小时。
4. **全局统一与局部特例冲突**：95% 字段用 `yyyy-MM-dd HH:mm:ss`，个别字段需精确到毫秒或使用时间戳。

##### 2. Java 时间类型推荐表

| Java 类型 | 推荐方案 | 说明 |
| :--- | :--- | :--- |
| **`LocalDateTime`**（首选） | 全局注册 `JavaTimeModule` + 关键字段 `@JsonFormat` | JDK8+ 标准，不可变且线程安全；无时区概念，推荐业务实体全面采用 |
| **`LocalDate` / `LocalTime`** | 全局配置 `yyyy-MM-dd` / `HH:mm:ss` | 适用于生日、账期、打卡时间等纯日期/纯时间字段 |
| **`java.util.Date`**（旧项目） | 全局 `time-zone: GMT+8` + `date-format` | 可变对象非线程安全，必须显式绑定时区 |
| **`Instant`** | 保持 ISO-8601 UTC 格式或毫秒时间戳 | 适合跨国多时区系统、审计日志时间戳 |

#### 二、SpringBoot 默认：Jackson 完整解决方案

##### 1. 依赖说明
Spring Boot 2.x 需确保引入 `jackson-datatype-jsr310`（`spring-boot-starter-json` 通常已传递依赖，Spring Boot 3.x 已原生内置）：

##### 2. 全局统一配置方案 A：`Jackson2ObjectMapperBuilderCustomizer`（推荐，零侵入）

一次配置，项目内所有 `Date`、`LocalDateTime`、`LocalDate`、`LocalTime` 自动双向格式化：

```java
import com.fasterxml.jackson.annotation.JsonInclude;
import com.fasterxml.jackson.datatype.jsr310.JavaTimeModule;
import com.fasterxml.jackson.datatype.jsr310.deser.LocalDateDeserializer;
import com.fasterxml.jackson.datatype.jsr310.deser.LocalDateTimeDeserializer;
import com.fasterxml.jackson.datatype.jsr310.deser.LocalTimeDeserializer;
import com.fasterxml.jackson.datatype.jsr310.ser.LocalDateSerializer;
import com.fasterxml.jackson.datatype.jsr310.ser.LocalDateTimeSerializer;
import com.fasterxml.jackson.datatype.jsr310.ser.LocalTimeSerializer;
import org.springframework.boot.autoconfigure.jackson.Jackson2ObjectMapperBuilderCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.convert.converter.Converter;

import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.LocalTime;
import java.time.format.DateTimeFormatter;
import java.util.TimeZone;

@Configuration
public class JacksonDateConfig {

    public static final String DATE_TIME_PATTERN = "yyyy-MM-dd HH:mm:ss";
    public static final String DATE_PATTERN = "yyyy-MM-dd";
    public static final String TIME_PATTERN = "HH:mm:ss";

    /**
     * 1. JSON 请求体 (@RequestBody / @ResponseBody) 全局双向格式化
     */
    @Bean
    public Jackson2ObjectMapperBuilderCustomizer jackson2ObjectMapperBuilderCustomizer() {
        return builder -> {
            // 统一东八区时区
            builder.timeZone(TimeZone.getTimeZone("GMT+8"));
            // 兼容 java.util.Date 全局格式化
            builder.simpleDateFormat(DATE_TIME_PATTERN);
            // 可选：忽略值为 null 的字段不返回前端
            builder.serializationInclusion(JsonInclude.Include.NON_NULL);

            // JDK8+ 时间模块双向绑定
            JavaTimeModule javaTimeModule = new JavaTimeModule();
            DateTimeFormatter dateTimeFormatter = DateTimeFormatter.ofPattern(DATE_TIME_PATTERN);
            DateTimeFormatter dateFormatter = DateTimeFormatter.ofPattern(DATE_PATTERN);
            DateTimeFormatter timeFormatter = DateTimeFormatter.ofPattern(TIME_PATTERN);

            javaTimeModule.addSerializer(LocalDateTime.class, new LocalDateTimeSerializer(dateTimeFormatter));
            javaTimeModule.addDeserializer(LocalDateTime.class, new LocalDateTimeDeserializer(dateTimeFormatter));

            javaTimeModule.addSerializer(LocalDate.class, new LocalDateSerializer(dateFormatter));
            javaTimeModule.addDeserializer(LocalDate.class, new LocalDateDeserializer(dateFormatter));

            javaTimeModule.addSerializer(LocalTime.class, new LocalTimeSerializer(timeFormatter));
            javaTimeModule.addDeserializer(LocalTime.class, new LocalTimeDeserializer(timeFormatter));

            builder.modules(javaTimeModule);
        };
    }

    /**
     * 2. GET 请求参数 (@RequestParam / 表单提交) String -> LocalDateTime 全局转换器
     * （注意：Jackson 注解对 URL Query 参数无效，需注册 Spring Converter）
     */
    @Bean
    public Converter<String, LocalDateTime> localDateTimeConverter() {
        return source -> LocalDateTime.parse(source, DateTimeFormatter.ofPattern(DATE_TIME_PATTERN));
    }
}
```

```java
public class FlexibleLocalDateTimeDeserializer extends JsonDeserializer<LocalDateTime> {
    private static final List<DateTimeFormatter> FORMATTERS = Arrays.asList(
        DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss"),
        DateTimeFormatter.ofPattern("yyyy/MM/dd HH:mm:ss"),
        DateTimeFormatter.ISO_LOCAL_DATE_TIME
    );

    @Override
    public LocalDateTime deserialize(JsonParser p, DeserializationContext ctxt) throws IOException {
        String text = p.getText().trim();
        // 兼容纯数字毫秒时间戳
        if (text.matches("^\\d{13}$")) {
            return LocalDateTime.ofInstant(Instant.ofEpochMilli(Long.parseLong(text)), ZoneId.of("GMT+8"));
        }
        for (DateTimeFormatter formatter : FORMATTERS) {
            try {
                return LocalDateTime.parse(text, formatter);
            } catch (DateTimeParseException ignored) {}
        }
        throw new IllegalArgumentException("无法解析的时间格式: " + text);
    }
}
```

##### 2. 核心：自定义元数据填充处理器 `MyMetaObjectHandler`

```java
import com.baomidou.mybatisplus.core.handlers.MetaObjectHandler;
import org.apache.ibatis.reflection.MetaObject;
import org.springframework.stereotype.Component;
import java.time.LocalDateTime;
import java.util.Optional;

@Component
public class MyMetaObjectHandler implements MetaObjectHandler {

    @Override
    public void insertFill(MetaObject metaObject) {
        // 支持通过自定义 @IgnoreFill 注解跳过特殊同步表
        if (metaObject.getOriginalObject().getClass().isAnnotationPresent(IgnoreFill.class)) {
            return;
        }

        LocalDateTime now = LocalDateTime.now();
        LoginUser loginUser = UserContextHolder.getUser();
        // 未登录场景（如定时任务、MQ 消费）使用系统默认账号 0L 兜底
        Long operatorId = Optional.ofNullable(loginUser).map(LoginUser::getUserId).orElse(0L);
        Long tenantId = Optional.ofNullable(loginUser).map(LoginUser::getTenantId).orElse(0L);

        // strictInsertFill：仅当目标实体存在该属性且值为 null 时才填充，安全无报错
        this.strictInsertFill(metaObject, "createTime", LocalDateTime.class, now);
        this.strictInsertFill(metaObject, "updateTime", LocalDateTime.class, now);
        this.strictInsertFill(metaObject, "createBy", Long.class, operatorId);
        this.strictInsertFill(metaObject, "updateBy", Long.class, operatorId);
        this.strictInsertFill(metaObject, "tenantId", Long.class, tenantId);
        this.strictInsertFill(metaObject, "deleted", Integer.class, 0);
    }

    @Override
    public void updateFill(MetaObject metaObject) {
        if (metaObject.getOriginalObject().getClass().isAnnotationPresent(IgnoreFill.class)) {
            return;
        }

        LocalDateTime now = LocalDateTime.now();
        Long operatorId = Optional.ofNullable(UserContextHolder.getUser())
                .map(LoginUser::getUserId)
                .orElse(0L);

        // 注意：strictUpdateFill 默认在字段已有值时不覆盖；
        // 若希望每次 update 强制刷新 updateTime，可使用 this.setFieldValByName("updateTime", now, metaObject)
        this.setFieldValByName("updateTime", now, metaObject);
        this.setFieldValByName("updateBy", operatorId, metaObject);
    }
}
```

##### 3. 常见踩坑与排查清单
1. **`update(Wrapper)` 不触发填充**：当调用 `mapper.update(null, updateWrapper)` 且第一个实体参数传 `null` 时，`MetaObjectHandler` 无法获取实体元信息导致填充失效。解决：传入空实体 `mapper.update(new UserDO(), updateWrapper)`。
2. **`strictUpdateFill` 不覆盖已有值**：先查出实体 `user`（此时 `updateTime` 非空）再调用 `updateById(user)`，`strictUpdateFill` 发现字段非 `null` 会跳过填充。解决：在 `updateFill` 中改用 `setFieldValByName` 强制刷新更新时间。
3. **微服务 Feign 调用丢失当前用户**：通过 Feign `RequestInterceptor` 将 `userId` / `tenantId` 写入请求头，下游服务拦截器解析并存入 `UserContextHolder`（搭配 TTL 支持异步线程）。

### 1.4 Spring 同名 Bean 冲突与多实现注入解决方案

当 Spring 容器中出现两个相同名称的 Bean（如不同包下存在同名类 `@Service public class UserService`），或同一接口存在多个实现类时，会导致启动报错 `ConflictingBeanDefinitionException` 或 `NoUniqueBeanDefinitionException`。

#### 五种标准解决方案汇总

| 场景 | 解决方案 | 代码示例 |
| :--- | :--- | :--- |
| **1. 两个 Bean 名称冲突（如跨包同名类）** | 显式指定唯一 Bean 名称 | `@Service("adminUserService")`、`@Service("customerUserService")` |
| **2. 同一接口多实现，需指定默认注入项** | 使用 `@Primary` 标记首选 Bean | `@Service @Primary public class DefaultPayService implements PayService` |
| **3. 同一接口多实现，需精确指定注入哪一个** | 使用 `@Qualifier("beanName")` 或 `@Resource(name = "...")` | `public OrderService(@Qualifier("wechatPayService") PayService payService)` |
| **4. 不同环境激活不同实现（Dev / Prod）** | 使用 `@Profile` 或 `@ConditionalOnProperty` | `@Bean @Profile("prod") public DataSource prodDataSource()` |
| **5. 策略模式批量注入所有实现类** | 直接注入 `Map<String, PayService>` 或 `List<PayService>` | `@Autowired private Map<String, PayService> payStrategyMap;`（Key 即 Bean 名称） |

## 二、大批量数据处理（批量校验、关联查询、导入与导出）

### 2.1 批量插入 + 逐条业务校验 + 内存去重 + 唯一索引兜底

#### 一、核心痛点与设计原则

**业务诉求**：上游传入几百至上万条数据列表，要求：
1. **逐条校验并反馈明细**：支持“部分成功、部分失败”，明确返回成功条数、本批内重复数据、数据库已存在数据及格式错误行号。
2. **禁止逐条查库与逐条插入（底线）**：10,000 条数据若循环单条查库 + 单条插入会产生 20,000 次网络 IO，直接拖垮数据库。
3. **并发强一致防重**：既要拦截本批次内部的重复项（如 Excel 里两行完全一样），又要拦截与数据库已有记录的冲突（如 `(name, sex, age, birth_date)` 复合唯一）。

**标准五步分层架构**：
```text
输入 List<DTO>
   │
   ▼
[Step 1] 内存自身去重 + JSR303 基础格式校验（零 DB 交互，拦截入参自重复与格式错误）
   │
   ▼
[Step 2] 批量预查数据库已存在唯一键（1 次 SELECT ... WHERE IN 查出已有 Key 集合转为 HashSet）
   │
   ▼
[Step 3] 内存 O(1) 逐条比对判定（Set.contains 判断是否与 DB 重复，分离 toInsert 与 errorList）
   │
   ▼
[Step 4] 分批批量插入（每 500~1000 条一批执行 Batch Insert）
   │
   ▼
[Step 5] 数据库唯一索引兜底（UNIQUE KEY + INSERT IGNORE / ON DUPLICATE KEY UPDATE 防并发击穿）
```

---

```java
@Service
@RequiredArgsConstructor
public class PersonBatchService {

    private final Validator validator;
    private final PersonMapper personMapper;

    public BatchProcessResult<PersonDTO> batchInsertWithCheck(List<PersonDTO> inputList) {
        if (CollectionUtils.isEmpty(inputList)) {
            return BatchProcessResult.<PersonDTO>builder().totalCount(0).build();
        }

        Map<String, PersonDTO> uniqueInputMap = new LinkedHashMap<>();
        List<PersonDTO> selfDuplicates = new ArrayList<>();
        List<BatchProcessResult.BatchErrorItem> errorList = new ArrayList<>();

        // ==================== Step 1：JSR303 校验 + 本批内存去重 ====================
        for (int i = 0; i < inputList.size(); i++) {
            PersonDTO dto = inputList.get(i);
            // 1.1 JSR303 注解校验
            Set<ConstraintViolation<PersonDTO>> violations = validator.validate(dto);
            if (!violations.isEmpty()) {
                String errorMsg = violations.stream()
                        .map(ConstraintViolation::getMessage)
                        .collect(Collectors.joining("; "));
                errorList.add(new BatchProcessResult.BatchErrorItem(i + 1, errorMsg));
                continue;
            }
            // 1.2 本批自身重复校验
            String uniqueKey = buildUniqueKey(dto);
            if (uniqueInputMap.containsKey(uniqueKey)) {
                selfDuplicates.add(dto);
            } else {
                uniqueInputMap.put(uniqueKey, dto);
            }
        }

        List<PersonDTO> candidateList = new ArrayList<>(uniqueInputMap.values());
        List<PersonDTO> toInsertList = new ArrayList<>();
        List<PersonDTO> dbDuplicates = new ArrayList<>();

        if (!candidateList.isEmpty()) {
            // ==================== Step 2：分批预查 DB 已存在 Key ====================
            Set<String> dbExistingKeys = new HashSet<>();
            for (List<PersonDTO> batch : Lists.partition(candidateList, 500)) {
                dbExistingKeys.addAll(personMapper.selectExistingKeys(batch));
            }

            // ==================== Step 3：内存 O(1) 判定是否与 DB 冲突 ====================
            for (PersonDTO dto : candidateList) {
                if (dbExistingKeys.contains(buildUniqueKey(dto))) {
                    dbDuplicates.add(dto);
                } else {
                    toInsertList.add(dto);
                }
            }

            // ==================== Step 4：分批批量入库（每 500 条一批防 SQL 超长） ====================
            for (List<PersonDTO> batch : Lists.partition(toInsertList, 500)) {
                personMapper.batchInsertIgnore(batch);
            }
        }

        return BatchProcessResult.<PersonDTO>builder()
                .totalCount(inputList.size())
                .successCount(toInsertList.size())
                .selfDuplicates(selfDuplicates)
                .dbDuplicates(dbDuplicates)
                .errorList(errorList)
                .build();
    }

    private String buildUniqueKey(PersonDTO p) {
        return p.getName() + "-" + p.getSex() + "-" + p.getAge() + "-" + p.getBirthDate();
    }
}
```

#### 三、模式 B：多线程并行校验 + 单线程批量入库（适合含远程 RPC / 复杂 IO 校验）

当单条数据的校验必须调用外部第三方 HTTP/RPC 接口（无法合并为一条 SQL 批量查询）时，采用 **自定义线程池 + `CompletableFuture` 并行校验 → 主线程汇总 → 单线程分批入库**：

```java
public BatchProcessResult<BizDTO> parallelCheckAndBatchInsert(List<BizDTO> dtoList) {
    // 1. 使用自定义线程池并行执行单条耗时校验（严禁使用 parallelStream 公共池）
    List<CompletableFuture<CheckResult<BizDTO>>> futures = dtoList.stream()
            .map(dto -> CompletableFuture.supplyAsync(() -> bizRemoteValidator.check(dto), checkExecutor))
            .collect(Collectors.toList());

    // 2. 等待全部校验完成并收集结果
    List<CheckResult<BizDTO>> results = futures.stream()
            .map(CompletableFuture::join)
            .collect(Collectors.toList());

    // 3. 拆分成功与失败列表
    List<BizEntity> successEntities = results.stream()
            .filter(CheckResult::isSuccess)
            .map(r -> convertToEntity(r.getData()))
            .collect(Collectors.toList());

    // 4. 单线程分批插入（避免多线程并发插入引发死锁或连接池耗尽）
    for (List<BizEntity> batch : Lists.partition(successEntities, 500)) {
        bizMapper.insertBatch(batch);
    }

}
```

### 2.2 “1 对多”关联查询性能优化（彻底消灭 N+1 问题）

在查询主列表并填充每个元素的子列表时（如：查询分类列表并填充每个分类下的标签、查询订单列表并填充订单明细），**严禁在 `for` 循环中单条查询数据库（N+1 问题）**。

#### 四种方案优先级与对比

##### 1. 【首选】批量 `IN` 查询 + 内存 `groupingBy` 分组组装（适用 90% 场景）

将 $N+1$ 次查询压缩为固定 **2 次查询**（1 次查主表 + 1 次 `IN` 查从表），在内存中以 $O(N)$ 复杂度完成组装：

```java
// 1. 查询 "1" 的主表列表（第 1 次 SQL）
List<Category> categories = categoryMapper.selectList(queryWrapper);
if (CollectionUtils.isEmpty(categories)) {
    return Collections.emptyList();
}

// 2. 提取所有主表主键 ID
List<Long> categoryIds = categories.stream()
        .map(Category::getId)
        .distinct()
        .collect(Collectors.toList());

// 3. 分批批量查询 "多" 的从表数据（第 2 次 SQL：WHERE category_id IN (...)）
List<Label> allLabels = new ArrayList<>();
for (List<Long> batchIds : Lists.partition(categoryIds, 500)) {
    allLabels.addAll(labelMapper.selectByCategoryIds(batchIds));
}

// 4. 内存按外键 ID 分组为 Map<Long, List<Label>>
Map<Long, List<Label>> labelGroupMap = allLabels.stream()
        .collect(Collectors.groupingBy(Label::getCategoryId));

// 5. 遍历主表回填子集合（注意 getOrDefault 空集合兜底，避免前端拿到 null）
categories.forEach(category ->
        category.setLabels(labelGroupMap.getOrDefault(category.getId(), Collections.emptyList()))
);
```

##### 2. 四种方案选型决策表

| 方案 | 适用场景 | 优点 | 缺点与注意事项 |
| :--- | :--- | :--- | :--- |
| **① 批量 `IN` 查询 + 内存分组** | **标准关系型数据库关联（首选）** | 仅 2 次 SQL、索引友好、无笛卡尔积膨胀 | 外键列（如 `category_id`）必须建索引；`IN` 超过 500 项需分批 |
| **② SQL `LEFT JOIN` 联表** | 从表字段极少、一对多数量小（`< 10`） | 1 次 SQL 查询完成 | 主表字段重复传输导致结果集膨胀；分页总数统计易失真 |
| **③ 多线程 `CompletableFuture` 并发查** | “多”的数据来自外部无批量接口的 RPC | 缩短多次网络 IO 的串行等待时间 | 必须限制并发度防打挂下游；禁止用于本地 DB 查询 |
| **④ Redis `HMGET` / Pipeline 批量加载** | 读多写少的高频热点关联数据 | 性能极致（接近 $O(1)$），保护 DB | 需维护缓存与 DB 的双写一致性 |

### 2.3 百万级数据批量导入架构（EasyExcel + 异步落库）

#### 一、三种数据库批量写入方式性能对比

| 写入方式 | 核心原理与必配参数 | 性能 | 适用规模与注意事项 |
| :--- | :--- | :--- | :--- |
| **1. MyBatis XML `<foreach>` 拼接 VALUES** | `INSERT INTO t VALUES (),(),()` | **极高** | 单批建议 500～1000 条，过多会超出 MySQL `max_allowed_packet` 报错 |
| **2. MyBatis-Plus `saveBatch(list, 1000)`** | JDBC `PreparedStatement.addBatch()` | 高 | **必须在 JDBC URL 追加 `rewriteBatchedStatements=true`**，否则底层仍是逐条发送 |
| **3. MySQL `LOAD DATA LOCAL INFILE`** | 数据库原生直接加载 CSV 数据流 | **天花板** | 比任何 `INSERT` 快 10～20 倍，适合百万/千万级初始化数据导入 |

#### 二、重复数据处理的三种业务策略

1. **策略 A：静默跳过重复项** → 使用 `INSERT IGNORE INTO table (...) VALUES (...)`（依赖唯一索引）。
2. **策略 B：存在则更新，不存在则插入（Upsert）** → 使用 `ON DUPLICATE KEY UPDATE`：
   ```xml
   INSERT INTO user (mobile, name, age)
   VALUES
   <foreach collection="list" item="item" separator=",">
       (#{item.mobile}, #{item.name}, #{item.age})
   </foreach>
   ON DUPLICATE KEY UPDATE
       name = VALUES(name),
       age = VALUES(age)
   ```
3. **策略 C：严格拦截并导出错误回执** → 分批 `SELECT ... WHERE IN` 预查或利用 Redis `Set` / 布隆过滤器快速判重，将重复行写入错误明细 Excel 供用户修正。

#### 三、十万/百万级大文件导入的四大核心优化

1. **EasyExcel 事件驱动流式分批读取（防 JVM OOM）**：
   严禁使用原生 `Apache POI` 一次性将整个文件加载进内存。使用 `EasyExcel` 的 `ReadListener`，每解析满 1000 行触发一次校验与批量入库，随后立即 `list.clear()` 释放内存。
2. **异步化架构（OSS + MQ / 线程池）**：
   前端上传文件至 OSS 后，接口仅创建一条“导入任务记录”并投递 MQ 消息，立即返回任务 ID；后台消费者异步解析入库，前端通过轮询或 WebSocket 展示进度条。
3. **拆分大事务为批次小事务**：
   切忌在 10 万条导入外层加一个全局 `@Transactional`（长事务锁表且回滚代价极大）。应以每 1000 条为一个独立小事务提交（使用 `TransactionTemplate` 编程式事务控制）。
4. **关闭 MyBatis 缓存干扰**：批处理会话中避免一级缓存无限堆积对象引用。

### 2.4 百万级数据批量导出架构（EasyExcel 流式分页 + 异步 OSS 下载）

海量数据导出必须跨越三座大山：**数据库深分页慢查询、JVM 堆内存 OOM、Excel 单 Sheet 行数上限**。

#### 一、同步导出 vs 异步导出分级选型

- **同步导出（`< 5 万条`）**：游标/分页查询 + `EasyExcel` 直接流式写入 `HttpServletResponse.getOutputStream()`。
- **异步导出（`10 万～百万级`，企业级标准）**：
  1. 前端点击导出 → 后端落库生成导出任务（状态 `RUNNING`）→ 提交异步线程池/MQ → 立即返回任务 ID；
  2. 后台工作线程采用**基于主键 ID 的游标分页**分批拉取数据，通过 `EasyExcel` 追加写入本地临时文件；
  3. 写完后上传至阿里云 OSS / MinIO，更新任务状态为 `SUCCESS` 并保存带过期时间的下载链接；
  4. `finally` 块中关闭 `ExcelWriter` 并**删除本地临时文件**。

---

#### 二、四大核心技术点与避坑指南

1. **用“游标分页（`WHERE id > lastId`）”替代传统 `LIMIT offset, size`**：
   当翻页到第 50 万行时，`LIMIT 500000, 5000` 会扫描并丢弃前 50 万行；改用 `WHERE id > #{lastMaxId} ORDER BY id ASC LIMIT 5000` 可始终走主键索引，耗时稳定在毫秒级。
2. **突破 Excel 单 Sheet 104 万行上限**：
   Excel 2007 (`.xlsx`) 单个 Sheet 最大行数为 **1,048,576** 行。超过 100 万行时需按每 100 万行动态创建新 `WriteSheet("数据_" + sheetNo)`，或直接降维导出为无行数限制、写入极快的 **CSV 格式**。
3. **控制并发导出任务数（防打崩 DB 与磁盘）**：
   使用独立定长线程池（如核心线程数 2～4）或 `Semaphore` 信号量限制同时执行的导出任务数，超出则排队或提示“导出任务排队中”。
4. **按需投影查询**：拒绝 `SELECT *`，仅查询导出列所需字段，禁止在导出循环内执行 N+1 关联查询。

---

#### 三、核心代码模板（游标分页 + EasyExcel 分 Sheet 异步导出）

```java
public void executeAsyncExport(Long taskId, ExportQueryParam param) {
    taskService.updateStatus(taskId, "RUNNING");
    String tempFilePath = System.getProperty("java.io.tmpdir") + "/export_" + taskId + ".xlsx";
    ExcelWriter excelWriter = null;

    try {
        excelWriter = EasyExcel.write(tempFilePath, ExportDataVO.class).build();
        int batchSize = 5000;
        int currentSheetRows = 0;
        int sheetNo = 1;
        Long lastMaxId = 0L;

        WriteSheet writeSheet = EasyExcel.writerSheet(sheetNo, "数据明细_" + sheetNo).build();

        while (true) {
            // 游标分页查询：WHERE id > #{lastMaxId} ORDER BY id ASC LIMIT #{batchSize}
            List<ExportDataVO> batchList = dataMapper.selectByCursor(param, lastMaxId, batchSize);
            if (CollectionUtils.isEmpty(batchList)) {
                break;
            }

            // 单 Sheet 满 100 万行时自动切新 Sheet
            if (currentSheetRows + batchList.size() > 1_000_000) {
                sheetNo++;
                writeSheet = EasyExcel.writerSheet(sheetNo, "数据明细_" + sheetNo).build();
                currentSheetRows = 0;
            }

            excelWriter.write(batchList, writeSheet);
            currentSheetRows += batchList.size();
            lastMaxId = batchList.get(batchList.size() - 1).getId();
            batchList.clear(); // 及时释放引用协助 GC
        }

        // 必须先 finish 刷盘，再上传 OSS
        excelWriter.finish();
        excelWriter = null;

        String downloadUrl = ossClient.uploadWithExpire(tempFilePath, Duration.ofHours(24));
        taskService.updateSuccess(taskId, downloadUrl);
    } catch (Exception e) {
        log.error("异步导出任务失败, taskId={}", taskId, e);
        taskService.updateStatus(taskId, "FAILED");
    } finally {
        if (excelWriter != null) {
            excelWriter.finish();
        }
        File tempFile = new File(tempFilePath);
        if (tempFile.exists()) {
            tempFile.delete(); // 务必清理临时文件防磁盘打满
        }
    }
}
```

## 三、并发编程、线程上下文传递与响应式编程

### 3.1 线程上下文传递三剑客（ThreadLocal → InheritableThreadLocal → 阿里 TTL）

#### 一、三者核心能力与选型终极对比

| 技术方案 | 存储容器（`Thread` 成员变量） | 新建子线程 (`new Thread`) | 线程池复用 (`ThreadPoolExecutor` / `@Async`) | 生产推荐度 |
| :--- | :--- | :--- | :--- | :--- |
| **`ThreadLocal`** | `Thread.threadLocals` | ❌ 无法获取（完全隔离） | ❌ 无法获取 | 仅限单线程同步链路 |
| **`InheritableThreadLocal`** | `Thread.inheritableThreadLocals` | ✅ 可继承（`Thread.init` 时拷贝） | ❌ **彻底失效且导致数据串号污染** | ❌ 生产禁用（除纯手动 `new Thread` 外） |
| **`TransmittableThreadLocal` (TTL)** | 继承自 `InheritableThreadLocal` + Holder 注册表 | ✅ 自动传递 | ✅ **捕获-回放-恢复，完美支持池化复用** | ⭐⭐⭐⭐⭐ **企业级生产唯一标准** |

---

#### 二、`ThreadLocal` 底层原理与内存泄漏根治

##### 1. 存储结构与源码机制
- **谁持有数据**：数据并不是存在 `ThreadLocal` 实例里，而是存在当前线程 `Thread` 对象的 `ThreadLocal.ThreadLocalMap threadLocals` 属性中。
- **`ThreadLocalMap` 特点**：
  - 初始容量 **16**，负载因子 **2/3**；
  - 哈希冲突解决方式：**开放地址法（线性探测）**，而非 `HashMap` 的链表/红黑树；
  - `Entry` 继承自 **`WeakReference<ThreadLocal<?>>`**：Key 是指向 `ThreadLocal` 对象的**弱引用**，而 Value 是指向业务对象的**强引用**。

```text
Thread ──► ThreadLocalMap ──► Entry[] table
                                ├── Key: WeakReference(ThreadLocal)  [弱引用，GC 可回收]
                                └── Value: LoginUser / Connection    [强引用，不 remove 会泄漏]
```

##### 2. 两大致命问题与根治方案
1. **内存泄漏**：当外部不再引用 `ThreadLocal` 实例时，GC 会回收弱引用 Key（变为 `null`），但线程池中的核心线程长期存活，导致强引用链路 `Thread -> ThreadLocalMap -> Entry(null, value)` 一直存在，Value 无法回收。
2. **线程池脏数据串号**：线程被归还给线程池后若未清理 `ThreadLocal`，下一个请求复用了该线程，就会读到上一个用户的残留身份信息。
3. **强制规范**：
   - `ThreadLocal` 变量一律声明为 `private static final`（避免弱引用 Key 过早变成 `null` 及重复创建）；
   - **必须在 `try-finally` 块或 Spring `HandlerInterceptor.afterCompletion()` 中调用 `remove()`**。

---

#### 三、`InheritableThreadLocal` 原理与为什么在线程池下失效

- **原理**：在 `new Thread()` 构造方法内部调用 `init()` 时，若发现父线程的 `parent.inheritableThreadLocals != null`，则调用 `ThreadLocalMap.createInheritedMap()` 将父线程当时的变量快照浅拷贝一份赋给子线程。
- **线程池失效原因**：`Thread.init()` **只在创建新线程对象时执行一次**。而线程池的核心线程在启动后一直复用，后续提交的任务只是往阻塞队列里放 `Runnable`，根本不会再次触发 `Thread.init()`，因此工作线程拿到的永远是当初第一次创建它时的旧上下文。

---

#### 四、阿里 `TransmittableThreadLocal` (TTL) 企业级落地

##### 1. 核心原理（CRR：Capture → Replay → Restore）
当使用 `TtlRunnable` / `TtlCallable` 或 `TtlExecutors` 提交任务时：
1. **Capture（捕获）**：在父线程提交任务瞬间，抓取当前线程所有的 TTL 上下文快照；
2. **Replay（回放）**：当线程池的工作线程开始执行该任务前，将原工作线程的上下文备份，并把捕获的父线程快照注入到工作线程；
3. **Restore（恢复）**：在任务的 `finally` 块中，清理本次任务的上下文并还原工作线程原有的上下文，绝对不污染线程池。

##### 2. Maven 依赖与线程池零侵入集成

```xml
<dependency>
    <groupId>com.alibaba</groupId>
    <artifactId>transmittable-thread-local</artifactId>
    <version>2.14.3</version>
</dependency>
```

```java
/**
 * 1. 企业级用户上下文工具类（底层直接采用 TransmittableThreadLocal）
 */
public final class UserContext {
    private static final TransmittableThreadLocal<LoginUser> CONTEXT = new TransmittableThreadLocal<>();

    public static void set(LoginUser user) { CONTEXT.set(user); }
    public static LoginUser get() { return CONTEXT.get(); }
    public static void clear() { CONTEXT.remove(); } // 拦截器 afterCompletion 必调
}

/**
 * 2. 使用 TtlExecutors 包装 Spring 业务线程池（之后所有 @Async 和 CompletableFuture 自动透传）
 */

    @Bean("bizExecutor")
    public Executor bizExecutor() {
        int core = Runtime.getRuntime().availableProcessors();
        ThreadPoolExecutor executor = new ThreadPoolExecutor(
                core * 2, core * 4, 60L, TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(1000),
                new ThreadFactoryBuilder().setNameFormat("biz-pool-%d").build(),
                new ThreadPoolExecutor.CallerRunsPolicy()
        );
        // 关键：一层包装即可实现线程池上下文自动传递

    }
}
```

### 3.2 企业级多线程使用规范与性能优化全攻略

#### 一、线程池 7 大核心参数与配置黄金法则

##### 1. 7 大参数速查
1. `corePoolSize`：常驻核心线程数；
2. `maximumPoolSize`：最大线程数（只有当有界队列塞满后，才会创建大于 `corePoolSize` 的非核心线程）；
3. `keepAliveTime` & `unit`：非核心空闲线程存活时间；
4. `workQueue`：工作阻塞队列（生产必须使用**有界队列**如 `ArrayBlockingQueue` 或指定容量的 `LinkedBlockingQueue(capacity)`，严禁使用默认 `Integer.MAX_VALUE` 无界队列导致 OOM）；
5. `threadFactory`：自定义线程工厂（**必须指定业务前缀名**如 `order-async-%d`，否则线上 `jstack` 满屏 `pool-1-thread-1` 无法排障）；
6. `handler`：拒绝策略：
   - `CallerRunsPolicy`：由提交任务的调用者线程自己同步执行（削峰降速、不丢任务，一般业务首选）；
   - `AbortPolicy`（默认）：直接抛出 `RejectedExecutionException`；
   - `DiscardPolicy` / `DiscardOldestPolicy`：静默丢弃当前任务或队列头最老任务。

##### 2. 线程数设置黄金公式
- **CPU 密集型（加解密、复杂计算、正则匹配）**：
  $$\text{核心线程数} = N_{\text{CPU}} + 1$$
  避免线程过多引发频繁的 CPU 时间片上下文切换。
- **I/O 密集型（90% 后端业务：DB、Redis、RPC、HTTP 调用）**：
  $$\text{核心线程数} = N_{\text{CPU}} \times 2 \quad \text{或} \quad N_{\text{CPU}} \times \left(1 + \frac{\text{I/O 耗时}}{\text{CPU 耗时}}\right)$$
  利用线程等待 I/O 的空档让 CPU 调度其他线程，提升整体吞吐量。

---

#### 二、多线程性能优化六大核心手段

1. **线程池隔离（Bulkhead 舱壁模式）**：
   核心交易链路（下单/支付）与非核心慢任务（报表导出、发短信）**必须使用独立的线程池**，防止慢任务占满全局队列拖垮核心接口。
2. **减少线程上下文切换**：
   - 控制线程总数，拒绝盲目开大线程池；
   - 将高频零碎小任务合并为微批（Batch）任务，减少线程调度唤醒次数。
3. **锁优化（从重锁 → 轻锁 → 无锁）**：
   - **优先无锁编程**：局部变量、不可变对象、`ThreadLocal/TTL`、`AtomicLong`/`LongAdder`（高并发计数 `LongAdder` 比 `AtomicLong` 性能高数倍，采用 Cell 数组分段 CAS 减少自旋冲突）；
   - **缩小锁粒度**：只锁涉及共享变量修改的最小代码块，切勿在 `synchronized` 块内执行远程 RPC 或慢 SQL；
   - **读写分离与分段锁**：读多写少场景使用 `ReentrantReadWriteLock` 或 `StampedLock`；键值存储使用 `ConcurrentHashMap`。
4. **消除 CPU 缓存伪共享（False Sharing）**：
   当多个线程高频修改位于同一个 64 字节 CPU 缓存行（Cache Line）中的不同变量时，会导致缓存行反复失效。可使用 `@jdk.internal.vm.annotation.Contended`（JDK8 为 `@sun.misc.Contended`，需加 JVM 参数 `-XX:-RestrictContended`）进行缓存行填充隔离。
5. **并发容器正确选型**：
   - 高并发 Map → `ConcurrentHashMap`
   - 读多写少列表（如白名单配置） → `CopyOnWriteArrayList`（注意：写多场景禁用，每次写都会复制整个底层数组）
   - 并发限流与批同步 → `Semaphore`、`CountDownLatch`、`CyclicBarrier`

### 3.3 CompletableFuture 异步编排实战指南

`CompletableFuture` 实现了 `Future` 与 `CompletionStage` 接口，彻底解决了传统 `Future.get()` 只能阻塞等待、无法链式回调、无法组合多任务的痛点。

#### 一、高频 API 分类速查表

| 分类 | 核心方法 | 特点与区别 |
| :--- | :--- | :--- |
| **1. 创建异步任务** | `runAsync(Runnable, executor)`<br>`supplyAsync(Supplier, executor)` | `runAsync` 无返回值；`supplyAsync` 有返回值。<br>⚠️ **生产强制传入第二个参数（自定义线程池）！** |
| **2. 串行转换回调** | `thenApply(fn)`（转换并返回新值）<br>`thenAccept(consumer)`（仅消费无返回）<br>`thenRun(action)`（无入参无返回）<br>`thenCompose(fn)`（扁平化串联另一个 CF） | 不带 `Async` 后缀的方法：若前置任务已完成则由当前调用线程执行，否则由前置任务线程执行；带 `Async` 后缀则重新提交给线程池执行 |
| **3. 两任务组合** | `thenCombine(other, biFn)`（全部完成合并结果）<br>`applyToEither(other, fn)`（谁快用谁的结果） | 适合双路并行查询汇总，或多渠道择优降级 |
| **4. 多任务组合** | `CompletableFuture.allOf(cfs...)`<br>`CompletableFuture.anyOf(cfs...)` | `allOf` 等待所有任务完成；`anyOf` 任意一个完成即返回 |
| **5. 异常处理** | `exceptionally(fn)`（仅异常时触发并返回兜底值）<br>`whenComplete((res, ex) -> ...)`（记录日志不改返回值）<br>`handle((res, ex) -> ...)`（正常与异常统一处理转换） | 异步链路末尾**必须配置异常处理器**，否则异常会被静默吞噬 |

---

#### 二、生产实战模板：多服务并行查询聚合（RT 从串行累加降为最大单次耗时）

例如商品详情页需要同时查询：商品基本信息（50ms）、库存信息（40ms）、优惠券列表（60ms）。串行耗时 `150ms`，使用 `CompletableFuture` 并行编排仅需 `60ms`：

```java
public ProductDetailVO getProductDetail(Long productId) {
    // 1. 并行发起三个异步查询（全部传入自定义线程池 bizExecutor，并配置超时与异常降级）
    CompletableFuture<ProductInfo> infoFuture = CompletableFuture
            .supplyAsync(() -> productService.getById(productId), bizExecutor)
            .orTimeout(2, TimeUnit.SECONDS)
            .exceptionally(ex -> {
                log.error("查询商品基本信息异常, id={}", productId, ex);
                return null;
            });

    CompletableFuture<Integer> stockFuture = CompletableFuture
            .supplyAsync(() -> stockService.getStock(productId), bizExecutor)
            .orTimeout(1, TimeUnit.SECONDS)
            .exceptionally(ex -> {
                log.warn("查询库存异常，降级返回 0, id={}", productId, ex);
                return 0;
            });

    CompletableFuture<List<CouponDTO>> couponFuture = CompletableFuture
            .supplyAsync(() -> couponService.listByProduct(productId), bizExecutor)
            .orTimeout(1, TimeUnit.SECONDS)
            .exceptionally(ex -> Collections.emptyList());

    // 2. 等待所有并行任务完成（链路最末端才 join）
    CompletableFuture.allOf(infoFuture, stockFuture, couponFuture).join();

    // 3. 汇总结果
    ProductInfo info = infoFuture.join();
    if (info == null) {
        throw new BizException("商品不存在或服务繁忙");
    }
    return new ProductDetailVO(info, stockFuture.join(), couponFuture.join());
}
```

#### 三、`CompletableFuture` 生产四大铁律
1. **严禁使用默认公共池 `ForkJoinPool.commonPool()`**：默认池线程数仅为 `CPU核数 - 1`，一旦混入阻塞 I/O 任务会瞬间打满并拖垮整个 JVM 内所有并行流与异步任务。
2. **禁止在循环或异步回调内部嵌套阻塞 `join()`**：当父任务与子任务共用同一个有界线程池，且父任务阻塞等待子任务完成时，极易引发**线程池饥饿死锁（Thread Pool Starvation Deadlock）**。
3. **必须加超时控制与异常兜底**：JDK9+ 原生支持 `.orTimeout(timeout, unit)` 与 `.completeOnTimeout(defaultVal, timeout, unit)`。
4. **配合 TTL 透传上下文**：线程池必须经 `TtlExecutors.getTtlExecutor()` 包装，否则异步线程内拿不到登录用户和 TraceId。

### 3.4 响应式编程 Project Reactor（Mono 核心原理与 WebFlux 实战）

#### 一、`Mono` 核心本质与生命周期

`Mono<T>` 是 **Project Reactor**（Spring WebFlux、Spring Cloud Gateway 底层引擎）的核心发布者，代表 **0 或 1 个元素的异步非阻塞数据流**（多元素流则使用 `Flux<T>`）。

- **三种终止信号**：
  1. **有值完成**：`Mono.just(data)` → 发出 `onNext(data)` → 发出 `onComplete()`；
  2. **空值完成**：`Mono.empty()` → 直接发出 `onComplete()`（注意：在响应式流中 `empty` 代表无数据正常结束，严禁向 `Mono.just(null)` 传 `null`）；
  3. **异常终止**：`Mono.error(ex)` → 直接发出 `onError(ex)`。
- **惰性求值（Lazy）**：Nothing happens until you `subscribe()`。仅定义 `Mono` 操作符流水线不会触发任何执行，直到调用 `.subscribe()` 或将 `Mono` 返回给 WebFlux 容器由框架订阅。

## 四、高并发核心组件实战（缓存一致性与分布式 ID）

### 4.1 缓存三大问题与数据库双写一致性落地方案

#### 一、缓存穿透、缓存击穿、缓存雪崩标准解法汇总

| 问题类型 | 产生原因 | 标准解决方案 |
| :--- | :--- | :--- |
| **1. 缓存穿透** | 恶意或高频请求查询**缓存和数据库中都不存在**的数据，每次请求直穿 DB | ① **缓存空对象（Null Value）** + 短 TTL（如 3～5 分钟）；<br>② **布隆过滤器（BloomFilter）** 前置拦截不存在的 Key；<br>③ 接口层参数合法性校验与风控限流 |
| **2. 缓存击穿** | 某一个**超高频热点 Key 过期瞬间**，海量并发请求同时打到 DB 重建缓存 | ① **互斥锁（Redisson 分布式锁 + 双重检查 DCL）**，仅放行 1 个线程查 DB 回写；<br>② **逻辑过期（永不过期）**，物理不设 TTL，Value 内封装 `expireTime`，过期时异步线程刷新，主线程立即返回旧值 |
| **3. 缓存雪崩** | **同一时间大面积 Key 集中过期**，或 **Redis 集群宕机**，流量全部压垮 DB | ① 基础 TTL 加上 **随机偏移量**（如 `30min + random(1~5min)`）打散过期时间；<br>② Redis 哨兵 / Cluster 高可用集群部署；<br>③ **Caffeine 本地缓存 + Redis 多级缓存** + Sentinel 熔断降级限流 |

---

#### 二、数据库与缓存双写一致性五大方案

互联网业务 99% 采用 **Cache Aside（旁路缓存模式）**，写操作核心原则：**先更新数据库，再删除缓存**（为什么删缓存而不是更新缓存：① 懒加载思想，避免写多读少场景大量无效计算写缓存；② 并发写场景下“先写 DB 的线程晚更新缓存”会导致脏数据长期驻留）。

| 方案 | 执行流程 | 一致性级别 | 优缺点与适用场景 |
| :--- | :--- | :--- | :--- |
| **1. 先更 DB，再删缓存** | ① 更新 MySQL；② 直接 `DEL` Redis Key + TTL 兜底 | 最终一致 | **实现最简单、性价比最高**；适用于 90% 常规业务（商品信息、用户资料） |
| **2. 异步延时双删** | ① 更 DB；② 删缓存；③ 异步延迟 500ms～1s 二次删缓存 | 较强最终一致 | 清理并发读请求在更新期间可能回填的旧数据；延迟时间需大于一次主从同步+读耗时 |
| **3. MQ / Canal Binlog 异步删缓存** | ① 业务只管更 DB；② Canal 监听 MySQL Binlog 投递 MQ；③ 消费者异步删缓存并带失败重试 | **高可靠最终一致** | **大厂高并发主流方案**；彻底解耦业务代码，自带 MQ 重试机制防止删缓存失败 |
| **4. 读写锁（`RReadWriteLock`）串行化** | 读操作加读锁，写操作加写锁（写期间阻塞读） | **强一致** | 保证绝对不会读到旧数据，但写多时吞吐量下降明显；适合金融账务、核心库存等强一致场景 |
| **5. 多级缓存（Caffeine + Redis）同步** | 本地缓存设短 TTL（1～3min）+ 更新时发送 Redis Pub/Sub 或 MQ 广播通知所有节点清除本地 Key | 准实时最终一致 | 解决集群多实例下本地内存缓存不一致难题 |

#### 三、企业级标准读写代码模板（防穿透 + 防击穿 + 事务后删缓存）

```java
@Service
@RequiredArgsConstructor
public class ProductCacheService {

    private final StringRedisTemplate redisTemplate;
    private final RedissonClient redissonClient;
    private final ProductMapper productMapper;

    private static final String CACHE_KEY_PREFIX = "product:detail:";
    private static final String LOCK_KEY_PREFIX = "lock:product:";
    private static final String NULL_PLACEHOLDER = "NULL";

    /**
     * 标准读：Cache Aside + 空值防穿透 + 分布式锁 DCL 防击穿 + 随机 TTL 防雪崩
     */
    public ProductDO getProductById(Long id) {
        String cacheKey = CACHE_KEY_PREFIX + id;
        // 1. 先查缓存
        String json = redisTemplate.opsForValue().get(cacheKey);
        if (StringUtils.hasText(json)) {
            return NULL_PLACEHOLDER.equals(json) ? null : JSONUtil.toBean(json, ProductDO.class);
        }

        // 2. 缓存未命中，加分布式互斥锁防击穿
        RLock lock = redissonClient.getLock(LOCK_KEY_PREFIX + id);
        lock.lock();
        try {
            // Double Check 二次检查缓存
            json = redisTemplate.opsForValue().get(cacheKey);
            if (StringUtils.hasText(json)) {
                return NULL_PLACEHOLDER.equals(json) ? null : JSONUtil.toBean(json, ProductDO.class);
            }

            // 3. 回源查询数据库
            ProductDO dbProduct = productMapper.selectById(id);
            if (dbProduct == null) {
                // 空值缓存 5 分钟防穿透
                redisTemplate.opsForValue().set(cacheKey, NULL_PLACEHOLDER, Duration.ofMinutes(5));
                return null;
            }

            // 4. 写入缓存（基础 30 分钟 + 0~300 秒随机偏移防雪崩）
            long randomSeconds = 1800 + ThreadLocalRandom.current().nextInt(300);
            redisTemplate.opsForValue().set(cacheKey, JSONUtil.toJsonStr(dbProduct), Duration.ofSeconds(randomSeconds));
            return dbProduct;
        } finally {
            lock.unlock();
        }
    }

    /**
     * 标准写：先更新 DB，事务提交后再删除缓存（配合失败重试或 MQ 兜底）
     */
    @Transactional(rollbackFor = Exception.class)
    public void updateProduct(ProductDO product) {
        // 1. 更新数据库
        productMapper.updateById(product);

        // 2. 注册事务同步钩子：确保数据库事务真正提交后再删缓存，防止事务未提交时其他线程读到旧库数据回填缓存
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                String cacheKey = CACHE_KEY_PREFIX + product.getId();
                redisTemplate.delete(cacheKey);
            }
        });
    }
}
```

### 4.2 分布式 ID 选型与深度剖析（Snowflake 雪花算法 + WorkerID + 美团 Leaf）

分布式 ID 的五大核心诉求：**全局唯一、趋势递增（利于 MySQL InnoDB B+ 树聚簇索引，避免随机插入导致页分裂）、高性能、高可用、安全防猜测**。

#### 一、六大主流方案横向选型表

| 方案 | 唯一性 | 有序性 | 性能 (QPS) | 外部依赖 | 核心优缺点与适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **UUID (v4 / v7)** | 极高 | v4 无序<br>v7 趋势递增 | 极高 | 无 | 字符串占空间（36 字节），v4 无序导致 B+ 树频繁页分裂；适合 TraceId、临时 Token |
| **数据库 `AUTO_INCREMENT`** | 高 | 严格递增 | `< 1万` | 强依赖 DB | 简单直观，但单库性能瓶颈明显、分库分表扩容困难、易暴露业务量；仅适合小型单体 |

| **美团 Leaf-snowflake / 百度 UidGenerator** | 高 | 趋势递增 | `100~600万` | ZooKeeper / DB | 基于雪花算法封装了 WorkerID 自动分配与时钟回拨保护，开箱即用 |

#### 二、Snowflake（雪花算法）深度剖析与生产级代码实现

##### 1. 标准 64 位二进制结构

```text
+--------------------------------------------------------------------------+
| 1 Bit (符号位) | 41 Bits (毫秒级时间戳差值) | 5 Bits (机房ID) | 5 Bits (机器ID) | 12 Bits (毫秒内序列号) |
+--------------------------------------------------------------------------+
|       0       |      可用约 69.7 年       |     0 ~ 31     |     0 ~ 31     |       0 ~ 4095        |
+--------------------------------------------------------------------------+
```
- **时间位（41 bit）**：存储当前时间与固定起始纪元（Epoch）的毫秒差值，$2^{41}-1$ 毫秒 $\approx 69.7$ 年。
- **机器标识位（5 bit `DataCenterId` + 5 bit `WorkerId` = 10 bit）**：最多支持 $32 \times 32 = 1024$ 个节点，保证不同机器同一毫秒生成的 ID 绝对隔离。
- **毫秒内序列号（12 bit）**：单机每毫秒最多生成 $2^{12} = 4096$ 个 ID（理论单机峰值约 409.6 万/秒）。

##### 2. `WorkerID`（机器节点号）的四种分配方案
1. **配置文件硬编码**：仅适合机器极少且固定的传统部署，K8s 容器动态扩缩容下极易冲突。
2. **Redis `INCR` 取模分配**：启动时通过 `INCR snowflake:worker:id` 对 1024 取模或结合心跳续期租约抢占空闲编号。
3. **数据库机器注册表**：启动时以 `IP + Port / 容器 Hostname` 向 MySQL 表注册获取自增 ID。
4. **ZooKeeper 持久顺序节点 + 本机文件缓存（美团 Leaf 方案）**：启动时在 ZK 注册有序节点拿序号作为 `WorkerID`，并缓存到本地磁盘防止 ZK 短暂抖动导致启动失败。

##### 3. 最大痛点：时钟回拨（Clock Moved Backwards）五级防护方案
当服务器因 NTP 时间同步导致系统时间后退时，同一台机器会在重复的毫秒内生成重复 ID：
1. **微幅回拨（`offset <= 5ms`）**：直接 `Thread.sleep` 或自旋等待时间追平 `lastTimestamp` 后继续生成；
2. **中等回拨（`5ms < offset <= 100ms`）**：**借用历史最大时间戳（追赶模式）**——不取当前回退的系统时间，而是继续沿用 `lastTimestamp` 并递增 `sequence`（序列号满则将 `lastTimestamp + 1`），无阻塞度过回拨期；
3. **扩展回拨位（Bit 预留法）**：从 10 位机器码或 12 位序列号中划出 2 bit 作为“回拨计数器（0～3）”，每次发生回拨时将该计数器 `+1`，即便时间戳和序列号相同，回拨位不同也绝不冲突；
4. **大幅回拨（`offset > 100ms` 或重启回拨）**：自动向 ZK/Redis **更换新的 `WorkerID`**，或触发告警拒绝服务。

##### 4. 带时钟回拨小幅自旋保护的 Java 实现代码

```java
public class SnowflakeIdWorker {
    // 起始基准时间：2024-01-01 00:00:00
    private static final long START_EPOCH = 1704038400000L;

    private static final long DATA_CENTER_BITS = 5L;
    private static final long WORKER_BITS = 5L;
    private static final long SEQUENCE_BITS = 12L;

    private static final long MAX_DATA_CENTER_ID = ~(-1L << DATA_CENTER_BITS); // 31
    private static final long MAX_WORKER_ID = ~(-1L << WORKER_BITS);           // 31
    private static final long SEQUENCE_MASK = ~(-1L << SEQUENCE_BITS);         // 4095

    private static final long WORKER_SHIFT = SEQUENCE_BITS;
    private static final long DATA_CENTER_SHIFT = SEQUENCE_BITS + WORKER_BITS;
    private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + WORKER_BITS + DATA_CENTER_BITS;

    private final long dataCenterId;
    private final long workerId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public SnowflakeIdWorker(long dataCenterId, long workerId) {
        if (dataCenterId > MAX_DATA_CENTER_ID || dataCenterId < 0) {
            throw new IllegalArgumentException("DataCenterId out of range [0, 31]");
        }
        if (workerId > MAX_WORKER_ID || workerId < 0) {
            throw new IllegalArgumentException("WorkerId out of range [0, 31]");
        }
        this.dataCenterId = dataCenterId;
        this.workerId = workerId;
    }

    public synchronized long nextId() {
        long currentTimestamp = System.currentTimeMillis();

        // 1. 时钟回拨检测与分级处理
        if (currentTimestamp < lastTimestamp) {
            long offset = lastTimestamp - currentTimestamp;
            if (offset <= 5) {
                // 5ms 以内微幅回拨：等待追平
                try {
                    wait(offset << 1);
                    currentTimestamp = System.currentTimeMillis();
                    if (currentTimestamp < lastTimestamp) {
                        throw new RuntimeException("Clock moved backwards by " + offset + "ms");
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    throw new RuntimeException("Interrupted while waiting for clock sync", e);
                }
            } else {
                throw new RuntimeException("Clock moved backwards, refusing to generate id for " + offset + "ms");
            }
        }

        // 2. 同一毫秒内序列号递增
        if (currentTimestamp == lastTimestamp) {
            sequence = (sequence + 1) & SEQUENCE_MASK;
            if (sequence == 0L) {
                // 当前毫秒 4096 个序列号耗尽，自旋等待下一毫秒
                currentTimestamp = waitNextMillis(lastTimestamp);
            }
        } else {
            // 新的一毫秒，序列号重置（偶发低并发下为避免全是偶数影响分表均匀度，可用 currentTimestamp & 1L 起始）
            sequence = 0L;
        }

        lastTimestamp = currentTimestamp;

        // 3. 位运算拼接 64 位 ID
        return ((currentTimestamp - START_EPOCH) << TIMESTAMP_SHIFT)
                | (dataCenterId << DATA_CENTER_SHIFT)
                | (workerId << WORKER_SHIFT)
                | sequence;
    }

    private long waitNextMillis(long lastTs) {
        long ts = System.currentTimeMillis();
        while (ts <= lastTs) {
            ts = System.currentTimeMillis();
        }
        return ts;
    }
}
```

#### 三、美团 Leaf 双模式核心原理

1. **`Leaf-segment`（数据库号段模式 + 双 Buffer 预加载）**：
   - 数据库表 `leaf_alloc(biz_tag, max_id, step, update_time)` 按业务标识隔离，每次批量领取一个号段（如 `step = 1000`）；
   - **双 Buffer 优化**：Server 内存中同时维护 `SegmentBuffer[0]`（当前号段）和 `SegmentBuffer[1]`（备用号段）。当当前号段消费到 **10%** 时，立即触发后台异步线程去 DB 预加载下一个号段到备用 Buffer。当前号段耗尽时毫秒级无缝切换，彻底消除号段边界的 DB I/O 毛刺。
2. **`Leaf-snowflake`（ZK 增强雪花模式）**：
   - 利用 ZooKeeper 顺序节点自动分配 `WorkerID`，并定时上报当前时间戳；启动时对比本机时间与 ZK 上报时间，防止宕机重启期间发生时钟回退。

## 五、集合高频判重、空安全防护与线上报错定位

### 5.1 Set 与 Map 集合 contains() 底层判重机制与避坑

#### 一、三大 `Set` 与三大 `Map` 判重规则全景对比表

| 集合类型 | 底层数据结构 | 有序性 | `contains` / `containsKey` 判重依据 | 查询时间复杂度 | 自定义对象作为元素 / Key 的强制要求 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`HashSet` / `HashMap`** | 数组 + 链表 + 红黑树 | 无序 | 先比 `hashCode()`，相等再比 `equals()` | **$O(1)$** | **必须同时重写 `equals()` 和 `hashCode()`** |
| **`LinkedHashSet` / `LinkedHashMap`** | 哈希表 + 双向链表 | 保留插入顺序 | 先比 `hashCode()`，相等再比 `equals()` | **$O(1)$** | **必须同时重写 `equals()` 和 `hashCode()`** |
| **`TreeSet` / `TreeMap`** | 红黑树 | 自然排序 / 比较器排序 | **仅依赖 `compareTo()` / `compare() == 0`**（与 `equals/hashCode` 无关） | $O(\log n)$ | **必须实现 `Comparable` 接口或构造传入 `Comparator`** |

> ⚠️ **注意 `Map.containsValue(val)`**：无论哪种 `Map` 实现，`containsValue` 都需要全表遍历比对 `equals()`，时间复杂度为 **$O(n)$**，高并发链路严禁高频调用。

---

#### 二、两大核心避坑代码示例

##### 1. 自定义对象存入 `HashSet` / 作为 `HashMap` 的 Key（重写 `equals` & `hashCode`）

若未重写 `equals` 和 `hashCode`，默认继承 `Object` 按内存地址判重，会导致内容完全相同的两个对象被判定为不同 Key：

```java
public class UserKey {
    private Integer id;
    private String name;

    public UserKey(Integer id, String name) {
        this.id = id;
        this.name = name;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        UserKey userKey = (UserKey) o;
        return Objects.equals(id, userKey.id) && Objects.equals(name, userKey.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name);
    }
}
```

##### 2. 自定义对象存入 `TreeSet` / 作为 `TreeMap` 的 Key（提供比较规则）

若既未实现 `Comparable` 也未传入 `Comparator`，调用 `add`/`put` 时会直接抛出 `ClassCastException: cannot be cast to java.lang.Comparable`；且只要比较器返回 `0` 即被视为重复元素拒绝存入：

```java
// 方式 1：实体实现 Comparable 接口（多字段组合比较：先按年龄升序，年龄相同再按 ID 升序，防止年龄相同时被误判去重！）
public class Student implements Comparable<Student> {
    private Integer id;
    private Integer age;

    @Override
    public int compareTo(Student other) {
        int ageCmp = Integer.compare(this.age, other.age);
        return ageCmp != 0 ? ageCmp : Integer.compare(this.id, other.id);
    }
}

// 方式 2：构造 TreeSet 时传入外部 Comparator（推荐用 Comparator.comparing 链式写法）
TreeSet<Student> set = new TreeSet<>(
    Comparator.comparingInt(Student::getAge).reversed()
              .thenComparingInt(Student::getId)
);
```

### 5.2 空指针异常（NPE）优雅判空与防御规范

#### 一、按数据类型选择标准判空工具类（Spring / JDK 原生）

| 数据类型 | 推荐判空方法 | 源码判空逻辑与注意事项 |
| :--- | :--- | :--- |
| **`String` 字符串** | `StringUtils.hasText(str)`（推荐）<br>`StringUtils.hasLength(str)` | `hasText` 同时过滤 `null`、`""` 和纯空格 `"   "`；<br>注意 Spring 5.3+ 已弃用 `StringUtils.isEmpty(Object)` |
| **`Collection` (`List`/`Set`)** | `CollectionUtils.isEmpty(coll)` | `return coll == null \|\| coll.isEmpty();` |
| **`Map` 集合** | `CollectionUtils.isEmpty(map)` | `return map == null \|\| map.isEmpty();` |
| **任意对象 / 数组 / Optional** | `ObjectUtils.isEmpty(obj)` | 自动识别 `null`、`Optional`、`CharSequence`、`Array`、`Collection`、`Map` |
| **普通单对象引用** | `Objects.isNull(obj)` / `Objects.nonNull(obj)` | 适合在 `Stream.filter(Objects::nonNull)` 中作为方法引用使用 |

---

#### 二、`ObjectUtils.isEmpty()` 的边界陷阱与 `Optional` 链式判空

1. **包含 `null` 元素的非空集合陷阱**：
   `Collections.singletonList(null)` 的 `size()` 为 1，此时 `ObjectUtils.isEmpty(list)` 或 `CollectionUtils.isEmpty(list)` 会返回 **`false`**！若需校验集合是否“为空或元素全为 `null`”：
   ```java
   boolean allNull = CollectionUtils.isEmpty(list) || list.stream().allMatch(Objects::isNull);
   ```
2. **用 `Optional` 消灭多层嵌套 `if (obj != null)`**：
   ```java
   // ❌ 传统多层判空
   String city = "未知";
   if (user != null && user.getAddress() != null && user.getAddress().getCity() != null) {
       city = user.getAddress().getCity();
   }

   // ✅ Optional 优雅链式取值
   String city = Optional.ofNullable(user)
           .map(User::getAddress)
           .map(Address::getCity)
           .orElse("未知");
   ```
3. **自动拆箱 NPE 防御**：数据库查询统计或包装类字段参与算术运算/三目运算符时（如 `Integer count = mapper.selectCount(); if (count > 0)`），若返回 `null` 触发自动拆箱 `count.intValue()` 会直接抛 NPE。务必先判空或使用 `Optional.ofNullable(count).orElse(0) > 0`。

### 5.3 Java 根据报错堆栈快速定位问题根源（5 步排查法）

#### 一、异常堆栈标准阅读顺序（黄金法则）

很多人看报错只看最后几行或最外层包装异常，这是最常见的误区。正确阅读顺序：
1. **找最底层的 `Caused by:`**：当存在多层异常包装（如 `MyBatisSystemException -> PersistenceException -> SQLIntegrityConstraintViolationException`）时，**最底层的最后一个 `Caused by:` 才是真正的案发现场（Root Cause）**。
2. **找该 `Caused by` 块下的第一行本项目包名代码**：忽略 `org.springframework.*`、`java.lang.reflect.*`、`com.sun.proxy.*` 等框架代理栈帧，定位到第一行 `at com.yourcompany.biz.service.XxxService.method(XxxService.java:行号)`。

```text
org.mybatis.spring.MyBatisSystemException: nested exception is org.apache.ibatis.exceptions.PersistenceException
    at org.mybatis.spring.MyBatisExceptionTranslator.translateExceptionIfPossible(...)   <-- 框架包装层，跳过
    at com.biz.service.OrderService.createOrder(OrderService.java:88)                    <-- 业务调用入口
Caused by: java.sql.SQLIntegrityConstraintViolationException: Duplicate entry 'ORD1001' for key 'uk_order_no'
    at com.mysql.cj.jdbc.exceptions.SQLError.createSQLException(...)
    at com.biz.mapper.OrderMapper.insert(OrderMapper.java:22)                            <-- 【真正根因与出错点】
```

#### 二、七大高频异常速查表

| 异常类型 | 关键报错特征 | 根因与快速排查点 |
| :--- | :--- | :--- |
| **`NullPointerException`** | `Cannot invoke "Xxx.method()" because "obj" is null` (JDK14+ 精确提示) | ① DB/RPC 返回 `null` 未判空直接调方法；② `Map.get()` 返回 `null` 自动拆箱；③ 非 Spring 管理的 `new` 对象内部 `@Autowired` 为 `null` |
| **`IndexOutOfBoundsException`** | `Index 0 out of bounds for length 0` | 未判空直接调用 `list.get(0)` |
| **`ClassCastException`** | `A cannot be cast to B` | 泛型擦除（如 Redis 反序列化成 `LinkedHashMap` 强转实体类）、不同 ClassLoader 加载同名类 |
| **SQL 异常** | `Duplicate entry` / `Data truncation` / `BadSqlGrammarException` | 唯一索引冲突 / 字段长度超限 / 表名列名拼写错误或动态 SQL `<where>` 拼接语法错误 |
| **网络 / IO 异常** | `ConnectException: Connection refused`<br>`SocketTimeoutException: Read timed out` | `Connection refused`：下游服务未启动、IP/端口错或防火墙拦截；<br>`Read timed out`：下游接口慢查询或死锁超时 |
| **Spring 容器异常** | `NoSuchBeanDefinitionException`<br>`BeanCurrentlyInCreationException` | 漏加 `@Service` / 包扫描路径未覆盖；<br>构造器循环依赖或 AOP 代理循环依赖 |
| **`Error`（严重错误）** | `OutOfMemoryError: Java heap space`<br>`StackOverflowError` | 堆内存溢出（一次性查百万行大对象、内存泄漏）或无终止条件的无限递归调用 |

#### 三、日志打印与异常处理的四大禁忌

1. **严禁只打印 `e.getMessage()` 丢弃堆栈**：
   - ❌ 错误：`log.error("下单失败: {}", e.getMessage());`（完全丢失行号和 `Caused by` 链条，线上无法排查）
   - ✅ 正确：`log.error("下单失败, orderNo={}", orderNo, e);`（将 `Throwable` 作为最后一个参数传入）
2. **严禁空的 `catch` 块或吞掉原始异常**：捕获后若需向上抛出自定义业务异常，应保留 `cause`：`throw new BizException("下单失败", e);`。
3. **异步线程池异常静默丢失**：`ThreadPoolExecutor.submit()` 提交的任务若未调 `.get()` 且内部未 `try-catch`，异常会被吞在 `FutureTask` 内部。必须在 Runnable 外层统一 `try-catch` 打印日志。
4. **活用 IDEA `Analyze Stack Trace`**：复制线上报错堆栈，打开 IDEA 菜单 `Code -> Analyze Stack Trace or Thread Dump`，即可像本地控制台一样一键点击蓝字跳转到对应代码行。

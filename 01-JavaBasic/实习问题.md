# Java接口长时间不响应（接口hang住、超时、无返回）根因与完整排查方案

现象：前端/调用方请求发出去，接口**没有返回结果，不报错，不抛异常，长时间卡住，最后调用方超时断开**；日志没有error，线程卡死。

> 区分：
>
> 1. **报错超时**：代码抛异常、数据库慢查询；
> 2. **长时间无响应（hang）**：线程卡住，方法没有走完，没有输出返回值，线程处于WAITING / BLOCKED。

## 一、常见根因分类

### 1. 线程阻塞（最常见！Tomcat/Biz线程卡住）

1）**锁竞争死锁、synchronized / ReentrantLock 拿不到锁**，线程B等线程A释放锁，线程A也等待B，互相等待死锁；或者某一个线程持有锁长时间不释放，其他请求全部排队等待。 2）**外部同步IO阻塞**：调用第三方HTTP接口、RPC、Socket，**没有设置超时时间**。`httpClient / restTemplate / dubbo调用没有超时`，对方服务不返回，当前线程就一直卡在等待响应。 3）数据库JDBC阻塞：

- 获取数据库连接拿不到，连接池耗尽（maxActive满，全部连接被占用没有归还）；
- SQL执行本身很慢（慢SQL）； 4）CountDownLatch、CyclicBarrier、Object.wait()，代码里面做线程等待，条件永远不满足，线程永久WAITING。

### 2. 线程池耗尽

- 自定义线程池没有设置核心参数，队列无限大；

- Tomcat业务线程池全部耗尽，新的请求进来，没有工作线程处理请求，接口直接挂住。

  > Tomcat默认maxThreads 200，如果全部线程卡住，新请求直接排队，不进controller代码。

### 3. JVM层面原因

1）**Full GC长时间STW**：STW停顿时间几十秒，所有Java应用线程全部暂停，接口完全不响应；GC日志看不到业务日志输出。 2）OOM：堆内存耗尽，频繁GC，线程无法正常执行。

### 4. 业务代码死循环

`while(true)` 循环没有退出条件，CPU 100%，这个业务线程死循环跑，永远执行不到return；CPU使用率飙升。

### 5. 资源耗尽

文件句柄耗尽；网络socket连接泄露，不关闭流。

### 6. 中间件阻塞

redis操作没有超时；kafka同步发送阻塞。

------

## 二、全套排查步骤（生产实操顺序，从易到难）

### ✅步骤1：确认现象

1. 看access日志/Nginx日志：请求是否到达Java服务；
   - 如果Nginx收到请求，Java没有打印controller入参日志 → **请求没进入业务代码，大概率tomcat线程池满 / STW /网络问题**
   - 如果已经打印controller入参日志，但是没有打印出参日志 → 代码内部hang住。

### ✅步骤2：拿到Java线程堆栈，最核心手段 `jstack`

> 接口卡住的时候**实时抓堆栈，不要等服务恢复后再抓，恢复之后堆栈信息就消失！**

```
# 获取java进程pid
jps -l

# 输出线程栈到文件
jstack 进程pid > thread.txt
```

分析thread.txt重点看：

1. 大量线程状态为 `WAITING` / `BLOCKED`
2. 查找业务代码行号，看线程卡在那一行代码：

- 卡在 `Object.wait` / `AQS.await`：等待锁、CountDownLatch
- 卡在 http / socket / netty：第三方IO调用没有超时
- 卡在JDBC：拿数据库连接，或者执行SQL
- 搜索 `deadlock`，直接检测死锁

> IDEA也可以使用dump线程，线上服务器优先jstack。

### ✅步骤3：看GC日志，排查STW停顿

```
jstat -gc pid 1000
```

观察：

- FGCT full gc累计时间，单次FullGC时间是否很大； 如果发生长时间STW，业务接口全部停止响应。 打开GC日志文件，看停顿时间。

### ✅步骤4：查看CPU负载

```
top
# 看哪个线程占用CPU高
top -Hp pid
printf "%x\n" 线程号  #转16进制，去jstack里面搜索该线程
```

- CPU100%：大概率死循环；
- CPU很低但是接口hang住：**线程阻塞等待锁/IO，90%是这个情况**。

### ✅步骤5：数据库 & 连接池排查

1. 查看数据库连接池监控（druid监控页面）：

- active活跃连接数是否等于最大连接数，连接是否没有归还；

  > 如果连接拿不到，所有请求卡在获取连接那一步。

1. 查看数据库慢SQL日志，确认是否SQL执行时间超长。

### ✅步骤6：检查所有外部调用是否配置超时

- RestTemplate / HttpClient / OkHttp 是否设置connectTimeout、readTimeout

- Dubbo、Feign是否配置调用超时时间

  > 不设置超时，下游挂了，当前线程永久hang住。

### ✅步骤7：检查线程池

1. Tomcat线程池：活跃线程数是否打满；
2. 自定义线程池，看队列、活跃线程，有没有任务堆积。

### ✅步骤8：看文件句柄数

```
lsof -p pid | wc -l
```

判断是否打开文件、socket过多，达到系统上限。

## 三、典型案例对照

1. jstack看到大量线程卡在http请求：第三方调用**缺少超时时间**
2. jstack大量BLOCKED，提示waiting to lock xxx对象：锁竞争，某线程持有锁没有释放
3. jstack看到大量线程卡在getConnection()：数据库连接池耗尽
4. GC日志单次STW 15s以上：FullGC停顿，整个服务暂停
5. CPU持续100%，jstack某个业务线程一直在执行循环代码：死循环

## 四、预防优化手段

1. **所有外部调用必须强制设置超时时间（HTTP、RPC、Redis），不能无限等待**
2. 锁使用尽量缩小范围，不要长业务逻辑持有锁；使用tryLock带超时，不要无限lock()
3. 线程池一定要配置最大线程，拒绝策略，不要用Executors默认方法
4. 数据库连接池配置maxActive，监控活跃连接数
5. 开启GC日志，线上保留dump配置；开启druid监控
6. 接口加统一全局超时控制，增加日志埋点：进入方法打印日志，退出打印日志，可以定位卡在哪一行。

### 埋点小技巧快速定位哪段代码卡住

```
log.info("查询PMS开始");
// 业务逻辑
log.info("查询PMS结束");
```

如果日志只打印开始，没有打印结束，说明代码hang在两行中间。

# traceId & msgId 完整使用场景汇总

## 一、基础定义区分
1. **traceId（链路追踪ID）**
    一次完整业务请求/任务全链路唯一标识，用于串联整条调用流程，**全场景日志必须携带**。
2. **msgId（消息唯一ID）**
    单条独立报文/事件的专属标识，用于区分单条消息、幂等、丢失/重复排查，**仅存在独立消息载体时才生成并打印**。

## 二、traceId 全量使用&打印场景（所有场景必输出）
### 1. 同步调用场景
- 网关接收HTTP请求入口、接口全局拦截器
- Controller、Dubbo暴露服务入口
- Feign/Dubbo调用第三方服务前后日志
- 数据库CRUD、Redis缓存读写、第三方同步接口调用
- 全局异常捕获、业务报错、超时告警日志

### 2. 普通异步线程（无消息实体）
- @Async 异步方法、自定义线程池单纯执行业务逻辑
- XXL-Job/Quartz定时任务启动与执行日志
- 单纯异步更新积分、异步发送短信（无封装消息对象）

### 3. MQ消息全链路（生产者+消费者）
- MQ发送前、发送成功/失败日志
- 消费者消费入口、业务处理、异常、重试、死信日志
- 消息事务提交/回滚、消息拦截过滤日志

### 4. 本地事件/内存队列
- Spring Event事件发布、监听处理
- 自建阻塞队列、内存事件队列消费日志

### 5. 外部异步推送回调
- 支付回调、第三方系统异步推送报文处理日志

### traceId统一规则
1. 请求入口/定时任务起点生成；
2. 通过Header、附件、消息头、MDC透传到所有下游；
3. 所有级别日志（INFO/WARN/ERROR）强制打印，不可缺失。

## 三、msgId 使用&打印场景（仅存在独立消息载体时）
### 1. 中间件MQ相关（最常用）
- MQ生产者发送消息、发送失败/重试日志
- MQ消费者消费、消费异常、自动重试日志
- 消息进入死信队列、死信重处理、消息事务半消息提交/回滚
- 消息拦截过滤、消息堆积监控告警、人工补发消息操作日志
- 消息幂等校验、消息对账补偿定时任务

### 2. 本地自建异步消息队列
- 内存阻塞队列、本地事件队列封装独立Event对象，入队、出队消费日志
- Spring自定义事件总线，每条事件分配唯一msgId

### 3. 外部系统异步推送报文
- 微信/支付宝/银行支付回调报文
- 第三方系统主动推送HTTP报文、WebSocket上下行消息
- 外部异步通知类报文解析、异常处理日志

### 4. 文件/批量离线报文
- 批量导入导出、离线数据同步，单条业务记录生成msgId
- 短信、站内信批量推送，单条通知独立msgId

### 5. 不需要 msgId 的场景（禁止打印）
- 普通HTTP/Dubbo同步接口纯业务逻辑
- @Async单纯异步执行代码、无封装消息实体
- 纯定时任务无单条报文，仅批次处理
- 单纯DB、Redis、同步第三方接口调用

## 四、两者共存/单独打印区分标准
1. **只打印 traceId，无 msgId**
    同步接口、普通异步线程、纯定时任务、缓存/数据库操作，无独立消息载体。
    日志示例：`traceId=xxx 执行更新用户余额`

2. **traceId + msgId 同时打印**
    MQ收发、本地事件队列、第三方异步回调、文件单条报文处理。
    日志示例：`traceId=xxx,msgId=xxx 消费库存扣减消息`

## 五、核心使用原则总结
1. traceId：**全覆盖**，只要属于同一业务链路，所有日志必带；
2. msgId：**按需生成**，只有出现独立、可单独丢失/重复/重试的消息报文时才生成并打印；
3. 排查分工：
    - traceId：查整条业务链路完整调用流程，定位上游来源；
    - msgId：精准定位某一条异常消息，用于幂等、对账、消息丢失核对。
